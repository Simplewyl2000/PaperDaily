## 📝 逐条讲解

### Cloudflare Vulnerability Harness：把安全审计 skill 扩成多阶段漏洞发现流水线
很多安全 coding agent demo 停留在“让模型扫一个仓库并写报告”，但生产环境的难点在误报过滤、跨仓库可达性、结构化交付和可恢复执行。Cloudflare 这篇文章把他们的 Vulnerability Discovery Harness 拆开讲：先从一个约 450 行的 `security-audit` skill 开始，把攻击场景、漏洞类别和反模式写清楚，再逐步扩成多阶段系统。公开 skill 里的流程包括 recon、hunt、validate、report、structured output 和 independent verification，每个发现不仅要有人类可读报告，还要写成符合 schema 的 `findings.json`。更关键的是，发现者和验证者不是同一个 agent，验证阶段的目标是尽力推翻原发现，这能显著压低“看起来像漏洞”的噪声。Cloudflare 还提到后续生产 harness 覆盖 128 个仓库，并通过数据库和编排器把 skill 中的阶段一一提升成可恢复 pipeline。它对后训练软件工程的价值在于：安全 agent 训练数据不能只保存“发现了什么”，还要保存攻击面建模、候选发现、反证失败、结构化证据和跨仓库 trace。这个模式也说明 skill 可以是大规模 harness 的种子，而不只是一个提示词文件。
🔗 链接：https://blog.cloudflare.com/build-your-own-vulnerability-harness/ ｜ 代码：https://github.com/cloudflare/security-audit-skill

### Step Rejection Fine-Tuning：从失败 agent 轨迹中只屏蔽坏步骤
传统 Rejection Fine-Tuning 通常只保留成功轨迹，失败轨迹整条丢掉；在复杂 coding agent 任务里，这会浪费大量已经花钱生成的工具使用和代码阅读过程。JetBrains Research 的 SRFT 观察到，失败轨迹并不等于每一步都坏，很多失败 run 里仍包含正确的目录探索、相关文件阅读、测试脚本尝试和后续恢复动作。它的做法很工程化：用一个 critic 模型按步骤标注 good、unnecessary、mistake、recover 等标签，然后训练时只对有害步骤做 loss masking，而不是把整条轨迹删除或重新合成一条“干净轨迹”。这样学生模型仍然能看到完整上下文，包括错误发生后如何恢复，但不会被训练去复现错误动作。实验基于 SWE-smith trajectories 和 SWE-bench Verified，标准 RFT 为 30.9%，SRFT 提升到 32.2%；只用失败轨迹但屏蔽坏步骤也能达到 29.7%，超过天真混合失败/成功轨迹。它对 trajectory selection 很重要，因为筛选粒度从“整条成功/失败”推进到“步骤级可训练/不可训练”。落地时最值得复用的是 critic 标注、step mask、恢复步骤保留和对 critic 严格度的调参闭环。
🔗 链接：https://blog.jetbrains.com/research/2026/06/step-rejection-fine-tuning/ ｜ 代码：https://arxiv.org/abs/2605.10674

### SWE-Future：用仓库演化预测来合成未来导向 coding-agent 任务
许多 coding-agent benchmark 直接重放历史 GitHub issue 或 PR，这样任务更真实，但也更容易和模型预训练、合成数据、调参过程发生重叠。完全 synthetic 的任务可以避开污染，却常常不像真实仓库会发生的工作。SWE-Future 试图折中：在时间点 `T0` 只读取当时以前的仓库证据，先预测未来可能出现的 feature、bugfix、refactor 任务族，再用后来真实 PR 只验证预测方向是否靠谱，而不把那些 PR 直接改写成任务。论文在 80 个仓库上做回溯验证，主语义匹配指标下 future-work relevance 为 58.1%，然后基于验证过的任务族合成 200 个 coding-agent 任务，覆盖 61 个仓库。这个方法的新意不是简单“从仓库生成题”，而是把“预测真实未来需求”作为条件信号，让任务既贴近真实演化，又减少直接 replay 历史补丁的污染风险。对后训练数据工程来说，它提供了一个很有价值的 anti-contamination 思路：训练/评测任务可以来自仓库演化模型，而不是只来自已发生的公开 PR。未来如果配合自动 verifier 生成和 live benchmark，就能形成更稳定的滚动任务生产线。
🔗 链接：https://arxiv.org/html/2606.18733v1 ｜ 代码：None

### sandboxd：给 AI app-builder 提供自托管多租户 dev sandbox 与 preview URL
很多 AI app-builder 或 coding-agent SaaS 表面上是 prompt 和模型产品，真正难的是底层执行环境：每个用户都要有隔离 workspace、能跑 dev server、能分享 preview URL、空闲时释放资源，还不能让一个用户的代码影响另一个用户。sandboxd 把这些基础设施压成一个自托管控制面：用 Docker 创建隔离 Linux 容器，用 Traefik 自动路由 preview URL，用 SQLite 记录状态，并提供 HTTP API 创建 sandbox、运行命令、写文件和启动 headless coding-agent task。它还内置 OpenCode 与 Claude Code CLI，任务进度通过 Server-Sent Events 流式输出，sandbox 空闲会 stop、下次访问 preview URL 时再 wake。这个项目的工程价值在于它承认“agent 能写代码”只是产品的一半，另一半是多租户隔离、preview、成本控制和可恢复 state。README 也很坦诚地说明 v1 适合团队或产品原型，不适合直接运行不可信陌生人代码，真正生产还要补 VM/gVisor/Kata、API auth、egress logging 等硬化层。对 Agent-Friendly Software 来说，sandboxd 是把传统 dev environment 做成 agent 可调用 API 的典型例子。后训练/评测平台也能借鉴它的 create -> run-agent-task -> preview -> sleep/wake 控制流来批量跑真实软件任务。
🔗 链接：https://github.com/tastyeffectco/sandboxd ｜ 代码：https://github.com/tastyeffectco/sandboxd

### Canary：把 coding agent 的 UI QA 变成可回放 Playwright 证据包
前端和产品型任务里，agent 说“我测试过了”通常很难让 reviewer 放心，因为浏览器里到底点了什么、网络请求发生了什么、控制台有没有报错，常常只剩一段自然语言总结。Canary 的思路是把 agent-driven UI QA 变成可审计 artifact：agent 仍然用自然语言规划测试流程，但执行发生在 QuickJS WASM sandbox 中，通过 Playwright API 控制真实浏览器。每次 run 会自动产出 video、screenshots、console logs、network HAR、Playwright trace、`results.json` 和自包含的 `report.html`。更重要的是，它把 agent 发现的交互过程保存成可复用 Playwright script，之后可以在 CI 中零推理成本重放，而不是每次都让模型重新探索页面。这个设计解决了 agent QA 的两个痛点：一边避免纯 agent run 的黑盒不可复现，一边避免手写 E2E 脚本的高维护成本。它还给 Claude Code、Cursor、Codex 做了 plugin/skill/subagent 集成，使 QA harness 可以成为 coding agent 的自然工具。对评测工程来说，这类“证据包 + 可回放脚本”的输出格式很适合进入 agent 轨迹数据，帮助判断失败是 UI 探索、等待策略、断言缺失还是代码本身问题。
🔗 链接：https://github.com/wizenheimer/canary ｜ 代码：https://github.com/wizenheimer/canary

### CodeSeek：面向 Claude Code / Codex 的 Rust 代码智能 CLI + MCP
大仓库 coding agent 的一个常见失败原因不是模型不会写补丁，而是它找不到正确上下文，或者在全文搜索、语义搜索、调用关系之间来回浪费 token。CodeSeek 把代码理解做成一个本地 CLI 和 MCP 工具：先用 tree-sitter 解析 7 种语言，抽取函数、类和方法，再构建 call graph、dense embedding 索引、Tantivy BM25 索引和 LanceDB 向量库。查询时它会融合 dense search 与 sparse search，用 Reciprocal Rank Fusion 合并候选，再用 Qwen3-Reranker 做精排；没有 embedding 或 reranker 时，也能退回图结构名称搜索。所有查询命令支持 `--json`，并可通过 `codeseek serve --mcp` 暴露给 Claude Code / Codex 这类 agent。它不是顶级机构发布，当前 star 也不算特别高，所以可信度要谨慎；但它击中了 agent-friendly code retrieval 的真实痛点。对后训练软件工程来说，代码检索工具不只是 inference-time 增强，也会改变轨迹形态：agent 先问 call graph、再问语义候选、再编辑文件，这和裸 `rg`/读文件轨迹完全不同。未来做评测时应单独记录 retrieval precision、reranker 结果和图查询命中，否则 pass rate 里会混入大量上下文接口差异。
🔗 链接：https://github.com/CodeBendKit/codeseek ｜ 代码：https://github.com/CodeBendKit/codeseek

### Qwen open-computer-use：跨平台 accessibility computer-use MCP server
Computer Use 的常见实现依赖屏幕截图和坐标点击，但真正落地时会遇到权限、跨平台 API、坐标缩放、截图大小和操作可诊断性等细节。QwenLM 的 `open-computer-use` 把这件事做成 MCP server，面向 Qwen Code 和任意 MCP client，支持 macOS、Windows、Linux，通过 accessibility / UI Automation / AT-SPI 等平台能力控制桌面软件。它提供 9 个 Computer Use tools，并把 accessibility tree 与 screenshot 组合返回；macOS 上还提供截图超时、PNG 字节预算、最大边长和最小缩放等环境变量，避免把过大的图片塞进上下文。项目还保留坐标精度映射，确保模型在下采样图像上给出的坐标能映回真实窗口。这个方向非常符合 Agent-Friendly Software：如果某个软件短期无法 CLI 化或 API 化，至少要把 GUI 操作包装成标准化、可诊断、可授权的工具层。它的价值不只在 Qwen，而在跨平台 computer-use MCP 的工程接口设计，包括 doctor、snapshot、list-apps 等诊断命令。后续需要继续观察权限边界、危险动作审批、窗口状态漂移和日志回放能力。
🔗 链接：https://github.com/QwenLM/open-computer-use ｜ 代码：https://github.com/QwenLM/open-computer-use

### Ponytail：用可复现实验约束 coding agent 过度工程化
Coding agent 经常把一个简单需求做成组件库、依赖安装、复杂抽象和过量配置，这种“过度工程化”会增加维护成本，也会让 review 更难。Ponytail 的做法不是简单提示“少写点代码”，而是给 agent 一个决策 ladder：先理解真实代码路径，再选择满足需求的最小实现层级，同时明确不能削掉安全、可访问性、数据丢失处理和信任边界验证。项目最引人注意的是高热度和可复现实验：README 报告在真实 Claude Code sessions 中编辑 FastAPI + React 开源仓库，12 个 feature tickets、Haiku 4.5、n=4，对比无 skill baseline，平均 LOC 减少 54%、token 减少 22%、成本减少 20%、时间减少 27%，安全保持 100%。它还提供 `/ponytail-review`、`/ponytail-audit`、`/ponytail-debt`、`/ponytail-gain` 等命令，能审查当前 diff 或全仓库中的过度工程化。虽然它是社区项目，实验还需要外部复核，但 67k+ stars 和多 agent 适配说明痛点非常强。对 skill management 来说，Ponytail 展示了一个好方向：skill 不只是风格偏好，而应配套 benchmark、可复现实验和安全边界说明。对训练数据筛选来说，“少写但不偷工减料”的轨迹也是值得区分的高价值样本。
🔗 链接：https://github.com/DietrichGebert/ponytail ｜ 代码：https://github.com/DietrichGebert/ponytail

### ModSleuth：用证据约束 agent pipeline 审计模型依赖图
现代 LLM 的依赖关系越来越复杂：一个模型可能蒸馏自多个老师、混合多个数据集、继承某些生成器或过滤器，但这些关系常常散在技术报告、博客、model card 和 release note 里。ModSleuth 不是 coding benchmark，而是把“审计模型依赖图”做成证据约束的 agentic pipeline。它把 discovery 和 normalization 分开：第一阶段保留局部提法和上下文，第二阶段再做规范化实体合并；每条依赖 claim 必须有公开来源证据并经过验证，才能进入图谱。论文用 Claude Code 作为 agentic harness，对比单 prompt Claude Code、ChatGPT Deep Research、GPT-5.5 Pro 等 baseline，报告 unbounded 设置下恢复 1,654 条 verified relationships，显著超过单轮或浅层 agent。它对本日报的间接价值在于 provenance engineering：当 agent 需要构建可信研究/数据资产时，必须把证据、归一化、验证和冲突处理分阶段，而不是让模型一次性“总结”。对后训练数据工程也有启发，因为模型/数据依赖审计将直接影响污染判断、训练数据来源追踪和 benchmark 泄漏分析。它按 Medium 收录，因为主题不是软件工程任务本身，但方法论很适合证据驱动的 agent pipeline。
🔗 链接：https://arxiv.org/html/2606.12385v1 ｜ 代码：None

### Omnigent：跨 Claude Code / Codex / Cursor 的开源 meta-harness
随着 Claude Code、Codex、Cursor、OpenCode、Pi、Hermes 等 agent surface 同时存在，团队很容易被具体工具锁住：某个任务在哪个 harness 跑、谁能看、权限怎么控、能不能换模型和沙箱，都变成碎片化问题。Omnigent 的定位是 meta-harness，也就是在多个 agent 之上提供共同编排层。它支持在同一 session 里混用 Claude Code、Codex、Cursor、OpenCode 和自定义 YAML agent，让一个 agent review 另一个 agent 的工作，或者按模型和工具特长拆分任务。README 还强调跨设备协作、共享 session、团队 co-drive、云端 disposable sandboxes，以及 server/agent/chat 级别 policies，用来暂停高风险动作、限制工具或控制花费。它仍是 alpha，不能把 5.4k stars 等同于生产成熟度；但它代表一个很强的社区方向：agent 平台竞争正在从单个 CLI 转向“多 harness 编排 + 治理 + 协作 UI”。对后训练和评测来说，meta-harness 会让轨迹更复杂，因为同一任务可能包含多个 agent 的分工、互评和交接。未来如果这类系统成熟，数据格式需要记录 agent identity、handoff、policy gate 和 sandbox backend。
🔗 链接：https://github.com/omnigent-ai/omnigent ｜ 代码：https://github.com/omnigent-ai/omnigent

### BuilderIO Skills：把规划、复盘、watchdog 和 docs discipline 做成可组合 agent skills
很多团队已经开始给 coding agent 写 skills，但 skills 容易变成一堆个人提示词，缺少安装方式、作用边界和协作约定。BuilderIO 的 `skills` 仓库把技能拆成小而组合的单元，重点放在 agent judgment 相关的环节：规划、复盘、验证、文档纪律、跨 agent handoff 和清晰沟通。比如 `/visual-plan` 把普通文本计划变成带图、文件地图、开放问题和交互 review surface 的 MDX；`/visual-recap` 把 branch/commit/PR diff 转成交互式 recap；`/agent-watchdog` 可以从 Codex session、Claude Code transcript、PR 或 run summary 中重建任务并检查实际改动和验证缺口。它还提供 `/plan-arbiter` 比较多个 agent 方案，输出胜出或混合计划、被拒绝方案和验证门。工程上比较值得注意的是安装路径：支持共享 `.agents`、Claude Code native skills、Codex/Pi/Cursor/OpenCode/GitHub Copilot 等 agent，并可加 managed `AGENTS.md` / `CLAUDE.md` instruction blocks 或 PR Visual Recap GitHub Action。它按 Medium 收录，因为更像工具集合而非受控实验，但它说明 skill management 正在从“提示词分享”走向“可安装、可更新、可审查的工作流插件”。对后训练软件工程来说，这些 skill 产生的计划、复盘和 watchdog 报告也可能成为高质量过程监督数据。

### Dao Code：围绕 DeepSeek V4 prefix cache 设计低成本 terminal coding agent
前沿 coding agent 的问题不只是能力，也包括成本和可用性：长程任务会消耗大量上下文，企业或个人用户很容易被高价模型和缓存失效拖垮。Dao Code 以 DeepSeek V4 为核心，重点不是发明新 agent 形态，而是把 terminal coding agent 的 runtime 围绕 prefix cache、memory、reflection 和审批门重新设计。README 报告在 7 个真实 OSS bugfix 任务上输入 388.6 万 tokens、总体 cache hit 95.8%，按 DeepSeek V4 Pro 价格总成本约 1.07 元人民币，并对比同一 token trace 下 Opus / Sonnet 的官方价格倍数。它通过 byte-stable system prefix、cache-reusing forks、启动时自验证 memory、failure streak challenger、定期 refocuser 和自动 compaction 来控制长任务漂移与缓存破坏。评测方面，它提到 SWE-bench-style real OSS tasks，使用 fail2pass / pass2pass 双轨验证，并把隐藏测试在 run 后注入以减少 reward hacking。可信度需要谨慎，因为这是社区项目且评测规模较小；但它很好地体现了 agent runtime 的成本工程方向。对生产平台来说，未来每个 agent run 都应像 Dao Code 这样报告 cache hit、实际花费、权限决策、长上下文压缩和隐藏测试策略。

## 🔥 社区热点专栏

### 🔥 大佬观点

**Cloudflare 安全团队：真正持久的资产是 harness，不是某一个模型。**  
Cloudflare 在 vulnerability harness 文章里反复强调，模型可以替换，真正需要工程化的是 recon、hunt、validate、trace、report、数据库状态和反证机制这些 harness 层。这个观点值得注意，因为它把“安全 agent”从单次提示词变成了可恢复、可审计、可跨仓库扩展的生产系统。🔗 https://blog.cloudflare.com/build-your-own-vulnerability-harness/

**JetBrains Research / Igor Slinko：失败轨迹不是垃圾，坏步骤才是噪声。**  
SRFT 的核心观点是，失败 agent run 里仍然有大量正确探索和恢复行为；直接丢掉整条轨迹会浪费最昂贵的工具交互数据。它值得关注，因为这正好对应 Code LLM 后训练的核心瓶颈：训练数据筛选要从 outcome-level 走向 step-level。🔗 https://blog.jetbrains.com/research/2026/06/step-rejection-fine-tuning/

### ⭐ 超火仓库/项目

**DietrichGebert/ponytail：67k+ stars 的“反过度工程化” coding-agent skill。**  
它火在把一个普遍痛点说清楚并给出实验：agent 经常写太多、抽象太早、装太多依赖，而 Ponytail 用 skill + hooks + benchmark 让 agent 优先选择最小可行实现。真正的 insight 是“少写代码”不能牺牲安全和验证，好的 skill 要把简洁性与 guardrails 一起编码。🔗 https://github.com/DietrichGebert/ponytail

**omnigent-ai/omnigent：5.4k+ stars 的跨 agent meta-harness。**  
Omnigent 火在抓住了多 agent 工具碎片化问题：团队已经同时用 Claude Code、Codex、Cursor、OpenCode 等，但缺共同 session、策略、沙箱和协作层。它解决的真实痛点是把 agent 从个人 CLI 提升为可治理、可分享、可混合模型的团队控制面。🔗 https://github.com/omnigent-ai/omnigent

**BuilderIO/skills：2.9k+ stars 的可组合 agent skill 集合。**
