## 📝 逐条讲解

### Claude Science：把科研数据库、代码执行、HPC 和可追溯 artifact 做成 agent workbench
很多科研 agent demo 只展示“模型能回答论文问题”，但真实科研工作更像一条长流水线：查文献、找数据库、写脚本、跑分析、画图、复核引用、再把结果整理成可复现材料。Anthropic 6 月 30 日发布的 Claude Science 把这些碎片工具收进一个 workbench，而不是发布一个新模型。它可以查询 60+ 科学数据库，执行 Python、R 和 shell 脚本，连接本地机器、SSH/HPC login node 和 Modal 计算资源，并把 genomics、single-cell、proteomics、structural biology、cheminformatics 等领域工具预配置好。最值得关注的是 provenance 设计：图、表、notebook 和科学 artifact 都带有生成它们的代码、环境和完整消息历史，后台 reviewer 还会检查引用、数字和图是否能追溯。工程上这和 coding-agent harness 很相似，只是对象从软件仓库换成了科研数据与计算环境。它说明 Agent-Friendly Software 的核心不是“给模型一个聊天框”，而是把传统领域工具、数据权限、计算资源、artifact lineage 和复核机制做成可调用、可审计的工作面。对后训练软件工程的启发是，优质轨迹应保存环境、命令、数据版本、产物 provenance 和 reviewer 反馈，而不是只保存最终回答。
🔗 链接：https://www.anthropic.com/news/claude-science-ai-workbench ｜ 代码：None

### CodeEvo：双 agent + schema + 编译反馈合成 CodeEvo-100K 代码数据
代码模型后训练最缺的不是“更多题”，而是逻辑自洽、难度可控、能被验证的指令-代码数据。很多自动合成方法靠模板或简单变异，容易生成重复、过浅或根本不可执行的样本。CodeEvo 把数据合成设计成两个 agent 的协作：Reviewer 先用 schema 规划题目的逻辑、约束和复杂度，Coder 再迭代生成解法与测试，Reviewer 根据结果继续调整生成方向。质量控制不是只靠模型打分，而是把编译器、运行反馈和语义评价结合起来，让错误尽早被挡在数据集外。论文发布 CodeEvo-100K，并报告用这些数据微调的模型在代码生成 benchmark 上显著超过传统合成基线，且“更好的合成算法”比单纯堆数据量更关键。它对本日报最核心的数据工程方向很直接：后训练数据 pipeline 应该有题目设计、执行验证、难度分层、失败过滤和质量反馈闭环。即使它不是多轮 coding-agent 轨迹，也为 Code LLM 的可扩展数据构造提供了可复用骨架。
🔗 链接：https://aclanthology.org/2026.acl-long.438/ ｜ 代码：https://github.com/QiushiSun/CodeEvo

### TrajAudit / RootSE：自动定位 coding-agent 轨迹里的最早决定性错误
现在许多 coding-agent 评测只给一个最终 pass/fail，失败之后人类要翻几百步工具调用、日志和补丁才能知道 agent 到底从哪里走偏。TrajAudit 关注的就是这个生产痛点：失败轨迹太长、噪声太多、人工诊断太慢。它用一个 investigator agent 做根因分析，但在让模型读轨迹前先用 pattern matching 和关键词过滤去掉明显无关信息，再从测试失败报告里生成初步诊断作为 prior。作者还构造 RootSE benchmark，包含 93 个真实软件维护任务失败实例、4,500+ 执行步骤和约 2700 万字符，用来评测“最早决定性错误点”定位。实验显示 TrajAudit 相比强 baseline 定位准确率提升超过 24.4 个百分点，同时 token 消耗至少降低 18%。它的价值不只是帮人 debug 一次失败，而是把失败轨迹变成可标注、可分类、可复盘的训练资产。对 trajectory selection 来说，这类工具可以区分“检索走错”“测试理解错”“补丁方向错”“恢复动作失败”，避免把整条失败轨迹粗暴当成负样本。
🔗 链接：https://arxiv.org/html/2605.26563 ｜ 代码：None

### CodeTracer / CodeTraceBench：4,316 条轨迹的步骤级错误/无用动作诊断集
Agent 轨迹里有两类常见噪声：一种是明确错误动作，另一种是不一定错但浪费上下文和时间的无用动作。CodeTracer 把这两类都做成步骤级诊断标签，并把工具本身设计成能在轨迹环境中继续查证证据的 autonomous diagnosis agent。配套的 CodeTraceBench 包含 4,316 条轨迹，其中 verified split 有 1,000 条人工校验样本，覆盖 SWE-bench 与 TerminalBench，以及 mini-SWE-agent、OpenHands、Terminus2、SWE-agent 等 4 个 agent 和 Claude Sonnet 4、DeepSeek-V3.2、Kimi-K2、GPT-5、Qwen3-Coder 等 5 类模型。它不只给 solved 标签，还记录 step、difficulty、incorrect/unuseful annotations 和可解释 root-cause chain。工程价值在于，后训练团队终于可以用更细粒度的“过程质量”来筛选轨迹，而不是只看最终测试是否通过。一个成功轨迹里可能有大量无用搜索，一个失败轨迹里也可能有可学习的定位步骤；CodeTraceBench 这类数据能帮助把它们拆开。未来如果接入训练 pipeline，可以把错误动作 mask 掉、把有用探索保留，并统计不同 agent/harness 的系统性坏习惯。
🔗 链接：https://github.com/NJU-LINK/CodeTracer ｜ 代码：https://github.com/NJU-LINK/CodeTracer

### MCPMark Verified：把真实 MCP 工具评测切到版本锁定、verifier 稳定的 verified set
MCP 工具评测很容易被环境漂移影响：远端服务版本变了、账户数据变了、verifier 规则松了，都会让同一个模型的分数不可比。MCPMark 近期把 Verified set 设为默认任务集，重点不是增加宣传分数，而是把环境版本锁定、verifier 稳定和旧分数不可比这些评测工程问题讲清楚。仓库说明 6 月 12 日之后应报告 MCPMark Verified 分数，并明确旧任务版本的结果被 deprecated。当前公开结果里 `gpt-5.5` xhigh 在 verified set 上达到 92.9%，`kimi-k2.7` 也达到 81.1%，但更重要的是这些数字有可复现实验边界。MCPMark 的任务覆盖多个真实 MCP 服务和多步工具使用，适合发现 schema、认证、检索、状态更新和恢复策略中的问题。对本日报关注的 evaluation anti-cheating 来说，Verified 化是 benchmark 成熟的标志：不是让榜单永远不变，而是让每次变更都有版本和 verifier 说明。内部团队评估 MCP agent 时也应沿用这种做法，固定环境、记录 server 版本、区分模型错误和基础设施异常。
🔗 链接：https://github.com/eval-sys/mcpmark ｜ 代码：https://github.com/eval-sys/mcpmark

### MCP-Universe + MCP+：真实 MCP server benchmark 与 50-75% tool-output token 压缩层
很多 MCP demo 只测“工具能不能被调用”，但生产 agent 真正难在大工具空间、长上下文、多步状态和真实数据源。Salesforce AI Research 的 MCP-Universe 把这些问题做成一个综合框架，既能跑真实 MCP server benchmark，也能开发和测试 agent workflow。近期仓库重点更新包括支持 MCPMark 任务，以及 MCP+ 这个上下文管理扩展。MCP+ 的思路很实用：不要把冗长工具输出原样塞给主 agent，而是在 MCP client 层做后处理，只把与当前任务有关的“针”交给模型；公开页面称可减少 50-75% token 成本，同时尽量保持任务质量。这个设计回应了近两周社区反复讨论的 MCP schema/output bloat：协议统一之后，下一层瓶颈变成工具输出裁剪、按需暴露和成本治理。它对 harness 工程的价值在于，把“上下文压缩”放在工具边界而不是纯 prompt 层，因而可以跨模型和跨 agent 复用。对后训练数据采集来说，也应记录原始工具输出、裁剪后上下文和裁剪器判断，否则模型成功可能来自隐藏的上下文工程而不是本身能力。
🔗 链接：https://github.com/SalesforceAIResearch/MCP-Universe ｜ 代码：https://github.com/SalesforceAIResearch/MCP-Universe

### GeneBench-Pro：OpenAI 用 129 个复杂生物数据任务评测 agent 的研究判断力
OpenAI 6 月 30 日发布 GeneBench-Pro，主题是 computational biology，不属于本日报最高优先的软件工程方向，因此放 Medium；但它是一个很值得借鉴的 agent eval 设计。普通科学 benchmark 往往测知识问答或固定流程执行，GeneBench-Pro 则给模型真实且混乱的数据、简短实验背景和一个下游决策相关的目标量。模型需要自己做数据探索、质量控制、统计建模、诊断迭代和最终结论，而不是沿着明确步骤填空。OpenAI 把这类能力称为 research taste，也就是科学家在分析中不断做出的判断链：哪些数据支持问题、诊断信号是否要求换模型、初始计划何时要被推翻。公开结果显示 GPT-5.6 Sol 在最高推理设置下 pass rate 为 28.7%，Pro-enabled settings 下为 31.5%，说明 benchmark 仍很难。对软件工程后训练的间接启发是，好的 benchmark 不应只给明确 issue，还要评估 agent 在含糊需求、脏数据和多轮诊断中的判断质量。GeneBench-Pro 的 case studies 还把 prompt、数据和 supporting materials 展示出来，这种透明度也值得 coding-agent benchmark 学习。
🔗 链接：https://openai.com/index/introducing-genebench-pro/ ｜ 代码：https://cdn.openai.com/pdf/6dc7175d-d9e7-4b8d-96b8-48fe5798cd5b/oai_genebench_benchmark.pdf

### OpenAI Core dump epidemiology：用全量 crash population 数据拆分硬件腐坏与 libunwind 竞态
OpenAI 这篇 6 月 30 日工程博客不是 LLM 方法论文，但它非常贴近“大规模数据基础设施如何工程化排障”。团队一开始像医生一样研究单个 core dump，试图从少量样本中解释 Rockset 服务里的奇怪崩溃；问题是不同 crash 被误认为同一种病，导致所有假设都互相打架。转折点是把所有生产 core dump 做成高质量数据集：用脚本下载 core 前缀、提取寄存器、过滤误报，并自动标注 return-to-null、misaligned-stack 等类别。全量 population 视角揭示了两个无关问题：一个是单台 Azure 物理机的 silent hardware corruption，另一个是 GNU libunwind 里存在 18 年的 x86_64 exception unwinding race condition。这个故事对 agent 数据工程有很强类比：不要只盯一条失败轨迹做玄学复盘，要先把失败样本结构化、分群、标注，才能看见系统性模式。它还说明 ChatGPT 在内部被用来辅助写数据清洗脚本，但真正的价值来自人类把问题改写成可统计的 population analysis。对长期运行的 agent 平台来说，core dump、trajectory、tool failure、permission denial 和 verifier failure 都应进入类似的 epidemiology pipeline。
🔗 链接：https://openai.com/index/core-dump-epidemiology-data-infrastructure-bug/ ｜ 代码：None

### Anthropic Sandbox Runtime：OS 级边界让 Claude Code/MCP server 在少弹窗下安全运行
Coding agent 需要读文件、写代码、跑命令、访问网络，但如果每一步都弹权限确认，用户很快会疲劳并机械点击允许。Anthropic 的 Sandbox Runtime 给出了另一条路径：用 OS 级边界限制进程树能读写哪些文件、能访问哪些网络域，而不是把安全完全交给模型或用户。它在 macOS 上使用 Seatbelt，在 Linux 上使用 bubblewrap，并通过代理做网络 allowlist；README 也展示了如何把 MCP server 放进 `srt` 包装，限制 filesystem MCP 这类高权限工具。仓库目前约 4.5k stars，6 月底仍有更新，说明社区对“轻量、无容器、本地 agent sandbox”的需求很强。它的工程 insight 是，sandbox 不是单纯安全功能，也是 autonomy 功能：边界足够硬，agent 就能在边界内少打断地运行。对后训练/评测平台来说，轨迹里应明确记录 sandbox policy、被拦截动作和网络 allowlist，否则同一 agent 在不同权限边界下的行为不可比较。需要注意的是该项目本身早于本期发布，本期按活跃社区基础设施和近月热度收录，而不是作为全新官方博客处理。
🔗 链接：https://github.com/anthropic-experimental/sandbox-runtime/ ｜ 代码：https://github.com/anthropic-experimental/sandbox-runtime/

### Commandable MCP：动态工具注册让 agent 按需生成和加载 MCP toolset
MCP 生态快速增长后，一个反复出现的问题是“工具太多”：几十个 tool schema 一次性加载进上下文，当前任务真正需要的可能只有两三个。Commandable MCP 把 Claude Code 支持的 dynamic tool registration 推到更激进的方向：server 不只是静态列出工具，而是让 agent 按需加载 toolset，甚至在会话中创建 integration 和 custom tool。它内置 GitHub、Jira、Notion、Google Workspace、Airtable、Confluence 等工具集合，也提供 `/mcp/create` 模式让 agent 为实际工作流生成更贴近需求的工具。仓库 star 只有十来个，所以不能夸成爆火项目；它的价值在于把 MCP context bloat 的一个解决方案具体化了。与 MCP+ 的“压缩工具输出”不同，Commandable 关注“不要一开始暴露所有工具”，更像 progressive disclosure。工程风险也很明显：agent 自己生成工具会带来权限、凭证、审计和测试问题，必须配合加密、allowlist、schema review 和运行日志。对 Agent-Friendly Software 来说，这是从“API-to-MCP 包装器”走向“agent 自适应工具层”的早期探索。
🔗 链接：https://www.commandable.ai/blog/mcp-isnt-dead ｜ 代码：https://github.com/commandable/commandable-mcp

## 🔥 社区热点专栏

### 🔥 大佬观点

**Hacker News MCP 讨论：MCP 是 agent 与工具之间的线缆格式，不等于模型原生工具调用格式。**
HN 近期高信号讨论指出，MCP 解决的是 client 如何发现并调用工具，但模型侧的 tool-call 表达仍由 Claude Code、Cursor、Codex 等客户端各自实现。这个观点值得注意，因为它解释了为什么同一个 MCP server 在不同 agent 里仍会有参数、截断、schema 校验和 UX 差异；评测 MCP 工具时不能只测 server，还要记录 client/harness。🔗 https://news.ycombinator.com/item?id=47767815

**Commandable 团队：MCP 的关键机会是动态工具注册，而不是把 API 全量转成巨型 schema。**
Commandable 的文章把 dynamic tool registration 称为 MCP 以来最被低估的能力：server 可以按会话状态增加/删除工具，让 agent 只加载当前需要的 ability。这个观点火在击中了 MCP schema bloat 的真实痛点，也和 MCP+ 的输出压缩形成互补。🔗 https://www.commandable.ai/blog/mcp-isnt-dead

### ⭐ 超火仓库/项目

**anthropic-experimental/sandbox-runtime：4.5k+ stars 的本地 agent OS 级沙箱。**
它火在给 Claude Code、MCP server 和任意子进程提供 Seatbelt/bubblewrap 级别的文件系统与网络边界，降低“每步审批”的弹窗疲劳。真正的 insight 是：想让 agent 更自主，不能只靠用户批准或模型自觉，而要把可行动范围做成确定性边界。🔗 https://github.com/anthropic-experimental/sandbox-runtime/

**SalesforceAIResearch/MCP-Universe：590 stars 的真实 MCP server benchmark + MCP+ 压缩层。**
MCP-Universe 热点不在 star 绝对数，而在它把 MCP agent 的真实工具空间、MCPMark 评测和 MCP+ 50-75% token 节省放进同一个工程框架。它解决的痛点是：MCP 生态已经从“能连工具”进入“怎么评测、怎么压上下文成本、怎么复现实验”的阶段。🔗 https://github.com/SalesforceAIResearch/MCP-Universe

**eval-sys/mcpmark：432 stars 的 MCPMark Verified 评测集。**
MCPMark 近期把 Verified set 设为默认，说明社区正在把 MCP benchmark 当作需要版本、环境和 verifier 治理的软件资产。它解决的是排行榜污染和环境漂移问题：没有稳定 verifier，agent 的工具使用能力就无法长期比较。🔗 https://github.com/eval-sys/mcpmark
