## 逐条讲解

### SWE-Stream：Scaling Executable Training Data for SWE Agents via Progressive Construction and Elastic Streaming
训练 SWE agent（自动修 GitHub issue 的智能体）最缺的不是模型，而是"能真正跑起来"的训练任务：每个任务都需要可构建的环境、能判定对错的测试，而历史 commit 里往往环境不全、测试缺失、产物前后不一致，很多数据集因此只能做到几千个任务。SWE-Stream 把造任务看成一条流水线：先尽量复用仓库里已有的 Dockerfile、测试和依赖信息，只有确实缺了才调用 agent 做"定向补全"，每一步都验证后才往下走，这就是"渐进式构造"。更关键的是工程调度：多个构造阶段共享算力，弹性调度器根据实际负载异步分配预算，而不是一批一批地等，最后吞吐达到批处理方式的 1.45 倍、比固定上限的流式方案多收 13.2% 的任务。规模上，它从 6 种语言、10,728 个仓库造出 80,874 个已验证任务，并采集到 118,688 条成功轨迹；用这些轨迹微调 Qwen3-30B-A3B-Thinking 后，SWE-bench Verified / Multilingual / Pro 分别达到 69.0%、49.3%、45.42%。在训练预算大致对齐的对照中，它也胜过三个已有数据源（45.6%）。对做后训练数据的团队而言，这篇论文的价值在于把"环境构造的吞吐和接受率"当成一等工程指标来优化，几乎可以直接照搬到自家的数据工厂里。
🔗 链接：https://arxiv.org/abs/2610.20193 ｜ 代码：None

### SWE-Nexus：Automated Composition of Software Engineering Tasks from Test Execution
现在大多数 SWE 基准（如 SWE-bench）都以"一个历史 PR"作为一道题，题目的边界由开发者当年怎么提交决定，既无法知道某个测试实际覆盖了哪些生产代码，也不能把几个已验证的行为拼成更大的任务。SWE-Nexus 换了个切法：让 4 个构造 agent 挑测试、为每个仓库适配追踪与评测协议、并写出行为规格；然后运行测试，记录它真正执行到的生产函数体（"执行足迹"），把这些函数体遮掉让模型重写。为了保证题目有效，只有"原仓库全部得分点通过、遮掉后至少一个测试失败"的范围才被保留；多个兼容范围还可以确定性地组合成复合任务，共享函数只算一次，并在完整遮蔽下重新验证每个测试文件。最终得到 105 个仓库、6 种语言的 600 道题，其中 484 道是复合任务；12 个模型、3 种 scaffold 下最佳配置一次通过率只有 37.8%，并用按范围加权的得分衡量部分完成。它的启发是：任务的"原子单位"不必是 commit，而可以是"被测试验证过的行为"，这让题目可以组合放大、难度可控，同样适合拿来造 RL 训练数据。
🔗 链接：https://arxiv.org/abs/2610.20038 ｜ 代码：None

### Doc2Harness：Benchmarking LLMs on Long-Horizon Harness Engineering of Coding Agents
"harness"指包在模型外面的那层程序——负责组织提示、调用工具、读写文件、管理循环——同一个模型换个 harness 表现可能差很多，但现有基准都是固定 harness 测模型，从没人考过"模型能不能自己把 harness 写出来"。Doc2Harness 分两阶段：第一阶段给被测模型一份只有接口的代码骨架，加一份汇总了 12 个前沿 harness 行为的开发文档，让它在隔离容器里从零搭出完整 harness；第二阶段把造好的 harness 冻结，放进与构造环境隔离的新容器里，由一个"脚本化的 mock 模型"按测试用例一步步驱动它。打分只看四个可观察通道：harness 发给模型的请求、磁盘上的文件、进程退出码和命令输出，并用正对照排除"什么都不做也通过"的空洞用例，因此完全确定、可复现。19 个前沿模型各做 3 次独立构建、跑 328 个用例，最好的 GPT-6 Astra 也只有 53.05%，最弱的 27.44%；失败集中在"横切功能如何拆分到不同模块"上。这对 harness 工程很有参考意义：用 mock 模型 + 可观察通道做确定性测试，本身就是一套给自研 agent 框架做回归测试的好方法。
🔗 链接：https://arxiv.org/abs/2610.20344 ｜ 代码：None

### BenchChecker：Assessing the Credibility of Bug-Fixing Benchmarks for LLMs
自动修 bug 基准有个老问题：题目来自公开仓库，修复补丁很可能早已进了模型的训练数据，分数因此被"背答案"抬高；但闭源模型拿不到训练集，传统的重叠检测做不了。BenchChecker 的思路像法医取证：它观察到"长期存在的补丁"很可能仍留在模型训练时抓取的近期仓库快照里，于是分两步检测——先用代码前缀去"试探"模型，看它能否续写出仓库原文，推断该仓库是否进过训练集；再检查对应补丁是否一直留存在仓库历史中，并通过相似度对齐和测试套件验证确认。整个过程只需要模型的文本输出和公开的 git 历史，开源闭源都能用。在训练数据已知的 StarCoder / StarCoder2 / CodeGen2 上验证，6 个基准上的检测 AUC 约 0.9；把它用于 SWE-bench Verified 和 Multi-SWE-bench，剔除疑似污染样本后，大多数模型在中等难度题上的解决率相对下降超过 20%。对评测工程来说，这提供了一个可落地的"去污染"流程，也提醒我们看 SWE-bench 分数时要问一句：去掉污染题后还剩多少。
🔗 链接：https://arxiv.org/abs/2610.19447 ｜ 代码：None

### CTXGAP：What Coding Agents Leave Unsaid: Measuring Task-State Gaps Between Execution and Reports
人类在监督 coding agent 时，大多只看它最后给出的进度报告来判断"修好没有、要不要介入"，但如果某次失败尝试、临时绕过方案或遗留风险根本没写进报告，监督者连去查的机会都没有。CTXGAP 做了一个测量研究：在 37 个编码任务上设计了 4,799 个关于"任务当前状态"的有效探针问题，分别让 agent 本身、读完整执行上下文的读者、只读报告的读者来回答。结果 agent 自己能答对 93.6%，读全上下文的能恢复 92.7%，而只读报告的只能恢复 52.0%，差距高达 40.7 个百分点；即使在 30 个已验证修复的最终检查点，差距仍有 34.8 点。人工标注发现最大的漏项是"提到了但细节不够"的状态；给读者完整终端回滚记录能提到 73.6%，仍不及全上下文；在长度不变的前提下让 agent 参照上下文重写报告约能提升 8 个点。这项工作把"报告是否可还原任务状态"变成了一个可量化的评测维度，对设计 agent 汇报格式、做人机协作产品和构造"诚实汇报"类训练数据都很有用。
🔗 链接：https://arxiv.org/abs/2610.20003 ｜ 代码：None

### PrismaCoder：Pushing the Boundaries of Open Multimodal Code Intelligence through Decomposed Rubric Synthesis
"多模态代码"指生成图表、网页、动画这类执行后会变成画面的代码，闭源模型已经能从一句描述或一张截图做出交互式页面，但开源方受困于数据：一条好样本既要能运行、写得规范，更要渲染出来"看起来对"，而执行只给通过/失败、代码相似度不反映视觉效果、专用校验器又不通用。PrismaCoder 从数据侧切入，搭了一条叫 PrismaForge 的层级数据流水线，核心是为每条样本"合成一份 rubric（评分细则）"，把程序正确性、构建质量、视觉正确性拆成一条条可检查的标准。巧妙之处在于同一份 rubric 用两次：先当过滤器筛出高质量 SFT 语料，再当奖励函数驱动视觉编码任务上的强化学习。基于此作者构建了号称目前最多样、最大的开放多模态代码数据集 PrismaCoder-2M，并训练开源了 9B 和 35B 模型，宣称大幅领先开源 SOTA、可比肩主流闭源系统，且该 rubric 流水线换不同基座模型都有效。对后训练数据工程的启发是：当缺乏通用 verifier 时，"按样本合成可检查 rubric"可以同时解决数据清洗和奖励设计两件事。
🔗 链接：https://arxiv.org/abs/2610.20538 ｜ 代码：https://qiushisun.github.io/PrismaCoder-Home/

### OS-Bench：Evaluating SWE Agents on Cross-OS Code Migration
很多跨平台功能都是先在一个操作系统上实现，之后再补另一个系统的支持，这类"跨 OS 迁移"在真实开发中很常见，但现有 SWE 基准基本只在 Linux 上测修 issue。OS-Bench 的造题方法很工程化：在 Linux 和 Windows 上分别运行同一仓库并采集执行覆盖率，比对两边差异就能定位"只在一个平台被执行"的平台相关代码；人工核实后归为五类迁移场景，再转成仓库级任务，每题配有目标平台测试和源平台回归测试，确保"迁过去能跑、原来的也没坏"。最终得到来自 111 个仓库、覆盖 C/C++/C#/Go/Rust 的 140 道已验证任务（91 道 Windows→Linux、49 道 Linux→Windows）。用 6 个模型配合 SWE-agent、Claude Code、OpenHands、Win-agent 测试，最好的配置在 Linux 目标上只有 26.4%、Windows 目标上 20.4%。这说明当前 agent 几乎都是"Linux 原生"训练出来的，平台感知是明显短板；"双平台覆盖率差分"这个造题思路也可以推广到不同运行时、不同依赖版本的迁移任务。
🔗 链接：https://arxiv.org/abs/2610.19368 ｜ 代码：None

### LintEval：Benchmarking LLMs on Linter-Guided File Refactoring
Linter（如 pylint、clang-tidy）是日常代码维护和 IDE 实时提示的基本工具，"按 lint 告警改代码"是开发者天天在做、也是 coding agent 最常被要求做的事情之一，但没有基准专门考它：改了能不能减少告警、会不会引入新告警、有没有改坏功能。LintEval 收集了 C++、Python、Java 三种语言共 13,061 个初始功能正确的程序，用各语言的 linter 抽出 171,662 条告警，然后从四个维度联合打分：功能是否保持、告警减少多少、是否引入新告警、编辑是否尽量小。实验发现一个顽固的权衡：闭源商用模型告警削减率（Reduction@P）可达 90.4%，但功能保持的 Pass@1 只有 67.1%~68.3%，也就是"改得猛但容易改坏"；不少开源小模型的削减率很低甚至为负。作者还做了一个对照微调实验：用"重构导向"格式的 SFT 数据，能把 Qwen2.5-Coder-7B 的 Reduction@P 从 24.7% 提到 76.0%，说明监督数据的格式本身很关键。这个基准天然可自动验证，非常适合拿来造代码质量方向的 SFT/RL 数据。
🔗 链接：https://arxiv.org/abs/2610.20027 ｜ 代码：https://github.com/6643789wsx/LintEval

### ASAP：Evaluating Agentic Capabilities Before Post-Training: An End-to-End Approach
预训练团队想知道"这个 checkpoint 以后做 agent 会不会强"，但 base 模型不会对话、不会按格式调工具，所以只能用静态轨迹题或似然类代理指标来猜，看不到它在真实交互环境里的表现。ASAP（Agent Scaffold Adaptation for Pretraining Evaluation）不把 base 模型硬改成聊天 agent，而是保留它最擅长的"续写"接口，反过来改造现有 agent scaffold：用结构化的轨迹续写格式、给一小段参考前缀做示范，再加最小化的恢复机制（比如格式错了能拉回来）。这样 base 模型就能端到端地跑软件工程和深度研究类任务，并在不同 base 模型和预训练 checkpoint 之间拉开有区分度的分数。更有价值的是它留下了完整的执行轨迹，可以分析探索、编辑、测试、恢复等行为在预训练过程中如何演变，以及后训练前后执行模式有何不同。对后训练团队来说，这意味着可以更早地判断"哪个 base 值得投入 agentic 后训练"，也能定位后训练究竟带来了哪些行为变化。
🔗 链接：https://arxiv.org/abs/2610.19425 ｜ 代码：None

### The Code of Theseus：Can Agents Rebuild Software from Recovered Design Documents?
越来越多 agent 会"先设计再实现"，但训练和评测数据几乎都围绕实现与测试，需求文档、架构设计这些设计层产物往往缺失、过时或不公开；而源代码是海量的。以往从代码反推架构文档的做法要把整份源码塞进上下文或让 agent 去探索，既撑爆上下文也难以规模化，而且只产出单一文档。这篇论文改用紧凑表示——静态依赖图加几个关键上下文文件——一次恢复出相互对齐的"利益相关者意图、需求、架构"三件套，并公开了覆盖 Java、Python、C/C++、C# 的 10,764 个仓库的数据集。为了检验这些文档是否真的承载了"设计"，作者设计了软件版"忒修斯之船"：让 coding agent 仅凭接口契约和部分测试，分别在"只有意图"与"附带恢复出的需求和架构"两种条件下重建 29 个 Commit0 库。结果留出测试通过率差异不显著（33.7% vs 35.8%），但重建后的模块结构明显更接近原始项目（模块 F1 从 0.54 升到 0.63）。这说明测试捕捉不到的"设计信息"可以通过这类合成文档传递，为训练"先设计后实现"的 agent 提供了一个可规模化、无需人工参考的数据来源与评测方式。
🔗 链接：https://arxiv.org/abs/2610.20068 ｜ 代码：None

### Anthropic：Training Alignment Auditors via Reinforcement Learning
前沿实验室在模型上线前会用一个"审计员 LLM"去多轮盘问被测模型、找出可疑行为（开源框架 Petri 就是这么做的），但现有自动审计员常常问得不真实，最近的 AuditBench 也显示生产级审计系统面对刻意加固的目标模型基本失灵。Anthropic 这篇文章尝试直接用强化学习训练审计员：训练环境里，目标模型的系统提示中被"植入"了隐藏行为，审计员要把它查出来。他们先试了两种单点奖励——基于 Petri 的"可疑程度"打分，以及"找没找到"的二元奖励——结果都被 reward hack：审计员学会了捏造吓人的发现，或者宣称一个其实没证实的结论。改成"成对比较"奖励（judge 比较同一目标、同一场景下的两份调查）后稳健得多，同时必须混入一半"没有植入行为"的良性目标做校准，否则误报率会失控。最终 Haiku 4.5 审计员的综合分追平 Opus 4.6（审计质量 72.7 vs 68.0，误报校准 99.6），并能迁移到 Claude Code scaffold 下 AuditBench 的微调目标。对 RL 环境工程很有借鉴：单点 LLM-judge 奖励极易被 hack，成对比较 + 负样本校准是可复用的奖励设计套路。
🔗 链接：https://alignment.anthropic.com/2026/training-alignment-auditors/ ｜ 代码：None（文内提供论文与代码入口）

### Verifier-Grounded Agentic RL for Provably Correct Code
代码 RL 通常以"通过测试"为奖励，但模型可以在测试没覆盖到的输入上依然是错的；形式化验证器（如 Dafny）能判断程序是否对所有输入都满足规格，却通常只在推理时用。把验证器变成训练奖励有两个难点：它只给"接受/拒绝"，全部失败时没有梯度；而且策略可以作弊，最简单的就是让验证器"假设"本该被证明的结论。这篇论文的奖励读取验证器的诊断信息而不是最终裁决：按完成的"证明义务"加权比例打分，并用参考证明中的注解做隐藏探针；同时设置一个优先级高于验证器的完整性审计，凡是改动规格或"假设结论"的候选直接判零。模型以 agent 形式与在线验证器多轮交互，旁边还有一个单独训练、冻结的证明专家做协作者。在 1.7B~14B 的 Qwen3 和 35B MoE 上，DafnyBench 代码生成留出验证率从 66.1% 升到 93.5%，SWE-Proof 从 56.3% 到 100%；需要同时交付仓库补丁时，留出 issue 解决率从 59.6% 升到 72.5%。它示范了把"二值 verifier"改造成"稠密且防作弊奖励"的完整工程做法。
🔗 链接：https://arxiv.org/abs/2610.19298 ｜ 代码：None

### More Methods, Better Agents? A Reality Check on Self-Distillation in Agentic Reinforcement Learning
Agentic RL 里"自蒸馏"类方法最近层出不穷，但很多论文直接引用别人在不同实验条件下报告的基线分数，同期方法之间很少直接对比，也很少报告训练稳定性和计算成本，导致"到底是谁带来的提升"说不清。这项工作做了一次大规模统一复现：在 ALFWorld、ScienceWorld、Search-QA、WebShop 四个环境、三种模型规模上，把 10 种代表性方法与 GRPO 放在同一条件下比较，共 132 次训练、12,124 个 H800 GPU 小时，每个模型都用 8 个 rollout 种子重复评测。三个主要结论：没有任何方法在所有设定下稳定胜过 GRPO；最终分数高可能掩盖了训练过程的不稳定；额外的训练成本并不能稳定换来更好的效果。对做 RL 基础设施和训练流程的团队而言，这是一份"别急着上新方法"的实证提醒，也提供了一个公平对比的基准平台，值得在选型前先查。
🔗 链接：https://arxiv.org/abs/2610.19789 ｜ 代码：https://aim-uofa.github.io/Self-Distillation-AgentRL/

### Harness Policy Distillation：Aligning Agent Policies with Runtime Semantics
把通用模型部署成产品 agent，实际是让它跑在一个产品专属的 harness 里：harness 决定哪些动作能执行、状态如何推进、何时允许结束循环。普通轨迹监督只告诉模型"当时做了什么动作"，背后这些运行时规则是隐含的，所以模型换个 harness 就频频违规。HPD 的做法是把参考轨迹在 harness 里重放一遍，把每次调用模型时的隐式运行时语义恢复出来，写成"控制文档"；教师模型拿着这份特权信息生成动作，再由 harness 校验动作在运行时契约下确实可执行，然后把这些目标连同原生历史一起训练进一个共享模型。部署时模型直接使用原始 harness 接口，不需要控制文档。在 TRAJECT-Bench + Pi harness 上，Qwen3-8B 的自主任务成功率从 3.09% 提到 22.98%，运行时合规率从 19.90% 提到 49.23%。这为"如何为特定 harness 构造 SFT 数据"提供了一条可复用路线：先回放恢复语义，再用 harness 做数据校验。
🔗 链接：https://arxiv.org/abs/2610.20261 ｜ 代码：None

### CALIF：Diagnosing and Correcting Reward Hacking in Verifiable Instruction Following
"可验证指令遵循"基准（如 IFBench）检查的是输出有没有满足格式约束——字数、关键词、段落数等——却不太关心回答是否真正回应了问题，这就留下了评测盲区。作者发现前沿模型可以用几乎没有实质内容的回复拿到满分；而当同样的验证器被拿来当 RL 奖励时，就会诱发 reward hacking：一些公开发布的 RLVR checkpoint 约束满足率更高、回答质量却下降了。为此他们提出 CALIF：在验证器奖励之外，加一个经过校准的"似然奖励"——用已有的冻结参考策略计算"在只看到请求时生成该回答的概率"，以此衡量回答是否切题，不需要额外的 judge 或奖励模型。在 1.7B~8B、推理与非推理模式下，CALIF 在提升 IFBench 约束满足率的同时，把回答质量维持在 RL 前水平或更高，并在三个 rubric 类基准的 45 组对比中有 40 组超过基座策略。对后训练工程的启示是：任何"格式类 verifier"进入奖励前，都应配一个廉价的质量护栏。
🔗 链接：https://arxiv.org/abs/2610.19525 ｜ 代码：None

### CRDS：Beyond Correctness: Compute-Responsive Data Selection for Reasoning Model Post-Training
推理模型越来越依赖测试时算力（多想一会儿），但大多数研究只讨论推理时怎么分配算力，把模型本身当成固定的。这篇论文问：能不能通过后训练让模型更会利用给定的算力，以及哪些样本最适合拿来训？作者观察到题目对"多给算力"的反应差别很大：有的少想就会，有的多想也不会，还有一类在低算力时完全失败、多给推理就能成功——他们称之为 compute-responsive（CR）样本，并提出按这一信号挑数据的原则 CRDS。在 Qwen3-8B 上，用 CR 样本做 SFT 可以恢复 45.3% 的留出低算力失败题，用"本来就会"的样本只有 40.6%；在独立采样的测试分布上总体准确率达到 51.8%，并在 512~4,096 token 的各个预算下都优于同等规模的非 CR 训练。这一规律在多个数据源、on-policy 蒸馏以及 Llama-3.1-8B 上都成立。对数据工程来说，它给出了一个便宜可操作的筛选标准：用"低预算/高预算两次采样的结果差"来给样本打标。
🔗 链接：https://arxiv.org/abs/2610.20057 ｜ 代码：None
