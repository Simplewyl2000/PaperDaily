## 📝 逐条讲解

### PACMS：把 agent 上下文装配做成可插拔选择引擎
长程 agent 最大的工程问题之一是上下文会被聊天历史、记忆条目和工具输出不断塞满，最后只能按“最近的留下、旧的丢掉”粗暴截断。PACMS 把这个问题放到 prompt assembly 这个关键边界上处理：它不改写内容，而是把 memory、turns、file reads、search results 等所有候选上下文放到一个池子里，在 token 预算内选择最覆盖当前查询、又尽量少重复的原文片段。具体做法是用 submodular facility-location 目标做预算约束选择，并作为 OpenClaw 的 context-engine 插件接入，运行时通过本地 FastAPI 服务完成 keep/drop 决策。论文在 100 个 LongMemEval 问题上显示，PACMS 的证据召回和 LangChain MMR 接近，但在两个 GPT-5 系列 reader 的端到端 QA 准确率上比 MMR 高 8 到 12 个百分点。它的重点不是一个更花哨的检索算法，而是把“上下文装配策略”做成可替换、可观测、可调预算、可降级的 runtime 组件。对 coding agent 后训练和 harness 工程来说，这提醒我们要把 context selector 视为系统能力来源，并记录哪些片段被保留、哪些被丢弃，方便做失败分析和训练数据筛选。
🔗 链接：https://arxiv.org/abs/2606.20047 ｜ 代码：None

### NRT-Bench：安全关键控制室里的多轮红队 agent 评测
很多 agent 安全评测仍停留在单轮 jailbreak：给模型一个恶意 prompt，再让另一个 LLM 判断回答是否违规。NRT-Bench 把评测推进到更接近真实部署的状态：五个角色化 LLM operator 共同运行一个核电控制室模拟器，攻击者通过四种入口持续多轮注入消息，并根据每轮反馈逐步升级。它最重要的设计是 harm signal 不由 LLM judge 判定，而是由模拟器里的 critical safety function 是否丢失来决定；一旦某个 CSF lost，系统就记录导致失效的具体攻击 turn。论文报告四个前沿模型在固定攻击 replay 下都有 8.7% 到 12.1% session 被推过安全线，而且失败集合几乎不重叠，说明“更强模型包含弱模型漏洞”这种假设并不成立。防御也不是单向有效：同一套 guardrail 或 safety-advisor agent 对不同模型可能降低风险，也可能反而升高风险。对 agent eval 工程来说，它提供了一个很强的模板：安全评测应有状态化环境、角色权限、客观 harm oracle、固定 replay workload 和可追溯日志，而不是只看文本拒绝。
🔗 链接：https://arxiv.org/abs/2606.20408 ｜ 代码：None

### CircleCI MCP：把 coding agent 接到 CI 日志、配置验证和重跑闭环
AI coding agent 生成代码越来越快，但速度越快，越需要自动验证来防止不存在的依赖、错误 API、漏掉边界条件或安全漏洞直接进入仓库。CircleCI 这篇教程的技术点不是“如何安装 Claude Code”，而是把 CI/CD 平台通过 MCP 暴露给 coding agent，让 agent 在终端里验证配置、查看 pipeline、分析失败日志、定位 flaky tests，并触发重跑。这样 agent 的工作闭环不再是“改完代码后说应该可以”，而是能直接读取真实构建结果并继续修复。文章还区分了云端 MCP server 和本地 CircleCI CLI 的用途：前者适合查真实历史、触发远端 pipeline，后者适合快速本地配置验证和容器化复现。这个模式对 Agent-Friendly Software 很典型：传统 SaaS 仪表盘需要变成 agent 可调用的结构化工具，而不是让 agent 读网页截图或让人手动复制日志。对后训练数据工程也有价值，因为 CI 失败日志、修复动作、重跑结果天然构成可验证轨迹，可用于筛选高质量 coding-agent rollout。
🔗 链接：https://circleci.com/blog/getting-started-with-claude-code-and-circleci/ ｜ 代码：None

### Tree-like Self-Play：在 CWE 风险节点训练安全 Code LLM
安全代码生成的难点是漏洞往往由很局部的决定造成，例如一次不安全函数调用或一次缺失的输入校验，但传统 SFT/RL 通常只对整段代码给奖励或惩罚。Tree-like Self-Play 把代码生成看成一棵决策树，先用 LLM annotator 找出 CWE risk nodes，也就是最可能产生安全漏洞的关键分叉点。然后模型在这些节点上生成安全的 golden path 和自己产生的 vulnerable variants，把“过去的错误分支”变成对比学习的负样本。这样训练信号集中在真正决定漏洞的局部位置，而不是把整段代码均匀强化。论文报告 CodeLlama-7B 在 Python security benchmark 上 SPR@1 从 SFT 的 57.0% 提升到 75.8%，并能把 C/C++ 学到的安全原则迁移到 Python、Go、JavaScript 等语言。虽然它带有算法成分，但对本日报有价值的是它的数据工程思想：用模型自己的 on-policy 错误生成可定位、可对比、可迭代的安全后训练样本。
🔗 链接：https://arxiv.org/abs/2606.03489 ｜ 代码：https://github.com/Easonnoway/TSP

### agentmemory：23k+ stars 的跨 Claude/Codex/Cursor 持久记忆层
很多 coding agent 的失败不是不会写代码，而是每个 session 都像第一次接触项目：忘记架构决策、踩过的坑、用户偏好和上次验证结果。agentmemory 试图把这个问题做成跨客户端基础设施，而不是某个 CLI 的本地小功能。它通过 MCP、REST 和不同客户端的 lifecycle hooks 捕获会话事件，并把 Claude Code、Codex CLI、Cursor、Gemini CLI、OpenCode、Copilot CLI 等工具接到同一个 memory server。社区热度来自两个点：一是仓库已超过 23k stars，二是它把“同一项目在多个 agent 间共享记忆”变成现实痛点的解决方案。它还专门适配 Codex plugin platform 和 Claude Code hooks，说明持久记忆正在从聊天摘要走向 agent runtime 层。对后训练软件工程来说，类似项目提醒我们训练轨迹之外还要关注跨 session state：哪些事实应该进长期记忆、哪些只在当前任务有效、哪些需要用户确认或过期策略。
🔗 链接：https://github.com/rohitg00/agentmemory ｜ 代码：https://github.com/rohitg00/agentmemory

### OpenClaw 2026.6.10-beta.1：修复 compaction、subagent completion 与 transcript correctness
开源 coding agent/harness 的成熟度，很大程度体现在它是否认真处理 transcript、compaction、子代理完成通知和半途状态，而不是只展示模型能改代码。OpenClaw 2026.6.10-beta.1 的 release 重点是保存 pending completions、非空 histories、media fields、queued follow-ups、reasoning summaries 和 partial turns，并修复 compaction model alias 到 canonical model reference 的解析问题。它还明确修复了 agents 保留 pending subagent completion announces 的问题，这类细节在长程、多 agent、跨渠道任务中非常关键。表面看这些都是“边角 bug”，但真实 unattended loop 往往正是在这些边角状态里丢失上下文、重复提交或误报完成。OpenClaw 近期还和 PACMS 这类 context-engine 插件形成呼应：agent runtime 正在把 prompt、channel、memory、compaction、subagent、transcript 都做成可演化控制面。对内部平台来说，这类 release 值得跟踪，因为它暴露了大规模 agent 会话中最常见的状态一致性问题。
🔗 链接：https://github.com/openclaw/openclaw/releases/tag/v2026.6.10-beta.1 ｜ 代码：https://github.com/openclaw/openclaw

### AtomMem：用原子事实构建稳定长期记忆系统
长期记忆系统常在两个极端之间摇摆：保存原始对话会很完整但噪声巨大，保存摘要又容易丢细节并在反复改写中积累幻觉。AtomMem 的核心思路是把原始交互先压成自包含的 atomic facts，每条事实都带参与者、关键词、时间和事件关联等结构化元数据。系统再把这些事实组织成 event memory 和 temporal profile，用来表示一段经历以及用户偏好、背景、目标随时间的变化。检索时，它不是只做扁平向量召回，而是激活一个关联记忆图，把分散在多次会话里的实体、事件和邻近对话连起来。论文称在 LoCoMo 长期记忆 benchmark 上达到 SOTA，并开源实现。它按 Medium 收录，因为主题偏通用 personalized agent，但对 coding agent 也很有启发：项目记忆应尽量以可溯源事实、事件和版本化 profile 表达，而不是不可验证的长摘要。
🔗 链接：https://arxiv.org/abs/2606.19847 ｜ 代码：https://github.com/MINE-USTC/AtomMem

### DeXposure-Claw：高风险 DeFi 监管 agent 的证据门控与评测 harness
高风险领域里，直接让 LLM 读原始数据并给监管建议很危险，因为模型容易把弱证据、陈旧数据或不确定预测说得很有把握。DeXposure-Claw 的做法是把 LLM 限制在结构化证据之后：先由图时间序列 foundation model 预测未来 DeFi exposure network，再由确定性 monitor 和 stress scenario 生成 typed alerts、attribution、uncertainty 和 data-health 信号，最后才让 LLM 起草 supervisory tickets。系统还有 data-health gate 和 confidence gate，只有满足阈值时才允许更高干预级别的建议，否则退回 monitor 或 investigate。论文同时提出 DeXposure-Bench，按 forecast、warning、uncertainty、stress fidelity、ticket quality、robustness 六个轴评估，并显式报告 false-intervention rate。一个诚实的结果是，即使 Claude Sonnet 4.6 能提高 ticket 覆盖和解释，仍会在约 37% 干预中 over-read forecaster；更强 Opus 4.7 也没有解决这个问题。它对 agent 系统工程的启发是，高风险 agent 应被设计为 evidence-linked drafting component，而不是 release authority；真正安全来自 typed contract、gate 和人类复核。
🔗 链接：https://arxiv.org/abs/2606.19501 ｜ 代码：https://github.com/EVIEHub/DeXposure-Claw

### Contagion Networks：多 agent evaluator 偏差传播测量框架
多 agent 系统常用一个 agent 评价另一个 agent 的输出，或者让 reviewer agent 选择 writer agent 的方案，但大家很少测评价偏差会不会在 agent 网络里传播。Contagion Networks 把 evaluator bias 当成一种可传播信号，定义 cross-agent contagion matrix 来量化某个 agent 的评价偏好如何改变另一个 agent 后续策略。论文用三 agent 实验观察到偏差确实会传播，contagion coefficient 大约在 0.157 到 0.352 之间，并给出 suppression、persistence、cascade 三种传播状态。一个可落地的 mitigation 是增加评价委员会大小：从 k=1 到 k=3 可把有效 contagion 降低 72.4%。这对 multi-agent coding 很相关，因为 maker-checker、writer-reviewer、planner-implementer 都依赖评价信号。如果所有 reviewer 共享同一偏好，例如偏爱冗长解释、偏爱某种 patch 风格或偏爱模型自己的输出，系统多样性会被慢慢磨平。工程上应记录 reviewer 配置、偏好 profile 和跨模型组合效果，而不是默认“多 agent 就更客观”。
🔗 链接：https://arxiv.org/abs/2606.20493 ｜ 代码：None

### Uncertainty Decomposition：把 action confidence 与 request uncertainty 分开触发澄清
真实用户请求经常不完整，例如“帮我买一件衬衫”但没说尺码和颜色；agent 如果只给出一个总 confidence，很难知道应该继续执行还是先问问题。Uncertainty Decomposition 把 prompt-based uncertainty 拆成两个信号：action confidence 表示当前动作是否有把握推进任务，request uncertainty 表示用户目标是否缺关键条件。它的工程取向很实用，因为许多生产 agent 只能调用黑盒模型 API，拿不到 logprob、隐藏状态，也不能为每一步做多次采样。作者构造 WebShop-Clarification 和 ALFWorld-Clarification，让 50% 任务刻意缺信息，评估 agent 是否会主动澄清。结果显示，平均五个模型上 ALFWorld-Clarification 的 clarification F1 比 ReAct+UE 高 73%，比 UAM 高 36%。它对 coding assistant 也有直接启发：需求不明确时，agent 应区分“我不知道怎么做”与“用户没告诉我验收标准”，并把澄清作为可评测能力，而不是把所有不确定都压成继续搜索或继续实现。
🔗 链接：https://arxiv.org/abs/2606.19559 ｜ 代码：None

### 🔥 大佬观点

**CircleCI / Roger Winter：AI coding 速度必须和 CI 验证闭环绑定。**  
CircleCI 的 Claude Code + MCP 教程把观点落到工程实践上：AI 生成代码越快，越需要自动测试、配置验证、安全扫描和失败日志分析来兜底。它值得注意，因为这不是抽象“用 agent 写代码”，而是把 CI 平台变成 agent 可调用的反馈源，让修复、重跑、再修复形成可验证 loop。🔗 https://circleci.com/blog/getting-started-with-claude-code-and-circleci/

**Boris Cherny / Cat Wu（Claude Code 团队，经 The Neuron 访谈整理）：routine 的第一批真实用途是 code review、PR babysitting、CI fixes 和 rebasing。**  
这组观点与前几天的泛 loop engineering 不同，重点在于把循环落到具体 SDLC 任务：看 PR、跟 CI、修失败、重放上下文、在验证点停下。它提示我们评估 coding agent 时不应只测一次性补丁，还应测“无人值守但有停止条件”的维护类 routine。🔗 https://www.theneuron.ai/explainer-articles/claude-code-creators-boris-cherny-and-cat-wu-explain-how-to-use-agent-loops/

### ⭐ 超火仓库/项目

**agentmemory（rohitg00/agentmemory）：23k+ stars 的跨工具持久记忆层。**  
它火的原因是击中所有 coding agent 用户都会遇到的痛点：会话结束、compact 或换客户端后，agent 失去项目事实和历史决策。通过 MCP、hooks 和 REST 统一 Claude Code、Codex、Cursor、Gemini CLI 等客户端，它把“记忆”从某个模型的上下文技巧变成共享基础设施。🔗 https://github.com/rohitg00/agentmemory

**OpenClaw 2026.6.10-beta.1：开源 harness 继续修补长程状态正确性。**  
OpenClaw 近期 release 的重点不是炫能力，而是 transcript、partial turns、subagent completion、compaction alias 等运行时一致性细节。它火在说明开源 agent runtime 正进入“状态机和证据链”阶段：长程 loop 能否稳定跑完，取决于这些看似琐碎的边界条件。🔗 https://github.com/openclaw/openclaw/releases/tag/v2026.6.10-beta.1

**AgentBridge / Claude-Codex bridge：Claude Code 与 Codex 互相调用成为新协作模式。**  
多个小项目开始用 MCP、Claude Code Channels 或本地 daemon 让 Claude Code 和 Codex 在同一工作会话里互相发消息、请求 review、并行实现或共享状态。虽然单个仓库 star 数还不高，但它解决的痛点很真实：不同 vendor agent 各有强项，团队希望 maker/checker 或 planner/executor 能跨供应商组合，而不是手工复制粘贴 transcript。🔗 https://github.com/raysonmeng/agent-bridge

**PACMS + OpenClaw context-engine：上下文选择开始从 prompt 技巧变成插件市场能力。**  
PACMS 论文和 OpenClaw 插件机制共同说明，context management 正在被产品化为 swappable engine：保留什么、丢掉什么、预算多少、是否可视化，都可以成为 runtime 策略。它解决的是 agent 长程运行中最实际的 token、噪声和证据丢失问题，也会直接影响不同 harness 的公平比较。🔗 https://arxiv.org/abs/2606.20047
