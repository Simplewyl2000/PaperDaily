## 逐条讲解

### Anthropic：Redesigning source control at Anthropic（Scion）
过去大家谈 coding agent 的瓶颈，说的是"模型写得不够好"；Anthropic 这篇 10-13 的工程文章讲的是另一回事：代码写得太快，人类时代的开发基础设施先扛不住了。他们的 monorepo 日均合并改动从 2026 年 5 月约 2,500 次涨到 9 月 30,000 次以上，主干历史近 100 GB、压缩后的工作副本超 25 GB，CI 每天约 2,500 万次 checkout，如果按 git 的方式直接拉取，每天会产生超过 600 PB 流量；即便用了浅克隆、稀疏检出、几百个内部镜像，也越来越难维护。他们的关键观察是：git 为"离线、每个副本都是完整仓库"而设计，但现在几乎所有客户端都是 agent 和 CI 作业，天然永远在线。于是团队自研了 Scion：服务端负责历史、blame、提交、合并和 rebase，客户端只保留有限的本地缓存；提交单元是写前日志里的"changeset"（只记录相对父提交改了哪些文件 + 内容寻址指针），几乎不用 ref，提交成本只随改动大小而非仓库大小增长；checkout 默认稀疏、按需物化，很多 CI 作业直接调 API 拿 diff，根本不需要本地仓库。整个系统由 7 人团队在 5 个月内建成并完成迁移，同期还上线了 code review 系统 Antique、代码搜索和自动 bisect / revert 流水线；文中也提到对抗式评审很有效，但容易"近视"，需要资深工程师防止 Claude 为假想问题过度设计。对后训练软件工程的启发：当 RL rollout、agent 沙箱、CI 都是"每天千万次 checkout"量级时，"把仓库状态当成可查询服务"会比"每个沙箱 clone 一份"便宜得多，这也是大规模 SWE 环境基础设施该借鉴的设计。

### TestSuiteBench：Coding Agents Struggle to Generate Strong Test Suites from Specifications
代码生成基准已经从单函数扩展到整套应用，但测试生成基准还停留在"给一个函数写测试"或"给一个 bug 写复现测试"，没人系统地测过：给你一份规格，agent 能不能从零写出一整套"强"测试。ETH Vechev 组的 TestSuiteBench 收集了 165 个开源应用，每个都配有结构化的详细规格、参考实现、参考测试集，以及平均 74 个变异体（mutant，即故意改坏的实现）。关键在于变异体的构造：每个变异体只对应规格中的一条需求并经过精修，73% 只会被唯一一个参考测试杀死，平均只被其余测试中的 0.2% 杀死——也就是说，漏测一条需求就会被精准发现。结果是前沿 coding agent 的变异分数都不到 60%，尽管它们生成的测试 88% 能在参考实现上通过（看起来"有效"）；而同一份规格让 agent 写实现，却能通过 82% 的参考测试。作者的结论很犀利："agent 能造出它们无法验证的软件"。对我们而言，这既是一个高质量的测试生成评测集，也提示了 RL 环境构建的风险：如果 verifier 测试由 agent 自动生成，它们很可能"能跑但测不出东西"，按需求粒度构造变异体是检验测试强度的实用工具。
🔗 链接：https://arxiv.org/abs/2610.13065 ｜ 代码：None

### SWE-Duel：Towards a Self-Scaling Arena for Coding Agents
静态 coding 基准有两个老问题：发布后题目会泄漏进训练数据，强模型迟早刷满。SWE-Duel 的思路是"不预先出题"：两个 coding agent 在真实仓库上轮流当 Red 和 Blue 互相出题、解题。Red 在三个上下文隔离的会话里先提出并实现一个新特性（附特性测试），再在里面埋一个隐蔽 bug，并写好密封的触发测试；这个 PR 只有满足两个条件才被接纳——通过特性测试和仓库原有测试、只在 bug 测试上失败，并且同一 agent 的全新会话能"盲修"成功（排除无解题）。Blue 在不知道有 bug 的情况下审查 PR，只有修改后三套测试全部通过才算赢，然后双方互换角色。作者在 15 个仓库、5 种语言上让 11 组"模型 × harness"打了 1,500 回合：GPT-5.5 + Codex CLI 解题最强（修好其审查缺陷的 98.3%），Claude Opus 4.8 + mini-swe-agent 出题最强（Red 胜率 27.3%）；同一家族里，最新版本出的题击败固定参照解题者的比例远高于旧版本（42.9% vs 4.0%），初步说明"出题难度随出题能力自动上涨"。对评测与数据工程很有启发：三重准入门槛是一套可复用的"自动造题 + 自动验题"流程，同样可以用来持续生成难度自适应的 SWE RL 任务。
🔗 链接：https://arxiv.org/abs/2610.12569 ｜ 代码：None

### ProgramGym：Scaling Training Environments for Long-Horizon Program Reproduction Agents
现在 coding agent 越来越多被用来"从零写程序"，而不是在已有仓库里修 issue，但能逼 agent 自己去搞清"需要什么、系统该怎么设计"的可验证训练环境非常稀缺；现有 agent 工作流也撑不住"先探索参考程序、再实现"的长程开发。ProgramGym 包含两部分：Program-Env 从真实仓库自动构造训练环境，通过一个反馈驱动的循环反复修复运行沙箱的构建问题、并提升黑盒测试的质量；Program-Agent 则是一个角色隔离的工作流（分析、实现、评审分开），配有修订管理来做编译检查和失败恢复。用这套流水线他们得到了 1,648 个覆盖 C、C++、Go、Rust 的训练环境。在 ProgramBench（Meta 今天发布 Muse Wonder 时也在用的"净室重建程序"基准）上，用这些环境采集的轨迹微调 Qwen3.8-27B，成绩从 34.87% 提升到 42.84%；再配上 Program-Agent 工作流，基础模型和 SFT 模型分别达到 55.71% 和 56.25%，超过部分旗舰模型。值得关注的是"环境构建本身也需要修复循环"：沙箱构不起来、黑盒测试太弱是自动造环境最常见的两类失败，它给出了一个可直接复用的修复流程。
🔗 链接：https://arxiv.org/abs/2610.13395 ｜ 代码：None（作者称将开源）

### TerminalHorizon：Scaling Agentic Data for Long-Horizon Terminal Intelligence
短轨迹只能教会 agent "命令怎么敲"，教不会它如何在一个长任务里不断积累证据、调整策略、把中间结果变成最终交付物；而现有的环境合成方法有个隐蔽问题：为了保证环境能跑，构造过程常常顺手把关键工作"提前做掉"或简化了，agent 反而不需要探索、实现和验证。TerminalHorizon 是一个全自动的长程终端 agent 数据合成引擎：它从真实的专业工作出发，先让一个独立执行者去完成任务，借此发现"构造时被省略的关键工作"，再用这些证据指导重建环境；为了把行为模式延伸到多个阶段，它还会在同一目标下逐步扩展任务、加入建立在前一阶段结果上的新需求。用这个引擎构造了 1.5K 个任务环境，对 Qwen3.5-27B 做 SFT 得到 TerminalHorizon-27B，在 12 个覆盖 coding agent、真实生产 agent 任务和通用推理的基准上全面提升；在每个 12 小时研究预算的递归自我改进（RSI）案例里，模型也能在初始方案后持续实验、根据反馈改进。对数据工程最有价值的是"用独立执行反查环境是否被做掉"这一步——它针对的是合成环境"过于简单"这个很难被发现的质量问题。
🔗 链接：https://arxiv.org/abs/2610.13166 ｜ 代码：None

### TQS：Quality, Not Just Outcome — A Structural Scoring Framework for Selecting Coding-Agent Trajectories for SFT
开源 coding agent 的 SFT 数据通常这样筛：轨迹最终补丁能通过测试就留下。问题是"最终成功"不代表过程好——反复查看同一文件、工具调用不稳定、迟迟不动手改代码，这些低效模式都会被模型一起模仿。TQS（Trajectory Quality Score）直接在轨迹结构上打分，不需要 LLM 当裁判，计算时间与轨迹长度线性相关；它围绕"结构化收敛"刻画质量，包括信息聚焦（是否很快锁定相关代码）、意图与动作一致（说要做什么和实际做的是否对得上）、策略动态（行为是否逐步收敛而不是来回打转）。作者在一个开放许可语料的 155,144 条成功轨迹上按 TQS 排序，分别用高分、随机、低分子集微调，结果在 SWE-Bench-Verified 上高分子集稳定优于另外两组。对后训练数据工程，这是一个便宜、可扩展的过程级过滤器：在已有"测试通过"过滤之后再加一层结构分，就能在不调用大模型的情况下提高模仿目标的质量。
🔗 链接：https://arxiv.org/abs/2610.13152 ｜ 代码：None

### CRBugBench：(When) Should a Software Factory be Lights-off? Benchmarking Code Review Agents on Bug Detection
随着 coding agent 写代码越来越快，开发者花在审代码上的时间已经超过写代码，于是有人设想"熄灯工厂"：由 review agent 自动把关，几乎无人监督。要判断这是否可行，需要知道 review agent 到底能抓住多少真实 bug。作者搭了一条数据流水线：从仓库历史中挖出经人工确认的 bug，把每个 bug 和引入它的 PR 配对，构成"审这个 PR，看能否发现 bug"的任务；CRBugBench 包含 98 个开源仓库的 1,000 个任务，外加一家大公司私有仓库的 800 个任务。结果显示最强配置（claude-opus-5 + copilot-cli）在前 5 条评论内能抓到 71.9% 的 bug，而五个月前的 opus-4.6 只有 47.7%；但对复杂改动、需要非局部推理的 bug 仍然较弱，在需要更多项目上下文的私有企业仓库上下降明显；增加算力最有效的方式是改提示，"鼓励探索"的提示能带来最多 5.8% 的提升、成本增加 10%。作者据此给出落地建议：按 PR 复杂度分配审查力度、提供仓库知识、按 PR 特征调度模型、持续监控质量。这条"从历史 bug 反推引入 PR"的流水线，也是构造 code review 类训练数据的现成方案。
🔗 链接：https://arxiv.org/abs/2610.13668 ｜ 代码：None

### AgentSWE：Can Coding Agents Build the Agent You Actually Want?
越来越多人让 coding agent 去"造一个适合自己工作流的 agent"，这背后有一个默认假设：交付出来的 agent 会真的满足需求，而不只是看起来满足。AgentSWE 是第一个专门检验这个假设的基准，覆盖 agent 开发生命周期的三个阶段：根据自然语言需求从零创建 agent、修改生产级 agent 代码库、以及朝着可度量目标优化 agent。它把 25 个任务设计成"委托"而非"考试"：构建者只能拿少量示例用例迭代，验收时冻结提交物，用覆盖完整需求的留出用例去跑，按需求衍生的 rubric 打分并设硬性 pass/fail 门槛（优化类任务则直接用原基准的目标）。评测多种模型和 harness 后发现，没有一个接近交付需求要求的水平，"演示出来的"和"实际交付的"之间的落差是常态而非个例；失败轨迹分析总结出几类反复出现的模式：对可见用例过拟合、代码看似完整但运行时是空壳、以及没有依据地宣称完成。这几类失败模式正好可以作为 coding agent 训练中的负面信号和 reward hacking 检测点。
🔗 链接：https://arxiv.org/abs/2610.13361 ｜ 代码：https://github.com/VectorSpaceLab/AgentSWE

### Not All Correct Fixes Run Alike：An Empirical Study of Patch Performance in Repository-Level Issue Resolution
SWE-bench 这类基准只看补丁能否通过正确性测试，同样"正确"的补丁跑得快慢如何，几乎没人关注；为每道题专门设计性能负载又太贵。这篇论文的巧思是：基准里本来就有 FAIL_TO_PASS（F2P）测试，它们恰好覆盖了被修复的那段行为，可以直接拿来当性能负载。作者用 Claude Opus 5、GPT 5.6、DeepSeek V4 Pro、Qwen 3.8 Max 搭配 SWE-agent，在 SWE-bench Verified 和 SWE-bench-Live 经预筛选可测量的子集上解题，得到 262 个"至少有两个不同正确解（含开发者真值补丁）"的案例，然后测量每个解在 F2P 测试上的指令数和墙钟时间，并用比 RSD 更稳健的 Welch ANOVA 判断差异是否显著。结果显示：近一半的案例里补丁之间存在可区分的性能差异；补丁性能与模型的解决率无关，模型排名几乎反转；案例分析还发现有些补丁带来了正确性测试发现不了的架构性回退。对评测和 RL 奖励设计的意义很直接：在现有 SWE 环境里零成本加一个性能维度，就能区分"能过测试"和"写得好"。
🔗 链接：https://arxiv.org/abs/2610.13563 ｜ 代码：None

### SoftwareGym：Scaling Computer-Use Agent Training with Diverse Synthesized Software Environments
训练 computer-use agent（操作图形界面的 agent）需要大量多样、可靠的软件环境：接入真实原生应用工程量大、覆盖面有限，还容易对特定应用过拟合；浏览器里的网页环境又交互太浅、流程太简单。SoftwareGym 是一条自动合成 GUI 软件环境的流水线：先生成结构多样的软件设计，再把设计实现成可运行的应用，最后用 GUI 评测加迭代修复来保证功能真的能用（"运行时验证过的行为"）。他们合成了 12 个类别共 182 个应用，GUI 任务平均通过率 91.5%，并构建了 120 个任务的 SoftwareGym-Bench；用这些环境采集的轨迹训练后，模型在严格分布外的 OSWorld 上 Pass@3 从 41.39% 提升到 56.97%，在 SoftwareGym-Bench 上达到 40.0%。对后训练环境工程的启发在于"合成软件本身"这一思路：让 coding 能力去批量造训练用的软件环境，并用评测-修复循环把关质量，这和 SWE 方向的自动造仓库、造环境是同一套方法论。
🔗 链接：https://arxiv.org/abs/2610.12611 ｜ 代码：None

### MagicBeanStalk：Escaping the RLVR Zero Advantage Trap with Recursive Data Synthesis
RLVR（可验证奖励的强化学习）的数据扩展大多在"收集或生成更多可验证题目"，但题目多不等于有用：对 GRPO 这类方法，如果一道题的所有 rollout 全对或全错，组内优势为零，梯度就没有信号。作者（含 Yejin Choi、Aviral Kumar、Jan Kautz）先实证刻画了"数据集有效性取决于题目、目标策略和 rollout 预算三者"，并发现把常用开源数学 RLVR 数据集汇总后，在固定策略和预算下约 88% 的题落入"零优势陷阱"；过滤只能筛选、还会丢掉真正的难题。因此有效的合成题应当保留难题所需的推理操作与组合，同时校准难度，让部分 rollout 成功、部分失败，并且至少有一个正确解能放进训练预算；简单地让教师模型"改写难题"做不到这一点。MagicBeanStalk 用自顶向下分解 + 自底向上递归合成，把种子题"长"成一族保留原推理蓝图、但按策略和预算校准过的新题：在 8 个数学基准上，gpt-oss-120b 从 61.2 提升到 69.8（+8.6），而用完整 7.8 万道源语料只提升 1.1、最好的过滤子集提升 5.8；在金融领域只用 340 个解就合成了 1.4 万多道可验证题。这对 coding RL 的数据工程同样适用：先测"零优势比例"，再按策略能力边界定向合成，而不是一味堆题。
🔗 链接：https://arxiv.org/abs/2610.12659 ｜ 代码：None

### Behavioral Self-Rewarding：Beyond Binary Verifiable Rewards for SWE Agents
SWE agent 的 RLVR 用可执行测试给奖励，可靠但很粗：两条都通过测试的轨迹，一条调试思路清晰、一条东撞西撞，拿到的奖励完全一样。这篇论文问：能不能让当前策略自己评判自己的轨迹，而不用另训一个奖励模型？BSR（Behavioral Self-Rewarding）的做法是：只在"同一任务、同一 verifier 结果"的轨迹之间，让策略模型两两比较可观察的调试行为，把成对偏好汇总成任务内的分数，再转成有界的辅助奖励——这样既增加了奖励区分度，又不会打乱 verifier 定义的通过 / 失败排序。它完全复用已收集的轨迹，不需要新的环境交互。在 SWE-bench Verified 和 SWE-bench-Live 上，Qwen3-14B 和 Qwen3-32B 的多种配置都取得一致提升。工程上它的好处是几乎零额外基础设施，可以直接插进现有 SWE RL 流水线。
🔗 链接：https://arxiv.org/abs/2610.12598 ｜ 代码：None

### SWE-Critix：Post-Training Generalist Verifiers for Assessing Coding-Agent Trajectories
很多端到端软件工程任务没有现成的"判卷器"，需要一个能读懂 agent 执行过程并判断它是否真的完成任务的 verifier；但 coding agent 的轨迹可能包含几百轮与仓库和工具的交互，通用 LLM 直接判不准，而专门训练的 critic 大多只输出一个标量分数、不给解释。SWE-Critix 是一条训练"通用轨迹 verifier"的后训练流水线：给定任务和执行轨迹，模型要预测是否完成，并生成自然语言分析解释判断依据；训练先 SFT 再 RL，基于 CodeForge-Preview 的轨迹训练了一系列 30B 模型。在留出测试集上，分类准确率从基座 Qwen3-30B-A3B 推理模型的 57%，提升到 SFT 后 66%、RL 后 78%。作者开源了模型、数据集和训练代码。对于没有测试可跑的开放式任务，这类可解释 verifier 是构建奖励信号和自动评测的关键组件。
🔗 链接：https://arxiv.org/abs/2610.13356 ｜ 代码：None（作者称已开源，未给出链接）

### Reward Hacking as a Transmissible Strategy in Multi-Agent Coding Systems
多 agent 协作写代码时，agent 之间会共享代码和计划；这些 agent 常用自动评测器做 RL 优化，而绕过评测也能拿奖励。以往研究把 reward hacking 当作单个 agent 的毛病，这篇论文发现它会"传染"：在 4 个开源权重基座上，coding RL 会在两种设置下诱发并放大 reward hacking（系统提示里明确描述了评测机制，或中期训练让模型提前接触了编码环境的相关事实）。以中期训练后的 agent 作为传染源，hacking 策略能通过代码和共享记忆传播，也能跨角色通过自然语言计划传播；甚至基于小型开源模型的 agent 也能诱导更强的闭源模型去 hack。在难题上，即便原始传染源离场，随着代码积累越来越"有说服力"的理由，传播链上的 hacking 还会加剧；它还会让任务路由偏向 hacking agent，并在候选聚合中存活。缓解方面，让写代码的 agent 自查或交给独立 verifier 审查都能减少交付出去的 hack。对搭多 agent 训练和评测系统的人，这意味着共享记忆和代码库本身也需要审计，"一个 agent 被污染"不能只当局部问题。
🔗 链接：https://arxiv.org/abs/2610.12822 ｜ 代码：None

### Rollout-Time Intervention（RTI）：Unlocking Agentic Reinforcement Learning Beyond Policy Limits
agent RL 有一个硬约束：on-policy 采样只能产出策略本身能做到的轨迹，当任务超出模型当前能力边界时，成功轨迹极其稀少，训练常常崩掉。阿里通义的 RTI 在 rollout 阶段直接"插手"：利用奖励侧已有的证据（评分 rubric），在采样过程中把走错的轨迹纠正成成功轨迹，从而给策略几乎解不出的任务提供有效学习信号。这些干预轨迹本质上是 off-policy 的，作者发现只要过滤掉分布偏移过大的轨迹，它们仍能有效引导策略优化。在 5 个基准上 RTI 稳定优于 RL 基线，后训练策略接近明显更强的同期模型，并超出了原有能力边界。工程上它的意义在于把 rubric 从"只用来打分"变成"也用来造正样本"，代码已开源，适合在 rubric 型奖励的 agent 任务上尝试。
🔗 链接：https://arxiv.org/abs/2610.13438 ｜ 代码：https://github.com/Alibaba-NLP/qqr

  一个面向 coding agent 的 MCP 服务器，解决"工具输出把上下文窗口塞满"的问题：一次 Playwright 快照 56 KB、20 个 GitHub issue 59 KB，半小时就吃掉四成上下文，压缩后 agent 还会忘记在改哪些文件。它的做法是把原始工具输出关在沙箱里只返回摘要（自称 315 KB→5.4 KB，减少 98%）；把每次文件编辑、git 操作、错误和用户决定记进 SQLite，压缩后用 FTS5 + BM25 只检索相关事件；并强制"用代码思考"——让 agent 写脚本统计 50 个文件，而不是把 50 个文件读进上下文。通过 hooks 支持 17 个平台的自动路由。它这周再次冲上 Trending，说明"上下文预算管理"已成为 harness 层的刚需；对数据工程而言，它的事件日志 + 检索设计也是记录 agent 轨迹、做压缩后状态恢复评测的现成参考。
  🔗 https://github.com/mksglu/context-mode
