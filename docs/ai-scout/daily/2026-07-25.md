## 📝 逐条讲解

### Anthropic Claude Opus 5：面向长程 coding agent 的更低 cost-per-task 官方模型
过去几周的 agent 讨论已经越来越少只看“模型分数”，而是看一个模型在真实 harness 里每个成功任务要花多少钱、会不会反复跑偏、能不能自己验证工作。Anthropic 7 月 24 日发布 Claude Opus 5，官方定位是接近 Fable 5 前沿智能但成本约为一半，并保持 Opus 4.8 的 API 价格。它最贴近本日报主题的部分是 software engineering：官方称 Opus 5 在 Frontier-Bench v0.1 上超过其它模型，在 CursorBench 3.2 max effort 下接近 Fable 5 峰值，同时在不同 effort 档位上给出更好的 cost-per-task 曲线。早期用户案例也很“工程化”：模型会为缺少外部 feed 的交易所数据任务自己搭 test harness，会在 PR 交接前检查分支、模板和测试影响，也会在前端任务中打开页面检查桌面和移动端布局。更重要的是配套运行时更新：Claude Platform 支持 mid-conversation tool changes，不再因为工具变化就让 prompt cache 失效；API 还支持 safety classifier 触发后的 automatic fallback。对后训练软件工程的启发是，未来训练和评测不能只记录“用了 Opus 5”，还要记录 effort、fallback、工具集变化、prompt cache 状态和每个成功任务成本。这个发布按 High 收录，因为它虽然是模型发布，但官方材料直接围绕 coding agent、tool runtime 和验证行为展开。
🔗 链接：https://www.anthropic.com/news/claude-opus-5 ｜ 代码：None

### Harness AI Evals / AgentTrace：把 agent 质量门接入 CI/CD 与生产 trace 闭环
很多团队做 agent 原型很快，但真正上线时会遇到传统测试体系不擅长的问题：agent 不崩溃也可能答错，质量不是二值，模型和 prompt 会漂移，生产失败还很难变回回归测试。Harness 7 月 21 日发布 AI Evals，并把它放进 Agent DLC / AgentTrace 叙事里，核心是让 agent eval 成为原生 CI/CD pipeline step，而不是一个工程师本地跑的脚本。它支持 offline evaluation，在部署前用 golden dataset 测 correctness、faithfulness、tool correctness、安全和任务完成度；也支持 online evaluation，用同一套指标评分真实生产输入，再把失败案例加入后续离线数据集。开源侧的 `harness-evals` 提供 correctness、groundedness、safety、trajectory、performance 等指标，可以通过 exit code、baseline regression 和 `--fail-under` 进入任意 CI。这个方案的亮点是把 production trace、eval dataset、release gate、RBAC、OPA policy 和 audit trail 接在同一条链上。它解决的真实痛点是“agent 改了 prompt 或模型后，到底可不可以发布”，而不是只给一个 dashboard 分数。对后训练数据工程来说，这类 trace-to-dataset loop 会把线上失败、tool path、阈值、人工标注和后续回归结果变成高质量训练/评测素材。
🔗 链接：https://www.harness.io/blog/introducing-ai-evals ｜ 代码：https://github.com/harness/harness-evals

### UiPath coder_eval：用 YAML、sandbox 和 CI gate 评估 Claude/Codex/Gemini coding agents
公共 benchmark 能告诉你某个 agent 在通用任务上大概多强，但团队真正关心的是：我的技能、我的仓库规则、我的 CLI 配置和我的模型组合是不是变好了。UiPath 7 月公开的 `coder_eval` 把这个问题做成可复现实验框架，用 declarative YAML suites 描述任务、评分权重、sandbox 和要比较的 agent。它支持 Claude Code、Codex 和 Gemini/Antigravity 这类 coding-agent runtime，也强调技能评估，例如检查某个 skill 是否真的被触发，而不是只看最后输出像不像。GitHub 元数据核验显示该仓库 7 月 9 日创建、7 月 24 日仍活跃推送，当前约 107 stars，说明它不是大热项目，但工程方向很实用。相对普通 LLM eval，coder_eval 运行的是完整 agent：它会在隔离环境中观察文件、执行命令、多轮迭代，再输出结构化结果。对工程团队来说，它可以用于 A/B 测试 Claude vs Codex、skill on/off、prompt variant、工具权限变化，甚至把 agent regression 接进 CI。对后训练软件工程来说，这类 eval harness 能产生包含配置、工具调用、文件 diff、验证结果和成本的标准化轨迹，比单条聊天记录更适合长期比较。
🔗 链接：https://github.com/UiPath/coder_eval ｜ 代码：https://github.com/UiPath/coder_eval

### SWE-MeM：让长程 coding agent 学会何时压缩、压缩什么、如何压缩
长程 coding agent 经常被上下文窗口拖垮：它读了很多文件、跑了很多命令、经历多次失败，后面要么忘掉早期关键线索，要么把大量无关历史一直带着走。传统做法通常是固定时机压缩，比如到窗口快满时总结一次，但这并没有教会 agent 根据任务状态主动管理记忆。SWE-MeM 提出一个 adaptive memory management framework，让 agent 可以调用一个 memory tool，自己决定什么时候压缩、压缩哪些内容、以及用什么摘要粒度保留信息。训练上，作者合成包含任务求解和记忆管理的轨迹，并用 Memory-aware GRPO 把 issue resolution 与 memory efficiency 一起优化；它还通过 memory-aware trajectory splitting 做步骤级 credit assignment。论文报告在 SWE-Bench Verified 上，4B 和 30B 模型分别达到 43.4% 与 60.2% resolve rate，并优于静态压缩基线。这个工作值得关注，因为它把“上下文工程”从手写策略推进到可训练的工具使用行为。对后训练数据工程来说，成功轨迹不应只保存最终 patch，还要保存压缩触发点、被保留/丢弃的信息、摘要质量和后续是否因为记忆选择而成功或失败。
🔗 链接：https://arxiv.org/abs/2606.28434 ｜ 代码：None

### Promptfoo coding-agent evals：把 Codex SDK、Codex app-server、Claude Agent SDK 纳入同一评测配置
评估 coding agent 和评估普通聊天模型不同，因为 agent 的能力来自“模型 + 文件系统 + shell + approval + skills + app-server protocol”的组合。Promptfoo 新的 coding-agent eval guide 把这个差异拆成 provider tiers：Tier 0 是纯文本模型，Tier 1 是 Codex SDK、Claude Agent SDK、OpenCode SDK 这类会读写仓库的 agent SDK，Tier 2 是 Codex app-server / Open Interpreter 这类 rich client server。它的实用价值在于把这些 runtime boundary 都放进 YAML 配置里，团队可以明确设置 working_dir、read-only sandbox、network/search 开关、allowed tools、approval policy 和 output schema。文档还给出 app-server approval eval 的例子：不是检查最终回答是否说“我被拦住了”，而是从 provider metadata 中断言真的出现了 command approval request。另一个关键点是 trace assertions，例如检查 agent 是否实际运行过 `pytest`、是否使用了特定工具、step count 是否超出预期。这样做能把“看起来完成任务”拆成路径、成本、权限和可验证 side effect。对后训练软件工程来说，这类配置化 eval 可以成为私有回归套件，也能给训练数据提供可复现的 runtime 元信息。
🔗 链接：https://www.promptfoo.dev/docs/guides/evaluate-coding-agents/ ｜ 代码：https://github.com/promptfoo/promptfoo

### Vercel skills CLI v1.5.20：把 agent skills 做成跨 70+ agent 的可安装包管理层
随着 Claude Code、Codex、Cursor、Gemini CLI、OpenCode 等工具都开始支持 skills / rules / agent instructions，团队很快会遇到一个新问题：同一套工程流程如何在不同 agent 宿主里安装、升级和共享。Vercel Labs 的 `skills` CLI 把这件事做成类似包管理器的体验，7 月 22 日发布 v1.5.20，GitHub 约 27.1k stars。开发者可以用 `npx skills add owner/repo` 从 GitHub、GitLab、URL 或本地目录安装 skill，也可以 `find`、`list`、`check`、`update`、`init` 管理生命周期。它支持项目级和全局级安装，也支持 symlink/copy 模式，让团队能把 skills 提交进仓库或作为个人工具箱使用。这个方向解决的痛点不是“写一段更好的提示词”，而是把技能分发、版本、兼容目标和团队共享变成可治理资产。对于后训练软件工程，skills CLI 这类基础设施会影响轨迹分布：同一任务在安装了不同版本 skill、不同宿主适配器和不同 scope 时，会产生不同工具调用和验证行为。未来如果要从真实 agent 使用中抽取训练样本，必须记录 skill package 名称、版本、安装范围和触发证据。
🔗 链接：https://github.com/vercel-labs/skills ｜ 代码：https://github.com/vercel-labs/skills

### RepoAgentBench v0.1：从自己的 merged PR 生成本地、低污染 coding-agent benchmark
公共 benchmark 的最大问题之一是离真实团队太远：它测的是别人选好的仓库、别人设计的测试和可能已经进入训练语料的任务。RepoAgentBench 的想法很直接：把你自己仓库里已经 merged 的 PR 变成可回放 benchmark task。它用 PR 描述作为目标，把 PR 中新增或修改的测试作为验收标准，再把 source patch 和 test patch 分开，使起始状态变成“新测试已经存在、源码还没修复”。这样 agent 要做的事情更接近真实维护工作，而且团队可以选择模型 cutoff 之后的 PR 来降低污染风险。v0.1 还提供 per-task venv isolation、`verify.sh` 自动生成、`manifest.json`、`events.jsonl`、`verification.json`、`report/replay/diff` 等结构化 artifact。虽然 GitHub star 很低，可信度不能和大厂框架相比，但它代表了一个很重要的评测方向：从“通用榜单”转向“你的仓库、你的测试、你的约束”。对后训练数据工程来说，PR-to-task mining 也可以成为数据构造 pipeline，关键是同时保存原始 PR、测试来源、被反转的 patch、验证脚本和 agent 运行轨迹。
🔗 链接：https://pypi.org/project/repoagentbench/ ｜ 代码：https://github.com/HumphreySun98/repoagentbench

### How to Run Agent Evals in CI Without a Flaky Gate
把 agent eval 放进 CI 很诱人，但如果每个 LLM judge 分数波动都能阻塞 PR，工程团队很快会把它关掉。Dreaming Press 这篇文章把 release gate 分成两层：第一层是 deterministic contract assertions，第二层是带噪声的质量趋势。第一层包括 JSON/schema 是否有效、工具参数是否正确、是否泄露 secret、是否包含 PII、是否违反明确 policy；这些应该像单元测试一样稳定，适合 hard-fail。第二层是 helpfulness、tone、语义质量这类 LLM-as-judge 指标，更适合 dashboard、趋势线和持续下降告警，而不是单次构建 veto。这个区分很重要，因为它避免把非确定性模型评分硬塞进确定性 CI 语义里。它也呼应 Harness、Promptfoo、OpenAI skill eval 的共同方向：尽量先用代码能验证的东西做门禁，再让 judge 处理真正无法形式化的部分。对后训练软件工程来说，这提醒我们给轨迹打标签时也要区分 hard contract failure 和 soft quality degradation，否则训练/评测信号会混在一起。
🔗 链接：https://dreaming.press/posts/how-to-run-agent-evals-in-ci-without-a-flaky-gate.html ｜ 代码：None

### Cline MCP setup guide：把 MCP server 安装、配置和 agent-generated server 做成开发者流程
MCP 的理论很简单：让 agent 通过统一协议连接工具、数据库和服务；但真实开发者卡住的地方往往是安装、凭证、配置文件、重启和权限边界。这个 7 月 MCP setup guide 把 Cline、Cursor、Continue.dev、Claude Code、Windsurf 等工具的 MCP 接入方式做了横向说明，其中 Cline 被描述为有比较成熟的 marketplace 和配置体验。Cline 用户可以在面板里浏览并安装 server，也可以直接编辑 `cline_mcp_settings.json`，保存后通常能被热加载。文章还提到一个值得注意的模式：当不存在合适 server 时，可以让 Cline 根据自然语言描述 scaffold 一个简单 MCP server，再由人类 review。这个做法很贴近 Agent-Friendly Tooling，因为它把“把某个服务变成 agent 可用工具”从手写 glue code 推向可生成、可安装、可审查流程。风险是自动生成 MCP server 容易带来权限过大、错误认证和未处理 rate limit，因此安装体验越顺滑，权限和审计越要显式。对后训练软件工程来说，MCP 配置、server 来源、权限提示和生成后人工修改都应该进入轨迹元数据。
🔗 链接：https://cursor-alternatives.com/blog/mcp-setup-guide-ai-coding-agents/ ｜ 代码：None

### AGENTS.md vs CLAUDE.md：跨 agent 仓库指令标准与 Claude 专用记忆如何分层
很多仓库现在同时服务人类开发者和多个 AI coding agent，但 README 往往太长、太人类化，模型也很难从里面稳定抽取“应该运行哪个测试、禁止改哪些文件、架构约束是什么”。AGENTS.md 的定位是给 agent 的 repository brief：用明确、可执行、可继承的方式写构建命令、测试命令、代码风格、安全限制和目录约定。Dreaming Press 的文章把 AGENTS.md 和 CLAUDE.md 的关系讲得比较清楚：AGENTS.md 适合跨工具共享，CLAUDE.md 则适合 Claude Code 专用的 memory/import/layering 能力。它还强调 nested scope：在 monorepo 中，根目录 AGENTS.md 给全局规则，子目录 AGENTS.md 覆盖更窄的路径，离目标文件越近的规则越具体。这个分层解决了团队常见痛点：不同 agent 读取不同隐藏配置，最后行为漂移、review 时说不清有效规则是什么。对后训练数据工程来说，repo-level instruction 文件不是背景噪音，而是 agent 行为的重要输入；记录适用的 AGENTS.md/CLAUDE.md 版本、scope 和冲突解析，才能复现一次代码修改为什么发生。
🔗 链接：https://dreaming.press/posts/agents-md-vs-claude-md.html ｜ 代码：https://github.com/agentsmd/agents.md

### Anthropic Project Pilot / Drone-Bench：把 AI 控制无人机拆成可评测的五个子任务
Project Pilot 不是软件工程主题，但它是 Anthropic 7 月 24 日官方 Research 新发布，且和 computer use / agent evaluation 的工程方法有关，因此按 Low 收录。Anthropic 与 Andon Labs 把“AI 控制无人机在室内找到并跟随某个人”拆成 Drone-Bench：Reconstruct、Localize、Navigate、Detect、Follow 五个子任务。这个拆法很有工程意义，因为端到端任务失败时，团队能知道是建图失败、定位失败、导航失败、目标识别失败，还是目标跟随失败。搜索摘要显示 Fable 5 在多数子任务上超过 baseline，但 reconstruction 的短板会传导到 localization 和 navigation，阻碍真实无人机端到端自治。它的价值不在于鼓励无人机应用，而在于展示 frontier red team 如何把高风险自治能力拆成可测、可复现、可比较的 harness。对后训练软件工程的间接启发是，复杂 agent 任务也应按必要子能力拆解，并记录每个子任务的 verifier 和误差传导，而不是只给一个最终成功/失败标签。
🔗 链接：https://www.anthropic.com/research/project-pilot ｜ 代码：None

## 🔥 社区热点专栏

### 🔥 大佬观点

**VentureBeat / Artificial Analysis：Opus 5 的重点不是“又一个大模型”，而是 cost-per-task 和 agent runtime 经济性。**
围绕 Anthropic Opus 5 的报道和测评都把焦点放在“接近 Fable 5 的智能、明显更低的任务成本”，并特别提到 mid-conversation tool changes、automatic fallback 和 OSWorld / Frontier-Bench / CursorBench 这类 agent benchmark。这个观点值得注意，因为 coding-agent 选型正在从单次能力转向“相同预算下能完成多少可验证任务”。🔗 https://venturebeat.com/orchestration/anthropic-launches-claude-opus-5-a-cheaper-ai-model-for-coding-agents-and-enterprise-workflows ｜ https://artificialanalysis.ai/articles/opus-5

**Hacker News：通用 SWE-bench 分数不够，团队开始做“evals for your repo”。**
HN 讨论里一个反复出现的共识是，公共 benchmark 不能告诉你 agent 是否适合自己的代码库、测试策略和架构约束；更有价值的是从真实 merged PR、linter、scope footprint 和 review 质量构造私有 eval。这个方向和 RepoAgentBench、Harness AI Evals、Promptfoo coding-agent evals 同频：评测工程正在从榜单消费走向团队本地数据生产。🔗 https://news.ycombinator.com/item?id=47344709

### ⭐ 超火仓库/项目

**addyosmani/agent-skills：约 80.2k stars，24 个 production-grade engineering skills，把 senior engineer 流程变成 agent 可执行 runbook。**
它火在解决 coding agent 最常见的“跳过 spec、测试、安全 review 和 scope 控制”问题：每个 skill 都包含 workflow、verification gates 和 anti-rationalization 表。真正的 insight 是，团队经验正在从口头提示词迁移到可安装、可版本化的技能包，成为 agent 的质量门。🔗 https://github.com/addyosmani/agent-skills

**gastownhall/beads：约 25.6k stars，v1.1 近期发布，把 agent memory 做成 Git-backed issue graph。**
Beads 的卖点不是普通 TODO list，而是用 Dolt-backed、可分支/合并的结构化 issue database 替代 Markdown 计划，支持 dependency graph、auto-ready task detection、semantic compaction 和多 agent 协作。它火在解决长程 agent 会话死亡、计划漂移和多分支冲突的真实痛点。🔗 https://github.com/gastownhall/beads

**vercel-labs/skills：约 27.1k stars，v1.5.20，成为跨 agent skills 的包管理器。**
`npx skills` 把技能发现、安装、更新和脚手架化做成统一 CLI，支持 Claude Code、Codex、Cursor、Copilot、Gemini CLI、OpenCode 等大量宿主。它火在把“共享 agent 指令”从复制粘贴变成生态基础设施，未来团队可能像管理 npm 包一样管理 agent skills。🔗 https://github.com/vercel-labs/skills
