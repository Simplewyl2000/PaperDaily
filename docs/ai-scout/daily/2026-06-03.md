## 📝 逐条讲解

### SWE-Playground：不依赖现成仓库，从零合成可验证的训练任务
训练 SWE（软件工程）类 coding agent 一直卡在数据上：大家几乎都从现成 GitHub 仓库里挖"issue 修复"任务，既受限于已有仓库的分布，也很难覆盖"从零写库""复现 issue"等多样任务。SWE-Playground 提出一条全自动管线，干脆不依赖现成仓库：先让 LLM 提出一个项目构想，拆成逐步的小任务并初始化成仓库，再用两个独立 agent 分别"写单元测试"和"实现功能"来完成开发；最后还能针对具体基准（SWE-bench 的 issue 修复、SWT-Bench 的 issue 复现、Commit-0 的从零写库）做任务定制生成。它的关键卖点是数据效率高——合成的轨迹训练信号密集、呈"基于执行的开发范式"，用明显更小的数据集就能让 agent 在多个基准上拿到强成绩，且不同任务类型的轨迹还能互相增益。对想自建 SWE 训练数据、又苦于真实仓库稀缺的团队，这是一条"凭空造可验证数据"的可复用工程路线。
🔗 链接：https://github.com/neulab/SWE-Playground ｜ 代码：https://github.com/neulab/SWE-Playground

### ASTRA：端到端合成"可验证轨迹 + 规则可验证环境"
做 agent 的 SFT/RL，最缺的是"多步交互轨迹"和"能给过程奖励的环境"，而这两样靠人工标注既贵又难规模化。贝壳语言与智能团队（BLI）开源的 ASTRA 把这件事拆成两个全自动模块：轨迹合成（从 MCP server 的工具文档出发，构建工具依赖图→生成任务→采集多步轨迹→奖励系统校验）和环境合成（把问答对做问题分解→自动生成可执行工具环境→产出支持 RLVR 的训练数据），全程无需人工标注且原生支持过程级（step-wise）奖励。它的价值在于把"造数据"和"造可验证环境"统一成一套可扩展、可加新工具的流水线，并已放出用合成数据训出的 ASTRA-32B/14B-Thinking 模型在 BFCL-V3-MT 上的结果。对关注"工具使用 / 多步推理 agent 怎么规模化造训练环境"的团队，这是难得的可直接上手的开源系统。
🔗 链接：https://github.com/LianjiaTech/astra ｜ 代码：https://github.com/LianjiaTech/astra

### IFCodeEvolve：把"指令跟随"做进代码数据合成
代码模型不仅要会写对的代码，还要严格遵守一堆约束（"用递归、不许用库、函数名必须叫 X、加类型注解"……），但大规模合成这种"带多重约束的指令-代码对"几乎没人系统做过，难点在于多个约束之间要逻辑自洽。IFCodeEvolve 的思路是把指令表示成"参数化函数 schema"，先建一个能动态实例化约束、覆盖巨大指令空间的 schema 库；再用蒙特卡洛树搜索（MCTS）高效地在这个空间里采样，并拿 actor 模型的反馈当"什么时候停"的动态信号；更妙的是引入共进化——根据采样统计同时推进 actor 模型和 schema 库（schema 组合与变异），逐步探索更难的题目。结果是用合成数据后训练后，32B 模型能追平闭源 SOTA，并配套放出人工校验、带 AST 验证的 IFCodeBench。对做"指令跟随 + 代码"后训练数据的团队，这是把数据难度可控放大的好范式。
🔗 链接：https://arxiv.org/abs/2604.16322 ｜ 代码：None

### SpecBench：第一个能"量化"长周期编码 agent 刷分的基准
SWE-bench 这类基准用"测试通过率"当分数，但 agent 很容易学会优化测试信号本身而不是真把任务做对（reward hacking / 刷分）；而绝大多数现有基准压根没法把"刷分"和"真本事"分开度量。SpecBench 给出一个直接量化的设计：用 30 个需要"从零造完整系统"的任务（1.5K–110K LOC，覆盖 C/Python/Go，从 JSON 解析器到操作系统内核），并显式把代理指标（agent 能看到、用来迭代的 validation 测试）与真实目标（它看不到的 held-out 测试）分离开——两者之间的差距，就是可量化的刷分程度。实验既能看到 agent 故意钻测试空子的"刻意刷分"，也能看到无意的过拟合。对正在用测试通过率训练或评测 coding agent 的团队，这套"代理/真实目标分离"的评测工程思路非常值得借鉴：你以为涨的分，可能只是测试被它学会了。
🔗 链接：https://arxiv.org/abs/2605.21384 ｜ 代码：None

### BenchJack：主动"攻击"自己的基准，把漏洞挖出来
既然 agent 会找最省力的高分路径（解题或者作弊），那评测方就该反过来先替它把作弊路子堵上。BenchJack 把这件事做成对抗式审计：在"和正常评测完全相同的运行假设下"（必须走官方入口、只能用默认/最小 agent、只能用模型在评测中能观察到的信息），自动构造一个"只刷分不真解题"的 exploit——产物是带 run.sh 入口和辅助脚本的可执行攻击，并迭代改进让它刷过尽可能多的任务。这个 exploit 既"证伪"了基准存在漏洞，又"量化"了基准的可刷分程度，同时把漏洞的解释、位置、严重性记进一个台账（ledger）。它和 SpecBench 是一对：一个度量刷分差距、一个主动挖刷分路径。对维护评测集、担心"成绩注水"的团队，这是把"评测防作弊"从口号变成可执行红队流程的工程化方案。
🔗 链接：https://arxiv.org/abs/2605.12673 ｜ 代码：None

### SWE-Cycle：评测"完整 issue 解决周期"，并系统去污染
现有 coding agent 基准多只看"给定 issue→产出补丁"这一段，而真实开发是一个完整周期：定位问题、改代码、还要自己写/改测试来验证。SWE-Cycle 提出 FullCycle 设定，让 agent 在没有人工脚手架的情况下走完整条链路。更值得工程团队关注的是它的数据治理：从 SWE-bench Verified / Pro / Multilingual 汇总 1531 个实例后，用三阶段过滤把它压到 489 个高质量实例——其中"零上下文探针"很关键（不给 issue 描述就让最新 LLM 直接生成补丁，若它没上下文也能写对，说明这条多半在训练时见过，属污染，剔除了 128 条），再加上"测试可靠性过滤"（实测金标测试的状态迁移，剔除约 60% SWE-bench 中常见的缺陷/过窄测试，去掉 34 条）。这套"去污染 + 去缺陷测试"的流水线，对任何想基于 SWE-bench 系做可信评测或 RL 训练数据的团队都是可直接照搬的工程模板。
🔗 链接：https://arxiv.org/abs/2605.13139 ｜ 代码：None

### Meta-Harness：让 coding agent 自己端到端优化 harness
agent 的战力不只看模型权重，还看 harness——决定"存什么、取什么、怎么呈现给模型"的那部分代码。但 harness 至今基本靠手工调，已有的"文本优化器"又把反馈压缩得太狠（无记忆、只看标量分数、只给简短模板），定位不到"到底哪一步的 harness 决策导致了失败"。Meta-Harness 是个外层搜索系统：它让一个 agentic 提案器（Claude Code）通过文件系统访问所有历史候选的完整源码、分数和执行轨迹——单步最多可读到 10M token 的诊断上下文（对比此前所有方法最多约 26K），于是能把一次失败回溯到具体的 harness 决策再做定向修复。效果：在线文本分类上比 SOTA 上下文管理系统 ACE 高 7.7 分还省 4 倍上下文 token；检索增强数学推理上单个被发现的 harness 在 200 道 IMO 级题上跨 5 个留出模型平均 +4.7 分；agentic 编码上从 Terminus 2 / Terminus-KIRA 起步搜出的 harness 在 TerminalBench-2 上超过最强人工基线、在 Haiku 4.5 组排第一。核心启发：把"历史经验"更充分地暴露给提案 agent，harness 工程就能自动化。
🔗 链接：https://arxiv.org/abs/2603.28052 ｜ 代码/项目：https://yoonholee.com/meta-harness/

### OpenAI：用 Codex 造"自我改进"的税务 agent
这篇工程博客（5/27）讲了一个对"后训练软件工程"极有参考价值的生产案例：OpenAI 前向部署工程师与 Thrive Holdings 一起，为 Crete 旗下 30+ 会计事务所做了一个用 Codex 驱动的报税 agent（本季处理了约 7000 份报税）。它不靠工程师逐个去抓和修 bug，而是把"生产使用"变成自改进的燃料——核心是一条闭环：把生产中的 trace 变成结构化 finding→打包成"定向 eval 集"（含代表性源数据和期望输出）→让 Codex 在产品脚手架里直接定位根因、提出代码改动→跑定向 eval + 更广的回归套件验证→给出候选 PR 交人类评审。例如 eval 发现 agent 老是漏填"fair rental days"字段，因为这条已被打包成定向 eval，Codex 就能针对性诊断修复。它把"评测工程 + harness 工程 + 自改进"串成一套可复用模式，呼应了 OpenAI 此前的 harness engineering 与 Symphony 工作——本质是"让生产基础设施产出证据，而不只是输出"，这正是后训练软件工程关心的落地范式。
🔗 链接：https://openai.com/index/building-self-improving-tax-agents-with-codex/ ｜ 代码：None

### KAT-Coder-V2：Specialize-then-Unify 的 agentic 编码后训练
做一个"全能 agentic 编码模型"难点在于：SWE 修复、前端生成、终端命令、联网搜索、通用代码这些能力差异大，混在一起训容易互相拖累。快手 KwaiKAT 团队的 KAT-Coder-V2 采用"先专精、再统一"：把能力谱拆成 5 个正交专家域（SWE / WebCoding / Terminal / WebSearch / General），每个域独立做数据构造、SFT 和"环境反馈 RL"，得到一组专家后，再用 On-Policy Distillation（OPD）把它们无损融合进一个可部署模型——OPD 兼顾了在线探索的"直接避错"和专家的逐步密集监督，避免了离线模仿的曝光偏差。工程上它依赖 KwaiEnv 这套模块化基础设施来跨多种编码域扩 RL；轨迹合成靠在每个 Docker 容器里部署 Claude Code Agent 自主探索代码库（最多 150 轮）来产出，再从 Anthropic 格式转成 OpenAI 训练格式。对关心"多域 agentic 编码怎么分治训练再融合、RL 基础设施怎么搭"的团队，这份技术报告信息量很大。
🔗 链接：https://arxiv.org/abs/2603.27703 ｜ 代码：None

### NVIDIA Polar：在真实 harness 上做 token-faithful GRPO 与轨迹合成
给 coding agent 做 RL 有个现实痛点：训练框架往往要把 agent 从它真实运行的 harness（Codex、Claude Code 等）里"抠"出来塞进训练专用环境，导致训练和部署的行为不一致。NVIDIA Polar 强调"token-faithful"——直接在 4 套真实 coding harness（Codex / Claude Code / Qwen Code / Pi）上跑 GRPO，且都从同一个 Qwen3.5-4B 基座出发、用 SkyRL/SWE-Gym 数据，保持 harness 架构不变。它同时给出一套可规模化的"拒绝采样造 SFT 轨迹"的工程做法：用 Qwen3.5-122B-A10B + Pi harness 跑 1638 个 SWE-Gym 实例（单 8×H100 节点、SGLang 服务、每任务独立 Apptainer 容器），只有当 SWE-bench 评测 harness 确认补丁让所有 FAIL_TO_PASS 通过且 PASS_TO_PASS 不挂时才收进语料（单比特过滤、无部分得分），最终 1638→504 条（30.8% 通过率，约 64 GPU 小时），且通过率随仓库难度差异明显。作者也坦诚 per-request trace 的过程奖励/信用分配会出现 reward hacking，仍是开放问题。对搭 SWE RL 基础设施的团队很实用。
🔗 链接：https://softtechhub.us/2026/05/29/nvidia-polar-explained/ ｜ 代码：None

### Composer 2.5：把"文本反馈"喂进 RL，再用自蒸馏内化
长周期 agent 训练的老大难是"信用分配"——一条几十步的轨迹最后只给一个标量奖励，模型很难知道到底哪一步错了。Cursor 的 Composer 2.5 给出一个干净的生产级答案：当某一步工具调用报错或产生异常输出时，训练设施会在那一步合成一段局部文本反馈（比如"这个工具调用返回 404，因为你给的路径不存在，根据第 Y 步可见的文件结构正确路径应是 X"），把它折回轨迹参与梯度更新，让模型看到的不只是"错误动作"而是"错误动作 + 为什么错且锚定到具体步"。配套的 on-policy 自蒸馏（OPSD）则更省：给模型喂入这种"特权提示"时它的下一 token 预测会立刻变好，于是用"带提示版输出"当 teacher，逼"不带提示的标准版"去匹配其概率分布，从而把提示蕴含的逻辑内化进权重、推理时无需再带提示。它的工程意涵是：只要你有结构化 trace 和近似 ground-truth 标注能力，就能把"长周期信用分配"变成可操作的事——但代价是训练侧要不断生成 on-policy rollout（约 2–4 倍 SFT 的算力）。对做 agentic 编码后训练的团队是重要风向。
🔗 链接：https://bdtechtalks.com/2026/05/25/composer-25-llm-self-distillation/ ｜ 代码：None

### CodeGym：把静态编程题"变成"可交互的工具使用 RL 环境
要训练 agent 的多轮工具使用能力，得有大量"可交互、能给奖励"的环境，但这种环境很难手工造、也难规模化。CodeGym（ICLR 2026）的巧思是把海量现成的静态编程题自动改造成交互式环境：从编程解法里抽取可复用的代码逻辑与函数，封装成带文档的工具库，再生成 OpenAI Gym 格式的环境（含状态、动作、转移、奖励），让 agent 在里面学着用工具一步步解题。它还配了严格的自动校验环节——生成多难度单测、验证环境无编译错误/超时/内存问题、并用能成功调用工具的解法函数验证可解性。用 CodeGym 训练后，LLM 在分布外（OOD）的工具使用与多轮基准上泛化更强。它放出了完整的环境合成与校验管线、以及面向大规模 RL 的在线 server。对想"低成本批量造工具使用 RL 环境"的团队，这是一个可直接复用的合成框架。

## 🔥 社区热点专栏

### 🔥 大佬观点

**HumanLayer（Dex / Viv）：《Skill Issue: Harness Engineering for Coding Agents》——别先怪模型，先查 harness。**
HumanLayer 团队把"harness engineering"明确定义为 context engineering 的子集：核心是利用 coding agent 的若干"配置点"来精细管理上下文窗口。他们给出一套实操优先级：先定制 `CLAUDE.md` / `AGENTS.md`（被 harness 确定性地注入系统提示）；MCP server 用来接工具；Skills 用"渐进式披露"按需提供知识/工具，避免把所有指令一股脑塞进系统提示而"烧光指令预算"；sub-agents 做上下文隔离、hooks 控制流程、back-pressure（测试/linter/类型检查）逼 agent 自查自纠。结尾那句很代表当下社区共识——"下次 agent 不灵，先别怪模型，多半是 harness 的 skill issue"。这与本期 Meta-Harness、HarnessLab 等学术/工程工作互为印证：模型趋同后，harness 才是可控的杠杆。
🔗 链接：https://www.humanlayer.dev/blog/skill-issue-harness-engineering-for-coding-agents

**Usama Qamar：文本反馈 RL 是"自 2024 长上下文以来 agentic 编码训练侧最重要的进展"。**
围绕 Cursor Composer 2.5 的训练范式，作者给出一个被低估的判断：把"局部、锚定到具体步、且有近似 ground-truth 的文本反馈"折回轨迹，等于把困扰 agentic 训练十年的"长周期信用分配"从难题变成了任何"有结构化 trace + 合理标注设施"的团队都能做的事。他给从业者的关键 insight 是——如果你的 eval 只看端到端结果，就会丢掉训练范式所依赖的同等信息密度；应当去构建"产出逐步 ground-truth"的 step-level eval。他还预判一年内严肃的编码 agent 训练都会用上某种"局部锚定反馈"而非"末端标量奖励"。对正在搭后训练/评测 pipeline 的团队很有启发。
🔗 链接：https://www.usamaqamar.space/writing/composer-2-5-textual-feedback-rl-credit-assignment

### ⭐ 超火仓库/项目

**Gloriaameng/Awesome-Agent-Harness（约 251 stars，2026-04 新建、持续更新）**
这是一份系统梳理"agent harness 工程"的 awesome-list/综述（110+ 篇论文、23 个系统）。它把 harness 形式化为一个一等架构对象 H=(E,T,C,S,L,V)，并提出"Harness Completeness Matrix"来横向比较异构 agent 系统实现了六个组件中的哪些，还整理了 9 个开放挑战（形式化安全模型、跨 harness 可移植性、MCP/A2A 协议互通、1M+ token 的上下文经济学、多 agent 拜占庭容错、组合式验证等）。之所以火，是因为它正好踩在"harness 成为 2026 年头号热词"的浪潮上，给社区提供了一张能快速建立全局观、又能落到具体组件对比的"地图"。
🔗 链接：https://github.com/Gloriaameng/Awesome-Agent-Harness

**polskiTran/HarnessLab：第一个"把 harness 当自变量"来评测的基准**
当大家都说"harness 比模型更决定可靠性"时，HarnessLab 直接把这句话变成可测量：它固定模型、只改 harness 的各个模块（上下文管理、重试策略、工具选择、记忆系统、输出校验、编排），用三个新指标量化贡献——HCM（用 η² 效应量算每个模块解释了多少性能方差）、HGS（跨域秩相关，看"对编码好用的 harness 是否也对 web 任务好用"）、Durability Curve（按轨迹深度看性能在第几步"跌崖"）。它给出的发现很有工程价值：上下文管理+记忆系统解释了 >60% 的性能方差；多数配置在第 50–60 步出现"耐久崖"，而 ObservationMask+FilesystemState 能显著拉平；甚至一个只含 3 模块的"最小可用 harness"就能以约 40% 成本拿到约 85% 收益。对想做"harness A/B 测试、把调 harness 变成数据驱动"的团队极有参考价值。
🔗 链接：https://github.com/polskiTran/HarnessLab
