## 📝 逐条讲解

### OpenAI：用 Evals 系统化测试 Agent Skills
很多团队开始把 `SKILL.md` 当成 agent 能力的分发单元，但一个技能“看起来更好”并不等于它真的更稳：它可能触发太宽、该触发时没触发、漏跑关键命令，或者留下脏文件。OpenAI 这篇开发者博客把 skill 迭代改造成一套轻量端到端 eval：先定义 outcome/process/style/efficiency 四类成功条件，再用一小组正负 prompt 检查技能触发边界。工程关键是 `codex exec --json`，它把 agent 运行过程输出成 JSONL 事件流，评测脚本可以直接检查是否执行了 `npm install`、是否创建了目标文件、命令顺序是否符合预期。对于“组件结构是否合理、样式是否符合约定”这类难写死的条件，文章建议再跑一个只读 Codex pass，并用 `--output-schema` 强制输出符合 JSON Schema 的 rubric 结果。它的价值不是某个 demo app，而是给 skill 工程提供了一条从“凭感觉改 prompt”走向“可回归、可比较、可进 CI”的路径。对后训练软件工程来说，skill 自动生成和技能市场越热，越需要这种行为级 eval 来防止技能库退化。
🔗 链接：https://developers.openai.com/blog/eval-skills ｜ 代码：None

### Harness-Bench：把 harness 作为一等评测变量
传统 agent 评测常常把分数归给“模型”，但真实运行里模型只是 agent 的一部分，周围的 prompt、工具接口、权限、状态管理、恢复策略、trace 记录共同构成 harness。Harness-Bench 的核心贡献是把 harness 从隐形实现细节拉到评测主轴：固定任务环境、预算、超时和 evaluator，同时保留每个 harness 的原生执行行为，观察同一批模型在不同 harness 下如何变化。它包含 106 个离线沙箱任务，覆盖软件工程、数据分析、知识检索、办公工作流、DevOps 等八类真实 agent 用法，并记录最终 artifact、工具调用、workspace diff、usage 与 validator 输出。实验规模达到 5,194 条执行轨迹，显示不同 model-harness pairing 在完成率、过程质量和 token/turn 成本上差异很大，NanoBot、Hermes、OpenClaw 等 harness 之间可拉开二十多分。更重要的是，它总结了 execution-alignment 失败：模型推理看似合理，但没有和工具反馈、当前文件状态、证据或输出契约保持一致。对我们关注的 harness engineering，这是一个能直接用于定位“为什么同一个模型换壳就变强/变弱”的诊断底座。
🔗 链接：https://arxiv.org/abs/2605.27922 ｜ 代码：https://github.com/Qihoo360/harness-bench

### HarnessForge：harness 与 policy 共同进化
已有工作常常要么搜索外部 harness，要么训练模型 policy，但真实 agent 系统里这两者是耦合的：harness 暴露什么计划结构、动作接口和记忆，模型就必须学会按这种接口可靠执行。HarnessForge 把 agent 明确定义成一个 harness-policy pair，并让两边共同进化。harness 侧，它让 meta-agent 阅读失败轨迹，做 fault attribution，把问题归到 planning/action/memory 组件，再参考历史高质量 harness 做局部修订和 Pareto 选择。policy 侧，它不追求训练一个通用更强模型，而是复用筛选过程中的成功 rollout，把它们转成 harness-conditioned 数据，用轻量 LoRA 让 reasoner 适配当前 harness 的执行协议。实验覆盖 ToolHop、SearchQA、TMDB、API-Bank 等工具/检索任务，Qwen3-4B/8B 上平均超过最强 harness-only 或 policy-only 基线 3.56%，TMDB 最高 +12.0%。它提示后训练团队：当你改工具协议、记忆格式或计划模板时，最好同步让 policy 学会这个“新操作系统”，否则外部结构再漂亮也可能执行不稳。
🔗 链接：https://arxiv.org/abs/2606.01779 ｜ 代码：https://github.com/mingju-c/HarnessForge

### SABER：状态化项目工作区里的 coding-agent 操作安全
过去安全评测多看模型是否拒绝一个危险 prompt，但 coding agent 真正的风险来自多步行动：它会改文件、跑 shell、移动数据、改变权限，最后留下一个可能已经被破坏的工作区。SABER 把安全评测从“单轮回答”升级为“状态化项目 workspace 的最终状态”：给 agent 一个真实风格项目和任务，让它在沙箱里执行若干步，再根据动作轨迹与最终文件/权限/数据状态判断是否发生操作安全违规。它不只给二元安全结论，还按原因分类，让研究者能看到模型是误删文件、越权访问、执行危险命令，还是为了完成任务牺牲了 workspace 完整性。结果很刺眼：即使最好的模型也有超过 54% harmful safety violation rate，说明“会拒绝坏请求”并不等于“会在真实项目里安全行动”。仓库里包含任务、沙箱 runtime、MCP runtime、judging pipeline 和 baseline 复现实用脚本。对 coding agent 评测与部署，这类 benchmark 很关键，因为它把“最小权限、状态保护、危险动作审计”变成可测指标，而不是安全文档里的口号。
🔗 链接：https://arxiv.org/abs/2606.01317 ｜ 代码：https://github.com/sssr-lab/saber

### BenchAgent：多 agent 是否真的有帮助？
社区里很容易默认“多几个 agent 分工会更强”，但很多比较没有统一工具、预算、答案格式、日志和评测协议，导致很难判断收益来自 agent 数量还是来自更宽松的运行条件。BenchAgent 要测的正是 workflow lift：在同一 benchmark loader、tool access、answer contract、usage accounting 和 trajectory logging 下，把单 agent、固定 MAS、动态/进化 MAS 放在一起比。它覆盖十个 reasoning/coding/tool-use benchmark，结论很克制：在 substrate-internal 条件下，六个 MAS 里最多一个略高于匹配的单 agent anchor，而且差距落在一次运行的 Wilson 不确定范围内，其余五个落后 2.56–11.29 分且成本更高。GAIA 的外部协议对齐实验则显示，一个 Claude-Code-style runtime workflow 在长程任务上优势明显，但作者明确不把它归因给“agent 多”，而是归因给一整套部署配置。它的工程启发是：多 agent 编排不能只看最终准确率，必须同时记录 token、latency、handoff、约束丢失、验证阶段和恢复路径。对后训练/agent 评测来说，这能防止我们把“更复杂的编排”误当作“更好的系统”。
🔗 链接：https://arxiv.org/abs/2606.05670 ｜ 代码：None

### SWE Atlas：评测 bug fix 之外的真实软件工程
SWE-bench 类评测把 coding agent 的主战场定义成“修 issue、让测试通过”，但真实软件工程还包括读懂系统、写能抓住回归的测试、做不改变行为的重构。SWE Atlas 补上这块空白：它构建了 284 个专家编写任务，分为 Codebase Q&A、Test Writing、Refactoring 三类，来自 18 个活跃开源仓库。评测不只跑程序测试，还使用专家 rubric 检查代码放置、维护性、artifact cleanup、负面反模式等工程质量；测试写作任务还引入 mutation check，看 agent 写的测试能否真的杀死缺陷，而不是只跑过 happy path。结果显示，即使 GPT-5.4 Codex 和 Opus 4.7 Claude Code 领先，总体 pass@1 也只有四成左右，而且 Pass3 一致性明显更低。分析里最有价值的是“工程质量滞后于功能正确”：模型可能通过回归测试，却没清理旧接口、漏掉调用点、或者写出不能抓住真实缺陷的测试。对 coding agent 后训练，这说明数据与评测不能只奖励“patch 可运行”，还要把维护性、测试有效性和 runtime evidence 做成可优化信号。
🔗 链接：https://arxiv.org/abs/2605.08366 ｜ 代码：https://github.com/scaleapi/SWE-Atlas

### PawBench：LLM × Harness 联合诊断基准
PawBench 是 AgentScope 团队开源的一个轻量但方向很对的 benchmark：它不是单独给模型排榜，而是把“模型 × harness”的组合当成被评测对象。v1.0 包含 150 个 agent 任务、9 个模型和 3 个 harness（QwenPaw、OpenClaw、Hermes），并保留 prompts、graders、task labels、submission 与 leaderboard slices，便于切片分析。它的一个直接发现是，同一个模型换 harness 可能差 10 分以上，比如某些 Qwen 模型在 QwenPaw/OpenClaw/Hermes 下表现差异明显。相比 Harness-Bench 的大而全，PawBench 更像社区可快速跑的诊断板，适合开发者在选模型、选 harness、调工具数、调 workspace awareness 时做 A/B。它也把任务按 capability、scenario、complexity、modality、environment 标注，方便定位“是工具使用差、规划差，还是 harness 没把状态暴露好”。对 agent 系统工程，这类小型可复现的 harness-aware benchmark 能帮助团队在日常迭代中避免只盯模型名。
🔗 链接：https://github.com/agentscope-ai/PawBench ｜ 代码：https://github.com/agentscope-ai/PawBench

### Harness MCP v2：用少量 generic tools + skills 降低 MCP 膨胀
前几天社区集中讨论 MCP 相比 CLI 的 token 膨胀，但 Harness.io 这篇文章给出一个更工程化的中间答案：问题不在 MCP 这个协议，而在“把上百个工具 schema 一次性塞给模型”的设计。Harness MCP v2 把 120+ 资源类型收敛成 10/11 个通用工具，例如 `harness_list`、`harness_create`、`harness_execute`、`harness_describe`，其中 `harness_describe` 是本地 schema lookup，不需要发 API 请求。这样 agent 不必看到 100 多个工具，也不必凭空猜复杂 DevOps API 字段，而是在执行前按需发现 resource schema。更关键的是配套 skills layer：`/create-pipeline`、`/debug-pipeline`、`/analyze-costs` 等 Markdown workflow 会规定先确认 account/org/project、先验证依赖、再查 schema、最后创建或执行，从而把工具调用从“裸 API 访问”变成阶段化操作规程。它解决的是大型企业 API 的真实痛点：CLI 对本地确定性任务很好，但复杂 SaaS/DevOps 平台需要权限、发现、校验和治理。对 Agent-Friendly Software 来说，这是一种值得借鉴的接口分层：少量稳定 tool primitives + runtime schema discovery + skill workflow。
🔗 链接：https://www.harness.io/blog/harness-mcp-server-redesign ｜ 代码：https://github.com/harness/mcp-server/ / https://github.com/harness/harness-skills

### OpenAI：用 Codex SDK 自建结构化代码审查
很多团队想用 Codex 做自动代码审查，但仓库不一定托管在 GitHub，或者不想完全依赖 Codex Cloud 的托管 review 流程。OpenAI 这份 cookbook 把这个能力拆成可以自建的 CI/CD harness：在 runner 里安装 Codex CLI，用 headless `codex exec` 读取 PR diff，让模型按审查 prompt 输出结构化 JSON，再由脚本把 findings 发布成 inline comments。工程重点是 JSON Schema 输出：每个 finding 必须含 title、body、confidence、priority、文件路径和行号范围，否则后续 SCM API 无法安全锚定评论。文章给了 GitHub Actions、GitLab CI、Azure DevOps、Jenkins 等环境的落地模板，并提醒公共仓库/不可信 PR 中要隔离 OpenAI API key，避免 agent 读到或外泄 secret。它不是新模型论文，但对“把 coding agent 作为 CI 组件接入企业流程”很实用。对后训练软件工程团队，这类结构化审查 harness 也可以反过来产出高质量失败案例、review rubric 和回归 eval。
🔗 链接：https://developers.openai.com/cookbook/examples/codex/build_code_review_with_codex_sdk ｜ 代码：None

### Stop Comparing LLM Agents Without Disclosing the Harness
这篇 position paper 直接点名当前 leaderboard 的一个根本问题：长程 agent 分数通常写成“某模型在某基准上多少分”，但真正被测的是模型与 harness 的混合体。作者提出 Binding Constraint Thesis：当模型能力接近时，性能方差常常更多由 harness 配置决定，而不是模型本身决定。文章用闭环控制系统来解释：模型是 open-loop policy，harness 才是管理状态、上下文、工具反馈、异常恢复和停止条件的 controller；稳定性、context drift、control lag 都是 controller 属性。它还提出 Harness Card 披露标准，要求报告 execution、tool、context、scheduling、observability、verification、governance 七层信息，并建议 locked-harness 或 factorial protocol 来分离 model variance 与 harness variance。一个小型 SWE-bench Verified 子集实验里，harness 方差均值约是 model 方差 7.8 倍，并出现多次模型排序反转。对评测工程来说，这篇的价值在于把“请披露 harness”从倡议变成了可执行的报告格式和方差分解协议。
🔗 链接：https://arxiv.org/abs/2605.23950 ｜ 代码：None

### From Model Scaling to System Scaling：Scaling the Harness
这篇稿件把 2026 年 agent 工程的共同趋势概括成一句话：下一阶段瓶颈不只是 model scaling，而是 system scaling，也就是 scaling the harness。作者把 agent 系统拆成 reasoning substrate、memory store、context constructor、skill routing、orchestration loop、verification/governance 六个组件，强调模型只主要提升第一项，其他五项需要系统工程。文章尤其关注三类 bottleneck：context governance（不是能塞多少 token，而是每轮该选择、压缩、刷新、标注来源哪些内容）、trustworthy memory（记忆要有精度、耐久、可检索、可验证，不能 stale-but-confident）、dynamic skill routing（技能存在不等于会选对、会组合、会检查后置条件）。配套的 CheetahClaws 是一个 Python-native reference harness，用来把这些设计轴显式化，并与 Claude Code、OpenClaw 做对照。它偏框架性，但对构建长期运行 agent 很有启发：prompt、skill、memory 是不同时间尺度的控制层，不能互相替代。对后训练软件工程，这提示我们评测也应覆盖 memory hygiene、context efficiency、verification cost 和 safe evolution，而不是只看一次任务是否完成。
🔗 链接：https://arxiv.org/abs/2605.26112 ｜ 代码：https://github.com/SafeRL-Lab/cheetahclaws

### Anthropic：Making Claude a chemist
Anthropic 6 月 5 日发布的这篇 science research 与 coding agent 关系不强，因此按低优先级官方源收录，但它展示了大模型如何进入专业科研工作流。化学家日常要在手绘结构、论文图、SMILES、专利文本、实验方法和 NMR 光谱之间来回翻译，这类“表示之间的转换与核对”非常耗时，也很难靠传统结构化数据库完全覆盖。Anthropic 让 Claude Opus 4.7、Opus 4.6、Sonnet 4.6 与 ChemDraw、MestReNova 在 20 个近期 ChemRxiv 化合物上比 1D NMR forward prediction，并测试了从质谱/NMR 数据反推结构的 inverse elucidation。结果显示 Opus 4.7 在氢谱平均误差、峰形/耦合间距等指标上接近或超过传统软件，并能在若干 1D NMR 反向结构解析任务中给出正确候选。局限也明确：样本只有 20/15 个，2D NMR、立体化学、复杂天然产物尚未覆盖。对泛 LLM 跟踪来说，它说明官方实验室正在把“通用多模态推理 + 专业数据表示转换”产品化为科学工作流助手。
🔗 链接：https://www.anthropic.com/research/making-claude-a-chemist ｜ 代码：None

## 🔥 社区热点专栏

### 🔥 大佬观点

**Cobus Greyling：Agent = Model + Harness，别再只给模型记功。**  
他围绕 Harness-Bench 写了「Agent = Model + Harness」，强调 agent 能力应报告为 model-harness configuration，而不是孤立模型分数。值得注意的是，他把 execution alignment 讲得很清楚：可靠 agent 的关键是让推理、工具反馈、workspace 状态和 verifier 检查条件保持对应。🔗 https://cobusgreyling.substack.com/p/agent-model-harness

**HN / MCP 社区：MCP vs CLI 争论转向“动态工具注册 + 惰性加载”。**  
围绕 Apideck CLI、mcp2cli 和 Commandable MCP，社区讨论已经从“CLI 一定赢还是 MCP 一定输”转向更细的接口工程：schema 不应全量常驻上下文，而应通过 CLI `--help`、tool search、dynamic tool registration 或 ability loading 按需暴露。这个观点重要，因为它把 MCP token 膨胀问题还原成 harness/context 工程问题，而不是协议宗教战争。🔗 https://news.ycombinator.com/item?id=47400261 ｜ https://news.ycombinator.com/item?id=47412133

### ⭐ 超火仓库/项目

**agentmemory（rohitg00/agentmemory）：跨 Claude Code / Codex / Cursor / Copilot CLI 的共享长期记忆层，约 21.7k stars。**  
它用 MCP、hooks 和 REST API 给多个 coding agent 共享持久记忆，支持 Claude Code、Codex CLI、Cursor、GitHub Copilot CLI、Gemini CLI、OpenCode 等，最新 release 到 2026-06-07 仍在快速迭代。它火的原因很直接：多日开发任务里 agent 最大痛点之一就是“换会话/换工具就忘”，agentmemory 把项目事实、文件历史、决策和 session 摘要变成可检索数据库。🔗 https://github.com/rohitg00/agentmemory

**mcp2cli（knowsuchagency/mcp2cli）：把 MCP/OpenAPI/GraphQL 运行时转成 CLI，约 2k stars。**  
它主打不把完整 tool schema 塞进模型上下文，而是让 agent 通过 CLI 按需 `--list`、查看参数和执行工具，号称在大工具集下节省 96–99% schema token。它解决的是真实痛点：MCP server 工具数一多，schema 成本会在每轮对话里反复燃烧；CLI 化让工具发现回到 LLM 擅长的文本命令模式。🔗 https://github.com/knowsuchagency/mcp2cli

**Commandable MCP：用 dynamic tool registration 让 agent 会话中按需生成/加载工具。**  
Commandable MCP 的思路是让 MCP server 不只是静态 swagger doc，而是在 session 中按需加载 toolset，甚至让 agent 为具体团队的 GitHub/Jira/Notion 流程生成更窄、更好用的新工具。它之所以值得关注，是因为它给“MCP 上下文膨胀”提供了另一条路线：不是逃到 CLI，而是在 MCP 内部做能力分组、动态注册、credential 隔离和自生成工具。🔗 https://github.com/commandable/commandable-mcp ｜ https://www.commandable.ai/mcp
