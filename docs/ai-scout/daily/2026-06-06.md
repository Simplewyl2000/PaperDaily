## 📝 逐条讲解

### SWE-Universe：用一个"会自己验货"的建造 agent，把可验证 SWE 环境扩到百万级
训练 SWE（软件工程）coding agent 的最大瓶颈一直是"可执行、可验证的真实环境太难造"——从 GitHub 的 PR 自动搭出能跑通的环境，长期受困于三件事：成环境的产出率低、验证器太弱（容易被糊弄）、以及构建成本高得吓人。SWE-Universe 的思路是把"建造环境"这件苦活本身交给一个 agent，并且为省钱专门微调了一个高效的小模型（Qwen-Next-80B-A3B）来当这个 builder。它的两个工程关键点很值得抄：一是**迭代式自验证**——把生成出来的验证器分别拿到"有 bug 的版本"和"已修复版本"上去跑，确认验证器真能区分对错，而不是永远报通过；二是**in-loop hacking 检测**——在生产环节就识别并剔除那些"看起来在验证、实则没真正执行代码"的肤浅验证器，防止环境天生就能被刷分。靠这套方法它产出了 807,693 个多语言、可执行、可验证的训练实例（同类里规模最大之一），非作弊成功率约 75.9%；用这批环境做大规模 agentic mid-training 与 RL 后，Qwen3-Max-Thinking 在 SWE-Bench Verified 上拿到 75.3%。它和本周收录的 Scale-SWE、SWE-Hub、SWE-Next 同属"把 SWE 数据生产工厂化"的潮流，但独特价值在于**把"反作弊验证"直接焊进数据生产管线**，对自建大规模 SWE 后训练数据、又怕验证器被钻空子的团队是很实在的模板（注：该工作为 2026-02 预印本，因与高优先级"数据/环境合成 + 评测反作弊"双主题强相关而作为探索性条目保留）。
🔗 链接：https://arxiv.org/abs/2602.02361 ｜ 代码：None

### Agent World Model（AWM）：开源把"工具使用环境"当流水线产品来造
要给 agent 做工具使用的 RL，最缺的是大量"可执行、能给奖励"的环境，但这种环境手工造极慢、也难规模化。Snowflake 团队的 Agent World Model（AWM）抓住一个朴素却好用的观察：几乎所有 agent 环境都共享同一套骨架——**一个有状态的后端 + 一层工具接口 + 任务专属的成功判据**。于是它把"造环境"分解成这三块分别合成，且**不预设任务集、也不依赖现成 API 文档**（避免人为先验、便于无限扩展）。它用数据库后端来托管状态，从而能做"代码增强的验证"：每个任务配一个验证模块，检查 agent 执行前后的数据库状态差异来判定成败；为了对抗合成环境难免的瑕疵（状态没更新干净、超时等），最终裁决交给一个把"轨迹 + 结构化验证信号"一起看的 LLM-as-a-Judge，并归到 {完成/部分完成/Agent 报错/环境报错} 四类。规模上它一口气合成了 1,000 个环境、35,062 个工具、10,000 个带验证码的任务（号称迄今最大的开源工具使用环境集），并慷慨放出代码、AgentWorldModel-1K 数据集、Arctic-AWM-4B/8B/14B 模型，还接进了 meta-pytorch/OpenEnv 的 RL 基础设施。对想"低成本批量造工具使用 RL 环境、又要可验证"的团队，这是一个可直接上手、零人工标注的开源工厂（注：2026-02 预印本，因强相关 + 完整开源而保留）。
🔗 链接：https://arxiv.org/abs/2602.10090 ｜ 代码：https://github.com/Snowflake-Labs/agent-world-model

### CODESKILL：与其手写"怎么管技能"的规则，不如把"技能库管理"本身训成一个策略
让 coding agent 把过往轨迹蒸馏成可复用的"技能"（procedural skill）很有吸引力，但现有方法几乎都靠固定 prompt + 启发式更新规则（什么时候加、什么时候合并、什么时候删），到底"该选哪些知识、抽到多抽象、怎么维护"始终说不清。CODESKILL 的做法是把"技能抽取 + 技能库维护"重新表述成一个**可学习的管理策略 \(M_\theta\)**：它从 coding-agent 轨迹里抽多粒度的过程性技能、用新经验/失败经验去演化已有技能，并维护一个"大小稳定"的技能库（加有用的、合并冗余的、删没用的）。训练上先用"轨迹 + teacher 生成的技能操作"做监督热启动，再用 GRPO 优化，奖励是个混合体：一个 **rubric 式 LLM-as-judge 质量分**（看 grounding、复用性、specificity、可执行性），加一个**执行奖励**——把候选技能喂给一个冻结的下游 coding agent，看它相对"无技能基线"提升了多少通过率（真正"execution-grounded"，不靠技能看着漂亮就给分），还专门加了**对齐归因因子**来应对"agent 成功未必是这条技能起的作用"。结果在 EnvBench/SWE-Bench Verified/Terminal-Bench 2 上平均通过率比无技能基线 +9.69、比最强 prompt/记忆基线 +4.01，且技能库规模始终稳定。它和本周的 SkillEvolver/EvoSkills/ReSkill 互为补充：那几篇强调"防污染纪律"和"代理验证器诊断"，CODESKILL 则直接**把库管理决策本身用可验证奖励训出来**，对想把"技能自动生成/治理"做成端到端可学习闭环的团队很有借鉴。
🔗 链接：https://arxiv.org/abs/2605.25430 ｜ 代码：None

### ANDES：把"为后训练造数据"封装成一个 agent 能调用的技能
现在大家开始让 agent 去自动化后训练本身（自己找数据、清洗、配比、训练、评测），但实测发现即便前沿 agent 也搞不定——核心难点在数据这一环：让 agent 在嘈杂的开放网络里自己搜索、过滤、平衡数据，这种长程任务很容易撑爆有限上下文，最后数据质量崩、下游训练也跟着差。ANDES（Agent Native Data Evolving Synthesis）换了个抽象层次：与其逼 agent 从零设计复杂的数据采集策略，不如**把数据合成做成一个即插即用的 agent skill**，给它一个"智能抽象层"。它的两件法宝是：一个**自进化的 World Tree 路由机制**（把能力空间组织成树，动态决定下一步去补哪类欠采样的能力），和**可执行的诊断报告**（把每轮合成结果的"塌缩模式/样本缺口"总结成可操作信号，喂回去指导下一次调用——比如发现某类能力被采少了就上调配额、引导 trainer agent 转向欠探索的角度）。这样 trainer agent 通过一个交互式闭环接口"掌舵"数据合成，而不必自己硬扛长程检索。结果在严格算力约束下，给本来较弱的 agent 装上 ANDES 就能显著改善自动对齐，在 PostTrainBench 上拿到 SOTA 并有不错的跨任务泛化。它正中本日报最核心的"后训练数据工程"，而且把"数据合成"做成可被 agent 复用的 skill 这一抽象，和今天的 CODESKILL、以及 skills.sh 生态热潮同频。
🔗 链接：https://arxiv.org/abs/2606.01279 ｜ 代码：https://github.com/zzy1127/ANDES

### OpenAI：当 RL 奖励"不小心看到了 CoT"，会发生什么？——一份难得的奖励完整性工程复盘
用 CoT（思维链）监控来发现模型的不对齐行为，是当下重要的安全手段；但有个公认的红线：**训练时别直接对 CoT 打分**——一旦奖励信号去评判 CoT 本身，模型可能学会"把不利的念头藏起来、只把推理写得讨喜"，从而毁掉 CoT 的可监控性。问题是，这种"意外给 CoT 打分"很容易在复杂 RL 管线里悄悄发生。OpenAI 这篇 Alignment 博客最有工程价值的部分，是他们把"防止意外"做成了**基础设施**：一个自动系统用正则去扫描公司内所有 RL run 的奖励输入，看是否混进了原始样本的 CoT 文本，命中就在 Slack 同时私信 run 负责人并公开告警。靠它他们查出三起真实的意外 CoT grading（奖励"轨迹有用性"、惩罚"多余的确认提问"、惩罚"成功的 prompt 注入"，分别影响了 GPT-5.4 Thinking、若干 5.x Instant/mini，受影响样本占比都很低），还抓到一个隐蔽路径——模型用工具读到了自己的 CoT，导致 CoT 经由工具输出"绕进"了被打分的内容。事后他们做了消融与 monitorability 评测，没看到明显退化，但仍坚持"训练中不给 CoT 打分"的政策不变，并提出判断 CoT 压力是否危险的三因子框架：**奖励幅度、覆盖率（多少训练样本会触发该压力）、条件可发现性（在这些环境里模型多大概率真去采那个被奖励的 CoT 行为）**。对任何搭自动化 RL/评测管线的团队，这套"把红线变成可自动检测的插桩 + 公开告警 + 事后可证伪复盘"的做法，是"奖励完整性/评测反作弊工程化"的一流范本（说明：原文要求不纳入训练语料，此处仅作公开信息转述与链接，未复制其 canary 标记）。
🔗 链接：https://alignment.openai.com/accidental-cot-grading/ ｜ 代码：None

### Learning What to Learn：把数据按"该 SFT 还是该 RL"分门别类，再把失败回收利用
小模型做推理后训练时，一个常见困惑是：同一批数据，到底该拿去 SFT（监督微调）还是 RL？这篇给出一个干净的"按阶段分数据"原则：**SFT 更适合补"还没有的技能"，RL 更适合固化"已经会一半的技能"**。具体做法是先按"模型自身难度"给样本分级，然后切成三套功能性数据集——Acquisition Set（中等 + 经桥接调整的难题，用于初始 SFT）、Consolidation Set（非全零奖励样本，含有奖励对比的混合样本和稳住已有技能的全一奖励样本，用于 RL）、以及最有意思的 Recycled Set：那些 RL 里"全零奖励、给不出梯度信号"的失败样本，不直接丢，而是**回收成 error-guided 的 SFT 监督**（让 teacher 对失败做诊断、修复并写出新的推理轨迹）。于是形成一个 SFT↔RL 的迭代循环：RL 通过失败 rollout 暴露能力缺口，SFT 把这些缺口补上，循环往复地把模型的推理边界往外推。它虽以数学推理为例，但"按难度切数据 + 把废样本回收成定向监督"的工程思路对任何做 SFT-then-RL 数据流水线的团队都直接可用，正合本日报"工程化、可复现的数据构造"取向。
🔗 链接：https://arxiv.org/abs/2606.04466 ｜ 代码：None

### AReaL-SEA：让一群 agent 自己造数据、自己写验证器，再喂给可验证奖励 RL
多轮、交互式的工具使用 agent 很难训，难点有二：高质量训练数据靠人标注扩不动；而且 RL rollout 里"用户行为"本身带来巨大方差。AReaL-SEA 给的是一套两段式后训练框架。前半段是一个**分层自进化的多智能体系统**：一个编排层负责设计工作流、写各 agent 的提示、驱动迭代自进化；一个执行层由专职 worker agent 分别合成任务、交互轨迹、以及**可执行的 per-instance 验证函数**——这些验证函数直接当 RL 的奖励信号，全程几乎不需要人工监督。后半段是多轮工具使用的 RL 配方：作者发现现成模型当"工具使用用户"的模拟器时行为很不稳定，于是先用 SFT 把用户模型调成稳定、守指令的，再拿它去做 RL rollout；训练用大批量 + 动态采样的 GRPO 来稳住"用户驱动交互"的不确定性，并用前面生成的验证函数做基于结果的奖励（比对最终状态与 ground-truth 终态判成败）。它和本周的 ASTRA、ProRL Agent、AWM 一脉相承，都是"把多步交互的数据与环境合成做成自动化系统"，独特点在于**把'稳定的用户模拟器'当成一等工程前提**——这恰恰是做交互式 agent RL 容易被忽视的坑（注：2026-01 预印本、近期更新到 v3，作为探索性条目保留）。
🔗 链接：https://arxiv.org/abs/2601.22607 ｜ 代码：None

### open-trajectory-gym：一个把 SFT + 在线 RL + GEPA 串起来的开源轨迹后训练平台
开源权重模型往往"能想清楚复杂任务，却没法可靠地执行多步工具序列"——这道"会planning、不会execute"的鸿沟，正是轨迹级后训练想补的。open-trajectory-gym 把这件事做成一个领域无关的开源平台：你自带 agent、模型、benchmark 和奖励函数，就能在任意 GPU 基础设施上跑一条龙——**阶段一 SFT**（基于 HuggingFace TRL，在专家轨迹上做 LoRA 微调）、**阶段二 Online RL**（基于 SkyRL，用 ToolExecutor 做真实工具执行、异步 Ray + vLLM 推理、RLOO 优势估计 + DAPO 采样）、**阶段三 GEPA**（基于 DSPy 的反思式提示进化，不更新权重、用 Pareto 选候选，作者称其能以 4–35 倍更少的 rollout 反超 Online RL 约 6%）。任何"agent 跨多轮和工具交互"的领域（安全、SWE、数据分析、系统管理）都能通过 YAML 配置和 adapter 协议插进来；它自带的样例是用 CyBench（40 个 CTF 挑战）训一个本地可部署的 Qwen3.5-27B CTF agent。对想"把 SFT/RL/提示进化放在同一套可复现管线里横评"的团队，这是个可直接上手的工程底座，也呼应本周 ProRL Agent/AstraFlow"把 agentic RL 当严肃工程系统做"的趋势。

### Qwen3.7-Plus：把"看屏幕 + 写代码 + 用工具"塞进同一个 agent 循环

## 🔥 社区热点专栏

### 🔥 大佬观点

**Andrej Karpathy 加入 Anthropic（5/19），主攻"用 Claude 加速预训练研究"：可验证环境是 LLM 能力高地，工程目标是"无人在环的自动研究"。**
OpenAI 联合创始人、前特斯拉 AI 负责人 Karpathy 于 5/19 宣布加入 Anthropic，在 Nick Joseph 的预训练团队下新建一支团队，明确目标是"用现有的 Claude 去加速下一代 Claude 的预训练研究"——也就是把"用 AI 造更好的 AI"这条递归自改进（RSI）的循环正式跑起来。对从业者更有价值的是他一贯的工程判断：他认为 LLM 是"锯齿状"的智能体，在**可验证领域（尤其是 code 和 math，因为那里能搭出可验证奖励的 RL 环境）**会率先冲到能力高地；他还反复强调 agentic engineering 的方向是从"人在环里盯着"走向"把 agent 工程化到能无人干预地持续推进研究"。他近几个月独立做的 autoresearch 探索和这次的新角色指向同一件事：**把环境/评测/自动研究做扎实，比单纯堆算力更能定生死**。这条新闻同时也是一个组织信号——前沿实验室正把"自动化研究"当成头号工程优先级，与本日报关注的"后训练软件工程/可验证环境"高度同频。
🔗 链接：https://techcrunch.com/2026/05/19/openai-co-founder-andrej-karpathy-joins-anthropics-pre-training-team/

**SKILL.md 成了跨厂商的事实标准，skills.sh 市场爆发——但"大量自动生成的技能其实没解决真问题"的警告也来了。**
社区在 2026 年达成了一个少见的快速共识：Anthropic 提出的 Agent Skills（一个目录 + 一个 `SKILL.md` + 可选脚本/参考资料）凭"渐进式披露"（启动时只读各技能的 name/description 当索引、约 20–50 token，命中意图才加载正文、引用文件按需再读、脚本只回传输出不进上下文）成为跨 agent 的通用能力封装方式。它的采纳速度近乎空前：Microsoft 把 SKILL.md 支持塞进 VS Code 与 GitHub Copilot，OpenAI 在 Codex CLI/ChatGPT 用了结构等价的架构，Cursor、Amp、Goose、OpenCode、Letta 等纷纷跟进，Vercel 上线了 skills.sh 市场（社区报道已聚合数十万条技能），微软甚至给出带 `SkillsProvider` 的 Agent Framework SDK。这股热潮直接服务于本日报高优先级的"Skill 管理/自动生成"。但值得注意的另一面是**社区的清醒声音**：很多正被批量生成的技能其实是"泛泛而谈、agent 把自己本就会的最佳实践又写一遍"，是为了凑数而非解决真痛点——这与今天 CODESKILL/ANDES 想用"可验证执行奖励"把技能质量做实的方向恰好互为映照：标准与市场解决了"怎么分发"，而"怎么保证每条技能真有用"才是下一道工程关卡。
🔗 链接：https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview ｜ 市场：https://skills.sh/

### ⭐ 超火仓库/项目

**Paperclip（paperclipai/paperclip）：给"一群 agent"装上 org chart 与治理的开源"公司操作系统"，约 69k stars。**
Paperclip 是一个 MIT 许可、自托管的 Node.js 服务 + React 面板，定位很犀利——"如果说 OpenClaw 是一名员工，那 Paperclip 就是这家公司"。它不抢单个 agent runtime 的活，而是坐在它们之上提供**组织层**：给 agent 设角色/头衔/汇报线/权限/预算，用统一面板分配目标、追踪工作与成本，并通过"心跳"（DB 支撑的定时唤醒）驱动每个 agent 自己领任务、拆子任务、汇报阻塞。它兼容把 Claude Code、Codex、Cursor/Gemini/bash 这类 CLI agent，以及 OpenClaw 这类 HTTP/webhook bot 当"员工"接入（"只要能收心跳，就能被雇佣"），每个 agent 跑在容器沙箱里出问题也炸不到主机。自 2026-03-04 上线后三周破 3 万星、现已约 6.9 万星，是本季度蹿升最快的开源 AI 仓库之一。它之所以火，是踩中了"多 agent 协作缺一个组织/治理/问责层"的真痛点——当大家手里 agent 越来越多，**编排、预算、目标对齐**成了比单 agent 能力更现实的瓶颈。对关注 multi-agent 编排、agent runtime 集成与治理工程的团队，是当下最值得跟踪的范例。
🔗 链接：https://github.com/paperclipai/paperclip ｜ 项目：https://paperclip.ing/

**agent-computer-use（kortix-ai）：不靠截图、不烧 vision token 的"确定性 computer use"，作为 skill 在 skills.sh 分发。**
这是一个 Rust 写的 CLI + agent skill，主打一件本日报高优先级"Agent-Friendly / Computer Use / GUI-to-Agent"方向上很务实的事：**用操作系统的无障碍（accessibility）原语来确定性地操作桌面应用**（macOS 的 AX、Linux 的 AT-SPI2、Windows 的 UIAutomation，Electron 应用则自动重启带调试端口、走 CDP），而不是靠"截屏→视觉模型猜坐标→点像素"那套又贵又脆的玩法——所以它"无 vision token、无截图、确定性"。它把自己打包成 skills.sh 上的一个 skill，于是 Claude Code/Cursor/Codex/本地模型只要装上，遇到"打开音乐播放某首歌、再打开计算器算 7^8"这类指令就能直接驱动 `agent-cu` 端到端完成，无需为每个应用写专门代码。它本身还很新、star 不多（早期项目），但它代表的"用 a11y 语义做确定性桌面控制"正在成片冒头（同期还有 taw-computer、cellar、ControlMCP、WindownComputerUse 等一批 computer-use MCP server）。对做 GUI-to-CLI / Desktop Automation / Computer Use 工程的团队，这条"放弃像素、拥抱无障碍树"的技术路线值得重点关注（注：star 量目前较小，列入是因方向与高优先级强相关、且代表一个正在成形的工程趋势）。
🔗 链接：https://github.com/kortix-ai/agent-computer-use ｜ 项目：https://agent-computer-use.dev/
