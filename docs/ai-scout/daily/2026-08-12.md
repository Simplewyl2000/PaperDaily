## 📝 逐条讲解

### FailForge：把 RFT 丢弃的持续失败轨迹锻造成可内化技能
现在很多 code agent 后训练会用 rejection sampling fine-tuning：同一个可验证 SWE 任务采多条轨迹，只保留测试通过的轨迹做监督，失败的全部丢掉。问题是，越难的任务越可能所有 rollout 都失败，而这些“持续失败任务”恰恰位于模型能力边界，人工和执行环境成本都已经付出，却没有进入训练集。FailForge 的做法是让诊断 agent 读取失败轨迹、测试错误和执行证据，把失败原因提炼成一条不泄露答案的通用程序性技能，例如如何审计调用点、如何验证导入路径、如何按测试约束定位接口。然后系统把这条技能临时注入 teacher 的上下文，指导它再次尝试；如果第二次成功，就把成功轨迹纳入 RFT 语料，但在训练前移除那条技能文本，让 student 必须从原始任务中学会这种调查方法。论文报告它以较低额外成本恢复超过 26% 的先前失败实例，并让 Qwen3.5-4B 在 SWE-bench Verified 上比强 RFT baseline 提高 6.6 个百分点，收益集中在最难样本。它值得关注的地方是把失败轨迹从“垃圾样本”变成“技能合成原料”，同时避免部署时依赖外部提示。对后训练软件工程来说，这提供了一条很可落地的管线：失败诊断、技能去泄漏、技能引导重试、成功轨迹剥离脚手架、再进入训练。
🔗 链接：https://arxiv.org/abs/2608.08570 ｜ 代码：None

### SKT：用 2,000 个 public skills 合成 27,164 条 verified skill-use 轨迹
Agent skills 已经变成 Claude Code、Codex、Cursor 等工具里的常见扩展方式，但“有技能文件”不等于模型知道何时检索、如何执行、如何组合多个技能。SKT 直接把这个能力当成可训练对象：先从公开技能库里筛出质量、可验证性和可组合性足够好的技能，再围绕单技能或多技能组合生成任务包。每个任务包不仅有自然语言指令，还包含隔离运行环境、参考解、执行设置和 evaluator；失败的任务会回到 author 侧用反馈修复。生成轨迹时，系统只保留真正成功且“实质使用了每个要求技能”的轨迹，而不是只看最终答案对不对。最终它用 2,000 个 public skills 合成 4,000 个任务包和 27,164 条 verified trajectories，并构造了 held-out SkillEval benchmark。实验显示，用这些轨迹做 SFT 能跨模型、跨 benchmark、跨 harness 改善 skill-use performance。对后训练数据工程来说，SKT 的关键不是技能数量，而是把技能依赖、任务可验证性、轨迹忠实使用和 held-out skill pool 放进同一条数据生产线。
🔗 链接：https://arxiv.org/abs/2608.02287 ｜ 代码：None

### SWE-RPG：把 issue resolution 拆成需求澄清、实现规划和代码生成三段诊断
传统 SWE-bench 风格评测通常只看最后 patch 是否通过测试，这对排行榜足够，但对改进 agent 不够，因为失败可能发生在需求理解、规划或真正写代码的任一环节。SWE-RPG 把仓库级 issue resolution 拆成 Requirement Clarification、Implementation Planning 和 Code Generation 三个阶段，并为前两个阶段提供经过验证的 ground-truth references。它包含 163 个来自 31 个 Python/Java 仓库的任务，其中 113 个 bug fix、50 个 feature addition，并用 Claude Code、Codex、OpenCode 搭配 6 个 LLM backend 做矩阵评测。结果显示平均 resolve rate 只有 31.5%，而中间阶段诊断发现隐式需求恢复是主要瓶颈，24.5% 到 46.0% 的运行都卡在这里。这个发现很重要，因为很多用户请求并不会明确写出所有实现约束，agent 必须从 repo、tests、PR 和上下文里还原未说出口的需求。工程上，SWE-RPG 可以帮助团队把失败轨迹标成“没读懂需求”“计划不足”或“实现错误”，而不是只得到一个红色测试。对后训练软件工程来说，这种 stage-aware label 比整条轨迹 pass/fail 更适合做数据筛选、skill 更新和 targeted eval。
🔗 链接：https://arxiv.org/abs/2608.09072 ｜ 代码：https://github.com/Xin-Zhou-smu/SWE-RPG-Bench

### SWE-Bench ProMax：专家清洗的多语言大型重构 benchmark
很多 coding-agent benchmark 已经接近饱和，而且真实软件维护里大量工作不是修一个局部 bug，而是跨文件、跨语言、保持行为不变的大型重构。SWE-Bench ProMax 专门选择 refactoring 作为压力测试，收集 170 个真实 commit，覆盖 Python、Java、TypeScript、Go、C、C++ 和 Rust 七种语言。它的工程质量控制很重：每个 issue description 都根据 gold patch 和测试重写成明确规格，测试套件也由人工检查并移除过窄或过宽的断言，避免 benchmark 把正确解误判成错或把未说明需求算进分数。任务规模明显比常规 SWE-bench 大，平均修改 11.4 个文件、261.6 行代码，30% 的任务超过 10 个文件。实验中最好模型也只有 41.2% resolve rate，失败轨迹常见模式是修改文件数少于 gold patch，却消耗更多轮交互，说明 agent 不擅长跨文件协调。它还发现更高成本不必然带来更高分，例如 GLM-5 以远低成本接近 Claude Sonnet 4.6 的表现。对评测工程来说，ProMax 的价值在于把 benchmark 质量、任务复杂度、语言多样性和成本分析一起纳入，适合衡量 agent 是否能做真实工程重构。
🔗 链接：https://arxiv.org/abs/2608.09802 ｜ 代码：https://huggingface.co/datasets/swe-bench-promax/SWE-Bench-ProMax

### Evo-Bench：评测模型是否能自主改进 agent harness
现在大家越来越相信 harness 会显著影响 agent 表现，但“让模型自己改 harness”到底是能力进步还是对验证集过拟合，过去很难测。Evo-Bench 把模型当成 long-horizon harness engineer，让它在固定 policy model 前提下迭代修改一个可执行 harness，而不是直接完成业务任务。为了让评测真的测到 harness-evolving capability，作者先筛选对 harness 改动敏感的任务，再做 sensitivity-aware stratified split，保证验证集和最终 held-out evaluation suite 的响应模式一致但不重叠。任务覆盖 Search、Office 和 General Agent 三个域，验证集 160 个任务，最终评测集 448 个任务。实验显示 GPT-5.6 Sol 和 Claude Opus 4.8 这类 top evolver 可带来约 16 点绝对提升，接近人工工程 baseline，但在 Office 这类高度流程化任务上明显更吃力。更有意思的是，演化常出现 early saturation：模型很快找到好结构，后面继续乱改反而可能变差。对后训练软件工程来说，Evo-Bench 把 harness evolution 从一次性 demo 变成可比较、可复现、可防过拟合的评测问题。
🔗 链接：https://arxiv.org/abs/2608.09096 ｜ 代码：None

### HarnessOpt-Bench：把 harness 优化做成有预算、有隔离、有 held-out test 的任务
HarnessOpt-Bench 和 Evo-Bench 关注相近问题，但它更强调“优化协议”的可信边界：一个 optimizer agent 拿到 seed harness、开发/验证反馈和固定预算后，可以修改 harness 并提交最终候选。最终候选只在搜索期间不可见的 held-out test partition 上评分，分数按相对 seed 的 normalized gain 计算。论文特别设计 trusted execution environment：optimizer 只能写目标 harness，不能接触 held-out state、provider credentials 或预算机制；每个候选都在隔离 sandbox 里评估，并保存版本以便审计。这样一来，benchmark 测的是“在昂贵、随机、不完全反馈下如何做系统优化”，而不是谁能偷偷看测试或无限试错。作者用 5 个 frontier optimizer models、共享 coding harness 与 native harness，在 4 个 downstream tasks 上跑了 111 个 scored runs。结果显示 optimizer model 之间的差异通常大于它们所处 coding harness 的差异，native harness 也没有稳定优势。对 AI R&D agent 和后训练平台来说，这个协议很重要，因为未来模型可能不只写应用代码，也会修改评测、prompt、tools、memory 和运行时本身；这类自改必须有预算、隔离和候选审计。
🔗 链接：https://arxiv.org/abs/2608.06301 ｜ 代码：None

### LivePlan：用确定性 monitor 在线发现 programming agent 漂移再最小纠偏
长程 programming agent 常见失败不是一开始完全不会，而是中途偏离计划、反复查看同一位置、跳过验证、提前提交或在某个阶段停滞太久。很多纠偏方法会让另一个 LLM 定期读整条轨迹并重新规划，但这既贵，也容易因为 LLM judge 幻觉出不存在的问题而把原本正确的 run 带偏。LivePlan 的核心设计是把 judging 和 advising 解耦：先用确定性的 rule-based monitor 增量维护轨迹的过程表示，检测 plan violation、oscillation、long stagnation 和 repeated action 等信号；只有 monitor 触发时，才调用 advisor LLM 给下一步高层建议。它实现于 SWE-agent 之上，在 SWE-bench Verified 和 SWE-bench Pro 上评测 5 个模型组合，平均提升 9.9%，最高提升 15.2%，额外成本约 0.08 美元/实例。更关键的是，它主要解决 medium/hard instances，并且对已成功运行的回归较小。工程上，这比“失败后总结再重跑”更贴近生产 agent runtime，因为它在错误变成终局失败前介入。对轨迹选择和后训练来说，monitor 触发点、漂移类型、advisor 建议和纠偏是否成功，都是比最终 pass/fail 更细的训练信号。
🔗 链接：https://arxiv.org/abs/2608.06701 ｜ 代码：None

### The Scaffolding Matters More Than the Interface：MCP vs CLI 成本差异主要来自 harness
社区关于 MCP vs CLI 的争论很多，但很多数字来自不可复现的个人经验，很难区分协议本身、工具 schema、agent harness 和任务设计各自的影响。这篇论文做了一个受控实验：同一个固定软件任务、七种 agent scaffolding、五个语言模型、MCP 和普通 CLI 两种工具接口，并通过检查私有在线 git 仓库状态来验证任务是否完成，而不是相信 agent 自报。最强结论是，成本差异首先由 scaffolding 决定，不是单纯由 MCP 或 CLI 决定；有些不支持 MCP 的 scaffold 只用 CLI 也能 100% 完成，而且比支持 MCP 的 scaffold 便宜 5 到 28 倍。严格配对的 MCP-to-CLI 成本比从 0.43x 到 29x 都出现过，说明“某协议必然更贵/更便宜”这种说法不稳定。它还发现两种接口的失败频率相近，但 MCP run 中失败所消耗的成本占比更高，12.9% 的钱买到了未完成工作，而 CLI 是 2.2%。论文特别提醒，agent 经常会忽略分配给它的接口，所以不核验实际行为的 benchmark 测到的是未知混合物。对 agent-friendly software 来说，这非常实用：评测工具接口时必须记录 scaffold、实际调用路径、失败成本和仓库状态验证，否则会把 harness 偏差误判成协议优劣。
🔗 链接：https://arxiv.org/abs/2608.08654 ｜ 代码：None

### Rendered Code：把源代码渲染成图片能省 token，但不能替代结构化定位
代码上下文越来越长后，有人尝试把源代码渲染成图片，让视觉模型看代码排版，从而减少文本 token。Rendered Code 这篇研究把这个思路放进真实 repository-level repair workflow，而不是只做静态代码理解。作者在 SWE-bench Verified 上评估 rendered code，并设计受控 agent 设置来区分无引导仓库探索和更结构化的修复阶段。结果比较克制：视觉代码确实能减少 prompt-token cost，而且多数情况下保持 end-to-end repair accuracy，但节省并不会随名义压缩比线性增长，过度压缩时还会不稳定。更重要的是，当仓库定位已经被结构化工具解决后，剩余成本往往来自 patch-test 试错，而不是读源码本身，这时视觉压缩帮助有限。它按 Medium 收录，因为方向偏 context compression，但对长程 coding agent 成本工程很有参考。对后训练数据工程来说，是否用 rendered code、压缩比例、何时切回原文、是否影响 test/debug 行为，都应该被记录为轨迹上下文。
🔗 链接：https://arxiv.org/abs/2608.09268 ｜ 代码：None

### RefactorAssist：用静态修复 + 测试日志 + diff 上下文提高 LLM 重构可靠性
LLM 生成重构代码时，表面上看起来更干净，但很容易引入行为变化、重命名不一致、缺导入、作用域错误或边界条件遗漏。RefactorAssist 先人工分析 10 个开源项目中 LLM 重构失败的根因，发现上下文误解/幻觉、错误重命名、新增不该有功能、代码不完整和语法结构错误都是常见问题。它的流程并不是每次都立刻再问 LLM，而是先用静态 repair 处理缺 import、括号不平衡、编译错误等低层问题，避免把便宜确定性检查交给大模型。对仍然失败的重构，它再结合单元测试日志、错误解释、项目上下文检索和 code diff 引导 agent 做迭代修复。论文报告在剩余失败上最高 70.8% repair rate，最佳配置累计 pass rate 可到 94.2%。它不像 ProMax 那样是大型 benchmark，但很贴近实际 IDE/CI 中“让 agent 做重构后如何提高可靠性”的问题。对后训练软件工程来说，它提示重构轨迹不该只记录最终 patch，还要记录静态检查、测试日志、diff 语义和修复轮次，才能训练出真正稳的 refactoring agent。
🔗 链接：https://arxiv.org/abs/2608.00924 ｜ 代码：None

### VulnGym：带 vulnerability trace 的仓库级漏洞检测 agent benchmark
很多漏洞检测 benchmark 只给一段函数或文件，让模型判断是否有漏洞；但真实安全 agent 需要在整个仓库里探索依赖、入口、数据流和危险操作。VulnGym 把任务推进到 repository-level vulnerability detection：它把已审核 GitHub advisories 对齐到对应的 vulnerable repository versions，构造 184 个 advisories、408 个 vulnerability entries，覆盖 23 个仓库。每个 entry 不只标“有漏洞”，还带 line-level entry points、critical operations 和 vulnerability traces，因此能诊断 agent 是找不到入口、无法构造证据，还是最终判断错误。评测任务包含端到端检测和三个 oracle-based subtasks，用来拆开 localization、evidence construction 和漏洞判定能力。论文结论是当前 coding agents 在仓库级漏洞检测和支持性 trace 构造上都仍然有限。它按 Medium 收录，因为安全检测不是今天主线里的数据合成，但它是非常工程化的 eval anti-cheating / evidence benchmark。对后训练来说，这类细粒度 trace 比普通漏洞标签更有价值，因为它能筛选“猜对漏洞名但没证据”的轨迹。
🔗 链接：https://arxiv.org/abs/2608.02001 ｜ 代码：None

### CodeProbe：从自家已合并 PR 自动挖 coding-agent eval，并比较模型+工具+harness
公开 SWE-bench 很有价值，但每个团队真正关心的是自己的代码库、自己的 review 标准和自己的 CI 习惯。CodeProbe 是一个轻量 Python CLI，思路是从仓库已合并 PR/commit 历史里挖任务，把变更前状态重建出来，再让不同 agent 配置尝试完成同类任务。它强调评测对象是完整系统，而不是单个模型：配置里可以 pin agent、model、preamble、MCP surface、retrieval 工具、timeout 和 turn limits。它还支持按目标选择任务形状，例如 quality、navigation、mcp 或 general，并用 isolation modes 和 bias detectors 防止工具系统自证有效。项目目前只有 7 stars，可信度和社区热度都低，所以按 Medium/Low credibility 处理；但它解决的是非常真实的企业问题：如何把“我们自己的工程历史”转成可回归 eval。对后训练软件工程来说，这类工具能让失败样本、检索策略和 harness 改动直接在私有仓库分布上验证，而不只依赖公共榜单。它也提醒我们，生产 agent eval 的单元应是 repo + task reconstruction + verifier + config，而不是一条孤立 prompt。
🔗 链接：https://github.com/sjarmak/codeprobe ｜ 代码：https://github.com/sjarmak/codeprobe

### OpenAI GPT-Live realtime system：全双工语音 agent 的低延迟流式架构
这条不是 coding-agent 后训练主线，所以按 Low 收录；但它是 OpenAI 8 月 3 日官方工程文章，属于官方源强制检查范围，且包含较明确的 agent runtime 工程细节。GPT-Live 的目标是让语音 AI 能同时听、想、说，而不是传统 request-response 式一问一答。OpenAI 描述的关键架构包括 streaming inference、动态上下文管理、异步 delegation，以及为低延迟优化的媒体传输路径。它把实时语音流和更深层推理任务拆成不同路径：语音必须持续流动，复杂思考可以异步委托给更强模型。文章还提到 Instant Connect 和 transport handshake 优化，把用户意图到媒体流开始的等待压低。对软件工程 agent 的直接影响有限，但对 agent runtime 有启发：长程工具 agent 也需要把交互通道、后台推理、上下文管理和网络传输解耦。它说明“agent 工程”不仅是 prompt 和工具选择，也包括会话协议、流式事件、异步委派和用户可感知延迟。

## 🔥 社区热点专栏

### 🔥 大佬观点

**Joel Niklaus / AINews：同一模型换 harness，pass@1 变化可大过模型升级。**  
`best-of-Agent-Harnesses` 引用了 Joel Niklaus 的社区分析：在 SWE-bench Pro 风格结果里，同一模型放到不同 harness，GLM-5.2 可从 23% 到 52% pass@1，Gemma 4 26B 可从 15% 到 36%，而 harness ranking 跨模型相关性甚至接近 0。这个观点值得注意，因为它把“选哪个模型”之外的第二个核心变量暴露出来：harness 的工具、内存、sandbox、恢复策略和 prompt 结构本身就是能力来源。🔗 https://x.com/joelniklaus/status/2085725862142623875 ｜ https://github.com/RyanAlberts/best-of-Agent-Harnesses

**HN / ScaleKit / CLI-MCP 讨论：MCP schema tax 的争论正在从立场战变成测量问题。**  
HN 近期围绕 MCP vs CLI 有多轮讨论，核心不再是“永远 CLI”或“永远 MCP”，而是 schema 是否懒加载、工具实际是否被调用、失败成本如何统计、OAuth/audit 是否值得额外上下文税。ScaleKit/Firecrawl 类基准给出 4-32x token 差距，但新 arXiv 受控实验也提醒，dominant factor 往往是 scaffold，而不是接口名。🔗 https://news.ycombinator.com/item?id=47208398 ｜ https://www.scalekit.com/blog/mcp-vs-cli-use

### ⭐ 超火仓库/项目

**RyanAlberts/best-of-Agent-Harnesses：528 stars，100+ agent harness 排名 + MCP 推荐器。**  
它火在解决“agent 应该用哪个 harness”这个越来越实际的问题：仓库不仅列举 Claude Code、Codex、OpenCode、Gemini CLI 等，还把 sandboxing、memory、hooks、prompt optimization、复杂度和恢复能力整理成可查询数据。更有意思的是它自己提供 MCP server，让 agent 可以调用 `recommend` / `pick_harness`，把社区知识变成 agent 可消费的选择器。🔗 https://github.com/RyanAlberts/best-of-Agent-Harnesses

**AntigmaLabs/ante：约 1.2k stars，自包含、高优化核心的 shell agent harness。**  
Ante 近期更新活跃，定位是“Ghost in your shell”，强调像 Claude Code/Codex 一样运行但不绑定特定模型或供应商。它的热度说明社区仍在寻找更轻、更可拥有、更可替换底层模型的 terminal harness，而不是只接受闭源客户端。🔗 https://github.com/AntigmaLabs/ante

**jgravelle/jcodemunch-mcp：约 2.5k stars，用 tree-sitter 做符号级代码检索以压缩 token。**  
这个项目持续活跃的原因很直接：coding agent 在大仓库里最容易把 token 花在读错文件、读整文件和重复 grep 上。jCodeMunch 用 AST/symbol 检索和紧凑 MUNCH wire encoding，把公开 benchmark 中代码探索 token 降低到 grep+read baseline 的约 3.6%，解决的是 codebase navigation 的硬成本问题。🔗 https://github.com/jgravelle/jcodemunch-mcp

**madeye/mcp-cli：118 stars，用 sidecar daemon + MCP bridge 减少 fork/exec 与重复索引成本。**  
它不是最大星标项目，但方向高信号：传统 shell wrapper 每次工具调用都 fork/exec，长程 coding agent 会在大量 read/grep/git 操作上烧掉延迟和 token。mcp-cli 把文件系统、git state 和 tree-sitter 索引做成驻留 daemon，并给 Codex/Claude Code 等 agent 提供 bridge，展示了 CLI 与 MCP 可以组合，而不是二选一。🔗 https://github.com/madeye/mcp-cli
