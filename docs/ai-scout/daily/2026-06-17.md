## 📝 逐条讲解

### StateGen：状态真源驱动的 tool-agent 合成数据平台
训练 tool-augmented agent 的一个老问题是，真实生产日志里有隐私、支付、账号和业务敏感信息，不能直接拿来做后训练数据；人工标注多轮工具对话又慢、贵且质量不稳定。StateGen 的做法是把合成数据生产变成一个带“世界状态真源”的四角色系统：用户模拟器提出需求，待训练 agent 调工具，工具模拟器给响应，judge 对整段轨迹打分。最关键的工程点是 authoritative state manager，它维护结构化世界状态，要求每次工具返回都和后端真相一致，从源头减少“工具突然查到不存在订单/账户”的幻觉。它还支持把 sub-agent 声明成工具，让多 agent 编排的数据生成共享同一个状态对象，而不是每个模拟器各编一套世界。论文报告在三个生产语料上生成 64,698 条已评估对话，工具调用幻觉分达到 9.66/10，并用 23 维 persona 向量制造用户差异。对后训练数据工程来说，这比普通 Self-Instruct 更接近真实 agent 数据流水线：先定义状态、工具、persona、judge，再规模化生成可评分、多轮、带 reasoning trace 的训练样本。值得借鉴的是“backend-is-truth”这个不变量，它把数据合成从语言续写问题变成了有状态仿真问题。
🔗 链接：https://arxiv.org/abs/2606.16307 ｜ 代码：None

### SWE-Explore：把仓库探索从最终修复分数中拆出来评测
SWE-bench 类评测通常只看最终 patch 是否通过测试，但 agent 修不好一个 bug 时，我们很难知道它是没找到相关代码，还是找到了代码却不会改。SWE-Explore 专门把“仓库探索”单独拿出来测：给定 issue 和仓库，agent 不需要写补丁，只要在固定行数预算内返回最相关的文件与行区间排序列表。它的 ground truth 不是人工逐行标，而是从多个成功修复同一 issue 的 agent 轨迹里提取真实读过、用过的代码区域，再聚合成 line-level supervision。数据规模为 848 个 issue、203 个开源仓库、10 种语言，每个样本平均有 4.3 个相关文件、4.7 个代码区域和 1,578 行可见上下文。论文同时验证这些探索指标和下游修复成功率强相关，说明这不是“为了测检索而测检索”，而是能预测 patcher 后续能否修好。一个很有启发的结果是，现代 agent 找到正确文件已经不难，但 line-level coverage 和高效排序仍然弱，这会直接限制修复质量。对 coding-agent 评测工程来说，SWE-Explore 提供了一个更细的诊断接口：先优化“读对证据”，再谈“写对补丁”。
🔗 链接：https://arxiv.org/abs/2606.07297 ｜ 代码：https://github.com/Qiushao-E/SWE-Explore-Bench

### LLM-as-Code：让程序掌控 agent 控制流，LLM 只做判断节点
很多 agent framework 默认让 LLM 自己决定下一步做什么、什么时候调用工具、什么时候停止，这在短 demo 里很灵活，但长程任务会暴露三类问题：上下文爆炸、控制流幻觉、提前宣布完成。LLM-as-Code 的核心观点很直接：循环、分支、顺序、重试这些确定性控制流应该由程序语言保证，而不是让概率模型每一步重新“想起来”。它提出 Agentic Programming，让代码负责 workflow，LLM 只在需要理解、总结、生成或判断的节点被调用。这样执行历史不再是一个越来越长的扁平 transcript，而是函数调用图；每个 LLM 调用只看自己的祖先上下文和已返回子树摘要，形成 DAG-scoped context。多 agent 协作也变成并行函数调用，子 agent 返回 typed value，失败可以被程序重试、降级或记录，而不是污染同一个聊天上下文。论文在 OSWorld GUI 自动化 case study 中报告 LLM-as-Code + Claude Sonnet 4.6 在 15 步内达到 86.8，总体超过多个 100-step baseline。对 harness engineering 的启发是：不是所有智能都要放进模型，可靠性更应该来自“哪些步骤由代码保证、哪些判断交给 LLM”的边界设计。
🔗 链接：https://arxiv.org/abs/2606.15874 ｜ 代码：https://github.com/Fzkuji/Agentic-Programming

### LangSmith Sandboxes GA：给每个 agent 一台 microVM 电脑
当 agent 能写代码、装依赖、跑测试、启动服务时，执行环境就不再是普通工具，而是可靠性和安全边界本身。LangSmith Sandboxes 的产品化信号很明确：每个 agent 需要一台像电脑一样的隔离环境，既有文件系统、shell、包管理器和持久状态，又能快速启动并在任务结束后销毁。LangChain 选择 hardware-virtualized microVM，而不是普通容器，原因是容器共享宿主机内核，面对模型生成或用户输入触发的未知代码时安全边界更薄。GA 版本强调 snapshots、parallel workloads、企业安全、资源限制和 lifecycle control，并把 auth proxy 放在网络层注入凭据，避免 secret 直接进入 agent runtime。这个设计解决的是生产 agent 最现实的痛点：让 agent 能真实运行代码验证结果，同时不把主机、凭据、邻居 workload 暴露给它。它还和 Deep Agents、Open SWE、LangSmith tracing/evals/deployment 连接，说明 sandbox 正在从“自搭基础设施”变成 agent 工程平台的一等组件。对后训练和评测团队来说，microVM sandbox 也会影响 rollout 并发、环境 snapshot、轨迹可复现和安全审计成本。
🔗 链接：https://www.langchain.com/blog/langsmith-sandboxes-generally-available ｜ 代码：https://docs.langchain.com/langsmith/sandboxes

### GitHub Copilot cloud agent：Automations + Agent Tasks REST API
过去 cloud coding agent 的入口主要是 issue assignment、IDE 或聊天窗口，自动化程度有限；GitHub 6 月的两个 changelog 把它推进到可编程控制面。Automations 允许 Copilot cloud agent 按 schedule 或 repo event 自动运行，比如定期修 failing tests、给新 issue 打标签、准备每周 release notes。Agent Tasks REST API 则提供 `POST /agents/repos/{owner}/{repo}/tasks` 这类端点，让内部平台、脚本或 webhook 直接创建和追踪 agent task，并可选择自动开 PR。这个变化的工程意义是，coding agent 从“用户手动派活的工具”变成“可以被 CI、portal、cron、release pipeline 调度的后台 worker”。同时 API 也暴露了生产必须关心的字段：base ref、head ref、model、create_pull_request、状态轮询、waiting_for_user 等。它解决的痛点不是模型会不会写代码，而是团队怎么把 agent 接进已有开发运营系统，并在可审计、可暂停、可追踪的状态机里运行。对 Agent-Friendly Software 来说，这相当于 GitHub 把自己的开发平台开放为 agent-native dispatch layer。
🔗 链接：https://github.blog/changelog/2026-06-02-schedule-and-automate-tasks-with-copilot-cloud-agent/ ｜ 代码：https://github.blog/changelog/2026-06-04-agent-tasks-rest-api-now-available-for-copilot-pro-pro-and-max/

### Omnigent：Databricks 开源跨 Claude Code / Codex 的 meta-harness
单个 coding agent 已经很强，但很多团队真实使用的是 Claude Code、Codex、Cursor、Pi、OpenAI Agents SDK、Claude Agent SDK 混合栈，结果就是 session、权限、成本、review 和上下文分散在多个工具里。Omnigent 的定位是 meta-harness：不替代底层 harness，而是在它们上面提供统一消息/文件/tool-call 接口。Databricks 博客强调三个能力：组合不同模型和 harness，集中做 policy 与 cost control，以及让团队通过 web、mobile、terminal 共享同一个 live session。项目还提供 Polly 这类多 agent coding orchestrator，让一个 agent 拆任务、不同供应商 agent 并行实现，再由另一个供应商 reviewer 做 maker-checker。HN 讨论里最被认可的点是，approval、成本和权限最好在 harness layer 强制执行，而不是写在 prompt 里让 agent 自觉遵守。仓库约 2k stars，6/16 还在加入 Cursor first-party harness 和安全 hardening，说明它不是静态 demo。对 agent 系统工程来说，Omnigent 代表一个新层级：当 harness 已经成为能力来源，meta-harness 会成为治理、协作和跨供应商调度的控制面。
🔗 链接：https://www.databricks.com/blog/introducing-omnigent-meta-harness-combine-control-and-share-your-agents ｜ 代码：https://github.com/omnigent-ai/omnigent

### Search-Time Contamination：搜索型 deep research agent 的推理污染
带 web search 的 deep research agent 评测有一个新风险：agent 不是自己推理出答案，而是在搜索时把公开 benchmark 题目、上下文甚至答案搜出来了。Search-Time Contamination 把这种现象分成三类：benchmark metadata leakage、question-context leakage 和 explicit answer leakage，严重程度逐级上升。它的重要性在于，传统数据污染关注“训练前模型是否见过测试集”，而 search-time contamination 发生在推理时，即使模型训练干净，只要评测允许联网，也可能绕过原本的能力测量。论文在六个公开 benchmark 上评估现代 deep research agents，发现污染普遍存在，并可把分数虚高最多约 4%，甚至改变模型排名。作者建议的工程手段包括隔离 sandbox、透明搜索轨迹、受控 benchmark 访问、source filtering 和 contamination-aware audit。虽然它主要面向 deep research/medical benchmark，但对 coding agent 同样有警示：一旦 agent 能搜索网页、读 GitHub、查 Hugging Face，公开 verifier、题解和测试数据都可能成为捷径。对 eval anti-cheating 来说，这篇把“联网 agent 的评测污染”从直觉风险变成了可分类、可检测、可治理的工程问题。
🔗 链接：https://arxiv.org/abs/2606.05241 ｜ 代码：None

### Claude Managed Agents：把 Claude Code harness 变成托管 agent surface
Claude Code 让很多开发者第一次体验到完整 agent harness：loop、工具执行、subagents、context management 和持久 session 都已经调好。Claude Managed Agents 的产品叙事是把这套 machinery 从终端 coding 场景抽出来，变成开发者可以在自己业务里调用的托管 agent surface。官方博客强调，用户定义任务、工具和 guardrails，Anthropic 托管 execution environment、failure recovery、multi-agent orchestration 等底层 loop。它还提到 outcomes，让 agent 可以按照 rubric 给自己的工作打分；再加上 webhooks、permission policies 和 sandbox sessions，就更像一个 production agent runtime，而不是普通聊天 API。与 Claude Agent SDK 的区别是，SDK 让你在自己的进程里复用 Claude Code loop，Managed Agents 则把运行环境和生命周期也托管出去。它值得关注，是因为大厂正在把“harness”从产品内部实现升级成 API 级平台能力。对后训练软件工程而言，这会影响真实轨迹采集、运行时 policy、客户自定义 eval rubric 和多 agent 任务编排的标准形态。
🔗 链接：https://claude.com/blog/building-with-claude-managed-agents ｜ 代码：https://docs.anthropic.com/en/docs/claude-code/sdk

### LangChain sandbox 架构模式：Agent in Sandbox vs Sandbox as Tool
“给 agent 一个 sandbox”听起来简单，但架构上至少有两种常见模式，差别会影响安全、迭代速度和状态管理。LangChain 这篇把它拆成 Agent in Sandbox 和 Sandbox as Tool：前者把 agent 本身跑在 sandbox 内，更接近本地开发体验，agent 和环境状态强绑定；后者让 agent 在你的服务或本地进程里运行，只把代码执行作为远程 sandbox 工具调用。Sandbox as Tool 的好处是 agent 逻辑更新快，API key 和长期 memory 可以留在 sandbox 外，sandbox 崩了不会带走对话状态。Agent in Sandbox 则适合希望生产环境和本地执行强一致、需要 agent 完整占有机器状态的场景。文档还区分 thread-scoped 和 assistant-scoped sandbox，说明同一个 assistant 是否共享环境也要显式设计。它的工程价值不在某个新产品，而在给团队一个决策框架：安全边界、凭据注入、生命周期、状态持久性和可观测性应该在接 sandbox 前就定下来。对 agent runtime 工程来说，这能避免“先把 shell 接上再说”的脆弱实现。
🔗 链接：https://www.langchain.com/blog/the-two-patterns-by-which-agents-connect-sandboxes ｜ 代码：https://docs.langchain.com/oss/python/deepagents/sandboxes

### Harness Engineering Survey：把 Claude Code / Codex 的能力归因到 harness
David Daniel 这篇更像一份证据标注过的实践综述，不是新 benchmark，但它把 2026 上半年围绕 harness engineering 的很多碎片梳理到一起。文章的核心判断是，agentic coding 的能力增长越来越多来自 harness，而不是单纯来自底层模型权重：loop engine、context compaction、permission layer、memory substrate、lifecycle hooks 等组件都会改变一个 agent 能独立工作多久、能否恢复、能否被审计。它引用并整理了九组件 anatomy：loop、context、tools/skills、subagents、built-in skills、session persistence、dynamic system prompt、hooks、permissions/safety。比较有价值的是作者对证据强弱做了标注：哪些是厂商自述，哪些是采访转述，哪些只是未验证的社区估计，避免把营销叙事直接当结论。文章还用 Amazon/Microsoft 对 Claude Code、Kiro、Copilot CLI 的组织选择说明，企业争夺的变量不只是模型，而是可被定制和治理的 harness。它对工程团队的启发是，选型和建设 agent 平台时要问“我们能改 loop、权限、memory、review 和 observability 吗”，而不只是问“背后模型是哪一个”。本文按 Medium 收录，因为它是综述而非新系统，但对统一团队语言很有用。
🔗 链接：https://daviddaniel.tech/research/papers/harness-engineering/ ｜ 代码：None

### Anthropic：Agentic coding 中领域专家仍有持续收益
Anthropic 6 月 16 日发布的研究不是新 harness，也不是新 benchmark，而是基于约 400,000 个 Claude Code sessions 的实际使用分析。它把 interactive agentic coding 拆成工作模式、决策分工、用户专业度和成功信号，并用隐私保护分析工具读取 transcript 与 telemetry。一个关键发现是，典型 session 里人类做约 70% 的 planning decisions，而 Claude 做约 80% 的 execution decisions，也就是人决定“要做什么”，agent 决定“怎么做”。另一个重要结论是，成功更多取决于用户对任务领域的理解，而不是传统编程职业身份；非软件职业用户在产出代码的 session 中成功率和软件工程师差距不大。更专业的用户每个 prompt 能触发更多 agent actions，也更能在出错后把 agent 拉回正确方向。它对后训练软件工程的启发是，真实 agent 数据不能只看模型能力，还要记录用户给出的任务约束、验证要求、纠错行为和领域知识密度。按本日报规则，它属于高可信官方源，但更偏 usage/economic research 而非可复用工程机制，因此放在 Low。
🔗 链接：https://www.anthropic.com/research/claude-code-expertise ｜ 代码：None

## 🔥 社区热点专栏

### 🔥 大佬观点

**Matei Zaharia / Databricks：单个 agent harness 之上需要 meta-harness 控制面。**  
Databricks 围绕 Omnigent 的发布把问题说得很清楚：当团队同时使用 Claude Code、Codex、Pi、Cursor 和自定义 agent 时，下一层价值不再是再造一个 harness，而是把 composition、policy、cost、live collaboration 放在统一层管理。这个观点值得注意，因为它把“多 agent 编排”从 prompt 话术拉回到工程控制面：权限和预算要由平台强制执行，不能只写进提示词。🔗 https://www.databricks.com/blog/introducing-omnigent-meta-harness-combine-control-and-share-your-agents

**HN 社区对 Omnigent 的讨论：maker/checker split 和并行 worktree 是 meta-harness 的真实痛点。**  
HN 讨论中最有信息量的评论不是“又一个 agent 工具”，而是指出 Omnigent 添加的正是 loop engineering 缺的机器：并行 git worktrees 防止 agent 互踩，approval/cost policy 在 harness layer 执行，不同供应商 writer/reviewer 减少同模型盲点。它值得关注，因为这说明社区已经开始要求 agent 编排工具有可审计控制面，而不是只展示多个聊天窗口。🔗 https://news.ycombinator.com/item?id=48518176

### ⭐ 超火仓库/项目

**Omnigent（omnigent-ai/omnigent）：约 2k stars 的开源 meta-harness。**  
它火的原因是直接踩中“我有 5 个 coding agents，但没有统一控制面”的痛点：同一 session 可从 terminal、web、mobile 访问，底层可换 Claude Code、Codex、Cursor、Pi 或 SDK agent。更重要的是它把 cost budget、PII policy、maker-checker review、parallel worktrees 做成平台能力，适合继续观察能否成为跨 harness 的事实标准。🔗 https://github.com/omnigent-ai/omnigent

**SWE-Explore-Bench（Qiushao-E/SWE-Explore-Bench）：新发布的仓库探索评测数据与代码。**  
这个项目热在它切中了 SWE-agent 评测的盲点：很多 agent 能“碰到正确文件”，但找不到真正决定修复的行级证据。仓库公开 848 个 issues、trajectory-grounded line-level labels 和评测指标，适合内部团队把 context retriever / explorer 单独拉出来回归，而不是等最终 patch 失败才知道问题。🔗 https://github.com/Qiushao-E/SWE-Explore-Bench

**LangSmith Sandboxes：生产 agent 执行环境层开始产品化。**  
LangChain 把 microVM sandbox 做成 LangSmith GA 能力，说明 agent 基础设施正在从“框架 + tracing”扩展到“隔离执行环境 + 凭据代理 + snapshot/fork”。它解决的痛点非常现实：agent 需要真的运行代码和测试，但不能把主机、secret 或邻居 workload 交给模型生成的命令。🔗 https://www.langchain.com/blog/langsmith-sandboxes-generally-available

**GitHub Copilot Agent Tasks API / Automations：cloud coding agent 进入可编程调度阶段。**  
这个项目/接口火的原因不是新模型，而是触发面变了：内部开发者门户、cron、release pipeline、repo event 都能直接派发 agent 任务并追踪状态。它解决的是企业把 coding agent 纳入现有 SDLC 自动化的问题，后续会推动 agent 任务队列、权限、成本和 PR 审计成为平台级能力。🔗 https://github.blog/changelog/2026-06-04-agent-tasks-rest-api-now-available-for-copilot-pro-pro-and-max/
