## 📝 逐条讲解

### Probe-and-Refine：用失败探针自动调优 AGENTS.md 仓库指南
现在很多仓库会写 `AGENTS.md` 或类似文件，告诉 coding agent 先看哪里、怎么跑测试、哪些目录容易踩坑，但这些指南常常靠人工经验维护，质量好坏很难验证。Probe-and-Refine 的出发点是把“仓库指南是否真的帮 agent 做事”变成一个可测试的数据工程问题，而不是靠感觉写长说明。它先用合成 bug-fix probe 去测试当前指南，观察 agent 在文件选择、测试流程和修复路径上哪里失败，再用单轮 LLM 调用补丁式改写指南。整个流程不跑多步 agent loop，也不做 RL，而是产出每个仓库不超过约 3000 字符的紧凑操作知识。论文报告，在 SWE-bench Verified 上，相比静态知识库，调优后的指南让 agent 覆盖更多可解决实例，约多解决 14.3 个百分点，同时 patch precision 没有显著下降。它值得关注，是因为它把 repo memory / AGENTS.md 从“文档资产”升级成可探测、可回归、可迭代的 harness 数据资产。对后训练软件工程来说，这类 probe 也可以成为筛选训练轨迹和维护项目级 agent 指南的低成本流水线。
🔗 链接：https://arxiv.org/html/2606.20512v1 ｜ 代码：https://github.com/asashepard/probe-and-refine-tuning

### Phoenix：带七层安全控制的 GitHub issue 到 PR 多 agent 系统
许多 GitHub issue agent demo 能从问题描述生成补丁，但真正接进仓库工作流时，还要处理权限、CI、flaky tests、token 过期、PR 创建边界和错误定位。Phoenix 把这个流程做成生产路径：六个专门 agent 分别负责规划、复现、编码、测试、失败分析和 PR 创建，并由 GitHub webhook 的 label 状态机协调。它不是让一个大 agent 一路自由发挥，而是把每个阶段的输入输出和安全门拆开，尤其强调 baseline-aware test evaluation：先跑基线，再判断新变更是否引入 pass-to-pass 回归。论文在 24 个 SWE-bench Lite curated slice 上报告 75% oracle-resolve，在 42 个真实 issue、14 个仓库 pilot 中报告 correctness preservation 为 100%，但也诚实指出约一半 PR 因路径定位错误而不够理想。这个结果说明“安全开 PR”不是单纯提升模型分数，而是工程状态机、权限边界和测试解释一起发挥作用。对内部 agent 平台来说，Phoenix 的价值在于它公开了 WAF、token、权限、CI 等部署失败模式，以及每个安全机制为什么被加入。后训练视角下，这些失败模式可以反过来变成训练和评测的真实负样本。
🔗 链接：https://arxiv.org/abs/2606.20243 ｜ 代码：https://github.com/kkipngenokoech/phoenix

### StaminaBench：用 100 轮连续变更请求测试 coding agent 耐力
传统 coding-agent benchmark 往往把每个任务当作一次性 issue，agent 只要在一个窗口内修好并通过测试即可。真实 vibe-coding 或产品迭代更像连续对话：用户不断追加需求、改 API、换约束、要求保留既有行为，agent 需要在几十轮后仍然理解系统状态。StaminaBench 直接测这种“耐力”，让 agent 先实现一个 REST API server，再连续处理最多 100 轮程序化生成的 follow-up change requests。它关心的不是一次 pass rate，而是 agent 能撑到第几轮、在哪类变更后开始退化、是否破坏旧功能。这个设置很贴近长程后训练数据，因为高质量训练轨迹不只是“最终补丁成功”，还应包含多轮维护、回归保护和需求漂移下的状态管理。它也会暴露 memory、context compaction、测试选择和 stop condition 的问题：很多 agent 前 10 轮表现不错，越到后面越容易忘记早期设计。对评测工程来说，这类 benchmark 能补上 SWE-bench 的盲区，衡量 agent 是否适合真实持续开发会话。
🔗 链接：https://arxiv.org/abs/2606.19613 ｜ 代码：None

### Before the Pull Request / Grite：把多 agent 协作状态写进 git refs
现在很多团队让多个 coding agent 并行处理同一仓库，但真正的冲突往往发生在 PR 之前：两个 agent 同时认领相邻文件、重复调查同一问题、各自保存不同上下文，最后才在 diff 或 CI 里暴露。Before the Pull Request 关注的正是这个 pre-PR 协作层，并提出 Grite 作为 git-native coordination substrate。Grite 不需要外部服务器或数据库，而是把 issue、任务、锁和记忆写进仓库的 git refs，例如 append-only event log，并用 CRDT 做确定性合并。它还提供 TTL-based lease locks，让 agent 可以声明“我正在改这个资源”，其他 agent 即使在不同机器上也能通过 git sync 看到状态。这个设计很适合 agent 工程，因为 git 本来就是代码和变更历史的真源，把协作状态放进 git refs 可以减少工作树污染和外部系统依赖。论文的核心启发是，未来多 agent 软件工程需要的不只是更聪明的 planner，还需要可同步、可审计、可离线工作的任务与记忆层。对后训练数据采集来说，pre-PR telemetry 能记录 agent 如何分工、碰撞和让步，这是最终 PR 元数据看不到的训练信号。
🔗 链接：https://arxiv.org/abs/2606.19616 ｜ 代码：https://github.com/neul-labs/grite

### ToolPrivBench：评测 agent 是否滥用高权限工具
工具 agent 的安全问题不只是“能不能拒绝危险请求”，还包括它在有多个工具可选时是否遵守最小权限原则。ToolPrivBench 定义了 over-privileged tool selection：明明低权限工具已经足够，agent 却选择或升级到更高权限工具，尤其在低权限工具临时失败后更容易发生。论文覆盖 8 个领域和 5 类风险模式，分别测初始选择和 transient failure 之后的升级行为。一个重要发现是，通用安全对齐并不可靠迁移到 least-privilege tool choice，prompt 级提醒也只能有限缓解，遇到工具失败时尤其脆弱。作者进一步提出 privilege-aware post-training defense，让模型学会优先使用足够的低权限工具，只在必要时升级，同时尽量不损害一般能力。它的工程价值很直接：企业 agent 平台不能只给工具打标签，还要在 eval、训练和 runtime policy 中测“为什么要用这个权限”。对 Agent-Friendly Software 来说，ToolPrivBench 提醒我们工具 API 设计应包含权限等级、失败语义和升级证据，而不是只暴露一组等价函数名。
🔗 链接：https://arxiv.org/html/2606.20023v1 ｜ 代码：https://github.com/AISafetyHub/agent-tool-selection-bias

### CodeSentinel：面向代码上下文间接 prompt injection 的 CST 清洗器
Coding agent 会读取仓库代码、注释、issue、文档和示例，这些内容一旦被攻击者写入“忽略安全规则、泄露 secret、运行外部命令”等指令，就会变成间接 prompt injection。普通文本过滤很难处理代码场景，因为恶意内容可以藏在字符串、注释、标识符、伪测试、decoy code 或自然语言片段里。CodeSentinel 的关键做法是把不可信代码当作结构化输入，用 Tree-sitter 解析 concrete syntax tree，再抽取最可能进入模型上下文的高风险节点。它组合三层检测：显式异常的 syntax-guided pre-filter、针对扰动的 CST-guided Dynamic Min-K% scoring、以及发现自然语义触发器的 node perturbation analysis。被标记的节点会在传给下游 Code LLM 前被删除或中和，而不是要求模型自己忽略它。论文报告在六类近期攻击上达到 0.80 平均节点级 F1，并优于 CodeGarrison、DePA、KillBadCode 等 baseline。对 harness 工程来说，这说明代码检索层需要“模型可见上下文清洗”，安全边界应放在 Read/Grep/RAG 输出进入模型之前。
🔗 链接：https://arxiv.org/html/2606.19235v1 ｜ 代码：None

### PhantomSkill：把恶意 payload 藏进 Agent Skill 辅助资源
Agent Skills 正在变成插件生态，但很多安全扫描只看 `SKILL.md` 里的自然语言描述，或者只扫描显式脚本恶意行为。PhantomSkill 指出一个更隐蔽的问题：攻击者可以把恶意行为藏在 skill 的辅助资源、脚本和支持文件里，并让它看起来像普通漏洞。它的核心技术 VulMask 会把直接恶意脚本改写成 vulnerability-shaped implementation，也就是表面上像一段有缺陷但正常的代码，只有在攻击者控制的触发条件下才激活原 payload。这样自动 reviewer 和 coding agent 自查时更容易把问题当作一般安全弱点，而不是识别成恶意意图。论文在多种 host skills、攻击目标、coding agents、生成模型和自动审查器上验证，显示 VulMask 能保持 benign utility，同时降低 warning 和 malware-level detection。它对 skill supply chain 的启发很强：不能只审 skill 描述，还要做 resource-level vetting、执行时 containment、权限最小化和可疑漏洞策略。对后训练安全数据来说，这类样本很适合作为“看似普通漏洞、实为触发型恶意载荷”的训练与评测集。
🔗 链接：https://arxiv.org/html/2606.19191v1 ｜ 代码：https://anonymous.4open.science/r/PhantomSkil-6C18/

### ToolPro：把多步 Web 服务调用封装成可执行 tool program
当前很多 agent tool interface 仍像静态 endpoint 列表：每个 API 是一个孤立函数，循环、重试、分页、join、条件分支和幂等语义都要由模型在主推理轨迹里一步步管理。ToolPro 的观点是，agent 对 Web 服务的意图常常不是一次调用，而是一段可执行的 tool program。它把多步服务交互压缩成带 effect types 的程序结构，并通过 constraint-guided program construction 构造满足 schema、依赖和副作用约束的调用计划。对于有副作用的操作，它引入 effect-aware replay，目标是在重试或恢复时仍能做到 exactly-once 语义，而不是重复下单、重复发邮件或重复写数据库。这个方向很符合 Agent-Friendly Software：传统 Web API 需要从“给人或脚本调用的 endpoint”升级为“给 agent 执行工作流的可验证程序接口”。它的工程价值不在替代 MCP，而是在 MCP/HTTP/SDK 之上表达更长程、更安全的服务操作。对训练数据来说，tool program 也比展开后的低级 tool-call trace 更适合作为可复用技能和 verifier contract。
🔗 链接：https://arxiv.org/abs/2606.19992 ｜ 代码：None

### Claude Code Artifacts：把终端 agent 会话发布成组织内实时交互页面
终端 coding agent 的一个协作痛点是，agent 在 shell 里做了大量调查、读代码、跑测试和分析，但团队成员看到的往往只是最终 diff 或一段难读的 transcript。Claude Code Artifacts 把这个过程转成 live interactive page：比如 PR walkthrough、incident timeline、架构图、license audit、release checklist 或成本 dashboard。它不是要求用户手工接数据源，而是 Claude Code 从当前会话上下文、代码库、connectors 和对话里生成页面，并在 agent 继续工作时更新同一个 URL。每次发布都有版本历史，可回滚；页面默认只对作者可见，分享后也只在组织内认证用户可访问，管理员可以设置开关、角色范围、retention 和 compliance API。这个功能的工程意义是把 agent trace 从“开发者私人终端日志”提升成团队协作 artifact，让 reviewer、SRE、经理和安全团队共享同一份证据。对后训练软件工程来说，artifact 也可能成为新的监督信号：好的 agent 不只产出 patch，还能产出可审阅、可解释、可持续更新的工作产品。它直接服务 harness observability 和人机协作，因此按 High 收录。
🔗 链接：https://claude.com/blog/artifacts-in-claude-code ｜ 代码：https://code.claude.com/docs/en/artifacts

### MCP Enterprise-Managed Authorization：企业级 MCP 连接器零触摸授权
MCP 让 agent 接入外部工具更容易，但企业部署时一个大问题是授权：如果每个员工、每个 connector 都要单独 OAuth，同意、撤权、审计和条件访问会变成治理噩梦。Claude 与 MCP 官方博客 6 月 18 日发布 Enterprise-Managed Authorization，把组织 IdP 变成 MCP server access 的权威决策者。管理员在 Okta 等身份系统里配置一次，用户登录 Claude、Claude Code 或 Cowork 时就自动获得对应 connector，不需要逐个授权；离职或角色变化也可通过 IdP 集中撤销。该扩展基于 MCP 的 Enterprise-Managed Authorization 和 Okta Cross App Access / ID-JAG 流程，Anthropic 已在共享 MCP 层实现，Microsoft VS Code 也加入支持，Asana、Atlassian、Canva、Figma、Granola、Linear、Supabase 等 server 首批支持。它解决的是 agent 工具生态规模化的真实痛点：连接器越多，权限和 token 生命周期越不能靠用户点击维持。对 Agent-Friendly Software 来说，这是 MCP 从开发者插件走向企业控制面的关键一步。对评测和后训练也有启发：agent 工具调用应携带身份、权限和撤权语义，不能假设所有工具永远可用。
🔗 链接：https://claude.com/blog/enterprise-managed-auth ｜ 代码：https://modelcontextprotocol.io/extensions/auth/enterprise-managed-authorization

### PACT：用 privileged trace 做多轮工具 agent 的 SFT/RL 共训练
多轮工具 agent 的训练经常在两种信号之间摇摆：SFT 专家轨迹有密集过程监督，但容易把模型绑死在固定路径；RL 更贴近推理时自由探索，但奖励稀疏、credit assignment 困难。PACT 试图把两者结合起来，使用 privileged trace co-training：训练时可以看到更丰富的过程信号，推理时仍保持 prompt-only 的工具使用设置。它的核心价值在于把多轮工具调用中“哪些步骤有帮助、哪些观察改变了决策、哪些错误应该归因到前面动作”显式化。相比只用最终成功/失败奖励，这类 privileged trace 能给模型提供更细的过程方向；相比纯模仿专家，它又保留了 RL 对多样轨迹的优化空间。本文按 Medium 收录，因为它更偏 post-training 方法，但重点在工具 agent 的训练数据和流程，不是纯理论算法。对工程团队来说，PACT 提醒我们记录轨迹时应尽量保留可训练的中间信号，例如工具状态、失败原因、替代动作和验证结果。否则后续即使想做 RL，也只能从稀疏 outcome 里猜原因。
🔗 链接：https://arxiv.org/abs/2606.16215 ｜ 代码：None

### VISUALSKILL：给 Computer-use agent 的多模态技能库
Computer-use agent 面对 GUI 软件时，很多知识不是纯文本：按钮位置、视觉状态、面板层级、图标含义和操作前后截图都很重要。现有 skill library 多数仍把技能写成文本说明或脚本片段，这对 GUI 长程任务不够自然。VISUALSKILL 提出 hierarchical multimodal skill，把每个目标应用的技能组织成中心索引和按主题拆分的多模态文件，agent 通过 `load_topic` 这类 MCP 工具按需加载。这样技能不必一次性塞满上下文，也能把截图、视觉提示和操作说明绑定在一起。它特别关注长程任务和未见软件，因为这些场景里 agent 不能只靠通用 GUI 常识，需要把上次学到的应用结构复用起来。本文和本日报的 Agent-Friendly Software 方向相关：把 GUI/桌面软件转成 agent 可调用的技能层，不一定要完全 CLI 化，也可以把视觉操作经验结构化。落地时需要注意技能版本、截图过期、应用 UI 改版和权限隔离，否则视觉技能会快速陈旧。
🔗 链接：https://arxiv.org/abs/2606.18448 ｜ 代码：None

### LLMZero：让 LLM agent 搜索 RL post-training 策略
RL post-training 的难点不只是选算法，还包括不同阶段的学习率、KL、熵、batch、正则和停止条件如何随训练动态变化。固定 schedule 常常无法适应非平稳训练过程，而人工网格搜索成本高、也很难总结跨任务规律。LLMZero 把这个过程交给 LLM agent：它读取训练 checkpoint 的文本指标和可视化图，诊断训练病灶，再提出下一阶段多参数转移，并用 tree search 在训练轨迹空间里探索。系统还带 agentic early stopper，提前终止没希望的分支，把预算集中到更有价值的策略上。论文在 4 个 GRPO 任务上报告，相比 base model 有 9% 到 140% 相对提升，相比 grid search 也有 6% 到 15% 相对提升。本文按 Medium 收录，是因为主题偏 RL 策略自动化而非 coding agent，但它体现了“后训练流程本身由 agent 管理”的趋势。对工程落地来说，最值得借鉴的是把训练监控、策略版本、早停和多阶段组合做成可审计搜索树。
🔗 链接：https://arxiv.org/html/2606.18388 ｜ 代码：None

### N-Version Programming with Coding Agents：用多实现多样性研究 agent 失败相关性
传统软件可靠性里有一个老思路叫 N-version programming：让多个团队独立实现同一规格，再用投票或交叉测试降低共同失败概率。现在 coding agent 可以很便宜地产生许多实现，这篇工作重新问了一个问题：不同 agent、模型和语言生成的失败模式是否真的足够多样，能不能借鉴 N-version 的可靠性思想。作者使用经典 Knight-Leveson Launch Interceptor Program Specification，生成 48 个 agent 实现，并用共享 oracle 和 100 万个随机测试输入进行评估。它关注的不是某个 agent 单独写得多好，而是多实现之间的错误是否相关、哪些 diversity 维度真正带来独立性。这个问题对多 agent maker-checker 和 ensemble coding 很重要，因为如果两个 agent 共享相同错误倾向，互相 review 也可能只是共同盲点的确认。本文按 Medium 收录，因为它不是新 harness，但提供了一种评估 agent 多样性和交叉验证可靠性的实验方式。对后训练数据筛选也有启发：高价值轨迹不应只来自一个模型/一个 harness，失败相关性低的实现更适合作为对照和审计材料。
🔗 链接：https://arxiv.org/html/2606.20158v1 ｜ 代码：None

### OpenAI 罕见病重分析：o3 Deep Research 辅助专家找回 18 个诊断线索
这项 OpenAI Applied AI 研究不属于 coding agent，但它是近月官方新增 publication，并展示了长程 expert workflow 里的 AI 辅助分析。罕见病基因诊断的痛点在于，患者数据、表型、变异注释和新文献分散在多个系统里，即使专家也很难持续重分析所有旧病例。研究团队把 376 个此前未解决病例整理成去标识化 packet，让 o3 Deep Research 产生带证据链的候选分子解释，再由专家用 ACMG/AMP 框架复核、补充测试和临床确认。最终医生确认了 18 个诊断，额外诊断率为 4.8%；模型没有直接诊断病人，而是提供可审查的假设。它对本日报的间接价值在于“AI 作为 evidence-linked hypothesis generator”的工程模式：输入需要标准化，输出要可追问，结论必须经过人类 gate 和外部确认。虽然主题偏医学，按 Low 收录，但它和 GPT-Rosalind、LifeSciBench 一样说明高风险 agent 工作流必须把评测、审计、隐私和专家裁决一起设计。对后训练软件工程也有借鉴：长程 agent 的输出越重要，越需要证据链接、版本化 prompt、审计日志和不可跳过的人类确认。
🔗 链接：https://openai.com/index/diagnose-rare-childhood-diseases/ ｜ 代码：None

### ⭐ 超火仓库/项目

**Grite（neul-labs/grite）：git-native issue/task/lock 层，面向多 agent 协作。**  
Grite 火在它解决了多个 agent 同仓库并行工作时最实际的问题：谁认领了什么、哪些资源被锁、哪些记忆应随代码一起同步。它把状态放进 git refs，使用 CRDT merge 和 TTL lease locks，不需要中心服务器，适合 agent 在本地、CI、云 worker 间协作。🔗 https://github.com/neul-labs/grite

**trace-mcp（nikolai-vysotskyi/trace-mcp）：用代码图谱替代 agent 反复 grep/read。**  
trace-mcp 近期持续更新，卖点是一次建立 framework-aware graph，再通过 MCP 给 Claude Code、Codex、Cursor 等 agent 提供 impact analysis、usage、dependency 等结构化查询。项目宣称一个 tool call 可替代约 42 分钟探索，解决的是 coding agent 反复读取同一代码结构导致的 token、延迟和上下文污染。🔗 https://github.com/nikolai-vysotskyi/trace-mcp

**agentproto：一次定义 tool contract，多 transport / 多框架复用。**  
agentproto 的热度来自一个很真实的痛点：同一个能力今天可能要作为内置函数、CLI、HTTP service、MCP server 或 Vercel/Mastra tool 暴露，重复写 adapter 会让 tool 生态碎片化。它把 TOOL.md contract 和 DRIVER.md implementation 分开，让 runtime 按 policy、成本或区域选择实现，这对 agent-friendly tool interface 标准化很有参考价值。🔗 https://github.com/agentproto/agentproto ｜ https://github.com/agentproto/ts

**Phantom（r3dlight/phantom）：AI 时代供应链扫描开始覆盖 MCP / CLAUDE.md / Cursor config。**  
Phantom 项目不是 PhantomSkill 论文代码，但它代表社区在同一风险面上的工程响应：把 XZ tarball diff、prompt injection、MCP 配置、CLAUDE.md/Cursor 规则等 agent 配置风险做成 CI/SARIF 扫描。它火的原因是安全团队开始意识到 agent 配置文件和 MCP server 与 npm 包一样，都是可被供应链攻击利用的执行入口。🔗 https://github.com/r3dlight/phantom
