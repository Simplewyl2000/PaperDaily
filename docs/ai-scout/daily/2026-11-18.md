## 二、逐条中文讲解

### 1. Experience Rot: Experienced Agents Fail Where Novices Succeed

代理会把对话、笔记和技能留下来，好让做过的事下次还能用。工具的字段和含义却可能在没有公告的时候换掉。文档不全时，这些旧记录本来是做成任务的原因；文档写全之后，人们又会以为代理看一眼当前定义就会改口。

六个模型在按 MCP 定义的工具上做了对照。文档不全时，没有经验做成 63%，经验仍然有效时是 100%；同一份经验过期后降到 23%，比没有经验低 0.40（±0.01）。四种改动之后，过期经验的成功率落在 15% 到 31%，第一次写入用的都是旧含义。文档写全、当前定义已经列出新字段时，过期经验仍只有 49%：定义写着 guests，代理却写 attendees，服务接受了旧调用，失败就被说成做完。在每条工具说明里加上版本号，并在任务里通知“服务已更新”，成功率只到 50%。

过期经验会让代理照抄旧调用，比从零开始更差；在说明和任务里通知更新，成功率只到 50%。

**链接：** [原文](https://arxiv.org/abs/2611.20922)

### 2. Benchleaking Is Accelerating

基准分里混进背题并不是新问题，但以前更常出现在后训练：模型或数据见过测试题，分数就变成回忆。公开基座经常被当成还没针对这些题优化过的起点。如果基座自己就会把没写进输入的题目和答案续出来，后面的微调对比就站在一块被污染的地上。

作者用少样本续写，看四个公开基座会不会写出输入里没有的其他测试题。ERNIE-5.5-Flash-Base 写出 96% 的 HumanEval 参考实现，以及 85% 带答案的 OpenBookQA；DeepSeek-V4-Flash-Base 分别是 9% 和 0。他们把这种调整叫 Anti-Hack：泄漏样例仍留在分母里，但一律算错。套件平均后，DeepSeek-V4-Flash-Base 掉 1.5 分，Hy3-preview-Base 掉 1.3 分，MiMo-V2.5-Base 掉 5.0 分，ERNIE 掉 16.6 分。这是续写探针，不是训练数据的成员推断。文中另引审计说，有代理在 23% 的尝试里说出没给过的隐藏测试要求，前代是 0；那是别人的审计，不是这次续写实验。

基座会把输入里没有的试题和答案续写出来；这些题不判错，公布的基座分数就掺着回忆。

**链接：** [原文](https://arxiv.org/abs/2611.21315)

### 3. Benchmark Factory: Agentic Benchmark Creation via Dataset Curation and Label-Free Quality Anchors

团队想用自己已经落地的代码变更做基准。手写题目、再逐题标对错都很贵，没人验证的基准又会安静地排错名次。常见补救是造完再抽人看，人看的时候仍然要给每题一个标签。

Benchmark Factory 让代理根据生产代码变更写检索条件，再拿已知相对强弱的模型去跑。候选没通过时，它改查询、提示和配置，直到满足一批不需要逐题人工标签的锚。五个团队的 5% 样本里，工程评分给任务质量 2.3、给裁判结论 2.6，量表是 1 到 3。造基准时没用过的配置上，高推理的 Claude Opus 4.7 通过 60.6%，低推理 54.4%（p=0.002）；GPT-5.5 是 65.8%，GPT-5.4 是 60.5%（p=0.004），10 组里 9 组方向一致。故意做烂的基准过不了锚，五个坏裁判也过不了；把模型标签打乱、使真实顺序不存在时，随机重抽最多只有 1.4% 的模拟能通过。作者把锚写成必要的，不是充分的。

没有逐题标签时，已知强弱的模型可以先拦住造坏的基准。

**链接：** [原文](https://arxiv.org/abs/2611.18890)

### 4. Beyond Plain MCP: Do Decision Models and Code Mode Make Tool Use Cheaper and Faster?

工具一多，模型要先读完整份目录，再把每次调用的结果读回来。两种省法已经很常见：让模型对着工具存根写一小段脚本，脚本在沙箱里把调用串起来，只把短结果交回模型；或者先用一个便宜模型挑出少数工具。人们容易把第二层当成第一层的必要补充。

这项预注册比较用了 12 个服务器、最多 1,958 个干扰工具，以及 Qwen、Gemma、Nemotron 三个开源权重代理。成功看的是模拟世界的最终状态，不是模型自己说做完了。代码模式把 token 降了 70% 到 90%，效用高于把目录直接塞进上下文。存根里如果不声明返回值的形状，Gemma 的成功率降 22.7 个点，Nemotron 降 39.5 个点，Qwen 没有显著变化；这个影响大于再加一个路由器。预先写下的中心假设是“路由器再加上代码模式，会胜过单独的代码模式”；较弱代理只有很小、校正后不显著的提升，最强的那个还有一点损失。论文页面给出的代码仓库可以复现这套对照，本次接口查询是 0 星，不能当成已有人采用。

省下来的 token 主要来自代码模式，返回形状要写在存根里；再前面加一层选工具，这次没有更值。

### 5. SWE-CoWork: Benchmarking Coding Agents as Digital Employees in Organizations

仓库级基准通常给一段问题描述，再看私有测试从失败变成通过。组织里的开发不是这样开始的：要做什么散在同事和记录里，写完还要真正交得出去。只看测试通过，会把“改对了一部分”和“这项工作做完了”记成同一件事。

SWE-CoWork 在 101 个真实仓库上放了 101 项开发任务，覆盖 11 种语言和 12 个领域。每项任务把代理放进一个有 26 名同事的模拟组织，同事的职责和知情范围是受控的，不是一家正在运转的公司。代理只拿到一份简短交接，要自己把需求问出来，再改代码。十一个模型里，领先的两个大约通过 63% 的失败转通过测试，完整做完的任务不到 8%。事先把需求给全，Seed Evolving 和 GPT-6 Astra 的测试通过大约提高 16 个点，整项完成率没有变。Claude Opus 5.5 第一次提问有 93% 问到了该问的负责人，却只拿到 64% 放在同事处的需求；被说成已经做完的需求里，31% 没有通过测试。

测试通过率可以单独抬高，整项交付仍然不动；缺口在需求有没有被跟完。

**链接：** [原文](https://arxiv.org/abs/2611.20218)

### 6. Procedure without Judgment: What Small Language Models Learn under an Exact Verifier

有一个不会出错的验证器时，很容易以为训练会把“怎样才算对”学进去。这篇工作把验证器做成可以算尽的东西：一份可执行的授权策略，每一项决定的最小充分理由都能穷举出来。解释对不对，是对着这个理由打分。学生看不到策略原文，只能改一改请求再问，或者问某一组事实够不够。

只给工具时，前沿模型大约一半次数能找到那个理由。加一句话，让它把答案缩小，Haiku 4.5 从 58% 到 75%。用 2,000 条删除算法的轨迹微调一个 4B 模型，它在训练过的策略上到 92%；同样的数据量下，三个种子里，算法轨迹教出的学生都高于前沿模型轨迹教出的学生，两组没有重叠。换到三份没见过的公开策略，它的答案仍然充分，比例是 94%，但真正最小的只剩 48%；同一句话下，Haiku 在全部 47 次里都给得精确。再用这个精确奖励做强化学习，留出准确率停在原来的位置，做法却倒了过来：从试探策略，变成把预算都花在“这组事实够不够”上。

精确验证器把训练效果变成看得见的，却没有把可迁移的判断教进去。

**链接：** [原文](https://arxiv.org/abs/2611.21529)

### 7. Evaluation-Free Recursive Self-Improvement for Coding Agents

让编码代理改自己的程序时，常见做法是把每个候选放到下游任务上跑一遍，留下分高的那一支。任务一长，多探索一次就多一轮评测；反复对着同一套任务选，也容易把代理改得只适合这套题。

ELITE 不挑选一个孩子接着进化。每一代从同一个父代独立做出几种小改动，再读这些程序，留下互相补得上的机制，去掉重复和冲突，重写成一个后代。循环里不用候选的任务分数，也不用它们的解题轨迹，只用结构和运行是否成立的确定性检查。在作者测的配置下，SWE-bench Pro 从 60.0% 到 85.6%，要做任务评测的 Darwin Gödel Machine 是 86.7%，Huxley-Gödel Machine 是 88.3%；墙钟时间大约缩短到这两个配置的 1/8.8 和 1/3.2。不做进一步适配时，SWE-bench Verified 平均 73.3%，Polyglot 平均 69.3%。论文页面没有给出这项工作自己的代码仓库。

不看任务分也能把多次改动合成改进，但只在作者这套检查和初始代理里，接近要评测才能进化的方法。

**链接：** [原文](https://arxiv.org/abs/2611.21056)

### Trending Open-source Projects

#### 1. LoopForge

编码代理能改仓库，但同一次需求换一次对话，计划、测试和审查就可能换一套做法。团队很难把“这次跑通了”原样再交给下一个人，也很难在中途停下、退回某一步再批。

LoopForge 是腾讯开源的自托管交付台。它把一次交付写成 SOP：节点可以是代理、脚本或人工门，按顺序在各自的 Docker 沙箱里跑。执行器可以换成 CodeBuddy、Codex、Claude Code 等命令行，聊天里的 Main Bot 也会开沙箱并把工作派给角色。做顺的流程可以存成下一次仍带审批的 SOP，需求和聊天、流程记在同一条上。仓库在 2026 年 7 月 28 日创建。本次接口查询有 3,236 星、446 个分叉，11 月 18 日仍在推送。GitHub 日趋势页写着今日 591 星；这个数字来自趋势页，不是接口里的累计星标。

它把一次聊通的交付收成可以重试、回放和人工放行的流程。交出去的代码质量仍取决于接进去的编码代理，沙箱和密钥也要自己管。

**链接：** [GitHub](https://github.com/Tencent/LoopForge)
