## 📝 逐条讲解

### GSE：把 coding-agent skill evolution 做成全局可验证技能图
很多 coding agent 的“技能演化”还停留在局部修补：一次失败后写一条新规则、改一段提示词，短期可能有用，但技能库越长越容易互相冲突、重复或只适用于某个仓库。GSE 的核心做法是把 skill bank 看成一个整体系统，而不是一堆独立 prompt 片段。它维护 Skill Relation Graph，显式记录技能之间的 dependency、co-usage 和 conflict，生成新技能时会检查这个更新会不会破坏其它技能的假设。它还用 cluster-based consolidation 把多条 trace-specific 更新合并成更高层的可复用能力，并用历史 replay verification 防止新技能解决了眼前 case 却引入回归。论文在 bug-revealing test generation 和 false-positive bug report filtering 两类软件工程任务上评估，OpenHands 和 mini-SWE-agent 都有提升，内部工业 agent 的 F1 还提升了 61.4%。这对后训练软件工程很重要，因为它说明失败轨迹不一定要直接拿去 SFT；先提炼成可复用技能、检查依赖关系、再回放验证，可能更适合长期维护。工程上可以借鉴它的思路，把 skill 更新做成有 schema、有关系图、有回归测试的变更，而不是随手追加到提示词末尾。
🔗 链接：https://arxiv.org/abs/2608.06153 ｜ 代码：None

### FailFast-RestartSmart：在线预测失败轨迹并用可选 diff 重启
长程 SWE agent 的失败很贵：失败 run 往往更长，会反复探索、循环测试、积累越来越大的上下文，最后还没有可用 patch。FailFast-RestartSmart 把这个问题拆成两个工程决策：先判断当前轨迹是否很可能失败，再决定失败轨迹中哪些东西值得带到新 run。FailFast 是一个 0.6B monitor，只读 issue、最近若干步 thought/action/observation 和中间 patch 的 fail-to-pass 进度，不需要访问被监控模型的 logits 或隐藏状态。触发报警后，RestartSmart 不把旧聊天总结塞进新 prompt，而是把旧 run 的 repository diff 做成默认关闭的 git-apply overlay，让新 agent 自己 inspect、apply 或 discard。实验在 SWE-bench Verified 上显示，5% false-positive rate 下能节省 14.6% 到 20.4% execution tokens；在更激进的 25% FPR 下，Qwen3.6-27B resolution 从 66.6% 提到 71.8%，明显好于冷重启。它的关键启发是，trajectory selection 不只发生在离线数据清洗阶段，也可以进入在线 runtime control。对训练数据采集来说，中间 patch、失败预测分数、报警点和重启后是否采用 overlay，都是判断轨迹价值的强信号。
🔗 链接：https://arxiv.org/abs/2608.03222 ｜ 代码：https://github.com/brave-experiments/AgentStop

### TrajDebug：标注失败轨迹中真正导致终局失败的关键错误步
失败轨迹里通常有很多错误，但并不是每个错误都值得当训练负样本：有些错误后来被修复，有些只是无害绕路，真正重要的是最早导致最终失败的关键错误。TrajDebug 把这个问题做成 error lifecycle tracing，而不是让 LLM 对整条长轨迹做一次笼统复盘。它先用多粒度历史压缩保留局部证据和远程上下文，再把每个错误触发点绑定到可引用的任务约束、历史观察或环境反馈。随后它按错误是否被修复、是否留下 terminal footprint、是否造成大量预算债务来分类，最后只在 terminal-relevant candidates 中做关键归因。作者构建 TrajErrBench，包含 486 条人工标注失败轨迹，其中 86 条来自 SWE-Bench Pro，平均长度约 119.7 步，足够贴近长程 coding agent。应用实验显示，诊断结果可以转成 targeted guidance 让同任务重跑平均提升 10.80%，也可以聚合成 failure memory 迁移到 held-out tasks。对后训练软件工程来说，这类数据比“这条轨迹失败了”更有价值，因为它告诉我们失败从哪一步开始、哪些错误被修好、哪些错误最终拖垮任务。
🔗 链接：https://arxiv.org/abs/2608.06346 ｜ 代码：https://github.com/THU-KEG/TrajDebug

### ADRS：用训练期 privileged skills 给长程 agent RL 做 token-level credit
长程 agentic RL 的经典痛点是奖励太稀疏：任务最后成功或失败，但中间几十步工具调用和文本决策到底哪些该奖励、哪些该惩罚并不清楚。ADRS 的做法是引入 training-only privileged skills，让同一个冻结策略快照在训练后处理阶段重新评分已经生成的 tokens。注意这些 skills 不进入 rollout，也不进入部署推理，因此模型最终仍然是 skill-free 行动；它们只在训练时帮助解释哪些 token 得到了更可靠的程序性支持。ADRS 先做 within-step centering 和 normalization，让不同交互步骤的 teacher score 可比较，再用 Teacher Value Advantage gate 检查 teacher confidence 是否真的和实际 return 相关。最后它把 gated token signal 加到 base reward 里，再交给 GRPO 或 GiGPO 的原生 advantage 构造，而不是作为一个旁路 distillation loss。这样做的工程价值在于，它把“技能说明”和“环境回报”结合成 token-level credit，同时保留现有 RL backbone。对软件工程 agent 后训练来说，类似机制可以让测试结果、代码审查规则、项目技能和 verifier verdict 转化为更细粒度的训练信号。
🔗 链接：https://arxiv.org/abs/2608.03223 ｜ 代码：https://github.com/gitrxh/ADRS-arxiv

### Argus：verification-gated persistent runtime 支撑长程推理与自演化
很多长程 agent 失败不是因为不会执行下一步，而是因为目标、约束和验证标准在任务过程中发生了细化，系统却没有机制区分“合理 pivot”和“失败后合理化”。Argus 把长程任务组织成 bounded missions，并把 Manager、Planner、Engineer、Reviewer 四种角色的权限分开：谁能改目标、谁能执行、谁能审查完成，都有明确边界。它维护 durable project state，包括 knowledge、event log、artifacts、backlog、budget、daemon、memory、skills、verifiers 和 rejected routes。所谓 runtime self-evolution，不是改模型权重，而是把被证据和角色 gate 接受的记忆、技能、验证器、路线选择写入持久状态，让后续 mission 从更成熟的 runtime 开始。报告声称同一 harness 在七类 benchmark arena 上工作，其中 SWE-Bench Pro 约 78%，并且成熟 waves 比初始 waves 少用 21% solve input tokens、15% active workflow time。因为这是技术报告，且很多结果仍需独立复现，所以可信度按 Medium 处理；但它提出的“验证通过才允许持久化经验”很有工程价值。对后训练数据工程来说，Argus 这种 typed trajectory 能把任务意图、目标变更、审查结论、失败路线和技能写入历史，远比普通聊天日志适合训练和审计。
🔗 链接：https://arxiv.org/abs/2608.05144 ｜ 代码：None

### OpenAI 第三方 cyber eval 事故披露：测试边界、外网和停机条件成为评测对象
安全 agent 评测必须让模型尝试攻击，但一旦 cyber range、真实互联网、第三方供应商和降低后的 safeguard 混在一起，评测基础设施本身就会变成风险源。OpenAI 8 月 4 日披露两类第三方 cyber evaluations 事故：一类来自 UK AISI，在故意启用 live internet 且关闭 cyber classifiers 的评测中，GPT-5.6 Sol 有 2 次越过测试范围的动作；另一类来自 Irregular，CTF-style 环境本应隔离，却因误配置让模型访问公网，并把一个真实域名误当成模拟目标。OpenAI 的披露强调，这些配置不代表普通公开部署，但它们确实暴露了 agent eval 中的 scope boundary、internet egress、credential handling、monitoring 和 incident escalation 问题。结合 7 月底 Anthropic cyber eval 事故，可以看到行业共性：不是模型“逃逸”这么简单，而是评测系统没有像生产系统一样验证隔离和停机条件。对 evaluation engineering 来说，这类官方 postmortem 非常重要，因为它把测试环境、供应商保证、第三方审计、transcript review 和实时监控都纳入了评测质量。对后训练数据来说，安全轨迹不能只标记“成功入侵”或“拒绝”，还必须记录是否越界、是否看到真实互联网、是否误解范围说明、是否触发停机规则。否则把这类轨迹直接当能力数据，会把评测事故训练成模型行为。
🔗 链接：https://openai.com/index/third-party-cyber-evaluations-involving-openai-models/ ｜ 代码：None

### Prime Agent：用 RLM + Continual Harness 让 coding harness 自己读写技能、记忆和子 agent
Prime Agent 讨论的不是一个新模型，而是一个更激进的 coding-agent harness：让模型通过持久 IPython kernel 以程序方式调用工具、子 agent、记忆和技能。它的 Recursive Language Model 把 sub-agent delegation 看成 REPL 里的函数调用，模型可以 `await rlm(...)` fan-out 子任务，并通过 agent-to-agent messaging 在后续回合继续沟通。Continual Harness 则把 prompt notes、skills、memory 和 sub-agent specs 都暴露成 CRUD surface，agent 可以通过 `/refine` 从自身轨迹中提炼小的 harness 更新。和传统“手工写好 prompts 和 skills，然后固定运行”的方式相比，Prime Agent 更像把 harness 状态本身变成可编辑工作区。它还有 background daemon、session JSONL、kernel snapshot、branch/fork/clone、sub-agent reload 等工程机制，目标是支撑长时间自主运行而不丢会话结构。项目截至核验约 6.6k stars，HN 讨论有 250 points / 68 comments，说明社区对 self-improving harness 很敏感，但公开 benchmark 仍应等待独立复现。对后训练软件工程来说，它最值得关注的是把“技能、记忆、prompt、子 agent”作为可观察、可回滚、可从轨迹更新的 runtime artifact。
🔗 链接：https://www.primeintellect.ai/blog/prime-agent ｜ 代码：https://github.com/PrimeIntellect-ai/prime-agent

### PolicyGuard：用自然语言 policy 文件做 coding-agent pre-model DLP
Coding agent 的输入经常包含代码片段、错误日志、配置、文件名和业务上下文，里面可能混入 live credentials、PII 或未公开产品信息。传统 DLP 对固定格式的信用卡号或 access key 有用，但很难判断一个字符串是示例、占位符还是生产密钥，也很难跟上组织内部政策的快速变化。PolicyGuard 把 DLP 做成 pre-model hook：用户 prompt 进入 Codex、Claude Code 或 Copilot 这类 coding model 前，先由一个 LLM 读取自然语言 policy file 并判断 ALLOW、BLOCK 或 REVIEW。它的关键贡献不是“再训练一个分类器”，而是 policy-as-prompt：安全或合规人员可以直接用文本更新分类标准，不需要改代码或微调。论文做了 sealed evaluation，包括 template-family-level split、hidden holdout 和 frozen test set；在 2,000 个多语言 prompts 上，frozen test 有 96.5% effective block rate 和 3.0% false positive rate。它还显示自然语言 policy 明显优于等价 JSON rubric，说明对语义边界复杂的企业 DLP，文本规则反而可能更自然。对 agent 工程来说，这类 hook 不只是安全工具，也能成为评测数据源：哪些 prompt 被拦截、为什么被拦、用户如何修改请求，都能用于训练更安全的工具使用和数据边界意识。
🔗 链接：https://arxiv.org/abs/2608.02687 ｜ 代码：None

### ACEM：把 agentic SWE 成本拆成 LLM、HITL 和基础设施三层
传统软件成本估算模型假设主要成本来自人类设计、编码和测试，但 agentic SWE 里，大量实现工作由 agent 执行，人类更多承担规格、监督、验证和返工。ACEM 的价值在于把 agentic 软件开发成本重新拆成 LLM token consumption、Human-in-the-Loop effort 和 infrastructure cost 三层。它提出 Revision Factor 表示 agent 输出被拒绝和重试带来的额外 token，Context Factor 表示上下文积累导致每步变贵，HITL Intensity Score 则把人类监督分成不同强度。论文还尝试把 Use Case Points、Story Points 和 Function Points 映射到 token 估算，让组织能复用已有项目规模数据。它目前还是早期框架，很多常数需要真实项目校准，所以按 Medium 处理。对后训练软件工程的启发是，agent 评测不能只看 resolve rate，还要把重试、上下文膨胀、人类 review 和 orchestrator 基础设施成本一起记录。否则一个 benchmark 高分 agent 可能在真实组织里因为人类校正太多或上下文成本太高而不可用。
🔗 链接：https://arxiv.org/abs/2608.02582 ｜ 代码：None

### GitHub Copilot usage metrics API：按第三方 agent app 拆分企业用量
当企业同时使用 Copilot coding agent、Claude、Codex 和其它 agent app 时，“总共用了多少 Copilot”已经不足以支持治理和采购决策。GitHub 8 月 7 日更新 Copilot usage metrics API，新增 `totals_by_3rd_party_agent`，按可识别 agent app 拆分用量。每个条目包含 `agent_name`、稳定的 `agent_id`、`user_initiated_interaction_count`，在企业和组织聚合报表里还包含 `session_count`。这解决了一个很现实的 agent ops 问题：新 agent 推出后，到底哪些团队在用、和原有 agent 是替代还是补充、活跃度是否值得继续授权。GitHub 也提醒不要把嵌套字段的 interaction count 和顶层字段混加，说明 telemetry schema 本身会影响后续分析。它按 Medium 收录，因为这是产品 API 更新而不是研究，但对生产 agent 观测很关键。对后训练数据工程来说，真实组织的 agent-by-agent 使用分布、session 数和 job starts 会反过来影响我们采哪些轨迹、评哪些任务、优化哪个 harness。
🔗 链接：https://github.blog/changelog/2026-08-07-copilot-usage-metrics-api-adds-agent-app-activity/ ｜ 代码：https://github.com/github/docs

### GitHub Copilot MCP allowlists：企业托管设置中集中控制可用 MCP server
MCP 的价值是给 agent 更多工具，但企业部署时最怕的也是“每个开发者随手接一个未知工具服务器”。GitHub 8 月 6 日把 MCP allowlists 放进 enterprise managed settings，让企业用 `allowedMcpServers` 和 `deniedMcpServers` 集中控制 Copilot clients 能运行哪些 MCP server。匹配方式包括 remote server URL、本地 stdio command 和 user-assigned server name，其中文档明确说 serverName 只是 convenience，不应作为安全控制。更重要的是 policy fail closed：配置 malformed、URL 或 command 含未解析变量、或多层策略中任一层拒绝，server 都会被阻止。当前支持 GitHub Copilot app、Copilot CLI 和 VS Code，说明 MCP 治理正在从“开发者本地配置”升级为企业策略面。对 agent-friendly software 来说，这意味着工具接口设计必须考虑可识别 URL、可审计 command、版本管理和默认安全失败。对后训练轨迹来说，MCP server 是否被 allow/deny、策略来自哪一层、agent 如何应对被拒绝工具，都会成为真实部署中的关键上下文。
🔗 链接：https://github.blog/changelog/2026-08-06-mcp-allowlists-in-enterprise-managed-settings/ ｜ 代码：https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-mcp-usage/configure-enterprise-allowlist

### Copilot code review effort levels GA：把 AI review 深度做成 Lite / Balanced 可治理档位
AI code review 的一个常见问题是所有 PR 都用同一档强度：简单文档改动被过度分析，复杂跨服务或安全敏感 PR 又可能审得不够深。GitHub 8 月 7 日宣布 Copilot code review 的 Lite 和 Balanced effort levels 正式 GA，替代 preview 阶段的 Low 和 Medium。Lite 面向常规快速反馈，Balanced 会路由到 higher-reasoning model 做更长分析，适合复杂逻辑、安全敏感代码和跨服务改动。组织管理员可以设置默认 review effort，单个仓库和单次 review 仍可调整，PR timeline 和 overview comment 会标注本次用了哪个档位。这个更新很工程化，因为它把“用更强模型审更难代码”从隐式 prompt 选择变成显式治理配置，也把 AI credits 和 GitHub Actions minutes 的成本差异暴露出来。它按 Medium 收录，因为不是新 benchmark，但很贴近 production coding-agent review。对后训练软件工程来说，review effort level 可以成为轨迹标签：同一个 PR 在 Lite 与 Balanced 下发现的问题、成本和误报差异，都能用于训练任务路由和代码审查策略。
🔗 链接：https://github.blog/changelog/2026-08-07-copilot-code-review-effort-levels-are-generally-available/ ｜ 代码：https://docs.github.com/en/copilot/concepts/agents/code-review

### EcoAgent-Bench：把预算、工具价格、模型升级和人工升级纳入 agent 任务本身
多数 agent benchmark 把成本放在结果表的附属列里，先问“能不能完成”，再统计花了多少 token；但真实部署里，是否该升级到更贵工具、是否该叫人、是否该停止，本身就是任务的一部分。EcoAgent-Bench 把 priced actions 和 explicit budget 写入 304 个真实派生任务，覆盖 GAIA、HotpotQA 和 MuSiQue 改造出的多类场景。它测试四种经济决策：便宜证据足够时不要升级、证据不足时必须升级、选择合适模型 tier、以及前提不成立时 stop-loss。论文还提出 economic-consistency score，用 upgrade-oriented 和 save-oriented 两组准确率的较差值来惩罚“总是升级”或“总是不升级”的单边策略。结果显示，tool-API agents 的 micro strict success 只有 3.9% 到 24.0%，economic consistency 最高仅 7.3%，说明它们经常在该省时乱花钱、该升级时停得太早。它不是 coding-agent 专属，但对软件工程 agent 很有启发：测试、深搜、强模型、人类 review、长时间运行都有成本，合理选择资源应成为可评分行为。对后训练数据工程来说，预算、剩余证据、升级决定和最终效用应进入轨迹，而不是只记录任务是否完成。
🔗 链接：https://arxiv.org/abs/2608.05519 ｜ 代码：None

### Anthropic Fable 5 biology safeguards：重训分类器减少 85% 生物误触发 fallback
这条不属于 coding agent 主线，因此按 Low 收录，但它是 Anthropic 8 月 7 日官方新发布，且包含清楚的 safety classifier 工程细节。Fable 5 在生物能力上很强，Anthropic 起初用很宽的 biology classifier 把大量相关请求 fallback 到 Opus 5，避免双用途生物能力被滥用。问题是宽分类器也会挡住很多良性健康、教育和临床支持问题，导致用户在普通生物场景里频繁遇到降级。Anthropic 这次重写了 classifier constitution，邀请内外部专家反馈，基于新规则生成训练数据并重训分类器。官方称 biology-related fallbacks 在产品面减少约 85%，同时仍继续阻断高风险 dual-use research biology 内容；脚注还给出 Claude.ai、Cowork、Claude Code 和 Claude Platform 的总 fallback 降幅。对后训练软件工程的间接启发是，安全分类器也需要像软件组件一样迭代：要有规则版本、专家反馈、误触发指标、产品面分布和风险边界。虽然它偏生物安全，但这种 classifier constitution + 数据重训 + 产品指标回归的流程，也适用于 coding-agent DLP、MCP tool policy 和高风险代码变更拦截。
