## 逐条讲解

### LASER：OpenAI 用"廉价分类器选样 + 推理模型打标"的循环快速造安全评测集
做安全评测最难的不是常规样本，而是那些落在政策边界上、模棱两可、出现频率又很低的对话。以前每出现一个新的安全关注点，OpenAI 都要研究员、工程师和政策专家多轮手工筛选，才能凑出一套合格的评测集，往往要迭代好几轮。LASER（Logistic Augmented Sampling over Embeddings, Recursively）把这件事做成了一个自动循环：先根据政策文档生成合成对话，用它们去召回相似的去标识化对话，再混入一批随机对话作为初始样本；然后用贵的推理模型给样本打"是否违规"的标签，用这些标签在对话 embedding 上拟合一个便宜的 logistic 回归，再让这个回归模型去挑预测概率接近 50% 的对话（也就是决策边界附近、信息量最大的样本），交给推理模型继续打标，如此反复。为了避免挑出来的样本都长得一样，它还加了基于 embedding 的贪心多样性采样；工程上还有两个技巧：把近似 logistic 推理直接写进数据库查询，以及利用 prefix caching 压低大规模打标的成本。结果是一套评测集几个小时就能做出来，找到同样数量的违规样例所需的打分算力比随机抽样少约 1 万倍，而且全程不接触原始用户数据。对后训练数据工程来说，这套"便宜模型定位、贵模型标注、边界主动采样、强制多样性"的方法，可以直接套用到 coding 评测和难例挖掘上，比如从海量 agent 轨迹里专门捞出 verifier 判断最没把握的那部分。
🔗 链接：https://alignment.openai.com/laser/ ｜ 代码：None

### WorkForge：从真实文件出发，让每个任务的验收标准都能追溯到 workspace 里的证据
训练"办公类 agent"（处理表格、报告、合同等专业文件的 agent）需要大量长程、可验证的环境。手工搭环境成本太高，没法规模化；纯合成又往往牺牲了真实感，或者验收只能靠 LLM 主观打分。WorkForge 的思路是从真实世界的资源倒推：先从专家工作流里梳理出这个工作需要哪些资料、要做哪些决策、最终交付什么；再去检索相关的真实文件，组装成一个 workspace；接着检查 workspace，抽取出一批具体、可核对的事实，作者称之为"事实锚点"（比如某张表里某个数字、某份合同里某个条款）。这些锚点决定了这个 workspace 能出哪些类型的任务、结果怎么验证，任务说明、参考解法、程序化 verifier 和语义 verifier 都直接从锚点派生出来，所以每一条判分都能追溯到 workspace 中看得见的证据，而不是凭空编的。最终他们造了 16.7K 个可验证环境，覆盖 40 个专业领域、60 种文件类型；用它后训练 Qwen3.5-35B-A3B-Base，GDPVal 从 45.5 升到 73.6，APEX 从 5.0 升到 21.3，并且在数据量和交互长度两个维度上都观察到稳定的 scaling。它的启发是：造环境时先抽取"可验证事实"，再围绕事实出题，能从源头上避免"题目出得出来、但判不准"的问题，这个做法对 coding 环境（先抽取仓库里可执行的不变量，再出题）同样适用。
🔗 链接：https://arxiv.org/abs/2610.04906 ｜ 代码：None

### VERA：环境、模型和 harness 一起进化，每一步改动都要过验收
长程任务（比如医学研究里要经过几十步：定位发现、分类、写报告）的训练环境很少，而且大多只看最终结果打分，中间过程完全不管，导致训练不稳定。VERA 做了两件事。第一是规模化造环境：以已有的初始轨迹为起点，由 agent 写出 rubric（评分细则）和可执行检查，再由一个 judge 逐个验证每个沙箱是否靠谱，只有通过的环境才进入训练库，而且沙箱可以从任意阶段恢复。第二是"协同进化"：在这些环境上交替做两类更新，一类是用 rubric 奖励训练模型参数，另一类是修改 harness 里的 skill（即给 agent 的操作说明和脚本）；每次更新之前，另有一个 verifier 按开发集上事先写明的验收标准决定这次改动是否保留，这样能分清提升到底来自模型还是来自 harness。他们开源了 9,000 多个长程可验证环境；9B 模型配上协同进化后的 agent，在两个领域分别比最强基线高 10.3 和 13.0 个点，27B 模型在 AutoCoWorkBench 和 AutoMedBench 上分别达到 71.6 和 80.7，还能迁移到没见过的工作流，通用能力也没有退化。值得借鉴的是"环境入库前先过 judge、模型和 harness 的改动都要过验收门"的工程纪律，这正是现在很多团队把 harness 优化和 RL 混在一起时缺少的归因手段。
🔗 链接：https://arxiv.org/abs/2610.05923 ｜ 代码：None（论文称环境语料开源）

### SWE-CC：功能正确的 patch，在真实仓库里未必能合并
SWE-bench 一类基准只用单元测试判定 patch 是否正确，但成熟的开源项目都有自己的贡献规范：代码风格、git 提交规范、必须跑哪些测试、哪些文件不能动等等。一个能通过测试却无视这些规范的 PR，维护者通常也不会合并。SWE-CC 用一条半自动管线，把 12 个开源仓库的开发者文档转成了 823 条可以机器检查的"原子规则"，每条规则都对应一个轻量、确定性的检查函数；审计不只看最终交付的 patch，也看 agent 运行过程中的行为（比如有没有按规范先跑 lint、有没有直接改受保护文件）。他们在 SWE-bench Verified 基础上扩展出 500 个端到端贡献任务，评测了 4 个模型和 2 种 agent 脚手架：即使 patch 功能正确，agent 仍然违反了 43.1% 的适用规则，而且接近一半的违规发生在中间执行步骤，只看最终 diff 是发现不了的。对评测和后训练来说，这提供了一种新的奖励维度："过程合规"可以做成确定性检查，作为 RL 奖励的一部分或 rollout 过滤条件，补上"测试全过但不可合并"这块缺口。
🔗 链接：https://arxiv.org/abs/2610.06193 ｜ 代码：https://github.com/dangtruong01/swe-cc-arxiv

### Teaching Agents to Code Reliably：把"搜得广、改得多样、验得准"训进策略里
给 coding agent 多花推理算力（多采样几次、多试几种方案）只有在两件事同时成立时才有用：确实能生成有用的修复，并且有可靠的证据从中挑出对的那个。作者发现三个关键问题：一是定位缺乏多样性，多次尝试总是回到同一个代码位置，多采样并没有增加覆盖；二是编辑方式的多样性没被利用，不同方法论能解决的 issue 其实互补；三是验证会误导，agent 给自己 patch 写的测试会放过大量错误 patch。他们先在推理时改进：用执行反馈引导搜索，并把每个 patch 放到"回滚了该 patch 的代码树"上对比打分（即看这个测试在修复前后是否真的有区别），只用 8 次采样基线 48.1% 的步数就解决了 SWE-bench Verified 的 52.8%。然后再把这些行为训进模型：在 SFT/RL 训练没见过的 270 个 issue 上，加权 SFT 把 pass@1 从 31.9% 提到 35.2%；接着用 RL 训练 verifier，让它区分标准修复和错误变体，并对真正能识别错误的断言给奖励，pass@1 进一步到 43.0%、pass@8 到 60.7%，verifier 精度从 26.8% 升到 41.7%，误接受率减半以上，并且在 7B、14B、30B 上都成立。对后训练来说，"verifier 本身也可以用正确/错误 patch 配对来训练"是一条很实用的路线，可以直接缓解 agent 自写测试太宽松的问题。
🔗 链接：https://arxiv.org/abs/2610.03984 ｜ 代码：None

### What Does a Harness Buy?：换 harness 主要改变的是账单，而不是分数
现在各家 coding agent 的 harness（系统提示、工具集、上下文管理）几乎每天都在发版，厂商经常宣传"改了 harness 提升了几个点"，排行榜也把不同 harness 混在一起比。但很少有人测过：模型固定时，harness 本身到底能让分数动多少，同一配置重跑一次又会动多少。作者用 Claude Code、mini-SWE-agent、OpenCode 三个生产级 harness 配 5 个模型跑 SWE-bench Verified，并且同一配置重复跑来测"什么都不改时的波动"。在 447 题上，最重的 Claude Code 和最轻的 mini-SWE-agent 差距在 5 个点以内；在 45 题难题子集上，换 harness 翻转的题数和同一 harness 重跑翻转的题数一样，都是 13%，而且这次赢的题下次未必赢。唯一超出噪声的 harness 效应是负面的：OpenCode 最多落后 9 个点，其中一个模型有一半差距来自输出长度上限把运行截断了。真正被 harness 决定的是成本：同模型同任务同价格表，每题成本最多差 3 倍，差距主要来自每一步都要重复发送的系统提示和工具 schema 前缀，再乘以步数。论文还给出了功效分析：45 题只有一半概率测出 13 个点的差距，447 题也只能分辨 5 个点。对评测工程而言，这是很实用的提醒：宣称 harness 改进前，先测重跑方差、按功效算样本量；做 harness 优化时，先盯每步的固定前缀开销。
🔗 链接：https://arxiv.org/abs/2610.04433 ｜ 代码：https://github.com/YangzeLiu/what-does-a-harness-buy

### HarnessTester：agent harness 本身也是软件，而且测得很浅
agent 由底层模型和外层 harness 组成，harness 负责解析模型输出、调度工具、管理状态，是 agent 的"操作系统"。harness 越来越复杂，bug 也越来越多，但它本身测试得怎么样，之前没人系统研究过。这篇论文对真实 agent 系统做了第一个测试充分性实证研究：harness 整体测试不足，尤其是"依赖 LLM 输出的那部分代码"（比如解析工具调用、处理格式异常、决定下一步走向的逻辑），现有测试覆盖的行和分支不到一半，因为这些代码需要构造各种模型输出才能触发，常规单测很难写。作者据此提出 HarnessTester：先显式建模 agent 与 harness 之间的契约（模型应该输出什么格式、harness 应该如何响应），再按契约构造忠实的测试场景，大量覆盖这部分代码。与最先进的通用测试生成方法相比，它的行覆盖增益高 75.95%、分支覆盖增益高 84.76%、变异分数增益高 69.89%；还在 OpenClaw 等常用 agent 系统里找到 122 个真实 bug，其中 88 个此前未知，69 个已被开发者确认。对做 RL 的团队来说，harness bug 会直接污染 rollout 和奖励，这类"按契约生成 harness 测试"的方法值得纳入训练基础设施的 CI。
🔗 链接：https://arxiv.org/abs/2610.04921 ｜ 代码：None

### Measurement-First Auditing：说一个 agent 排行榜被"污染"之前，先拿出对应证据
agent 排行榜通常用公开基准，题目和含答案的材料长期挂在网上，于是"某模型分数虚高是因为见过题"的说法很多，但证据通常不足。这篇论文提出一个"先测量、后下结论"的审计框架，把污染拆成三个需要不同证据的通道：训练时见过（训练暴露）、评测时检索到了答案（评测时检索），以及评测管线或脚手架本身泄漏了答案；每个通道按开放、部分、关闭、未知编码，并采用 fail-closed 规则（证据不足就不能判为"已关闭"）。在 Holistic Agent Leaderboard 的 9 个配置上，27 个通道评估没有一个能判为关闭，其中 4 个配置确认出现过泄漏事件。他们又用同仓库配对对照的方法检验一个被广泛引用的结论"SWE-bench Verified 上存在文件定位差距"：GPT-4.1 表面上有 10 个点的差距，但两种置信区间都包含 0，结论不成立；更关键的是，用来复现的自动 scorer 没有通过与人工标注对比的验证关，DeepSeek-V4-Flash 的两次报警都是误报。对评测工程的启发是：污染审计本身也需要实验设计，包括对照组、对称的泄漏筛查，以及"先验证 scorer 再使用"。
🔗 链接：https://arxiv.org/abs/2610.05830 ｜ 代码：None

### SkillScriptBench：agent skill 包里的脚本坏了，agent 能修好又不改坏别的吗
Agent Skill 现在不只是一份 Markdown 说明，很多还带着可执行脚本，合在一起成为可复用的"技能包"。让 agent 自己维护、修订这些技能包（self-evolution）时，需要同时做到三件事：修好说明文档、修好脚本，并且不破坏原本正确的行为。已有基准没有把这三种能力分开考。SkillScriptBench 先普查了 GitHub 上 3.5 万多个 skill，挑出 100 个包构造 150 个修复任务：往包里注入脚本错误，配上一条维护需求和可执行的行为检查；另有一个对照赛道，用 50 个包各在四种状态（干净、文档有错、脚本有错、两者都有错）下接受同一条维护需求，共 200 个任务。结果发现，同时改文档和脚本的方法能修好脚本错误，但在文档修复和保持原有行为上并不比只改 Markdown 更好。作者因此提出 AST 引导的修订：用抽象语法树和调用关系把维护需求定位到相关代码位置，只允许在这些位置改脚本，再同步更新文档；修复成功率平均提高 21.9 和 27.7 个点，三次运行都成功的比例提高 20.8 和 31.5 个点。随着 skill 成为 harness 的标准组件，"skill 维护"本身会成为一类重要的评测和训练任务，这个基准提供了很好的出题模板。
🔗 链接：https://arxiv.org/abs/2610.04008 ｜ 代码：None

### Verification Trap：生成器和 verifier 被同一个错误前提"带偏"时，多采样反而选错
测试时扩展（test-time compute）在代码生成里的标准做法是：采样很多候选程序，再用 verifier 能看到的证据（比如 verifier 自己写的测试）挑一个。这套做法默认 verifier 提供的是独立于生成器的纠错信号。论文指出，当任务描述里带有误导性前提时，这个假设会失效：生成器按错误前提写出"走捷径"的代码，verifier 写的测试也继承了同样的盲点，于是两者通过同一个错误认知耦合在一起，选择器会挑出一个隐藏测试会失败的候选，哪怕候选池里其实存在正确答案。作者称之为"验证陷阱"。在 3 个代码生成基准和 5 个代码模型上，错误前提一致地降低了首个样本的正确率，也降低了 64 次采样后选出答案的正确率，并放大了"本可选对却选错"的情况；好消息是，这种失效在运行隐藏测试之前就能预测，只用 verifier 可见特征的轻量预测器 AUROC 达到 0.846。缓解方向是让证据"解耦"：单纯加大同类采样作用有限，而专门针对前提做鲁棒性审计的检查器能找回大量本可获得的提升。这提醒做 best-of-N 和 RL 奖励的团队：verifier 和 policy 共享同一份任务描述时，要有一部分检查不依赖任务描述中的假设。
🔗 链接：https://arxiv.org/abs/2610.05170 ｜ 代码：None

### Selecting Long-Horizon Trajectories：terminal agent 的 SFT 数据，监督多长比全部都训更重要
训练 terminal agent 的常见做法是模仿教师模型的长轨迹，但每条轨迹到底保留多少 token 来做监督，此前没人仔细研究过。作者把这个量称为"监督长度"（supervision horizon），发现它是影响可靠性和成本的关键设计轴：效果随长度增加而提升但会饱和，在 Terminal-Bench 上，12K token 的监督长度比 16K 解出更多任务（29 对 26），训练时间还少 30%。长度还会塑造行为：太短会让 agent 过早结束，中等长度带来有效的错误恢复，太长则让 agent 过度坚持、不肯收手。作者用偏差-复杂度界解释了饱和：更长的监督减少了时间维度上的偏差，但轨迹后段的历史千差万别，有限样本下估计误差会变大。据此提出"选择性长程精修"：先在短前缀上训练，再只在热启动模型认为最可能的那部分续写上精修。16K 设置下成功尝试数从 110 升到 126，8 次中至少 6 次成功的任务从 9 个升到 14 个；只用一半长程数据也能到 122，同时省 23% 训练时间，并且在 Terminal-Bench v2.0 和 OpenThoughts-TBLite 上同样有效。结论很直接：对长程轨迹做 SFT，挑选比堆量更重要，"截断长度"应该当作超参数来调。
🔗 链接：https://arxiv.org/abs/2610.05831 ｜ 代码：None

### ThunderSyncRL：不引入策略过时，也能把 agentic RL 的流水线空泡挤掉
agentic RL 的轨迹又长又不均匀，同步训练系统里，训练引擎要等所有 rollout 和验证都跑完才能开始算梯度，大量时间是空等。异步训练让 rollout 和学习跨步重叠，能消除空等，但代价是策略过时（policy staleness，用旧策略采的数据去更新新策略），可能影响效果。ThunderSyncRL 换了个思路：不跨步重叠，而是"某个梯度需要的输入一旦确定就立刻开始算"。对 GRPO，每条轨迹的奖励一到就计算它的梯度项，不必等同组其他轨迹；对在线策略蒸馏（OPD），每完成一个 agent 回合、教师打完分，就在沙箱执行工具调用的同时计算这一回合的梯度。作者证明这种梯度流式计算得到的更新与批量同步训练完全一致，不改变优化目标。在 SWE-bench Verified 和 Terminal Bench 4.0 上，达到同样性能最多快 1.9 倍；在固定预算下，由于没有策略过时，效果还比异步训练高最多 2.47 个点。对做 RL 基础设施的团队来说，这是"同步语义 + 细粒度流水线"的一个可落地方案，不需要在吞吐和正确性之间二选一。
🔗 链接：https://arxiv.org/abs/2610.05935 ｜ 代码：None

### TrajLong：把 agent 轨迹"编译"成长上下文训练任务用于 mid-training
coding、搜索、办公类 agent 都高度依赖长上下文能力，要在很长的交互历史里找证据、整合信息、跟踪状态。最近有工作把 agent 轨迹直接加进 mid-training（预训练和后训练之间的继续训练阶段），因为轨迹天然又长又富含交互，但"怎么把轨迹里的信息组织成有效的监督信号"还没人好好研究。TrajLong 分析了长上下文能力和 agent 基础能力的关系，挑出三种代表性的原子能力：证据定位（在历史中找到相关证据）、跨证据聚合（把多处信息合起来推理）和时序状态维护（记住环境状态随时间如何变化），然后把轨迹编译成针对这三种能力、带密集监督的长上下文任务。他们用这些数据 mid-train Qwen3-14B-Base 和 Qwen3-30B-A3B-Base，再做 SFT，在 6 个长上下文基准和 12 个 agent 基准上都有提升，对照实验显示优于直接用原始轨迹或掩码轨迹训练。对数据工程的启发是：同一批 agent 轨迹，除了做 SFT，还可以按能力维度改写成"考题"，在更早的训练阶段复用。
🔗 链接：https://arxiv.org/abs/2610.04973 ｜ 代码：None

### What Will Post-Training Fix?：哪些题会被 RL 提升，很大程度由基座模型决定，可以用旧 checkpoint 预测
数据筛选、课程学习和后训练配方评估都隐含一个假设：训练前就能判断模型会在哪些题上进步。作者直接检验了这个假设：在 DeepSeek-R1-Distill-Qwen-1.5B 和 Qwen2.5-Math-1.5B 两个基座上跑了 18 次后训练，在最多 1,532 道竞赛数学题上逐题、多样本评估。结果有三点在两个基座上都成立：第一，"能被修好的题"在独立运行间高度一致，噪声上限约 0.9，但两个基座之间的一致性只有 0.25，说明这是基座模型的属性而不是题目的属性；第二，训练前能拿到的信号（基座通过率、正确解的似然、更大模型的通过率及其组合）只能解释可解释方差的 0.30 和 0.24；第三，已有的 checkpoint 预测得更好，哪怕是另一个模型家族的一个 checkpoint 的逐题增益，预测新一次运行的效果也胜过所有先验信号（0.52 对 0.33、0.34 对 0.17）。作者建议把"噪声上限"作为逐题信号的标准配套指标。实验虽然是在数学上做的，但对 coding RL 的选题同样有启发：与其只按基座通过率挑"难度适中"的题，不如利用已有的训练记录来预测哪些题值得放进训练集。
🔗 链接：https://arxiv.org/abs/2610.04978 ｜ 代码：None

### ImproveAnyTask：把"分析错误→选方法→造数据→训练→评估"自动化的后训练 harness
把通用大模型适配到具体任务，通常需要人花大量精力设计数据和训练策略；而且模型每更新一次，错误分布就会变，策略也得跟着重新调。ImproveAnyTask 把这个过程做成一个自主的后训练 harness，并借鉴梯度下降的思路组织成三步：错误归因（相当于算"梯度"）、选择更新方向、执行模型更新。具体来说，它结合整体指标和逐条案例分析，先找出当前最主要的问题；再检索有研究支持的改进策略，比较它们报告的收益和复现难度；把选中的策略转成训练数据和训练配置，先跑小规模执行检查，没问题再做完整后训练；评估结果用于选模型和决定下一轮方向，验证有效的策略和脚本保存下来供以后复用。在 11 个任务上，8 张 H20 等价资源、24 小时预算内，Base 模型和 Instruct 模型平均提升 18.29 和 11.97 个点，最高提升 41.96 个点。值得关注的是它的工程结构："小规模试跑再全量"的门控和"策略/脚本沉淀复用"，正是把后训练流程交给 agent 时最需要的两道保险。
🔗 链接：https://arxiv.org/abs/2610.06347 ｜ 代码：None

### Advancing computer use with Ironclad：OpenAI 与软件厂商合作，为专业工作流建训练环境
computer-use agent 在通用网页任务上进步很快，但在专业软件里的复杂业务流程上仍然薄弱，原因之一是训练方拿不到这些软件的真实环境，也不知道什么样的结果才算"做对"。OpenAI 10 月 6 日宣布与合同管理软件公司 Ironclad 合作：Ironclad 的员工和 OpenAI 用户一起定义了 11 个法务、商务和采购类任务（例如配置合同、设置审批流程、维护可复用的法律条款），每个任务按复杂度用 8 到 50 条标准评分，从而能看出模型具体哪部分做对了、哪部分没做好；Ironclad 提供产品的托管环境供模型练习，OpenAI 研究员围绕代表性工作流构造合成训练任务，用强化学习让模型在练习和反馈中提升。在这套研究评测上，GPT-6 Astra 平均得分 55.0%，GPT-5.6 Sol 为 41.6%，每次尝试的估计耗时从 37.0 分钟降到 19.2 分钟，一个内部开发中的模型达到 63.7%；OpenAI 还在邀请其他软件厂商贡献类似任务和安全的测试环境。这是"领域专家定标准 + 厂商托管环境 + 合成任务 RL"的一种环境供给模式，对想要获得真实工作流 RL 环境的团队很有参考意义。

### Sharing AI progress in mathematics：OpenAI 公开内部模型的 722 篇数学手稿
OpenAI 9 月曾表示其内部前沿模型"解决了 100 多个长期悬而未决的数学问题"，但一直没有公布具体结果。10 月 6 日，他们在 GitHub 仓库 openai/math 中发布了 722 篇手稿，归为 372 个结果族（每个族包含一个主要结果及其配套论证、推论或其他证明），来自一次涵盖约 4,000 道问题的评测。仓库还附带证明材料、部分结果的 Lean 形式化（可由计算机检查的证明，并非全部都有）、10 份删节版的模型推理摘要、按 ChatGPT Pro 用量折算的算力估计（平均每个结果约相当于 3 小时 Pro 思考），以及论文修订和引用的规范。发布方式参考了普林斯顿高等研究院（IAS）数学与 AI 独立顾问组的建议。从评测角度看，值得注意的是 README 里的说法：在现有数学评测饱和之后，他们把评测扩展到开放研究问题，"用开放问题做评测"正在成为前沿模型的新评测形态。

### 3SUM / APSP 假设被推翻：核心算法由 Claude 在无人干预的单次会话中发现
3SUM（给定 n 个整数，判断是否有三个数之和为 0）和全源最短路（APSP）的"无法实质加速"假设，是细粒度复杂度理论的两块基石，过去十多年大量条件下界都建立在它们之上。10 月 5 日，Josh Alman（哥伦比亚大学）和 Virginia Vassilevska Williams（MIT）在 arXiv 发表论文，给出 O(n^1.9992) 的确定性 3SUM 算法和 O(n^2.9995) 的 APSP 算法，首次在多项式意义上超越教科书算法，从而推翻 3SUM、APSP、Exact Triangle 和 Zero-Weight k-Clique 等假设。论文的"致谢与方法"部分说明：一名 Anthropic 员工用内部研究模型检查基于 Zero-k-Clique 平均情况困难性的密码学构造，Claude 的任务本来是验证并改进这些构造，结果却先在平均情况、后在最坏情况下打破了底层假设，整个会话输出约 1,600 万 token、没有人工输入；两位作者随后对算法做了理解、简化、加强和扩展，Anthropic 用 Lean 4 对主要定理做了形式化验证。这一条属于低优先级的"高影响力事件"：它说明长时间自主运行加形式化验证的组合，已经能在一个与原任务无关的方向上产出可验证的研究成果，相应的长程 agent harness 和验证链路值得持续关注。

### Expanding the Cyber Verification Program：Anthropic 网络安全能力分三档开放
网络安全能力是典型的双刃剑：帮防守方找漏洞、修漏洞的能力，同样能帮攻击者利用漏洞。因此 Anthropic 对普通可用的模型（Opus 5.5、Fable 5.1、Sonnet 5.5）设置了保守的网络安全拦截，大多数网络安全工作会被拦下。过去半年，它通过 Project Glasswing（让保障关键软件的组织使用 Claude Mythos）和 CVP（让经过审核的安全团队使用降低拦截的 Opus/Sonnet）两个项目提供可信访问。10 月 6 日两者合并为扩展版 CVP，分三档：Defense Access 面向防御工作（安全运营、应急响应、恶意软件逆向、漏洞分析），预计几天内审核完；Red Team Access 增加授权渗透测试和红队，但部署勒索软件、破坏物理系统等行为仍会被实时拦截；Specialized Access 拦截最少，只给经过深度审核、有权测试航空、电网、电信、银行间转账等关键系统的组织，审核与美国政府合作进行。加入项目的组织必须保留数据以便监控滥用，等今年秋天 Enterprise Frontier Safeguards 上线后可以把数据存在自己控制的云上。对做 coding agent 安全评测的人来说，这套"按用途分档放开能力"的做法，是模型能力准入工程化的一个具体样本。

- **rauchg/gdp-ts（约 0.7k stars，10-04 创建，Vercel CEO Guillermo Rauch）**：把 "Ghosts of Departed Proofs"（用类型系统携带"已经检查过"的证明）落地到 TypeScript 的库 + linter + agent skill。它要解决的是很常见的权限 bug：代码里先 `assertProjectAdmin(userId, projectId)`，下一行再操作 `projectId`，但两行之间没有任何机制把"检查过"和"被操作的对象"绑在一起，人和 coding agent 都很容易漏检或查错对象。gdp-ts 让权限检查返回一个带"证明"的 id 类型，敏感操作只接受这种类型，因此漏检在类型检查阶段就会报错，运行时几乎零开销，每个调用点冷启动类型检查约 0.3ms。它火的原因是给出了一个很实际的答案：与其指望 agent 每次都记得写权限检查，不如把规则编码进类型系统，让编译器当 verifier；这种思路也可以直接用来给 coding 环境构造确定性的安全判据。
  🔗 https://github.com/rauchg/gdp-ts
- **AgentMemoryRepo/agentmemoryrepo（约 0.57k stars，10-04 创建，Cognition 发布的规范）**：Cognition（Devin 背后的公司）提出的 "Agent Memory Repo" 规范：agent 在会话中把从用户那里学到的偏好和知识实时写进一个独立的 git 仓库，条目之间互相链接，像 wiki 一样导航，新会话可以直接读取；支持通过 Devin CLI 或 `npx skills add` 装进 Claude Code、Cursor 等工具。同期 Devin 也上线了每天自动整理一次记忆的功能。它受关注是因为跨会话记忆一直是各家 agent 各做各的私有格式，用 git 仓库做载体，天然获得版本历史、diff、审查和跨工具共享能力；对 harness 工程来说，"记忆即代码仓库"是一个容易审计、也便于回滚的设计。
  🔗 https://github.com/AgentMemoryRepo/agentmemoryrepo 、https://cognition.com/agent-memory-repo
- **elstongun/leviathan（约 0.64k stars，10-05 创建）**：一个 Rust 单二进制工具，把 JSONL、CSV、SQLite 或任意数据库 CLI 的输出一次性建成排序全文索引，agent 用自然语言提问，拿回的是简短、带出处的结果卡片。作者的基准显示：在 100 万条记录（678MB）上，每个问题的中位 token 消耗约 436，而最好的 grep 策略约 10.7 万、按实体翻历史约 20.9 万。它火是因为抓住了一个真实痛点：agent 面对大日志或大数据表时，习惯用 grep 把大段原始内容塞进上下文，既贵又容易漏；把"检索"做成工具层的确定性能力，是控制上下文成本的典型 harness 设计，也可以用来在海量 rollout 日志上做轨迹分析。
  🔗 https://github.com/elstongun/leviathan
