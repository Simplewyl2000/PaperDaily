## 📝 逐条讲解

### Alberta 50-agent Claude Code 安全扫描：把政府遗留系统审计做成并行 agent 工厂
很多政府和大型企业的代码库不是没有安全工具，而是遗留应用太多、文档不全、技术债太重，传统扫描器只能发现一部分已知模式。Anthropic 披露的 Alberta 案例把这个问题做成了一个大规模 agent 安全审计流程：约 50 个 Claude Code agent 并行工作，在 20 小时内扫描 466 million lines of code，覆盖 1,280 个应用和 3,400 个代码仓库。流程不是让模型随便读代码后写报告，而是先用 rules engine 标出已知风险，再让 Claude Code 复核这些 flag，并引用具体文件和行号，方便工程师验证。对发现的漏洞，Claude Code 还能生成补丁、写缺失测试、构建和测试；对过旧或过复杂的系统，则辅助重建为更现代、可维护的实现。Alberta 还把流程扩展成持续安全 review：red-team agent 从外部攻击角度探测，blue-team agent 按约 95 个安全控制项评估防御并生成修复计划。它值得关注，因为这是 coding agent 从“帮个人修 bug”走向“政府级遗留系统治理”的少数公开案例。对后训练软件工程来说，真正高价值的数据不是最终漏洞列表，而是 rules flag、agent 复核证据、line-level citation、测试补写、人工审批和持续控制项结果这些完整轨迹。

### Claude Code loops 官方指南：把 /goal、/loop、/schedule 变成可选工程原语
最近社区频繁讨论“loop engineering”，但如果没有统一语言，loop 很容易变成“让 agent 一直跑”的危险口号。Claude Code 团队的官方指南把 loop 拆成四类：turn-based loop、goal-based loop、time-based loop 和 proactive loop，并且每类都说明触发方式、停止条件和适用任务。最关键的工程点是停止条件：`/goal` 适合有明确可验证完成状态的任务，比如 Lighthouse 分数达到 90；`/loop` 和 `/schedule` 适合重复检查外部系统，比如 PR review、CI 失败或定期摘要。文章还强调用 SKILL.md 编码验证流程，例如前端改动必须启动 dev server、打开页面、点击控件、检查 console、跑 Chrome DevTools MCP，而不是只看编辑成功。这样 loop 不只是提示词重复，而是把“做一次、测一次、根据证据再做一次”的工程闭环固定下来。它对后训练软件工程非常直接：loop 的触发、停止、验证证据、失败重试和 token 使用都应该成为轨迹 schema。未来筛选高质量 agent 轨迹时，能清楚退出且有定量验证的 loop，比开放式“继续改进”更值得训练。
🔗 链接：https://claude.com/blog/getting-started-with-loops ｜ 代码：None

### Benchmarking the Benchmarks：审计 BFCL、tau2、LiveMCPBench、MCP-Atlas 的评测可靠性
工具调用和 MCP benchmark 正在被用来排名 agent，但很多团队默认 evaluator 本身就是可靠的，这篇论文专门审计这个假设。作者抽查 BFCL v4、tau2-Bench、LiveMCPBench 和 MCP-Atlas 等四类主流评测，在 496 个专家复核任务中发现 92 个 evaluator-human disagreement，错配率达到 18.5%。问题不是简单标注错误，而是系统性工程缺陷：状态匹配太脆、轨迹被锁死、ground truth 错误、substring 通信失败、reward basis 和真实任务目标不一致。LLM judge 侧也有典型问题，比如 rubric drift、幻觉式判定完成、只看最终答案不看工具执行，以及 run-to-run variance 很大。LiveMCPBench 的一个同设定重复实验分数从 57.9% 到 76.8%，18.9 个百分点的波动足以改变 leaderboard 结论。论文提出 failure taxonomy，并计划释放 trace-level audit artifacts、修正组件、Tool-Veritas 配置和 Harness Lab。它对 evaluation anti-cheating 的启发很明确：评测不能只给一个最终成功率，必须拆开工具调用正确性、任务完成、状态验证和 outcome verification，否则 agent 可能是在优化 evaluator artifact。
🔗 链接：https://arxiv.org/abs/2607.02577 ｜ 代码：None

### A Few Teacher Steps Go a Long Way：用少量 on-policy teacher continuation 做 agent SFT 增强
Agent 后训练常见做法是收集完整专家轨迹做 behavior cloning，但完整轨迹很贵，而且学生模型真正会出错的位置不一定和专家轨迹分布重合。这篇论文把数据构造改成 budget allocation 问题：先用已有 BC 数据训练一个初始学生，再让学生自己 rollout，抽取学生诱导出来的中间状态，然后请 teacher 从这些状态继续走几步。核心方法 OP-Short 不追求 teacher 完整解决任务，而是保留短 horizon continuation，让训练预算覆盖更多学生真实会遇到的状态。直观地说，它像是在学生摔倒的位置给几步示范，而不是只让学生看老师从起点到终点的完美录像。论文在 HotpotQA、ALFWorld 和 Terminal-Bench-Dev 上实验，结论是少量 on-policy teacher continuations 在相同监督预算下通常比继续扩充完整 BC 更划算。在 Terminal-Bench-Dev 上，OP-Short 用 10% BC corpus 加少量 continuation、没有 RL，就能匹配使用完整 15,209 条 BC 轨迹再做 720 个 GRPO 任务的 OpenThoughts-Agent baseline。对 Code LLM 后训练数据工程来说，这很重要：真正稀缺的是 learner-induced failure context，而不是又一条 teacher 从零开始的长演示。
🔗 链接：https://arxiv.org/abs/2607.04574 ｜ 代码：None

### Vercel Eve：filesystem-first durable agent framework，把生产 runtime 变成目录结构
很多 agent 框架把 demo 做得很快，但真正上线时才发现还缺持久会话、sandbox、model routing、外部连接、观测和多渠道入口。Vercel Eve 的切入点是 filesystem-first：一个 agent 就是 `agent/` 目录，里面按约定放 `instructions.md`、`tools/`、`skills/`、`channels/` 和 `schedules/`。这种设计的好处是 agent 能力像 Web 应用路由或组件一样可检查、可版本化、可由 coding agent 直接编辑。更重要的是，Eve 把生产 runtime 接到 Vercel 现有基础设施：Workflows 负责持久会话和 checkpoint，Sandbox 负责隔离执行，AI Gateway 做模型路由，Connect 管 OAuth/API key，Observability 展示 agent runs、token usage 和 trace。它不是单纯 TypeScript SDK，而是把 agent 的“脑、手、渠道、调度、可观测性”打包成一个部署形态。仓库 6 月中旬创建，已有约 3.3k stars，说明开发者确实在寻找比手写 LangGraph/cron/worker 更集成的 agent backend。对后训练工程的启发是，未来轨迹采集会越来越依赖这种 durable session runtime，训练样本必须记录目录结构、tool/skill 版本、channel、schedule、sandbox 和 event log。
🔗 链接：https://vercel.com/blog/introducing-eve ｜ 代码：https://github.com/vercel/eve

### DevSpace：把 ChatGPT/Claude Web 接成本地 Codex-style MCP coding workspace
很多用户想让 ChatGPT 或 Claude Web 直接处理本地项目，但浏览器聊天界面通常不能安全地读写文件、跑测试或使用真实终端。DevSpace 把这个缺口做成自托管 MCP server：用户在自己机器上运行服务，通过受控 tunnel 暴露 `/mcp`，再用 owner password 授权连接。连接后，模型可以在 approved project roots 内读、写、编辑文件，搜索代码，运行 shell 命令，使用隔离 Git worktrees，读取 `AGENTS.md` / `CLAUDE.md`，并发现本地 skill folders。它火的原因不是“又一个本地文件工具”，而是把 ChatGPT 这类通用聊天产品变成 Codex-style coding workflow，同时保留用户对文件根目录和连接授权的控制。近期 release 还加入实验性 local subagent delegation、agent profile、provider adapters，以及 Codex-compatible `apply_patch` / `exec_command` tool surface。工程风险同样真实：一旦授权，远端 MCP client 在工作区内拥有强大的本地能力，所以必须把它当作可信 coding partner，而不是低风险网页插件。对 Agent-Friendly Software 来说，DevSpace 代表一个重要方向：无法等待每个产品都内置 coding agent 时，可以用 MCP 把本地开发环境显式、可审计地暴露给模型。对评测和训练来说，这类工具会让“Web 模型 + 本地 MCP”轨迹接近 CLI agent 轨迹，需要单独记录权限、tunnel、worktree 和 tool surface。
🔗 链接：https://github.com/Waishnav/devspace ｜ 代码：https://github.com/Waishnav/devspace

### Claude Code model + effort levels：把“换模型”和“多努力”拆成可诊断 runtime knob
开发者常把“换更强模型”和“让 agent 想久一点”混在一起，但 Claude Code 这篇官方文章把两者拆得很清楚。model selection 换的是固定权重，也就是模型固有知识和能力范围；effort level 则控制 Claude Code 在一次任务中愿意做多少工作，包括读多少文件、用多少工具、跑多少测试、在回来问用户前推进多少步骤。文章强调 effort 不是单纯 thinking time，而是整体工作量策略；高 effort 可能产生约 7 倍 token，因为它会计划、查证、双检和继续执行更多步骤。它还给出实用诊断：如果 Claude 明明有上下文且认真尝试仍错，可能要换更强模型；如果错误来自跳过文件、没跑测试、重构半途停止，则更像 effort 不够。这个区分对 agent runtime 很有价值，因为很多团队现在只记录 model name，却不记录 effort、tool budget、verify policy 和 context 质量。对后训练软件工程来说，effort level 是很好的轨迹条件变量：同一任务在低 effort 和高 effort 下失败原因不同，不能混在一起训练。它也提醒我们，cost governance 不能只看输入 token，还要理解 agent 为什么决定多读、多测或提前停。
🔗 链接：https://claude.com/blog/claude-model-and-effort-level-in-claude-code ｜ 代码：None

### How Claude Code is built：从 product overhang 到 CLI-first harness 的构建复盘
Pragmatic Engineer 对 Claude Code 构建过程的采访不是论文，但它很好解释了为什么一个看似朴素的 terminal CLI 能成为高价值 coding agent。Boris Cherny 最早只是为了熟悉 Anthropic API 搭了一个终端原型，转折点是给模型 filesystem 和 bash 能力后，Claude 会自己沿 import 和文件结构探索代码库。文章把这种现象称为 product overhang：模型已有某种潜在能力，但现有产品形态没有把它释放出来。Claude Code 的 CLI 形态因此保留下来，因为 terminal 已经是工程师的真实工作面，bash、文件、git、测试、脚本和管道都天然可组合。更值得注意的是 dogfooding：工具在 Anthropic 内部快速传播，产品团队通过用户已经在做的事情发展 CLAUDE.md、plan mode、hooks 等能力，而不是预先设计一个复杂 UI。对 agent harness 工程来说，这个故事的核心不是“终端一定最好”，而是先给模型可行动工具和真实反馈，再从实际使用中发现哪些约束、记忆和流程需要固化。它对后训练数据也有启发：最有价值的轨迹往往来自真实工作流里的自然使用，而不是人为设计的孤立 prompt。
🔗 链接：https://newsletter.pragmaticengineer.com/p/how-claude-code-is-built ｜ 代码：None

### loop-engineering：把“设计循环而非提示词”做成 CLI、评分和成本工具
“Loop engineering”如果只停留在社交媒体口号，很容易被理解成无限重试或包装一层 shell while。`cobusgreyling/loop-engineering` 把它具体化成工具包：`loop-init` 脚手架 skills、state 和 budget files，`loop-audit` 检查 loop readiness，`loop-cost` 估算开销，`loop-worktree` 处理隔离工作树，还有 pattern picker 帮开发者选择适合的循环模式。README 的一句话很清楚：stop prompting, design the loop, get a score。它支持 Claude、Codex、OpenCode 等多种 coding agent，说明社区正在把循环行为从某个厂商功能抽象成跨 harness 的工程纪律。真正有价值的是 Loop Ready score 和 audit 思路：loop 是否有明确目标、验证、预算、停止条件、状态记录和安全边界，可以被检查，而不是完全靠作者自觉。仓库 6 月创建，约 6.4k stars，热度来自一个真实痛点：agent 已经能重复执行，但开发者缺少判断一个自动循环是否可交付的 rubric。对后训练软件工程来说，这类评分和审计结果可以成为 trajectory metadata，帮助区分“有边界的迭代”与“无约束 token burn”。
🔗 链接：https://github.com/cobusgreyling/loop-engineering ｜ 代码：https://github.com/cobusgreyling/loop-engineering

### Loopy Loop Library：把可复用 agent loops 做成目录、skill 和运行 receipt
很多团队会在项目里积累“每周检查 CI”“提升测试覆盖”“修复生产错误”这类重复工作，但这些流程通常散在 Slack、README 或个人提示词里。Loopy 把 loop 做成两层：一个公开 Loop Library 网站供人和 agent 查找可复用 loop，另一个可安装 skill 帮 agent 发现、审计、修复、改写、运行和保存 loop。它对 loop 的定义很朴素：不是让 agent 做一次，而是说明目标、如何判断最新尝试是否有效、学到东西后下一步做什么，以及什么时候停止或请人介入。README 里特别强调 bounded passes 和 receipt：运行 loop 后应返回 actions、evidence、outcome 和 stopping reason，而不是只说“我做完了”。这和本日报关注的轨迹筛选高度相关，因为一个可训练的 loop 样本必须有证据、停止条件和复盘，而不是开放式自然语言总结。Loopy 还可以把项目内值得保留的流程写入 `LOOPS.md`，让 loop 像 skill 或 runbook 一样被版本化。它按 Medium 收录，因为仍是早期社区项目，但与 skill management、workflow reuse 和 loop 工程化方向非常贴合。
🔗 链接：https://github.com/Forward-Future/loopy ｜ 代码：https://github.com/Forward-Future/loopy

### X hosted MCP server：把实时社交数据源官方封装给 Claude/Cursor/Grok Build 等 agent
Agent 要理解社区热点，最常见的数据源之一就是 X，但过去开发者需要自己建 MCP server、接 X API、处理认证和部署，门槛很高。TechCrunch 报道 X 推出 hosted MCP server，让 Claude、Cursor、Grok Build 等 MCP-compatible 工具可以用用户自己的账号权限访问 X API。这个发布不新增搜索、读帖、查用户、分析趋势等 API 能力，但把它们包装成 agent 更容易调用的标准接口，减少了“每个团队自建 connector”的重复工程。最重要的安全边界是它不兼容 Write API，所以不能用这个 MCP 直接自动发帖；X 也继续保留 API 规则、反垃圾检测和更高的发布/链接定价。它放 Low，是因为来源是产品新闻且不直接服务 coding-agent 后训练，但对 Agent-Friendly Software 有信号价值：大型平台正在把自身数据面官方 MCP 化。对本日报这种自动研究 scout 来说，它也说明“社区信息收集”会从网页搜索逐渐转向有权限、有速率限制、有审计边界的 hosted MCP。工程上值得借鉴的是 read-only 默认和账户权限继承，这比让 agent 拿一个高权限通用 token 更适合生产。

## 🔥 社区热点专栏

### 🔥 大佬观点

**Claude Code 团队 / Delba de Oliveira 与 Michael Segner：loop 的核心不是“跑久一点”，而是触发、停止和验证边界。**  
官方 loops 指南把 turn-based、goal-based、time-based、proactive loops 分开，并强调用 SKILL.md 写清楚验证动作和停止条件。这个观点值得注意，因为它把社交媒体里的 loop engineering 口号变成可执行 taxonomy：什么时候用 `/goal`，什么时候用 `/loop`，什么时候应该把工作放进 `/schedule`。🔗 https://claude.com/blog/getting-started-with-loops

**Addy Osmani / Boris Cherny / Peter Steinberger 等社区线索：设计 loops，而不是继续当人工 prompt router。**  
ADTmag 汇总的近期讨论显示，loop engineering 已从少数开发者实践变成主流话题：人类不再每轮提示 agent，而是设计 goal、trigger、verification、worktree、subagent 和成本边界。它值得注意，因为这正好对应生产 agent 的真实瓶颈：可靠性来自循环系统设计，而不是单条 prompt 写得更漂亮。🔗 https://adtmag.com/articles/2026/07/01/loop-engineering-emerges-as-developers-put-ai-coding-agents-on-repeat.aspx

### ⭐ 超火仓库/项目

**vercel/eve：约 3.3k stars，把 durable agent runtime 做成 filesystem-first 框架。**  
Eve 火在它不是又一个轻量 agent SDK，而是把 instructions、tools、skills、channels、schedules、sandbox、workflow checkpoint 和 observability 放进统一项目结构。它解决的痛点是：agent demo 很容易，长期运行、恢复、部署和观测很难。🔗 https://github.com/vercel/eve

**Waishnav/devspace：约 3.0k stars，用自托管 MCP 把 ChatGPT/Claude Web 接到本地开发环境。**  
DevSpace 的热度来自一个非常直接的需求：用户想让通用 Web 模型像 Codex 一样读写本地仓库、跑命令、用 worktree 和项目规则，但又不想把整个代码库上传到第三方。它的关键 insight 是把本地能力做成 explicit tools 和 approved roots，而不是给模型一个模糊的“电脑访问权”。🔗 https://github.com/Waishnav/devspace

**cobusgreyling/loop-engineering：约 6.4k stars，给 loop 工程加脚手架、审计和成本工具。**  
它火在把“设计循环”从文章变成可安装工具：`loop-init` 建目录，`loop-audit` 给 readiness score，`loop-cost` 估算预算，`loop-worktree` 管隔离。对团队来说，这比复制某个 viral prompt 更可持续，因为 loop 是否安全、可停、可测、可负担都能被检查。🔗 https://github.com/cobusgreyling/loop-engineering
