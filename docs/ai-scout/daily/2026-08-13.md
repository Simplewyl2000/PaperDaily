## 📝 逐条讲解

### Long-Horizon Agent Trajectory Attribution：给长轨迹做组件级因果归因
长程 agent 轨迹越来越复杂，里面混着用户指令、模型思考、工具调用、外部观察、记忆读写和安全拒答；如果最后任务失败或越权，单看最终结果很难知道到底是哪一段导致的。这个工作把“归因”单独做成评测任务：先把异构轨迹标准化成统一 component schema，再标注 primary attribution component，以及在攻击或执行场景中的多步 attribution chain。数据来自 AgentDojo 和 Agent3Sigma 的 Stage / Canary 设置，总计超过 1,300 条标准化轨迹，覆盖 task-aligned actions、unsafe actions 和 safety refusals。它设计了两类任务：一类是定位最主要的归因组件，另一类是恢复多步因果链，比如某个工具输出如何影响后续错误操作。论文还给出基于增量贡献和 leave-one-out perturbation 的参考 baseline，说明长距离归因和链式归因明显更难。它值得关注，是因为后训练数据筛选不能只问“这条轨迹成功了吗”，还要知道成功或失败由哪些组件造成。工程上，这类 schema 和 annotation skill 可以直接服务于失败轨迹清洗、安全事件复盘、可训练片段抽取和 eval anti-cheating。
🔗 链接：https://arxiv.org/abs/2608.06909 ｜ 代码：https://github.com/chenjing-2024/agent-trajectory-attribution

### Ouroboros：带 review gate 的自演化 frontier coding-agent core
很多 self-improving agent 的问题是边界不清：如果 agent 能随意改自己的 harness、memory 或核心代码，短期分数可能上涨，但系统也可能把错误经验、投机技巧或安全风险写进自身。Ouroboros 的看点是把自演化限制在 reviewed core evolution 里，也就是 agent 可以提出和实现 core/harness 修改，但修改需要经过 review gate，而不是直接永久生效。论文页面报告一个连续部署 feed：到 2026 年 8 月 6 日，系统运行 161 天，处理约 79.7B tokens，积累 227MB memory artifacts，并有 1,085 个 core modification commits。它还公开记录 reviewed self-edit attempts、recent review block rate 和 pattern recurrences，试图把“系统怎么改自己”变成可审计事件流。基准结果显示它在 Terminal-Bench 2.1、OSWorld-Verified、CL-Bench、SWE-bench Pro 和 GAIA 上接近或超过若干命名 baseline，但这些数字仍需独立复现。对后训练软件工程来说，Ouroboros 的价值不在某个 leaderboard 数字，而在自改协议：每次 runtime 变化都要有候选、证据、review、回滚和部署记录。它提醒我们，未来 harness evolution 的训练数据也应包含被拒绝的 self-edit、拒绝原因和上线后回归信号。
🔗 链接：https://arxiv.org/abs/2608.08311 ｜ 代码：None

### Claude Code Auto Mode：用工具调用风险分类器替代疲劳式人工许可
coding agent 运行时间变长后，传统“每个命令都让人点 approve”的模式会出现 permission fatigue：用户为了赶进度不断点通过，真正危险的命令反而可能混过去。Anthropic 8 月 7 日宣布 Claude Code 将在 Pro、Max 和 Team 新会话中默认启用 auto mode，用后台分类器评估工具调用是否可能有害，而不是让人机械审每一步。官方称在一项受控测试中，人类只抓到 13.6% 的植入危险命令，而 auto mode 抓到 89%；生产文章还称 Claude Code 在 auto mode 下两次中断之间能工作 9 倍更久。更重要的是，它不是“完全放开权限”：Nuro、Gusto、Garner 的案例都强调 deny dangerous commands、managed settings、MCP gateway、tool guards、telemetry 和高风险场景退回人工 review。这个变化直接击中了 agent runtime 的核心矛盾：要让 agent 长时间自主运行，又不能把安全边界交给模型自觉。对后训练工程来说，auto mode denial、被允许的 action、用户切换模式、组织 policy 和后续任务结果，都是极有价值的轨迹标签。它也说明权限系统应成为 harness 的一部分，而不是 prompt 里一句“请小心”。
🔗 链接：https://claude.com/blog/auto-mode-default-in-claude-code ｜ 代码：None

### Agent Against Agent / PIMiner：自动化 prompt-injection 红队攻击生成
工具型 agent 的 prompt injection 风险不只来自用户输入，也可能藏在网页、邮件、文档、工具描述或工具返回值里；人工红队能找到一些攻击，但覆盖不了复杂多轮场景。Agent Against Agent 把攻击者也做成 agent，让它自动构造和迭代 prompt-injection payload，目标是让 victim agent 在 IPIArena、AgentDojo 等环境里执行不该执行的动作。论文中的 PIMiner 会根据目标模型和环境反馈搜索攻击候选，并用 ASR@1 / ASR@10 这类指标衡量一次或多次尝试的成功率。摘要结果显示，不同模型家族的鲁棒性差异很大，例如某些模型在 AgentDojo 上 ASR@10 非常高，而 Claude Opus 4.5 在两个 benchmark 上明显更稳。它值得关注的地方不是“又一个攻击样例”，而是把 prompt-injection 红队自动化成可重复评测流程。工程上，安全团队可以把这类攻击生成器接进 MCP/tool-use CI，定期测试新工具、新 prompt、新权限模式是否引入回归。对后训练数据工程来说，失败的攻击、成功的攻击、被拒绝的边界和最终工具调用参数，都可以成为 agent safety training 的结构化样本。
🔗 链接：https://arxiv.org/abs/2608.05108 ｜ 代码：None

### AWB v1.7.0：把 Codex/Claude workflow 配置纳入真实仓库评测
很多团队对 coding agent 的比较还停留在“同一个模型分数多少”，但真实效果往往由模型、CLI、配置、项目说明、hooks、权限、测试策略和用户 workflow 一起决定。AI Workflow Benchmark（AWB）明确把评测对象定义为 full AI coding stack：tool + configuration + workflow + model，而不是裸模型。它用 100 个真实开源仓库任务和 12 个 capability dimensions 做评分，还提供快速 8-task probe，用来诊断当前 harness 哪些规则真的生效、哪些承诺没有触发。v1.7.0 的新增重点是 Codex CLI 端到端支持，包括 JSONL execution/traces、token budgets、model provenance、ChatGPT credit accounting、config A/B、workflow export 和 Codex checkup。这个项目星数很低，所以可信度按 Low，但方向非常贴近日常工程：同一个 Codex 或 Claude，在 vanilla 配置和经过项目化调优的配置下可能表现完全不同。对后训练软件工程来说，它提供了一种收集私有 eval 证据的方式：记录配置、轨迹、成本、验证结果和 rule promise，而不是只存最终 patch。它也能帮助团队决定某个 prompt、hook 或 skill 是否值得推广到组织默认模板。
🔗 链接：https://github.com/xmpuspus/ai-workflow-benchmark ｜ 代码：https://pypi.org/project/awb/1.7.0/

### mcp-agent：MCP-native + Temporal durable execution 的生产 agent runtime
MCP 生态快速扩张后，很多 agent 框架只是“能连 MCP server”，但 mcp-agent 的定位更进一步：直接把 MCP 当作 agent runtime 的原生协议。它支持 tools、resources、prompts、notifications，以及 OAuth、sampling、elicitation、roots 等较完整的 MCP 能力，同时把 Anthropic “Building Effective Agents” 中的 map-reduce、router、orchestrator、evaluator-optimizer 等 pattern 做成可组合 workflow。更工程化的一点是 Temporal integration：把执行引擎切到 Temporal 后，workflow 可以 pause/resume、自动 retry、保留 durable history，并在 worker crash 后通过事件回放继续。对生产 agent 来说，这比普通 async loop 更接近真实系统需要，因为长任务总会遇到等待人类输入、外部 API 抖动、worker 重启和审计追溯。仓库约 8.5k stars，说明它已经不只是小型 demo，而是 MCP-native agent runtime 的热门候选。它还支持把 agent app 自身部署为 MCP server，这让 agent 可以被其它 agent 或客户端作为工具调用。对后训练软件工程来说，durable history、token accounting、workflow step 和 MCP trace 都是比聊天记录更可靠的训练/评测数据来源。
🔗 链接：https://github.com/lastmile-ai/mcp-agent ｜ 代码：https://docs.mcp-agent.com/advanced/temporal

### Claude Code Week 32：跨 session messaging、自托管环境与 worktree 隔离更新
Claude Code Week 32 release notes 虽然是产品文档，但里面有多项直接影响 agent runtime 的工程更新。最显眼的是 cross-session messaging：Claude 可以通过 ListAgents 发现同一机器上的其它会话，再用 SendMessage 发送文本消息，用于通知另一个 session 某个共享前提已经变化。文档强调消息不是直接传 conversation history 或 files，这个边界很重要，因为多 agent 协作很容易无意扩大上下文和权限。另一个更新是 self-hosted environments，让 Team/Enterprise 可以把 Claude Code cloud sessions 跑在自家机器或容器上，使 agent 能访问内部服务，同时保留云端启动体验。release notes 还包含 worktree isolation 加强、credential masking、插件 zip 分发、fork 后独立 worktree、200 subagent cap 移除等细节。它按 Medium 收录，因为这些不是新论文，但都在把 coding agent 从单 CLI 会话推向多会话、可隔离、可托管的工程平台。对轨迹数据来说，session-to-session message、worktree 边界、runner 环境和 credential masking 都应进入 provenance，否则很难复现 agent 为什么看到或没看到某些上下文。

### 12 Agentic Harness Patterns：把 memory、权限、subagent、hook 沉到 harness
这篇 DEV 文章不是论文，也没有 benchmark，因此按 Medium / Low credibility 处理；但它把生产 agent 经常踩的坑梳理得很工程化。作者的核心观点是，真实 agent 不是 `User -> Prompt -> LLM -> Tool -> Answer`，而是一个 harness：上下文组装、分层记忆、规划、权限、子 agent、hook 和状态更新都围绕模型运行。文章把模式拆成 persistent instruction file、scoped context assembly、tiered memory、dream consolidation、progressive context compaction、Explore-Plan-Act、context-isolated subagents、progressive tool expansion、command risk classification 和 deterministic lifecycle hooks 等。它的价值在于把很多“提示词建议”重新放回软件边界里，例如高风险命令不应靠模型自评，而应由权限层判断；必须每次运行的格式化或验证不应写在 prompt，而应做成 hook。对后训练软件工程来说，这类模式能帮助我们设计轨迹 schema：需要记录哪些 instruction 被加载、哪些 memory 被检索、哪些工具因权限被过滤、哪些 hook 自动运行。它也提醒团队，不要一上来堆所有复杂性，而应先把 Explore-Plan-Act、工具渐进暴露、确定性 hook 和风险分类这几个高杠杆部分落地。虽然是实践博客，但它给 harness 工程提供了可操作的 checklist。
🔗 链接：https://dev.to/akki907/12-agentic-harness-patterns-2jkj ｜ 代码：None

### cc-codex-mutual-mcp：Claude Code 与 Codex 互为 MCP server 的桥接 skill
随着 Claude Code 和 Codex 都支持 MCP，社区开始把“一个 agent 调另一个 agent”从手工 subprocess hack 推向标准化工具接口。cc-codex-mutual-mcp 的做法是把 Claude Code 和桌面 Codex.app 互相注册为 MCP server，并用 SKILL.md 触发对应 delegation。Claude Code 调 Codex 时可以走 `codex mcp-server`，Codex 调 Claude Code 时可以走原生 `claude mcp serve`，另外项目还提供一个 `claude_agent` wrapper，把整段 headless Claude 任务包装成单个 MCP tool。这样做解决的痛点是跨 agent review、计划复核、实现委托和长期 session 复用，不必每次用冷启动 CLI 或复制上下文。风险也很清楚：互相调用容易形成递归、权限扩大和 provenance 混乱，所以 wrapper 需要 timeout、heartbeat、depth 和稳定路径。它按 Medium 收录，是因为项目热度和可信度有限，但方向非常贴近跨 harness orchestration。对后训练数据工程来说，这类桥接会让轨迹出现“agent 调 agent”的嵌套结构，必须记录 caller、callee、工具边界、返回摘要和真实执行环境。
🔗 链接：https://github.com/superchaospc/cc-codex-mutual-mcp ｜ 代码：https://github.com/superchaospc/cc-codex-mutual-mcp

### mcp-scan / MCP Client Inspector：把 MCP 安全审计拆成 server 扫描与恶意 client 测试
MCP 安全不只是一种风险：server 代码可能有路径遍历、SSRF、shell execution，client 也可能错误信任 tool description、过大响应、Unicode bidi 或动态重注册。mcp-scan 偏 server 侧，提供静态扫描与动态 harness，README 声称已经披露 6 个漏洞并验证 1 个上游修复。MCP Client Inspector 偏 client 侧，它是一个 deliberately malicious MCP server，用来测试 Cursor、Claude Code、Windsurf、Cline、Zed 等客户端面对 name collision、10MB tool response、prompt injection docstring、schema race、config-write RCE、notification flood 等场景时是否防御正确。两者星数都很低，所以不能当成成熟生态项目，但它们把 MCP 安全评测拆成了很实用的 test harness。这个方向与最近 Exposed by Design、MCP allowlist 和 OpenAI/Anthropic cyber eval 事故形成呼应：agent 工具协议必须被动态测试，而不是只读 README。工程上，企业 agent tool registry 可以把这类扫描和恶意 server 测试接到 CI 或准入流程里。对后训练数据来说，MCP 工具的安全姿态、客户端是否拒绝恶意 schema、agent 如何处理被阻断工具，都会影响轨迹是否适合训练。
🔗 链接：https://github.com/desledishant10/mcp-scan ｜ 代码：https://github.com/TreRB/mcp-client-inspector

### OpenAI Enterprise Signals：Codex usage 显示 agentic work 从工程扩到全公司
这条不是 coding-agent 后训练技术论文，因此按 Low 收录；但它是 OpenAI 8 月 12 日官方发布，且伴随 `The Shift to Agentic AI: Evidence from Codex` 工作论文，属于官方源强制检查新增项。OpenAI 把企业 AI 使用从“assistance”到“execution”的迁移具体化：截至 6 月，企业客户中 Codex 生成了 Codex + ChatGPT 合计输出 tokens 的 64%，说明代理式工作流在输出量上已经占很大比重。更有意思的是增长不只在工程团队：从 2 月以来，企业 Codex 周活在 legal 增长 108 倍，在 sales 和 recruiting 各增长 41 倍，在 marketing 增长 26 倍，而 engineering 是 5 倍。PDF 还提到超过 10% 用户每周某个时点管理 3 个或更多并行 Codex agents，26.6% 使用 skills，提交 8 小时以上人类任务请求的个人用户比例接近增长 10 倍。它没有给出可复现 harness 或训练 recipe，所以不能当作方法贡献；但它提供了非常重要的 agent ops 信号。对后训练软件工程来说，真实使用分布会反过来决定应该采哪些轨迹：跨职能任务、并行 agent 管理、skills adoption 和长任务委托会变成新的数据与评测重点。

## 🔥 社区热点专栏

### 🔥 大佬观点

**Ali Khater / DEV：生产 agent 的核心不是 LLM+工具，而是 harness 把状态、权限、记忆和 hook 接起来。**  
这篇 8 月 12 日文章的价值在于把 12 个模式讲成工程组件：scoped context、tiered memory、progressive tool expansion、command risk classifier、deterministic lifecycle hooks 等。它值得注意，因为社区讨论正在从“哪个模型更强”转向“哪些行为必须由 runtime 保证”，尤其是权限和生命周期 hook 不能再靠 prompt 约束。🔗 https://dev.to/akki907/12-agentic-harness-patterns-2jkj

**HN / Computer Use 讨论：GUI automation 真正的方向是 a11y、结构化 API 和可生成脚本，而不是让 agent 盲点屏幕。**  
HN 的 `Computer Use is 45x more expensive than structured APIs` 讨论里，一个高信号观点是：网站或桌面应用如果提供可访问性树、稳定 locator、CLI/API 或可生成脚本，agent 成本和失败率会大幅下降。这个 insight 对 Agent-Friendly Software 很关键，因为“把 GUI 交给 vision model”通常是最后手段；更好的工程路线是把传统软件做成可观察、可验证、可脚本化的 surface。🔗 https://news.ycombinator.com/item?id=48024859

### ⭐ 超火仓库/项目

**lastmile-ai/mcp-agent：约 8.5k stars，MCP-native agent framework 正在成为生产 runtime 候选。**  
它火在把 MCP 支持、effective agent patterns、Temporal durable execution、structured logging 和 token accounting 放到同一框架里，解决“demo agent 容易写，生产 agent 难恢复、难审计、难部署”的痛点。特别值得关注的是 agent-as-MCP-server 和 distributed tracing 方向，这会让多 agent 链路更容易被观测和复盘。🔗 https://github.com/lastmile-ai/mcp-agent

**Claude Code Auto Mode 生态：默认权限模式变化引发 classifier 成本、可解释性和组织策略讨论。**  
Auto mode 之所以热，不只是因为默认值改变，而是它把“人工点 approve”替换成了可被组织配置、统计和审计的风险分类层。社区已经围绕两阶段 classifier、transcript stripping、fail-open / fail-closed、成本归属和是否应在高风险生产操作中启用展开讨论，说明权限治理正在成为 coding-agent harness 的核心卖点。🔗 https://claude.com/blog/auto-mode-default-in-claude-code

**xmpuspus/ai-workflow-benchmark：v1.7.0 加入 Codex CLI 端到端评测，星数低但切中 workflow benchmark 痛点。**  
它不是星标爆款，但在本日报主题里高信号：真实团队需要比较的是 vanilla agent、带 hooks 的 agent、不同 `AGENTS.md` / `CLAUDE.md` 配置和不同 token budget 的差异。v1.7.0 的 Codex JSONL trace、config A/B 和 rule promise audit 让“我们改了 workflow 到底有没有用”变成可测问题。🔗 https://github.com/xmpuspus/ai-workflow-benchmark ｜ https://pypi.org/project/awb/1.7.0/
