## 📝 逐条讲解

### MCP 2026-07-28 RC：无会话核心、Tasks 扩展与 MCP Apps 重塑远程 agent 工具协议
过去几个月 MCP 已经成了 agent 接工具的默认协议之一，但远程部署仍有明显工程负担：要先 `initialize`，要保存 `Mcp-Session-Id`，负载均衡器要做 sticky routing，server 还要管理会话状态。2026-07-28 规范候选把协议层改成 stateless：每个请求都携带协议版本、client info、capability 和方法头，任何 server 实例都可以处理同一个 tool call。它不是说应用不能有状态，而是把状态变成显式 handle，例如 browser_id、task_id、basket_id，让模型在后续工具调用里看得见、传得动、也能被 trace。Tasks 从实验性 core 能力迁移成扩展，长任务由 `tools/call` 返回 task handle，再用 `tasks/get/update/cancel` 驱动；MCP Apps 则允许 server 提供 sandboxed iframe UI，但 UI 动作仍走 JSON-RPC 审计和 consent 路径。对 agent harness 工程来说，这会影响所有远程 MCP server 的部署、缓存、trace、auth 和长任务生命周期设计。它值得高优先级跟踪，因为 MCP 已经不只是一个本地插件协议，而是在变成可水平扩展、可治理、可观测的 agent runtime 连接层。
🔗 链接：https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/ ｜ 代码：None

### Approving：用可视化 workflow、sandbox、人工批准点和 rollback 编排可信 coding agents
并行或多步骤 coding agent 工作流的常见问题是，agent 可以很快生成代码，但人类很难知道什么时候该放行、什么时候该暂停、哪些步骤可以回滚。Approving 7 月 24 日创建，README 把目标定义为“Agent workflows that advance with humans”，核心不是让 agent 完全无人监管，而是把关键节点显式做成人工批准点。它提供可视化编排、sandboxed execution、human approval gates 和 rollback，让 workflow 在高风险动作前停下来，而不是靠最后一次 PR review 才发现问题。项目本身还把 CI、coverage、CodeQL、npm audit、gitleaks 等安全扫描放在仓库内，这说明它把 agent workflow 当作软件系统来交付，而不是 demo 脚本。它解决的真实痛点是：多 agent 生产力只有在每个状态转移可见、可暂停、可恢复时，才不会把风险转嫁给 reviewer。对后训练软件工程来说，这类 workflow 会产生很有用的轨迹标签：哪个节点需要人类批准、批准前后 agent 修改了什么、rollback 是否发生、sandbox 中哪些验证通过。
🔗 链接：https://github.com/cocofhu/approving ｜ 代码：https://github.com/cocofhu/approving

### ocm-mcp-server：让 agent 通过 OCM hub 操作 Kubernetes fleet，但不直接持有 kubeconfig
让 agent 管 Kubernetes fleet 很有吸引力，也很危险，因为一次错误写操作可能影响多个集群和生产 workload。ocm-mcp-server 的设计重点是把 agent 放在 Open Cluster Management hub 前面，而不是直接给它 kubeconfig。README 明确写着“agent never holds a kubeconfig”，每个写操作要经过 policy check、human approval token 和 audit trace，再通过 ManifestWork 这类受控资源进入集群。它还把 Kyverno policy、OCM、MCP 工具和审批流程连在一起，让 agent 可以诊断 degraded workload、提出修复、被 guardrail 拒绝、修正后等待人类批准并验证结果。这个项目星数还不高，但机制非常贴近 Agent-Friendly DevOps 的核心：把传统平台封装给 agent 的同时，不能把权限边界也交给模型自觉遵守。对后训练和 eval 来说，这种系统能生成比普通 shell 轨迹更可靠的数据：policy verdict、approval token、ManifestWork diff、集群验证结果和审计链都可以作为训练和回归信号。
🔗 链接：https://github.com/sandeepbazar/ocm-mcp-server ｜ 代码：https://github.com/sandeepbazar/ocm-mcp-server

### harness-eval：专门评估 AGENTS/skills/hooks/MCP 配置本身的 74 规则 agent harness linter
很多团队现在有 AGENTS.md、CLAUDE.md、Cursor rules、skills、hooks、MCP configs 和子 agent，但几乎没有工具能回答“这些 harness 配置整体是否安全、重复、冲突或过大”。harness-eval 把评估对象从模型输出转向 harness 本身：它支持 Claude Code、Cursor、Copilot、Gemini CLI、OpenCode，自动发现规则文件、skills、commands、hooks、MCP server 和第三方模块。它的核心亮点是 cross-component graph，不只单文件 lint，而是追踪 skill、agent、hook、MCP server 之间的数据流，寻找 credential exfiltration chain、confused deputy、触发重叠、token budget 和破损引用。安全侧还包括 Python/bash taint tracking、YARA、OSV CVE lookup 和可选 LLM semantic review；工程集成侧则有 CLI、GitHub Action、Claude Code plugin、Cursor commands 和 SARIF 输出。它解决的是 harness 工程规模化后的基础卫生问题：如果每个 subagent 都继承同一套坏配置，动态 workflow 会把问题放大。对后训练数据工程来说，这类 linter 可以成为轨迹采集前的质量门，先确保生成轨迹的 harness 不含明显污染、权限泄露或规则冲突。
🔗 链接：https://github.com/redhat-community-ai-tools/harness-eval ｜ 代码：https://github.com/redhat-community-ai-tools/harness-eval

### AutoDev Studio：先构建 repo knowledge base，再让多 agent 走 scope-code-test-review-PR 流程
普通“给仓库一个需求，让 agent 自己 grep”的方式，在大仓库里经常会把 token 花在定位而不是修改上。AutoDev Studio 的思路是先对目标 repo 构建一次 knowledge base，再让不同 agent 在 scoped、file-cited 的上下文切片里工作。它把任务流拆成 Backlog、Scoped、Approved、Dev、QA、Review、PR，并在面板里记录 token/cost，总体上更像一个小型 agentic SDLC 系统，而不是单次 CLI 调用。README 给出与冷启动 `claude -p` 对比的成本结果，尤其在 cross-cutting bug 和定位困难任务上节省明显；这些数字还需要独立复现，但方向很对。它的新意在于把 repo understanding 当成可复用资产，而不是每个任务重新让模型从零摸索代码库。对后训练软件工程来说，这种设计提醒我们，训练样本应记录 repo KB 版本、被喂给 agent 的文件引用、scope 决策、QA/review 结果和成本，而不是只保留最后 PR。
🔗 链接：https://github.com/krishagarwal314/autodev-studio ｜ 代码：https://github.com/krishagarwal314/autodev-studio

### godot-mcp-go：把 Godot 编辑器和运行中游戏暴露为 CLI + stdio/HTTP MCP 的 312 个可验证命令
游戏开发和可视化编辑器一直是 agent 难以可靠操作的场景，因为真实状态存在于 GUI 编辑器和运行中的游戏里，不在文本文件中。godot-mcp-go 把 Godot 4.7 编辑器做成 agent-friendly surface：Go CLI 和 GDScript addon 通过 WebSocket 通信，提供 312 个命令，覆盖场景、脚本、运行、检查和 API introspection。它同时支持三种入口：terminal-first agent 可以直接走 CLI，不付 MCP schema token；支持按需加载的客户端可以走 typed MCP；会一次性加载全部 schema 的客户端则可以折叠成一个 generic `godot_run` 加只读资源。这个设计很工程化，因为它没有把所有用户都强迫进一种协议，而是按 agent 的上下文成本和工具能力给出不同 surface。它解决的真实痛点是，让 agent 可以在真实编辑器状态上构建、运行、检查游戏，而不是只改 GDScript 文件再猜结果。对 Agent-Friendly Software 来说，这是 GUI-to-CLI/MCP 的典型案例：传统富客户端需要被拆成命令、状态、schema、trace 和可验证反馈。
🔗 链接：https://github.com/regiellis/godot-mcp-go ｜ 代码：https://github.com/regiellis/godot-mcp-go

### timecode:agent：长视频先转 timestamped evidence ledger，再让 coding agent 懒加载视觉验证
长视频理解对 agent 来说很容易变成昂贵的一次性多模态调用：把大量帧丢给模型，得到一个难以审计的总结。timecode:agent 反过来采用 transcript-first 方法，先生成带时间戳的 transcript，并收集 scene、audio energy、OCR、faces 等 deterministic placement signals。agent 只有在某个 claim 需要视觉证据时才懒加载对应时刻做 visual verification，并把检查结果写成 time-addressed checkpoints。所有 checkpoint、capture provenance、edit decision 都进入 append-only ledger，后续的 EDL、OTIO、FCPXML、SRT 和 wiki 是从 ledger 派生，而不是从一次模型回答派生。它不属于传统 coding-agent benchmark，但非常符合“把非代码软件/媒体工具 agent 化”的方向。对后训练软件工程来说，它提供了一个重要模式：复杂多媒体任务也要先做可审计证据账本，再让模型基于证据做决策，这样轨迹才能复现、比较和训练。
🔗 链接：https://github.com/mupozg823/timecode-agent ｜ 代码：https://github.com/mupozg823/timecode-agent

### How to Give an LLM Agent a Browser：OpenAI Agents SDK + Playwright MCP 的浏览器 agent 最小闭环
很多真实业务系统仍然只存在于浏览器里，agent 如果不能操作 admin console、CRM、support inbox，就很难进入生产工作流。Shuai Guo 这篇 7 月 26 日文章用 OpenAI Agents SDK 和 Playwright MCP 搭了一个最小浏览器 agent，任务是在本地 customer support console 中处理订单问题。文章最有价值的部分是把 browser use 拆成 observation channel 和 action channel：截图加坐标是一类，structured page state 加 element-targeted action 是另一类。示例选择了 Playwright MCP 的 accessibility snapshot，让页面元素带 ref id，agent 可以点击和填写具体控件，而不是在截图上猜坐标。它还用 `max_turns` 限制循环，并在最后检查 case 状态和 audit log，避免只听 agent 自称完成。按 Medium 收录，是因为它偏教程和最小 demo，但对团队落地 browser harness 很实用：清楚展示了观察、动作、验证和循环上限该如何接起来。
🔗 链接：https://towardsdatascience.com/giving-an-llm-agent-a-browser/ ｜ 代码：https://github.com/ShuaiGuo16/llm-browser-agent

### Pinggy MCP + Skill：让 agent 自己给 localhost 开公网 tunnel，但强调实验状态与权限审查
开发者做 webhook、移动端回调或远程 demo 时，经常需要把本地服务临时暴露到公网；过去这一步通常会打断 agent，因为要人类另开终端跑 tunneling 工具，再把 URL 复制回上下文。Pinggy 的 MCP server 和 Agent Skill 把这个动作变成 agent 可调用能力：用户可以说“把 3000 端口暴露出去”，agent 通过 tool call 创建 tunnel 并返回公网地址。文章也做了一个值得肯定的区分：先安装 skill，让 agent 读文档并自己执行普通 CLI；只有需要 agent 直接管理 tunnel 时，再加 MCP server。由于 tunnel 是网络边界能力，文章明确提醒该 server 仍是 early/experimental，要审查源码、控制 IP whitelist、使用认证，不要把“agent 礼貌请求”当作安全授权。它解决的真实痛点很具体：agent 写完 webhook handler 后，可以继续完成外部服务注册和测试，而不是停在 localhost 边界。对后训练软件工程来说，这类工具会产生重要的安全轨迹：agent 何时暴露端口、暴露给谁、是否加认证、何时关闭 tunnel，都应该进入审计和训练样本。
🔗 链接：https://instatunnel.hashnode.dev/letting-ai-drive-exposing-localhost-via-mcp-servers ｜ 代码：https://github.com/Pinggy-io/pinggy_mcp

### Vigla：跨 Claude Code / Codex / Antigravity 的 mission control，用四类边界触发人工介入
当团队同时运行多个 coding agent 时，真正困难的不是启动五个终端，而是统一任务分解、事件记录、权限边界、diff 审计和最终合并判断。Vigla 把自己定位为“Mission control for AI coding agents”，让 Claude Code、Codex CLI、Antigravity 和 profile-backed agent CLI 在各自 git worktree 中工作，再把输出归一化到 canonical event stream。它强调人类不需要审核两百个小动作，而是设定 authority envelope，由 supervisor agent 分配任务并在 Scope、Reversibility、Risk、Quality 四类边界触发时升级给人。README 还提供 deterministic recorded events 和 replay，说明它关注的不只是运行时调度，还有事后可解释性。它与 Sigbound/mergetrain 一类项目方向相邻，但更偏“operations room”和监督界面，而不是单纯 merge gate。对后训练数据工程来说，这种 mission-level trace 很有价值，因为它把任务拆分、vendor adapter、边界触发、人类介入和最终 verdict 记录在同一条链上。
🔗 链接：https://github.com/Kilbex/Vigla ｜ 代码：https://github.com/Kilbex/Vigla

### OpenHub：终端里的 AI coding tools / MCP servers / skills 发现与安装 TUI
AI coding 工具体系已经变得很碎：MCP servers、skills、agents、rules、package installers、模板仓库散落在 GitHub、博客和各自客户端目录里。OpenHub 把这件事做成一个 keyboard-first TUI discovery hub，本地 SQLite 缓存、后台同步 GitHub 数据，并支持 fuzzy search 和 curated collections。它还把导出格式对齐到 Universal Open Agent Skills Standard / `SKILL.md`，让导出的工具可以进入 OpenCode、Claude、Cursor、Windsurf、Cline、AutoGen、CrewAI 等不同宿主。它的工程价值不是某个单项能力很强，而是承认“agent skills 和 MCP server 需要包管理/发现/安装层”，否则团队会继续复制粘贴不明来源配置。按 Medium 收录，是因为项目还早、星数不高，但它击中了 agent tooling supply chain 的痛点。对后训练软件工程来说，工具发现和安装本身也会影响轨迹：agent 用了哪个 skill、从哪里安装、版本和质量评级是什么，都应被记录。
🔗 链接：https://github.com/24KaratAu/openhub ｜ 代码：https://github.com/24KaratAu/openhub

### ForgeOS：用 skill routing、context governance 与 evidence gates 组织 agent control plane
ForgeOS 是一个低星但机制密集的新项目，定位为 skill intelligence OS 和 trust control plane。它关注六个问题：目标是什么、该用哪种 technique、最小上下文是什么、哪些步骤必须确定性执行、什么证据足够证明完成、失败后能否恢复和审计。README 显示它提供 skill routing、context governance、deterministic steps、evidence threshold、58 个 MCP tools 和 388 项测试。这个方向值得关注，是因为 agent 生态已经从“给模型更多工具”进入“决定什么工具/技能/上下文被允许进入这次工作单元”的阶段。它的可信度仍按 Low 标注，因为项目很新、star 较少，许多声明还需要真实使用验证。对后训练软件工程来说，ForgeOS 这种 control-plane 思路可以帮助构造更干净的轨迹：模型不是在无限工具面中漂流，而是在被路由、被约束、被证据门判定的工作单元里执行。

## 🔥 社区热点专栏

### 🔥 大佬观点

**MCP Working Groups：远程 MCP 的核心矛盾从“能不能接工具”转向“能不能像普通 HTTP 服务一样扩展、缓存和追踪”。**  
2026-07-28 RC 的热点在于它删除协议层 session，把状态变成显式 handle，并把 Tasks、MCP Apps、Trace Context、OAuth hardening 放进协议演进路线。这个观点值得注意，因为 agent 工具协议已经进入生产部署阶段，负载均衡、缓存、trace、auth、deprecation policy 都会影响 coding-agent harness 的稳定性。🔗 https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/

**UNU Macau：harness 应被当作独立治理对象，而不是模型或平台的附属实现细节。**  
UNU 报告把 harness 定义为把模型输出转成 tool calls、memory updates、approvals、interruptions 和 recoverable actions 的 runtime 层，并建议在采购和合规中评估 model-harness pair。它值得注意，因为这把社区里“harness engineering”的工程共识推进到机构治理：skills、MCP servers、plugins 和 tool wrappers 都是供应链组件，需要文档、权限和可替换性。🔗 https://unu.edu/publication/engineering-and-governing-agent-harness-technology-and-policy-framework-runtime-layer

**Shuai Guo / Towards Data Science：浏览器 agent 的关键不是“会看网页”，而是观察通道和动作通道怎样配对。**  
文章把 screenshot+coordinate 与 accessibility snapshot+element refs 这两种模式讲清楚，并用 OpenAI Agents SDK + Playwright MCP 跑完整 support-console case。这个 insight 对前端和业务后台 agent 很实用：结构化页面状态和可定位元素能显著降低坐标误差、DOM 噪声和验证困难。🔗 https://towardsdatascience.com/giving-an-llm-agent-a-browser/

### ⭐ 超火仓库/项目
