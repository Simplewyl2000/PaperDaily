## 📝 逐条讲解

### RST：递归合成 37,484 个可验证长程 terminal-agent 任务
长程 terminal-agent 训练数据很贵，真正困难的不是写一句任务描述，而是让指令、环境、参考解、测试器和 verifier 同时保持一致。RST 的核心做法是反过来做数据合成：先从一个已经可验证的 seed task 出发，扩展参考解和运行步骤，再同步改写公开指令与 verifier，最后放进 fresh sandbox 里验证整套任务是否还能跑通。通过这种递归方式，成功的新任务又会变成下一轮种子，所以任务难度会逐轮增长，而不是停留在一批静态模板。论文报告 15 轮递归后得到 37,484 个 validated terminal tasks，单任务成本约 0.05 美元；中位参考解从 67 行长到 374 行，中位命令数从 40 增到 244。更重要的是，这些任务不是只用于 benchmark：作者用 Qwen3.5 自 rollout 收集轨迹做 SFT，并在 Terminal-Bench 2、Terminal-Bench Hard 和 Long-Horizon Terminal Bench 上带来最高约 10 分提升，PPO 还继续提高 Qwen3.5-27B。对后训练数据工程来说，它提供了一个很强的模板：先构造能执行、能验证、能递归变难的任务工厂，再采成功轨迹和 verifier reward，而不是直接让模型生成一堆看起来合理的任务。这个方向特别适合 coding/terminal agent，因为 shell、文件系统和测试器天然能给出机器可验证信号。
🔗 链接：https://arxiv.org/abs/2608.05466 ｜ 代码：https://huggingface.co/datasets/Zhongzhi1228/Recursive-Task-Synthesis ｜ https://zhongzhi660.github.io/recursive-verified-synthesis-site/

### CodeGrep：用 67K OpenHands 轨迹训练 14B 仓库检索 agent
很多 coding agent 的 token 并不是花在真正写 patch 上，而是花在找文件、grep、glob、读无关上下文上。CodeGrep 把这个“文件发现税”单独拆出来训练一个 14B retrieval agent，让它先用 grep、glob、read 等只读工具找到候选文件，再把结果交给冻结的下游 OpenHands agent。训练数据不是人工标注的文件相关性，而是从 67K 条 OpenHands 轨迹中挖掘出来的 Code Agent Trajectory Mining 标签，再在 Git-worktree sandbox 里做多轮 GRPO。实验最有意思的不是 +1.2 个百分点 resolve rate，而是效率：在 500 个 SWE-Bench Verified 实例上，resolved runs 的轮数减少 15%，token 减少 19%。论文还给出一个很实用的阈值发现：BM25 precision 0.375 会污染上下文并降低分数，Jina 0.445 基本中性，CodeGrep 0.677 才越过“检索真的有帮助”的门槛。工程上，这提醒我们不要把任何检索都当成省 token 的好事；错误候选文件会让 agent 读更多、想更久、甚至修错地方。对后训练软件工程来说，CodeGrep 展示了如何把历史 agent 轨迹转成专门的前置技能模型，而不是把所有探索过程都塞给主修复模型学习。
🔗 链接：https://arxiv.org/abs/2608.05886 ｜ 代码：None（论文称模型、训练 pipeline、RL 环境和 eval harness 将发布）

### Screenshots or Tools?：GUI-MCP 混合 agent 的工具采用 gap 与截图压缩
Computer-use agent 现在常有两种行动方式：看截图点 GUI，或调用 MCP/text tool 直接操作应用状态。直觉上，给 agent 更多工具应该更强，但这篇论文发现“工具可用”并不等于“模型会正确采用工具”。在 OSWorld-MCP 的 309 个任务上，同一套 GUI-MCP harness 对 reasoning model 有 +4.0pp 帮助，却让 non-reasoning model 下降 -5.9pp，因为后者会忽略、误命名或错误终止工具调用。即使 reasoning model 能避免明显错误，也只在 55 个任务里使用工具，只覆盖 tool-reachable tasks 的 23.9%，作者称之为 adoption gap。论文用多轮 RL probe 发现，给 spreadsheet 工具调用加 dense bonus 可以提高工具采用率，但 held-out accuracy 不一定跟着提升，说明“愿意调用工具”和“会用工具完成任务”是两件事。另一个工程点是截图冗余：工具调用成功后，下一个截图往往只是重复文本状态，跳过这些 observation 并减少 image history 能把输入 token 降到约 53%，重新训练后还可消除精度损失。对 Agent-Friendly Software 来说，这篇很有价值：GUI-to-agent 的关键不是把 GUI 和 MCP 都暴露出来，而是训练模型在何时切换通道、如何整合工具结果、以及何时压缩多模态上下文。
🔗 链接：https://arxiv.org/abs/2608.03327 ｜ 代码：https://github.com/redai-infra/hybrid-routing-agent

### OneDayAgent：用分解、执行记忆和全局验收修复长程 everyday agent
长程 everyday agent 任务通常跨网页、文件、图片、表格、代码执行和最终交付物，普通 ReAct 轨迹很容易在几十步后忘掉最初约束。OneDayAgent 把长任务变成一个受管理的执行流程：先把用户请求拆成最多 6 个 bounded subtasks，再让每个子任务在统一工具面里执行，并把中间结果和文件句柄写进 execution memory。它不把全部低层轨迹传给后续步骤，而是用子任务答案、结果文件和压缩摘要作为跨环境状态，这样能缓解 context pressure。完成所有子任务后，系统会合成最终产物，并用 global verifier 对照原始请求、子任务输出和实际附件检查是否遗漏要求；如果缺文件或内容不一致，就进入 targeted repair，而不是重跑整个任务。论文在 AgentIF-OneDay 的 104 个任务上报告 GLM-5.2 backend 得到 0.821 overall score，并且同一 harness 可迁移到 Gemini、Qwen 等多个 backend，只是延迟、工具调用数和 repair rate 不同。它还公开了完整轨迹和 judge scores，这比只报 leaderboard 分数更适合复核和二次训练。对后训练软件工程来说，OneDayAgent 的重点是把“交付物是否满足原始 intent”做成显式验收与修复事件，让轨迹不只是聊天记录，而是带计划、执行、产物、验收和修复的结构化日志。
🔗 链接：https://arxiv.org/abs/2608.05013 ｜ 代码：https://github.com/zjunlp/OneDayAgent ｜ https://huggingface.co/datasets/zjunlp/onedayagent_traj

### HyperAgent：把工具依赖建成 Tool-Schema Hypergraph，减少盲目工具探索
工具型 agent 在复杂 API 环境里常靠自然语言描述猜“先调用哪个工具、哪个输出能喂给下一个工具”，这会带来大量无效调用和参数拼错。HyperAgent 的做法是把工具关系显式建模成 Tool-Schema Hypergraph：每个工具是一条从输入 schema 节点指向输出 schema 节点的超边，工具的前置条件、产出和状态变化都能在图上表达。给定任务后，它先抽取任务相关的工具上下文图，再构造 schema-aware Task DAG，让模型不是凭感觉编排工具，而是围绕缺失的输入需求做规划。执行阶段的 deficit-oriented expansion 很实用：系统维护当前状态还缺哪些输入 schema，再沿超图找能生产这些输入的工具，逐步补齐 support subgraph。AppWorld 实验显示，这种结构化工具规划提升 task completion，同时减少冗余 API calls、LLM interactions 和 token consumption。它不直接面向 coding agent，但对 MCP、enterprise API、SaaS 工具链很重要，因为工具数量变多后，单靠文本描述会让模型在 schema 组合里迷路。对后训练数据工程来说，HyperAgent 提醒我们工具轨迹的质量不只看最后成功，还要看每次工具选择是否由明确的数据依赖支持。
🔗 链接：https://arxiv.org/abs/2608.02650 ｜ 代码：None

### OpenAI Astra critical cyber controls：把高能力 agent 训练/评测纳入强化隔离和 CoT 监控
OpenAI 8 月 7 日发布的这条官方安全更新不只是模型新闻，而是一次 agent 评测与训练基础设施的风险升级信号。OpenAI 表示，未发布模型 Astra 的内部评估显示其 agentic coding 和 cybersecurity 能力足够强，以至于目前不能排除达到 Preparedness Framework 的 Critical cybersecurity threshold。这个阈值指向很高风险的能力，例如在很少人工干预下发现和武器化零日漏洞，或执行端到端的新型网络攻击策略。相应措施包括暂停不满足强化安全控制的 Astra 内部活动、使用隔离测试环境、限制网络和工具访问、加强模型权重保护与加密、扩展监控检测和沙箱执行。最贴近本日报主线的是 OpenAI 对所有 Astra agentic applications，包括 training 和 evaluation，实施 universal monitoring：monitor 会评估 Chain of Thought 并触发安全响应来审查或中断高风险行为。结合近几天第三方 cyber eval 事故披露，这说明 frontier coding/cyber agent 的评测环境本身已经成为必须治理的系统，而不是附属实验脚本。对后训练软件工程来说，高能力 agent 的 rollout、red-team、eval 和训练数据采集都需要记录网络边界、工具权限、监控触发和中断条件，否则能力数据和安全事故会混在一起。

### EASy：用 milestone-plan-act 与多组件 reward 训练成本敏感 orchestrator
很多 agent 系统会把任务直接丢给一个强执行器，或者用简单 router 按任务类型分配模型，但真实任务里的成本和中间反馈会动态变化。EASy 把 agent orchestration 看成可训练策略：orchestrator 明确知道不同 executor 的能力和成本，再用 milestone-plan-act workflow 把复杂任务拆成里程碑、依赖图和可并行步骤。这样它不是只问“哪个模型最强”，而是能在执行过程中根据中间结果调整后续 executor 选择。训练上，EASy 使用 tree-structured rollout，从已有轨迹的 milestone 或 plan 节点扩展替代分支，让同一任务上下文下的不同策略可比较。reward 也不是单一成功率，而是同时考虑 task correctness、execution efficiency 和 trajectory completeness，并在节点和 query 层做归一化，减少不同任务难度带来的噪声。它按 Medium 收录，因为主题更通用，不专门面向 coding agent；但成本敏感 orchestration 是软件工程 agent 规模化部署必需的。对后训练数据工程的启发是，训练集应保留 executor 选择、成本 profile、依赖图、并行边界和中间反馈，而不是只保存最终成功的合并轨迹。
🔗 链接：https://arxiv.org/abs/2608.04588 ｜ 代码：None

### Control Under Compression：15,525 次运行测 agent control context 压缩可靠性悬崖
很多团队为了省 token 会压缩 system prompt、工具说明、协议规则和恢复策略，但这些 agent control contexts 不是普通文本摘要，它们控制的是工具参数、执行协议和失败恢复。Control Under Compression 提出 CompressAgent benchmark，用 9 个独立构造的 ACC、3 类任务、3 个 Qwen API 模型、6 档保留预算和 15,525 次可审计运行，专门测压缩后 agent 是否还能正常执行。结果显示压缩有明显非线性悬崖：保留 75% 时，generic rewriting 和 section-based compression 仍接近 full-context baseline 的 93.8% 成功率；但在 50% 到 35% 之间方法差异突然放大，35% 下 generic rewriting 只有 19.9%。失败分析也很实用：压缩问题主要表现为 tool-execution 和 action-parsing errors，而不是最终回答文字变差。论文因此把 ACC compression 从“token reduction”重新定义为 runtime-reliability problem，必须用可执行环境结果评估。它和之前的 KV cache compaction、Supercompress、Paritok 不同，焦点在控制指令和工具协议是否被破坏。对后训练软件工程来说，任何压缩器都需要记录压缩比例、保留策略、上下文结构和后续工具错误，否则训练数据会把“因控制信息丢失导致的失败”误标成模型能力不足。
🔗 链接：https://arxiv.org/abs/2608.01056 ｜ 代码：None

### AgentOPSD：用递归自蒸馏做长程 agent turn-level credit assignment
长程 agentic RL 的核心痛点是 outcome reward 太稀疏：一条轨迹最终成功或失败，但真正决定结果的可能只是中间几个关键 turn。AgentOPSD 试图在不训练额外 critic、也不增加额外 rollout 的情况下，把 sparse reward 转成 turn-level credit。它把 teacher-student token log-probability gaps 聚合为每个 turn 的证据，再在 log-odds space 里递归更新一个 Bayesian belief state。每个 turn 对 belief 的边际改变就被当作这个 turn 对最终成功概率的贡献，用来重加权训练信号，帮助模型识别“真正让任务走向成功或失败”的节点。alphaXiv 摘要报告它在 ALFWorld、WebShop 和 Search-QA 上优于 GRPO 和其它 self-distillation baseline，Qwen2.5-7B 在 ALFWorld 达到 89.1%，相对标准 GRPO 的 81.2% 有明显提升。按 Medium 收录，是因为它更偏 RL credit assignment 方法，软件工程落地还需要把测试、diff、工具错误等 domain 信号接进来。对我们的关注点而言，它的价值在于提供一种通用的 pivotal-turn 识别框架，可以和 coding agent 的关键 grep、关键测试、关键 patch、关键 verifier failure 结合。
🔗 链接：https://www.alphaxiv.org/overview/2608.05987 ｜ 代码：None

### agentgateway v1.4：MCP 2026-07-28、EMA 和 OAuth token exchange 进入 agent proxy
MCP 进入企业部署后，问题不再只是“agent 能不能连工具”，而是认证、授权、路由、观测、限流和多版本兼容谁来负责。agentgateway v1.4 的重点是支持 MCP 2026-07-28 规范，这个规范把协议推进到更适合网关和负载均衡的 stateless core。release 还加入 Enterprise-Managed Authorization / Cross App Access，让集中式访问控制能作用在 MCP server 上，并提供更灵活的 OAuth token exchange backend auth。对平台团队来说，这意味着 agent 不必直接持有 GitHub、SaaS 或内部服务凭证，而可以通过 gateway 做身份、策略和审计。v1.4 还增强 standalone mode、数据库持久配置、统一端口服务 LLM/MCP/UI、OIDC UI auth、Gateway API v1.6、fault injection 和更丰富的 guardrails。仓库约 4.3k stars、716 forks，说明它不是一次性 demo，而是正在成为 MCP/A2A/LLM traffic 的基础设施候选。对后训练软件工程来说，gateway 层会变成轨迹 provenance 的关键来源：谁调用了哪个 tool、哪个 auth policy 放行或拒绝、哪个版本协议参与，都应该被记录下来。
🔗 链接：https://github.com/agentgateway/agentgateway/releases/tag/v1.4.0 ｜ 代码：https://github.com/agentgateway/agentgateway

### epsilab v0.17.x：把 agent workflow 环境、轨迹导出和 GRPO/DPO/SFT 接成 SDK
epsilab 不是热门 GitHub 项目，仓库星数几乎为零，因此可信度按 Low；但它代表了一类值得关注的 post-training 基础设施形态。它把自己定位为 open hub for RL environments，支持研究者搜索、运行和导出 hosted environments，也支持环境构建者发布自己的任务。SDK 里有 `agent_workflow`、`code_sandbox`、`simulation` 等环境类型，能创建 RL session、逐步执行 action、获取 reward、验证 trajectory integrity，并导出 GRPO、DPO、KTO、SFT 或 process supervision 数据。PyPI 页面还给出 online GRPO、batch evaluation、multi-env data collection、Together/Fireworks/Tinker/local TRL 训练路径。它解决的真实痛点是：agent RL/SFT 往往卡在环境管理、轨迹标准化和训练数据导出，而不是算法本身。风险也很清楚：公开项目热度和可复现案例不足，需要观察是否能积累真实环境和第三方使用。对后训练数据工程来说，这类 SDK 的方向正确，因为训练数据应该从可验证环境 session 里导出，而不是从不可重放的聊天日志里手工清洗。

### Anthropic Claude Riemann zeta：未发布 Claude 把相关零点下界从 41.6% 提到 67.2%

## 🔥 社区热点专栏

### 🔥 大佬观点

**Yucheng Shi / RST 作者：长程 terminal 任务合成要“先做可运行解，再反写任务和 verifier”。**  
他在 LinkedIn 解释 RST 的核心 inversion：不要先写自然语言任务再希望环境能跑，而是先扩展 reference solution 和 runtime environment，再拟合 verifier 与 task statement。这个观点值得注意，因为它把 agent 数据合成从语言生成问题变成软件构建问题，直接解决了长程任务中 instruction、environment、solution、verifier 四者不一致的痛点。🔗 https://www.linkedin.com/posts/yucheng-shi_building-synthetic-long-horizon-terminal-activity-7491366307129593856-lEpq

**Daniel Vaughan / Codex Knowledge Base：CodeGrep 暴露了 coding agent 的 file discovery tax。**  
他的分析把 CodeGrep 的论文结果翻译成工程决策：检索精度低于阈值时，false positives 会污染上下文，BM25 这类“便宜检索”反而让 agent 花更多 token。这个 insight 对团队很实用，因为很多人只问“要不要加 repo search”，却没有测 precision、token delta 和下游 resolve rate 的联动。🔗 https://codex.danielvaughan.com/2026/08/08/codegrep-rl-trained-retrieval-agent-coding-agents-codex-cli-file-discovery-token-efficiency/
