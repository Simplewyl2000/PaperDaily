## 逐条讲解

### FrogNano-4B-2609：微软只用 RL、不用强模型轨迹，靠约 1,500 个合成环境把 4B 模型训成 coding agent
小模型 coding agent 现在的主流做法是“蒸馏”：先让强模型（如前沿闭源模型）跑出大量解题轨迹，再让小模型照着模仿。这样做成本高，还容易把老师的偏好和错误一起学过去，而且 SWE 类任务的真实环境（仓库 + 运行时 + 测试）很难大批量获取。微软的 FrogNano 走了另一条路：从 Qwen3.5-4B 出发，智能体相关的后训练**只用强化学习**，不用任何强模型的解题轨迹、动作或补丁。训练环境由一个叫 TaskPilot 的系统生成：它在真实仓库快照上让一个“出题模型”写问题描述、参考补丁和隐藏测试，每个环境包含仓库、运行时、题面、参考补丁、新生成的评分测试和原有回归测试；而且题目会**对照当前策略的水平进行校准**，保持在“刚好学得会”的难度区间。奖励来自可执行测试：新测试要通过（fail-to-pass），原有测试不能被破坏（pass-to-pass）。在官方模型卡里，SWE-bench Verified（Avg@3）随 5 轮 TaskPilot 迭代从 39.4% 依次涨到 49.1 / 53.1 / 56.7 / 59.1 / 61.5%；在没参与调参的 SWE-bench Pro、Terminal-Bench 2.0、PatchEval-Verified 上分别是 37.6%、31.1%、47.3%。配套的 Leaf harness 只有 read / write / edit / glob / bash 五个工具。对我们来说，这是一份大厂给出的“环境合成 + 在线难度校准 + 纯 RL”完整配方，说明**环境生成流水线本身可以代替蒸馏数据**；模型卡也坦白了局限：训练数据以 Python 为主，效果依赖 harness 和测试质量。社区反应很快，10-02 起一天内就出现了十几个 GGUF / MLX 量化版本。
🔗 链接：https://huggingface.co/microsoft/FrogNano-4B-2609 ｜ 代码：https://github.com/microsoft/FrogNano

### Invent-A-Dataset：手上一条数据都没有时，怎么直接造出可用的后训练数据集
很多团队想给模型补一项新能力时，手里**一条种子数据都没有**，现有的数据合成方法大多要先给几条样例，再让模型模仿扩写。这份技术报告专门研究这种“零种子”场景：用户只给一段数据集描述，Invent-A-Dataset 通过一套基于提示的系统直接生成真实感强、规模大的后训练数据。作者在 8 类任务、最多 2 万条样本的规模上，与 Anthropic、Google、OpenAI、DeepSeek、智谱五家前沿 API 直接生成的数据做对比：质量相对高 17%，多样性相对高 19%。更有意思的是多样性优势会**随规模扩大**：200 条时与对手持平，2 万条时相对领先 37%。也就是说，前沿模型直接批量生成时，越往后越容易重复。用这些数据微调出的下游模型，在多种架构上的排名也都更靠前。对数据工程来说，它提醒我们：评价合成数据不能只看小样本质量，**多样性在大规模下会不会塌缩**同样是关键指标。
🔗 链接：https://arxiv.org/abs/2610.01674 ｜ 代码：None

### Effective Synthetic Data Curation Requires Group-Level Signals：筛选合成数据不能只给每条样本单独打分
当前筛选训练数据的常见做法，是给每条样本单独估一个“训练价值”（比如影响力分数、质量分），再保留高分样本。但合成数据有一个特点：样本之间高度相关，比如同一个生成器产出的大量相似样本，单独看每条都不错，放在一起训练却可能让模型的生成能力变差。这篇论文在预训练和后训练两种场景下证明，这种**单样本（individual-level）信号看不见样本之间的组合效应**：组成不同的两个合成数据集，按单样本影响力看几乎一样，按组级影响力看差别很大，而按组级信号筛选的数据在下游效果更好，生成能力上尤其明显。作者还发现，训练流程里合成数据的比例越高，组级信号越重要；在主流的数据筛选方法中，只有引入了组级信号的方法能超过基线。考虑到组级估计很贵，作者给出一个低成本诊断，先找出最需要做组级估计的数据组，用一小部分算力就能拿回大部分收益。对于大量用合成轨迹做 SFT / RL 的团队，这是一个可以直接落地的检查点：**筛选数据时要看“这一批数据放在一起训练”的效果**。
🔗 链接：https://arxiv.org/abs/2610.00779 ｜ 代码：None

### Agents Are Systems, Not Models：评测 agent 时，配置往往比模型本身更重要
现在的 agent 评测除了成功率，也开始报告成本、稳定性和鲁棒性，但通常把 agent 当成一个固定的东西来测。实际上 agent 是一个**可配置的系统**：给它多少任务信息、让它跑多久、开不开自我验证、用哪个底座模型，都由使用者决定。这篇论文构建了 4 个科学计算任务的基准，要求 coding agent 找到并正确运行一个已发表的专业模型，然后系统地改变五个配置维度。第一个发现是运行之间的随机性很大：**约 54% 的结果方差来自“同一配置重复运行”，而不是换配置**。第二，给 agent 的任务信息影响最大，超过时间预算和模型规模，而且还能降低成本、改善校准；多给时间只有在信息充足或模型足够强时才有用。第三，在提示词里要求“请验证答案”几乎不会改变 agent 的实际验证行为，而**直接提供一个专门的验证工具**会显著改变行为。作者开源了基准和 1.8 万多条轨迹。对评测工程来说，结论很直接：报分时必须多次重复运行，并把配置当作实验变量；想让 agent 做某件事，做成工具通常比写进提示更可靠。
🔗 链接：https://arxiv.org/abs/2610.01618 ｜ 代码：None（论文称已开源基准与轨迹）

### Continuous Process-Level Evaluation：企业 agent 技能的“结果对了”远不等于“过程对了”
企业里的 agent 技能（skill）会持续变化：工具 API 升级、底座模型更换、需求说明修改都会影响行为，如果只检查最终输出，就会漏掉过程中的“行为漂移”。这篇 NeurIPS 2026 workshop 论文给出一个持续评测框架，把结果层检查和过程层检查结合起来：每次运行都独立计算真值，把检查固化成可复用的模板测试，再用程序化检查（外加一个职责范围很窄的 LLM judge）逐项核对工具选择、参数、执行顺序和数据库完整性。作者在 2 个业务技能 × 2 个需求版本 × 2 种 harness × 3 个模型上跑了 240 次试验。结果很醒目：最终数值全部正确的 175 次运行里，有 **162 次（92.6%）仍存在其他偏差**；换一个更宽的“最终状态正确”定义，也有 92.1% 违反了某条轨迹检查。为了避免报警刷屏，框架还做“依赖归因”，把平均每次 6.34 个失败检查归并为 2.65 个根因。这套“真值独立计算 + 模板化回归 + 根因归并”的流程，很适合直接搬到 coding agent 的 CI 回归评测里。
🔗 链接：https://arxiv.org/abs/2610.01833 ｜ 代码：None

### Auditing Web Agent Evaluation on WebArena-Lite：人工逐题复核，自动评测器漏判了多少
Web agent 的评测通常依赖规则或 LLM 评测器，而且只看最终结果；有多少成功被误判为失败、失败到底卡在哪一步，很少有人系统核对过。这篇论文把 WebArena-Lite 全部 165 道题，在 GPT-5.5 与未训练的 Qwen3.5-9B 组成的 6 种条件下逐一人工审计：保留原分数、纠正自动评测的误判（false negative）、标出“第一个导致失败的关键错误”，并检查整条轨迹上的进展。结果显示，在 GPT-5.5 的四种设置下，人工复核能找回自动评测器漏掉的 **5.45~8.49 个百分点**的成功率，足以改变很多方法对比的结论。作者还测试了两个 harness 机制：显式维护执行状态的记忆模块 MASM，以及提供任务相关操作指引的 Guide Text，两者都有提升。对 102 条失败轨迹的分析发现，常见问题是滚动死循环、探索没做完、过早作答、非法动作和表单流程没走完，而且“前期进展很大但最终失败”的情况很普遍。启示：基准分数需要定期做人工抽检，评测报告里也应包含**过程进展**这类指标。
🔗 链接：https://arxiv.org/abs/2610.01491 ｜ 代码：None

### KaliBench：一个能直接当 RL 奖励来源的安全工具命令行基准
安全分析工作高度依赖命令行工具，一个参数写错、参数顺序颠倒，命令就执行失败；但现有评测要么考安全知识问答，要么测端到端 agent 任务，没有专门衡量“把自然语言意图准确翻译成可执行命令”的能力。KaliBench 构建了 8,504 条“需求—命令”对，覆盖 Kali Linux 上 1,642 个工具、23 个能力维度和 5 个渗透阶段。数据从工具手册出发构造，配合确定性的命令规范化和别名感知比对，因此**不用真正执行命令就能精确判分**。为了保证命令既语义正确又真能跑，作者用了“LLM 校验 + 沙箱终端实际执行 + 人工修订”的多级验证流程。在不提示工具的设置下，没有任何开源模型的完全匹配准确率超过 42%。更有工程价值的是，这种确定性打分可以直接当作“免运行时的可验证奖励”：用它做 SFT + RLVR 后，一个 8B 模型达到了与 685B MoE 模型相当的水平。这为“如何低成本为工具调用类任务构造 RL 奖励”提供了一个可复用的范式。
🔗 链接：https://arxiv.org/abs/2610.02206 ｜ 代码：https://github.com/RISys-Lab/KaliBench

### SecureVibe：功能对了但不安全的代码，问题出在没做安全规划和测试
随着“氛围编程”（vibe coding，主要由 AI 写代码、人只看结果）普及，一个越来越突出的问题是：代码功能正确，却藏着安全漏洞。作者分析这类“功能正确但不安全”的解后发现，写出不安全代码的 agent，**针对隐藏安全风险做有效规划和测试的概率不到安全 agent 的一半**。也就是说，问题主要出在行为习惯上，而不只是知识欠缺。基于这个观察，SecureVibe 围绕“安全规划”和“安全测试”这两种行为构造训练信号：先在包含 4 类安全任务的数据集上做 SFT，再用两种后训练方式继续强化，一种是基于执行反馈的 RL，另一种是基于提示的自监督。结果：BaxBench 安全 pass@1 提升 6.9 分，在没见过的 CWE 漏洞类型（SusVibes）上提升 11.5 分，功能正确率也没有下降，SusVibes 上 +13.6、通用的 SWE-bench Verified 上 +4.1。两条实践经验值得记下：把监督**分散到规划、编码、测试多个环节**，比单纯堆编码轨迹更有效；当模型原有能力太弱、从结果反馈中学不动时，提示引导的监督特别有用。
🔗 链接：https://arxiv.org/abs/2609.38606 ｜ 代码：None

### STITCH：把 harness 拆成可复用的“原语”，测试时按任务现拼
Harness（套在模型外面的那层控制代码，负责收集上下文、调用工具、验证结果、保存状态和决定何时结束）对 agent 表现影响很大。但同一个机制并不是对所有任务都有用：对 A 任务有帮助的机制，放到 B 任务上可能只增加开销、分散上下文，所以“一个全局固定 harness”天然次优。为每个任务现写 harness 代码又太贵，还会引入新 bug。STITCH 的思路是先从**失败轨迹中挖掘“Harness 原语”**：每个原语是一个可复用的机制，带有清晰的适用范围和组合约定；测试时根据任务信息挑出合适的原语，编译成任务专属的 harness，不需要临时生成或修复代码。实验中它比固定 harness 最多提升 12 个百分点，超过 Codex CLI 这类人工设计的 harness；测试时组装开销只有 2.7%，比从零生成任务专属 harness 高效 638 倍，而且效果随原语库变大而提升。这给 harness 工程提供了一个实用的中间路线：**把 harness 拆成带适用范围说明的组件库，按任务组合**，而不是只在“一个固定 harness”和“每次现写”之间二选一。
🔗 链接：https://arxiv.org/abs/2609.38912 ｜ 代码：None

### Mingbird：同一个 2B 模型从 0.017 到 0.821，问题出在 harness 上
2~9B 的开源小模型可以在普通笔记本上运行，但放进为云端大模型设计的 agent 框架里，几乎完成不了真实任务：工具说明一预填就撑爆上下文，自我纠错越改越偏，模仿工具示例陷入死循环，任务做到一半悄悄放弃。Mingbird 的作者认为，**很大一部分失败要归咎于 harness，而不是模型**。他们为 Windows + Ollama 做了一个本地优先的 harness，用 10 个机制逐一补偿小模型的失败形态，代表性的三个是：按字节严格控制预填预算、接受“完成”之前强制重读一遍任务的完成闸门、基于调用签名的循环检测。在他们构建的受控对比中（同一台机器、同样的模型和预算，4 个 harness × 4 个模型 × 18 个真实任务，按产出物确定性打分，288 个结果全部公开），Mingbird 总分 0.886，goose 0.631，opencode 0.479，agent-mini 0.405；在 τ²-bench 上也领先。作者也写明了局限：基准是自建的，只有一台机器，单次试验，消融结论只能算方向性证据。但对“小模型 agent”和端侧 coding agent 的工程实践来说，这份逐项失败模式 → 逐项补偿机制的对照表很有参考价值。
🔗 链接：https://arxiv.org/abs/2610.02001 ｜ 代码：https://github.com/Mingbird/Mingbird-agent

### Mixture of Self-Improving Branches：harness 自动优化不要只走一条搜索路径
“让 agent 自己改自己的 harness”已经是一个热门方向，代表作 Meta-Harness 的做法是：反复生成 harness 代码、在开发集上评测、根据反馈继续改。但它固定了开发集和“怎么提改动”的策略，整个演化只沿一条路径进行，容易陷入局部最优。这篇论文（据报道来自 Meta、杜克大学和 UC Davis）把搜索拆成多个分支：每个分支有自己不断变化的开发子集，只保留本分支领先 harness 比其他分支解得更好的用例，剔除所有分支都能解的用例；每个分支还会根据自己的搜索历史修改提案策略。部署时由一个路由器为每个新输入挑一个分支的最优 harness。相对 Meta-Harness，它在奥赛级数学上相对提升 34.8%，Terminal-Bench 2.0 上 +11.6%，SWE-bench Lite 上 +3.8%，而且 harness 选择和路由配置只用了开发集数据。启示：自动 harness 优化里，**“用哪些题来提供反馈”本身也应该跟着演化**。
🔗 链接：https://arxiv.org/abs/2609.37834 ｜ 代码：None

### RuleEvolve：让 coding agent 的规则文件自己进化
Coding agent 的表现很大程度上取决于“编码规则”，也就是 `AGENTS.md`、`.cursorrules` 这类告诉 agent 该怎么写代码的说明。现实中这些规则大多是手写的，写完基本不再改，既费人力，效果也未必好。RuleEvolve 维护一个候选规则池并反复迭代：每一轮由 LLM 变异器基于现有规则生成变体，再由 judge 模块评测这些变体，把表现最好的放回池中。论文在 2 种 coding agent 框架、4 个底座模型和 3 个基准上测试，在功能正确率、代码长度和生成成本（token 消耗）上都优于人工规则和现有的提示优化方法。论文已被 NeurIPS 2026 接收。对团队来说，这意味着规则文件可以像超参数一样**用评测集自动调优**，前提是先有一套可靠的评测集。
🔗 链接：https://arxiv.org/abs/2610.00650 ｜ 代码：None

### PG-SFT：在 agent 轨迹上做 SFT 时，怎样少忘掉原有能力
用离线 agent 轨迹做 SFT 是训练专用工具调用 agent 的标准做法，但逐 token 强制模仿推理和动作，往往会损害底座模型原有的能力，比如通用推理、工具调用和代码生成。作者的对比实验显示：标准 SFT 提升了目标基准，却让好几个非目标基准下降；常见的补救措施（加 KL 惩罚限制分布漂移、限制更新幅度）都**没能扭转这种退化趋势**。PG-SFT 的做法是用轨迹中每一轮的“信息增益”作为指标来调节监督强度：信息量大的轮次多学，信息量小的轮次少学。结果是分布漂移和整体能力退化明显减少，代价是目标任务略有下降。核心结论是：要平衡“学新能力”和“保留旧能力”，关键不只是“锚定原模型”，而是**在哪里、以多大力度偏离原模型的行为**。对做 agent SFT 数据配方的人来说，这提供了一个按轮次加权监督的思路。
🔗 链接：https://arxiv.org/abs/2610.00949 ｜ 代码：None

### DARS：失败的轨迹里，哪些步骤其实是有用的
Agent RL 通常只有最终的成功 / 失败奖励。这带来一个问题：一条失败轨迹里每一步的未来奖励都是 0，即使其中很多步骤其实做出了有效进展。另一方面，建立在没有纠正的错误之上的后续工作确实是白做的，而与该错误无关的工作仍然有效，现有的步级打分方法通常不区分这两种情况。DARS 把任务进度表示为一组带前置依赖的“谓词”（例如“文件已找到”“测试已通过”），由标注器标出每一步验证、破坏或修复了哪些谓词；已验证的谓词按照与最近“断掉的前置条件”的图距离打折，独立的谓词不受影响，再通过固定的势函数转成每一步的正负奖励。它通过统一的奖励和标注接口接入 GiGPO、ARPO/AEPO 等现有方法，不需要改 rollout 和优化器。在 ALFWorld 上比同预算的 GiGPO 最多高 10 个点，在 WebShop、Search-R1 上也有提升。工程上值得注意的一点是：**蒸馏出的 8B 标注器效果与 API 标注器相当**，可以不依赖前沿模型当 judge。
🔗 链接：https://arxiv.org/abs/2610.01207 ｜ 代码：https://github.com/JianhuiWei7/DARS

### RISED：多环境 RL 里用 rubric 来选数据、给监督
把一个 agent 放在多种交互环境里联合训练，是走向通用 agent 的常见路线，但有两个工程难题：现有的课程或数据选择多按环境分配预算，没有考虑不同环境 rollout 之间的关系；各环境学习速度不同，同一个 batch 里会同时出现“全失败”和“全成功”的组，这些组拿不到组内相对奖励（GRPO 一类方法依赖组内比较）。RISED 让 LLM judge 用一套**跨环境共享的 rubric 词表**给每条 rollout 打行为标签，由此得到行为画像：数据选择时让被选数据的行为组成贴合整体、并减少与已选数据的重叠；正向 rubric（期望行为）作为特权上下文提供给一个在线自蒸馏老师，补充 token 级监督；负向 rubric（不良行为）用来引导后续 rollout 避开反复出现的失败模式。在多个底座模型上，它的平均通过率最高，在每个单独环境上都排第一或第二。这为 rubric 提供了“奖励”之外的用法：**同时用于数据选择和蒸馏监督**。
🔗 链接：https://arxiv.org/abs/2610.00979 ｜ 代码：None

### Keyword Harnesses Fail Open：关键词匹配式的工具调用评测会把“不会”判成“会”
很多小模型的工具调用评测只用关键词匹配，比如输出里出现了工具名就算对，这会把根本没真正调用工具的模型也判成功。作者在一对架构相同的西班牙语安全小模型（661.6M 和 1.1B）上碰到了这个假阳性：两者宽松指标几乎一样（0.660 vs 0.650），但让它们复现训练样例时，600M 模型 6/6 都能输出带泛化参数的有效工具调用，1B 模型一次都做不到（0/6）。作者设计了一套逐级加严、成本很低的诊断：先做训练样例复现检查，再用“首 token 探针”定位，发现 1B 模型对 `<|tool_call|>` 这个特殊 token 的先验概率只有 1e-4~1e-5，这个先验是被以网页为主的训练阶段抹掉的。随后一个定向 SFT 配方（更多样的语料、5 倍学习率、2,202 步、约 3.3 GPU 小时）就修复了问题，所用 token 比造成问题的那个训练阶段少三个数量级，有效调用率从 0.100 升到 0.959。启示：**工具调用评测要用严格格式校验来把关**，这套只需几分钟 CPU 的诊断阶梯可以直接加进训练流水线做门禁。
🔗 链接：https://arxiv.org/abs/2610.02142 ｜ 代码：None

### A model guide for the GPT-6 family：OpenAI 官方的 GPT-6 选型与 agent 工程指南
GPT-6 家族现在有好几个型号（Astra、6.1 Sol、Luna 等），每个型号又有多档推理强度，开发者普遍不清楚该怎么选、提示和 skill 该怎么写。OpenAI 10-02 发布的这份指南给出了官方建议：最难的推理用 GPT-6 Astra；复杂编码、研究和电脑操作用 GPT-6.1 Sol；目标明确的大批量日常任务（抽取发票字段、分类请求、结构化摘要）用 GPT-6 Luna。推理强度分档使用：low 用于例行任务和小改动，medium 用于需要判断的规划，high 用于困难调试和仔细审查，xhigh / max 只有在 high 不够且收益值得额外时间和成本时才用；API 支持在对话中途调整推理强度而不破坏缓存。在 agent 工程方面，指南要求 prompt、skills 和仓库说明（`AGENTS.md`）在“交付什么、哪些可以自主做、怎样算完成”上保持一致；skill 描述要短而明确，细节按需加载；生产环境要用缓存和上下文压缩，并度量任务成功率和延迟；长任务要用中途引导（steering）、异步工具和任务委派。配套的 API 文档还特别提醒：GPT-6 Astra 对 skills 和 `AGENTS.md` 里的指令**更敏感**，建议审计模型能读到的所有指令文件。
🔗 链接：https://openai.com/index/practical-guide-building-gpt-6 ｜ 代码：None
