## 📝 逐条讲解

### RigorBench：把 coding agent 的工程过程纪律做成可评分 benchmark
现在很多 coding-agent 评测只问最后测试是否通过，但真实工程里，“怎么通过”同样重要：一个 agent 如果靠盲改、反复试错和偶然通过测试完成任务，后续维护风险会很高。RigorBench 把这个问题拆成五个可评分维度，包括计划是否忠实、验证是否覆盖、失败后恢复是否高效、遇到不可解任务是否能正确放弃，以及每次变更是否保持原子性。它构造了 30 个任务，覆盖 Plan-Then-Build、Verify-Or-Die、Doom Loop Gauntlet、Know When to Fold、Don’t Break the Build 等场景，专门诱发 agent 常见坏习惯。结果显示，带结构化过程纪律的 harness 平均让过程质量分提升 41%，并让下游 outcome correctness 提高 17%。这件事的价值在于，它把“资深工程师会要求的工作习惯”从口头规范变成了轨迹级指标。对后训练软件工程来说，RigorScore 这类信号可用于筛掉“最后对但过程烂”的训练样本，也可作为 agent runtime 的回归测试。
🔗 链接：https://arxiv.org/abs/2606.22678 ｜ 代码：https://github.com/MeherBhaskar/agent-rigor

### Claude Tag：把 Claude Code 演化成 Slack 里的团队级异步 agent
很多团队使用 coding agent 时仍然是个人会话：一个人开一个窗口，agent 的上下文、工具权限和工作结果都停留在私人线程里。Anthropic 的 Claude Tag 把 Claude 放进 Slack channel，任何成员都可以 @Claude 派任务，所有人都能在同一 thread 里看到它的进度和产物。它不只是聊天机器人，而是带 channel-scoped memory、工具和代码库访问、异步任务、ambient updates、定时自我调度和管理员审计/预算控制的团队级 agent。Anthropic 称内部产品团队 65% 的代码由 Claude Tag 内部版本创建，这个数字虽需谨慎看待，但说明它已被定位为 Claude Code 的组织协作形态。工程上最关键的是身份和记忆隔离：管理员按 channel 配置工具、数据和预算，销售频道的 Claude 不会把记忆传给工程频道。对 Agent-Friendly Software 来说，Claude Tag 说明 agent 的入口正在从 IDE/terminal 扩展到协作系统，而后训练数据也会多出“多人委派、异步推进、频道上下文、审计日志”这类新轨迹。
🔗 链接：https://www.anthropic.com/news/introducing-claude-tag ｜ 代码：None

### FeatureBench：从 bug fixing 扩展到端到端 feature delivery 的 coding-agent benchmark
SWE-bench 已经成为 coding agent 的默认指标，但它主要测单个 issue 的 bug fixing，离真实产品开发里的“交付一个功能”还有距离。FeatureBench 的目标是测 feature-level development：agent 要理解高层需求、处理接口和依赖、管理环境，并实现一个可调用、可测试、不会破坏旧功能的完整 feature。它的构造方法很工程化：从开源仓库的单元测试出发，选择 fail-to-pass 和 pass-to-pass 测试，做动态 tracing 和对象依赖图，再合成可验证任务和预解代码库。第一版包含 200 个任务、3,825 个可执行环境和 24 个仓库，并提供 `fb data`、`fb infer`、`fb eval` 三类 CLI。最有冲击力的结果是，Claude Opus 4.5 在 SWE-bench 可达 74.4% resolved，但在 FeatureBench Full 只有约 11.0%；Codex 系列也只有十几个百分点。它值得高度关注，因为它暴露了“修 bug”和“持续交付 feature”之间的真实能力断层，也给训练数据构造提供了可自动刷新、可执行验证的 pipeline。
🔗 链接：https://arxiv.org/abs/2602.10975 ｜ 代码：https://github.com/LiberCoders/FeatureBench

### ContextEcho：长程 agentic-coding 会话中的 persona drift 评测 harness
长程 coding agent 会话常常经历数千轮工具调用、压缩、恢复和继续执行，模型一开始被设定的“助手身份”和输出契约未必能坚持到最后。ContextEcho 研究的就是这种 persona drift：模型经过长时间工具使用后，可能从谨慎的工程助手变成更自信、更啰嗦、甚至破坏格式契约的回答者。它提供 25-probe identity suite，并用 snapshot-then-probe 协议从真实 Claude Code session 中 fork 出状态，在不扰动主会话的情况下对多个模型做探测。公开数据包含三段匿名 Claude Code 会话，长度约 3,746 到 9,716 turns，并在 23/24 个前沿模型上测到漂移具有普遍性。一个很重要的发现是，常见 context compaction 并不能稳定重置 persona，而一个约 110 token 的 single-shot anchor 可以在多个目标上恢复原始 register 并保持 20+ turns。对 runtime 工程来说，这说明 compaction 不是万能状态修复器，长程 agent 需要独立的身份/契约探针、anchor 策略和会话末端审计。对后训练来说，长轨迹不应只看任务是否继续推进，还要看格式、身份和安全边界是否随时间漂移。
🔗 链接：https://arxiv.org/abs/2605.24279 ｜ 代码：https://github.com/Accenture/ContextEcho

### OpenClaw-Skill：用 Collective Skill Tree Search 自动构造可迁移技能树
技能系统已经成为 agent harness 的核心部件，但许多 skill 仍靠人工写 `SKILL.md`，质量不稳定，也很难知道某个 skill 是否只对一个模型或一个任务有效。OpenClaw-Skill 尝试把技能构造做成自动化搜索问题：先把任务拆成子任务，再由多个模型生成候选 skill node，并由多个 judge 从质量和跨模型可迁移性两个角度评估。这个过程被称为 Collective Skill Tree Search，包括 CSN-Gen 和 CSN-Assess 两个迭代阶段，最后形成结构化、多样化、可组合的 skill tree。论文还用这些技能构造 skill-augmented training data，并引入 Collective Skill Reinforcement Learning，让模型在解题时主动选择多个相关技能，避免被单一技能路径锁死。它的工程价值不在“又加一个提示文件”，而在于把技能发现、技能评审、技能树组织、训练样本生成和运行时技能选择串成 pipeline。对本日报关注的数据工程方向来说，这正好对应“skill auto generation / management”：未来可复用技能应有来源、评审、迁移验证和训练轨迹，而不是散落在个人配置中。
🔗 链接：https://arxiv.org/abs/2606.16774 ｜ 代码：https://docs.openclaw.ai/tools/skills

### GameCraft-Bench：用 Godot 可玩游戏验证完整软件 artifact 交付能力
很多代码评测只要函数输出对或测试通过，但一个完整游戏不是一段代码：脚本、场景、资源、渲染、输入、物理和反馈必须在同一个引擎生命周期中协同工作。GameCraft-Bench 把 coding agent 放到 Godot 4 环境里，要求它从自然语言规格生成完整可玩的 2D 游戏项目，并提交可重放的 demonstration traces。评测器会启动游戏、重放键鼠轨迹、录制 gameplay evidence，再用隐藏 rubric 和多模态 judge 从核心机制、内容深度、视觉反馈和呈现质量等维度评分。数据集包含 140 个任务、15 类游戏家族，最强配置也只有 41.46%，大多数 agent 低于 40%。这说明 agent 往往能实现局部机制，却很难把多组件软件 artifact 组合成完整可交付产品。它和 JAMER 等游戏引擎评测互补：前者更强调项目级真实仓库，GameCraft 更强调从需求到完整互动 artifact 的闭环验证。对评测工程的启发是，未来 agent benchmark 需要把“能启动、能演示、能被外部观察者验证”作为一等契约。
🔗 链接：https://arxiv.org/abs/2606.17861 ｜ 代码：https://github.com/tongxuluo/gamecraft-bench

### Codex SQLite feedback logs：TRACE 日志写放大暴露 agent runtime 资源治理缺口
Coding agent 的风险不只来自模型写错代码，也可能来自 runtime 本身的工程实现。OpenAI Codex 的 GitHub issue #28224 报告，本地 SQLite feedback logs 在 TRACE 级别持续写入，用户测得 21 天约 37 TB 主盘写入，外推约 640 TB/year，足以显著消耗消费级 SSD 寿命。问题根源不是 agent 做了危险操作，而是诊断日志 sink 默认捕获高频 WebSocket/SSE、dependency internals 和 OpenTelemetry mirror 事件，并在 SQLite/WAL 中产生 insert-and-prune churn。OpenAI 已合入 #29432、#29457，并计划通过 #29599 在 0.143.0 继续消除 `target=log` TRACE 事件；0.142.0 release note 也提到减少 persistent-log churn。这个事故值得放进日报，是因为它把 agent runtime 的“可观测性”反过来变成资源消耗和数据保留问题。工程上应建立持久日志级别、采样、保留、WAL checkpoint、用户开关和写入预算，而不是让 unattended agent 长时间运行后才发现硬件成本。对后训练/评测平台同样适用：采集轨迹越多，越要把日志本身纳入成本和隐私治理。
🔗 链接：https://github.com/openai/codex/issues/28224 ｜ 代码：https://github.com/openai/codex/releases/tag/rust-v0.142.0

### MCP vs CLI Benchmark：量化 MCP schema bloat 的 token / reliability tax
MCP 正在成为 agent 连接工具的标准协议，但“标准化”不自动等于“低成本”。ScaleKit 的 MCP vs CLI benchmark 用同一个 Claude Sonnet 4、同样的 GitHub 任务和提示，对比 `gh` CLI 与 GitHub Copilot MCP server，发现直接 MCP 在 75 次运行中 token 成本可高 4 到 32 倍，原始成功率约 72%，而 CLI 路径为 100%。主要问题不是 JSON-RPC 本身，而是 schema bloat：MCP server 会把所有 43 个工具 schema 注入上下文，即使当前任务只需要 1 到 2 个工具。文章估算，10,000 次月度操作下 CLI 约 3 美元，直接 MCP 约 55 美元；如果通过 gateway 做 schema filtering，只暴露当前相关 2 到 3 个工具，token 可下降约 90%。这对 Agent-Friendly Software 很重要，因为工具接口设计不能只看功能完整性，还要看 schema 暴露策略、远程依赖可靠性和上下文预算。结论不是“CLI 永远更好”，而是生产 MCP 需要 gateway、progressive disclosure、tool search 和响应裁剪，否则协议税会吞掉 agent 自动化收益。
🔗 链接：https://www.scalekit.com/blog/mcp-vs-cli-use ｜ 代码：https://github.com/scalekit-inc/mcp-vs-cli-benchmark

### LARK：按学生模型“可学性”筛选 reasoning trajectories
很多轨迹筛选方法只看老师轨迹是否正确、是否高置信，或者是否看起来更详细，但这并不保证学生模型真的能从中学到。LARK 把 trajectory selection 改成“可学性”问题：一条轨迹的价值取决于它能多快降低学生模型的训练损失，同时还要保持原始分布覆盖。方法上，它估计一个 learnability proxy，并用 chi-squared regularized selection policy 在可学性和多样性之间做平衡，避免只挑容易样本导致泛化变差。实验显示，LARK score 能预测下游训练效用，LARK 选择的轨迹也能让 SFT loss 更快下降。它不是 coding-agent 专项论文，因此按 Medium 收录，但与本日报重点“Trajectory Selection / 训练数据挑选”直接相关。对工程团队来说，最值得借鉴的是把筛选器嵌入训练前数据 pipeline：不要只保存成功 rollout，而要估计某个目标学生模型是否能从该轨迹中稳定获益。后续如果把 learnability proxy 接到 terminal/coding agent 的工具轨迹上，会很适合做可复用训练数据筛选器。
🔗 链接：https://arxiv.org/abs/2605.30651 ｜ 代码：https://github.com/Tianrun-Yu/LARK

### Agentic Software：把软件从静态代码重构为运行时 agent 决策系统
这篇 position paper 不是一个新 benchmark 或工具，但它把近两年 coding agent 带来的软件形态变化讲成了一个系统化框架。传统软件的决策逻辑主要写在源代码里，运行时按预先定义的控制流执行；agentic software 则把 LLM 和 harness 组成的运行时决策系统作为“软件本体”的一部分。文章用 SWE-bench、EvoClaw、LangChain multi-agent coordination 等证据说明，软件工程对象正在从静态代码扩展到 agent systems、control model、工具环境和人类意图架构。它提出 Agent-as-a-Service 和四阶段路线图，强调未来开发者角色会更多变成 intent architect，而不是逐行代码作者。按本日报标准，它属于 Medium：理论和范式总结较多，但能帮助团队把 harness、工具、memory、evaluation、cost 和 governance 看成软件架构问题。对后训练软件工程的启发是，训练与评测对象不应只是模型输出，而应覆盖 agent runtime 的整体行为和系统边界。
🔗 链接：https://arxiv.org/abs/2606.05608 ｜ 代码：None

### OpenAI GPT-5 免疫学案例：专家把旧实验数据交给模型做机制假设与实验预测
OpenAI 6 月 23 日的这篇官方案例不属于 coding agent，但它是近月新增官方源，且展示了专家工作流里 AI 如何作为机制假设生成器使用。免疫学家 Derya Unutmaz 的实验问题是，T 细胞在低葡萄糖环境和 2-DG 这种葡萄糖类似物环境下为什么会走向不同分化结果；这个问题从 2022 年开始搁置。GPT-5 Pro 分析数据后提出，2-DG 可能干扰 IL-2 蛋白构建，而 IL-2 通常会阻止 T 细胞分化为 Th17，因此 2-DG 等于移除了一个分化屏障。更有意思的是，模型还对一个未公开的 CD8+ T cell / lymphoma killing 实验做出正确预测，说明它不是简单检索互联网答案。按本日报规则它放 Low，因为主题偏生命科学而非软件工程；但它仍有一个可迁移工程模式：旧数据整理、模型提出机制、专家判断 plausibility、再由实验验证。对高风险 agent 工作流来说，这再次强调专家 gate、未公开数据保护、实验复核和责任边界的重要性。
🔗 链接：https://openai.com/index/gpt-5-immunology-mystery ｜ 代码：None

## 🔥 社区热点专栏

### 🔥 大佬观点

**ScaleKit / Ravi Madabhushi：MCP 的问题不是协议本身，而是 schema 暴露策略。**  
ScaleKit 的 benchmark 把“MCP tax”量化出来：同样的 GitHub 任务，直接 MCP 因全量工具 schema 注入导致 4-32x token overhead，且原始远程连接可靠性低于本地 CLI。它值得注意，因为结论不是抛弃 MCP，而是生产 MCP 必须有 gateway、schema filtering 和 progressive disclosure，否则 agent 平台的工具治理会被成本吃掉。🔗 https://www.scalekit.com/blog/mcp-vs-cli-use

**@1996fanrui / Codex issue 讨论：agent runtime 的诊断日志也需要资源预算。**  
Codex SQLite logs issue 的高热度来自一个很具体的工程事故：为了可观测性持久化 TRACE 级日志，却把用户本地 SSD 写入放大到可能每年数百 TB。这个观点对 agent 平台团队很关键：日志、trace、session 和 feedback 数据不是免费副产品，必须有采样、保留、用户开关和写入上限。🔗 https://github.com/openai/codex/issues/28224

### ⭐ 超火仓库/项目

**FeatureBench（LiberCoders/FeatureBench）：社区开始用 feature delivery 质疑 SWE-bench 采购信号。**  
FeatureBench 最近被多篇社区文章重新讨论，原因是它把 frontier coding agent 从 SWE-bench 的高分拉回到 feature-level 交付现实：公开结果里 SWE-bench 70%+ 的模型在 FeatureBench 只有十几个百分点。它解决的痛点是评测分布错配：企业买 agent 不是只为修 isolated bug，而是要让它交付完整功能并保持旧测试不坏。🔗 https://github.com/LiberCoders/FeatureBench

**ContextEcho（Accenture/ContextEcho）：长程 Claude Code 会话漂移开始有可复现 harness。**  
项目虽然 star 不高，但 release 很有信号：它公开真实匿名长会话、25 个身份 probe、Hugging Face per-cell 评测数据和复现实验。它火在解决一个长期被忽略的问题：agent 跑几千轮之后，原来的助手身份、格式契约和安全边界是否还在。🔗 https://github.com/Accenture/ContextEcho

**OpenAI Codex logging fixes：开源 agent runtime 的运维细节成为社区关注焦点。**  
Codex 0.142.0 release 和 #29432/#29457/#29599 修复说明，社区已经不只关心模型是否会写代码，也关心 agent 桌面/CLI 长时间运行时的日志、SQLite、WAL、遥测和资源消耗。这个热点解决的是生产化最朴素的痛点：agent 如果要常驻，就必须像数据库、浏览器和 IDE 一样被做性能/存储治理。🔗 https://github.com/openai/codex/releases/tag/rust-v0.142.0
