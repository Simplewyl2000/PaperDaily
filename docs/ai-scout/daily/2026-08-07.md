## 📝 逐条讲解

### LongHorizon-Harness：用 Manage-Execute-Audit 外循环维持长程任务状态
长程 agent 最大的问题往往不是第一轮不会做，而是做着做着上下文越来越乱，模型把未验证的自我判断当成事实继续推进。LongHorizon-Harness 把这个问题改写成“任务状态管理”问题：Manager 维护原始目标和已验证进度，Executor 每轮用新上下文完成一个边界清楚的小任务，Auditor 只读环境并独立检查结果是否真的成立。只有通过 Auditor 验证的事实才写回持久状态，所以一次失败、一次幻觉式“我完成了”、或者一次上下文刷新，都不会污染后续计划。它不替代 Claude Code、Codex 或 OpenClaw，而是用 AgentAdapter 包住这些已有 agent loop，让原生工具继续执行，外层负责状态、证据和回合边界。公开结果显示，在同一 Qwen 3.7-Plus backbone 和 Claude Code backend 下，WeaveBench PassRate 从 51.8 提到 80.7，Terminal-Bench 2.1 从 69.7 提到 77.2，OSWorld 2.0 binary 从 2.8 到 8.3。它对后训练软件工程的启发很直接：长程轨迹不应只是一条巨大的聊天记录，而应拆成“计划、执行、独立验证、状态更新”的事件流。这样的轨迹更适合筛选、复现和训练，因为每一步是否真的推进了任务有可审计证据。  
🔗 链接：https://arxiv.org/abs/2608.01964 ｜ 代码：https://github.com/AMAP-ML/LongHorizon-Harness ｜ https://lh-harness.pages.dev

### RealReplicaBench：用可复现业务服务副本评测长程 agent 是否能完成真实工作流
很多 agent benchmark 要么是单个代码 issue，要么是问答式任务，和真实企业工作流中“跨浏览器、CLI、文件、API/MCP、表格和文档”的连续操作差距很大。RealReplicaBench 的做法是构造本地可复现的业务服务副本，让 agent 在模拟的 SaaS、commerce、messaging、document 和 operational systems 中真的改变状态。它包含 107 个任务，其中 53 个 CLI、28 个 browser、16 个 file、10 个 API/MCP，并分成 text-only、browser-text-capable 和 vision-required 三类能力切片。每个任务在 fresh container 中运行，并保留 resolved configuration、trajectory、verifier result、artifacts、logs 和 container metadata，评分由 deterministic 或 LLM-assisted verifier 给出。项目还同时展示 OpenClaw 和 Accio 两套 harness 上的模型结果，提醒读者同一任务集也会因为 harness 不同产生差异。工程价值在于它把“真实工作流”做成可重放 mock，而不是直接连生产账号，这能显著降低数据泄漏和不可复现风险。对后训练数据来说，这类 benchmark 能产生高质量的环境状态、工具轨迹和 verifier verdict，是训练多工具 agent 的好原料。  
🔗 链接：https://github.com/Accio-org/RealReplicaBench ｜ 代码：https://realreplicabench.site.accio.ai/

### GDPevo：用规则重组构造企业工作流，评测 agent self-evolution 是否真泛化
self-evolving agent 会把训练任务中的经验写成策略、记忆或工作流，然后在后续任务里复用；难点是分数变高到底是学到了可迁移规则，还是记住了测试集表面模式。GDPevo 用 rule hybridization 处理这个问题：先把 CRM、ERP、finance、healthcare、legal、data-centric 等企业 workflow 拆成原子业务规则，再把部分规则分配给训练任务，最后在 held-out 测试任务中重新组合这些规则。这样如果 agent 在测试任务上提升，至少可以更有把握地说它复用了训练中学到的规则，而不是直接见过同一个任务。V1 release 有 12 个 task groups、120 个任务，每组共享 business environment、5 个 train tasks 和 5 个 held-out test tasks；自动化 pipeline 能在两天内扩到 24 组、240 个任务。实验中 self-evolution 在 held-out accuracy 上最多带来 16.44 个百分点提升，但最强 evolved agent 仍远低于 fully informed oracle 的 91.6%，说明当前 agent 的经验迁移还很不充分。它对 skill evolving 和 trajectory selection 很重要，因为它把“经验是否可迁移”做成了可验证的训练/测试设计。工程团队可以借鉴这种规则分解和重组方式，构建不容易被污染、且能解释泛化来源的 agent 训练任务。  
🔗 链接：https://arxiv.org/abs/2608.03764 ｜ 代码：https://github.com/Prism-Shadow/GDPevo

### DataSpace：异构工作区上的可验证数据分析 agent benchmark
数据分析 agent 的真实难点不是只会写 SQL，而是要在一个混合工作区里找到相关 CSV、JSON、SQLite、Markdown、PDF、视频和图片证据，再把结果整理成完整表格。DataSpace 把这种任务做成 410 个 cross-language task、7,439 个 artifacts、约 15GB 的 benchmark，并作为 KDD Cup 2026 Data Agent Track 的官方评测。它要求 agent 只看到自然语言问题和 task-local workspace，自主发现证据、整合多模态/多格式信息，并输出完整 tabular result。评分不是让 LLM judge 泛泛判断，而是用 frozen gold reference 和 type-aware deterministic evaluator 检查 header、类型、单位和行列匹配。论文还做了 harness comparison：固定 MiMo-V2.5 backbone 时，Grok Build、Claude Code、DataSpace-Agent、Codex、Smolagents 之间最高相差 15.36 个百分点，再次说明 harness 本身会改变 agent 成绩。虽然 DataSpace 不是纯 coding agent benchmark，但它非常贴近数据工程 agent、分析自动化和企业 BI 工作流。对后训练软件工程来说，它提醒我们评测数据 agent 时要保留工作区构成、证据路径、输出表结构和 deterministic evaluator，而不是只保存自然语言最终答案。  
🔗 链接：https://arxiv.org/abs/2608.03451 ｜ 代码：https://github.com/BugMaker-Boyan/DataSpace ｜ https://huggingface.co/datasets/HKUSTDial/DataSpace

### Anthropic Inference Hooks：把 prompt 和 MCP/skill/tool 返回都接入企业 DLP 判定
企业部署 agent 时，最难治理的不是单个聊天框，而是员工会通过 chat、Claude Code、Cowork、MCP connectors、skills 和 plugins 把各种内部数据送进模型上下文。Anthropic 的 Inference hooks 试图把这些入口统一成一个组织级 DLP 检查点：每次 inference request 先通过 signed WebSocket 发给客户自己的 security server，由服务器返回 allow 或 deny verdict，Claude 只有拿到允许才继续生成。更关键的是它也检查工具调用返回值：当 Claude 调用 MCP、skills 或 plugins 得到响应后，响应在进入模型前同样先过 DLP。相比 Claude Code 里本地 client-side hooks，这个机制覆盖更多 Claude Enterprise surface，不需要每个产品分别集成一套安全逻辑。它还支持 shadow mode、role-based exclusions、percentage rollout、timeout 和 failure policy，方便企业先观察再逐步强制执行。对 agent 工程来说，这相当于把“模型是否能看到某段数据”变成了可编程的 runtime policy，而不只是事后审计日志。对后训练轨迹也有意义：哪些 prompt/tool result 被阻断、为什么阻断、agent 如何恢复，都是企业 agent 安全训练和评测的重要标签。  
🔗 链接：https://claude.com/blog/claude-enterprise-inference-hooks ｜ 代码：None

### OpenAI Codex Security CLI：把深上下文漏洞发现、验证和修复放进 CLI/SDK/CI
传统 SAST 或普通 AI code review 往往会产生大量低影响、低上下文的告警，安全团队真正花时间的是判断某个 finding 是否可达、是否有业务影响、应该怎样修。OpenAI 的 `openai/codex-security` 把 Codex Security 做成 CLI 和 TypeScript SDK，让团队可以在本地仓库或 CI 中运行 repo scan、保存 scan history、比较两次扫描结果，并把 findings 按 root cause 关联为 new、persisting、reopened、resolved 或 unknown。README 里还提供 deep mode、workers、subagents、stop-after-no-new、max-discovery-runs 等参数，说明它不是只跑一次静态规则，而是面向多轮探索和验证的 security agent workflow。它支持 ChatGPT 登录、API key、OpenRouter、Fireworks、Bedrock 等 provider 路由，也支持 containerized bulk scans 和共享 knowledge base。HN 讨论中 OpenAI 相关开发者也强调，CLI 不是绕过安全模型 guardrails 的后门，而是把同一 scanner 用到多仓库、历史结果、false-positive tracking、budget controls 和 CI integration。这个项目对 coding-agent eval 很有价值，因为安全 review 需要的不只是“模型指出漏洞”，还要看 threat model、验证环境、修复 patch、结果去重和长期趋势。对后训练软件工程来说，它可能产生更结构化的安全轨迹：发现路径、验证证据、拒绝/权限边界、修复建议和回归检查都能被记录。  
🔗 链接：https://github.com/openai/codex-security ｜ 代码：https://learn.chatgpt.com/docs/security/cli

### firecrawl/anydoc：把 Office/PDF/CSV 等文档转成 agent 可读 Markdown Skill
很多企业知识不在网页和代码里，而在 Word、PowerPoint、Excel、OpenDocument、RTF、EPUB、CSV 和 PDF 里；agent 如果只能读纯文本或网页，进入真实工作流会频繁卡在文档 ingestion。firecrawl/anydoc 的目标很明确：用 Rust 把这些文件统一解析成干净的 GitHub-Flavored Markdown，并提供 Node、Python、WASM 和 CLI 绑定。它最适合本日报关注的点是 Agent Skill：`npx skills add firecrawl/anydoc` 后，Claude Code、Codex、Cursor、OpenCode 等 agent 可以在本地遇到 office documents 时自动用 CLI 转换。相比把文件上传到外部 OCR/解析服务，anydoc 的浏览器 demo 和本地 CLI 路径更适合隐私敏感场景；同时它的 benchmark 覆盖 100 个真实文档、14 种格式，报告 median 4.4ms、质量分 81，高于多个常见转换器。它不是一个模型或 benchmark，但它解决的是 Agent-Friendly Software 中非常实际的一层：把传统办公文件变成 agent 可检索、可引用、可 diff 的文本。对后训练数据工程来说，稳定的文档到 Markdown 转换能减少输入格式噪声，让 agent 轨迹更容易回放和筛选。这个项目 8 月初新建后已超过 8k stars，说明社区对“agent 能读公司文档”的底层工具需求很强。  
🔗 链接：https://github.com/firecrawl/anydoc ｜ 代码：https://firecrawl.github.io/anydoc/

### FutureBridge-OPD：先看未来轨迹，再决定老师指导是否值得蒸馏
On-policy distillation 的优点是学生模型在自己会访问的状态上接受老师指导，减少训练和部署之间的分布差距；但多轮 agent 任务里，学生前几步偏掉后，后面的状态可能已经远离老师指导有效的区域。FutureBridge-OPD 的直觉是，不能只看当前状态下老师和学生是否分歧，还要看“如果此处插入老师的一小段指导，学生后面几步会不会真的走向更好的轨迹”。它在 high-disagreement state 执行一个 teacher bridge，然后让同一个 student 从原始状态和 bridge 后状态各继续若干步，再由 teacher preference 判断哪条 future trajectory 更值得训练。只有当 bridge 后续确实增加正向 distillation signals 时，这段老师指导才被保留。实验在 ALFWorld、WebShop 和 ScienceWorld 上，用 Qwen3-32B teacher 到 Qwen3-1.7B student，平均比 vanilla OPD 高 16.6 点、比 TCOD 高 7.6 点。按 Medium 收录，是因为它更偏 agentic OPD 算法，而不是 coding-agent 专属工程；但它对 trajectory selection 的启发很强。工程上筛选 agent 轨迹时，也应验证某个“纠偏步骤”是否改善后续执行，而不是只看局部动作是否像老师。  
🔗 链接：https://arxiv.org/abs/2608.01953 ｜ 代码：https://github.com/ChenChiShui/FutureBridge-OPD

### CRISP：从成功搜索轨迹反向标注关键工具步骤，减少冗余交互
Deep search agent 常见的问题是工具调用越来越多：重复搜索、打开无关网页、保存无用 observation，最后虽然答对了，但轨迹又长又贵。直接惩罚工具次数会带来另一个问题：模型可能少用关键证据工具，变得省但不准。CRISP 用 Backward Evidence Induction 从最终答案往回看一条成功搜索轨迹，判断每个 tool-interaction step 是否提供或保留了最终答案所需证据。然后它把这些 step-wise judgments 蒸馏成一个较小的 critical-step recognizer，让系统能一次性分析整条轨迹，区分“该保留的证据步骤”和“可删的冗余步骤”。训练时 efficiency-aware reward 只作用在成功 rollouts 上，避免把失败轨迹里的短路径误当成好路径。论文在 BrowseComp 和 HLE-Verified 上保持最终准确率的同时，把平均交互轮数分别减少 15.1% 和 33.2%。虽然它聚焦 search agent，而不是 coding agent，但方法论很适合迁移到软件工程：从最终通过测试或 verifier 的轨迹中反向识别真正推进任务的 grep、test、edit、debug 和 browser 步骤。对后训练数据工程来说，成功轨迹也要去冗余，关键是别删掉验证和证据收集步骤。  
🔗 链接：https://arxiv.org/abs/2608.01867 ｜ 代码：None

### Claude Enterprise 成本可见性与控制：把 skills/connectors/artifacts 成本纳入治理面
长程 agent 的成本管理不能只看总 token，因为一次任务可能同时用了不同模型、skills、subagents、plugins、MCP connectors 和 artifacts，每一层都可能是成本和价值的来源。Anthropic 这篇成本可见性文章面向 Claude Enterprise 管理员，重点是把“谁用了多少 Claude”升级成“哪个团队、哪个模型、哪些 skills/connectors/artifacts 产生了多少成本”。它提到 model entitlements 和 defaults 可以分层控制：把最强模型留给最难任务，把普通团队默认引到更便宜模型，减少无意识过度使用。硬 spend caps、75%/90% 管理员告警、用户侧通知、以及 Admin API 让成本治理可以进入脚本和 FinOps 流程，而不是月底看账单。Analytics API 还能把 Claude usage 拉进 Datadog Cloud Cost Management、CloudZero 等现有云成本工具，把 AI spend 和普通云资源一起看。对 agent 工程来说，这类可见性非常关键，因为高成功率但不可控成本的 agent 很难规模化部署。对后训练软件工程来说，成本也应成为轨迹标签：同样成功的两条轨迹，哪个 skill、connector 或模型 routing 更省，应该能被训练和 eval 系统看见。  
🔗 链接：https://claude.com/blog/a-guide-to-cost-visibility-and-control-in-claude ｜ 代码：None

### OpenAI Learn/Teach plugins：ChatGPT Work 与 Codex 的教育场景 agent workflow

### Anthropic + Millennium digital risk analyst：金融风险分析 agent 的可审计部署案例

## 🔥 社区热点专栏

### 🔥 大佬观点

**Simon Willison / Claude Code fireside chat：真正难的是持续积累 eval，而不是只换更强模型。**  
Simon 与 Anthropic Claude Code 团队的 Cat Wu、Thariq Shihipar 访谈中，Cat 强调新模型能否替换旧模型，依赖长期积累的外部与内部 eval suite；除了能否修 bug、跑测试，还要为用户讨厌的行为建立 behavioral eval。这个观点值得注意，因为它把 coding-agent 质量改进从“模型升级”拉回“任务定义、完整代码库、行为回归和用户反馈闭环”。🔗 https://simonwillison.net/2026/Jul/21/cat-and-thariq/

**HN / Codex Security 讨论：安全 agent CLI 的价值在于组织级扫描、历史结果和 CI，而不是绕过 guardrails。**  
OpenAI 相关开发者在 HN 上解释，Codex Security CLI/SDK 使用同一 scanner，但更适合跨多仓库长期运行：org-wide scans、dedup、false-positive tracking、budget controls 和 CI integration。社区也提醒它不会自动绕过模型的网络安全拒答，真正的工程问题是如何在授权防御场景下保存证据、降低噪声并让发现进入修复流程。🔗 https://news.ycombinator.com/item?id=49089755

### ⭐ 超火仓库/项目

**firecrawl/anydoc：8 月 3 日新建，约 8.6k stars，把混合办公文档 ingestion 做成 Rust CLI + Agent Skill。**  
它火在解决一个非常朴素但高频的痛点：agent 要处理企业任务时，经常先要读 docx、pptx、xlsx、pdf 等传统文件。anydoc 用本地 Markdown 转换和 agent skill 分发降低了接入成本，也减少了把敏感文件送到外部解析服务的需求。🔗 https://github.com/firecrawl/anydoc

**RealReplicaBench：8 月 2 日创建，约 1k stars，用本地业务服务副本评测 107 个长程 workflow。**  
它的热点不是单纯 star 数，而是把 Gmail、Shopify、Google Docs、Notion、Stripe、Jira、Amazon SP-API 等业务表面做成可复现 mock，让 agent 能在不碰生产账号的情况下完成状态变更任务。对评测工程来说，这比“真实网站 live test”更安全，也比纯文本任务更接近企业自动化。🔗 https://github.com/Accio-org/RealReplicaBench ｜ https://realreplicabench.site.accio.ai/

**AMAP-ML/LongHorizon-Harness：8 月 4 日创建，Hugging Face paper 热度高，主打长程 computer-use verified state。**  
它火在把 context rot、错误自评和任务状态漂移直接拆成 Manager / Executor / Auditor 三个角色，而不是继续延长单个 agent session。对长程 desktop+CLI agent 来说，这种“只把独立验证过的进度写回状态”的设计非常容易被其它 harness 借鉴。🔗 https://github.com/AMAP-ML/LongHorizon-Harness ｜ https://arxiv.org/abs/2608.01964

**openai/codex-security：约 9k stars，OpenAI 安全扫描 CLI/SDK 从研究预览走向可集成工具。**  
它火在命中开发团队的真实瓶颈：AI 生成代码越来越多，安全审查必须能批量扫描、多仓库跟踪、比较历史 findings，并把结果接进 CI。相比一次性“让模型看看有没有漏洞”，它更像安全 agent 的工作台和长期记忆层。🔗 https://github.com/openai/codex-security
