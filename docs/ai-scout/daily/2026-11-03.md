## 二、逐条中文讲解

### 1. From Weeks to Hours: Fast and Principled SFT Data Generation for Reasoning LLMs

合成推理数据时，通常先让教师模型把很长的轨迹写完，再用另一个模型按难度和多样性丢掉大部分。一条轨迹可以有几万个 token，算力主要花在最后不会进训练集的文本上。

SFTProbe 改成看预训练模型附近的损失盆地。做一次很短的低秩适应之后，只在每条轨迹 5% 的 token 上算损失：损失形状怎么聚类，用来代表多样性；拐弯处的损失，用来代表难度。同一个学生模型上，这样得到的 5,000 条追上了用 89,000 条训练的 OpenThinker-7B。论文图里的整理成本是 3.3 对 176 个 H100 GPU 日。7,500 条再高 2.5 个准确率百分点，成本是 4.3 个 GPU 日。代码和数据放在项目页。物理实验在正文里写成接近一枚能拿国际物理奥赛银牌的模型，摘要写成超过，这里按正文，不把“超过”当成结果。

推理轨迹的难度和多样性，可以在写完之前用损失盆地的边界估出来。

**链接：** [原文](https://arxiv.org/abs/2611.00554) · [项目](https://bigml-cs-ucla.github.io/SFTProbe-page/)

### 2. From Apparent Search Gains to Selection Failures

测试时搜索一涨分，很容易把功劳记到“用了树”或“投了票”上。各组的提示、后处理和选择规则并不相同，多出来的正确率可能只是某一步换了写法。

这篇把结构化工作流规划拆成三笔账：有没有生成出正确流程，结构校验有没有把它留下，最后有没有选中它。DisasterBench 上，名义上的树搜索其实是把整条流程一次采样完，并不按中间节点改后面的扩展。换上同一套扩展提示做独立采样，GPT-4o-mini 在 183 题里发现 154 条正确流程，树搜索是 153 条。他们检查的候选池里，结构校验没有删掉最后一条正确流程。一个读工具说明的验证器修回 90 次投票错误，同时推翻 175 个本来选对的决定。抽查 60 个投票失败，57 个赢的候选在工具选择或信息流上确实错了。另一组模型是 Qwen3.5-9B。代码仓库本次检索时 1 star。

这组树搜索多发现的正确流程，独立采样换上同一提示就能复现。正确流程主要丢在投票，不丢在结构校验。

**链接：** [原文](https://arxiv.org/abs/2611.00579) · [代码](https://github.com/TamuChen18/Found-but-Not-Chosen)

### 3. Skill++: Towards Lifelong Agents via Routing-Aware Skill Refinement

技能库变大以后，路由只看名称和描述，正文要等选中才加载。新技能的名字和旧技能太像时，路由器会改选新的。旧技能和路由模型都没有变，以前能选对的查询却失败了。公开技能的描述还经常和正文对不上。

Skill++ 不重训路由器，也不做逐条标注。每来一条新技能，只重写它的名称和描述：正文实际能做什么，和最接近的旧技能差在哪里，哪些相近的事明确不做。库长到 731 条、分十次加入时，所需技能全部被选中的查询从 36.4% 升到 76.3%。放进 Codex 命令行，87 条技能、150 个查询上，先点名五个技能的命中率，GPT-5.6 Luna 从 33.3% 到 77.3%，GPT-5.6 Sol 从 82.0% 到 88.0%。同一批隐藏测试只提高 4.0 和 0.7 个百分点。论文没有给出代码仓库。

改描述能把该选的技能选中。隐藏测试几乎没有一起抬起来。

**链接：** [原文](https://arxiv.org/abs/2611.00544)

### 4. To Jev or Not to Jev: When Can System-1 Decision Models Replace LLM Judges?

生成式裁判要先把理由写出来，所以贵。另一类模型只做一次前向，直接给是非、选项或分数的概率。便宜会不会更脆，并不是这种架构自动带来的。

作者按事先写好的协议选了 14 个一次前向模型，对上四个生成式裁判，覆盖 11 个已有的裁判基准。其中 5 个在全部两两比较和四选一上，与不开推理的 GPT-5.6 统计上分不出差别。每个提示先有一份参考答案时，11 个模型在 JudgeBench 上到 90.3%–93.4%，与开思考的 Claude Opus 5.5 和开推理的 GPT-5.6 分不出差别。在 PPE 的 16 选一上，这些有参考答案的一次前向裁判对齐开推理的 GPT-5.6，单题成本大约是十六分之一。在被评回答末尾加一句指示，5 个模型只翻掉 0%–5% 的正确判决，另外 9 个翻掉 17%–49%。不含裁判题的两份榜，对裁判准确率的相关系数是 0.95–0.96。论文没有给出代码仓库。

一次前向可以顶上生成式裁判。抗提示注入是单个模型的性质，不是这一类设计的通性。

**链接：** [原文](https://arxiv.org/abs/2611.00505)

### 5. Scaling Git at OpenAI

编码代理让同一个人同时推很多分支，每次推送又让多台机器来取同一段历史。服务如果要求所有分支在任一时刻是同一张快照，不相干的推送就要在同一个协调点上排队。OpenAI 的单仓因此变慢，合并可靠性有时低于 90%。

Pando 仍说 Git 协议，但不再为每个客户端现算一份独有的包，也不再保证一次读取看到全部分支的同一时刻。推上来的包原样放进对象存储，元数据只给这一条分支记下新尖端和它依赖的更早版本。默认只向推送方广播主干，打出来的包就不依赖其他功能分支，后来的人只要有主干就能整包复用。取回时在线回一个空包，字节从缓存拉。他们的单仓里，这种包的中位数不到 20 KiB。上线后中位推送延迟降了将近 80%，一天可以送出近 1 PB；有一个小时超过 57 TB，其中超过 99% 来自本机磁盘缓存。Pando 本身还没有公开。文中的仿真曲线标明是教学模型，不是生产基准。

并行推分支时，全库同一快照是瓶颈。按单条分支排序并复用推送包，中位延迟降了将近八成。

**链接：** [原文](https://openai.com/index/scaling-git-at-openai/)

### 6. Do Social Influence Pressures Move LLM Agents?

审计里的人会屈从上级、同事和客户。若模型的反应不同，把对人的复核规定直接套到模型上，回路会装错。

模型先做分析性复核里的估计，再收到一句没有新证据的反对。反对来自项目合伙人、同事、另一家事务所的复核人，或客户的财务总监。十二个设置里，合伙人的反对在九个设置上显著改变均值。同事的反对在未校正时有七个设置显著，Holm 校正后剩三个。财务总监把估计往管理层的数字上推时，GPT-6 各设置、Claude Opus 5.5 和 Sonnet 5.5 没有一次把估计改低，合并比例的 95% 置信区间上界低于 2%。相对等长却没有内容的句子，职业诱导让移动变少，模型还会把雇佣诱导说成对独立性的威胁。两个 Qwen 设置在无人施压时漂移更大，作者要求谨慎解释。这是一道审计估计题，不是软件工程任务。

没有新证据的上级反对，仍会改模型的估计。前沿模型几乎不向客户让步，职业诱导让它们更不肯改。

**链接：** [原文](https://arxiv.org/abs/2611.00508)

### 7. Roz: A Taste Test for World Model Latents

潜空间世界模型的重建误差下降，只说明预测的下一帧更像，不说明它记住了质量、摩擦或弹性。这些量可以几乎不改变画面，却改变物体之后怎么动。

Roz 用成组短片比较潜变量的距离：两段揭示同一物理事实的片子，应当近于一段终点画面相似、但揭示了不同事实的片子。颜色和位置是正对照，合理的距离函数应该通过。只看最后几帧的 Cosmos 和 FastWAM，在它们看不见那段历史的项目上接近 0，和实验设计一致。弹跳扫描里，多个模型的通过率大片是 0。作者自己的 PantheonWM 随训练步数大致变好，但这并不一定跟着重建均方误差变好。整套共 1,734 个场景，打分只需要帧、潜变量和一个距离。论文给出的代码地址本次检索无法打开。

画面更像，不能当成潜变量记住了弹性。要故意做“看起来像、物理不同”的对照。

**链接：** [原文](https://arxiv.org/abs/2611.00612)

### Trending Open-source Projects

#### 1. lyramakesmusic/neuron-explorer

想知道一个小模型里某个神经元往上推或往下推之后，生成会怎么变，通常得自己写扫描脚本，而且中间的 rollout 很容易只留一个摘要。

neuron-explorer 对 Qwen3.5-4B 每一层的 MLP 神经元做向上和向下的推动，把每次 rollout 都留下来，再铺到模型的三维视图上。点开一个神经元可以看到不同剂量下的生成、与随机方向对照后的词簇、以及它在网页文本上激活最高的上下文。仓库带有已经算好的缓存；本机加载模型后可以做实时的引导对话。它也能把仓库注册成 MCP，让已登录的 Claude 命令行来读这些结果。仓库 10 月 21 日创建，本次检索时 1,859 star、227 fork。星数是创建以来的存量，没有单独的日增量。

它把“推动一个神经元并保住全部生成”收成可以浏览的实验记录。证据只覆盖这一个 4B 模型，不能当成对大模型机制的结论。

**链接：** [GitHub](https://github.com/lyramakesmusic/neuron-explorer)

#### 2. OpenBMB/MiniCPM-OCR

文档进了代理的上下文之后，识别错的表格和公式会一直往下传。只看整页识别率，不知道哪一块该交给人再看。

MiniCPM-OCR 在识别模型之外放了一个约 20 亿参数的正确性模型。输入是页面图像和一份识别结果，输出 0 到 1 的质量分，用来留下可靠结果并标出要复核的区域。仓库给出的 JevOCRBench 上，AUROC 乘以 100 是 93.6，高于 JEV-35B-A3B 的 90.1，接近 Qwen3.5-397B-A17B 的 93.8。换四种解析器的输出，这个数在 91.9 到 93.4 之间。这些是项目自己的基准，不是独立复测。仓库 10 月 27 日创建，本次检索时 773 star、53 fork。

它把“这段识别要不要信”收成一个小模型的分数。分数高不等于下游任务已经做成，基准也还是他们自己的。

**链接：** [GitHub](https://github.com/OpenBMB/MiniCPM-OCR)

#### 3. l0ng-ai/openidea

代理和人一起改一个大仓库时，IDE 把时间和内存花在自己的启动与索引上。换一套更轻的编辑器，又往往丢掉熟悉的快捷键、调试和 Git。

OpenIDEA 用 Rust 做核心，把 IntelliJ 式的键位、工具窗口和全局搜索放到原生应用里，并带编辑、代码洞察、调试、Git、终端、数据库和 HTTP 客户端，声称覆盖 60 多种语言。仓库自己的对照是打开约 770 个文件的 freqtrade：窗口出现 0.9 秒对 3.1 秒，CPU 安静下来 1.1 秒对 13.2 秒，内存 169 MB 对 2011 MB。机器是一台 32 核、62 GB 内存的 Windows 11。作者写明 IntelliJ 对 Python 的分析更深，两边的“就绪”不是同一份工作，并给出了可在本机重跑的脚本。仓库 10 月 21 日创建，本次检索时 5,053 star、404 fork。这是项目自己的一次测量，不是独立复测。

它把更低的启动和内存做成可替换的编辑器。一次仓库、一台机器上的对照，不能当成所有语言都已经同样快。

**链接：** [GitHub](https://github.com/l0ng-ai/openidea)
