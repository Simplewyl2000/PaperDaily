## 📝 逐条讲解

### Supabase Evals：用真实 Supabase 栈评测 Claude Code、Codex、OpenCode
很多产品团队现在已经让 coding agent 写数据库 schema、修 RLS policy、调 Edge Function，但之前只能靠人工试几个案例来判断“agent 用我们的平台好不好”。Supabase Evals 把这个问题做成了开源 benchmark：每个场景包含 agent 看到的 prompt、起始本地/远端状态、scorer，以及是否属于公开 benchmark 或内部 regression suite。它不会只检查 diff，而是启动接近托管环境的 Supabase stack 和本地 CLI 项目，让 agent 真实调用 Supabase CLI、MCP server 或工具表面。评分同时使用确定性检查和 LLM-as-judge，并允许一次 retry，结果可以按 product、topic、stage、agent 和 skill 开关过滤。最值得关注的是它把任务分成 build、deploy、investigate、resolve 等阶段：模型在常规构建任务上可能已经很强，但在读日志、追副作用、定位部署失败时仍需要更好的 skills 和 harness。Supabase 还说明这套系统同时支撑公开 leaderboard 和每日内部 regression，意味着 eval 不只是营销页，而是产品发布门禁的一部分。对后训练软件工程来说，这类平台级 eval 很有价值，因为它把真实支持工单、GitHub issue、产品工具、执行环境和评分证据连接成可回放轨迹。
🔗 链接：https://supabase.com/blog/introducing-supabase-evals ｜ 代码：https://github.com/supabase/evals

### Qwen-UI-Agent：把 GUI 操作、CLI 执行和 DeepSearch 统一到同一训练/运行时
传统 computer-use agent 往往被分成几类：手机 agent 点屏幕，浏览器 agent 点网页，桌面 agent 看截图，coding agent 跑 CLI；这些能力如果分开训练和运行，很难处理真实跨设备长流程。Qwen-UI-Agent 的目标更像“跨平台执行器”：同一个 agent 可以在 mobile、computer-use、web 和 DeepSearch 环境中行动，并把 GUI 操作与 CLI 执行统一到一个 action space。报告里一个关键工程点是 batched actions，模型可以在一个 turn 内产出多步操作，减少逐步点击的往返成本。它还描述了 AutoResearch-style data flywheel：agent 自动构造任务和环境、诊断失败，再规划下一轮数据生成和训练迭代。训练侧支持超过 100 turn 的在线 RL，并用超过 10,000 个并发环境加速 rollout，这说明重点不只是模型结构，而是环境、数据、评测和运行时的整体系统。公开结果显示它在 MobileWorld、MobileWorld-Real、AndroidDaily、OSWorld-Verified、WebArena 等多类 benchmark 上有竞争力。对本日报关注的 Agent-Friendly Software 来说，Qwen-UI-Agent 的启发是 GUI-to-Agent 不应只靠截图点击，而要把 GUI、CLI、搜索、状态化服务和失败记忆放进同一 harness。
🔗 链接：https://arxiv.org/abs/2607.28227 ｜ 代码：https://tongyi-mai.github.io/Qwen-UI-Agent/ ｜ https://github.com/Tongyi-MAI/MAI-UI

### BackendForge：用 OpenAPI 合约和黑盒 HTTP 测试评测端到端后端生成
很多代码评测还停留在修一个函数或一个 issue，但真实后端开发要生成能启动、能部署、能处理状态和权限的完整服务。BackendForge 把任务设计成 56 个 contract-defined backend generation tasks，每个任务来自真实开源应用改写，并提供自然语言规格和 OpenAPI contract。agent 必须生成 Dockerized service，最终只通过黑盒 HTTP tests 来评估，而不是让评分器直接读内部实现。它的评测构造也很有意思：test agent 提出规格内的测试，code agent 修 reference service，二者共同强化 oracle，目标是在不加入隐藏需求的前提下发现服务级缺陷。结果显示，GPT-5.5 在 base oracle 下能过 55.4%，但在 final oracle 下只有 28.6%；Claude Opus 4.7 也从 58.9% 掉到 17.9%。这说明当前 agent 能让单个 endpoint “看起来能用”，但常在状态一致性、授权、级联副作用和错误处理上失败。对后训练软件工程来说，BackendForge 提供了一种很好的 verifier 形态：用合约约束任务边界，用黑盒执行检查行为，再用 oracle co-evolution 提高测试强度。
🔗 链接：https://arxiv.org/abs/2607.11042 ｜ 代码：None

### ContextPilot：轻量 explorer + 工具化记忆，训练 agent 先找对代码上下文
仓库级任务的最大成本之一是“找上下文”：agent 要读哪些文件、追哪些符号、记住哪些中间发现，常常比最终写代码更难。ContextPilot 把这个流程拆成 explorer-generator 两段：轻量 explorer model 负责高效探索仓库并收集相关上下文，大模型 generator 只基于收集到的上下文生成最终答案。为了避免 explorer 的历史越滚越长，它提供 tool-based memory mechanism，定期把探索记录压缩成可管理的文字记忆。训练上先用大模型专家 rollout 做 cold-start distillation，并通过 rejection sampling 只保留能导向正确答案的高质量轨迹；再用 RL 优化 explorer 的探索和 memory update 行为。它的过滤规则很工程化，例如剔除 malformed tool call、过长低效轨迹，以及上下文超过阈值却不调用 memory update tool 的轨迹。换句话说，这篇工作不是简单说“给模型更多上下文”，而是训练一个专门负责找上下文、维护记忆、控制探索成本的小 agent。对后训练数据工程来说，它直接触及 trajectory selection：成功轨迹也要看是否读了正确代码、是否过度探索、是否及时沉淀记忆，不能只看最终回答。
🔗 链接：https://shuzhenggao.github.io/files/contextpilot.pdf ｜ 代码：None

### Atlassian RLVR：用可验证奖励训练小模型稳定调用 Jira / Confluence API
企业 SaaS API 的难点不在于模型会不会生成 JSON，而在于它是否能按正确顺序读写、填对嵌套参数、处理 parent-child 关系，并在完成后及时停止。Atlassian workflow 这篇 RLVR proof of concept 把问题收窄到 Jira REST v3 和 Confluence v2 的五个合成环境。它不用 live API、人工标签或 learned judge，而是根据 tool-call trace 本身计算奖励，例如是否读 before write、是否调用正确 endpoint、参数是否完整、是否重复创建、是否正确停止。训练上使用 GRPO，让 Qwen3-1.7B 和 Qwen3.5-4B 这类小模型直接在 schema-faithful synthetic environments 中学习。结果显示，在四个非退化场景上，RL 后平均 reward 从 4B baseline 的 0.35-0.92 提升到 0.95-1.00，其中 Confluence page creation 从 0.35 到 1.00。它的局限也很清楚：手写 reward 很难扩展到所有 API，而且一个 ticket-transition 场景 reward 过饱和。对后训练软件工程的价值在于，它把“工具调用是否正确”转成程序化 reward，为 API agent 的 SFT/RL 数据构造提供了可复用模板。
🔗 链接：https://arxiv.org/abs/2607.01465 ｜ 代码：None

### Gemini API Managed Agents：3.6 Flash、环境 hooks 和预算控制进入托管 agent
托管 agent 的问题通常不在于能不能跑代码，而在于团队如何在 sandbox 中审计、阻断、限额和定时运行这些动作。Google 7 月 28 日的 Managed Agents 更新把 Gemini 3.6 Flash 设为默认模型，同时加入 environment hooks，让开发者能在 agent 每次 tool call 前后执行脚本。这个机制很像软件工程里的 pre-commit / post-test hook：可以 lint 工具调用、阻止危险命令、记录审计日志，或把特定行为转成告警。更新还加入预算控制、scheduled triggers 和 free tier，让 managed agents 更像成本可控的后台 worker，而不是一次性实验。它的重要性在于把 agent runtime 的治理能力下沉到平台层，开发者不必另搭一套外部 orchestrator 才能做基本门禁。对后训练软件工程来说，hook 事件、阻断原因、预算触发和 sandbox trace 都是高质量轨迹元数据。按 Medium 收录，是因为它偏平台能力更新，但对真实 agent lifecycle 工程非常实用。
🔗 链接：https://blog.google/innovation-and-ai/technology/developers-tools/expanding-managed-agents-gemini-api-3-6-flash-hooks/ ｜ 代码：None

### Agent Security Harness v3.8.1：把 MCP / A2A / x402 等协议攻击做成 CI 安全门
随着 agent 通过 MCP、A2A、L402、x402 等协议访问工具、服务和支付通道，安全测试不能只看模型会不会拒答。Agent Security Harness v3.8.1 把协议层攻击做成可跑的测试集合，覆盖 MCP tool discovery 完整性、恶意 tool registration、capability escalation、A2A 通信、支付协议 recipient manipulation 和 session theft 等场景。它宣称包含 342 个测试，并提供 GitHub Action，把安全扫描结果变成 CI gate。项目还把部分结果映射到 NIST、AIUC-1 和 EU AI Act readiness，这个合规叙事需要谨慎看待，但“把协议攻击纳入回归测试”本身方向正确。可信度按 Low 标注，是因为仓库星数低、项目来源不如 OWASP 或大厂，很多覆盖声明仍需独立验证。即便如此，它提醒团队：agent 安全 harness 应覆盖工具协议、授权边界、返回内容注入和支付/执行副作用，而不是只跑 prompt jailbreak。对后训练数据工程来说，安全失败轨迹必须记录在哪个协议层、哪个 tool schema、哪个授权条件下触发。
🔗 链接：https://pypi.org/project/agent-security-harness/3.8.1/ ｜ 代码：https://github.com/msaleme/red-team-blue-team-agent-fabric

### FutureAGI：读 coding-agent 榜单时必须把模型分数拆成 harness 分数
很多团队采购或选型时会直接看某个 SWE-bench / SWE-bench Pro 分数，但不同页面的分数可能来自完全不同的 harness、预算和评分设置。FutureAGI 这篇文章的核心提醒是：同一个模型如果经过不同 harness，分数和成本都可能发生显著变化，因此要先问“这个分数是谁、用什么运行时、在什么成本约束下跑出来的”。它用 Claude Opus 4.5 在 SWE-bench Pro 上的多个结果做例子：标准化 scaffold 和 vendor 自家 harness 的分数并不等价。文章还提到 Princeton HAL 一类共享命令与成本控制的思路，强调只有固定 evaluation harness，模型差异才更容易解释。它不是新 benchmark，但很适合作为评测读数指南，因为最近一周社区里 Supabase Evals、BackendForge、Scaffold Effect 等内容都指向同一个结论。工程上，任何 leaderboard 都应附带 harness spec、工具接口、上下文策略、预算、失败样例和任务质量审计。对后训练软件工程来说，这意味着训练数据来源也不能只写模型名，必须保留 harness provenance。
🔗 链接：https://futureagi.com/blog/coding-agent-harness-benchmark/ ｜ 代码：None

### Phil Schmid：Harness is the Dataset，把轨迹采集视为 agent 竞争壁垒
Phil Schmid 这篇文章把 agent harness 讲成包裹模型的基础设施：提示预设、agent 管理、状态、上下文、工具、约束、成本和验证都属于这个层。文章最值得注意的一句话是 “The Harness is the Dataset”：竞争优势不再只是 prompt，而是 harness 捕获的失败轨迹、上下文漂移、长程疲劳和工具使用证据。这个观点对团队很实用，因为很多人想马上 fine-tune 模型，却没有先把运行时里的失败原因记录清楚。文章建议保持 harness 轻量、模块化、可删除，因为模型能力会快速变化，硬编码复杂控制流可能很快过时。更稳妥的做法是提供强原子工具、guardrails、重试和验证，让模型承担计划，但把关键证据留给系统。它也把 context durability 视为下一阶段瓶颈：长程 agent 什么时候开始忘规则、误用旧上下文、停止验证，需要 harness 捕获并回流训练。对后训练软件工程来说，这正好对应数据飞轮：失败不是噪声，而是下一轮 eval、skill、tool 和训练样本的来源。
🔗 链接：https://www.philschmid.de/agent-harness-2026 ｜ 代码：None

ECC 最近继续推进 OpenCode agent setup，补齐 harness-optimizer、loop-operator、语言 reviewer 等 agent prompts，说明社区正在把 skills、hooks、MCP、rules 和多宿主适配做成可同步资产。它火在解决“同一套工程约束如何跨不同 coding agent 复用”的痛点，但也要注意这种超大配置仓库会成为新的供应链和提示污染入口。🔗 https://github.com/affaan-m/ECC

**supabase/evals：公司级真实环境 benchmark 开源后快速活跃，8 月 2 日仍有推送。**  
虽然当前约 82 stars，不属于纯 star 爆炸型项目，但 Supabase 背书和真实 stack 执行让它在 eval 圈信号很高。它解决的是平台团队的真实痛点：不是问“哪个 agent 最会写代码”，而是问“哪个 agent 在我的产品工具、CLI、MCP 和错误模式下能稳定完成任务”。🔗 https://github.com/supabase/evals ｜ https://supabase.com/evals

**Tongyi-MAI/MAI-UI + Qwen-UI-Agent：约 1.88k stars，GUI agent 从单点点击走向跨平台 runtime。**  
Qwen-UI-Agent 热在把 mobile、desktop、browser、DeepSearch 和 CLI action 放进同一报告与项目页，配合长程 RL 和并发环境 rollout。它解决的真实痛点是，agent 面对传统软件时不能只靠视觉点击，必须同时拥有命令接口、状态化服务、搜索和失败回流。🔗 https://github.com/Tongyi-MAI/MAI-UI ｜ https://tongyi-mai.github.io/Qwen-UI-Agent/
