## 📝 逐条讲解

### KAT-Coder-V2.5：把 agentic coding 后训练做成可执行环境与轨迹工程
很多 Code LLM 后训练论文会说自己用了更多代码数据或更多 agent 轨迹，但真正卡住工程落地的往往是环境能不能复现、测试能不能运行、轨迹质量能不能被筛掉。KAT-Coder-V2.5 的报告把 agentic coding 能力明确当成系统工程问题，而不只是模型规模问题。它的 AutoBuilder 会用 agent 自动重建多语言仓库环境，把每个 SWE 样本整理成任务描述、执行环境和 verifier 三件套，并用 fail-to-pass 与 pass-to-pass 测试给出可执行验证信号。更重要的是，它不只保留最终通过的轨迹，而是评估探索、定位、设计、编辑、验证和恢复等过程，把“能过但过程很差”的轨迹删掉，同时把接近成功的 near-miss failure 重新加工成有信息量的数据。KwaiClawEnv 则把 Service、Task、Eval 分层，用来合成跨工具、跨服务、长程推理的 agent 轨迹。它的启发非常直接：Code LLM 后训练的数据工程应该先建设可复现环境和过程质量门，再谈 SFT 或 RL。对我们关注的 trajectory selection 来说，这类 process-aware pipeline 比单纯 pass/fail 更接近生产质量控制。
🔗 链接：https://arxiv.org/abs/2607.05471 ｜ 代码：None

### CurateEvo：让数据清洗策略根据失败轨迹自动演化
传统 agent 后训练流水线通常先写一套固定清洗规则，再把原始轨迹变成 SFT 数据或 RL 任务；问题是模型能力和失败模式会不断变，固定规则很快就跟不上。CurateEvo 的核心想法是把“数据清洗策略”本身写成可执行代码，并让它根据 held-out development set 里的失败轨迹不断改写。每个 epoch 中，当前策略会把固定原始语料转成 SFT 数据、RL 数据和 inference-time memory bank；随后系统诊断反复出现的失败模式，决定要增强、过滤、改写还是压缩哪些训练片段。它分两步优化：先提升效果，确保数据针对真实失败；再提升效率，用 cost-aware objective 剪掉冗余或低价值 turn。实验覆盖 ACEBench-Agent、BFCL-V4 和 tau2-Bench，在有标签和 wild-data 设置下都比旧方法高 3.2 或 2.7 个平均分。它真正新在把 curation 从“人写的一次性预处理脚本”变成了可迭代的 agent 工程组件。对后训练软件工程来说，这提示我们以后应该版本化清洗策略、失败诊断和被剪掉的数据，而不只保存最终训练集。
🔗 链接：https://arxiv.org/abs/2607.06140 ｜ 代码：None

### OpenAI GPT-5.6 API Runtime：Programmatic Tool Calling + Multi-agent beta
OpenAI 7 月 9 日把 GPT-5.6 家族推到 GA，表面上是 Sol、Terra、Luna 三个模型层级，工程上更值得看的其实是 Responses API 里的新 runtime 原语。Programmatic Tool Calling 允许模型写轻量 JavaScript，在隔离的 hosted runtime 里协调工具调用、循环处理中间结果、过滤大输出，再把压缩后的结果交回模型。这个设计解决了工具型 agent 的一个老问题：每个工具结果都塞回上下文，会增加 token、延迟和上下文污染；让程序先处理可机械处理的部分，模型只看关键证据。Multi-agent beta 则让 root agent 能 spawn、message、wait、interrupt 子代理，并由 root 负责综合答案，相当于把 ultra 模式背后的并行 agent 原语暴露给开发者。官方迁移指南还强调 persisted reasoning、explicit prompt caching、max/pro mode、reasoning effort 校准和代表性任务评测，说明模型升级不应只改 model slug。对 agent 系统工程来说，这些功能把许多团队自建的 harness 能力下沉到 API 层。对后训练轨迹采集来说，未来必须记录是否启用 PTC、子代理树、cache breakpoints、reasoning context 和 tool caller，否则同一模型的行为不可复现。
🔗 链接：https://openai.com/index/gpt-5-6/ ｜ 代码：https://developers.openai.com/api/docs/guides/latest-model

### GameEngineBench：真实 Unreal Engine 5 C++ 项目里的 coding-agent eval
大多数 coding-agent benchmark 仍集中在 Python 或普通后端仓库，环境和测试相对静态；但真实软件里有大量状态化、交互式、实时系统，例如游戏引擎、机器人仿真和 3D 应用。GameEngineBench 把评测场景推进到 Unreal Engine 5：agent 要在九个真实 C++ game repositories 里完成 110 个 scoped implementation tasks。任务覆盖 gameplay mechanics、multiplayer behavior、AI/world orchestration、animation、UI、loading、online service、persistence、XR 和 rendering plugin 等类型。评测不是只看 diff 或单元测试，而是要求 native C++ change 能编译，并通过 Unreal 的 Play-in-Editor 行为测试，再通过 judge/rubric audit 判断是否满足目标行为。结果显示最强配置 pass@1 只有 55.5%，还有 31 个任务没有任何配置解出，失败集中在 authority、state synchronization、object lifecycle 和 initialization 等真实系统问题上。它值得关注，因为这些错误不是“不会写语法”，而是 agent 对运行时状态和系统交互理解不足。对后训练软件工程来说，这类 benchmark 能产生更接近复杂工程系统的失败轨迹，尤其适合训练 agent 处理编译、运行、状态同步和行为验证。
🔗 链接：https://arxiv.org/abs/2607.03525 ｜ 代码：None

### Reliable and Developer-Aligned Evaluation：面向真实协作仓库的 agent 评测方法论
OpenAI 刚审计 SWE-Bench Pro 后，社区更需要一种能解释“什么评测才可靠”的框架，而不只是换一个榜单。Reliable and Developer-Aligned Evaluation 这篇 FSE Companion 论文提出的方向是，把评测从假设性、静态、语法化任务拉回真实软件开发实践。它强调三个关键词：contamination-awareness、in-the-wild agentic behavior assessment，以及 trajectory-aware metrics。作者计划通过 agent 在真实开源协作仓库中的 tell-tale signatures，比较 agent-authored 与 human-authored 贡献如何影响协作、进度和代码维护轨迹。它还提出要面向 evolving repositories 建 benchmark，观察 agent 在需求变化、反复修改和复杂系统不同区域里的失败模式。虽然它更像研究计划和方法论，而不是一个完整可下载 benchmark，但它非常符合当前评测危机的方向：不能只测最终 patch，还要测协作行为、可维护性和随时间变化的影响。对后训练数据工程来说，in-the-wild 贡献数据和 trajectory-aware metrics 可能会成为比静态 issue 更有价值的样本来源。
🔗 链接：https://arxiv.org/abs/2607.06713 ｜ 代码：None

### mini-swe-agent v2：用极简 bash-only harness 固定模型评测变量
很多 coding-agent 评测最大的问题是模型和 harness 缠在一起：Claude Code、Codex CLI、Cursor、Gemini CLI 都有自己的工具形状、编辑原语、提示词和恢复策略，分数很难归因。mini-swe-agent 走了反方向：用大约 100 行核心 Python agent 和一个 bash-only 接口，把 scaffolding 尽量压到最小。它已经被 Ramp SWE-Bench 和 DeepSWE 用作统一 harness，因为所有模型面对同一个 bash tool 和同一套提示，能更清楚地隔离模型能力而不是厂商 scaffold。项目 README 声称在 SWE-bench Verified bash-only leaderboard 上超过 74%，并提供 CLI、batch inference、Python bindings 和 trajectory browser。它不是说生产 agent 应该永远只用 bash，而是给评测工程一个干净基线：先用最少假设测模型，再单独测复杂 harness 带来的收益。DeepSWE 的分析也指出 mini-swe-agent 可以匹配或超过一些 native harness，但代价是牺牲现实性，因为真实开发者会用更丰富的 Codex/Claude Code 工具面。对后训练软件工程来说，这类极简 harness 很适合做消融、数据采集基线和污染审计。
🔗 链接：https://github.com/SWE-agent/mini-swe-agent ｜ 代码：https://github.com/SWE-agent/mini-swe-agent

### jcode：Rust 多 agent coding harness，把并发 agent 成本压到本地可承受
开发者同时跑多个 coding agent 时，经常不是模型 API 先崩，而是本地 harness 太重、启动慢、内存高、多个会话互相踩文件。jcode 用 Rust 写成，目标是做一个高性能多 session coding-agent harness，让 10 到 20 个 agent 在普通 8GB 笔记本上也能并行运行。公开资料称它冷启动约 14ms，每增加一个会话约 10MB RAM，并通过单 server、多 client 架构共享基础设施。更重要的是，它不只是快，还加入跨 agent handoff、文件冲突检测和消息总线，能在一个 agent 读取文件而另一个 agent 改同一文件时提醒，减少 stale diff。项目支持 Claude、OpenAI 和本地模型等 35+ provider，GitHub 当前约 8.2k stars，7 月仍活跃发布。它解决的是多 agent 工程的底层瓶颈：如果每个 agent 都是一个重进程和孤立终端，并行很快变成资源与冲突灾难。对后训练轨迹来说，这类 harness 也会产生新元数据，例如并发会话数、冲突提醒、handoff 消息和被中断的编辑路径。
🔗 链接：https://github.com/1jehuang/jcode ｜ 代码：https://github.com/1jehuang/jcode

### AgentCanvas：让 MCP 工具输出落到共享看板，而不是一次性 transcript
MCP 解决了 agent 能不能调用工具的问题，但没有解决工具调用结果如何在多个 agent 和人类之间长期可见。AgentCanvas 的观点是，很多 tool output 不应该只返回到当前 transcript，而应该被放到一个持久共享 board 上。它提供标准 MCP 工具，例如 `create_html_asset`、`create_image_asset`、`append_html` 和 `list_assets`，让 agent 把截图、运行日志、研究结果或设计草稿贴到看板上。这样下一个 agent 不需要翻长聊天记录，也不需要重跑工具，只要读取 board assets 就能接手。这个思路特别适合便宜 subagents：它们可以在独立上下文里探索，把完整产物贴到板上，主 agent 或人类再挑选和复核。它的工程价值在于把 artifact handoff 从“自然语言总结”升级为可见、可引用、可复用的工作面。对 Agent-Friendly Software 来说，未来 MCP 工具不只是函数返回值，还可能需要面向人机协作的持久 artifact destination。
🔗 链接：https://www.developersdigest.tech/blog/mcp-tools-shared-board ｜ 代码：None

### Beyond Static Evaluation：用模拟环境与 run-to-verify 支撑 agentic RL
Agentic RL 的难点不是写一个 reward 函数，而是要有大量安全、隔离、可重复的环境，让 agent 能持续交互并收到可信反馈。Beyond Static Evaluation 介绍的 AgenticAI-Supervisor 试图把这层做成 API 和 UI 驱动的 simulation environment。它强调并行、隔离的 trajectories，支持 agent 与模拟工具和 web UI 交互，并把 programmatic verifier 直接放进 authoring pipeline。核心理念是 run-to-verify：不要只让 LLM judge 看自然语言总结，而是检查数据库状态、预算、单测、副作用和内部状态 mutation，确保 reward 对应真实业务逻辑。对于开放式或软约束部分，它仍会混合 LLM-as-judge，但把严格状态验证放在优先位置，减少 reward hacking。它按 Medium 收录，因为论文更偏通用 agentic RL 基础设施，而不是专门 coding-agent benchmark。对后训练软件工程来说，它提示我们 RL 环境设计要先有 sandbox、state oracle、trajectory efficiency 和 mutation tests，否则训练出来的 agent 很容易学会 evaluator 漏洞。
🔗 链接：https://arxiv.org/abs/2607.05773 ｜ 代码：None

### Agentic RL: Frameworks and Best Practices：把 agent RL 工程栈系统化
很多团队谈 agentic RL 时容易直接跳到 GRPO、PPO 或某个损失函数，但真正让训练跑起来的是 rollout、环境、轨迹格式、reward、重试和基础设施。Cameron Wolfe 这篇长文更像工程地图：它解释 agent 轨迹为什么应按 step-level action/environment interaction 记录，而不是只按 token 记录。文章还梳理了 rollout engines、trajectory rewards、process rewards、agent-environment loop、并发采样和框架选择，强调 agentic RL 的核心是多轮环境交互与可验证反馈。它的价值不是提出新算法，而是把很多散落的工程概念放在同一个 mental model 里。对软件工程 agent 来说，这些问题尤其关键，因为一次 rollout 可能包含读仓库、改文件、跑测试、失败恢复和提交判断。它也提醒后训练团队，RL 成本主要来自环境执行和长轨迹，而不是单个模型 forward。作为中优先级技术博客，它适合帮助团队检查自己的 agent RL pipeline 是否缺了轨迹 schema、环境隔离或 reward 审计。
🔗 链接：https://cameronrwolfe.substack.com/p/agentic-rl ｜ 代码：None

### cmux：面向多 AI coding agent 的 Ghostty-based macOS 终端
当开发者同时开 Claude Code、Codex、OpenCode、Gemini CLI 等多个 agent，会话管理本身就变成一个产品问题：哪个 agent 在等输入，哪个分支关联哪个 PR，哪个端口在跑，哪个 pane 需要注意。cmux 是一个基于 Ghostty 的 macOS 终端，专门围绕 AI coding agents 做 UI 和自动化增强。它的侧边栏用 vertical tabs 展示 workspace、git branch、PR 状态、工作目录、监听端口和最新通知；notification system 可以接收 OSC 9/99/777 序列，也可以通过 `cmux notify` 接入 Claude Code、OpenCode 等 hooks。这样 agent 卡住或请求用户注意时，pane 会亮起，开发者不用在多个终端窗口里来回扫。项目当前约 24k stars，7 月 10 日仍活跃，说明“agent-native terminal”已经从小众体验变成高热工作流基础设施。它按 Medium 收录，因为主要是终端产品而非评测或后训练框架，但它解决了多 agent 本地协作的真实可用性问题。对轨迹采集来说，终端通知、workspace 状态、PR 关联和用户介入点也应被记录，不能只保存模型输出。
🔗 链接：https://github.com/manaflow-ai/cmux ｜ 代码：https://github.com/manaflow-ai/cmux

### OpenAI GPT-5.6 System Card：同一模型家族内按 cyber/bio 风险分层加固
GPT-5.6 System Card 不是 coding-agent 数据工程内容，因此按 Low 收录，但它对高能力 agent 的部署治理有参考价值。OpenAI 将 Sol、Terra、Luna 三个模型都评为 Cybersecurity 和 Biological/Chemical 两个 tracked category 的 High 能力，同时认为 AI Self-Improvement 低于 High 阈值。一个值得注意的点是，小模型和快模型也进入 High 风险等级，这说明安全治理不能只盯旗舰模型。系统卡还强调按模型能力 profile 做差异化 safeguards，包括实时 cyber 与 bio misuse classifiers，在输出生成中同步审查，必要时可能阻断或延迟合法但双用途的请求。对 coding-agent 团队来说，这类 safeguard 会影响漏洞研究、代码审计、patch 开发和安全教育工作流，因此运行轨迹里要记录被拦截、被延迟或被路由的事件。它也说明官方系统卡正在从“模型风险说明”变成 runtime 行为说明。对后训练软件工程的间接启发是，安全 classifier、fallback、误报和人工复核都应该进入 eval harness，而不是只在发布文档里描述。
🔗 链接：https://deploymentsafety.openai.com/gpt-5-6 ｜ 代码：None

## 🔥 社区热点专栏

### 🔥 大佬观点

**OpenAI / 开发者社区：GPT-5.6 的重点不只是新模型，而是把 agent orchestration 下沉到 API。**  
MarkTechPost、TestingCatalog 等社区解读都把 Programmatic Tool Calling 和 Multi-agent beta 视为这次发布的核心信号：模型可以在请求内写程序协调工具，也可以由 root agent 管理子代理树。这个观点值得注意，因为它说明很多过去要靠 LangGraph、脚本或自研 harness 完成的编排能力，正在变成模型 API 的内置运行时能力。🔗 https://openai.com/index/gpt-5-6/ ｜ https://developers.openai.com/api/docs/guides/tools-multi-agent

**SWE-bench / DeepSWE / Ramp 线索：固定极简 harness，才能知道到底是模型强还是 scaffold 强。**  
DeepSWE 和 Ramp SWE-Bench 都选择 mini-swe-agent 作为统一执行层，把所有模型放在同一个 bash-only 环境里比较。这个观点火在它击中了评测归因痛点：厂商 native harness 越强，越难判断分数来自模型、工具、提示词还是恢复策略；极简基线不够真实，但很适合做消融和污染审计。🔗 https://deepswe.datacurve.ai/blog/deepswe ｜ https://labs.ramp.com/swebench

**Developers Digest / AgentCanvas：MCP 让工具可调用，但 shared board 才让结果可交接。**  
AgentCanvas 的文章指出，多个 agent 共享 MCP tools 只代表它们都能行动，并不代表它们共享“做过什么”的可见记忆。把截图、日志、HTML 文档和草稿落到持久 board 上，能让下一个 agent 和人类直接检查 artifact，而不是在 transcript 里找摘要。🔗 https://www.developersdigest.tech/blog/mcp-tools-shared-board

### ⭐ 超火仓库/项目

**SWE-agent/mini-swe-agent：约 5.6k stars，正在成为固定模型能力的极简 SWE harness。**  
它火在“少即是多”：用极小控制流和 bash-only 工具面，减少模型评测时的 scaffold 干扰，并被 Ramp SWE-Bench、DeepSWE 等用于统一比较。对后训练团队来说，它是一个很好的 baseline：先测模型在干净工具面下能做到什么，再测复杂 harness 带来的增益。🔗 https://github.com/SWE-agent/mini-swe-agent

**manaflow-ai/cmux：约 24k stars，把终端做成多 coding-agent 工作台。**  
cmux 的热度来自真实使用痛点：开发者已经能同时跑多个 Claude Code/Codex/Gemini 会话，但传统终端不知道哪个 agent 等人、哪个分支对应哪个 PR、哪个 pane 有新通知。它用 vertical tabs、状态侧边栏和 hookable notification 把 agent 等待/完成/卡住变成可见状态。🔗 https://github.com/manaflow-ai/cmux

**1jehuang/jcode：约 8.2k stars，用 Rust 性能让本地多 agent 并发变得现实。**  
jcode 火在性能指标非常抓人：毫秒级启动、每会话约 10MB 增量内存，让 10 到 20 个 agent 在普通机器上并行不再只是云端功能。它还加入 file-collision detection 和 message bus，说明多 agent harness 的关键不只是“跑多个进程”，还要治理共享仓库里的写入冲突和交接。🔗 https://github.com/1jehuang/jcode
