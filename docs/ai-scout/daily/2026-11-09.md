## 二、逐条中文讲解

### 1. The components of agent memory

长程代理要在下次开会时还用得上这次的经验，但不能把整段会话都留下。权重更新、同一次对话里的临时学习和压缩旧回合，都不算这里说的记忆。Anthropic 把记忆看成一次预测：写下一则笔记，就是在赌以后还会用到它。人还不知道后面会发生什么，所以当场写下的内容会过期，也会写错。他们把空闲时对照原始会话整理笔记的过程叫做做梦。

较强的模型会把失败收成以后还能用的规则。查库那道持续学习题每次都是新会话，只留一个记忆目录。Sonnet 4.6 写下的是没检验的猜测；要求它先读记忆再检验，分数将近变成两倍。Sonnet 5 不经提示，十次里有九次会先读。若规定只许记下失败，Opus 4.7 和 Opus 5 从记忆得到的提升会掉下去一大块，文中没有给出确切点数。游戏两边各跑一次，不能当成重复样本：Sonnet 3.7 写了 413 个文件，拿到 1 枚徽章；Fable 5 写了 9 个文件加一份总览，拿到 4 枚。一次做梦改掉错误地标后，角色才到达下一座城；没改时三次掉回路口。约 35 万份、约 4.2 亿 token 的文档上，做梦从 2 轮加到 128 轮，25 道题达到的评分标准从 13% 增到 48%。搜索加维基从 54% 到 61%，只用搜索是 53%。需要跨文件或再做判断的标准上，维基是 87%，只搜索是 73%。多个代理改同一张合同摘要，57 条里只留下 41 条；改成每份合同单独一页并照抄原文后，57 条都在。单份文件就能回答的题，维基没有明显好处。

值得留下的是以后还会用到的规则。写错的笔记，要拿原始会话核对，才会被改回来。

**链接：** [原文](https://www.anthropic.com/research/components-of-agent-memory)

### 2. Take It from Here: Evaluating Coding Agents on Project Takeover

编码代理接手一个已经做了很久的项目时，当前该遵守什么，往往散在以前的对话里，而不是写在这一条需求里。常见基准给的是一份现成说明和一个仓库。能回忆历史，也不等于能把还有效的约束收成新的目标，再交得出能通过验收的项目。

ReqMemBench 从 44 个协作项目里取出 349 个接手点。完整历史平均 181.4 轮，中位 110 轮。其中 7 个项目、37 个目标有可执行的构建、目标测试和回归测试。六个组合各跑一次：四种 GPT 配 Codex，Opus 5.5 和 Sonnet 5 配 Claude Code，推理力度都是 high。完整历史下，整套交付的平均成功率是 4.95%；只留下相关历史后是 2.70%。GPT-6 Astra 最高，10.81%；Sonnet 5 是 0%。需求被拆成可以单独变化的原子。应该直接动手的 312 个目标上，六种组合的更新后状态全部正确的次数都是 0。Astra 能找回 0.9211 的相关证据，精度只有 0.2254。把正确的目标状态直接交给代理以后，平均整套交付从 4.95% 到 8.11%，构建通过率从 58.56% 到 96.40%，回归从 51.35% 到 90.99%，但目标测试只从 6.31% 到 9.01%。论文没有给出可打开的代码仓库。每个组合只有一次运行。

目标状态给对以后，构建和回归大多能过，要改的那一项仍然几乎做不成。

**链接：** [原文](https://arxiv.org/abs/2611.07307)

### 3. Which Signals of Code Correctness Survive Distribution Shift?

模型给代码打“对”或“错”时，真去跑测试很贵。于是有人用回答的概率、多次采样是否一致，或者隐藏状态，先挑出值得再查的候选。这些分数在原来的题上常常很好看。换一个基准，或者从 Python 换到 C++ 和 Java，它们还认不认得出真正的错误，并不清楚。

作者在 Qwen3-Coder-30B 和 gpt-oss-20b 上比较了四类信号，并多加了一种从自然语言任务借来的做法：在隐藏状态里找出真正能改动判决的那一小块。两个目标要分开。一个是程序能不能通过测试，一个是模型自己的“对/错”判得对不对。语言一换，Qwen 上普通探针的判决 AUROC 从 0.76 降到 0.67，那一小块上的探针从 0.76 降到 0.73，直接看概率是 0.64。它比同一次比较里最好的非因果方法平均高 0.042，配对检验的 95% 区间是 ±0.021。gpt-oss 上，受过训练的方法都会掉 0.07 到 0.12，因果方法并没有显著领先。换成预测程序对错，这个优势也不在。更要紧的是分数从哪来。语言切换后，Qwen 几种受训方法在同一道题内部的 AUROC 都是 0.616 到 0.618。程序对错上，题内 AUROC 是 0.58 到 0.64，把所有题混在一起则是 0.67 到 0.81。只看题目、还没看见候选代码的探针，和看过候选的探针差不多。论文没有给出代码仓库。判决不用推理，gpt-oss 若打开推理，平衡准确率从 62.4% 到 67.8%，但每份候选中位大约要 1,101 个 token。

不跑测试的正确性分数，主要标出模型容易失败的题。它还分不开同一道题里的对错两份。

**链接：** [原文](https://arxiv.org/abs/2611.07876)

### 4. What the Middleman Delivers: Answer Behavior, Tool Permissions, and Billed Usage in LLM API Relays

很多代理不直接调用模型厂商，而是走一个更便宜或更好付款的中转。用户看见的是模型名字、回答和账单。中转可以改指令、换上游、交回不该出现的工具调用，也可以多报输入 token。回答看起来正常，这些都不会自己露出来。

作者从推荐和公开列表里选了 20 家提供 GPT-6 Astra 或 Claude Opus 5 的中转，不是随机样本。十家标价低于官方，十家相同或更高，请求从美国发出。第一轮里，低价组 10 家里有 7 家、同价或高价组 10 家里有 2 家，至少有一个目标模型的回答被标成和官方不同。两组的差别是 p=0.07，还不能说便宜就更不可靠。11 到 18 天后再测 35 对，按原规则有 7 对的标记出现或消失，6 家两轮都被标出。3,332 条固定的代码和安装回答里，没有确认到注入。第一轮仍有 4 家在明确关掉工具后交回工具调用，这些调用没有执行；第二轮是 0。五家对相同请求上报的输入 token 比官方多 4,200 到 60,000。六家能看到余额的服务，扣款和“上报用量乘标价”分毫不差，其中包括一家多报的输入。测试看的是客户端收到的内容，不能断定后面跑的是哪一个模型，也没有覆盖会保存对话但不改回答的情况。

标出的模型名字和单价，代替不了对工具权限和上报输入量的核对。多报出来的 token，会按标价进入账单。

### 5. How AI agents shape experts’ judgment calls

人们常假设，代理负责写代码和跑计算，遇到没有唯一正确答案的分析决定时，仍由专家拍板。因果推断里这种决定很多：产量按面积算还是按成本算，两组怎么比，估计覆盖哪些农场，大农场要不要加权。每一个都会把生产率的估计挪好几个百分点，而决策阈值只有大约 3% 到 4%。

这篇 10 月 27 日的试验近几天没有收过。61 名有因果推断经验的分析师用 Claude Code 分析一份农业合作社的观察数据，11 人不用代理，主要结果来自其余 50 人。四个分析决定和最后的推广建议上，代理倾向由抛硬币指定，人不知道。代理要做数据能支持的论证，证据相反时可以改口，不许改数字。四个决定上，人的选择与倾向相同的比例是 86%，没有作用时期望约 50%，分项是 92%、82%、81% 和 90%。倾向推广时 54% 建议推广，相反时 36%。只看这四个硬币，就能预测 82% 的推广或停办建议，总猜最常见答案是 61%，提出延期的人不在此数内。38 次人先表过态的情形里，倾向相反时 60% 改口，相同只改 6%，95% 区间是 24 到 82 个百分点。事后 77% 至少一次复述代理的论证，只有 15% 提到代理。52% 觉得建议更像自己的；四个决定都跟上的人，信心平均 71，其余 73。没有指定倾向时，Opus 4.8 在 123 次里有 112 次自己做出同一组选择，所以这次是故意加强了倾向。48 人里 6 人猜到研究的是代理影响，没有人猜到倾向被指定。用了代理的人更快，严重错误也更少；不用的只有 11 人且经验更低，作者不把这组差别当成可靠对比。

没有唯一正确答案时，被指定的倾向会进入专家的结论。专家仍常常把这个结论算成自己的。

### 6. Who Should Know What? Empirical Information Design for Multi-Agent LLM Economies

多个代理一起交易时，常见做法是把知道的价格和偏好尽量告诉对方，认为信息越多，成交越好。对单独一个决策者，多知道一点不会更差，因为少信息时的做法还在。双方都要争利时，精确的底价也会告诉对方还能再要多少。于是“看清机会”和“最后成交”可能分开。

这篇把信息披露当成可以单独开关的设计。市场、模型、激励和交互规则不动，只改对方能看见排序，还是能看见精确估价。十个前沿模型分别做多种资源的交换、双边议价和双边拍卖，收益按已知的最大福利来量。交换里，从粗信息改成精确估价，GPT-6 Sol 实现的收益从最大可能的 97.7% 降到 90.8%，GPT-6 Luna 从 68.9% 升到 79.0%。拍卖里，充分公开后 Claude Opus 5.5 从 94.6% 降到 64.1%，Grok 4.7 从 97.4% 降到 62.1%，原因是报价被抬高，市场做不成。六轮消息的议价里，同样的改动使 Grok 4.7 的归一化纳什分数从 0.71 降到 0.17，不同意记 0；GPT-6 Sol 则从 0.71 升到 0.83。这些对照里，两边是同一个模型的不同实例。文中写了代码地址，本次用 GitHub API 查询返回 404，所以不附代码链接。这是固定规则的小市场，不是编码代理的仓库任务。

把估价从排序改成精确数字，成交福利会随模型上升或下降。多知道一点，并不自动变成更好的成交。

**链接：** [原文](https://arxiv.org/abs/2611.07667)

### 7. Project EVE: Claude plays MMORPGs

长时程代理以后可能要管库存、分工和有人目标不一致的小组。真实公司里试这些事代价很高。Anthropic 的实习生项目在 4 月到 7 月用 EVE 的两个游戏做了一个低风险的观察，11 月 6 日公开。一边是重放的市场，一边是仍在开发、会定期重置的多人游戏。

市场实验不进入真服务器，用的是玩家曾经挂出的买卖单。它不会因为代理下单而改价。九个两周窗口里，试过的简单规则只有一条勉强不亏。Opus 4.7、Opus 4.8 和 Fable 5 九个窗口都赚钱，资金大约增加 16%、22% 和 43%；Opus 4.6 大约增加 4%，和最好的规则接近。六个月的窗口里，平均收益从初始资金的大约 200% 增到大约 600%，也就是从 Opus 4.6 到 Fable 5 大约三倍。它们主要自己写成程序，赚买卖价差，利润率大约 8% 到 13%。2025 年 3 月游戏提高销售税后，Opus 4.7 中位 2.5 天才注意到，43% 的 Opus 4.6 一直没注意。若规定只能做方向判断，Fable 5 大约一半的运行赚钱。人为加入压价单后，它们仍赚钱，但利润大约少 35%。多人游戏里，快动作靠模型自己写的脚手架。Fable 5 写的脚手架上，队伍没有丢船，教程在 12 小时内做完；用 Opus 4.8 写的脚手架，会丢船，而且要好几天。造大型战舰最远大约走到一半。另有一组实验明确指示一名队员暗中阻止完成任务，这不是模型自己产生的倾向。其余成员事先知道队里可能有人目标不同。从公开消息里明确认出这名队员的，只有一次 Opus 4.8 运行里的一名诚实代理。不看私人推理、并把误指诚实成员控制在 5% 以内的监视代理，Opus 4.6 到 4.8 抓住 30% 到 40%，Sonnet 4.6 抓住 20%，信心都没有超过 50%。

这批代理更会把现成价差做成程序。判断接下来会发生什么，以及从队友的话里认出被指示拆台的人，这次的证据仍然很弱。

### Trending Open-source Projects

#### 1. Pinky

让编码代理操作手机，常见做法是把点击步骤写进提示，或者把整个屏幕交给模型。付款、发消息和银行应用一旦可点，提示里的“请先问我”挡不住模型自己点下去。人要看着，也要能中途拿走控制权。

Pinky 让 Claude Code、Codex、Cursor 或其他能用 MCP 的程序操作 iPhone 或 Android。批准发生在它自己的网关里，不靠对模型的文字要求。付款、转账默认等待点击；银行、钱包和密码管理应用默认不可见，密码和一次性验证码字段不能由代理输入。Android 13 及以后可以用一块隐藏的第二屏幕，手机自己的屏幕仍留给人。每一步有文字、截图和录屏，留在本机。项目写明状态是 pre-alpha，并称 Claude Code 已在一台 USB 连接的 Android 和一台 iOS 27 的 iPhone 上跑通；这次没有重做该验收。仓库建于 2026 年 11 月 6 日，本次用 GitHub API 读到 858 star、69 fork，Apache-2.0，最近一次推送是 11 月 9 日。没有逐日 star 差额。

它把“代理能不能自己批准自己”从提示挪到网关。手机操作仍然是早期实现，验收范围是项目自己的记录。

**链接：** [GitHub](https://github.com/DIYgod/pinky)

#### 2. Kiri

代理每做一步都要起一个容器时，桌面版 Docker 的启动时间会变成等待。兼容现有的 `docker` 命令仍然有用，因为脚本、Compose 和构建工具都认这套接口。

Kiri 用 Rust 实现 Docker Engine API。macOS 和 Windows 上容器跑在一个很小的 Linux 虚拟机里，Linux 上直接用内核。虚拟机里的 1 号进程用一次 `clone3` 启动容器，中间没有 runc，也没有 dockerd。项目 2026 年 10 月 24 日的自测文件写着，经这套 API 创建 alpine、执行 `true` 再删除，热身之后 30 次的中位数是 2.55 毫秒；同一文件里 OrbStack 的 `docker run` 是 325 毫秒。README 表格另有 Docker Desktop 的对照，这次打开的结果文件里没有这一行。仓库建于 2026 年 11 月 2 日，本次读到 1,237 star、80 fork，Apache-2.0，最近一次推送是 11 月 8 日。

短命容器的启动被收成毫秒级，而且现有 Docker 客户端不用改。速度是项目自己在一台 Apple Silicon 机器上的测量。

**链接：** [GitHub](https://github.com/libracoder/kiri)

#### 3. gputaskman

显存只显示“用了 15 GB”时，看不出是模型权重、KV cache、浏览器还是桌面合成器。本地做推理或后训练的人需要这个区分，云上的服务不在范围内。

gputaskman 是一个终端界面，把每个进程的显存和引擎占用，与加载的运行时、模型文件放在一起。权重、KV cache 和计算缓冲的划分来自 GGUF 等旁证，程序写明这是估计，不是把显存倒出来。NVIDIA 在 Windows、Linux 和 WSL 上可用，AMD 有 Windows 和原生 Linux 的范围，Apple Silicon 另有一条路径。进程显存和引擎占用是测量；只看到一个 PyTorch 动态库，不能据此断定正在训练，也不能断定某个映射文件正放在 GPU 上。可用 `uv tool install gputaskman` 安装。仓库建于 2026 年 11 月 3 日，本次读到 1,060 star、55 fork，MIT，最近一次推送是 11 月 8 日。

它让本地 GPU 上的模型占用变得可以按进程查看。缓冲划分仍然是估计，不是显存转储。
