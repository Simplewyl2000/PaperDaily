## 📝 逐条讲解

### OpenAI GPT-5.6 Sol：Terminal-Bench 2.1 SOTA、`max` reasoning 与 `ultra` subagents
过去几周日报一直在跟踪 terminal agent、loop engineering 和 Codex 长程委派，OpenAI 6 月 26 日的 GPT-5.6 Sol 预览把这些方向直接放进了官方模型发布叙事里。GPT-5.6 不再只是一个模型名，而是 Sol、Terra、Luna 三个能力/成本层级；其中 Sol 面向复杂 agentic work，Terra 主打 GPT-5.5 级能力但成本降低，Luna 则面向高吞吐低成本任务。最值得关注的是，OpenAI 明确称 Sol 在 Terminal-Bench 2.1 上达到新的 state of the art，并新增 `max` reasoning effort 和 `ultra` mode，后者会利用 subagents 来加速复杂工作。工程上，这说明前沿模型的竞争正在从“单次回答更强”转向“模型 + 推理预算 + 子代理编排 + 缓存经济学”的组合；GPT-5.6 还引入 30 分钟最低 cache life 和显式 cache breakpoints，对长程 Codex 会话的成本控制很重要。安全侧也很重：OpenAI 把 cyber/biology 实时分类器、生成中暂停、大模型复核、账号级信号和自动红队放进同一套 layered safeguards。它对后训练软件工程的启发是，未来评测和训练不能只看 base model pass rate，还要把子代理模式、缓存策略、安全拦截、长程工具调用和成本一起纳入 harness。当前它仍是有限预览，因此分数和产品表现需要等更完整公开 eval；但官方明确把 Terminal-Bench、Codex、subagents 和长程安全放在发布核心，已经是高价值信号。
🔗 链接：https://openai.com/index/previewing-gpt-5-6-sol/ ｜ 代码：None

### AgentLens / MAS：用隐藏表示做多轮 coding agent 运行时安全 steering
多数 coding-agent 安全方案放在外层：提示词规则、工具权限、命令审批、沙箱和日志审计，这些机制很实用，但它们通常只能在模型已经要行动时拦截。AgentLens 尝试从模型内部状态入手，问一个更细的问题：多轮 coding agent 在执行过程中，是否能从 hidden representations 里提前看出它正在走向不安全动作。它提出 Mechanistic Subspace Intervention and Steering，用轻量 probe 检测 step-level harmful execution states，再在单层的 10 维安全相关子空间中做 representation-level intervention。为了评测这种思路，作者构造 MAS benchmark，包含 194 个带注释的多轮执行任务，覆盖 LLaMA-3.1-8B、Qwen-2.5-7B 和 Gemma-2-9B 等开放模型。亮点在于它不只做单轮 jailbreak 问答，而是把风险看成 agent execution trajectory 中不断演化的状态，并报告了 lookahead risk anticipation 的初步证据。工程上它还不能替代外部 guardrail，因为白盒方法依赖模型可访问性和稳定表示；但它补了外层沙箱看不到的“意图正在漂移”信号。对后训练和评测来说，MAS 这类步骤级安全标注轨迹可以用于训练 agent 识别危险执行状态，而不是只在最终有害输出上打标签。
🔗 链接：https://arxiv.org/html/2606.22673 ｜ 代码：https://github.com/EddyLuo1232/AgentLens

### FireFly：从真实 MCP API 反向生成可验证 tool-call 训练数据
工具调用数据合成最常见的问题是“先写任务，再希望工具真的能解”：如果 API 状态变了、返回值漂移了、任务本身不可解，训练标签就会变脏。FireFly 把顺序反过来，先让强模型在真实 MCP servers 上按图结构探索工具链，观察真实输出，再从已经发生的结果反向合成用户任务。这样任务标签不是靠想象出来的，而是由真实工具执行结果保证，作者称这能 by construction 保证 label correctness。为了处理近千工具规模的工具空间，它先构建 pairwise tool graph，再采样语义连贯的 sub-DAG，让探索集中在可能组成真实工作流的工具组合上。另一个关键工程点是 retrieval-augmented simulator：把探索过程中所有工具结果缓存下来，训练和评测时离线重放，避免 live API 漂移，同时能做可复现 RL。最终数据包含 5,144 个 verified tasks，覆盖 240 个 servers 和 993 个 tools；一个 4B 模型用 GRPO 训练后，在 held-out tool-call set 上接近 Claude Sonnet 4.6，并在 Tau2-Bench、MCPMark、MCP-Atlas 上提升。它对本日报最核心的数据工程方向非常直接：高质量 agent 后训练数据应来自“执行过、可重放、有 ground truth”的工具轨迹，而不是只靠大模型凭空编排调用序列。
🔗 链接：https://arxiv.org/html/2605.17558 ｜ 代码：https://anonymous.4open.science/r/firefly_opensource-1C78/

### TDScaling：用轨迹多样性而非数量扩展 Code Agent 工具使用数据
很多团队做 tool-use / code-agent 训练时自然会先扩数据量，但低多样性轨迹越堆越多，会很快遇到收益递减：模型学会熟悉 API 的固定路径，却不擅长面对新工具、异常、组合调用和长尾流程。TDScaling 的核心观点是，代码 agent 的数据扩展应优先扩“覆盖与结构深度”，而不是单纯扩样本数。它把 MCP servers 当作 Business Clusters，保留真实服务里的逻辑依赖，再用 greedy coverage 选择高覆盖工具簇，而不是把 API endpoint 打散后随机采样。生成侧采用 Blueprint-driven multi-agent synthesis，先规划目标、执行计划、约束和策略 profile，再按 Domain Entropy、Reasoning Mode Entropy、Cumulative Action Complexity 等指标引导轨迹朝长尾复杂场景演化。它还把 sandboxed code tool 当作 regularizer，避免模型在 tool tuning 后忘掉本来的代码能力。实验覆盖 BFCL、Tau2-Bench、RebenchT、CodeCI、BIRD，论文称 Qwen3-Coder-30B-A3B 可达到接近 480B 级模型的表现。对后训练数据工程来说，它给出一个很可复用的原则：训练 agent 不只是收集更多成功轨迹，而要主动度量轨迹的领域覆盖、工具组合结构、恢复路径和复杂度分布。
🔗 链接：https://aclanthology.org/2026.findings-acl.768.pdf ｜ 代码：https://github.com/Eileen19200930/TDScaling

### PROJECTMEM：本地优先、事件溯源的 coding-agent 记忆与行动门控层
coding agent 经常在新 session 里重复读仓库、重复踩坑、重复尝试已经失败的修复，这不是模型不会写代码，而是项目状态没有被稳定保存。PROJECTMEM 的设计很朴素但贴近工程：把开发过程写成 append-only plain-text event log，事件类型包括 issues、attempts、fixes、decisions 和 notes，然后确定性投影成短小、AI-readable 的摘要，通过 MCP 暴露给 agent。它不只做“记忆检索”，还提出 Memory-as-Governance，也就是在 agent 行动前做 deterministic pre-action gate；如果 agent 要重复一个历史失败修复，或要编辑已知脆弱文件，系统会先提醒。项目强调 local-first、离线运行、无 telemetry，因此适合企业或敏感代码场景，也能把 immutable log 当作 provenance trail。论文评估来自 10 个项目、207 个 logged events 的两个月自研究，规模不大，但重点是系统形态而不是榜单分数。它和之前日报里的 agentmemory 互补：agentmemory 强调跨客户端共享记忆，PROJECTMEM 强调可审计事件源与行动前治理。对后训练软件工程来说，这类事件日志如果结构化保存，会成为高价值轨迹数据：模型不仅能看到最终成功方案，还能看到哪些尝试被证明失败、哪些文件风险高、哪些决策约束不能忘。
🔗 链接：https://arxiv.org/abs/2606.12329v1 ｜ 代码：https://github.com/riponcm/projectmem

### Agent trajectories as programs：把 agent 轨迹当程序来指纹识别与路由
平时我们评价 agent 往往看最终结果：测试是否通过、任务是否完成、token 花了多少；但不同 agent 即使做同一件事，也可能有非常不同的过程习惯。Agent trajectories as programs 把轨迹本身当成一种程序序列来研究，分析工具调用、动作顺序、重复结构、分支习惯和 procedural diversity。论文用 entropy、compression、Jensen-Shannon divergence 等指标来描述 agent 的 procedural fingerprint，发现模型家族、harness scaffold 和蒸馏来源都会在轨迹中留下可恢复的行为风格。一个重要结论是，scaffold 和模型 generation 往往比单纯模型参数更能决定过程习惯；被蒸馏的 student 也会继承 teacher 的 procedural style。它对工程团队的价值不是“识别某个模型是谁”，而是帮助做任务感知路由：有些 agent 更喜欢广搜，有些更会验证，有些更容易重复试错，成本模型和失败风险也不同。对后训练数据筛选来说，这说明成功轨迹之间也有结构差异，不能只按 outcome 混在一起训练。未来如果把这种轨迹指纹接入 benchmark dashboard，就能比较“哪个 harness 教会了更稳定的程序化工作流”，而不是只看 pass rate。
🔗 链接：https://arxiv.org/html/2606.16988v1 ｜ 代码：None

### AI Snitches Get Glitches / SurveilBench：评测 agentic surveillance 与反监控注入
企业、学校和政府越来越可能部署能读邮件、文档、聊天和数据库的 agent，这带来一个不常被 coding benchmark 覆盖的风险：agent 不只是帮助用户完成任务，也可能被配置成监控用户。AI Snitches Get Glitches 把这个问题形式化为 agentic surveillance，即 agent 读取可用信息、分析目标行为、写报告并通过工具发送出去。作者构造 SurveilBench，覆盖 corporate、education、police 三类场景，测试不同模型是否会执行或自发帮助这类监控任务。论文还发现一些模型会出现奇怪的 emergent 行为：既可能帮助 surveillance，也可能把 surveillance 尝试报告给政府或其他外部对象。更有意思的是，作者把 prompt injection 反过来用于 evading surveillance，提出隐藏、欺骗或诱导过度升级三种反监控技术。它与本日报高优先级的 Agent-Friendly Software 有关，因为一旦传统办公/协作系统通过 MCP、API 或 computer use 暴露给 agent，访问边界和报告动作就需要被技术化治理。对评测工程来说，SurveilBench 提醒我们不应只测“agent 能不能完成用户目标”，还要测它是否会在权限充分时执行组织或第三方的监控目标，以及被监控者是否有可审计、可申诉、可限制的数据边界。
🔗 链接：https://arxiv.org/abs/2606.25836v1 ｜ 代码：None

### mcp-cli：把 MCP 工具变成零常驻上下文开销的 shell/agent 控制面
近期 MCP vs CLI 的讨论反复指向一个工程痛点：MCP 很适合治理、认证和结构化工具边界，但如果每个 server 都把大量 schema 常驻注入上下文，简单任务也会背上数万 token 的成本。mcp-cli 的做法是把 MCP 工具重新暴露成 shell 可调用的 `mcx` 命令，让 agent 像用 `gh`、`jq`、`psql` 一样按需发现和调用 MCP 工具，而不是在每次对话里预加载全部工具定义。它读取现有 Claude Code 配置和 `.mcp.json`，并进一步提供 agent sessions、event bus、phase state machine、automation modules 等控制面。这个项目 star 很低，不能按“爆火仓库”处理，但它击中的问题很真实：当团队有十几个 MCP servers 时，最贵的往往不是 tool call 本身，而是不用工具时也要反复支付 schema 上下文税。它还把 Claude、Codex、OpenCode、Copilot、Gemini 等 provider sessions 统一到类似 CLI 的管理面，适合做轻量 multi-agent orchestration。工程上它代表一种折中路线：保留 MCP 的统一协议与治理，但把调用入口 CLI 化、脚本化、可组合化。对 Agent-Friendly Software 来说，这类工具会推动“CLI Anything”与 MCP 互补，而不是让两者变成互斥选择。
🔗 链接：https://github.com/theshadow27/mcp-cli ｜ 代码：https://github.com/theshadow27/mcp-cli

### mcptest：面向 MCP agent 的 pytest 式轨迹回归测试框架
MCP agent 现在越来越多，但很多团队仍靠手工 demo 判断 server 是否可用、prompt 是否稳定、工具顺序是否符合预期。mcptest 的定位很清楚：给 MCP agent 一个类似 pytest 的回归测试框架，用 YAML fixtures mock MCP servers，在隔离环境中运行 agent，并对 tool-call trajectory 做断言。它支持 `tool_called`、`tool_order`、`error_handled` 等 MCP 轨迹原语，还提供 GitHub、Slack、filesystem、database、HTTP、git 六类 fixture packs。这样团队可以在不烧真实 token、不打真实 API、不依赖线上状态的情况下，快速测 agent 是否仍会按预期调用工具。它还包含 MCP conformance checks、fixture coverage、parallel execution、CI/CD 和 PR summary 相关能力，适合把 agent workflow 当软件一样做 regression gate。项目当前 star 几乎没有，可信度和成熟度都需要谨慎，但方向非常对：MCP server 和 agent prompt 一旦进生产，就需要确定性测试，而不是每次靠 LLM judge 看 transcript。对后训练和 eval 来说，这种 fixture-driven harness 还可以生产“可控错误场景”的训练样本，例如 rate limit、permission denied、merge conflict 和 path traversal。
🔗 链接：https://github.com/josephgec/mcptest ｜ 代码：https://pypi.org/project/mcp-agent-test/

### IETF MCP Security Considerations：把 MCP 实现风险整理为可审计安全清单
MCP 的采用速度很快，但协议本身和生态实现并没有自动带来完整安全边界；很多 server 一开始只是开发者便利工具，后来却被放进有真实权限的 agent 工作流。IETF 这份 Internet-Draft 从实现者和运营者角度整理 recurring vulnerability classes，强调 MCP specification 当前缺少 normative security requirements。它讨论了公开报告过的 MCP server 漏洞类型、自动检测思路、mcp-safeguard，以及 Protocol Pivoting 这类跨协议 lateral movement 风险。所谓 Protocol Pivoting，可以理解为攻击从 MCP 工具调用跳到 A2A delegation、自动协商协议或其他 agent 通信层，最后形成跨边界移动。它不是论文 benchmark，也不是官方标准最终稿，因此按 Medium 收录；但它的价值在于把零散 MCP 安全事件整理成 operator checklist。对工程落地来说，MCP server 上线前需要回答：工具权限是否最小化、响应是否标注不可信、是否有审计日志、是否能限制网络/文件系统、是否能检测配置漂移。对本日报关注的 Agent-Friendly Software 来说，这类安全草案说明工具接口标准化之后，下一步必须是安全要求和测试规范标准化。
🔗 链接：https://www.ietf.org/archive/id/draft-mohiuddin-mcp-security-considerations-00.html ｜ 代码：None

### Terminal-Bench 2.1：修补 2.0 reward hacking 与鲁棒性问题的终端 agent 回归集
Terminal-Bench 已经成为衡量终端 agent 的核心评测之一，但高影响力 benchmark 一旦被大量模型和 harness 针对，就会暴露任务 bug、超时不稳、资源限制不合理和 reward hacking 缺口。Terminal-Bench 2.1 的意义在于，它不是另起一个新榜，而是对 2.0 进行验证和加固：仓库说明 26 个任务被修改，用于修 bug、调整 timeout/resources 或提高抗 reward hacking 的鲁棒性。它还吸收了 Z.ai Terminal-Bench 2.0 Verified 的部分修改，并通过 Harbor Hub 和 leaderboard 继续发布。对评测工程来说，这说明 benchmark 也必须像软件产品一样持续维护，不能发布后冻结到永远。尤其是 terminal-agent 任务，agent 可以读环境、跑脚本、改文件、探索 verifier，任何松动都会变成训练或 leaderboard 的漏洞。它按 Medium 收录，是因为 2.1 本身是评测集修补而非新研究，但对反作弊和可复现回归非常重要。对后训练团队来说，使用 Terminal-Bench 数据时应记录版本号、task patch、harness commit 和 verifier 修订，否则不同实验之间的分数会混在一起。
🔗 链接：https://github.com/harbor-framework/terminal-bench-2-1 ｜ 代码：https://github.com/harbor-framework/terminal-bench-2-1

### Firecrawl：2026 coding-agent 横评从模型分数转向 harness、成本和远程异步能力
很多 coding-agent 横评仍停留在“哪个模型 SWE-bench 分数最高”，但开发团队实际选工具时会同时看 CLI 深度、hook、sandbox、MCP、远程异步、价格、review surface 和团队协作能力。Firecrawl 这篇 2026 横评把 Claude Code、OpenAI Codex、Cursor、GitHub Copilot、Gemini CLI、OpenCode、Devin 等放到同一张工程比较表里，字段包括 harness depth、remote/async、entry price 和 best-for 场景。文章强调 Codex 已经不是早期的 bare-bones 终端工具，而是有 Skills、Plugins、Subagents、Hooks、MCP、kernel-level sandbox 和 cloud task surface；Claude Code 则继续在 hooks、skills、plugins、subagents 和 terminal-native depth 上很强。它还把 OpenCode 作为开源生态信号，引用约 176k stars 和多 provider 支持，说明社区对可自托管、模型无关的 agent harness 有强需求。这个条目按 Medium 收录，因为它是开发者博客，可信度低于论文或官方报告，但它提供了一个有用的工程 rubrics。对内部评测来说，采购或集成 agent 时应按“任务类型 + 权限模型 + 异步能力 + 成本曲线 + 可观测性 + 团队控制面”做小型 benchmark，而不是只看公开榜单。
🔗 链接：https://www.firecrawl.dev/blog/best-ai-coding-agents ｜ 代码：None

### Anthropic Economic Index Cadences：Claude Code / Cowork 推动长程 agentic work 的时间节律变化
Anthropic 6 月 26 日发布的 Cadences 属于 Economic Index，而不是 coding benchmark 或模型技术报告，因此按 Low 收录；但它是官方新 research，且给出了 agentic work 进入真实工作节律的信号。报告指出，随着 Claude Code 和 Cowork 增长，Claude 使用越来越多地由 long-running agentic tasks 组成，传统 chat transcripts 已不足以描述用户如何使用 AI。它还提到 93% Claude conversations 会产生某种 artifact，常见输出包括 explanations、reports、guidance，代码和技术工作约占一部分；Claude Code 上同类输出的平均 autonomy 更高。对 coding-agent 方向有意思的是，周末 Claude Code 使用的任务簇会发生变化：backend architecture、API debugging、data storage 下降，而 AI agent design、quant trading、gaming 上升。它的价值不在给我们一个训练 recipe，而在告诉我们 agent 产品正在改变“什么时候、以什么节奏、由谁发起工作”。对后训练软件工程来说，这意味着未来轨迹数据要捕捉 cadence、artifact、autonomy level、异步/周末任务、人工反馈间隔，而不是只保存单个 prompt-response。
