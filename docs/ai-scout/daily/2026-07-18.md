## 📝 逐条讲解

### Grok Build：xAI 新 coding-agent harness/TUI，4 天冲到 16.5k★
过去几个月 coding agent 的竞争越来越不只是模型能力，而是模型外面的运行时：终端界面、权限、状态、任务队列、上下文和验证怎么组织。Grok Build 是 xAI 在 7 月 14 日创建的新仓库，描述为 coding-agent harness and TUI，短时间内达到约 16.5k stars，说明社区对新一代 agent harness 仍然非常敏感。它的公开说明强调 fullscreen、mouse interactive 和 extensible，意味着它试图把 CLI agent 从普通命令行会话升级成可持续操作的工作台。与传统 IDE agent 不同，这类 TUI 的重点是让 agent 在真实终端环境中运行，同时给人类更清晰的状态和控制面。它值得关注，不是因为现在就能断言其技术成熟，而是因为高热度本身反映了开发者正在寻找 Claude Code、Codex、OpenCode 之外的可组合 harness 形态。对后训练软件工程来说，新的 harness 会改变轨迹结构：同样的模型在不同 TUI、权限、上下文加载和验证循环下，行为可能完全不同。后续如果 Grok Build 公开更详细的事件日志、工具协议或评测结果，它会成为研究“模型-运行时耦合”的重要样本。
🔗 链接：https://github.com/xai-org/grok-build ｜ 代码：https://github.com/xai-org/grok-build

### Herdr：面向多 coding agent 的终端 multiplexer 与状态面板
当开发者同时运行 Claude Code、Codex、OpenCode、Cursor Agent 或其它 CLI agent 时，普通 tmux 只能告诉你某个 pane 有输出，却不知道它是在工作、等待输入、已经完成还是卡住了。Herdr 的定位就是“给 agent 时代重做 tmux”：每个 agent 仍运行在真实 PTY 里，但侧边栏能显示 blocked、working、done、idle 等语义状态。它还支持 detach/reattach 和 SSH 场景，适合把长任务放在服务器或沙箱里继续跑，而不是依赖本地 GUI 一直开着。更有意思的是它提供 socket API，让 agent 本身也可以创建 pane、读取输出、等待其它任务完成，形成轻量自编排。项目 7 月 17 仍有预发布版本，GitHub 约 17.6k stars，说明“管理一群 agent”已经成为真实需求。它解决的痛点不是让模型更聪明，而是降低人类监督多个异步 agent 的认知负担。对训练和评测来说，Herdr 这类工具提醒我们应该记录 agent 的生命周期状态、阻塞原因、人工介入点和跨 pane 依赖，而不是只保存每个 agent 的单独 transcript。
🔗 链接：https://github.com/ogulcancelik/herdr ｜ 代码：https://github.com/ogulcancelik/herdr

### Graphify：把代码、文档、图像/视频转成 agent 可查询知识图
大型代码库里的 agent 失败常常不是因为不会写某个函数，而是没能建立正确的项目地图：哪些模块相关、设计约束在哪、数据库 schema 和基础设施如何连接、历史 ADR 为什么这么写。Graphify 把这个问题做成一个 agent skill：对代码用 tree-sitter 做本地确定性解析，对文档、论文、图像和视频做语义抽取，最后合并成可查询知识图。它提供 query、path、explain 等操作，让 agent 不必靠反复 grep 和读长文件来寻找上下文。项目约 90k stars，7 月 17 仍有 release，热度很高；这类数字要谨慎解读，但至少说明“知识图作为 agent 上下文层”已经是强社区方向。它的新意在于把 code intelligence 和多模态项目资料放到同一张图里，而不是分别维护代码索引、文档 RAG 和视频笔记。工程价值在于可审计：agent 可以回答“我为什么认为 A 和 B 相关”，而不是只给出一个向量检索片段。对后训练数据工程来说，未来高质量轨迹需要保存 agent 查询了哪些图节点、走了哪条 path、哪些解释被用于补丁决策，否则难以区分结构化理解和碰巧命中。
🔗 链接：https://github.com/Graphify-Labs/graphify ｜ 代码：https://github.com/Graphify-Labs/graphify

### Chrome DevTools MCP v1.6：把真实 Chrome 调试能力接进 coding agent
前端 coding agent 的一个老问题是，它能改代码但不一定能可靠看到浏览器里的真实行为；只靠静态检查或截图，经常漏掉 console error、network failure、performance bottleneck 和交互状态。Chrome DevTools MCP 把 Chrome DevTools 的能力暴露成 MCP server，让 Claude Code、Cursor、Copilot、Gemini 等 agent 控制和检查真实 Chrome 浏览器。它可以支持性能 trace、网络请求检查、console 信息、截图和浏览器动作自动化，把“跑起来看看”从人类手工步骤变成 agent 工具调用。7 月 14 发布 v1.6.0，仓库约 47k stars，并且 Google 官方文档已经把它归入 Chrome DevTools for agents 的安装路径。它值得关注，因为 browser harness 是前端 agent 验证闭环的关键一环：没有真实浏览器反馈，很多 UI 或性能修复只是模型猜测。相比简单 Playwright 脚本，DevTools MCP 更接近浏览器调试器本身，能让 agent 观察网络、性能和控制台这些工程师日常依赖的证据。对后训练软件工程来说，前端轨迹应保存 DevTools 事件、trace、network diff、console 证据和 agent 如何把这些证据映射到代码修改。
🔗 链接：https://github.com/ChromeDevTools/chrome-devtools-mcp ｜ 代码：https://github.com/ChromeDevTools/chrome-devtools-mcp

### CubeSandbox 0.5.1：面向 agent 的硬隔离 sandbox 生命周期与集群化
让 coding agent 或 RL rollout 执行任意代码时，Docker 级隔离和普通临时目录经常不够：共享内核逃逸、凭证外泄、网络策略和高并发冷启动都会成为生产瓶颈。CubeSandbox 用 RustVMM/KVM 提供硬件级隔离，并兼容 E2B SDK，目标是在几十毫秒级启动可服务的 sandbox。7 月 3 的 0.5.0 引入 AutoPause/AutoResume、ARM64 支持、Terraform 集群部署、CubeEgress fail-closed 引导和 per-sandbox traffic tokens；7 月 10 的 0.5.1 又把生命周期管理器抽出为独立 control-plane service，并修复 host-mount allowlist、ARM64 snapshot integrity 和 egress/TAP 可靠性。这个方向的价值在于，agent 工作负载大量时间其实在等待用户、回调或下一轮 rollout，AutoPause 能把 idle sandbox 资源释放出来，同时在下一次 dataplane 请求时恢复。它解决的是 agent infrastructure 的真实成本问题，而不只是安全口号。对后训练和评测来说，sandbox 不只是“能跑代码”的容器，而是影响成本、隔离、可复现、网络可观测和失败恢复的关键条件变量。高质量轨迹应该记录 sandbox 镜像、snapshot/rollback、egress policy、生命周期事件和权限边界。
🔗 链接：https://github.com/TencentCloud/CubeSandbox/releases ｜ 代码：https://github.com/TencentCloud/CubeSandbox

### Deja-vu：从 Claude Code/Codex/opencode 日志构建本地 agent 记忆层
很多团队已经积累了大量 Claude Code、Codex、opencode、Cursor、Gemini CLI 等工具的 session logs，但这些日志通常只用于事后查错，很少被转成下一次 agent 能主动利用的记忆。Deja-vu 的思路是直接挖这些现成日志，构建本地 memory layer，提供搜索、MCP recall、auto-context、secret redaction、统计和分享/同步能力。它在 7 月 14 创建，几天内有约 338 stars，说明“从真实 agent 历史中恢复上下文”是开发者刚需。和手写 `LEARNING.md` 不同，日志挖掘能覆盖更细的事实：哪些命令失败过、哪些文件总被一起改、哪些工具或审批步骤经常出现。关键工程挑战是隐私和安全，所以 secret redaction 与本地优先是必要设计，而不是附加功能。它值得关注，因为后训练数据和个人/团队记忆开始在同一条线上：生产轨迹既可以被摘要成上下文，也可以被筛成训练/评测样本。对后训练软件工程来说，我们需要更系统地记录日志来源、脱敏策略、召回依据和记忆版本，否则记忆层可能把旧错误或敏感信息带进新任务。
🔗 链接：https://github.com/vshulcz/deja-vu ｜ 代码：https://github.com/vshulcz/deja-vu

### Codex App Server：OpenAI Codex 的 Thread/Turn/Approval 双向 harness 协议
MCP 很适合把外部工具接给模型，但一个完整 coding agent 产品还需要处理会话生命周期、流式 diff、命令审批、线程恢复、多客户端状态和长任务回放。OpenAI Codex 仓库里的 app-server README 展示了这个更内层的 harness 协议：它使用类似 JSON-RPC 2.0 的双向消息，围绕 thread、turn、item、approval 等对象组织 agent loop。客户端可以 `thread/start` 创建持久会话、`turn/start` 触发 agent 工作，并处理 `item/commandExecution/requestApproval` 这类由服务器发起的审批请求。它还把 MCP 放在工具桥接层：app server 可以按 thread 的配置登录 MCP OAuth、调用 MCP tools，但 agent loop 与 UI/CLI/IDE 的交互不直接等同于 MCP。这个分层很关键，因为很多团队容易把“接了 MCP server”误认为“有了完整 harness”。真正产品化的 coding agent 需要 App Server 这样的协议来表达 streaming、approval、resume、permissions 和 thread state。对后训练软件工程来说，这意味着轨迹 schema 不应只保存 tool call，还应保存 turn 边界、approval 决策、权限 profile、compaction 事件和客户端如何响应 agent 的请求。
🔗 链接：https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md ｜ 代码：https://github.com/openai/codex

### PolyWorkBench：多语言长程工作流揭示 agent harness 与语言复合误差
许多 agent benchmark 默认整个任务在英语环境里完成：输入、推理、工具结果和输出都使用同一种语言，这和跨国企业真实工作流不太一致。PolyWorkBench 构造了 67 个长程 workplace tasks，覆盖 commerce、knowledge work、legal analysis、localization 和 manufacturing 等五个领域，并涉及十种语言和异构文件。它不是单轮问答，而是要求 agent 处理文档、表格、多语言资源，调用外部工具，并产出结构化结果。评测上，它结合结构化评分、可执行验证和 LLM 语义评估，用来同时检查功能正确性和语言一致性。结果显示，强 agent 在多语言工作流下会出现明显性能下降，错误会跨推理、工具调用和最终输出逐步累积。它按 Medium 收录，因为不是 coding-agent 专项，但对 agent evaluation 很有启发：语言不是表层翻译问题，而是会影响过程决策和证据理解。对后训练软件工程来说，跨语言 issue、日志、文档和 API 错误会成为真实轨迹的一部分，训练和评测都需要记录语言切换点与工具输出语言。
🔗 链接：https://arxiv.org/abs/2607.06008 ｜ 代码：None

### MILES：可学习选择的模块化 instruction memory，用于自改进推理
很多 agent memory 方法把整段成功解法或反思文本存起来，下一次遇到类似任务再检索，但这种粗粒度记忆很容易不适配新问题。MILES 把记忆拆成更小的 modular instruction units，每个单元包含 sub-goal embedding 和 sub-instruction，并配有可学习的 selection head。它的流程是先用粗检索扩展记忆和收集监督，再在细阶段用学习到的选择头重排候选记忆，帮助 uncertain samples 做推理。这个设计的关键是，记忆选择不再只是 embedding 相似度或启发式规则，而是直接面向最终答案正确性优化。它按 Medium 收录，因为主要场景是推理而非软件工程，但对 skill management 很相关。Coding agent 的技能和经验也会遇到同样问题：一条旧经验是否该用，取决于当前任务子目标、仓库状态和验证信号，而不只是文本相似。对后训练软件工程来说，未来的 skill/memory 系统需要记录“为什么选中这条记忆、选中后是否帮助了任务、是否造成负迁移”，这样才能训练更可靠的记忆选择器。
🔗 链接：https://arxiv.org/abs/2607.06974 ｜ 代码：None

### VulnHunter：Capital One 开源 agentic source-code security analysis
安全代码审查是 coding agent 很自然但也很危险的场景：模型可能指出看似合理的问题，却没有可复现证据；也可能漏掉跨文件数据流和业务逻辑漏洞。Capital One 的 VulnHunter 把自己定位为 agentic AI security tool，采用 attacker-first analysis 直接分析 source code，7 月 7 创建后达到约 316 stars。它的企业来源值得注意，因为金融机构对安全审计、可追溯和误报控制的要求通常更高。虽然公开搜索片段没有足够细的 benchmark 数据，因此本期按 Medium 而不是 High 收录，但它代表公司级 security team 正在把 agent 用到源代码风险分析上。工程价值在于，如果安全 agent 要进入生产，必须把 findings 和 evidence、复现步骤、受影响路径、风险分级和人工确认绑定，而不能只输出自然语言风险列表。它也会和 MCP、browser、sandbox、secret scanner、dependency scanner 形成组合，而不是独立工具。对后训练数据来说，安全审计轨迹需要保存“攻击假设→代码证据→验证命令→反例/误报排除→最终 finding”的完整链条，才适合作为训练样本。
🔗 链接：https://github.com/capitalone/VulnHunter ｜ 代码：https://github.com/capitalone/VulnHunter

### OpenAI：A scorecard for the AI age
OpenAI 7 月 17 发布这篇官方文章，主题是企业如何衡量 AI 投资价值，因此按 Low 官方源记录。文章的核心指标是 Useful Intelligence per Dollar，也就是不要只看 token 单价，而要看 AI 实际完成了多少有用工作、每个成功任务成本多少、结果是否可靠，以及规模化后每一美元是否买到更多工作。它特别强调 cost per successful task：一个便宜模型如果需要更多尝试、更多人工 review 和更多返工，最终未必便宜；强模型如果一次完成高质量任务，可能在完整流程上更划算。文章还把 dependability 拆成 ready to use、needs correction、needs escalation，这与 coding agent 的“可直接合并/需修补/需人工接管”非常相似。它不是技术论文，也没有公开新 benchmark，所以不应提升到 High。对后训练软件工程的启发在于，成本治理必须进入评测：pass rate 之外，还要统计尝试次数、人工审查、修复轮数、工具开销和最终可用工作量。官方源要求强制检查，因此本期记录为低优先级重点官方更新。
🔗 链接：https://openai.com/index/a-scorecard-for-the-ai-age/ ｜ 代码：None

### 🔥 大佬观点

**Hacker News：Towards a harness that can do anything，社区把焦点放到“确定性检查 + agent 复修循环”。**  
HN 讨论的核心不是再写一个更长 prompt，而是把典型开发循环拆成可执行的测试、失败归因、子代理调查、修复、提交和继续下一项。值得注意的是，评论里提到通过 ACP/API 启动新 session、配置 MCP、运行测试后把失败重新喂回原会话，这说明社区正在把 agent workflow 当作可编程控制系统。🔗 https://news.ycombinator.com/item?id=48921077

**Manu Bhardwaj / PolyWorkBench 讨论：最贵的错误是用更聪明模型修补 scaffolding 问题。**  
围绕 PolyWorkBench 的社区观点强调，同一模型在不同 harness 下可能出现很大分数差距，因此企业不应把所有失败都归因于模型能力不足。这个 insight 很贴合本日报主线：文件选择、工具验证、重试、停止条件和多语言处理都是工程层，许多收益可以通过 harness 改造获得。🔗 https://www.linkedin.com/posts/ifitsmanu_the-most-expensive-mistake-in-ai-right-now-activity-7481474794321018882-hMXW ｜ https://arxiv.org/abs/2607.06008

### ⭐ 超火仓库/项目

**xai-org/grok-build：7 月 14 创建，约 16.5k stars，xAI 把 coding-agent harness/TUI 推到社区中心。**  
它火在“新模型供应商也要自带 agent harness”这个信号：开发者不满足于裸 API，而是在比较终端工作台、状态控制、扩展点和本地 workflow。即使公开细节仍有限，高 star velocity 已足以说明 coding-agent runtime 仍是最热基础设施层。🔗 https://github.com/xai-org/grok-build

**ogulcancelik/herdr：约 17.6k stars，7 月 17 仍有预发布，把多 agent 管理变成终端基础设施。**  
它解决的是多 agent 并行时的人类监督瓶颈：谁在跑、谁卡住、谁等待批准、谁已经完成，一眼可见。socket API 又让 agent 可以自建 pane 和读取其它任务输出，向“agent 管 agent”迈了一步。🔗 https://github.com/ogulcancelik/herdr

**Graphify-Labs/graphify：约 90k stars，7 月 17 release，把多模态项目上下文变成知识图。**  
它火在解决大仓库 agent 的上下文供应链问题：不是继续扩大窗口，而是用结构化图把代码、文档、schema、图像和视频连接起来。对真实团队来说，这类 graph artifact 也方便人类 review agent 是否真的理解了系统。🔗 https://github.com/Graphify-Labs/graphify

**ChromeDevTools/chrome-devtools-mcp：约 47k stars，v1.6.0 让浏览器调试成为 agent 标准工具面。**  
前端 agent 要可靠交付，必须能进入真实 Chrome 观察 console、network、性能和截图，而不是只靠静态代码推断。Google 官方把安装路径整理到 DevTools for agents 文档后，它更像 web-agent harness 的基础设施，而不是单个社区插件。🔗 https://github.com/ChromeDevTools/chrome-devtools-mcp
