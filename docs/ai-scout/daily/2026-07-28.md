## 📝 逐条讲解

### ESAT：只靠 API spec 合成多步 API-calling agent 训练轨迹
训练 API-calling agent 最大的工程瓶颈不是写 prompt，而是要为每个领域搭真实后端、填充数据库、维护可执行 API，再收集多步调用轨迹。ESAT 的思路是把这件事从“建一个完整环境”降级成“给一份 API specification”：先按难度、读写类型、多 app 组合和 API 覆盖度生成任务，再让 teacher agent 逐步调用 API。真正的关键是旁边有一个 LLM simulator，像一个临时数字世界一样根据任务、调用参数和历史状态生成模拟 API 返回，因此轨迹里仍然有 read/write 状态变化，而不只是静态函数调用样例。最后再用 LLM judge 过滤不完整、不一致或冗余的轨迹，形成可用于 SFT 的数据集。论文在 AppWorld 和 OfficeBench 上报告，1.7B 到 27B 模型用 ESAT 数据微调后有明显提升，AppWorld 上甚至超过用真实环境训练任务轨迹收集的数据。它对后训练软件工程的启发很直接：如果 API spec 足够结构化，数据团队可以更快扩展到新工具域，先合成可训练轨迹，再把高风险域留给真实环境回归验证。风险也要记住：模拟器给出的世界状态必须被审计，否则模型可能学会“看起来合理但不符合真实后端”的调用习惯。
🔗 链接：https://arxiv.org/abs/2607.16900 ｜ 代码：None

### eslint-plugin-vibe-proof：把 coding agent 常犯错做成确定性 ESLint gate
很多团队给 coding agent 安装越来越多 skills，希望模型记住项目风格、性能约束和常见坑，但长会话和上下文压缩会让这些规则逐渐失效。`eslint-plugin-vibe-proof` 的观点很朴素：不要只把规则写给模型读，要把能形式化的错误写进不会忘记的 linter。它把 coding agent 常见的偷懒和坏模式做成 ESLint 规则，例如禁止无说明的 `eslint-disable`、避免重复 JSX props、避免低效数组链式操作、要求正则 hoist 等。这样 agent 写出坏代码时，不需要 reviewer 记得提醒，CI 或本地 lint 会直接失败，并给 agent 一个确定性的修复信号。这个项目热度不高，但它代表了很重要的工程方向：把“提示词里的最佳实践”迁移到可执行反馈环。对后训练数据来说，lint 失败、规则 ID、修复 diff 和最终通过状态都可以成为高质量轨迹标签，比“请注意代码质量”更可复现。
🔗 链接：https://github.com/SukkaW/eslint-plugin-vibe-proof ｜ 代码：https://github.com/SukkaW/eslint-plugin-vibe-proof

### semantic-review：把 git diff 重组为可评论的语义审查报告并回传给 agent
coding agent 生成 diff 以后，人类 review 的痛点通常不是看不懂代码，而是 diff 按文件顺序展开，真正的设计问题、风险点和重复模式散落在多个位置。`semantic-review` 让 LLM 先读 git diff，把改动重组为按 concern 分组的 HTML 审查报告，并把关键片段内联展示出来。人类 reviewer 在浏览器里直接对这些语义分组发表评论，点 Done 后，评论会以纯文本写到 stdout，调用它的 agent 可以把这些评论当成下一轮 change request。它支持 Anthropic API，也支持本机 `claude`、`codex`、`gemini`、`pi` 等 CLI 后端，说明它试图成为跨 agent 的 review harness，而不是某个产品的插件。它解决的真实问题是把“人类审查”从巨大 diff 的被动阅读，变成 agent workflow 中一个结构化、可回传、可自动继续的节点。对后训练软件工程来说，这类工具能产出非常有价值的偏好数据：哪些 diff concern 被人评论、哪些评论被 agent 修复、哪些语义分组容易漏掉，都能反哺 review agent 与 patch agent。
🔗 链接：https://github.com/mikker/semantic-review ｜ 代码：https://github.com/mikker/semantic-review

### ContextOps：用 Markdown/YAML 文件看板编排 coding agents 的 plan-assign-review 生命周期
很多团队把 agent 任务管理放在聊天上下文里，结果任务状态、验收标准、人工批准和历史决策很难被版本化，也很难跨工具复用。ContextOps 把 agent lifecycle 做成一个本地文件化看板：产品背景、PRD、任务、验收标准、事件和状态转移都存在 `.contextops/` 下的 Markdown/YAML 文件里。Claude Code、Cursor、Codex、Cascade 等 agent 通过根目录指针文件读取同一个 contract，只能从 `READY_FOR_AGENT` 取任务，完成后进入 human review，而不是随意改看板引擎本身。它还有本地 FastAPI + buildless JS UI，方便人类像看 Kanban 一样计划、分配、审查和批准任务。这个设计有工程价值，因为它把 agent orchestration 的状态从“某个工具的隐藏 session”变成 git 可 diff、可审计、可迁移的项目 artifact。对后训练数据工程来说，任务卡、验收标准、状态变化、人工拒绝原因和最终 diff 可以天然 join 成一条完整训练轨迹，而不是事后从聊天记录里猜。
🔗 链接：https://github.com/Phil200727/contextops ｜ 代码：https://github.com/Phil200727/contextops

### Old Coder skill：让 agent 先交测试计划、后交证据报告，而不是让人逐行读代码
Robert C. Martin 最近关于 coding agents 的观点很适合总结成一句话：如果你想利用 agent 的速度，就不能把主要精力放在逐行阅读它写的所有代码上，而要把它放进一套严格约束和验证关卡里。Old Coder skill 把这个观点做成可安装的 agent skill，流程是先写 SPEC/test plan，经人类批准后再进入 RED-GREEN-REFACTOR，最后跑一组 gauntlet checks 并产出 evidence report。它建议的关卡包括完整测试、类型检查、lint、复杂度、changed-line coverage、mutation testing、property-based tests、真实执行、供应链和 secrets 检查。人类主要审两份文档：开工前的测试计划和收工后的证据报告，而不是在每次 agent 改动后被迫通读所有 patch。它不是一个复杂系统，但把一个重要 workflow 明确成了技能包：先证明要测什么，再证明真的测过什么。对后训练软件工程来说，这类轨迹特别适合筛选，因为每个步骤都有可检查 artifact：计划、失败测试、修复、重构、最终证据和未覆盖风险。
🔗 链接：https://github.com/AmazingAng/old-coder ｜ 代码：https://github.com/AmazingAng/old-coder

### FlightRules：从 SigNoz traces 挖 release contracts，拦截 agent canary 行为漂移
生产 agent 的危险之处在于，最终用户看到的回答可能完全一样，但底层路径已经悄悄变坏，例如跳过 policy check、重复执行 payment refund、或者走了未知工具路径。FlightRules 针对的是这个 output evaluation 看不到的问题：它从 SigNoz traces 中重建 agent 执行图，把已批准版本的路径挖成 deterministic release contracts。新版本 canary 发布前，`flightrules gate check` 会比较真实 trace 和 contract，发现 skipped checks、duplicate side effects、unknown tool paths 或 behavioral drift 就失败。它还把 SigNoz 当作证据存储和控制面，不只读 trace，还能创建 dashboard、saved views 和 alert rules，再读回确认同步。项目星数很低，所以可信度标 Low，但机制非常贴合生产 agent evaluation 的未来方向。对后训练软件工程来说，它提醒我们评估不能只看输出文本或最终状态，还要把工具路径、span 属性、幂等性 ledger 和路径差异纳入轨迹质量信号。
🔗 链接：https://github.com/winsznx/flightrules ｜ 代码：https://github.com/winsznx/flightrules

### Bruriah：给 coding agents 一个“证据有出处、知识不能下指令”的项目记忆 MCP
项目记忆是 coding agent 的刚需，但把历史文档直接塞给模型也有风险：旧决策可能过期，文档里可能含有不该被执行的指令，模型也可能把“有人曾经这么写”当成当前规则。Bruriah 的边界设计很清楚：它索引 git history 和项目文档，让 agent 查询“为什么这里这样设计”，但返回的是带 provenance 的引用，而不是把知识当成指令注入。README 强调 recovered text 会被标记为 untrusted/stale，MCP 只暴露两个 read-only tools，没有生成模型依赖。它解决的真实痛点是让 agent 能追溯架构决策来源，同时不让历史材料越权改变当前开发行为。这个模式对多 agent 团队很重要，因为不同 session 可以共享“某个 commit/文档决定了什么”，但是否采纳仍由当前规则和人类判断。对后训练数据工程来说，记忆检索结果、引用 commit、agent 是否正确使用证据，以及是否忽略过期材料，都是值得记录的高价值信号。
🔗 链接：https://github.com/leonardoprimero/bruriah ｜ 代码：https://github.com/leonardoprimero/bruriah

### mcp-audit：扫描 MCP servers 与 skills 中的工具描述注入、凭证外传和下载执行
MCP server 的风险不只在代码里，也在它给模型看的 tool descriptions 里，因为这些描述会进入 agent 上下文，实际效果接近指令。`mcp-audit` 专门扫描 MCP servers 和 AI-agent skills 中的恶意模式，包括 “ignore previous instructions” 这类工具描述注入、凭证外传、`curl | sh` / `eval(fetch(...))` 下载执行、私钥助记词采集、敏感目录写入等。它的工程亮点是低噪声校准：URL、路径、安装命令等能力描述进入 informational tier，不会直接抬高风险分，避免安全工具因为误报太多被团队关掉。README 称它在 196 个官方 registry 公共 MCP servers 上做过校准，误报率从 14.8% 降到 1.0%，并发现了一个真正值得关注的 tool-description prompt injection。它适合放进 agent 连接第三方 MCP server 前的 CI 或预检流程。对后训练软件工程来说，MCP 工具目录本身是输入数据的一部分，扫描结果、风险类别和人类批准/拒绝都应成为 agent tool-use 轨迹的元数据。
🔗 链接：https://github.com/eltociear/mcp-audit ｜ 代码：https://github.com/eltociear/mcp-audit

### Rethinking Harness Evolution：用同预算 test-time scaling 重新审视自动 harness evolution
自动 harness evolution 最近很热，很多工作让 agent 根据 benchmark feedback 修改自己的 prompts、tools、memory 或控制逻辑，然后报告分数提升。这个论文提醒一个容易忽略的问题：harness evolution 本身也是一种搜索，如果它在同一批 benchmark 任务上反复试错，再在同一批任务上报告最终分数，就很难判断提升来自可泛化的 harness 设计，还是来自对测试集的适配。作者把 parallel sampling、sequential refinement、harness evolution 和 harness scaling 放到统一预算框架下比较，控制它们能看到什么 feedback、花多少推理预算、修改轨迹还是修改 harness。Terminal-Bench 2.1 实验显示，自动 harness evolution 并不稳定优于简单 test-time scaling；当搜索任务和评估任务分开时，优势也不容易泛化。它不是在否定 harness 工程，而是在要求更公平的评测协议。对本日报主线很有价值，因为我们不能只追逐“自动改 harness 分数涨了”，还要问是否有 held-out task、预算是否匹配、是否过拟合公开 benchmark，以及改动能否解释。
🔗 链接：https://arxiv.org/abs/2607.12227 ｜ 代码：https://github.com/rethinking-harness-evolution

### portable-resume-skills：9 类 coding-agent 会话源到 9 类宿主的本地离线 context 迁移
现在开发者经常在 Claude Code、Codex、Cursor、OpenCode、Qwen Code、Kimi、Pi 等多个 agent 之间切换，但每个工具的 session 存储格式都不同。`portable-resume-skills` 试图把“接着上一个 agent 的上下文继续工作”做成离线技能：从 9 类源读取本地 transcript 或数据库，再把有界上下文打包给 9 类目标宿主的新 session。它很强调 clean-room 和安全边界：reader 不调用源 agent CLI，不增加网络路径，恢复出的文本被标记为 untrusted 和 stale，而且是 inert handoff，不是 live restore。这个 distinction 很重要，因为迁移上下文如果直接变成新 agent 的指令，很容易把旧 session 的污染、误解或恶意内容带到新任务里。项目还有 PyPI 包和 marketplace install 证据，说明它关注的是跨宿主技能分发，而不是单一脚本。按 Medium 收录，是因为它不直接解决代码质量，但触及了 agent 工程的真实痛点：会话连续性、工具迁移和上下文可信边界。
🔗 链接：https://github.com/ImL1s/resume-skills ｜ 代码：https://github.com/ImL1s/resume-skills

### mcp-expect：用 Jest 风格断言给 MCP server 写 CI 测试
很多 MCP server 在 demo 时能跑，但真正接给 agent 后会暴露很具体的失败：工具没注册、schema 接受了错误输入、handler 挂住、返回结构和调用方预期不一致。`mcp-expect` 把这些问题做成 Jest 风格断言，让开发者写 `.mcptest.ts`，用 `expect.tool("search").exists()`、`rejectsInvalidInput()`、`respondsWithin()`、`returnsSchema()` 等 API 测 MCP server。它基于官方 `@modelcontextprotocol/sdk` client，支持 stdio 和 Streamable HTTP，失败时可以在 GitHub Actions 里产生 PR inline annotation。它的价值在于把 MCP server 从“手动让 agent 试一下”推进到普通软件工程的 CI 流程。虽然项目刚创建、星数很低，但这个薄层抽象解决了非常高频的工程问题。对后训练和 eval 来说，MCP server 的测试结果应先通过确定性 gate，再让 agent 使用；否则训练轨迹里混入的是工具实现 bug，而不是模型能力问题。
🔗 链接：https://github.com/fba5147/mcp-expect ｜ 代码：https://github.com/fba5147/mcp-expect

### Stormy Cookbook：把 X/Reddit/YouTube/TikTok 等社交数据统一成 REST + MCP agent 接口
AI Research Scout 这类任务经常需要读 X、Reddit、YouTube、TikTok、Instagram、LinkedIn 等平台，但每个平台 API、认证、限流、分页和数据形状都不同，agent 很难稳定使用。Stormy Cookbook 提供一个统一 cookbook：同一套 REST contract 和 Streamable HTTP MCP server 暴露 search、profile、emails、jobs 等能力，背后处理多平台数据、cache-first routing、durable jobs、shared provider rate limits 和 per-call metering。它不是开源后端本身，而是围绕 Stormy API/MCP 的 recipes 和接入说明，7 月 27 日创建后已有 72 stars，说明社区对“社交数据 agent front door”有实际需求。它解决的痛点是把 live social data 从 scraper 脆弱性和多 SDK glue code 中抽出来，变成 agent 可发现、可计费、可重试的接口。对本日报任务也有直接启发：社区热点采集如果要可复现，不能长期靠浏览器搜索和人工判断，应该有明确 API、任务 ID、成本信号和返回 schema。按 Medium 收录，是因为它偏商业 API cookbook，但对 Agent-Friendly Data API 很有代表性。

### OpenAI Work at the Frontier：43.5% 职业专属 ChatGPT 请求发生 task crossover
OpenAI 7 月 27 日发布 Work at the Frontier 系列首篇，分析超过 800,000 条美国 ChatGPT 用户工作相关消息，研究 AI 是否让人们跨越传统职业边界做事。它提出 task crossover：某个职业用户在 AI 中执行通常属于另一个职业的任务。报告称，在去掉写邮件、总结、排期这类泛用任务后，43.5% 的职业专属消息落在用户本职之外；工程任务也是外溢源之一，很多非工程岗位会用 AI 做软件排查、技术系统处理或编码相关工作。它不是 coding-agent post-training 技术项，因此按 Low 收录，但它是官方源近 30 天未覆盖的新发布。对 agent 工程的间接启发是，未来内部工具会被非专业用户通过 agent 调用，因此权限、解释、验证和升级路径必须面向“跨职能用户”设计，而不能假定操作者就是领域专家。对后训练数据来说，这类跨角色工作流会改变任务分布：训练样本不仅来自工程师，也会来自法律、财务、HR、客服等角色在 agent 帮助下做技术任务的轨迹。

### Anthropic：open-weights models 立场，反对类别禁令但主张强制安全测试
Anthropic 7 月 27 日发布 open-weights models 立场文章，回应围绕中国开源权重模型和潜在禁令的讨论。文章明确说 Anthropic 从未主张按类别禁止 open-weights models，认为没有危险能力的开放模型可以是公共品；真正需要关注的是强大算力流向、工业级蒸馏和足够强模型的安全测试。它提出的政策组合是限制向威权国家出售强大芯片、打击工业规模模型蒸馏，以及对足够强的开放和闭源模型都要求强制安全测试。它不是本日报主线的软件工程内容，但属于 Anthropic 官方源当天新发布，且与模型发布治理、开放权重风险评估和预发布测试有关。对后训练软件工程的间接价值是，它提醒我们“开放/闭源”不是唯一维度，能力测试、危险任务 eval、蒸馏追踪和发布前 gating 也会影响模型生态。低优先级收录它，是因为它技术细节有限，但官方可信度高且未在历史日报覆盖。

## 🔥 社区热点专栏

### 🔥 大佬观点

**Robert C. Martin / Uncle Bob：不要把信任建立在“读完 agent 写的所有代码”上，要建立在 gauntlet 上。**  
Old Coder skill 引用 Uncle Bob 的观点：为了真正利用 agent 生产力，人类不应逐行审完所有 agent code，而应把 unit tests、gherkin tests、QA procedures、quality metrics、mutation testing、coverage 等约束做成硬门。这个观点值得注意，因为它把 agent review 的重心从“阅读所有输出”转向“设计可复验的证据系统”，与本日报关注的后训练轨迹筛选和 eval gate 完全同向。🔗 https://x.com/unclebobmartin/status/2080257779395154409 ｜ https://github.com/AmazingAng/old-coder

**Hacker News harness 讨论：很多 coding-agent 进步可能藏在 harness，而不是模型权重里。**  
HN `Improving 15 LLMs at Coding in One Afternoon. Only the Harness Changed` 讨论中，多个开发者强调 startup hooks、codebase maps、脚本化工具和轻量 CLI 往往比继续调 prompt 更有边际收益。这个社区共识重要在于，它把“模型好不好”拆成“模型 + harness + context delivery + deterministic tools”的系统问题，也提醒评测必须固定或显式记录 harness。🔗 https://news.ycombinator.com/item?id=46988596

**SukkaW / vibe-proof：skills 会被上下文挤掉，linter 不会忘。**  
`eslint-plugin-vibe-proof` 的 README 很直接地指出，装更多 skills 会占上下文，长会话压缩后 agent 仍可能忘记 AGENTS.md 或技能规则；能形式化的规则应该下沉到 lint/static analysis。这个 insight 对团队很实用：把可验证约束变成代码，比反复提醒模型“请小心”更稳定。🔗 https://github.com/SukkaW/eslint-plugin-vibe-proof

### ⭐ 超火仓库/项目

**OneInterface/stormy-cookbook：约 72 stars，7 月 27 日创建，把多平台社交数据做成 MCP/REST cookbook。**  
它火在解决了 research/scout agent 的真实痛点：X、Reddit、YouTube、TikTok、Instagram、LinkedIn 各自 API 和数据形状不同，agent 很难稳定采集社区信号。Stormy 把这些统一成一个 API/MCP 入口，并显式处理 jobs、计费、缓存和 rate limits，比临时 scraper 更适合可复现信息管线。🔗 https://github.com/OneInterface/stormy-cookbook

**ImL1s/resume-skills：约 32 stars，持续推送到 07-28，做跨 9 类 agent 宿主的离线 context 迁移。**  
它热在命中多 agent 切换后的新痛点：Claude Code、Codex、Cursor、OpenCode、Qwen、Kimi、Pi 等工具的上下文不能自然接力。项目把恢复内容标为 untrusted/stale，并强调 inert handoff，不把旧会话直接变成新指令，这个安全边界比普通“导出聊天记录”更值得关注。🔗 https://github.com/ImL1s/resume-skills

**mikker/semantic-review + SukkaW/eslint-plugin-vibe-proof：低星但高信号，代表“人类语义反馈 + 确定性机器门禁”的组合。**  
semantic-review 让人类在 concern-grouped 报告上评论，再把评论回传给 agent；vibe-proof 则把常见错误转成 lint fail。它们共同说明社区正在把 agent 质量控制拆成两层：机器能判的交给 deterministic gate，人类只审机器难判的语义与设计问题。🔗 https://github.com/mikker/semantic-review ｜ https://github.com/SukkaW/eslint-plugin-vibe-proof
