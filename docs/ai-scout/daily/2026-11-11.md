## 二、逐条中文讲解

### 1. A Cost That Practice Accuracy Hides: Worked Solutions in Self-Generated Training Data and the Compositional Use of New Rules

合成训练数据时，规则旁边常放一道已经写好步骤的例题。模型照着例题把过程写短，采集更便宜，最后答案也对。题目只考“按这个规则算一次”时，这种省法看不出损失。规则还要在下一段接着用，例题可能已经把这一步替模型做完了。

这篇用一个 20 亿参数的推理模型学习两条虚构的定量规则。规则属于一个并不存在的电池元件，没有规则表时，基座模型写不出那个数值。采集分两种：只给规则表，或规则表再加上程序写好的例题。生成的目标只按最终答案对不对收下，微调和考试时把规则表和例题都拿走。练习题要求在一段过程里正向用一次；组合题要求同一条规则在前后两段里接着用。六遍之后，用程序核对过的数值签名，只给规则表的目标在前瞻测试的组合题上高 24.3 个百分点，95% 区间 14.6 到 34.0。没见过的参数上，两种做法的正向准确率都是 87.5%，组合准确率是 58.3% 对 23.6%。另一组独立抽取的目标重复了这个方向，高 14.6 个点，区间 2.1 到 26.0。把较短的例题目标训到十遍，使领域 token 大约对齐六遍的规则表目标，其他训练量会一起变，差距收到 16.3 和 6.2 个点；第二组的区间跨过 0，预先登记的检验不成立。六遍对六遍时，例题方案的采集 token 和更新时间更少，训出来的模型每做成一道组合题，生成 token 是规则表方案的 2.6 倍，另一组是 2.1 倍。

练习题做对了，还不代表新规则能接起来用。例题省下的采集，可能在组合用法上加倍还回来。

### 2. System Optimizations for Cost-Efficient Agent Harnesses

换一套提示词或工具，任务做成的比例往往还是跟着模型走。脚手架这边动得更明显的是账单。同一模型和同一批任务上，文中看到费用最多可以差到 2.6 倍。长会话比短会话贵一个数量级。省钱不能靠让人记得新开对话，也不能靠模型自己丢掉上下文。

Agency 插在现成脚手架外面。Claude Code、Codex 和一个较瘦的脚手架接到同一套接口，优化写一次就能换着跑。轨迹里露出五处可以下手的地方：工具输出很长、旧上下文还占着缓存、已经做完的子任务仍留在上文、找文件靠一遍遍搜索、可以一次发出的调用被拆成多轮。对应的五件事是压短工具输出、丢掉以后用不到的上下文、把结束的子任务收成栈、用文件元数据代替盲目搜索、把多次调用并到一轮。合在一起，每个模型和每个脚手架的费用都下降，费用比在 0.65 到 0.85 之间。所有任务平均，费用降到原来的 0.77，准确率比是 0.97。较大模型的准确率比在 0.97 到 0.99；Luna 在一部分文档任务上是 0.93，因为它没有按说明去用那张元数据表。省得多的是文档检索。文件名是随机编号、又放在目录树里时，费用降到 0.51 到 0.66；文件名本身能看懂、又平铺着放时，只到 0.81 到 0.96。编码任务少得多：SWE-bench 是 0.80 到 0.92，SWE-bench Pro 是 0.82 到 0.95，Terminal-Bench 2 是 0.90 到 0.96。单独让模型把调用并成一批，步数少了 19%，新输入多了 19%，费用升到 1.02，因为模型为了凑批多调了工具。摘要写不影响准确率，正文的准确率比是 0.97。没有公开代码。

编码轨迹里能丢掉的工具输出不多，费用只降到原来的八成到九成六。文件名看不出内容时，才降到大约一半。

**链接：** [原文](https://arxiv.org/abs/2611.12122)

### 3. Done Is Not Correct: Measuring Silent Failures and Self-Verification Calibration When LLM Agents Take CAD Actions

代理写一段参数化的零件代码，代码能跑、实体也能渲染，尺寸和装配关系仍可能是错的。只看有没有报错，或者代理有没有说“做完了”，这两件事会分开。几何已经画出来了，语义检查却没有过，这种失败以前很少被单独记一笔。

这篇放了 13 道题。每条要求都对应到几何内核可以量的性质，公差事先公布，并附有参考解。四个厂商的模型，每种条件 156 次。一次生成就交卷时，98% 的尝试声称完成，其中 14.1% 是静默错误：实体有效、明确说做完了、至少一项语义检查失败，按任务聚类的区间是 5.8 到 24.4。工具循环如果规定，没有测量过就不能声称完成，静默错误降到 3.2%，声称的精确率从 64% 到 96%。四个模型上只改这一条契约、反馈保持不变：旧契约是 14/156、精确率 68%，新契约是 5/156、精确率 96%。规划、编码、检查分成三个角色，精确率接近，成功次数并没有更高。单次生成时口头信心的校准误差是 0.32；加上这套验证后，四个模型里有三个的信心开始带有信息。作者把检查标准收紧以后，519 个重判里有 18 个从通过改成失败，没有反方向的改判，所以报出来的失败率是下限。盲审专家推翻了这 18 个静默错误里的 3 个，其中一个任务的规格本身有歧义。公差带放大或缩小到四倍，单次生成和工具循环的差别还在。

没测量过，就不该允许声称完成。多给一轮反馈，替不了这条契约。

**链接：** [原文](https://arxiv.org/abs/2611.10063) · [代码](https://github.com/rodriguescarson/cad-silent-failure-bench) · [数据](https://doi.org/10.5281/zenodo.22312792)

### 4. AutoBuddy: Evaluating Proactive, Always-On Agents on Task Discovery and Execution in a Simulated Workplace

现有的代理基准通常把任务原文交给模型。办公请求散在邮件、聊天和文档里，代理得先认出哪些事还欠着，再到对应的系统里做完。人和事如果不是从同一段历史里长出来的，就无法知道做对是什么样。

AutoBuddy-Bench 把员工、项目、业务系统和事件写成一张随时间生长的图，再渲染成邮件、聊天和记录。任务从那些产生义务的事件推导出来，正确结果由世界状态计算。评分看代理对工作区的改动。参考代理先从工作区找出任务，每条都要指回出处，再在另一次有写权限的会话里执行。只换骨干模型：十七个模型、同一世界里的 120 道题、每个模型三次。端到端从 Haiku 4.5 的 0.234 到 Opus 5.5 的 0.698，没被发现的任务记成 0。gpt-5.6-sol 的发现 F1 是 0.958，执行是 0.676；Opus 5.5 的发现 F1 是 0.925，执行是 0.739。gpt-6.1-sol 的发现 F1 仍有 0.944，执行掉到 0.548。较弱的模型主要漏任务，也会把别人的请求算进来：Haiku 4.5 平均漏掉 59.7 道，并把 71.3 条同事的请求列进去。较强的模型漏得少，失败改到执行，尤其是业务系统里的操作。没有公开代码。

发现了任务，还不等于做得成。最强的模型主要败在系统里的那一步。

**链接：** [原文](https://arxiv.org/abs/2611.12393)

### 5. SPRING-5: Measuring Tool Documentation Repair for LLM Agents by Efficiency

自动改工具说明的方法，通常用任务有没有做对来打分。说明写错时，模型可能一次就叫错工具，中间没有拒绝，也没有重试。准确率看不出它多花了多少次调用。

SPRING-5 有 20 个工具家族、344 道题。每个家族有一份故意写坏的说明、一份手写的正确说明、一个确定性后端和答案。正确说明不给方法看，只在构建时检查它必须能走到理想的调用路径。费用按相对这条路径多出来的调用计，答错则记满整个调用预算，所以这个指数大体跟着完成率走。他们另外报告做成一题所用的调用，这项不惩罚答错。2,644 次基线会话里，54% 的错误答案没有任何被拒绝的调用、拒绝或重试。同一份说明评两次，费用可以差到 0.64 到 1.56 倍，大约八次比较里有一次会只因噪声跨过常用的“算赢”门槛。对照这些检查，只改格式关上了从坏说明到理想费用的缺口的 1%，边用边改的循环关上 13%，把训练轨迹一次改完关上 33%，再给对错标签关上 58%。一次改完更好，是因为它读到的证据更多；只让它看循环所能看到的那些，优势就测不出来了。五个和十个工具同时在上下文里时，效应还在，基线费用不变。只有机器写的说明会把调用送到错误的工具。在 BFCL 上，62% 的留出问题用原装说明已经能答，所以那里合并起来看是空的。文中给出的代码仓库在 11 月 11 日打不开。

改工具说明要看它少花了多少调用。一次读完证据，比边用边改更要紧。

**链接：** [原文](https://arxiv.org/abs/2611.10040)

### 6. Correct Answers from Insufficient Histories: A Controlled Study of Agent Memory Evaluation

记忆评测常把模型的答案和完整历史的标准答案去对。对上了，只说明它说出了那个答案，不说明眼前这段记录已经够推出这个答案。两条都合规的历史可以显示得一模一样，正确答案却不同。

这篇用可以执行的设备日志把三件事分开：和标准答案是否一致、证据是否够、在当前上下文里弃权或回答是否合适。不够的定义是两条合法历史给出逐字节相同的可见上下文，但答案不同。公开的时间线和查询截止点用来证明哪些前缀是够的。80 段确认历史里有 203 个不够的原始前缀。Qwen3-32B 对上了其中 87 个隐藏答案，合适的弃权只有 7 次。同一批前缀上，固定输入的 DeepSeek-V4-Flash 对上 85 个，弃权 21 次。每个读者发出 1,600 次请求。把记录收成紧凑表格以后，合适行为的估计仍不确定：Qwen 高 3.16 个百分点，区间 0.00 到 6.57；DeepSeek 高 2.46，区间 −1.84 到 6.94。另有一个留出的裁判正确率 99.38%，但仍有支持错误和截断。一个确定性基线做对了全部构造出来的例子。这是两种托管阅读配置上的评测诊断，没有推广到自然语言证据，也不是一套通用记忆系统的增益。

答对了，不代表眼前的历史已经够用。不够的时候，这些模型很少弃权。

**链接：** [原文](https://arxiv.org/abs/2611.11840)

### 7. ChainCheck: Near-Perfect Evidence-Sufficiency Scores Can Conceal Sensitivity to Construction Artifacts

证据够不够的基准，要模型分辨一组完整段落和一组被拆断的推理链。断链如果是改写出来的，模型可能只是在认改写留下的痕迹。分数接近满分，甚至交叉对照为正，也不能单独证明它在做多跳推理。

ChainCheck 把验证器认可的反事实格子，和只含改写痕迹的基线配成对。在 2,214 对 HotpotQA 的探索性交叉对照里，一个从不读这条链的语言模型打分器，名义 AUC 是 0.997。只匹配一个字符串，就能把交叉的链敏感统计 CS4 打到上限 0.500。被评的 11 个系统在 0.308 到 0.484 之间。这两项不是同一个指标。作者因此把正的 CS4 读成桥接是否前后一致，而不是语义上的多跳推理。每个系统对多出来的一处编辑也敏感，这些编辑在模型给出的自然度评分里是可察觉的。换到另一组 2,276 对 HotpotQA 上，事先在 MuSiQue 和 2WikiMultiHopQA 上登记的模式没有复现：六个训练过的读出器里有五个被编辑主导，参照裁判的选择性区间是 −0.007 到 +0.042，包含 0。裁判分数还随一批样本的排版变化。MuSiQue 和 2Wiki 的记录是公开的，HotpotQA 的记录和微调过的检查点没有公开，外部只能部分复现。

不读链条也能把证据分打得很高，但这是探索性对照。预先登记的独立集上，这个选择性没有复现。

**链接：** [原文](https://arxiv.org/abs/2611.11965)

#### 1. tinker-ai-skill

编码代理的会话里已经有仓库、工具和这个人改错的习惯。把它们收成微调数据时，如果按普通聊天记录来切，一次工具调用会和它的结果拆开。整份数据共用同一套假名时，模型还会把假环境背下来，用到真仓库上。

这个仓库是一份给代理执行的技能，外加十一支脚本。它从 Claude Code 的原始会话做起：按校验和复制，跳过子代理和很短的会话，必须保密的项目整份排除。每条凭据按值替换，每个会话单独随机一套人名、目录和邮箱，检查到泄漏就失败。切段用目标模型自己的渲染器量长度，不把一次工具调用和它的结果拆开。第一段之后的每一段补上一段确定的工作上下文，模仿脚手架压缩长会话的方式。留出按整段会话做，种子固定。训练走 Tinker 上的低秩适配，先做不花钱的冒烟，再显示费用。仓库说明 Tess-4-27B 和 Tess-4.5-27B 是用这套流程从自己的会话训出来的。这两个模型页可以打开，本次没有重训或复测。仓库建于 11 月 7 日，本次读到 307 star、37 fork，MIT，最近推送也是 11 月 7 日。没有逐日差额。

自己的会话可以收成一份本地模型。假身份要按会话换，长会话的后半段要带上压缩后的上下文。

**链接：** [GitHub](https://github.com/drost-ai/tinker-ai-skill)

#### 2. satmux

地球同步卫星的客舱网络，往返常常要六百多毫秒。每个新网站如果都重新做域名解析、连接和握手，再遇上客舱对 443 端口的代理把连接丢掉，代码仓库和包索引会超时。座位上的带宽限额不是唯一的限制。

satmux 在靠近卫星落地站的虚拟机上维持一批非 443 端口的长连接，把多个网站的流量摊上去。本地打开一个新流时，不必先空等一个完整的卫星往返。一条路径把传输层安全留在笔记本上，另一条由地面虚拟机取回页面、压缩后再传回来。作者记录了一次 Inmarsat 客舱网络上的测量，往返大约 620 毫秒：六个来源里原来有三个超时或被重置，经这套转发后六个都返回，合计从 19.13 秒到 5.35 秒。这是一次飞行中的自测，不是重复实验。物理上的一跳仍在，文中写大约 580 到 650 毫秒，它也不绕过已经登录的付费门户。仓库建于 11 月 7 日，本次读到 1,034 star、49 fork，MIT，最近推送是当天。没有逐日差额。

它省的是每个新网站重复支付的握手，不是卫星本身的距离。测量来自一次飞行。

**链接：** [GitHub](https://github.com/Th0rgal/satmux)

#### 3. WowType

Linux 上打一整句拼音，简拼、错键和语音常常要分开凑。语音又常常把录音送出本机。日常要的是一句拼音直接出词，相邻键按反了还能认出来，而且默认不离开这台电脑。

WowType 是 fcitx5 下的拼音输入法。整句可以一次打完，也可以先上屏前半句。拼音没打全就给出词，打全的词排在第一。它认相邻键、键序颠倒、多按和漏按，并记住用户选过的词，三十天不用再淡掉。语音按住右 Alt 说，松开上屏。项目写明这段识别用微信输入法的离线模型，在本机完成，不上传录音。互译要用户自己填接口，只有切到翻译时才把那一句发出去。词库约 89 万条，项目写按一个键一般在几毫秒内出候选。这些是项目自己的说明，不是独立评测。仓库建于 11 月 6 日，本次读到 431 star、21 fork。说明页标注 MIT 与 Apache-2.0，仓库的许可证字段为空。最近推送是 11 月 10 日。没有逐日差额。

它把整句、错键和离线语音收进一个本机输入法。速度和识别效果来自项目自己的说明。

**链接：** [GitHub](https://github.com/Gloridust/WowType)
