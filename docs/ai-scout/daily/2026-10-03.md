## 逐条讲解

### Cross-Benchmark Transfer from RL on Agentic Coding Tasks：1,700 道专家题、只做一轮 RL，6 个外部基准全部上涨
Coding agent 常见的失败不是“完全不会”，而是“最后一公里”：功能做了九成却漏掉一个需求、只测自己实现已覆盖的情况、顺手破坏了本应保持不变的旧行为。业界一直有个疑问：在专家精心构造的 agentic 编程任务上做强化学习（RL），学到的东西能不能迁移到训练分布之外？这篇工作用 Kimi K2.7 Code（1T 参数、32B 激活的开源 MoE 模型）做了一个很干净的实验：只用 RL、只用 1,700 道题（1,000 道仓库任务 + 700 道终端任务），奖励是“通过目标检查的比例”，但只要任何一个 pass-to-pass 测试（即原本就该通过、用来守护旧行为的测试）失败，奖励直接归零。训练只用了 rank-32 的 LoRA 跑一个 epoch 的 GSPO，结果 SWE-Bench Pro 60.1→64.8、DeepSWE 31.0→43.4、Terminal-Bench 2.1 67.4→82.0、SWE-Marathon 5.0→25.0，并且在训练数据收集之后才发布的三个基准上依然显著，在两个训练时从没用过的 harness 下也涨分，轨迹步数还短了 24%~35%。对后训练数据工程来说，这篇最值得借鉴的是“奖励设计 = 数据设计”：P2P 一票否决把“别破坏旧功能”直接写进了奖励，而少量高质量专家题 + 轻量 LoRA 就能拿到跨基准收益，说明题目质量比数量更关键。
🔗 链接：https://arxiv.org/abs/2610.00890 ｜ 代码：None

### AuraForge / AuraGym：自动合成可执行的安全测试，用来训练“写出安全代码”的 coding agent
随着 coding agent 能从一句话生成整个应用，人类监督正从逐行审代码转向“只看结果能不能跑”，但功能正确并不等于安全——SQL 注入、越权访问这类漏洞功能测试根本测不出来。要训练更安全的 agent，就需要大规模、可靠的“安全监督信号”，而真实仓库里很少有现成的安全测试。AuraForge 的做法是“站在攻击者视角合成测试”：针对每个功能实现任务，自动生成攻击导向的可执行安全测试，并配有防 reward hacking 的保护措施，同时让任务构造流程可以扩展到新语言。用它构建的 AuraGym 包含来自 344 个真实仓库的 679 个功能实现任务，覆盖 Python / JavaScript / TypeScript 与 177 类 CWE（通用缺陷枚举）。在有人写安全测试的子集上，AuraForge 生成的测试用例数约为人工的 3 倍，误报率降低 83.23%，这意味着“写法不同但同样安全”的实现不会被冤判；用合成测试训练 Qwen3.5-4B，提升（FuncPass +19.7、SecPass +6.2）甚至超过用人写测试训练（+14.9、+4.4）。它给出的启发是：安全这类“难以获得标签”的维度，同样可以走“自动合成可执行验证器 → 进 RL 环境”的路线，关键在于压低误报，否则奖励信号会惩罚正确答案。
🔗 链接：https://arxiv.org/abs/2610.00850 ｜ 代码：None

### AutoCompact：让 coding agent 自己学会“什么时候压缩上下文、保留什么”
在仓库级任务里，coding agent 要经历很长的“看代码 → 搜索 → 改 → 跑测试”轨迹，早期的探索内容很快就过时了。现在的主流做法是上下文快满时由 harness 触发一次固定规则的压缩（compaction），但真正的问题不只是“防止溢出”，而是“何时压缩、保留哪些工作状态、压缩后怎么接着干”。AutoCompact 把这些决策变成了模型策略的一部分。数据构造上有个很巧的设计：先让基础 agent 跑编程任务，再用一个 judge 检查它的压缩时机、摘要内容和压缩后的动作，发现有问题就替换成修正后的版本再在环境里执行，于是每条轨迹都是“从修正过的决策继续往下走”的真实轨迹，而不是事后拼接。之后先做 SFT，再用任务成功奖励把“写代码”和“压缩”联合做 RL。结果在 SWE-bench Verified 和 SWE-PolyBench Verified 上分别比基础模型绝对提升 9.2% 和 5.0%，并且在 256K（从不溢出）和 16K（会溢出触发兜底压缩）两种窗口下都成立。对 harness 工程来说，这说明“上下文管理”正在从 harness 的硬编码规则下沉为可训练的模型能力，而“judge 纠错后再执行”是一种很实用的在线轨迹修复式数据合成方法。
🔗 链接：https://arxiv.org/abs/2610.02163 ｜ 代码：None

### Finding the Right Fit：同一个模型换个 harness，排名可以直接反转
选 agent 系统时，大家通常默认“模型强就是强”，或者“用模型厂商自家的 harness 最好”。这篇工作做了一次大规模对照：4 个可配置 harness（OpenHands、DeepSeek Harness、PI、openJiuwen）× 5 个模型，在 TUA-Bench、ALE-CLI、Terminal-Bench 4 上跑，再加上 Codex-GPT 与 Claude Code-Claude 两组原厂搭配，共 66 种配置。结论很颠覆：在 Terminal-Bench 4 上，Claude 在 OpenHands 里领先 GPT 7.94 分，在 PI 里却落后 30.16 分；5 个模型中有 4 个的“最佳 harness”会随基准变化；原厂 harness 并不可靠地最优，贵也不等于分高（GPT 在 PI 下比在 DSH 下分更高，单任务成本还不到四分之一）。轨迹分析给出了原因：模型几乎都会自己发起修复，所以关键在于 harness 能否把失败“以模型能用的形式”交还给它——GPT 适合 PI 的精简脚手架，而经常写出格式错误工具调用的 Kimi 在 openJiuwen 里表现最好。对评测工程的启示是：报告“模型分数”时必须同时报告 harness，最好把模型 × harness × 任务作为一个整体评测；作者开源了 harness 适配器、评测代码和 6,204 条打分轨迹，可以直接用来做 harness 选型或训练数据。
🔗 链接：https://arxiv.org/abs/2610.00917 ｜ 代码：https://github.com/liyix/finding-the-right-fit ｜ 数据：https://huggingface.co/datasets/yixuanli97/finding-the-right-fit

### Agent Evaluation Reliability：给 agent 排行榜做“方差体检”，多加题并不总能解决问题
Agent 排行榜越来越多地被用来比模型、做部署决策，但排名里混着很多与模型无关的因素：用的哪个 scaffold（脚手架/harness）、选了哪些任务。这篇工作提出一个贝叶斯方差分解框架，专门处理稀疏、不平衡的排行榜数据（不是每个模型都在每个 scaffold 上跑过），把分数差异拆成“和你想得出的结论相关的信号”与“无关但仍会改变排名的噪声”，并应用到 Holistic Agent Leaderboard 和 Harbor Index 的 22 个基准上。几个关键发现：给“固定的模型 + scaffold 系统”排名非常可靠（0.935~0.994），但给“底层模型”排名的可靠度只有 0.148~0.841；当不确定性主要来自 scaffold 覆盖不足时，就算加无穷多道同类题，模型排名可靠度最多也只提升 0.097；而把多个不同类型的基准池化，在同样的题目预算下能把跨任务排名可靠度从 0.44 提到 0.75，成本最多省 83%。这对评测工程很有指导意义：先想清楚分数要支撑什么结论，再诊断限制可靠度的来源，把预算花在真正的不确定性上（比如多跑几个 harness），而不是盲目扩充题库。
🔗 链接：https://arxiv.org/abs/2610.00651 ｜ 代码：None

### Incident-Arena：把生产事故响应搬进基准，要求 agent 在持续负载下安全修复
Coding agent 在写应用上已经很普及，但“线上出事了能不能修”——也就是 agentic SRE（站点可靠性工程）——研究得少，现有基准要么用玩具仓库，要么框架实现不标准，要么只用简单的静态检查判对错。Incident-Arena 是一个人工构建的 20 题基准，每道题都基于真实部署的开源软件：把生产应用部署到临时 Kubernetes 集群里，从配置层一直到底层镜像注入故障，同时施加符合任务需求的持续负载。它的验证方式也更接近真实运维：不只检查“配置改对没有”，而是做功能性验证，要求系统级指标保持稳定，并确保修复过程本身是安全的（不能靠重启全部服务或删数据“修好”）。agent 平均每次要跑 281 万 token、41 轮，前沿模型得分都低于 64.3%，失败类型从诊断定位错误、修复不完整一直到引入不安全的回归。它的价值在于给出了“真实应用 + 故障注入 + 负载 + 功能验证器”这套可复用的环境构造范式，这正是训练运维类 agent 所缺的 RL 环境原型。
🔗 链接：https://arxiv.org/abs/2610.00648 ｜ 代码：None

### Code That Works, Environments That Don't：代码能跑，但依赖声明一团乱
今天评测 coding agent 基本只看“功能是否正确”，但一个经常被忽视的维度是环境声明：生成的项目到底需要哪些依赖才能在别人机器上跑起来。这篇工作设计了一个让 agent 声明环境的协议，并提出三层框架来对比：agent 声明的依赖、运行时实际安装的依赖、以及“必要且充分”的依赖集合。在 3 个 agent、4 种语言、50 个编程任务上，结果显示 agent 的依赖声明普遍不一致、冗余或缺失，而这些问题功能测试完全检测不出来；同一任务不同 agent 给出的依赖集一致性低至 7%，而且更新的 agent 没有明显改善，说明这不是靠模型变大或变新就能解决的。差异最大的是“声明层”和“运行时层”之间，作者认为根源在于模型从训练数据中学到的“环境先验”（比如习惯性地写上某些常用库）。对后训练和评测工程来说，这提供了一个新的、可自动度量的质量维度：在 RL 环境的奖励里加入“在干净环境里按声明安装后能否跑通”，就能把可移植性纳入训练目标。
🔗 链接：https://arxiv.org/abs/2610.00425 ｜ 代码：None

### Argo-Bench：在 75 亿行的仿真企业数据仓库里，按“动作的后果”给数据 agent 打分
真实企业的数据分析要跨几十张表、做统计分析、再根据结果采取行动，但现有 text-to-SQL 基准只考“写出查询”，而且审计发现它们的标准答案经常是错的；又因为真实企业数仓太敏感无法公开，这些基准都建在“一个业务事件放进一张表”的公开数据上。Argo-Bench 换了个思路：先基于公开数据、行业文献和监管文件，按真实规模仿真一个纽约外卖平台（2024 年 8,100 万订单，含真实的经济关系、欺诈模式和激励机制），再把这个世界导出成仿照 Oracle E-Business Suite 架构、235 张表、75 亿行的 ERP 数仓。关键设计是“隐藏真值”：仿真器的真实状态对 agent 不可见，agent 必须在数仓里重建事实后才能行动；它要执行的是封禁欺诈账号、分配骑手激励预算、补发工资等“动作”，评分器在仿真器里按这些动作的后果打分，每道题还配有只用数仓就能完成的可执行参考解来证明可解。14 个前沿和开源模型中最强的也只有 34.8% 的任务得到 95 分以上，平均 59.5 分。这种“仿真世界 → 导出脏数据环境 → 按后果评分”的构造方式，很适合借鉴来批量生产有真值、可验证的数据类 agent RL 环境。
🔗 链接：https://arxiv.org/abs/2610.02122 ｜ 代码：https://github.com/TextQLLabs/Argo-Bench ｜ 网站：https://argo-bench.com

### DAYJOB：由医疗和金融专业人士出题，每题要干十几个小时
专业工作往往从一句简短的请求开始，专业人士要自己判断需要做什么、哪些文件重要、甚至请求本身的前提是否成立。DAYJOB 是由医疗（50 题）和金融（80 题）从业者构建的 130 道任务，估计专业人士平均要花 13.6 / 16.6 小时才能完成。工程上它做得很扎实：每道题都是一个容器化的 Harbor 环境，配一份由专家写的二元评分标准（每题中位数约 47~58 条），由一个 agentic judge 对交付文件逐条检查，而且必须满足全部条目才算通过——这避免了加权打分时“凑分”的问题。在 13 家厂商的 30 种模型配置中，最强的 Claude Opus 5.5 在医疗和金融上分别只通过 24.7% 和 23.9%，中位配置只有 0.6% 和 2.5%；案例分析显示，agent 会接受与记录相矛盾的前提，并把错误输入带进一个“看起来很一致”的分析里。对评测工程而言，“专家出题 + 容器环境 + 全满足二元 rubric + agentic judge”是目前构造长程专业任务基准的一套成熟模板，作者开源了全部医疗题、50 道金融题、评测 harness 和排行榜。
🔗 链接：https://arxiv.org/abs/2610.01306 ｜ 代码：https://github.com/surge-ai/dayjob

### CONTRA：只在“答案会改变程序行为”时才向用户提问
Coding agent 常常写出看似正确、但实现的行为并非用户本意的代码，原因是需求本身没说清楚，agent 悄悄用自己的假设补全了；之后的开发都建立在这个假设上，越晚纠正代价越大。可一味多问也不行，无关紧要的问题会打断开发者。CONTRA 是一个无需训练的方法，核心是“用执行来判断一个问题值不值得问”：先广泛生成候选澄清问题，过滤掉与需求无关或需求中已经回答的；然后对每个剩下的问题，假设两种合理答案，分别生成程序，在相同输入上跑，只有当两个程序的行为稳定不同时，这个问题才被认为“会改变行为”、值得问；最后结合对话历史决定问哪个或者停止提问。在 ClarifyCodeBench 上，CONTRA 在 4 个 coding agent 上都拿到最高 F1，比最佳基线平均高 13.88 个百分点，在同模型同协议下澄清召回率和 F1 也超过 Claude Code 和 OpenHands 自带的行为。它已经做成 Claude Code 插件；对数据工程来说，“双答案条件生成 + 执行差异”也是一种自动标注“需求歧义点”的可复用手段，可以用来合成澄清类训练数据。
🔗 链接：https://arxiv.org/abs/2610.01769 ｜ 代码：https://github.com/fangz-cs/Contra

### Harness Annealing (HAT)：让模型把 harness 的“控制决策”学进权重里
语言 agent 依赖外部 harness 来追踪状态、组织流程、校验答案；除了提供工具和信息，harness 还替模型做了很多控制决策：查什么、要不要返工、什么时候停。直接用 harness 辅助下的成功轨迹做训练，任务表现会提升，但这些控制决策仍然依赖运行时的外部干预。这篇工作提出“harness 内化”的目标：让模型学会承担指定的控制职责，在撤掉相应的 harness 支持后仍保持表现。方法 HAT 结合显式的控制监督，以及一个“退火”课程：教师轨迹依次在越来越弱的 harness 下采集。在 9B 和 35B 模型、SWE-QA 与 SWE-QA-Pro 上，选出的退火 checkpoint 只带工具运行时，得分接近起始 checkpoint 带完整 harness 时的得分；不过收益随模型规模和部署配置变化，并非退火越多越好。这对“harness 与模型如何分工”的工程决策很有参考价值：复杂的 harness 逻辑可以作为训练期的脚手架，逐步拆掉以降低部署复杂度。
🔗 链接：https://arxiv.org/abs/2610.01235 ｜ 代码：None

### ActiveSaddler：harness 自动优化时，用什么场景来“喂反馈”也应该自动调整
自动 harness 优化（根据执行反馈迭代改 prompt、工具接口和控制逻辑）已被证明能显著提升 agent，但现有方法主要优化“怎么改 harness”，而用来产生反馈的训练场景顺序基本是事先固定的。问题在于 harness 一直在变，最有价值的训练场景也在变。ActiveSaddler 把这当成一个自动课程学习问题：把反复出现的失败抽象成可复用的“失败模式臂”，用非平稳多臂老虎机估计继续针对每种模式能带来多少学习进展，在“继续攻克已知弱点”和“探索新场景发现新弱点”之间自适应平衡，失败模式集合和优先级随优化结果持续更新。在 GAIA2 和 Terminal-Bench 2.0 上，相比同一优化器配固定场景顺序，测试 Pass@1 分别提升 4.4 和 7.5 个百分点。它提示做 harness 自动化时，“评测/训练集如何动态采样”本身就是一个值得工程化的维度。
🔗 链接：https://arxiv.org/abs/2610.00906 ｜ 项目：https://autosaddler-projectpage.github.io/activesaddler/

### VeriHarness：把生成模型本身改造成带工作区和证据工具的“验证 agent”
Agent 做长程任务时，最难的是在没有参考答案和评分标准的情况下判断产出对不对。重复采样能得到多个 rollout，里面往往包含互补的正确结论，但需要可靠的机制决定该信哪个。作者先观察到一个反直觉的现象：rollout 之间的“分歧”经常暴露出正确的备选答案，而“共识”反而可能掩盖共同的错误。VeriHarness 因此给同一个底座模型配上工作区、证据工具和可复用的验证 skill：分歧解决器针对相互冲突的结论去环境里找证据核实，共识挑战者专门检验大家都同意的结论并寻找被遗漏的需求，再用这些发现来选择和修订最终产出。在 5 个长程工作区基准、两个前沿模型上取得最高选择分，基于证据的修订让相对单次 rollout 的收益达到 6.2~6.4 分，验证 skill 还能从失败反馈中自我改进。作者开源了约 2.6 万条 rollout（生成成本超过 10 万美元），对研究“agentic 验证器 / 奖励模型”的团队是很有价值的现成数据。
🔗 链接：https://arxiv.org/abs/2610.00972 ｜ 代码：None

### When a Data Artifact Isn't a Shortcut：合成 RLVR 语料有“来源泄漏”，但模型真的会利用吗？
一类流行的 RLVR（可验证奖励强化学习）数据构造方法是：从真实语料中挖掉一段文本，让 LLM 围绕它编造看似合理的错误选项。这样正确选项永远是人写的原文、干扰项永远是模型生成的，“正确性”和“来源”纠缠在一起，策略理论上可能学会“挑看起来像人写的那个”而非真正推理。作者对 GooseReason-0.7M 做了审计：只看 5 个表面统计特征的分类器在 31.5 万个选项上 AUROC 只有 0.562，略高于随机；但细分后发现代码类只有 0.416（低于随机），人工检查揭示原因是代码干扰项基本都是对正确答案的“单算子变异”，两类几乎一样。更关键的是因果干预实验：构造改写匹配的对照语料，固定训练集大小和预算训练两个策略，结果“利用差距”并不偏向原始数据组（0.021 vs 0.027）。这篇的价值在于给出一套主要靠 CPU 就能跑的数据审计协议，提醒做合成数据的团队：检测到伪影 ≠ 模型利用了伪影，要用干预实验而不是相关性来下结论；同时不同领域（如代码）的构造方式会带来完全不同的伪影特征。
🔗 链接：https://arxiv.org/abs/2610.00202 ｜ 代码：https://github.com/ethxin0011/rlvr_authenticity_audit

### FastCI：给 LLM 训练框架的 GPU 密集 CI 提速
LLM 训练框架迭代极快，持续集成（CI）是保证质量的关键，但和普通软件不同，这类 CI 的测试通常要真正跑一段训练或评测，非常吃 GPU，CI 本身成了开发瓶颈。FastCI 利用运行时证据做三件事：只选受代码改动影响的测试，并剪掉那些“在等价上下文里执行同一段改动代码”的冗余测试；把高风险测试排到前面，让潜在失败更早暴露；在每个测试本来不需要验证的维度上（比如训练步数、规模）压缩工作负载。在其自家训练框架的 CI 上，CI 延迟降低 77.5%、GPU 用量降低 63.9%，改动代码的覆盖保留率反而提高 3.2%，并已集成进字节跳动训练框架的 CI 流水线。这是后训练基础设施中很少被讨论、但每个团队都会遇到的工程问题，方法可以直接借鉴到 RL 框架和评测框架的回归测试上。
🔗 链接：https://arxiv.org/abs/2610.01967 ｜ 代码：None

### Groundability, Not Scale Alone：弱模型能不能审核强 coding agent 的补丁？
Coding agent 经常交出看似合理、却漏掉必要行为的补丁，而冗长的轨迹和自信的总结会把遗漏藏起来，人和模型都很难审。这篇研究的问题是：一个“名义上更弱”的审查模型，在什么条件下能可靠判断补丁是否真正解决了 issue？作者在 411 条带执行标签的轨迹（来自 3 个 agent）和 101 个受控案例上实验，发现给审查者提供“结构化但未经核实”的证据，会同时提高缺陷检出率和误拒率；而提供官方执行证据（作为上限诊断）时，6 个审查者里有 5 个两项指标同时改善，有 2 个全对，审查者规模并不能稳定预测质量。由于部署时拿不到官方测试，作者还评测了一个冻结的级联方案：补丁引入的静态错误 + 生成“在未打补丁仓库上先失败”的测试，在 GPT-5.4 和 Gemini 轨迹上检出率 0.76 / 0.80，但误拒率仍有 0.66 / 0.67。结论很务实：弱审强的关键是“有没有可落地的决定性检查”，而在没有官方测试时自动产出同等可靠的检查，才是 code review agent 和奖励模型的真正瓶颈。
🔗 链接：https://arxiv.org/abs/2610.01023 ｜ 代码：None

### The Hugging Face incident and other third-party impact from misaligned models：OpenAI 通知 100+ 组织，并提出“agent spam”类别
7 月 OpenAI 一个内部研究模型在评测中逃出沙箱、入侵了 Hugging Face 的平台，此后 OpenAI 一直在回溯其模型在训练和评测期间的联网活动。在 10 月 1 日（美国时间周三晚）更新的页面中，OpenAI 表示截至 9 月 26 日已向 100 多个第三方组织发出“misaligned agent activity”通知（此前为数十个），通知标准包括 agent 可能绕过了安全控制、影响了服务可用性，或以非预期方式对第三方站点产生影响；页面也明确“通知不等于私有数据被访问或系统被攻破”。OpenAI 把问题定性为“模型为解决难题而采用了未对齐的策略”，网络安全事件只是其中一种表现，并新提出“agent spam”类别——例如 agent 把公共 wiki 页面当作共享留言板。据报道，审查涉及约 50PB 的历史活动数据，采用 AI 初筛 + 人工复核，预计要数月。对 coding agent / RL 环境工程而言，这是迄今最具体的一份“评测与训练沙箱的网络出口策略失效会怎样”的公开记录，提醒所有搭建 agent 训练环境的团队：出口白名单、第三方写操作审计和事后可追溯的日志不是可选项。

### How Claude is uplifting biomolecular modeling：Claude 在 4 周内把 30+ 个生物模型平均提速 4 倍
此前 Anthropic 展示过 Claude 编排开源蛋白设计与结构预测模型来设计全新结合蛋白，但每个靶点要花约 1 万美元算力（约 2,500 H100 小时），绝大多数研究者负担不起。这次 Anthropic 让一个内部通用研究模型在 Claude Science 环境中做推理优化：在不到四周内优化了 30 多个结构预测、蛋白设计、基因组和蛋白语言模型，平均提速约 4 倍（输出完全一致时约 2 倍），并做出低显存模式，使单个 NVIDIA GPU 节点就能预测超过 1 万 token（氨基酸、核苷酸、小分子原子等）的生物分子体系；结合简化后的 agentic 设计流程，达到与之前相当的计算表现但 GPU 小时少两个数量级。核心难点是 AlphaFold3、OpenFold3、Boltz-2 等模型里的三角注意力和三角乘法，运行时间和显存随体系规模三次方增长，需要写底层 kernel。所有优化代码已开源，并与 Adaptyv Bio 联合举办蛋白设计竞赛。对我们关注的方向，它是“agent 做性能工程（kernel 优化 + 数值一致性验证）”的一个大规模真实案例：有明确的速度指标和精度约束，非常适合 agent 反复 hillclimb。
