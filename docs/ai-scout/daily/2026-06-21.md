## 📝 逐条讲解

### Open-SWE-Traces：20 万+ 多语言 SWE agent 轨迹数据集
训练 coding agent 最缺的不是静态代码，而是真实软件工程过程里的多步轨迹：agent 如何读 issue、查仓库、运行测试、改补丁、失败后恢复。Open-SWE-Traces 正是补这个缺口，它从 SWE-rebench-V2 的许可友好仓库出发，用 OpenHands 和 SWE-agent 两种 harness 生成 207,489 条轨迹，覆盖 Python、Go、TypeScript、JavaScript、Rust、Java、PHP、C、C++ 九种语言。一个重要设计是 dual-mode：MiniMax-M2.5 生成带显式 thinking 的轨迹，Qwen3.5-122B 生成更直接的 non-thinking 行为轨迹，让后训练模型既能学长程推理，也能学高效执行。作者还做了多阶段质量过滤，包括 AST 审计来剔除从元数据“抄答案”的 git hacking 行为。用这些数据微调 Qwen3-30B-A3B 系列后，最佳模型在 SWE-bench Verified 达到 61.7%，在 SWE-bench Multilingual 达到 57.1%，在 SWE-bench Pro 达到 36.8%。它对本日报最核心的价值在于，把 agent 轨迹从零散日志变成可公开复用、可蒸馏、可比较的数据资产。对内部后训练团队来说，这类数据集也提示我们要记录 harness 类型、语言、成功标记、最终 patch 和完整 tool trace，而不是只保存最终 diff。
🔗 链接：https://arxiv.org/abs/2606.16038 ｜ 代码：https://huggingface.co/datasets/nvidia/Open-SWE-Traces

### Auditing Reward Hackability：代码 RL 环境中可被错误补丁骗过的奖励审计
代码 RL 训练依赖 verifier：测试通过就给奖励，不通过就不给奖励。问题是很多真实仓库测试并不等于完整规格，如果错误补丁也能通过测试，模型会被奖励去学错误行为。本文直接测这个风险，在 49 个 SWE-bench Verified 样本里发现 28.5% 任务存在 Docker 验证的 incorrect patch pass，在 20 个 R2E-Gym 任务里也有 25.0%。作者进一步用 134 个前沿模型提交做 meta-analysis，发现同等人工难度下，hackable 任务会让 Pass@1 虚高 14.14 个百分点，说明这不是少数边缘漏洞，而会系统性扭曲 leaderboard 和训练信号。修复上，文章提出 FIX/KEEP/DROP 环境质量评分，并把 LLM 生成的补充测试先跑在 gold solution 上，只有 gold-sanity gate 通过后才交给 LLM judge。一个很强的工程发现是，LLM judge 单独漏掉了 61.9% 会误杀 gold patch 的测试增强，说明“让 LLM 写测试再让 LLM 判断测试”本身不够安全。对后训练软件工程来说，这篇非常重要：训练前必须先审计 reward 环境，否则 RL 会把测试漏洞放大成模型习惯。
🔗 链接：https://arxiv.org/abs/2606.16062 ｜ 代码：None

### JAMER / JamBench：Godot 专业游戏引擎上的项目级代码 benchmark
很多代码生成评测还停留在函数、单文件或常规 Web 项目，但真实软件工程常常依赖框架、资源文件、运行时状态和复杂项目结构。JAMER 把这个问题放到 Godot 专业游戏引擎里做，因为 Godot 的项目文件、场景文件和脚本都是文本格式，而且支持 headless execution。作者从 Game Jam 生态和 GitHub 大规模收集候选项目，用文件完整性、编译、运行稳定性和 60 秒行为采集组成确定性验证流水线，从 240,000+ 候选仓库里筛出 8,133 个可运行项目。JamBench 是其中 300 个手工复核项目，任务包括按主题从零生成项目，以及在不同粒度上补全真实项目代码。评测不只看能不能编译，还引入 Structural Completeness Score 和 Behavioral Alignment Score，衡量生成项目结构是否像真实项目、运行行为是否相近。结果显示，模型在小项目上还可以，但项目规模变大后 runtime pass rate 从 80.4% 掉到 5.7%；code agent 能提升编译率，却没有提升运行时行为质量。它的启发是，agent 评测要逐渐覆盖“架构设计 + 框架约束 + 运行时行为”，不能只用语法正确或单元测试通过代表真实工程能力。
🔗 链接：https://arxiv.org/abs/2606.19830 ｜ 代码：None

### Data Intelligence Agents：把企业数据集成做成可执行 artifact 的 ACA 系统
企业数据项目常常卡在反复交接：业务方知道字段含义，工程师负责建模和清洗，分析师写查询，但每次交接都会丢上下文。Data Intelligence Agents 的核心思想是，把这条流程改成由 autonomous coding agent 生成、执行、验证、修复具体 artifact，而不是只产出自然语言说明。系统由 Data Interpreter、Schema Creator、Query Generator 三个 agent 组成，但底层可以看作一个 ACA 在共享 workspace 中读写文件、脚本、schema、验证报告和查询日志。Data Interpreter 用代码探查 CSV、JSON、Excel 等源数据，Schema Creator 生成并验证关系数据库，Query Generator 再写 SQL 并实际执行。它还使用 artifact-based memory：过去确认过的 schema 经验、查询模式和 session lessons 只在当前数据上实时验证后才复用，避免 stale memory 直接污染答案。论文称该系统已部署到企业客户，并在七个 SQL benchmark、四类任务、四种方言上匹配或超过已有最佳结果。对 agent 系统工程来说，这展示了一条很务实的路线：把 agent 输出收敛成可审查文件和可执行验证，而不是让多角色在聊天里互相转述。
🔗 链接：https://arxiv.org/abs/2606.19319 ｜ 代码：None

### SafeClawBench：把语义同意、审计证据与沙箱危害分开评测
工具 agent 的安全失败不是一句“不该做但答应了”这么简单，它可能继续读文件、写 memory、发邮件、改数据库或触发代码执行。SafeClawBench 的贡献是把这些阶段拆开测，而不是把所有东西压成一个 attack success rate。它包含 600 个 adversarial tasks，覆盖直接 prompt injection、间接 prompt injection、tool-return injection、memory poisoning、memory extraction 和歧义诱导的 unsafe inference 六类攻击。评测报告三个端点：模型语义上是否接受攻击、审计 artifact 里是否出现危害证据、沙箱工具和状态里是否真正发生危害。一个关键发现是，语义检查和实际危害会错位：在 12,000 行 matched analysis 中，347 个 observed sandbox harms 里有 291 个发生在 semantic check 通过的行里。换句话说，只看文本层面的“模型没有明显答应攻击”会漏掉很多工具侧实际伤害。对后训练和安全 eval 来说，这篇提醒我们要把工具状态、memory 状态、审计证据和文本回答分层记录，否则训练和评测都会把不同风险混在一起。
🔗 链接：https://arxiv.org/abs/2606.18356 ｜ 代码：https://huggingface.co/datasets/sairights/safeclawbench

### Compositional Skill Routing / CompSkillBench：多技能链路的分解-检索-组合评测
技能库越来越大后，问题不再是“有没有某个 skill”，而是一个真实任务往往需要多个 skill 按顺序组合。例如“下载数据、转换格式、生成报告”至少需要 API 客户端、数据处理和可视化三类能力。Compositional Skill Routing 把这个问题形式化为三步：先把用户请求拆成原子子任务，再为每个子任务检索技能，最后把技能组合成可执行 DAG。作者提出 SkillWeaver，并构造 CompSkillBench：300 个组合查询、2,209 个真实 MCP server skills、24 个功能类别和标注的 skill chains。实验发现最大瓶颈不是 FAISS 检索，而是 decomposition granularity；标准 LLM 分解在 step-level category recall 上只有 34.2%。他们提出 Iterative Skill-Aware Decomposition，让第一轮检索结果反过来提示模型修正分解，使 decomposition accuracy 从 51.0% 提到 67.7%，并把上下文消耗降低 99% 以上。对 skill management 工程来说，这篇很有价值：大规模 skill routing 不能只做向量召回，还要让任务分解与可用技能词表互相校准。
🔗 链接：https://arxiv.org/abs/2606.18051 ｜ 代码：None

### GateMem：多主体共享记忆 agent 的访问控制与主动遗忘 benchmark
许多 agent memory 论文默认只有一个用户，但真实组织里的助手会同时服务医生、护士、学生、老师、家庭成员或多名员工。共享记忆里最难的不只是记得准，还要知道谁有权看什么、什么时候必须忘记、哪些请求是社会工程式恢复已删除信息。GateMem 专门评测这种 multi-principal shared-memory 场景，覆盖医疗、办公室、教育和家庭四类域。数据包含 91 个长篇多方 episode 和 2,218 个 hidden checkpoints，同时衡量合法长期请求的 utility、跨上下文授权边界的 access control、以及用户明确删除后的 active forgetting。实验发现没有一种方法能同时做到强 utility、稳健访问控制和可靠遗忘：长上下文 prompting 通常治理得最好但成本高，RAG/外部记忆省 token 却仍会泄露未授权或已删除信息。这对长期 coding agent 也有直接启发，因为项目记忆、用户偏好、组织 secret 和历史决策很可能被多个 agent 和多名用户共享。工程上，memory layer 需要 policy、身份、删除语义和 leak-target annotation，而不是只有“召回相似历史”。
🔗 链接：https://arxiv.org/abs/2606.18829 ｜ 代码：https://huggingface.co/datasets/Ray368/GateMem

### Decoupled Search Grounding：把实时搜索从模型原生能力拆成 MCP 控制面
生产 agent 常常需要实时搜索，但使用模型厂商的 native search 会把检索策略、provider、成本、延迟、证据注入和生成风格绑在一起。DoorDash 的 Decoupled Search Grounding 认为搜索不应是模型黑盒能力，而应是一个可配置、可观测、可迁移的系统边界。它用 MCP-compatible gateway 把搜索放到 reasoning model 外部，显式暴露 provider routing、source-aware context rendering、fallback、retrieval depth、exact/semantic cache 等控制项。论文还指出 native search 会带来 Search-Induced Verbosity：即使 prompt 要求“只输出最终实体”，模型也可能因为搜索上下文开始解释，破坏 JSON、boolean 或短答案这类下游 contract。公开 QA 上，DSG 在 SimpleQA 几乎追平 native accuracy（86.1% vs 87.7%），但搜索成本低 91%，warm-cache hit rate 达 99.4%，延迟低 68%。在 DoorDash 电商 Query Intent Understanding 生产负载上，它匹配或略超 native search，同时搜索成本降低 98% 以上。对 Agent-Friendly Software 来说，这说明工具接口要把 provider policy、成本、缓存和输出契约做成一等控制面，而不是把它们塞进模型 API 的隐式行为。
🔗 链接：https://arxiv.org/abs/2606.18947 ｜ 代码：None

### Beyond Static Leaderboards：用 predictive validity 重做 agent benchmark 排名
agent benchmark 越来越多，但单一平均分很难回答生产团队真正关心的问题：这个排名换到隐藏集、不同资产类别、不同检索策略、不同工具延迟后还成立吗？这篇 position paper 汇总了一个 MCP-based industrial-agent benchmark 的 14 个并行实现研究，并结合 7 个已有 agent benchmark，指出现有 leaderboard 普遍低估部署维度。作者主张不要只按 in-sample mean 排名，而要按 predictive validity 排名，也就是公开/样本内排名能否预测样本外排名。文中引用一个 149-team agentic competition 回顾：execution track 的 public-hidden Spearman 相关只有 -0.13，几乎不能预测隐藏评测；planning track 虽有 0.69，但私有分数仍明显下降。作者提出 12-tier measurement apparatus，覆盖成功率、工具卫生、规划质量、成本效率、失败模式、完整性、部署基础设施、多轮对话、reasoning mode、知识增强和 evidence grounding 等层。它虽然不跑新的受控实验，但把“leaderboard 是否可迁移”变成可证伪标准，而不只是抱怨榜单不准。对内部评测工程来说，这很实用：我们应该记录分数在不同子集、隐藏集、架构变体和对抗扰动下的 rank stability。
🔗 链接：https://arxiv.org/abs/2606.19704 ｜ 代码：None

### AutoPass：用编译器内部证据和运行时反馈调优 LLVM pass
编译器性能调优很像一种复杂软件工程任务：默认 `-O3` 不一定适合每个程序，pass 顺序和参数会与硬件、输入和微架构细节互相影响。传统 autotuning 把编译器当黑盒搜索，成本高；学习式策略又需要大量训练数据，并且跨程序和硬件迁移困难。AutoPass 把 LLM agent 放进 compiler tuning loop，但关键是它不只让模型猜 pass，而是打开编译器内部证据。系统会查询 LLVM IR snapshot、optimization remarks 和运行时 profiling，用多 agent 结构分析程序语义、生成候选 pass pipeline、编译验证、测量运行时间，并根据回归继续修正。它是 inference-only、training-free，不需要离线训练或特定任务微调，因此更像一个可迁移 harness。实验在 x86-64 和 ARM64 上相对 LLVM `-O3` 分别取得 1.043x 和 1.117x 几何平均加速，并超过 PGO、OpenTuner 等基线。对本日报的启发是，传统开发工具可以通过“内部状态可查询 + 验证闭环 + 运行时证据”变成 agent-friendly software，而不是只暴露命令行黑盒。
🔗 链接：https://arxiv.org/abs/2606.20373 ｜ 代码：None

### MobileForge：无人工标注的移动 GUI agent 目标应用适配系统
移动 GUI agent 的一个实际难点是，App 数量多、更新快，人工为每个 App 写任务、示范和奖励标签成本太高。MobileForge 的目标是让 agent 自己探索目标 App、挖掘可执行任务、执行 rollout、获得反馈，并把这些经验转成策略更新信号。它包含 MobileGym 和 HiFPO 两层：MobileGym 负责探索真实 App 状态、生成课程任务和做 hierarchical critic；HiFPO 则把轨迹结果、步骤级反馈和纠错 hint 转成 hint-contextualized step-level GRPO 数据。这里的重点不是一个新的 RL 公式，而是把“无标注 GUI 适配”做成从探索、课程、rollout、反馈到训练的完整 substrate。使用自动生成数据，MobileForge 让 Qwen3-VL-8B 在 AndroidWorld 上达到 67.2% Pass@3，接近闭源数据训练的 GUI-Owl-1.5-8B；进一步适配 GUI-Owl 后，ForgeOwl-8B 达到 77.6% Pass@3，并在 MobileWorld GUI-only OOD split 上有 41.0% success。它按 Medium 收录，因为主题偏移动 GUI，但工程模式与 Agent-Friendly Software 很相关。对桌面/CLI 化工作也有启发：如果无法人工标注所有软件，就要让 agent 从真实交互中自动构造任务和分层反馈。
🔗 链接：https://arxiv.org/abs/2606.19930 ｜ 代码：https://mobile-forge.github.io/

### ORAgentBench：端到端运筹优化 agent 的可执行工作流评测
运筹优化任务表面上像数学建模，但真实工作通常包括理解业务约束、整理多文件数据、选择建模策略、写求解代码、验证可行性和优化目标质量。ORAgentBench 把这个完整过程做成 agent benchmark，而不是只给模型一个已经形式化好的优化问题。它包含 107 个由人类复核的任务，每个任务都有自然语言 brief、多文件数据、配置 artifact、隔离执行环境和 required submission schema。agent 必须写并运行代码，提交结果再由 hidden validators 检查 schema validity、hard-constraint feasibility 和 normalized objective quality。十四种前沿 agent-model 组合里，最佳 agent 只通过 35.51% 总任务和 20.59% hard tasks，很多可行解也达不到质量阈值。失败主要来自战略层面：漏业务规则、建模脆弱、可行解构造弱、后续改进不足；OR-specific skills 能提高 hard-task feasibility，但不能稳定提高最终质量。它对 agent eval 的价值在于，很多专业工作流不能用“代码能跑”代表成功，还必须验证决策 artifact 是否满足约束并足够好。
🔗 链接：https://arxiv.org/abs/2606.19787 ｜ 代码：None

### ReproRepo：用 GitHub issue 扩展论文复现实验 agent 评测
复现论文结果是科研工程里的高价值工作，但人工构造复现 benchmark 很贵，因为需要读论文、跑代码、定位环境和数据问题，再判断 agent 的发现是否真实。ReproRepo 用一个很工程化的监督来源扩展评测：真实 GitHub 仓库里研究者和用户已经提交过大量复现 blocker issue。作者把 1,149 篇近期机器学习论文与对应仓库配对，让 agent 从 paper-repo pair 中找可能阻碍复现的问题，再用人类提出的 issue 做自然监督。实验显示，即使不执行代码，最佳配置 Codex with GPT-5.5 也能为约 90% 论文 surface 至少一个语义相关的人类报告 blocker。进一步分析发现 agent 很擅长发现可见失败和大致语义区域，但精确定位仍然不足。本文按 Medium 收录，因为它不是 coding agent 训练数据本身，但它提供了一个可规模化的真实问题来源：GitHub issue 可以作为复现实验、仓库健康和研究 agent 评测的监督信号。对内部评测来说，这种“人类自然 raised blockers + agent audit”的形式也可用于依赖升级、安装失败、文档缺口和测试不稳定性。
🔗 链接：https://arxiv.org/abs/2606.18237 ｜ 代码：None

### OpenAI Beneficial Trait RL：用现实场景 RL 强化可泛化的有益行为
OpenAI Alignment 6 月 20 日发布的这篇文章不是 coding agent 专项，但属于近月官方研究源，且直接讨论 post-training RL。它研究一个问题：如果用现实对话场景强化 honesty、epistemic humility、corrigibility、metacognitive transparency、公平性和人类福祉等 beneficial traits，模型的对齐行为能不能跨任务、跨领域泛化。OpenAI 构造了覆盖健康、教育、科学、法律、工程、经济等域的 realistic conversation dataset，并把少量 beneficial trait data 混入更广泛的 RL post-training 分布。结果显示，模型不仅在 held-out trait eval 上提升，也在 44/53 个独立内部和公开评测上优于 compute-matched baseline，覆盖 deception、honesty、reward hacking、harmful advice、health 和 mental health 等。文章还测试 adversarial prompting 和 harmful fine-tuning，发现 trait-RL 模型更难被引导到有害行为，但仍能被正常有益方向 steer。按本日报规则它是 Low，因为主题偏泛 alignment，不提供 coding-agent 数据/评测/harness 机制。它的间接启发是，高风险 agent 的后训练数据可以围绕“可泛化行为特质”组织，但仍需要在软件工程场景中建立具体 verifier 和过程信号。
🔗 链接：https://alignment.openai.com/beneficial-rl/ ｜ 代码：None

### 🔥 大佬观点

**Peter Steinberger（@steipete / OpenAI）：从 prompt engineering 转向 loop engineering。**  
Peter 6 月 8 日关于“不要再手动 prompt coding agents，而要设计 prompt agents 的 loops”的 X 观点被多篇社区文章引用，解释器页面记录该讨论达到 6.5M+ views。它火的原因是把开发者角色从“写一次提示”改成“设计循环、验证门和停止条件”，与本日报关注的 harness 工程完全一致。🔗 https://www.techtwitter.com/tweet/a3303b2f-1c7d-4c7d-8d06-69fe7c3e8efb

**Boris Cherny（Claude Code creator / Anthropic）：工程师的杠杆点变成写 loops。**  
WorkOS 对 Boris 的采访总结中提到，他已经不直接 prompt Claude，而是写会读取 GitHub、Slack、Twitter 并决定下一步的 loops。这个观点值得注意，因为它来自 Claude Code 的核心构建者，并把 autonomous coding 的实践重点落到自动调度、反馈聚合、验证和持续运行，而不是单个模型回答。🔗 https://workos.com/blog/boris-cherny-claude-code-acquired-interview-takeaways

### ⭐ 超火仓库/项目

**GitHub MCP Server v1.4.0：30k+ stars 的官方 GitHub agent 工具控制面继续扩展。**  
GitHub MCP Server 6 月 18 日发布 v1.4.0，仓库约 30.8k stars，并继续强化 toolsets、Copilot coding agent 相关工具、code quality findings、HTTP listen address 等功能。它火在解决一个真实平台痛点：agent 需要用统一 MCP 方式管理 issue、PR、Actions、code scanning、Copilot jobs，而不是每个客户端各写一套 GitHub API wrapper。🔗 https://github.com/github/github-mcp-server/releases/tag/v1.4.0

**NVIDIA Open-SWE-Traces：200k+ SWE agent 轨迹成为开源后训练数据热点。**  
Open-SWE-Traces 的热度来自规模和可直接训练价值：207,489 条轨迹、OpenHands/SWE-agent 两套 harness、thinking/non-thinking 两类模式，以及 Hugging Face 数据集公开。它解决的是开源 agent 模型缺少长程真实软件工程轨迹的问题，也会成为后续蒸馏、轨迹筛选和 harness 对比的基础资产。🔗 https://huggingface.co/datasets/nvidia/Open-SWE-Traces

**GateMem：共享记忆治理成为 agent memory 新焦点。**  
GateMem 数据集把 agent memory 从“记得更多”推进到“按身份、授权和删除请求正确记忆”，覆盖医疗、办公室、教育、家庭四种多主体场景。它火的原因是长期 agent 和组织级助手都绕不开这个问题：一个 memory store 同时服务多人时，泄露未授权信息和恢复已删除信息都可能成为严重事故。🔗 https://huggingface.co/datasets/Ray368/GateMem
