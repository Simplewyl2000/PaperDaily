## 📝 逐条讲解

### OpenAI：How agents are transforming work / Codex 使用数据证明工作单元转向长程委派
过去很多企业看 AI 工具时，默认衡量的是一次聊天、一次回答、一次代码补全是否有用；OpenAI 这篇 6 月 25 日的经济研究把观察对象换成了 Codex agent 的真实使用轨迹。它的核心观点是，agentic AI 改变了知识工作的“单位”：用户不再只是问一个问题，而是把一个会持续几十分钟到数小时、会调用工具和修改产物的任务委派给 agent。OpenAI 报告称，2026 年上半年 Codex active users 增长超过 5 倍，抽样个人用户里 80.6% 至少发起过一个估计超过 30 分钟人类工作量的 Codex 请求，25.6% 至少发起过一个超过 8 小时的请求。更有工程意义的是，论文提到超过 10% 用户每周会同时管理 3 个以上 Codex agents，26.6% 使用 skills 来共享复杂 workflow 指令。OpenAI 内部数据也很激进：截至 6 月，Codex 占 OpenAI 员工在 Codex + ChatGPT 中每周输出 token 的 99.8%，法律、招聘、财务等非工程部门也快速转向 Codex。它值得关注，不是因为“OpenAI 员工很会用 OpenAI 工具”这个结论本身，而是因为它给 agent runtime 提出新要求：并发 agent 管理、skill 分发、长程任务状态、成本统计、审计与人类 supervision 会成为生产系统一等能力。
🔗 链接：https://openai.com/index/how-agents-are-transforming-work/ ｜ 代码：https://cdn.openai.com/pdf/5d1e1489-21c0-43e4-9d42-f87efdbf0082/the-shift-to-agentic-ai-evidence-from-codex.pdf

### ToolBench-X：在工具环境不可靠时评测 agent 的诊断与恢复能力
很多 tool-use benchmark 默认工具稳定、schema 准确、返回值可信，只要模型会选函数、填参数、读结果就算通过。真实系统要混乱得多：API 会超时，文档会过期，不同来源会互相冲突，工具输出格式也可能悄悄改变。ToolBench-X 的价值在于，它把这种“不完美但可恢复”的工具环境显式做成 benchmark，而不是只测干净环境里的 function calling。它向原本可解的多步任务注入五类 hazard：规格漂移、调用错误、执行失败、输出漂移和跨来源冲突，同时保证每个实例仍然存在至少一条有效恢复路径，比如重试、fallback、验证或交叉检查。实验结论很符合工程直觉：在稳定工具上表现好的 agent，遇到可恢复异常后会出现明显可靠性缺口，失败主要来自 hazard diagnosis 和 recovery strategy 不足，而不是工具调用次数不够。对后训练软件工程来说，这类数据可直接用于训练 agent 学会“怀疑工具、验证输出、选择备用路径”，而不是只模仿顺利完成的 golden trace。落地时，它也提醒我们 eval harness 应该模拟 API drift、flaky command、部分错误数据和 conflicting evidence，否则上线后才会发现 agent 的恢复能力其实很弱。
🔗 链接：https://arxiv.org/abs/2606.25819 ｜ 代码：None

### CLI-Universe：用证据驱动深度研究 + 多阶段验证合成 terminal-agent 训练任务
Terminal agent 的后训练最缺高质量、可执行、可验证的任务数据；简单把文档、仓库或脚本改造成题目，经常会得到指令模糊、路径浅、测试脆弱的低信号样本。CLI-Universe 选择从能力空间出发做任务合成：先按领域、技能类型、能力和工程支柱采样任务候选，再让 research agent 去真实文档、仓库、issue 和示例中找证据，把抽象能力点落成具体工程蓝图。之后它把蓝图实例化为 Docker 环境，并经过 rubric-gated test construction、hint-conditional filtering 和严格 fail-to-pass 检查；整个漏斗会丢掉约三分之二候选，只保留真实、可验证、非平凡的任务。论文用 6,000 条 CLI-Universe 轨迹微调 Qwen3-32B，在 Terminal-Bench 2.0 上达到 33.4%，超过同规模开放数据训练模型和一些大一个数量级的开放模型。它的新意不只是又生成了一批 terminal 题，而是把任务合成变成“能力规格 → 证据 grounding → 可执行环境 → 测试审计 → 轨迹训练”的工程 pipeline。对我们关注的数据工程方向，这正是值得复用的范式：训练样本的价值来自验证强度、任务密度和覆盖控制，而不是单纯样本数。未来如果类似 pipeline 能公开更多中间 artifact，例如被过滤候选和失败原因，会更适合做 trajectory selection 和 reward-environment 审计。
🔗 链接：https://arxiv.org/abs/2606.22883 ｜ 代码：None

### Tmax：开源 15K terminal 环境与简单 RL recipe，缩小开放 terminal agent 差距
Terminal-using agents 已经成为 Claude Code、Codex CLI、Gemini CLI 这类产品的核心形态，但学术界和开源社区长期缺少能复现的训练 recipe。Tmax 的目标很务实：给 terminal agent 提供一套简单、公开、强基线的数据生成、SFT/RL 训练和评测代码。它发布 TMax-15K，大约 14,600 个 difficulty-controlled terminal 环境，任务由 difficulty、persona、verifier diversification 等轴组合生成，并以 Harbor / Docker 形式提供可执行 verifier。训练侧采用简单 outcome-only RL recipe，项目文档和博客称 TMax-9B 在 Terminal-Bench 2.0 上约 27%，TMax-27B 也在 Hugging Face 发布，对开放模型来说是很强的起点。相比只发布模型分数，Tmax 更重要的是把数据、模型、代码、训练 artifact、rollout/logprob 等都放出来，方便别人研究为什么某些 terminal 轨迹有效。它和 CLI-Universe 形成互补：CLI-Universe 强调高保真任务合成漏斗，Tmax 强调可复现 RL recipe 和全栈开源。对内部后训练团队来说，它提醒我们 terminal-agent 数据要同时记录环境、verifier、rollout、训练脚本和模型 checkpoint，否则很难判断提升来自数据、harness 还是训练 trick。
🔗 链接：https://arxiv.org/abs/2606.23321 ｜ 代码：https://github.com/hamishivi/tmax

### EnterpriseClawBench：从真实企业会话恢复 852 个可复现 workspace-agent 任务
很多企业 agent 评测仍然借用公开 QA、SWE-bench 或通用办公任务，但真实企业 workflow 更复杂：用户会上传文件，agent 要在 workspace 里读多种格式、调用工具、生成可下载 artifact，并受成本、时延和视觉质量约束。EnterpriseClawBench 从真实企业内部 agent 会话出发，经过隐私和可复现检查，把历史会话恢复成 852 个任务；每个任务包含 fixture、重写后的 prompt、角色类、技能子类、hard rules 和 semantic rubrics。由于原始数据包含内部内容，它不公开 benchmark 数据本体，而是公开构造和评估协议、leaderboard 与安全脱敏案例。论文报告人工审计的 120-task Lite 子集上，最佳配置 Codex + GPT-5.5 只有 0.663，说明企业 workspace agent 离稳定完成真实业务 artifact 还很远。它的重要性在于把 enterprise agent 的成功标准从“回答看起来合理”扩展成“输入是否恢复对、文件是否生成对、视觉/文本 artifact 是否可用、成本与运行时间是否可接受”。对 harness 工程来说，这类评测必须报告 model + harness 组合，而不是只报模型名，因为文件装配、工具权限、workspace 约定和输出目录契约都会显著影响结果。对后训练数据工程来说，企业日志转 benchmark 的 pipeline 是高价值方向，但隐私、脱敏、fixture recovery 和 rubric 生成会是核心难点。
🔗 链接：https://arxiv.org/abs/2606.23654 ｜ 代码：https://github.com/FrontisAI/EnterpriseClawBench

### Agent-as-a-Router / CodeRouterBench：把 coding model routing 做成 C-A-F 执行反馈闭环
现实团队常常同时能调用多个模型：有的模型修 bug 强，有的写测试强，有的便宜，有的在长上下文里更稳。传统 model router 往往把路由当成一次性分类：看一下任务文本，猜哪个模型更合适。Agent-as-a-Router 指出，这种静态路由最大的瓶颈不是推理能力，而是信息不足；只给 router 一些维度级历史性能统计，就能带来 15.3% 相对提升。它把路由做成 Context-Action-Feedback loop：先根据上下文选择模型，执行后用 verifier 评估结果，再把反馈写入 memory，后续类似任务就能利用执行经验。为此作者发布 CodeRouterBench，约 10K 个 coding tasks，带 8 个 frontier LLM 的验证分数矩阵，并包含 OOD176 agentic-programming task stream 来测试泛化。工程价值很直接：生产 agent 平台不一定要“一个模型包打天下”，而应把路由、验证、成本和历史经验做成控制面。对评测团队来说，CodeRouterBench 也提供了一种新指标：不只看单模型 pass rate，还看一个 router 在 streaming workload 下的 cumulative regret 与 cost-quality Pareto。
🔗 链接：https://arxiv.org/abs/2606.22902 ｜ 代码：https://github.com/LanceZPF/agent-as-a-router

### Qwen-AgentWorld / AgentWorldBench：用语言世界模型预测 agent 环境反馈
很多 agent 训练和评测依赖真实环境 rollout，但真实环境昂贵、慢、难并行，而且有些工具或网页状态不可复现。Qwen-AgentWorld 的想法是训练一个 language world model，让模型预测 agent 在环境中行动后的 observation，从而为 general agents 提供可模拟的反馈层。Qwen 6 月 24 日开源 Qwen-AgentWorld-35B-A3B，并发布 AgentWorldBench，覆盖 7 个领域，用 Format、Factuality、Consistency、Realism、Quality 等维度评估预测 observation 的质量。这个方向不是 coding-agent 专项，因此按 Medium 收录；但它和后训练基础设施有关，因为高质量 world model 可以降低 rollout 成本，也可以用于离线调试 agent policy。它的风险是，如果 world model 预测的环境过于“顺滑”或带有训练偏见，agent 会学到只适用于模拟器的行为。对工程落地来说，AgentWorldBench 的启发是：如果要让模型模拟环境反馈，就必须单独评测反馈格式、事实性、状态一致性和现实感，而不是只看最终任务分。它未来若能和真实 terminal / SWE / MCP 工具环境结合，可能成为更便宜的轨迹生成和 failure rehearsal 层。
🔗 链接：https://arxiv.org/abs/2606.24597 ｜ 代码：https://github.com/QwenLM/Qwen-AgentWorld

### Claude Code 2.1.191：/rewind、MCP retries、headless OAuth 与 streaming CPU 优化
Claude Code 这类 agent runtime 的成熟度越来越体现在“会不会丢状态、会不会卡 MCP、后台 agent 能不能真的停、长流式输出是否吃 CPU”这些细节上。社区跟踪的 2.1.191 changelog 显示，这个版本新增 `/rewind`，可以在误用 `/clear` 后恢复清空前的会话上下文；这对长程会话很重要，因为 accidental clear 过去可能直接毁掉当前工作线程。它还改进 MCP capability discovery，对 `tools/list`、`prompts/list`、`resources/list` 的 transient errors 做 backoff retry，并修复 headless OAuth 场景下的浏览器弹窗问题，改成 URL paste prompt。另一个运行时细节是 streaming coalescing，社区文章称可降低约 37% CPU，使长会话更顺滑。它不是论文，也不是严格 benchmark，所以按 Medium 收录；但这些修复正好对应 agent ops 的真实痛点。对内部平台来说，Claude Code 2.1.191 提醒我们：agent harness 的稳定性需要用长程 session、MCP flaky server、headless auth、stop/restart 和 context recovery 做回归，而不是只跑短任务 pass rate。
🔗 链接：https://explainx.ai/blog/claude-code-2-1-191-rewind-mcp-background-agents-2026 ｜ 代码：https://raw.githubusercontent.com/anthropics/claude-code/master/CHANGELOG.md

### mcpbr：用 SWE-bench 双跑实验衡量 MCP server 是否真的帮 coding agent
MCP server 很容易给人“接上工具就更强”的错觉，但真正的问题是：这个 server 在相同模型、相同任务、相同环境下，到底有没有提高完成率、降低成本或减少探索时间。mcpbr 的设计很简单，也因此有工程价值：它对同一个 SWE-bench task 同时跑两条路径，一条是带目标 MCP server 的 agent，另一条是不带工具的 baseline agent，然后都在 Docker 里的 SWE-bench 环境中生成补丁、应用补丁、运行测试。这样 MCP 的收益不再靠 demo 感觉判断，而是变成 paired evaluation。它当前 star 不高，属于早期社区工具，但击中了 MCP 生态的核心痛点：工具接口和 schema 越来越多，团队需要知道哪个 server 真的带来增益，哪个只是增加 token 和故障面。它也适合企业内部接入自研代码检索、CI、日志、知识库 MCP 时做准入门槛。对后训练数据工程来说，这类双跑结果还能帮助区分“模型能力不足”和“上下文/工具层不足”：如果带工具显著提升，训练数据和 eval 就应该记录工具提供了哪些关键证据。后续若 mcpbr 增加成本、轨迹、检索质量和 failure taxonomy，会更接近生产级 MCP eval harness。
🔗 链接：https://github.com/captradeoff/mcpbr ｜ 代码：https://github.com/captradeoff/mcpbr

### Agents All the Way Down：把自定义 agent 构建沉淀为 substrate→CLI→agent-tests-agent 方法论
很多团队想做自定义 agent，却容易在框架、MCP、工具调用、提示缓存、CLI、技能和多 agent 编排之间迷路。Agents All the Way Down 不是一个新模型，而是把构建 custom agent 的实践整理成一套方法论：先把 LLM 当作 substrate，也就是可被软件系统调用的组件；再把 function calling、MCP、CLI orchestration、liteshell、agent loop、skills、hooks 等 building blocks 组合起来。它最有意思的实践是 Turtle pattern：先用通用 agent 原型化工作流，再把反复出现的动作 harvest/fold 成 CLI，让未来 agent 调用这个更稳定的工具。另一个实践是 agent-tests-agent，也就是让通用 agent 通过行为场景测试自定义 agent，作为传统测试的补充。论文提出一个简洁但很有用的观点：multi-agent orchestration 本质上可以看作 CLI composition，而不是必须引入复杂框架。按本日报标准它是 Medium，因为方法论多于实证，但很贴合 Agent-Friendly Software 工程。对内部落地来说，它提醒我们不要把所有控制流交给模型；能沉淀为 CLI、测试、hook 和 audit trail 的部分，应尽量软件化。
🔗 链接：https://arxiv.org/abs/2606.11869 ｜ 代码：None

## 🔥 社区热点专栏

### 🔥 大佬观点

**OpenAI Economic Research / Drew Johnston 等：agentic AI 把工作从“问答”改成“委派生产”。**  
OpenAI 这篇 Codex 使用研究被 The Register、TechsCurrent 等媒体二次解读，核心观点是用户正在把长程、多步骤、有工具调用的生产任务交给 agent，而不是只让 chatbot 提供建议。它值得注意，因为数据里出现了并发 agent、skills、非开发者快速增长和 8 小时级任务请求，这些都指向 agent 平台需要任务管理、权限、审计和成本控制。🔗 https://openai.com/index/how-agents-are-transforming-work/

**@ClaudeCodeLog / Marc Krenn：Claude Code 的 release diff 本身成了 agent runtime 观测面。**  
Claude Code 2.1.191 的社区讨论热在 `/rewind`、MCP retries、headless OAuth 和 streaming CPU 这些“看似小但影响长程稳定性”的细节。这个观点值得注意，因为成熟 agent 工具的竞争不只是模型能力，而是会话恢复、后台任务停止、connector 授权、hook matcher 和资源占用这些 runtime 边界。🔗 https://explainx.ai/blog/claude-code-2-1-191-rewind-mcp-background-agents-2026 ｜ https://github.com/marckrenn/claude-code-changelog

**Matt Pocock：真实工程师的 Claude Code skills 比泛化“vibe coding”模板更有价值。**  
`mattpocock/skills` 近期继续在社区保持高热度，README 明确说这些 skill 来自他日常 `.claude` 目录，用来修复 misalignment、过度啰嗦、代码不可运行、架构失控等常见失败模式。它火在证明一个趋势：高质量 agent skill 不是漂亮 prompt，而是把资深工程师的诊断、TDD、triage、文档对齐和 git guardrails 工作流沉淀成可复用控制面。🔗 https://github.com/mattpocock/skills/

### ⭐ 超火仓库/项目

**hamishivi/tmax / AllenAI TMax：开源 terminal-agent 数据、模型和训练 recipe 一次性放齐。**  
Tmax 火在它不是只发论文分数，而是同时提供 TMax-15K 数据、2B/4B/9B/27B 模型、训练脚本和评测代码。它解决的是开源 terminal agent 后训练最实际的痛点：没有足够强、足够完整、能复现实验的数据和 recipe，导致每个团队都从零摸索。🔗 https://github.com/hamishivi/tmax ｜ https://huggingface.co/datasets/allenai/TMax-15K

**QwenLM/Qwen-AgentWorld：Qwen 把 agent 环境反馈建模做成开源世界模型与 benchmark。**  
仓库 6 月 24 日发布后已有数百 star，并同时提供 Qwen-AgentWorld-35B-A3B、AgentWorldBench 和评测脚本。它火在解决 agent 训练的成本问题：如果 world model 能可靠预测环境 observation，就能更便宜地做离线训练、policy rehearsal 和失败复盘。🔗 https://github.com/QwenLM/Qwen-AgentWorld

**FrontisAI/EnterpriseClawBench：真实企业 workspace session 评测开始从“分数”转向 artifact/cost/runtime cockpit。**  
项目 star 不高但信号强，因为它把企业内部 agent 会话转成可复现任务的流程公开出来，并提供 leaderboard、performance cockpit、任务类别和 artifact 诊断。它解决的是生产团队很在意但公开 benchmark 很少覆盖的问题：agent 最后交付的文件、视觉质量、成本、运行时间和缺失证据是否可接受。🔗 https://github.com/FrontisAI/EnterpriseClawBench ｜ https://frontisai.github.io/EnterpriseClawBench/
