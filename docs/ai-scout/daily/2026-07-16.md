## 📝 逐条讲解

### Function-Aware FIM：把函数调用结构转成 coding-agent mid-training 数据
很多 coding agent 后训练直接从成功轨迹开始做 SFT 或 RL，但基础模型在预训练阶段主要见到的是左到右代码文本，不一定自然适应“行动、看到工具结果、继续推理”的 agent 循环。Function-Aware FIM 的核心观察很巧妙：普通代码里的函数调用，本质上也有“调用者给参数、被调用函数在别处产生结果、下游代码消费结果”的结构，和 agent 的 action-observation-continuation 很像。论文用程序依赖图挑出复杂但可推断的函数，把函数体和 rationale 做成 fill-in-the-middle 目标，在 agentic post-training 之前插入一个自监督 mid-training 阶段。数据上，它从 968 个 permissive GitHub 仓库抽取 75,568 个 Python 文件，构造 400K 条样本，约 2.6B tokens，并声明对 SWE-Bench 做了去污染。结果显示，Qwen2.5-Coder 7B/14B 和 Qwen3-8B 在 SWE-Bench Verified / Lite 上都有 2.8 到 5.4 个点提升，而且跨 R2E-Gym、SWE-Smith、SWE-Lego 等后训练 pipeline 仍有效。更重要的是，它缓解了 agentic post-training 对 LiveCodeBench、tau-bench、BFCL 等非 agent 任务的能力侵蚀。对 Code LLM post-training 数据工程来说，这说明高质量训练信号不一定只来自昂贵 rollout，普通代码语料中也能挖出与 agent 工具循环同构的中间监督。
🔗 链接：https://arxiv.org/abs/2607.12463 ｜ 代码：https://huggingface.co/datasets/TIGER-Lab/FIM-Midtraining-400K

### OpenAI GPT-Red：用自博弈红队模型生成 prompt-injection 训练攻击
Prompt injection 对 agent 特别危险，因为 agent 会读网页、邮件、文件和工具返回，这些第三方数据都可能夹带恶意指令。传统红队依赖人类专家，能发现高质量攻击，但规模有限，也很难持续产生足够多样的训练样本。OpenAI 的 GPT-Red 把红队本身做成一个模型：它在自博弈 RL 中攻击一组 defender LLM，目标是诱导成功的 prompt injection，而 defender 学会抵抗并完成原任务。OpenAI 称 GPT-Red 在复刻的 indirect prompt injection arena 上对 GPT-5.1 的成功率达到 84%，明显高于人类红队的 13%。更贴近本日报主题的是，它还被用来攻击一个基于 GPT-5.4 mini 的 Codex CLI agent，在 10 个 held-out 数据外泄场景里比 prompted GPT-5.5 baseline 更有效且更省 token。OpenAI 进一步把 GPT-Red 生成的攻击纳入 GPT-5.6 训练，使 GPT-5.6 Sol 在最难 direct prompt injection benchmark 上失败数比四个月前生产模型少 6 倍。对后训练软件工程来说，这是一种“自动构造安全负样本”的 pipeline：定义 threat model、运行真实 agent/harness、收集成功攻击、再把攻击用于稳健性训练和回归评测。
🔗 链接：https://openai.com/index/unlocking-self-improvement-gpt-red/ ｜ 代码：None

### Failure as a Process：1,794 条 CLI coding-agent 轨迹的失败过程解剖
很多 coding-agent 研究把失败看成最后一个标签：任务没过测试，所以失败了。真正调试 agent 时，这个标签帮助很小，因为关键错误可能在第 3 步就已经发生，只是到第 40 步才表现成补丁无效。Failure as a Process 把失败当成一个时间过程来研究，分析失败何时开始、怎样演化、agent 是否意识到问题、以及是否还有恢复机会。作者从 Terminal-Bench 上收集 OpenHands、MiniSWE、Terminus2 三种 scaffold 和 7 个 frontier model 的 3,843 条原始执行，过滤出 1,794 条有效完整轨迹，包含 610 条成功和 1,184 条失败，人工标注超过 63,000 个执行步骤。结论很实用：失败主要是 epistemic errors，也就是 agent 不知道自己不知道；这些错误通常在早期步骤出现，并且常常隐藏到无法恢复时才暴露。它还发布了目前较大的公开 annotated CLI coding-agent trajectory dataset。对轨迹筛选和 eval 工程来说，这提示我们不能只在结尾审查最终 patch，而要在早期探索后设置检查点，保存关键假设、首批命令、定位路径和验证信号。
🔗 链接：https://arxiv.org/abs/2607.09510 ｜ 代码：https://github.com/xz-Sean/cli_trajectory_analysis

### Long-Horizon Terminal-Bench：46 个长程终端任务 + dense reward 评测
短程 benchmark 常常让 agent 在几十步内改一个文件或回答一个问题，但真实自动化任务可能要跑上百步、跨很多依赖状态，并且花 30 到 90 分钟。Long-Horizon Terminal-Bench 专门测试这个缺口：它给 agent 一个 containerized terminal，要求在 46 个长程任务中持续推进，任务覆盖软件工程、逆向工程、科学计算、多模态分析、研究复现、交互游戏等 9 类。它不只用二值 pass/fail，而是把每个任务拆成更细的 graded subtasks，用隐藏 verifier 给 partial credit，记录 agent 到底推进了多远。公开摘要显示，29/46 个任务没有任何模型完全解出，最佳模型平均 reward 约 0.505，说明远未饱和。这个设计很重要，因为长程任务里最常见的不是“完全没有进展”，而是 agent 走了很远却无法收口，或者误以为自己已经完成。dense reward 能把这种 completion cliff 暴露出来，为训练和调试提供中间信号。对后训练软件工程来说，LHTB 提醒我们需要保存“部分成功但未完成”的轨迹，它们能帮助训练预算管理、进度感知、恢复策略和终止判定。
🔗 链接：https://arxiv.org/abs/2607.08964 ｜ 代码：https://github.com/zli12321/LHTB

### Stripe Integration Benchmark：真实支付集成里的 agentic development eval
很多 coding-agent benchmark 的目标是“修一个 bug 并通过测试”，但企业 API 集成更苛刻：支付、订阅、checkout flow 只要 99% 正确也可能是生产事故。Stripe 的 benchmark 把 agent 放进 11 个可复现环境，要求它们完成真实 Stripe 集成任务，包括后端 API 更新、数据库/SDK 迁移、浏览器 checkout 流程和产品特定 gym exercises。评测 harness 基于 Goose 和 MCP，给 agent 终端、文件编辑、computer use，以及唯一的 Stripe 文档搜索 MCP endpoint。评分不是看模型解释，而是由 deterministic graders 通过 API 调用、UI 自动化和 Stripe objects 检查功能是否真的完成，最优运行 transcript 还由 Stripe 工程师做人类 integrity review。结果显示，强模型能做出不少可用集成，例如 Claude Opus 4.5 在 full-stack tasks 上平均 92%，但失败仍集中在验证推理、浏览器状态恢复、无效输入的解释和跨系统一致性。它值得关注，因为它把 coding agent eval 从开源 issue 推到真实商业 API 的端到端工程场景。对后训练数据工程来说，这类 benchmark 的关键资产不是题目数量，而是可回放环境、真实 API artifacts、浏览器动作、确定性 grader 和工程师复核记录。
🔗 链接：https://stripe.com/blog/can-ai-agents-build-real-stripe-integrations ｜ 代码：https://github.com/stripe/ai/tree/main/benchmarks

### Copilot CLI plan mode hard-block：把 read-only 从 prompt 约定提升到运行时阻断
很多 agent 产品有“plan mode”或“read-only mode”，但早期实现往往只是 system prompt 告诉模型不要改文件。问题是，prompt 约束会被模型漂移、工具描述混淆或 prompt injection 绕过；真正的安全边界必须在 tool dispatch 层执行。TechTimes 对 GitHub Copilot CLI 1.0.71 系列更新的分析指出，GitHub 在 7 月 14 日把 plan mode 的内置 workspace-mutating tools 做了 runtime hard-block：文件编辑、会修改 workspace 的 shell、PR opener 等会在执行前被拒绝。同期更新还把 sandbox filesystem policy 扩展到 LSP file reads 和 rename edits，堵住语言服务器绕过直接文件 API 的路径。值得注意的 caveat 是，MCP 和 external tools 仍被允许，因为它们经由独立 JSON-RPC server 进程，CLI 对第三方工具没有同样的内置拦截点。这个细节对 MCP 生态很关键：如果每个 client 的“只读模式”都只管自家工具，第三方 server 仍能改 workspace，那么只读承诺就是条件性的。对 agent runtime 工程来说，这条更新说明安全不能只写在提示词里，必须把模式、权限、工具来源和外部 server 能力都建成可审计的执行策略。
🔗 链接：https://www.techtimes.com/articles/320560/20260715/github-copilot-cli-closes-agentic-loophole-plan-mode-can-no-longer-edit-your-files.htm ｜ 代码：None

### Claude Code Harness：Dev→QE→Ops subagents + MCP telemetry + LEARNING.md
很多团队第一次用 coding agent 时会把所有事塞进一个长 prompt：让它计划、写代码、跑测试、开 PR、总结经验。LogRocket 这篇文章用一个小而完整的示例说明，可靠 agent workflow 更像一个 harness，而不是一段 prompt。示例项目定义 `/harness <spec.md>` slash command，由 orchestrator 依次委派 Dev、QE、Ops 三个 Claude Code subagents：Dev 负责实现和单测，QE 负责根据 acceptance criteria 跑 live curl、回归检查和服务生命周期清理，Ops 负责分支、提交、开 PR 并写回经验。每个阶段通过 local MCP telemetry server 调用 `recordTelemetry`，把 `dev_started`、`tool_call_start`、`test_run`、`qe_finished` 等事件写入 SQLite。`LEARNING.md` 则保存跨运行的 durable lessons，agent 每次启动和失败时都能重新读取。它不是大规模框架，但工程价值很清楚：把角色边界、质量门、遥测、失败回环和经验沉淀都落到 repo 文件和 MCP 工具里。对后训练数据来说，这类 harness 会产生更干净的阶段化轨迹，便于区分“实现错误”“验证错误”“发布流程错误”和“经验未复用”。
🔗 链接：https://blog.logrocket.com/building-an-agent-harness-with-claude-code/ ｜ 代码：https://github.com/andrewevans0102/agent-harness-with-claude-code

### Clawk：给 coding agent 一台 disposable Linux VM，而不是用户本机
让 agent 直接在开发者笔记本上执行命令，一直是生产风险的核心来源：它可能读到 SSH key、浏览器会话、云凭证或不该访问的本地文件。Clawk 的设计非常直接：给 coding agent 一台一次性 Linux VM，而不是把它关在用户主机上的一个“受限进程”里。它在 macOS 上使用 Apple Virtualization.framework，在 Linux 上实验性支持 Firecracker；代码挂载进 VM，agent 在 guest 里拥有 root 和完整 shell，但 host 的 keychain、dotfiles 和未共享目录不可见。更关键的是，Clawk 带 default-deny egress，常见 registry 可白名单放行，未知外联会被网络层阻断。项目 7 月 6 日创建，7 月 13 日发布 v0.2.0，Show HN 和开发者社区都在讨论，GitHub 约 237 stars，属于早期但方向很热。它解决的是 coding agent sandbox 的实际落地问题：既允许 agent “在自己的机器里随便折腾”，又把凭证和网络外泄边界从 prompt 转移到 VM 和防火墙。对后训练/评测来说，sandbox 配置、挂载目录、网络批准记录和 VM 生命周期应进入轨迹元数据，否则无法判断一次成功运行是不是建立在危险权限上。
🔗 链接：https://github.com/clawkwork/clawk ｜ 代码：https://github.com/clawkwork/clawk

### Tracing Agentic Failure from the Flow of Success：只用成功轨迹做失败步骤归因
失败归因通常需要标注失败轨迹中哪一步是真正的错误来源，但这种标注非常贵，而且长程 agent 里错误还会层层传播。Tracing Agentic Failure from the Flow of Success 提出一个更省数据的设定：只用成功轨迹学习“正常执行动态”，在失败轨迹上找偏离正常动态的步骤。它的方法 Oat 把每条轨迹表示成 latent-space 动态，用 Neural Controlled Differential Equations 做 one-class learning；推理时给失败轨迹每一步一个 anomaly score。论文称只用 100 条成功轨迹训练，Oat 就能比 prompting-based baselines 快 200 到 5000 倍，并在域内和 OOD 数据上分别带来约 +20% 和 +7% F1。它按 Medium 收录，因为方法层更偏模型诊断算法，而不是 coding-agent 专项系统；但它对 trajectory selection 很有启发。真实生产里成功轨迹总比高质量失败标注更容易积累，如果能用成功轨迹反推出失败偏离点，就可以显著降低审计和训练数据筛选成本。对工程落地而言，下一步重点是把 anomaly step 与可执行证据、tool output、环境状态和恢复建议连接起来。
🔗 链接：https://arxiv.org/abs/2607.12747 ｜ 代码：None

### PUST：用轻量 proxy model 探索并缓存可复用 post-training update signals
常见 RL 后训练会把昂贵探索直接放在目标大模型上，这在长程 agent 和代码任务中成本很高，也很难复用。PUST 的想法是把“探索高回报行为”和“让目标模型吸收方向”拆开：先用更轻量的 proxy model 进行探索，再提取 proxy 从初始到优化后的相对 update signal，最后把这个方向转给 primary model。这样训练信号可以异步生成、缓存、跨模型重复使用，而不是每个目标模型都重新跑一遍昂贵 RL。论文在 Qwen3 family 的数学和代码域上做实验，报告弱 proxy 的更新信号也能提升更强 primary model，code domain 最高约 +4.6。它按 Medium 收录，因为主题偏通用 post-training infrastructure，不直接解决 coding agent harness 或 eval；但“信号可复用”对大规模后训练很重要。对软件工程 agent 来说，未来也许可以用小模型在便宜环境里探索修复策略、验证习惯或工具使用风格，再把 update signal 迁移到更大模型。风险在于信号是否过期、是否会把 proxy 的错误偏好放大，以及不同 harness 下同一信号是否仍有效。
🔗 链接：https://arxiv.org/abs/2607.11505 ｜ 代码：https://github.com/KnowledgeXLab/PUST

### Execution-Security Balkanization：统一审视 coding-agent sandbox / ACL / TOCTOU 研究缺口
Coding agent execution security 的论文很多，但它们常常各说各话：sandbox isolation、capability model、access control、policy enforcement、TOCTOU、MCP threats、identity delegation、network control、provenance 都各自发展。The Balkanization of Execution-Security Research 试图把这些分散方向放到同一张地图上，指出没有一个单点防御能覆盖 agent 真实执行面。论文特别强调研究之间缺少交叉验证：隔离论文很少在 policy-denylist 攻击下重测，access-control 论文又常常不考虑 TOCTOU 的状态变化，MCP threat 和 sandbox threat 也被当作不同问题处理。它还指出一个被忽略的风险：即使没有恶意攻击，agent 在现实提示下也会做 benign-but-out-of-scope actions，而很多 capability / ACL 设计没有覆盖这类“不是坏但越界”的动作。它按 Medium 收录，因为更像 survey 和研究议程，不是新系统；但它对工程团队很有用。落地 coding agent 时，不能只问“有没有 sandbox”，还要问网络、身份、工具权限、文件路径、policy 作者错误、状态检查时机和审计证据是否一起闭环。对后训练和 eval 来说，这意味着安全 benchmark 需要组合攻击面，而不是分别测 prompt injection、MCP、文件系统和网络。
🔗 链接：https://arxiv.org/abs/2607.05743 ｜ 代码：None

### Systima：Claude Code 33K token floor vs OpenCode 7K，量化 harness 固定成本
Agent 成本讨论常常只看模型单价，但实际账单很大一部分来自 harness 固定开销：system prompt、tool schemas、MCP 描述、instruction files 和 cache 行为。Systima 的小型测量用 logging proxy 夹在 Claude Code / OpenCode 与 Anthropic endpoint 之间，比较同模型、同机器下的请求 payload。结果显示，Claude Code 在处理用户 prompt 前约有 33K tokens 的固定 payload，OpenCode 约 7K；其中 tool schemas 是主要来源，Claude Code 默认工具面更大。更有工程意义的是 cache behavior：Claude Code 在一些任务里会重复 rewrite 大块 prompt cache，产生昂贵 cache write，而 OpenCode 的 prefix 更稳定。HN 讨论把这条推到 686 points，说明开发者已经开始把“harness token floor”当成产品质量指标。它不是说 Claude Code 一定更贵，因为多步任务中 batching 和请求数也会改变总成本；真正的结论是，成本必须按任务形状测，而不是只看模型单价或一次短 prompt。对后训练软件工程来说，轨迹数据里应该保存 tool-schema size、cache write/read、MCP server 数量和子代理启动开销，否则同样成功的轨迹无法比较经济性。
🔗 链接：https://systima.ai/blog/claude-code-vs-opencode-token-overhead ｜ 代码：None

Anthropic 7 月 15 日发布这篇官方案例，汇总内部多个团队如何使用 Claude Code，因此按 Low 官方源记录。它不是研究论文，也没有公开 benchmark，但能看到 coding agent 在真实公司内部的落地形态：生产调试、陌生代码库导航、文档整理、自动化工具、业务团队自建小工具等。比较贴近本日报主题的部分是，文章多次提到 agentic coding 正在把非技术角色也变成“能描述问题并产出工具”的人，这意味着任务规格、权限边界和结果验证会从工程团队扩散到更多部门。它还提到通过 MCP 连接散落文档，把知识转成更可用的格式，这和 Agent-Friendly Software 的 connector / tool layer 趋势一致。因为文章偏官方宣传和实践故事，缺少可复现实验或系统细节，所以不放入 High。即便如此，它对观察 Claude Code 的实际使用边界有价值：agent 不只写代码，也在把组织内部流程、文档和重复操作转成可执行工作流。对后训练数据采集来说，这类内部实践提示我们，真实 coding-agent 轨迹会包含大量“非纯代码”的上下文整理、工具搭建和业务自动化任务。

## 🔥 社区热点专栏

### 🔥 大佬观点

**Systima / HN：coding-agent 成本不只是模型单价，而是 harness fixed overhead + cache policy。**  
Systima 对 Claude Code 与 OpenCode 的 API payload 做边界测量，发现第一轮固定上下文约 33K vs 7K tokens，并指出 tool schemas 和 cache rewrite 是主要成本来源。HN 686 points 的讨论说明，开发者已经开始把“每次会话的固定 token 税”当作 agent 产品选型指标，而不是只看模型榜单。🔗 https://systima.ai/blog/claude-code-vs-opencode-token-overhead ｜ https://news.ycombinator.com/item?id=48883275

**Failure as a Process / The Agent Beat：agent 常在前几步犯决定性错误，最后审查太晚。**  
The Agent Beat 把 Failure as a Process 的结论总结成可操作建议：不要只记录 pass/fail，要保留完整轨迹，并把人工检查点放在首批命令之后。这个观点值得注意，因为它把“失败分析”从事后验尸变成早期干预和训练数据筛选策略。🔗 https://dev.to/theagentbeat/the-33000-token-tax-a-30-hour-star-race-and-where-agents-actually-fail-468p ｜ https://arxiv.org/abs/2607.09510

**Copilot CLI hardening 讨论：read-only / plan mode 必须由 runtime enforce，而不能只靠提示词。**  
GitHub Copilot CLI 对内置 mutating tools 做 plan-mode hard-block，社区关注点迅速转向 MCP external tools 的剩余缺口。这个洞察很重要：agent 安全边界需要覆盖所有工具路径，包括 LSP、MCP、shell、browser 和子代理，而不是只管产品自带工具。🔗 https://www.techtimes.com/articles/320560/20260715/github-copilot-cli-closes-agentic-loophole-plan-mode-can-no-longer-edit-your-files.htm
