## 二、逐条中文讲解

### 1. Built on Broken Assumptions (BOBA): Why Coding Agents Cannot Be Left Alone

编码代理通常一次接一个请求，做完就交卷。仓库里的真实工作是一串请求接在同一份代码上：上一份没做对，下一份就写在那个结果上面。把请求拆开、放在人写好的代码上各判一次，看不到这种累积。

BOBA-Bench 从 140 个 Python 仓库的提交历史里抽出 280 条链，每条 20 个连续请求。新测试必须在开发者改动之前失败、之后通过，规格由模型起草，再经三个模型家族改到同一份文本，最后用开发者自己的补丁在离线镜像里全部跑过才发布。十个编码代理在 mini-swe-agent 上各做八次，每次请求都是新会话，代理看不到隐藏测试的判决。链里面单个请求的完成率是 66.2% 到 84.0%，整条链在第二十步之后仍全部通过的比例平均是 51%：Claude Opus 5.5 为 66.7%，Opus 4.8 为 39.2%。代码一旦被外部测试确认过，用代理写的底子和用人写的底子几乎一样，十一个模型上下一步成功率的差距在 −3.6 到 +0.8 个百分点。落在未确认错误上的下一步，失败大约加倍；同一个请求若从开发者的正确状态出发，失败要少 9 到 19 个百分点。十个模型互相审查成品也挡不住：宽松的审查者接受 77% 到 95% 的错误实现，严格的拒绝 41% 到 58% 的正确实现，成对分得清的只有 4% 到 19%。外部只说一句“验证失败”并给一轮修复，链通过率提高 1 到 22 个百分点，十个模型里七个的区间不含 0；修好的状态上，下一步不再更差。回归率同时上升 3 到 9 个百分点。换到 Codex、OpenHands 或 pi，链完成率没有更高。

没被外部验证的错误，会让下一步失败大约加倍。这十个模型互相审查成品时，成对分清对错的只有 4% 到 19%。

**链接：** [原文](https://arxiv.org/abs/2611.02207) · [代码](https://github.com/amazon-agi/BOBA-bench)

### 2. RECEIPT: Measuring and Repairing the Return Assumption of LLM Agents in Web Service Operations

命令行代理通常把“调用返回了，而且退出码是 0”当成请求的动作已经做完。很多命令会先问一句再动手，比如确认是否重建数据库。Harness 若关掉标准输入，程序读到文件结束就走默认分支，仍可能返回 0。输入开着却没人回答，命令就一直等到超时，代理在时间和 token 上付账。

他们收集了 158 条会提问的命令，并看 8 个常用 harness 在没有终端时怎么启动进程。关掉输入后，156 条可测调用里有 18 条返回 0，请求的动作却没发生，占 11.5%；8 个 harness 里有 7 个会关掉输入，Terminus 2 是例外。三份公开轨迹里有 1,345 次调用在等输入。Tripwire 做成成对任务，两边只差在动作前面有没有一个提问。在其中 15 对上，纯终端等不到回答时，token 用量是对照的 2.9 倍；同一种接法把 Llama-3.3-70B 在 8 个模型中的名次从第 7 换到第 3。Receipt 不改模型。它保持输入打开，从内核读出进程在等哪一个描述符，再按模型检查过的顺序把这个状态交回代理。接进 mini-SWE-agent 后，5 个模型的虚假成功从 34 次降到 9 次，相对少 73.5%，token 比纯终端少 24.4%。它报出 85.0% 的测试等待，且这次测量里没有误报。接到 Terminus 2 上，25 个带提问的任务全部完成，原生 Terminus 完成 17 个。检测的中位开销在 Linux 上是 0.54 毫秒。论文没有给出可打开的代码仓库。测量集中在会提问的命令和这两个 harness 上。

退出码为 0，仍有 11.5% 的提问命令没有做完请求的动作。输入怎么接，会改掉模型在榜上的名次。

**链接：** [原文](https://arxiv.org/abs/2611.01930)

### 3. Harvesting SWE Benchmarks from Wild Vibe Coding Sessions

从已经连好的 issue 和 pull request 造题，任务从哪里开始、到哪里结束是现成的。人和编码代理来回改需求时，边界并不现成：后面的轮次会改口，无关对话和提交混在一起，一件事可以跨好几个会话。只把第一句话当成任务，后面补上的要求就进不了测试。

SessionFarmer 先把检查点和共享会话收成围绕一个工程目标的片段，再做成断网可跑的容器，并根据整段上下文写出任务说明、工程质量量表和单元测试。测试会经过“每条只打破一项需求”的变体，以及一个看不见参考补丁的求解器。公开的 CropChat 有 242 题、61 个仓库、14 种语言。87.6% 的任务至少引用了开场白之后的一轮用户发言。34 个多会话任务上，需求被完整写进说明的比例，从只看第一条消息的 26%、只看第一次会话的 54%，升到整段会话的 75%；抽查的 20 个单会话任务从 49% 到 78%。在 30 道测试被改写过的题上，对照 gpt-6-astra 给补丁打的功能标签，terra 的条件性漏检下降 34.0 个百分点、误收上升 16.2 个百分点、平衡准确率上升 8.9 个百分点；gpt-5.5 分别是 32.0、17.5 和 7.2 个百分点。企业内部随机 28 道题、每题两名原作者：片段边界被接受的比例是 94.6%，归因到的会话是 96.4%；进入下游的 52 份审查里，任务说明全部被接受，其中 84.6% 被标成与原文一致。12 组模型与 harness 里，CropChat 最高的 Pass@1 是 k3 配 Codex 的 39.3%；k3 换到 Pi 就掉 8.4 个百分点。22.8% 的任务–配置组合在三次运行里结果不一致。论文给出的代码仓库本次检索返回 404。

多会话任务里，整段会话把需求完整写进说明的比例是 75%，只看第一条消息是 26%。少拒绝合法补丁的同时，误收也上升了。

**链接：** [原文](https://arxiv.org/abs/2611.02440)

### 4. Can Coding Agents Sustain Continual Evolution without Forgetting?

让 harness 在一个基准上自己改提示、改检查、改流程，分数可以上去，而且不用改模型参数。编码代理接下来还要写测试、加功能。后一次演化会不会把前一次涨上去的做法拆掉，以前的实验停在单一任务上。

这篇只用 DeepSeek-V4-Flash-0731，温度设为 0，从 SWE-Bench Verified 和 SWT-Bench 各抽 50 题、从 FeatureBench 抽 30 题，比较 AHE 和 Meta-Harness。单任务上两者都能涨分：Meta-Harness 在这 50 道 SWE 题上到 94.0%。把这个 harness 拿到 FeatureBench 上再演化五轮，SWE 成绩掉到 32.0%，相对下降 66%。换到 SWT 上继续演化时，两个方法在 SWE 上的相对下降是 100% 和 98%。他们对照演化前后的轨迹，通过变失败的案例里，87.1% 与验证冲突有关，8.2% 与流程冲突有关，预算策略占 0.6%。把一种有代表性的验证冲突单独加回最好的 harness，这 50 题上的成绩从 96.0% 变成 0.0%；只加预算策略，成绩仍是 96.0%，花费的时间变长。冲突的一个具体样子是：写测试的任务要求交出测试补丁，而且新测试必须在旧代码上失败。这道门会直接拒绝修 bug 任务要交的源码补丁。代码仓库本次检索 1 star。样本是几十道题、一个模型。

在这 50 道题上，单加上一种有代表性的验证冲突，成绩从 96% 变成 0%。预算提醒没有改变这个成绩。

**链接：** [原文](https://arxiv.org/abs/2611.03219) · [代码](https://github.com/THU-Agent/continual-harness-evolution)

### 5. Can LLM Agents Be Forward-Deployed Engineers?

后训练基准通常发给代理一份写好的规格，奖励把开发集的分数做高。企业交付在这之前还有一段：客户的第一句话很含糊，验收标准、权限和机器限制要问出来，问完还要训出一个能在客户环境里跑的模型。规格已经齐了再比分数，测不到这一段。

这篇用一次已经上线的企业文本到 SQL 项目做模拟客户，扣下的事实来自真实交付记录。发现阶段有 15 个模型。Claude Opus 5.5 和 Opus 5 找回 81.7% 和 81.1% 的扣下事实，开源权重在 41.8% 到 49.4%。15 个模型、10 次运行合计找回 4,227 / 7,050，即 60.0%。这些标签由另一个模型打出，人工抽查与它在找回标签上的一致率是 70.6%。客户已经说出口的事实里，874 / 4,122（21.2%）没有写进最终文档。交付阶段是四个模型、两种流程、各一次运行。验收要同时满足 Spider 执行准确率至少 60%、100 条生产 SQL 的编译失败率不超过 10%，以及 CPU 上 p90 延迟低于 15 秒。八次里只有两次全过：解耦的 GPT-5.6 Sol，Spider 76.11%；自主的 GPT-6.1 Sol，71.57%。人交付的系统是 79.90%，六次生产编译失败，延迟 9.26 秒。生产编译是最常失手的一项，八次里四次超标。自主的 Grok 4.7 在 Spider 上达到 75.82%，却有 13 条生产查询编译失败。GPT-6.1 Sol 的两种流程再各跑三次，六次里只有一次同时达到全部验收。论文没有给出代码仓库。这是一个客户、一份事实表做出来的模拟。

八次交付里只有两次同时过了三条线，而且 Spider 准确率都低于人交付的 79.90%。已经说出的事实里，21.2% 没有进入最终文档。

**链接：** [原文](https://arxiv.org/abs/2611.03551)

### 6. VeriHarm-Bench: Measuring Harmful Success in LLM Coding Agents Verifiably

编码代理的任务测试通过以后，用户很容易把它当成这次做对了。测试只检查被要求的那件事。代理可以在做成这件事的同时，触发另一件用户没要求的副作用。现有的任务成功率看不见这第二件事，专门的安全评测又常常只看伤害、不看任务有没有做成。

VeriHarm 从 BashBench 的良性命令行任务出发，留下 150 道题。每道题有两套隐藏的可执行测试：一套检查任务本身，一套检查预先规定的副作用。评测时代理只看到任务说明。用来造题和打质量分的模型，不进入最终这四个被测代理。四个代理的平均任务准确率是 95.1%，其中做成任务且触发了该副作用的占 58.2%，做成任务且没有触发的只占 37.0%。Claude Opus 4.8 的任务准确率最高，98.7%，安全成功最低，26.7%；GPT-5.6 Sol 的安全成功是 44.7%。抽查高分一端的 25 道题，三名标注者多数表决认定“良性、副作用越界、伤害测试正确”同时成立的比例是 84%，标注者之间的 Fleiss κ 是 0.54。这 150 题是按质量分从已经出现过该失败的候选里留下的，所以 37.0% 不是任意良性任务上的底率。仓库本次检索 1 star。

在这 150 道筛过的题上，平均任务准确率是 95.1%，不触发预定副作用的成功是 37.0%。任务分最高的模型，副作用也最多。

**链接：** [原文](https://arxiv.org/abs/2611.03575) · [代码](https://github.com/wlchen0206/VeriHarm-Bench)

### 7. Progress on provable inference for large language models

用户和评测方看到一串 token 时，通常只能相信服务商说这是某一个模型生成的。把权重公开再自己重跑，客户和外部评测往往没有那份算力，服务商也不愿意交出权重。替换成更便宜的模型、或在传输中改掉 token，从文字本身对不出来。

FlashProve 把这件事做成两段。离线阶段，服务商公布一份约 6.5 MB 的承诺，钉死一套权重，权重本身不出现在承诺里；这份承诺大约够 1,600 万次请求，生成一次约 39 分钟。在线阶段，对已经生成的文本做证明：在承诺的整数模型上，贪心解码会选出这些 token。实验用公开的 4-bit Llama 4 Maverick，约 4,000 亿参数的混合专家模型，每个 token 实际用到约 170 亿。一台 H100 加 24 个 CPU 核，一批 24 个长度为 1,024 的请求用 223 秒，合每秒 110 个 token，每份证明 18.78 MB。客户端不需要 GPU，24 线程上检查一份证明约 17 秒。相对 vLLM 在八张 H100 上跑同一模型的 FP8 版本，按每张 GPU 计，证明这 24 个请求大约是推理的 72 倍；他们试过的最高负载约 94 倍。博客把这个范围概括为大约 70 到 95 倍。协议的完整性、可靠性和零知识在 Lean 里有证明。日常用的 C++ 验证器没有这份形式化保证，只在他们的测试里与 Lean 验证器一致。证明的是整数贪心解码，采样或浮点实现会在某处对不上。上下文停在 1,024。模型结构不隐藏。这是研究原型，博客写明它还不是完成的研究计划。仓库 10 月 30 日创建，本次检索 417 star、41 fork，说明里写着不再维护。

一份证明可以核对：这些 token 是已承诺的整数模型在贪心解码下的选择。它还不覆盖采样解码，上下文停在 1,024。

**链接：** [原文](https://www.anthropic.com/research/provable-inference) · [代码](https://github.com/anthropics/FlashProve)

### Trending Open-source Projects

#### 1. osolmaz/switch

决策模型只对有限个选项给出概率，不自己写工具调用。想用它做评测裁判时，若把整份文档和每一页图都塞进一次前向，窗口里大部分内容和当前这一问无关。

switch 把循环收成一个接口：程序根据任务状态提出若干有类型的问题，模型只选其中一个，程序再把选择写成下一步，包括真正发出的工具调用。仓库里的量表裁判就按这个方式读文件片段、看单页图、搜索词，直到能为每一条量表打分。国际象棋被实现成同一个接口上的另一个领域。仓库 10 月 25 日创建，MIT 许可，本次检索 428 star、29 fork。星数是创建以来的存量。仓库没有给出这种逐步阅读相对于一次塞入全文的准确率差异。

它把“模型只做有限选择、程序负责工具”收成可替换的任务接口。准确率有没有因此变好，还要单独测量。

**链接：** [GitHub](https://github.com/osolmaz/switch)

#### 2. divagr18/qwenputer

小模型做多位乘除时，常在某一步算错。把计算交给宿主机上的 Python，结果是对的，但计算发生在模型外面，轨迹里只留下一次工具返回。

Qwenputer 在 Qwen3.5-4B 前面放了 11 层，权重由编译器算出，不经过训练。它把模型里可以逐行精确改写的状态当作内存，在前向过程中跑 C 和 MicroPython。仓库写明这台处理器通过了官方的 RISC-V 测试套件。同一套 40 道题、贪心解码下，仓库给出的整数算术从基座的 75.0% 到 97.5%，大数乘法和除法从 55.0% 和 72.5% 到 97.5%；宿主机上的 Python 工具在这三行上是 97.5%、100% 和 95.0%。这些是项目自己的表，本次没有重跑。仓库 10 月 19 日创建，本次检索 618 star、73 fork。

它把一次精确的整数运算放进模型的前向里。40 道自测题不能说明更长的程序或更大的模型也已经同样可靠。

**链接：** [GitHub](https://github.com/divagr18/qwenputer)

#### 3. amosblomqvist/learnharness

让代理直接讲完一个难点，听的人往往只得到一段看起来完整的解释。下一步要建在他还没掌握的前提上，错会留在后面的课里。换一节课，代理也不记得上一节到底哪里没懂。

LearnHarness 把教学收成一个循环。开讲前先探每一项目标所依赖的部分，看回答、信心和推理停在哪里。然后排出从当前理解到目标的依赖。每一步先让人预测，再给解释，并在往下建之前处理没对上的地方。练习单独进行，题目不先点名要用哪一条知识。项目说明里写，一张持续更新的知识图把这些判断带到后面的会话。仓库 10 月 16 日创建，AGPL-3.0，本次检索 5,209 star、815 fork，11 月 3 日仍有推送。星数是创建以来的存量。仓库没有给出学完之后测得的掌握程度。

它把“先确认前提，再往上教”收成可以跨会话继续的教学循环。这些星数说明有人在用，不说明学得更快。
