## 📝 逐条讲解

### Agents' Last Exam：面向 55 个行业的长程专业工作流评测
过去很多 agent benchmark 要么偏代码、终端、网页，要么偏问答，离“真实职业工作流能否被自动完成”还有距离。Agents' Last Exam（ALE）把评测对象定义成 Generalist Computer-Use Agent，也就是能同时用 GUI、CLI、文件、浏览器和代码执行的通用工作 agent。它的任务来自 250+ 行业专家，覆盖 O*NET / SOC 职业分类下 13 个行业集群、55 个子领域，并把任务做成虚拟机中的可执行 workflow：agent 只能看到输入、软件和任务描述，参考答案藏在 `reference/` 里由 `evaluate()` 打分。最重要的工程设计是“公私池 + 滚动评测”：只公开约 150 个任务，更多任务留在私有池并周期性轮换，以降低 benchmark 泄漏和过拟合。当前最强主流 harness 组合在最难层级平均 full pass 仍只有 2.6%，说明真实长程专业任务还远未被刷穿。对后训练软件工程来说，ALE 的价值不只是一个大榜，而是给“GUI + CLI + 可验证 artifact + 行业专家 QC + 私有滚动任务池”提供了完整评测生产范式。
🔗 链接：https://arxiv.org/abs/2606.05405 ｜ 代码：https://github.com/rdi-berkeley/agents-last-exam

### EvoCode-Bench：多轮需求演化下的持久 workspace 评测
真实开发不是一次性给完整需求、一次性提交最终答案；用户会不断补充格式、修正假设、改变约束，还要求旧功能别坏。EvoCode-Bench 正是针对这个缺口：它让同一个 Docker workspace 和同一个 agent session 连续跑 5 到 15 轮，每轮只追加或修订需求，并用累计可执行测试检查所有仍然有效的旧要求。它同时报告 MT@4 和 SR：MT@4 测 agent 能否维护自己一路写下来的 workspace，SR 则把前面轮次快进到参考解后只测当前轮，这两个分数的差异能直接暴露“单轮会做”和“长期维护会做”的差距。结果很刺眼，多数 agent 的 SR 比 MT@4 高 22 到 40 分，说明它们从干净参考状态出发能完成很多单步任务，但在自己积累的代码状态里会快速掉队。项目 6 月已迁移到 Harbor 官方 multi-step task format，说明它不只是论文基准，也在向可复用的评测基础设施靠拢。对 coding agent 后训练来说，这类持久状态、累计 verifier、fail-stop 计分非常适合作为训练/评测 harness 的模板。
🔗 链接：https://arxiv.org/abs/2605.24110 ｜ 代码：https://github.com/UniPat-AI/EvoCodeBench

### Bayesian-Agent：把 skill/SOP 演化做成可审计贝叶斯证据层
技能库和 SOP 很容易从“经验沉淀”变成“提示词垃圾堆”：一次失败后随手加一条规则，短期可能修好当前任务，长期却可能引入冲突、过拟合或陈旧假设。Bayesian-Agent 的核心做法是把每个 skill/SOP 当作一个“关于某类任务是否有帮助的假设”，而不是一段永远可信的文本。它从经过 verifier 检查的轨迹里提取证据，按任务上下文、失败模式、token/turn/延迟等离散特征维护 posterior，再把 posterior 映射成可审计动作：patch、split、compress、retire 或继续 explore。模型本身看不到复杂概率表，而是收到具体可执行的 guardrail 和 failure-mode patch；posterior 留给 harness 做排序、审计和调试。实验里 deepseek-v4-flash 在 SOP-Bench 从 80% 修到 95%，Lifelong AgentBench 从 90% 到 100%，RealFin-Bench 从 45% 到 65%。它对 skill management 的启发很明确：技能演化不应只靠 LLM 反思文本，而应由“外部验证证据 + 明确不确定性 + 可回滚操作”驱动。
🔗 链接：https://arxiv.org/abs/2606.08348 ｜ 代码：https://github.com/DataArcTech/Bayesian-Agent

### Harness-1：用 state-externalizing harness 训练搜索 agent
搜索 agent 常被训练成“在越来越长的 transcript 里边搜边记”，这会让模型同时承担语义决策和机械记账两件事。Harness-1 的观点是，候选文档池、已读文档、证据图、验证记录、上下文预算这些状态，环境比模型更适合维护；模型应该把精力放在“搜什么、保留什么、验证什么、何时停止”。它把搜索过程做成一个带 WORKINGMEMORY 的 stateful harness：候选池、importance-tagged curated set、evidence graph、verification cache、压缩去重观察都会被持久更新并按预算渲染回 prompt。训练上，SFT 先教模型操作这个接口，RL 再优化完整搜索 episode 的终局 reward，reward 区分“轨迹中找到过证据”和“最终 curated set 真的选对证据”。结果在 8 个 web、金融、专利、多跳 QA 检索基准上，20B Harness-1 平均 curated recall 到 0.730，比下一个开源搜索 subagent 高 11.4 分，并且 held-out transfer 增益更大。对 agent harness 工程来说，这是一个很好的“认知卸载”案例：把可恢复、可计算、可审计的状态移出模型，训练更稳定，推理也更可解释。
🔗 链接：https://arxiv.org/abs/2606.02373 ｜ 代码：https://github.com/pat-jj/harness-1

### WildClawBench：真实 CLI harness 中的长程多模态 agent 评测
很多 agent benchmark 仍然跑在短任务、mock API 或过度干净的沙箱里，无法回答“真实 CLI harness 里到底能不能完成长程工作”。WildClawBench 把评测搬到 native runtime：每个任务在可复现 Docker 容器里运行实际 CLI agent harness，如 OpenClaw、Claude Code、Codex 或 Hermes Agent，而不是只测模型裸能力。它包含 60 个真人编写的双语多模态任务，平均约 8 分钟墙钟时间、20+ tool calls，覆盖文件、图像、终端、真实工具和环境副作用。评分采用混合方式：可确定的部分用规则检查，环境状态用 side-effect audit，语义结果再由 LLM/VLM judge 补足。结果显示最强 Claude Opus 4.7 在 OpenClaw 下也只有 62.2%，而同一模型换 harness 最高可差 18 分。对后训练软件工程而言，这强调评测必须把“真实运行壳、真实工具、副作用和多模态观察”纳入变量，否则容易高估 agent 在生产 runtime 中的可靠性。
🔗 链接：https://arxiv.org/abs/2605.10912 ｜ 代码：None

### GitHub MCP Server 1.1.0：官方 MCP 成为 coding agent 基础设施
GitHub 是 coding agent 最常接触的外部系统之一，但传统做法往往是在 shell、REST API、GitHub CLI、网页之间来回切换，权限和审计边界也不统一。GitHub 官方 MCP Server 把 repository、issue、PR、workflow 等能力通过 MCP 暴露给 agent，近期 1.1.0 release 和 31k+ stars 显示它已经成为社区默认基础设施之一。它的价值不只是“多了一个工具服务器”，而是 GitHub 这种核心开发平台开始把 agent 当作一等客户端来服务。对 agent-friendly tooling 来说，官方 MCP 的好处是 schema、权限、身份、审计和 API 语义由平台方维护，企业更容易把它接进 Claude Code、Cursor、Codex、OpenCode 等不同 harness。风险也很清楚：GitHub API surface 很大，如果所有 schema 常驻上下文，会放大 MCP 税，因此仍需要工具过滤、动态发现和最小权限配置。今天把它放入 High，是因为它是“传统开发平台 agent 化”的关键落地点。
🔗 链接：https://github.com/github/github-mcp-server/releases/tag/v1.1.0 ｜ 代码：https://github.com/github/github-mcp-server

### Addy Osmani：Agent Harness Engineering
Addy Osmani 这篇文章把近期社区关于 harness 的零散讨论整理成一个工程纪律：coding agent 不是“模型”，而是“模型 + harness”。文章最有价值的观点是 ratchet：每次 agent 犯错，都应该转化成一条规则、一个 hook、一个测试 gate、一个 sandbox 限制或一个 context policy，让同类错误下次更难发生。它把 harness 拆成 system prompt、AGENTS.md、tools、skills、MCP、sandbox、memory、context compaction、subagent、observability、hooks 等可维护组件，而不是把失败归因给“模型还不够聪明”。文中对 context rot、tool-call offloading、渐进式 skills、planner/generator/evaluator 分离、success silent / failure verbose 的总结，都很贴近日常 coding agent 落地。对后训练软件工程来说，这类实践文章有一个重要启发：数据和 eval 之外，用户真正能持续改进的是 harness surface，本质上是一套可迭代的控制系统。它也解释了为什么同一个模型在不同 CLI 或 SDK 里表现差距很大，模型后训练和 harness 设计正在形成闭环。
🔗 链接：https://addyosmani.com/blog/agent-harness-engineering/ ｜ 代码：None

### WebGameBench：从需求到浏览器可玩应用的 coding agent 评测
很多 web/coding benchmark 检查的是源码、单测或中间轨迹，但用户最终关心的是应用能不能在浏览器里真的可用。WebGameBench 选择 browser-native games 作为评测对象，因为小游戏虽小，却要求输入处理、空间映射、状态转移、规则执行、终止条件、重启和视觉反馈同时正确。它给 agent 一个冻结的 Structured WebGame Specification，让 agent 产出完整应用，再统一 build、serve，并由运行时 evaluator 在真实浏览器中交互检查。评分不是只看能不能启动，而是分成 Excellent、Usable、Unusable，并用人工 gameplay review 校准 runtime label。111 个任务、12 个 coding agents、14 种评测配置的结果显示，最好配置 Usable 可到 76.9%，但 Excellent 只有 20.2%，说明“勉强能玩”和“完整满足需求”之间还有很大距离。对后训练评测来说，这提供了一个很实用的方向：把交付 artifact 放到真实 runtime 里验，而不是只在代码层面给分。
🔗 链接：https://arxiv.org/abs/2605.17637 ｜ 代码：None

### ComplexMCP：动态互依赖大型工具沙箱评测
现在很多 agent 工具评测仍假设 API 是独立、稳定、无噪声的，但真实商业软件不是这样：工具之间有状态依赖，调用结果会受环境影响，部分 API 还会随机失败。ComplexMCP 把这个“最后一公里”问题做成 MCP benchmark，提供 7 个 stateful sandboxes 和 300+ 系统验证过的工具，覆盖办公套件、金融系统等复杂场景。它用 seed-driven architecture 生成动态但可复现的环境状态，同时注入可控 API failure，让评测既有真实扰动，又能重复运行。论文还强调 latent tool interdependencies：agent 不能只会调用单个 schema，还要理解工具之间的隐含先后关系、状态更新和失败恢复。结果暴露出 clean-slate bias 等失败模式，即 agent 常假设环境干净、工具独立，从而在真实状态里误操作。对 Agent-Friendly Software 来说，ComplexMCP 很重要，因为它把 MCP 从“工具调用接口”推进到“复杂软件自动化沙箱”的评测层。
🔗 链接：https://arxiv.org/abs/2605.10787 ｜ 代码：None

### EvalAgent：用 evaluation skills 自动生成 agent 评测流水线
评测 agent 本身也越来越像软件工程任务：要读轨迹、定义指标、写可执行评测代码、跑场景、产报告，单靠一句 prompt 很难稳定完成。EvalAgent 的发现是，强 coding assistant 如果没有评测领域知识，只靠提示去写 eval，执行成功率只有 30%，还会产出平均 12+ 指标的过度工程化方案。它把评测知识封装成 evaluation skills，包括过程指令、可复用代码/模板和动态检索 API 文档，再组成 trace-based pipeline，输出 metrics、executable code 和 reports。作者还提出 AgentEvalBench：20 个 agents，每个配评测需求和测试场景，并用 Eval@1 衡量第一次生成的评测代码是否能执行且有意义。结果 EvalAgent 把 Eval@1 从 17.5% 提到 65%，人类专家偏好达到 79.5%。对本日报关注的 eval engineering 来说，这是“评测生产自动化”的直接案例：以后不仅训练数据可以 agent 化，评测脚本、指标和报告也需要 skill 化、模板化和可回归。
🔗 链接：https://arxiv.org/abs/2605.11378 ｜ 代码：None

### AgentAtlas：从结果榜转向控制决策与轨迹诊断
很多 leaderboard 只记录最终成功或失败，但 agent 的失败可能来自错误行动、该问不问、该停不停、拒绝过度、恢复失败等完全不同的控制决策。AgentAtlas 提出一套诊断词汇，把 agent 控制决策分成 Act、Ask、Refuse、Stop、Confirm、Recover 六类，并给轨迹失败标注 primary error source 和 downstream impact。它还用 0/1/2 方式审计 15 个 agent benchmark 覆盖了哪些行为轴，帮助研究者看清“这个榜到底测了什么、漏了什么”。论文的 synthetic protocol study 不是要给模型重新排榜，而是说明一个测量风险：显式 label menu 一拿掉，标签一致性和模型排序可能会明显变化。对评测工程来说，AgentAtlas 的价值在于给 benchmark designer 一套报告语言，让最终分数背后的控制错误可比较、可审计。它适合作为未来 agent eval report card 的方法论补丁，而不是又一个单一分数榜。
🔗 链接：https://arxiv.org/abs/2605.20530 ｜ 代码：None

### Ramp：生产系统中的 runtime agent assessment
静态 benchmark 往往把每个任务孤立运行，agent 状态清零，和真实生产系统中一环扣一环的依赖链差别很大。Ramp（Runtime Assessment of Models in Production）把评测放到更接近生产的软件工程工作负载里，使用编译器构建这类 serial dependency chain 来观察 agent 在长程依赖中的表现。它基于 YatCC integrated serving platform，统一不同 LLM provider 和 agent SDK 的接入、编排和运行评估，让 scaffolding effect 和 execution complexity 可以被系统比较。项目时间线也很工程化：4 月提出想法，4 月下旬启动，5 月 10 日开源 repo/leaderboard，5 月 14 日完成 draft。结果显示某些前沿模型在部分编译器任务上很强，但 IR optimization 等阶段仍会掉队，说明“会写代码”不等于能稳定穿过生产级依赖链。对后训练软件工程来说，Ramp 代表一类重要趋势：评测不再只是数据集，而是运行在生产式服务平台上的 runtime assessment infrastructure。
🔗 链接：https://arxiv.org/abs/2605.27492 ｜ 代码：None

### OpenAI：通过 Oracle Cloud commitment 访问 OpenAI 模型和 Codex
OpenAI 6 月 10 日发布的 Oracle Cloud 访问通道不是模型能力论文，但属于官方近月新发布，且直接涉及 Codex 的企业分发路径。它解决的是采购和治理摩擦：很多企业已经有 OCI 预算和采购流程，不愿为 AI 单独开新合同、新付款路径和新治理例外。通过 Oracle Universal Credits 访问 OpenAI 模型和 Codex，企业可以把 agent adoption 嵌入现有云承诺和审批框架。对本日报核心主题来说，它不是高优先级技术突破，但它说明 coding agent 正在从个人工具进入企业 IT 采购体系。工程上值得关注的是，一旦 Codex 通过云承诺分发，后续对 workspace 隔离、日志、身份、网络策略和审计的要求会进一步强化。

### Anthropic / Dario Amodei：Policy on the AI Exponential
Anthropic 6 月 10 日在 Newsroom 标出 Dario Amodei 的 Policy on the AI Exponential，主题偏政策，但与 frontier model evaluation 强相关。文章认为 Claude Mythos Preview 等近期能力显示前沿模型已经具备战略级网络安全风险，生物风险和自主性风险可能紧随其后，因此透明披露已经不够，需要更强的强制测试制度。核心提案包括：达到算力门槛的模型接受第三方风险测试，覆盖网络、生物、失控和自动化 R&D 加速风险；政府在风险不可接受时拥有阻止或逆转部署的权力；公司必须报告关键安全事件并强化权重安全、红队和渗透测试。虽然这不是 coding agent 工程文，但它会影响长程 agent 和高能力 coding model 的发布方式：eval、审计、风险报告和访问控制会越来越像部署门槛，而不是研究附录。对后训练软件工程团队来说，这意味着安全 eval、防滥用 harness、trace retention、trusted access 和 capability gating 都会更制度化。

## 🔥 社区热点专栏

### 🔥 大佬观点

**Andrej Karpathy：从 vibe coding 转向 agentic engineering，质量责任不能外包。**  
Karpathy 近期围绕“agentic engineering”继续强调，2026 年的默认范式不是人手写 99% 代码，而是人协调 agent 并承担架构、审查、安全和质量责任。它值得关注，因为这把讨论从“AI 写代码是否有趣”拉回到“如何在不牺牲质量栏的情况下让 agent 更快交付”，正对应本日报关注的测试 gate、review loop、权限和 harness 工程。🔗 https://www.youtube.com/watch?v=96jN2OCOfLs

**Addy Osmani：harness engineering 的核心是把每次失败变成系统规则。**  
Addy 的新文把 HumanLayer、Viv Trivedy、Simon Willison、Anthropic harness 经验串起来，提出“每次 agent 错误都应进入 ratchet”，也就是变成 AGENTS.md 规则、hook、sandbox policy、测试或 observability。这个观点重要，因为它把 agent 可靠性从“等下一个模型”改成“维护一个随失败历史生长的控制系统”。🔗 https://addyosmani.com/blog/agent-harness-engineering/

**Dario Amodei：AI 指数级进展需要把评测和审计从透明披露升级为强制测试。**  
虽然这是政策文章，但社区围绕它的讨论集中在一个工程事实：当模型进入 Mythos 级长程网络、科研和自动 R&D 风险区，eval 不再只是 leaderboard，而会变成部署许可的一部分。对 agent 团队来说，这意味着 red-team、第三方评测、trace 留存、capability gating 和 incident reporting 会成为产品发布基础设施。🔗 https://darioamodei.com/post/policy-on-the-ai-exponential

### ⭐ 超火仓库/项目

**GitHub MCP Server（github/github-mcp-server）：31k+ stars 的官方 GitHub agent 接口。**  
GitHub 官方 MCP server 已成为 coding agent 接入 PR、issue、repo 和 workflow 的默认基础设施之一。它火的原因是痛点明确：agent 不应在网页、REST、gh CLI 和自写脚本之间拼凑 GitHub 操作，而应通过平台维护的权限化、可审计、结构化工具面工作。🔗 https://github.com/github/github-mcp-server

**Agents' Last Exam（rdi-berkeley/agents-last-exam）：把 agent 评测推向真实职业工作流。**  
仓库公开了 ALE 的 `ale_run` 评测框架和约 150 个公开任务，背后还有更大的私有滚动任务池。它的热度不只来自 55 行业覆盖，而是解决了一个真实痛点：GUI/CLI 混合、专业软件、可验证 artifact 和行业专家 QC 如何放进同一个 agent benchmark。🔗 https://github.com/rdi-berkeley/agents-last-exam

**Boxes.dev（Show HN）：给 Claude Code / Codex 每个任务一台云端开发机。**  
HN 讨论里的核心痛点是 agentic coding 的 localhost 负担：多 agent 并行跑全量测试会吃掉本机资源，移动端和远程恢复也很差。Boxes.dev 的思路是把 dev environment snapshot 到云端，每个 Codex/Claude Code thread 拥有独立文件系统和 compute，让 agent 能真正端到端测试而不互相踩环境。🔗 https://news.ycombinator.com/item?id=48399358
