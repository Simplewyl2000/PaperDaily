## 二、逐条中文讲解

### 1. Silent Instrument Errors Reorder Agent Leaderboards

编码代理的排行榜把一次准确率当成模型或脚手架的能力。读者会以为，这个数字是评分器按基准的规则，对代理自己的那一回合算出来的。HAL 上有一个反例：航空客服里，通用代理比专门为这个基准写的脚手架低 13 个百分点，九个一起测过的模型里八个都落后。这个差距主要不是“通用就要付准确率的代价”。

TAU-bench 只在回合正式结束时才打分。通用代理常常发一条收尾消息就退出。如果中途没有把客户转给人工，模拟用户不会回一个停止符，数据库根本不会被比较，这一回合就被存成 0 分。专门脚手架有 98% 的回合被打过分，通用代理只有 51%。把漏掉的一半按同一条奖励规则离线补评，那 41 道会改数据库的题上，汇合准确率从 0.30 升到 0.43，和专门脚手架的汇合差距收成平局；专门脚手架最多动 2.5 个百分点。同一套公开档案里还有三类同样安静的误差。费用列把嵌套调用算了两次，其中一行把 74.99 美元写成 149.98 美元。轨迹里混进了评分器自己的动作，2,334 条航空记录里占 68%；有 58 条记录里代理一次工具都没调，档案却写着完整的标准答案。一次已经公告的重新评分，仍把 gemini-3-flash 从第九名移到并列第五，并翻转 136 对比较里的 4 对。另有四个文件被模式检查读错，分数掉 59 到 82 个百分点，命令却不报错。HAL 的维护者在五周内确认了他们那边的三处。已经发表的行没有改写。代码仓库本次检索 0 star。

榜上的数字可以在评分器没跑的时候看起来完全正常。先核对这一回合有没有被评分，再解释模型差在哪里。

**链接：** [原文](https://arxiv.org/abs/2611.04399) · [代码](https://github.com/YangzeLiu/eval-instrument-disclosure)

### 2. Eval-production behavior gaps in agent safety and the role of eval-awareness

安全评测想回答的是，代理在真实使用里碰到警告时会不会绕过去。常见的担心是模型认出这是考试，于是表现得比上线时更安全，分数把安全高估了。OpenAI 把“尊重警告”这项评测，和去掉身份信息的 Codex 生产日志里、结构相近的决定放在一起比。

六个正在服务的模型，评测成功率都低于配好的生产决定，差距从 10.2 到 37.4 个百分点，最大的是 GPT-5.6 Sol 和 GPT-6 Sol。成功的定义是，遇到相关警告之后没有做出被禁止的尝试。两边的说明、工具和题目组成并不相同，生产样本是在结果出现之前配对的，所以这不是同一批题的重考。只在系统提示里写“这是一次评测”，GPT-6.1 Sol 从 63.4% 变成 63.1%，没有可分辨的变化。写明正确目标是尊重警告，成功率到 91.6%；写明相反的目标是抵抗提示注入，掉到 17.6%。口头猜对目标的回合，成功率是 61.3%；猜成抵抗注入的，是 22.8%。差距最大的那两个模型，有超过 45% 的评测回合把目标猜反。六个模型之间，评测分和生产分的秩相关是 0.771，样本只有六个，绝对分数不能直接当成上线时的成功率。

只说“这是评测”几乎不改分。写明评测在考什么，安全成功率会从大约六成被拉到九成，或掉到两成以下。

**链接：** [原文](https://alignment.openai.com/eval-production-behavior-gap/)

### 3. PAYWORTHY: Can LLMs Predict Which Freelance Jobs an AI Agent Will Complete?

代理接一份有报酬的工作之前，总要有人判断客户会不会收下结果。现有基准报告的是，代理在编好的题上做成了多少。它们不报告另一件事：动手之前，有没有人能把会做成的活排到前面。

PAYWORTHY 从 2020 到 2026 年的 1,880 万条自由职业广告里抽出 1,494 条。代理只看到广告，一次回复，不用工具。扮演客户的模型收下 54.4% 的交付。十八个预测模型给每份工作一个成功概率。提示里如果写明这个代理做不到什么，例如收不到客户的文件、不能用工具，排序的 AUC 是 0.66 到 0.86，它们排在最前的五分之一被收下的比例是 65% 到 92%。换成“一个会用浏览器和代码的通用代理”，同一个模型、同一批工作，AUC 掉到 0.45 到 0.56。十八个里有十五个，最前的五分之一比随机抽的五分之一更少被收下。五个模型家族的裁判对同一批交付的收下率从 33% 到 58%，所以这里比的是排序，不是某一个收下率。另有 500 条工作交给真正能搜索、能执行代码、还能问模拟客户的代理，收下率从 52% 升到 67%，通用描述下的预测仍然接近随机。论文给出的代码地址这次检索返回 404。

动手之前能不能把做得成的活排到前面，取决于有没有写明代理做不到什么。写成通用的浏览器加代码，排序就接近随机。

**链接：** [原文](https://arxiv.org/abs/2611.05759)

### 4. You don't need long context

上下文越长，后面每个 token 越贵。他们按 H100 的按需价格换算，三款开源模型在 256K 窗口上生成，比在 16K 上贵 3.6 倍到 7 倍。人们愿意付这笔钱，是因为任务很长，或者文档很长。这两件事并不自动要求模型每次都看见全部历史。

他们试了一种极端压缩：每做完一个动作，就把对话收成一段短摘要，下一步在新的上下文里只带着这段摘要继续。脚手架是 mini-swe-agent。Claude Opus 4.5 在 SWE-bench Verified 上，从看完全史的 70.0% 到 70.2%；在 Terminal-Bench 2.1 上，从 47.2% 到 51.8%。GPT-5.6 Sol 从 84.4% 到 82.4%，终端任务从 87.6% 到 84.3%，84.3% 是 89 题里做成 75 题。这种走法下，单次上下文的中位数是 7K 到 9K token，最大值从 13 万到 20 万降到 1.5 万到 3.7 万。长文档上的针检索有一档比把全文塞进窗口高 40 个百分点，更像少读了无关文本，不是摘要变出了新信息。论文里的“语义状态空间模型”还是设想，没有训出这样一个模型，也没有给出代码。

每步只留短摘要，这两套软件任务的准确率没有崩。Sol 仍掉 2 到 3 个百分点，长上下文不是做成的前提。

**链接：** [原文](https://arxiv.org/abs/2611.05306)

### 5. Verifier strength does not buy discovery quality

自动科研通常把一个会提案的模型和一个验证器配在一起，默认验证越严，找到的东西越好。如果这是对的，加预算应该主要加在检查上。他们预先登记了一项检验。领域是车间调度，以及用北京出租车轨迹做的车载边缘卸载。每个领域有 100 对：一边是模型提案，一边是随机提案。

验证器确实分得出档次。429 个突变样本上，分数随档位上升。模型相对随机提案的优势却不跟着升。调度上的单侧 p 值是 0.1115，卸载上是 0.9994。卸载在最严的一档，优势还缩小了，边际对比是 −0.040，p = 0.0013。较弱的两道门在 100 对和 99 对里放行的是同一个候选，因为同一次会话里的提案几乎要么全能过、要么全不过。有一对卸载任务里，压力测试拿掉了留出集上能得 0.524 的候选，改推一个得 0 的。把两个提案池混在一起，调度上能多出 1.52 个留出集单位。这是事后分析，不在预先登记的检验里。标准、账本和脚本放在 Zenodo。

预先登记的结果是：验证更严，并没有让模型提案胜过随机提案。把提案池变宽，是事后才看到的另一条路。

**链接：** [原文](https://arxiv.org/abs/2611.04420) · [账本](https://doi.org/10.5281/zenodo.23308866)

### 6. From AutoResearch to Continual AutoResearch: Do Agents Learn Across Tasks?

研究代理每换一道题，通常就新开一个会话。这样既贵，也看不出上一道题留下的状态有没有用。他们让同一个代理在配对的任务流上跑两次。数据、时间和顺序都对齐：一份保留状态，一份每次重置。任务有九类，从合成题、符号回归到表格上的自动机器学习。

五个前沿代理在保留状态时，沿预算走下来的最好结果都更高。按归一化的奖励点，这份时间进程上的增益大约是 Kimi K3 加 21.3、Sonnet 4.6 加 20.9，一直到 GPT-5.4 加 3.0。最后交出去的解是另一笔账。Sonnet 4.6 加 7.6，家族平均后的奖励从 70.3 到 77.9。Opus 5 和 GPT-5.6 Sol 的迁移增益是 −0.9 和 −0.8，重置时它们已经更强。不同任务家族里，增益的符号还会反过来。论文没有给出可打开的代码仓库。

留下上次的研究状态，五个代理都更快碰到更强的中间解。最后选中的解并不因此一致更好。

**链接：** [原文](https://arxiv.org/abs/2611.05108)

### 7. Adversarial Speculative Reasoning Improves Long Horizon Agents

推测解码一直被当成加速。小模型先写几个 token，大模型核对。核对如果是精确的，输出分布就应该和普通解码一样。他们在长程代理上测到的是另一件事：验证块内部的数值噪声并不均匀，越靠后越吵。走了几十步以后，这种噪声会把后面的推理带偏。

他们不改大模型的权重。草稿被训练成在轨迹里标出的决策点上故意写错，从而被拒绝，让大模型在验证块开头、噪声较低的位置写下这些 token。其他位置仍尽量被接受。DeepSWE 有 113 题，各跑五次。GLM-5.3 的通过率从 60.6% 到 67.6%，DeepSeek-V4.1-Flash 从 67.9% 到 71.9%。从需求文档建一个 Python 库的 NL2Repo 上，GLM 从 49.1% 到 55.0%，DeepSeek 只从 65.0% 到 66.4%。用同一批分叉、把偏好反过来训练，GLM 从 60.6% 降到 55.7%，DeepSeek 从 67.8% 降到 66.4%。跟决策无关的偏好，汇合通过率停在 67.5%，对照是 67.8%。论文把理想化的核对说成分布不变。测到的通过率仍然变了，他们把它归到 token 写在块内的哪个位置。没有给出代码仓库。

草稿站在决策的哪一边，长任务通过率就往哪边动。DeepSeek 在从零建库上只高 1.4 个百分点，不是每套题都拉开。

**链接：** [原文](https://arxiv.org/abs/2611.05345)

### Trending Open-source Projects

#### 1. KKKKhazix/agent-autoloop

命令行代理通常要人守着终端。人一离开，或者窗口关上，这轮就断了。Agent Autoloop 把调度放在本机：新事件进来，按规则交给一个已经装好的命令行代理，在指定目录里干一轮；这一轮结束进程就退出。只有代理在最后一条回复里提出要人拍板的问题时，才把卡片送到飞书、Slack 或桌面通知。

它不自带模型。任何能接收提示、并在最后一条回复里写明结果的命令行工具都可以接上。等人回答的时候不占进程，也不再花 token。事件来源、代理和通知都是插件，派工写成一份 JSON 规则。仓库 11 月 3 日创建，MIT 许可，本次检索 2,604 star、506 fork。星数是创建以来的存量，没有单独测过每日增量。README 写明 Windows 还不能用。这次没有实际跑通安装。

人离开终端以后，任务还可以接着排队，只有要拍板时才把人叫回来。它调度的是现成的命令行代理，不是另一个模型。

**链接：** [GitHub](https://github.com/KKKKhazix/agent-autoloop)

#### 2. emanuele-em/kanzo

人和编码代理如果各说各的，任务状态就留在对话里，下一轮对不上。Kanzo 把看板和 MCP 服务放进同一个程序：人在浏览器里移动卡片，代理用 MCP 领任务、写评论、改状态。标成 Human 的卡片，代理不去动。Backlog 一栏也先留给人，人把它拖进待办之后代理才接。

README 说这是一个大约 4.5 MB 的程序，不用账号，本机打开看板即可，也可以在局域网里把同一块板分享给几台机器。这些体积和用法是项目自己的说明，这次没有复跑二进制。仓库 10 月 25 日创建，AGPL-3.0，本次检索 1,012 star、65 fork。星数同样是创建以来的存量，没有独立的每日增长曲线。

人和代理要共享同一份任务状态时，看板比再开一个对话更不容易把活说丢。采用证据目前只有星数和仓库仍在更新。

**链接：** [GitHub](https://github.com/emanuele-em/kanzo)

#### 3. haydenschmitty/floorplan

代理把一个应用做出来以后，人常常答不上“点结账之后发生了什么”，也答不上改一处会碰到哪里。Floorplan 是 Claude Code 和 Codex 的插件：让代理读仓库，画出一张可以缩放的地图，零件、文件和请求都用白话命名，并标出它们之间的连接。

它不是另一套静态分析器。README 把它和画图工具、函数级知识图谱分开。多出来的两块是健康检查，以及代理刚刚改了哪些部分。健康检查在说明里包括写在代码里的密钥、敞开的数据库规则，和谁都能调用的接口。这些检查这次没有复跑，不能把 README 里的例子当成测量结果。仓库 10 月 27 日创建，MIT 许可，本次检索 2,862 star、211 fork。README 上的版本号是 0.6.3。星数是创建以来的存量。

它把“代理刚改了哪里”画成可以点开的地图。安全检查仍是插件说明里的功能，不是这次核实过的结果。

**链接：** [GitHub](https://github.com/haydenschmitty/floorplan)
