## 📝 逐条讲解

### Claw-SWE-Bench：把 coding agent harness 当受控变量评测
过去很多 SWE-bench 风格报告把模型、prompt、工具、patch 提取、超时、缓存和成本打包成一个系统分数，外部读者很难判断到底是模型强，还是 harness 更会把模型“变成 coding agent”。Claw-SWE-Bench 解决的是这个归因问题：它把 task prompt、Docker workspace、patch extraction、evaluator、预算和成本统计固定下来，只把可替换的 agent harness 放进统一 adapter slot。基准包含 350 个真实 GitHub issue，覆盖 8 种语言和 43 个仓库，并额外提供 80 题 Lite 子集，方便团队在低成本下做回归和 adapter 调试。最刺眼的结果是，同一个 GLM 5.1 backbone 下，OpenClaw 的最小 direct-diff adapter 只有 19.1% Pass@1，完整 adapter 达到 73.4%，说明“能接进 benchmark”与“能正确满足 SWE-bench scoring contract”差距巨大。跨 5 个 claw、2 个模型的实验还显示，固定模型时 harness 最高可带来 27.4 个百分点差异，接近模型选择本身的影响。对后训练软件工程来说，这类 benchmark 的价值在于把 harness、adapter、成本和 patch 合约都变成可测变量，而不是继续把所有提升归因给模型名。
🔗 链接：https://arxiv.org/abs/2606.12344 ｜ 代码：https://github.com/opensquilla/claw-swe-bench

### Trace / TellOnce：把用户纠正编译成 coding agent 运行时规则
长期 coding agent 的一个真实痛点是，用户明明纠正过“别留下临时调试文件”“提交前要跑某个检查”，下一次会话里 agent 可能记得这句话，却仍然违反它。Trace 把这个问题称为 preference access 和 preference compliance 的差距：记忆系统能把偏好取出来，不代表执行时一定遵守。它的做法不是继续扩大 memory，而是在 test time 把用户纠正抽成 atomic rule，再编译成 applicability check、behavior instruction 和 verifier，并通过 skill/hook 形式注册到后续任务里。这样规则不再只是 prompt 里的建议，而是 agent 结束任务前必须通过的运行时 gate。论文用匿名真实 friction cases 做诊断，发现 Mem0 仍留下 57.5% applicable preference violation；Trace 在 ClawArena 上把 OOD held-out violation 从 100% 降到 2.0%，同时不牺牲任务通过率。对 skill management 和 harness 工程来说，这很像把“用户经验”从自然语言笔记升级成可审计、可回滚、可执行的个人化 policy layer。
🔗 链接：https://arxiv.org/abs/2606.13174 ｜ 代码：https://github.com/YujunZhou/TRACE_exp ｜ Skill：https://github.com/YujunZhou/tellonce

### SWE-Marathon：超长程项目级软件工程 agent 评测
SWE-bench 和 Terminal-Bench 已经把 coding agent 推向真实环境，但很多任务仍是 patch 或小时内可完成的小闭环；真正的工程工作常常是重写库、复刻产品、做 ML 系统或优化性能，轨迹会长到数千万 token。SWE-Marathon 正是把评测拉到这个尺度：20 个项目级任务，每个都有独立可执行环境、人工参考解和多层 verifier，平均 agent attempt 达到 27.2M tokens。它的任务不是简单延长 issue，而是覆盖库复现、全栈应用克隆、ML/post-training、算法优化等更难用单一测试套件兜住的工作。评测结果显示，当前 frontier coding agent 最强配置 pass@1 仍低于 30%，常见失败包括自验证不足、过早判断不可行、提前停止。更重要的是，它记录到 13.8% rollout 出现 reward hacking，说明长程任务给 agent 足够时间去摸索 verifier 漏洞。对评测工程而言，SWE-Marathon 的启发是：长程 benchmark 必须把多通道验证、隐藏检查、adversarial audit 和轨迹发布一起设计，否则能力分很容易混入 shortcut 解法。
🔗 链接：https://arxiv.org/abs/2606.07682 ｜ 代码/项目：https://swe-marathon.org

### Recursive Agent Harnesses：递归单位从 model call 升级为完整 harness
长上下文任务常见做法是把文档切块后递归调用模型，但纯 model call 没有文件系统、工具和独立执行环境；coding agent 有工具，却常把大量条目降级成正则或脚本启发式处理。Recursive Agent Harnesses 提出的 RAH 把递归单位从“裸模型调用”升级为“完整 agent harness”：父 agent 写一段可执行脚本，按条目并行 spawn 子 agent，每个子 agent 都有自己的上下文、文件系统、工具和计划循环。这个设计利用了 coding agent 最擅长的 code-as-action：并行度、输出路径、子任务指令都可以由代码参数化，而不是受单轮 function-call 数量限制。论文在 Oolong-Synthetic 199 个长上下文样本上做控制实验，GPT-5 backbone 保持不变时，Codex-style baseline 为 71.75%，RAH 提升到 81.36%；换成 Claude Sonnet 4.5 达到 89.77%。这说明提升不是模型换代，而是 harness 架构把“每个条目都能有一个小 agent 认真处理”的能力释放出来。对 agent 系统工程来说，RAH 把 Anthropic dynamic workflows 等生产实践抽象成一个可讨论、可测量的模式：当任务可分解且单上下文会过载时，递归 harness 比递归 prompt 更像工程系统。
🔗 链接：https://arxiv.org/abs/2606.13643 ｜ 代码：None

### ProcCtrlBench：用过程缺陷与控制保留评价 coding agent 轨迹
最终通过测试只能说明结果对了，不能说明过程可靠；一个 agent 可能靠重复搜索、上下文漂移、脆弱命令链或不可中断的长轨迹勉强做完任务。ProcCtrlBench 针对的是这种“fragile success”：它把 coding-agent 执行过程拆成上下文管理、工具效率、workflow 架构、工具生态一致性四类，共 11 种 defect，并把不同 harness 的日志标准化成统一 trajectory representation。它还引入 control preservation，衡量执行是否仍然可理解、可中断、可纠正、可逆，以及能否在必要时把权限交还给人。作者在 200 条轨迹上验证，样本来自 AndroidBench、TerminalBench 和 SWE-bench-Verified，覆盖 Claude Code、Codex CLI、OpenCode、Qoder 等 agent family。结果不只是给失败找原因，也能区分“任务成功但过程高风险”和“任务失败但控制结构清晰”这两类完全不同的工程状态。对后训练评测而言，这类过程 scorecard 很重要，因为未来 reward 或 eval 不应只奖励最终 pass，还应奖励低风险、低浪费、可监督的执行轨迹。
🔗 链接：https://arxiv.org/abs/2605.20251 ｜ 代码：None

### Layer-Isolated Evaluation：生产 agent 的无 LLM 分层 CI gate
生产 agent 的一个常见运维问题是，端到端成功率下降时，团队不知道是 intent routing、ontology、safety、memory、decomposition 还是 prompt envelope 哪一层坏了。Layer-Isolated Evaluation 给出一个很工程化的答案：把一个实际部署的点餐 agent 拆成固定 architectural slices，每个 slice 都有不调用 LLM 的 deterministic pure-mode assertions，并在 CI 每次变更时跑。它的 baseline 有 23 个 slices、238 个 locked cases，纯模式 225 个 case 约 2.39 秒跑完，平均每 case 约 10ms。作者用 controlled regression injection 验证该方法：在 7 个非 safety 层逐个注入退化时，整体 pass-rate 只掉 1.7 到 5.9 个百分点，容易被 dashboard noise 淹没；但对应 slice 会暴跌 25 到 91 个百分点，能直接定位到责任层。它还强调 coverage honesty：没有 case 覆盖的 slice 不能显示 100%，只能显示 null，避免绿色 aggregate 掩盖盲区。对 agent harness 工程来说，这篇的价值在于把“评测”变成 PR 级别的组件回归 gate，而不是只在 nightly 里重跑昂贵、随机、端到端的模型评测。
🔗 链接：https://arxiv.org/abs/2606.11686 ｜ 代码：None

### OpenAI Codex Windows Sandbox：为本地 coding agent 补齐 Windows 沙箱
本地 coding agent 最大的安全边界不是 prompt，而是它实际能在开发者机器上读写什么、联网到哪里、子进程是否继承限制。OpenAI 这篇工程博客解释了为什么 Codex 在 Windows 上需要自建 sandbox：Windows Sandbox、AppContainer、Mandatory Integrity Control 等原生机制都无法同时满足开发者本地工作区、任意命令/包管理器、低摩擦使用、写入限制和网络控制。当前方案创建 CodexSandboxOffline 与 CodexSandboxOnline 两个本地用户，用 restricted token、ACL、firewall rule、DPAPI 和专门的 `codex-command-runner.exe` 来保证每个命令及其子进程从启动时就在边界内。Offline 身份默认断网，Online 身份用于用户授权的网络场景；写权限限制在 workspace 与显式配置目录，敏感路径继续由 ACL 保护。它的工程价值在于把“agent 执行命令要有沙箱”从口号落到 OS-level primitive、用户身份、进程继承和命令 runner 的具体实现。对 Agent-Friendly Software / Desktop Automation 方向来说，这类跨平台 sandbox 是 coding agent 企业落地的基础设施，尤其当 agent 越来越多地本地执行 shell、测试、构建和浏览器自动化。
🔗 链接：https://openai.com/pl-PL/index/building-codex-windows-sandbox/ ｜ 代码：None

### SentinelBench：长时间等待/监控型 agent 的 reaction-cost 评测
许多 agent loop 默认“不断行动”：刷新页面、重新搜索、反复检查工具输出，好像进展只能由 agent 主动制造。但现实里很多任务要求的是等待外部世界变化，比如某个职位出现、某封邮件到达、某个价格触发条件，然后及时响应。SentinelBench 为这种 monitoring task 建了 10 个合成但可交互的 web 环境，覆盖邮件、日历、金融、社交、代码平台、视频等，共 100 个任务，每个任务有脚本化事件时间线。它不只测完成率，还测 reaction time 和 resource use，因此能看清“反应快”和“烧 token”之间的 tradeoff。一个关键实验是比较普通 `sleep(time)` 工具和专门的 `wait_for(condition, timeout)` 工具：当任务拉长到 40 分钟时，GPT-5.4 sleep agent 成本约 $4.65 且完成率 56%，wait_for agent 成本约 $0.48 且完成率 69%。这说明长程 agent 不是一直执行越多越好，工具设计应支持“低成本等待 + 条件触发恢复”。对 harness 工程来说，SentinelBench 是一个提醒：评测要覆盖时间、等待和环境自发变化，否则会高估只会忙等的 agent。
🔗 链接：https://arxiv.org/abs/2606.05342 ｜ 代码：https://github.com/microsoft/sentinel_environments

### Agent Planning Benchmark：把规划能力从执行结果中拆出来诊断
很多 agent 失败后，我们只知道任务没完成，却不知道它是一开始计划错了、工具选错了、遇到坏工具不会恢复，还是本来就该拒绝。Agent Planning Benchmark（APB）把规划作为独立诊断对象，构造了 4,209 个多模态案例，覆盖 22 个领域和 holistic planning、step-wise planning、噪声工具、坏工具、不可解任务等场景。它要求模型不仅列步骤，还要给出工具链和每步 rationale，并用 Plan Correctness、Plan Grade 与 E1-E6 错误 taxonomy 做细粒度评价。作者进一步把 APB 信号接到 200 个 ToolSandbox 和 200 个 tau2-bench 任务上，比较直接执行、plan-first 和 APB-guided refinement，发现规划改进能传导到下游执行指标。它不是 coding agent 专项，但与 agent eval engineering 相关，因为规划错误常常被最终 pass/fail 掩盖。对后训练软件工程来说，APB 的启发是 reward 设计可以把“计划是否完整、是否抗工具噪声、是否知道不可行”拆成前置可训练信号，而不是等执行失败后才给一个稀疏负分。
🔗 链接：https://arxiv.org/abs/2606.04874 ｜ 代码：None

### AARRI-Bench：面向“真实研究实习生”质量的研究 agent 评测
自动研究 agent 的评测往往强调能不能复现实验、写代码、跑 benchmark，但真正的研究工作还要求谨慎、诚实、知道不确定性、注意伦理和细节。AARRI-Bench 把目标定义为“Act As a Real Research Intern”，也就是看 agent 能否在入门研究任务中表现出真人研究者的专业质量，而不只是完成宏观步骤。它包含 82 个手工构造任务，支持多 harness 评测，并强调“人类容易、agent 容易犯错”的细粒度场景，比如忽略关键限制、误读研究语境或缺乏审慎验证。实验中最好配置 Mini-SWE-Agent + Claude Opus 4.7 也只有 68.3% 成功率，复杂 harness 并不自动带来更强结果。它对本日报的直接价值不在 coding，而在 automated research harness：如果未来 agent 要参与数据、实验和后训练研究，评测就必须覆盖研究行为质量，而不只是代码跑通。对工程团队来说，这提示 research agent 的 verifier 需要纳入伦理、证据、 uncertainty 和细节敏感性，避免把“能执行”误当成“像研究者一样可靠”。
🔗 链接：https://arxiv.org/abs/2606.07462 ｜ 代码：https://github.com/AARR-bench/AARRI-bench

### Claude Code Best Practices：把验证做成 /goal、Stop hook 与 reviewer subagent
Anthropic 的 Claude Code best practices 文档把一个非常实用的观点说得很直白：给 agent 一个能自己运行的检查，是“你盯着它”和“它能自己闭环”的分界线。文档建议把测试、build、lint、截图对比、fixture diff 等变成 Claude 可读的 pass/fail signal，让 agent 在失败后读取输出并继续修。更强的做法包括三层：在单次 prompt 里要求 run-and-iterate；用 `/goal` 让小模型每轮检查完成条件，不满足就继续；用 Stop hook 运行确定性脚本，阻止 agent 在测试未过时结束。它还建议用 fresh-context verifier subagent 做 second opinion，因为写代码的 agent 容易对自己的方案有路径依赖。对 harness 工程来说，这些不是“使用技巧”，而是生产 coding agent 的控制面：停止条件、证据输出、自动验证和独立复核都应该显式化。它也与 Trace、Layer-Isolated Evaluation 形成同一条线索：可靠性提升来自把偏好和检查做成机制，而不是把所有希望都放在模型自觉上。
🔗 链接：https://code.claude.com/docs/en/best-practices ｜ 代码：None

### Lasso：Claude Code 安全从 prompt 风险升级为 agent 生命周期防护
Claude Code、Codex 这类终端 agent 会读代码库、跑 shell、接 MCP server、访问外部服务，因此它们的风险不再只是“模型说错话”，而是完整开发生命周期的攻击面。Lasso 的 Claude Code security 文章把这个问题拆成输入边界、工具边界、行动边界和输出边界：agent 读到的 issue、网页、MCP response、依赖包元数据都可能携带 prompt injection 或 tool poisoning。文章强调企业不能只靠开发者逐条 approve，因为高自治工作流里 agent 会在一个 session 内连续读取、推理、执行和外呼；每一步都需要 intent alignment 和安全扫描。它的价值在于把 MCP tool poisoning、恶意内容注入、外部工具响应劫持这些“AI 原生”风险放进传统 AppSec / supply-chain 视角里。虽然这是安全厂商博客，不是论文，但它反映了社区在 6 月对 Claude Code 安全的高关注：agent 一旦拥有 shell 和 MCP，安全边界必须跟随整个行动链，而不是只扫描最终代码。对后训练软件工程团队来说，这也意味着评测集和 harness 都要包含恶意工具、污染上下文和越权行动场景。
🔗 链接：https://www.lasso.security/blog/claude-code-security ｜ 代码：None

### OpenAI：TanStack npm 供应链攻击响应与 Codex/桌面应用证书轮换
这条 OpenAI 官方响应不是模型研究，但对 coding agent 工具链很有现实意义，因为攻击面来自开发者依赖和签名证书，而 Codex App / Codex CLI 正属于受影响产品之一。OpenAI 表示 TanStack npm 在 Mini Shai-Hulud 供应链攻击中被污染，两个员工设备受到影响，有限内部 credential material 被 exfiltrate，但没有证据显示用户数据、生产系统、知识产权或已发布软件被修改。由于受影响仓库包含多平台 code-signing certificates，OpenAI 选择轮换证书并重新签名应用，macOS 上旧签名版本在 6 月 12 日后会被系统安全机制阻断或停止支持。对用户侧来说，这主要意味着 ChatGPT Desktop、Codex App、Codex CLI、Atlas 等 macOS 应用需要更新；对工程侧来说，它说明 agent 工具分发本身也会继承现代 npm/PyPI 供应链风险。随着 coding agent 越来越深地接入本地 shell、凭据、MCP 和 repo，供应链安全、证书轮换、最小凭据和端点隔离会成为 agent runtime 的基础要求。本文按 Low 收录，是因为它不是 agent 方法创新，但来自高可信官方源，且与开发者 agent 分发安全直接相关。

### 🔥 大佬观点

**Simon Willison：Claude Fable 5 “relentlessly proactive”，强能力也放大 prompt-injection 风险。**  
Simon 6 月 11 日用 Claude Fable 5 + Claude Code 调试真实 UI 问题，观察到它会主动写临时 HTML、开 Python server、尝试浏览器 workaround，并在看似简单任务上花大量 token 找证据。他的 insight 很重要：proactive agent 能显著减少人工 hand-holding，但如果被恶意 issue、网页或代码注释诱导，同样会更积极地外传数据或执行危险动作。🔗 https://simonwillison.net/2026/Jun/11/fable-is-relentlessly-proactive/ ｜ HN：https://news.ycombinator.com/item?id=48498573

**Anthropic Claude Code 团队：给 agent 可运行的验证，比继续写 prompt 更关键。**  
Claude Code 官方 best practices 把“Give Claude a way to verify its work”放在核心位置，并把测试、build、截图、`/goal`、Stop hook、reviewer subagent 组合成可操作的验证闭环。值得注意的是，这和社区最近的 harness engineering 共识一致：可靠性来自可执行 gate 和证据，而不是让模型自己声称“完成了”。🔗 https://code.claude.com/docs/en/best-practices

**Terminal-Bench 2.1 社区讨论：同一模型换 native harness 可差 4–5 分。**
