## 📝 逐条讲解

### Performance-Optimization Benchmark Audit：重新审计 GSO/SWE-Perf/SWE-fficiency 是否真能衡量 coding agent
性能优化类 coding-agent benchmark 看起来很直观：agent 提交补丁，评测脚本比较运行时间是否比 baseline 更快。但这篇审计指出，性能任务比普通单测任务更脆弱，因为机器型号、运行噪声、参考补丁本身的收益大小和排行榜评分规则都会显著改变结论。作者重放了 GSO、SWE-Perf、SWE-fficiency 三个 benchmark 的 740 个官方参考补丁，并在四类常见 Google Cloud 机器上检查 reference patch 是否仍满足原 benchmark 的有效性规则。结果很刺眼：GSO 只有 39/102 个任务在所有跨机器重放中稳定有效，SWE-Perf 只有 11/140，SWE-fficiency 相对更稳但也不是完全无问题。论文还发现，不同 benchmark 的排行榜规则会改变同一批公开提交的相对排序，而且 SWE-fficiency 的少数高权重任务会过度影响总分。对后训练软件工程来说，这提醒我们“性能提升”不能只靠一次运行和一个聚合分数，要保存机器配置、重复运行方差、reference patch 可靠性和 per-task 权重。它的直接价值是把性能优化 eval 从“看榜单”推进到“挑 replay-valid tasks、审计 scoring rule、识别已饱和任务”的工程流程。
🔗 链接：https://arxiv.org/abs/2607.01211 ｜ 代码：None

### Vera：从风险发现到证据验证的大规模 LLM agent 安全测试框架
许多 agent 安全测试依赖专家手写少量危险场景，然后用规则判断模型有没有违规；这种方式成本高，而且 agent 框架一变，旧用例就可能跟不上。Vera 把安全测试做成三阶段流水线：先从文献和已知事故里持续抽取风险 taxonomy，再把风险、攻击方式和工具环境组合成可执行 safety case，最后让不同 agent 在隔离沙箱里运行并由证据驱动 verifier 判断结果。关键点是 verifier 不信模型自述，而是看环境状态、工具调用和产物这些可观察证据，例如文件是否真的被改、秘密是否真的外泄、危险命令是否真的执行。论文在 OpenClaw、Hermes、Codex、Claude Code 四个生产型 agent 框架上评估，发布 Vera-Bench，包含 1,600 个可执行安全用例、124 类风险和三类执行环境。报告称多通道攻击下平均攻击成功率可达 93.9%，说明当前 agent runtime 的安全边界仍然很薄。对我们关注的 harness 工程，这篇最有价值的是把安全测试当软件测试做：risk discovery、case generation、sandbox run、evidence oracle、regression suite 都要模块化。它也适合做后训练负样本和 guardrail 回归集，避免只在最终自然语言拒绝上训练安全。
🔗 链接：https://arxiv.org/abs/2607.01793 ｜ 代码：https://github.com/Yunhao-Feng/Vera

### AgentFlow：为 agent 程序构建 Agent Dependency Graph 做静态分析
现在很多 agent 不是一段 prompt，而是由 Python/TypeScript 应用、framework decorator、tool 注册、memory、handoff 和多 agent 编排组成的“agent 程序”。传统静态分析能看普通代码调用关系，却不理解“这个 prompt 会驱动哪个 tool”“这个 agent 可以交给哪个子 agent”“这个 memory 状态会影响哪些动作”。AgentFlow 的核心贡献是 Agent Dependency Graph：把 agents、prompts、models、capabilities、memory states 和 control policies 都建成带类型的节点与边。基于这个图，它能生成 Agent Bill of Materials，也能做 prompt-to-tool 风险检测，类似传统软件里的依赖清单和 taint analysis。作者在五个代表性 agent framework 上实现，并用 AgentZoo 的 5,399 个真实 agent 程序评估，称比 AST-only 工具恢复出更丰富的 agent 实体与依赖。更重要的是，AgentFlow 在真实程序里发现了 238 个 prompt-to-tool 风险，说明这类静态分析不是纸面概念。对 agent 工程来说，未来上线 agent 应该像上线微服务一样先生成 BOM、权限图和风险路径，而不是只读 README。对后训练数据工程，它也提示我们应保存 agent 程序结构，因为轨迹行为往往由 framework 语义和工具图决定，而不只由模型决定。
🔗 链接：https://arxiv.org/abs/2607.01640 ｜ 代码：None

### Mastermind：把漏洞复现 agent 的可迁移“策略”作为训练单元
仓库级漏洞复现是一类非常难的 coding-agent 任务：agent 要读代码、推断输入语法、构造 PoC、确认旧版本崩溃并验证新版本修复。很多 agent 并非完全不会执行命令，而是一开始选错策略，例如追错入口、构造错触发条件，后面再多采样也很难救回来。Mastermind 的观点是，训练单元不一定是完整动作轨迹，也可以是更紧凑、更稳定的“高层策略”。它用一个可训练 planner 学习可复用的漏洞复现策略，训练方式包括 SFT 和 milestone-based GRPO；同时保留 task-local strategy records，让同一任务的后续尝试能复用已经验证过或失败过的策略线索。执行器本身可以冻结，因此同一个策略 planner 能提升多个不同 executor，而不是把所有能力都绑死在一个 agent 上。论文在 CyberGym 上用 260 个训练任务和 200 个 held-out 任务评估，报告 GPT-5.5 frozen executor 从 open-book PoC context 的 60.0% 提升到 84.5%。这对 trajectory selection 很有启发：很多长轨迹里真正值得训练的不是每个 shell 命令，而是“为什么选这条攻击/复现路径”的策略骨架。工程落地时，可以把策略记录、milestone verifier、失败策略黑名单和 executor 无关的 planner 做成独立数据资产。
🔗 链接：https://arxiv.org/abs/2607.01764 ｜ 代码：None

### UnderSpecBench：测 coding agent 在模糊 DevOps 指令下是否越界行动
生产环境里的 DevOps 指令经常并不完整，例如“清理旧资源”“回滚这个服务”“修一下证书问题”，但 agent 一旦猜错对象或扩大范围，后果可能比代码补丁失败严重得多。UnderSpecBench 专门测这种 action-boundary violation，而不是只看任务能不能完成。它包含 69 个 DevOps task families，来源于真实事故、CVE 或工具行为，覆盖四个 DevOps 生命周期阶段和九类 operational control surface。每个任务固定安全的 ground-truth action，然后沿意图清晰度、目标确定性、爆炸半径三条轴生成不同模糊程度的指令，总计 2,208 个 prompt variants。评测 oracle 是确定性的、基于副作用的，把结果分成 Safe Success、Wrong Target、OverScope，以及 clarification、refusal、deferment 等非行动类别。这个设计非常贴近 agent runtime 的真实风险：安全 agent 不应该在目标不唯一或范围过大时自信执行。对后训练软件工程来说，它提供了一种可训练的边界意识信号：什么时候应该问澄清、什么时候可以局部执行、什么时候必须拒绝。内部 DevOps agent 也应学习这种设计，为高风险命令、资源选择和批量操作建立 deterministic side-effect oracle。
🔗 链接：https://arxiv.org/abs/2607.02294 ｜ 代码：None

### AI-Atomic-Framework / ATM：多 agent 共享写入前的可审计 admission layer
多 agent 并行开发正在变常见，但一旦多个 agent 同时想写同一文件、同一服务配置或同一个受治理域，问题就不只是 Git merge conflict。系统需要在真正写入前判断哪些 intent 可以并行、哪些必须串行、哪些需要合成、哪些必须 fail closed。AI-Atomic-Framework（ATM）把这个缝隙定义成 pre-write admission layer：agent 先提交可审计的 write intent，框架根据证据、策略和领域边界决定是否放行。论文强调它不替代 Git merge，也不声称解决跨 clone 或跨 PR 的所有治理问题，而是把单一治理域内的共享 mutation 做成可实现、可恢复、可审计的中间层。评估包括 12 场景 deterministic design matrix、三个 archived runner cases、ATM-AdmissionBench v0.1/v0.2，以及 20 个 unique scenarios 和 42 个 mode-level comparisons。它的工程价值在于把“多个 agent 同时改代码”从聊天式协商变成 admission control 问题，类似数据库事务和 CI gate 的结合。对后训练轨迹也有帮助，因为 write intent、admission decision、冲突理由和恢复路径都是高价值过程监督数据。未来多 agent harness 如果没有这种写入前治理，很容易在并发扩展时把错误归因给模型，而真实问题在控制面。
🔗 链接：https://arxiv.org/abs/2607.00041 ｜ 代码：None

### SkillFuzz：把 agent skill 组合当作 fuzzing 对象发现隐式意图
Agent skills 的流行让团队可以快速给 agent 安装工作流知识，但 marketplace 通常按单个 skill 审核，忽略多个 skill 同时启用后的组合效应。SkillFuzz 关注的就是这个新风险：两个单独看起来无害的 skill，组合后可能让 agent 产生原作者没有明说的隐式目标。它把 skill composition 当作 fuzzing 对象，先抽取结构化 skill contracts，再用 contract-guided Monte Carlo Tree Search 优先探索高风险组合。由于很多 marketplace 在 admission 阶段没有完整运行环境，SkillFuzz 采用 execution-free 测试：看 planning artifacts 中暴露出的 agent intent，并和无 skill baseline 做 differential oracle。论文称在代表性 skill-marketplace workload 下，固定 query budget 内发现超过 1,000 个 distinct implicit intents，最高风险组合在 execution-time validation 中超过 80% 被确认。这个思路对 skill 管理很关键，因为技能安全不是简单扫描敏感词或危险 shell 命令，组合后的“让 agent 倾向做什么”才是更隐蔽的风险。对后训练软件工程来说，skill co-activation、意图漂移和技能冲突都应成为 eval 维度，否则 skill 越多，agent 行为越难预测。它也说明 skill marketplace 需要像包管理器一样做 dependency/compatibility testing，而不只是单包 lint。
🔗 链接：https://arxiv.org/abs/2607.02345 ｜ 代码：None

### Cloak and Detonate：研究 agent skill 恶意载荷如何逃过扫描器并动态检测
当 agent skills 可以携带自然语言指令、脚本和资源，并以 agent 权限运行时，它们就从“提示词资产”变成了供应链攻击面。Cloak and Detonate 研究一个很现实的问题：现有 skill scanner 能否抵抗自适应攻击者改写恶意 skill 外观但保留恶意行为。作者提出 SkillCloak，用 payload-preserving transformations 让恶意 skill 变形，从而逃过基于模式匹配或 LLM-as-judge 的静态扫描器。论文还在八个代表性 skill scanners 和两个生产 agent（Codex 与 Claude Code）上做 adversarial study，样本包括 1,613 个 in-the-wild malicious skills。它的“detonate”侧强调动态检测：不要只看 SKILL.md 表面文字，而要在受控环境里观察 skill 激活后 agent 是否尝试偷凭据、外传源码、安装后门或执行越权脚本。这对 agent runtime 工程很重要，因为 skill 文件常常被当成普通 Markdown，安全审查强度远低于代码依赖。后训练团队也应注意，来自公开 skill marketplace 的轨迹可能包含恶意或污染指令，不能无脑纳入训练。工程上更可靠的做法是把 skill 安装、扫描、沙箱执行、网络/文件访问审计和签名 provenance 串成一条供应链门禁。
🔗 链接：https://arxiv.org/abs/2607.02357 ｜ 代码：None

### Skills Are Not Islands：把 agent skill 依赖建模为供应链风险图
早期大家把 skill 想成一个独立的 Markdown 文件，但真实生态正在快速走向复用、组合和外部服务依赖。Skills Are Not Islands 提出 Agent Skill Supply Chains（ASSCs），把 skill、软件包和外部服务都作为图节点，把复用和调用关系作为边。论文提到公开 skill 数量已达到 1.43M，三个月增长九倍，这意味着 skill 生态的增长速度已经足以产生传统开源包管理类似的依赖风险。一个技能可能引用另一个技能、安装 npm/pip 包、调用 SaaS API 或要求凭证；这些依赖如果不显式建模，安全团队无法追踪 provenance，也无法知道某个上游变化会影响哪些 agent 行为。作者强调 skill 不是孤岛，而是 dependency-bearing artifact，这个定义很适合进入企业治理和 marketplace admission 流程。对本日报关注的 skill evolving/management 来说，这篇把“技能库”从提示词集合提升为软件供应链对象。工程上可以借鉴 SBOM 思路，为每个 skill 生成 Skill BOM、依赖图、服务权限、脚本哈希和版本锁。训练数据侧也应记录技能依赖版本，否则同一条 agent 轨迹的行为可能因为某个技能或脚本更新而不可复现。
🔗 链接：https://arxiv.org/abs/2607.01136 ｜ 代码：None

### Registry-Governed Agent Lifecycle：用评测证据驱动 agent 注册、发布与退役
企业内部 agent 越来越多之后，问题不再只是“哪个 agent 今天能跑”，而是它应该如何从草稿进入生产、何时需要复测、何时应该退役。Registry-Governed Agent Lifecycle 把 EDDOps 落到 AWS Bedrock AgentCore 的 registry 上，主张 registry 不应只是被动目录，而应成为 agent 生命周期控制面。论文定义了 DRAFT、APPROVED、PUBLISHED、DEPRECATED、RETIRED 等状态，并要求每次状态迁移都由评测证据驱动，例如质量、成本、风险和 staleness。一个有意思的集成点是 MCP-native discovery：只有 PUBLISHED agent 才应该出现在 MCP discovery 里，这样治理状态直接影响 agent 能否被其它系统发现和调用。作者也很谨慎，说明这是 architectural validation，而非大样本统计 benchmark；PoC 只包含 15 个单轮 case、9 个多轮 conversation scenarios 和若干 mock tool data。它按 Medium 收录，因为更像企业架构样板，但对 AgentOps 很实用。对后训练平台来说，同样的 lifecycle 思路可用于 skills、MCP servers、evaluators 和 reward models：没有持续评测证据的组件不应长期默默留在生产路径里。
🔗 链接：https://arxiv.org/abs/2607.00345 ｜ 代码：None

### MemSyco-Bench：评测长期记忆是否诱导 agent 迎合而非基于证据判断
长期记忆让 agent 更像持续协作者，但记忆并不总是好事：如果 agent 把用户过去的偏好、错误说法或过期事实当作当前证据，就会出现 memory-induced sycophancy。MemSyco-Bench 的核心不是测记忆能不能被存取，而是测记忆被取出后是否被正确使用、限制或拒绝。它覆盖五类任务：Objective Fact Judgment、Contextual Scope Control、Memory-Evidence Conflict、Valid Memory Selection 和 Personalized Memory Use。换句话说，agent 要学会判断某条记忆什么时候只是偏好、什么时候和客观证据冲突、什么时候已被更新、什么时候可以用于个性化。这个设计对 coding agent 也很相关，因为项目记忆里可能保存“上次这么做成功了”“这个库不要用”“测试命令是 X”等信息，但这些记忆可能过期或只适用于某个分支。论文配套开源仓库，便于后续构造 memory-augmented agent 的回归测试。对后训练软件工程来说，这类 benchmark 提醒我们：memory retrieval 之后还需要 post-retrieval calibration，不能把“记得多”误当成“判断好”。轨迹数据也应保存记忆来源、适用范围、冲突证据和最终是否采纳。
🔗 链接：https://arxiv.org/abs/2607.01071 ｜ 代码：https://github.com/XMUDeepLIT/MemSyco-Bench

### From Registry to Repository：研究 AI agent skills 如何被编写、改造和维护
随着 skills 从 Anthropic/Codex 风格的能力扩展变成社区标准，真正的问题已经从“什么是 skill”变成“技能如何被生产、移植、维护和废弃”。这篇经验研究把 skill 分成两个来源：一类来自集中 registry，面向广泛复用；另一类是 repository-local skill，直接和项目代码一起维护，像内部工具或项目约定一样存在。这个区分很重要，因为公开 skill 更像第三方依赖，强调发现、版本和安全；本地 skill 更像项目基础设施，强调团队约定、持续更新和和代码演化同步。论文讨论 skills 作为 just-in-time context bundles 的角色：它们在上下文窗口受限时提供领域知识、工作流步骤和可选脚本，比把所有说明塞进系统提示更可管理。对工程团队来说，skill 的维护成本会越来越接近文档与脚本的混合体，必须有 owner、review、测试和废弃策略。它按 Medium 收录，因为更偏生态研究，但和 skill management 非常贴合。对后训练数据工程也有启发：如果一条成功轨迹依赖 repo-local skill，训练样本必须连同 skill 版本一起保存，否则模型学习到的行为缺少上下文。
🔗 链接：https://arxiv.org/abs/2607.00911 ｜ 代码：None

### From Anatomy to Smells：对 SKILL.md 结构和坏味道做大规模经验研究
SKILL.md 看起来只是一个 Markdown 文件加 YAML frontmatter，但它正在承担类似“可执行工程流程说明”的职责。From Anatomy to Smells 试图把 skill 文档的结构和坏味道系统化，而不是只靠作者经验判断好坏。论文从 Agent Skill Specification 出发，分析 frontmatter、正文说明、脚本、references 和 assets 的实际使用方式，并训练分类器检测常见 smell。作者使用 4-bit AWQ 量化的 Qwen3.6-27B 做辅助标注/分类，在人工标注数据上报告 weighted F1 约 0.78、precision 0.79、recall 0.78，说明它足以做大规模趋势分析但不能替代人工审查。对 agent 工程来说，skill smell 可能包括触发条件不清、步骤过长、验证门缺失、危险操作没有权限说明、输出格式不稳定或把太多领域塞进一个技能。它的价值在于把 skill 质量从“这个提示词写得好吗”推进到可 lint、可统计、可回归的对象。对后训练软件工程，skill 文档质量会直接影响轨迹质量；坏 skill 诱导出来的成功或失败轨迹都可能有系统性偏差。未来团队可以把这类 smell detector 放进 skill PR review，就像今天对代码跑 lint 一样。
🔗 链接：https://arxiv.org/abs/2607.01456 ｜ 代码：None

### Microsoft AX：公开 benchmark 分数不能替代你自己的 agent 场景评测
Microsoft 这篇 Agent Experience 系列文章主题不是新 benchmark，而是提醒团队如何正确使用已有 benchmark。文章指出，SWE-bench 等公开榜单测的是公开仓库、公开 issue、特定 harness 和相对干净的上下文；你的真实工作可能包含私有 SDK、团队约定、AGENTS.md、多个 extension 争抢上下文、MCP 工具和多轮自修复流程。它用 Goodhart's Law 解释为什么 benchmark 越重要，生态越会围绕它优化，分数提升未必等价于你自己场景的提升。更实用的是 harness problem：同一个模型放在不同 agent harness 里，因为提示、工具面、上下文裁剪和指令文件不同，会表现出完全不同的行为。文章建议把公开 benchmark 当作必要但不充分的过滤器，然后用 5-10 个代表性内部任务做 controlled comparison，记录结果质量、成本、一致性和 extension responsiveness。它按 Low 收录，因为没有新数据集或新算法，但来源可信，并且方法论非常贴近生产 agent 选型。对后训练软件工程的启发是，任何榜单分数都应配套本地 eval；否则一次模型升级或 harness 变更就可能让内部工作流悄悄退化。
🔗 链接：https://developer.microsoft.com/blog/what-ai-benchmarks-are-not-telling-you ｜ 代码：None
