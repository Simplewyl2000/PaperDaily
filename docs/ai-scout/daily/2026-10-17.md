## 逐条讲解

### SWE-at-Scale：Scalable Issue Synthesis from Historical Bug Fixes
训练和评测 coding agent 都需要大量"可执行、可验证"的 SWE 任务，但真实 issue 的产出速度受限于开发者报 bug 的自然频率，人工整理成本又很高。已有的合成方法大多是让大模型凭预训练知识"编一个 bug"再加启发式提示词，造出来的 bug 往往很假，和真实软件里 bug 产生的机制对不上。SWE-at-Scale 的关键想法是把历史修复"倒着放"：一个真实的 fix 记录了 bug 是怎么来的，把修复监督反转过来就变成了"如何在这类代码里引入这类 bug"的监督。它先从历史修复中学到 bug 模式，再把这些模式迁移到新的代码上下文里反复采样不同 bug 类型，最后构造成带测试的可执行任务。实验显示它造出的任务比现有合成基线更多样、更真实，也更能难住最强的 coding agent；同一个文件即使生成 200 次，bug 多样性也还在稳定增长。对后训练数据工程来说，这提供了一条"把有限的真实修复变成可无限复用的造题素材"的路线，代码和数据都已在 GitHub 与 Hugging Face 公开。
🔗 链接：https://arxiv.org/abs/2610.21359 ｜ 代码：https://github.com/cslsolow/SWE-at-scale

### WEAVE：Weaving Real-World Code Evolution into Dependency-Structured Tasks
真实软件开发很少是单个孤立改动，一个功能、一次迁移、一组系统性修复往往要跨好几个 PR 才能完成，但主流仓库级基准仍把"一个 issue / 一个 PR"当作任务单位。少数多 PR 设置只是把几个 PR 粗暴拼在一起，评分也不看它们之间的依赖关系，于是既测不准长程 agent 的进度，也给不出好的训练信号。WEAVE 从已验证的 PR 历史出发，用按仓库校准的"类型化变更位点"把相关 PR 组织成有界的依赖 DAG（有向无环图，即谁依赖谁的先后关系），再把每个 DAG 实例化成一个统一的可执行任务。它还提出了 Graph Credit：一个完全由测试决定、确定性的指标，只有当前置依赖满足时才给后续节点记分，从而衡量"符合依赖顺序的部分进度"。作者在任务构造、agent 评测、SFT 和 RL 上都做了实验，结论是 WEAVE 的任务更连贯，打分比平铺式计分更忠实，并且能直接充当 RL 的稠密可验证奖励。对我们来说，"多 PR 任务 + 依赖感知的部分分"正好补上了长程 SWE RL 奖励稀疏的问题。
🔗 链接：https://arxiv.org/abs/2610.22039 ｜ 代码：None

### NVIDIA：Priming Base Models for Agentic Post-Training: An Open Midtraining Recipe
前沿模型普遍在预训练和后训练之间加了一个 midtraining（中期训练）阶段，但几乎没人公开它具体怎么做。问题在于：预训练通常在短上下文上进行、几乎看不到 agent 交互；SFT 数据又大多是合成的，而且 SFT 拉得太长反而会损害模型后续的 RL 可训练性。NVIDIA 这份配方把 midtraining 放在两者之间：以 256K 上下文训练数千亿 token，数据主体是"天然的软件工程数据"——打包后的整个仓库、PR、commit 历史、构建日志，再掺入一小部分 agent 轨迹。效果很直接：Nemotron 3.5 Lightning 用 500B token midtraining 后，在完全相同的 SFT 之后 SWE-bench Verified 从 60.7 升到 64.5、Multilingual 从 55.8 到 62.8、Pro 从 32.0 到 35.5；更大的 Super 用 280B token 把 DeepSWE 从 11.7 提到 15.7，并且在不同 agent harness 下都更稳。特别值得借鉴的是他们的评测方法：发现 base 模型的代理指标和后训练结果相关性不可靠，于是用"固定的短 SFT 跑一遍"作为 midtraining 消融的评测协议。这是少有的、把"SWE 数据怎么喂进 midtraining"讲清楚并附完整消融的公开资料。
🔗 链接：https://arxiv.org/abs/2610.22019 ｜ 代码：None

### Anthropic：How the Claude Code team does code review
当 agent 写代码后，改动量会暴涨：Anthropic monorepo 每天落地的变更从 5 月约 2,500 个涨到 9 月 3 万多个，逐行人工审查已经不现实。Claude Code 团队（约 90% 代码由 Claude 写）把目标重新定义为"在回滚率和事故率不上升的前提下，最少化每个改动消耗的人类时间"，并用每 PR 人工审批数、人工评论数、等待人的时长来度量。具体做法是分层：提 PR 前 Claude 先跑测试/构建并让一个新上下文的子 agent 审 diff；每个 PR 由多个 agent 并行找 bug、再由另一组 agent 投票确认才发评论；安全审查单独一轮且未关闭的发现会阻塞合并；一个分类器按风险把改动分成"无需人/一人/两人"审批；最后是合并队列、功能开关、灰度发布和快速回滚。最有工程价值的是两点：一是"每次事故都变成一条 eval"——把引发事故的历史 PR 经熟悉代码的工程师确认后组成评测集，审查器的提示词、工具或模型每改一次都每天全量回归，分数涨才保留；二是"审查必须收敛"——他们发现 agent 作者和 agent 审查者会互相无限折腾（有个 PR 一夜跑了 50+ 轮），而后续轮次报的问题约 59% 其实是首轮就存在的老代码，于是加了三轮上限、只审 diff、按 bug 类别报告和不重复报告，均值审查轮数从 2.08 降到 1.32、一轮通过率从 65% 升到 78%。6 月到 9 月合并 PR 翻倍，回滚占比反而降了 40% 以上，这为"agent 时代的代码审查评测怎么建"提供了一个可直接照抄的模板。
🔗 链接：https://claude.dev/blog/solving-code-review-at-anthropic/ ｜ 代码：None

### FDE-Gym：The Last Mile of AI Delivery
现有 agent 基准大多给的是"规格清晰"的任务：issue、规格说明或工单写得明明白白。但真实的客户交付不是这样，驻场工程师（forward-deployed engineer, FDE）要先澄清含糊的需求、在线上系统里动手，还要挖出客户没说出口的约束。FDE-Gym 收集了 20 个客户场景、18 个行业共 95 个端到端交付任务，每个都由行业专家从真实交付项目改编；环境里有脚本化的"干系人"可以对话，也有可修改的类生产客户系统。打分方式很务实：看交付让客户自己的业务成功指标提升了多少，在"系统不变=0、参考方案=1"之间归一化，并对发消息、试跑、等待等交互成本扣分。在需要自己发现隐含约束的现实设置下，13 个模型配置里最好的平均分只有 0.56，95 题只解决了 14 题；即便在 23 个已经从干系人那里拿到全部关键事实的任务上，也只有 10 个达到 0.8 以上。它把评测从"写对代码"推进到"交付对业务有用"，对构造面向企业场景的 agent 评测和训练环境很有参考价值，代码、数据和在线练习平台都已开放。
🔗 链接：https://arxiv.org/abs/2610.22350 ｜ 代码：https://github.com/deeplethe/fde-gym

### HPCAgent-Bench：Sound Benchmarking of Code-Optimizing Agents, Harnesses, and Skills
用 coding agent 做代码性能优化越来越常见，但已有基准往往把加速器、编程模型或 harness 固定死，于是没法单独回答"加一个工具/一个 skill 到底值不值"。HPCAgent-Bench 包含 689 个 kernel，分为循环级优化题、从 HPC 代码中抽出的 kernel、以及机器学习模型三条赛道；每个 kernel 只用 NumPy 写一次规格，自动派生 C 和 Fortran 参考实现，提交可以走统一的 C ABI 或 Python 接口，跑在 CPU/GPU、单机或多节点上。为了防止 agent 钻测试系统的空子，正确性由外部 judge 在隐藏的模糊（fuzz）输入上检查并独立计时。它提出两个指标：用配对实验衡量某项干预对加速比、成功率和成本影响的"干预效能"，以及明确写出权重的"加权 token 成本"（区分输入、缓存输入和输出 token）。结果很有启发：agent 最高比自动并行化工具快 4.2 倍，且优化结果换机器后 93%~99% 仍正确；但在 40 组配对设置里，干预只有 2 次显著改变了加速比，却能让 token 成本相差最多 3 倍。这说明评测 harness/skill 时必须把成本报告标准化，否则很多"改进"其实只是更贵。
🔗 链接：https://arxiv.org/abs/2610.20673 ｜ 代码：None

### Skip the Compressor：Coding Agents Fix More Issues When They Pick Whole Files
仓库往往远大于模型上下文窗口，常见对策是用检索器挑代码片段，或用提示词压缩器删 token 来塞进预算。但修 issue 需要两样东西同时具备：真正要改的那些文件，以及它们"原封不动"的内容——因为模型要原样复述它编辑的行，补丁才能打得上去。检索器按与 issue 的相似度排序，不一定选中要改的文件；压缩器保留了文件却改写了文本。作者提出一个很简单的选择器 CQ2-CARE：把 token 预算全部用来决定"展示哪些整文件"，并逐字展示。在 300 个较新的 SWE-rebench issue 上、相同的每题预算下，它让 GPT-5.6 和 Claude Opus 5 分别解决 43.7% 和 46.7%，比三种压缩器中最好的高 6.3 个点，比三种检索器中最好的高 9.3 和 12.7 个点，甚至超过专门为 issue 解决训练的 SweRank 和 SWE-Pruner。对 harness 工程的启示是：上下文构造里"精确性"比"信息密度"更重要，选对文件并保持原文，往往比花哨的压缩更有效。
🔗 链接：https://arxiv.org/abs/2610.21073 ｜ 代码：None

### ToolBottleneckBench：Measuring Tool-Agent Performance under Controlled Pressures and Fixed Harness Budgets
一个工具 agent 的成功率，其实同时反映了模型能力和运行它的 harness 的各种预算（输出上限、轮数上限等），但大多数报告只给一个总分，分不清是谁的锅。ToolBottleneckBench 用固定不变的合成企业任务，每次只改变一种"压力"：注册的工具目录大小、模型可见的工具菜单、认证过的工作流、或工具返回记录的编码方式。它的精确评分器会记录每个失败 episode 中第一个没满足的义务，以及（如果有的话）是哪个 harness 限制终止了它。在 21 种模型和 harness 配置上，只有"可见菜单"这一种压力对模型有大幅惩罚，而这个惩罚和输出被截断高度相关——把输出上限提高 16 倍就基本消失了。大多数失败其实是撞上了 harness 限制，而且有效的修复都是"改变哪些工具送到模型面前、由谁发起调用"，而不是改善模型行为本身。作者建议以后报告压力效应时必须连同 harness 预算一起报告，这对我们做 agent 评测时"如何归因失败"非常实用。
🔗 链接：https://arxiv.org/abs/2610.21098 ｜ 代码：https://github.com/zichuanxu/tool-bottleneck-bench

### Data World：Scaling Data Environments from Scratch
数据分析 agent 要写代码处理各种异构文件并得出洞察，但训练它很难：真实环境收集成本高，还受隐私和知识产权限制，开放式的"发现"也没有标准答案可以验证。Data World 的核心想法是"先规定文件背后的世界，再生成文件"：多 agent 引擎先用显式机制定义一个世界（比如某个业务里哪些因素以什么方式影响结果），再据此生成数据文件、任务和评分 rubric，因此每个洞察都有已知的"生成真相"。系统还会独立审计"目标是否能从观察到的文件里恢复出来"，rubric 既用于评测也用作 RL 奖励。他们用人类偏好筛出 50 个 held-out 世界、16 个领域的 100 道题作为 DataWorld-Bench，另从 1,037 个互不重叠的世界里得到 2,135 个训练任务。在这些任务上做 RL-zero（不蒸馏轨迹）训练 Qwen3.6-35B-A3B，得到的模型在自家基准 +7.06、DAComp +14.28、DABstep-Hard +20.90。这种"机制先行"的环境合成思路可以直接迁移到其他需要可验证奖励但缺乏标准答案的 agent 场景。
🔗 链接：https://arxiv.org/abs/2610.21656 ｜ 代码：https://github.com/Zhanli-Li/Data-World

### DesignReviewBench / DesignLore：Benchmarking and Enhancing Design-Aware Code Review in the Linux Kernel
在成熟的大型项目里，代码审查远不止"有没有 bug"：审查者要看出一个改动引入了什么设计权衡、和其他方案比怎么样、是否符合项目特有的约束。现有自动审查几乎都聚焦缺陷和正确性，而历史审查讨论中沉淀的大量设计知识很难被复用。这篇工作从 Linux 内核真实的补丁审查历史中构建了 DesignReviewBench，专门评测"设计感知审查"。同时提出 DesignLore：从历史审查讨论中抽取设计决策，组织成可自适应扩展的设计分类体系，审查新补丁时检索相关的历史知识来引导 agent。结果显示这类审查对当前 coding agent 仍然很难，最强基线识别设计权衡的 F1 只有 0.213，DesignLore 提到 0.259（相对 +21.6%），并且在不同 agent 系统和底座模型上都有增益。它和今天 Anthropic 的审查文正好互补：后者解决的是"量"，这篇指出"设计层面的判断"仍是 AI 审查的明显短板。
🔗 链接：https://arxiv.org/abs/2610.21925 ｜ 代码：None

### AutoSFT：An Agentic System for Automated Data Research in Supervised Fine-Tuning
越来越多工作让 LLM agent 自动化后训练，但作者观察到：给 agent 完整训练栈时，它们最终都收敛到 SFT，并把大部分精力花在改训练数据上。可现有系统只给 agent 一种控制手段——要么从固定数据池里挑行，要么调用生成器——而人类数据工程师会同时调配比、剪枝、修复、替换和合成。AutoSFT 先定义了一个覆盖这些操作的"数据动作空间"，发现单个 agent 跑这个循环时只会用"调类别配比"一种动作，而且上下文被执行输出塞满、搜索到一半就丢了。于是改成多 agent：meta agent 把执行和分析分开，从多个独立角度收集改进建议，遇到数据池覆盖不到的能力时调用合成子 agent。逐个加组件都有增益：执行器把上下文丢失减半，分析子 agent 让最佳 IFEval +6.5，合成再 +3.4 IFEval、+2.9 IFBench；迁移到代码任务上，分析模块让 MBPP+ +3.7，而单 agent 版本完全没提升。所有结果都是每轮从 base 模型重训，所以各组件的贡献可以单独归因，结论是"自动化 SFT 数据研究靠的是覆盖多样的数据动作，而不是把一种动作做得更强"。
🔗 链接：https://arxiv.org/abs/2610.22194 ｜ 代码：None

### Athanor：An Agent-Native System for Autonomous Post-Training Research
"AI 自己训练更强的 AI"通常停留在设想层面，这篇用一个今天就能测量的弱化版本来检验：让前沿 agent 只用公开数据，把一个原始 base 小模型后训练好。Athanor 是一个 agent 原生的系统，在真实 GPU 上运行，agent 拥有完全的研究自主权：自己读数据集和评测结果、构造训练数据、写和改训练算法、调超参、分析结果决定下一步；它们在沙箱里工作，不能调用外部教师模型。系统负责的是"工程托底"：冻结的评测服务、托管的训练作业、去污染的数据、持久的研究记录，以及一个 agent 不知道的 held-out 测试集。在 104 小时的实验中，4 个 Claude Opus 5.5 agent 各占一台 8 卡节点、没有任何研究建议，把 Qwen3-4B-Base 在开发集上从 15.9 提到 67.3、在 held-out 集上从 9.2 提到 48.2，略超官方 Qwen3-4B-Instruct-2507（66.5 / 47.9）。研究记录显示 agent 并没有发明全新方法，而是重组已知手段：公开推理数据 SFT、一个 agent 改了 rollout 的 RL、跨 agent 权重合并、多轮自蒸馏。对后训练工程团队来说，它说明"把执行层做好（评测冻结、作业托管、去污染、隐藏测试）"是让 agent 自主做实验的前提。
🔗 链接：https://arxiv.org/abs/2610.21055 ｜ 代码：None

### What Should We Remove? Evaluating the Reliability and Costs of RLVR Data Decontamination
RLVR（基于可验证奖励的强化学习）用的数学语料通常会先和评测基准做重叠筛查，但"按什么规则删"这件事的可靠性和误删代价很少被认真评估。作者审计了 16 个开源 RLVR 数学语料共 167 万条训练题，对照 6 个基准的 1,949 道题，比较了基于精确匹配、词汇匹配和语义匹配的 8 种清洗策略，并用 594 对独立双盲人工复核的"训练题-基准题"对来校准。结论很扎心：常用的余弦相似度 0.80 阈值下，抽样的 59 次删除里有 52 次（88%）是误删；在预注册的 0.80~0.98 阈值网格里，没有任何一个语义阈值能达到 90% 的保守精度目标。相比之下，"先召回候选、再由 judge 裁决"的现有策略在 held-out 语料上做到 98.1% 精度和 98.2% 召回。作者公开了人工标签、每种策略的决策和覆盖统计，呼吁报告去污染时同时报告可靠性和删掉了多少数据，而不只是"重叠数"。这对任何做 RL 数据清洗流水线的团队都是一份可直接复用的校准资产。
🔗 链接：https://arxiv.org/abs/2610.21229 ｜ 代码：https://github.com/ethxin0011/rlvr_data_contamination

### Same Answer, New Box：How Much of RLVR's Out-of-Domain Gain Is Answer Format?
很多 RLVR 工作声称数学训练能带来域外收益，比如 MMLU 也涨了；但这些准确率是靠"答案抽取器"从模型输出里读出来的。如果模型只是学会了把答案写在抽取器优先看的位置（比如 `\boxed{}` 里），分数就会上涨，答案本身却没变好。作者用从公开代码里复制来的抽取器、以及一个自己写的"不管答案在框里还是正文里都能读出来"的抽取器，对 base 模型和 RL 模型的同一批输出各打一次分。在 4 组公开的 7B SimpleRL base-RL 对上，82% 的域外选择题增益在新抽取器下消失了——base 模型其实早就在正文里给出了大部分答案，RL 只是把它们挪进了框里；换成独立的 LLM 阅读者，这个比例也有 77%。不过在另一套配方训练的 32B 对上，几乎没有格式增益。对评测工程的启示是：报告的增益部分是"抽取器的属性"，用第二个抽取器重打一遍存档输出就能审计，不需要重跑 RL。
🔗 链接：https://arxiv.org/abs/2610.20639 ｜ 代码：None

### OPRD：On-Policy Reminder Distillation for Long-Horizon Coding Agents
仓库级 coding agent 不仅要写对代码，还要在长交互中一直守住约束、及时响应工具反馈；作者的诊断发现，agent 经常"信息就在上下文里却没用上"，而最终的 Pass/Fail 只能提供很稀疏的过程监督。OPRD 的思路是给教师模型额外的"提醒"（Reminder）：全局提醒把最终测试的诊断转成整条轨迹的指导，回合级提醒只作用于某次环境观察之后的下一步决策。训练时，学生在没有提醒的情况下自己 rollout：成功的轨迹直接做自模仿，失败的轨迹则由带提醒的教师在同一前缀上重新评估，用反向 KL 来纠正学生。推理时学生不需要任何提醒。在 SWE-bench Verified、Pro 和 Multilingual 上，OPRD 让开源 Qwen3.5-4B 的平均解决率提高 11.3 个点，按同一诊断协议统计的错误事件从 446 次降到 222 次（减少 50.2%）。这是把"特权信息教师 + on-policy 蒸馏"用到长程 SWE agent 上的一个工程上较轻量的方案。
🔗 链接：https://arxiv.org/abs/2610.21496 ｜ 代码：None

### Microsoft AI：MAI-Base-2 预训练基座
Microsoft AI 此前主要依赖 OpenAI 的模型，自研基座的实力一直是外界关注点。10-15 它发布技术长文介绍 MAI-Base-2：2.8T 总参数、80B 激活的原生多模态 MoE，在 16k 块 GB200 上用 38 天训练了 50T token，强调全部是"有机数据、没有从其他模型蒸馏"，爬虫遵守 robots.txt。文中披露了不少工程细节：用"数据源缩放"的缩放阶梯和拟合的超参缩放律、固定显存的无丢弃 MoE（MoE 层 MFU 从 24% 提到 35%）、带重分片的 Muon 优化器、激活梯度裁剪，整体平均 MFU 21%、goodput 89%。微软自报在 held-out 文本、内部代码等集合上超过所有测试过的开放权重模型，预训练算力效率是 DeepSeek-V4-Pro-Base 的 4.2~12.3 倍；但这些都是 bits-per-byte 类的预训练指标，模型仍在后训练中、尚未发布。对我们而言，它主要提供了一份大规模预训练基础设施（MFU/goodput、MoE 显存管理）的公开参考数据点。
