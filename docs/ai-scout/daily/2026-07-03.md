## 📝 逐条讲解

### Claude Sonnet 5：把近 Opus 级 agentic coding 下放到 Sonnet 成本层
过去几个月，复杂 coding agent 任务常常默认要用 Opus 级模型，因为长程规划、终端操作、调试和持续验证对模型稳定性要求很高。Anthropic 6 月 30 日发布的 Claude Sonnet 5 试图把这部分能力下放到更便宜、更高吞吐的 Sonnet 层：它能做计划、调用浏览器和终端工具，并在 Claude Code 与 Claude Platform 中直接可用。官方强调 Sonnet 5 在 agentic search、OSWorld-Verified、coding、tool use 和 knowledge work 上比 Sonnet 4.6 明显增强，并提供不同 effort level 让用户在成本和能力之间选择。早期用户反馈里最有工程价值的是“会自己写复现测试、修复、再 stash 回滚确认 bug 复现”这类闭环行为，这正是生产 coding agent 最需要的验证纪律。安全侧，Sonnet 5 默认启用 cyber safeguards，但 Anthropic 明确说其危险 cyber 能力低于 Opus/Mythos 级模型，这使它更像一个大规模 agent 执行层而不是最高风险研究模型。对后训练软件工程的启发是，未来 eval 和训练记录不能只写模型名，还要记录 effort level、工具面、guardrail、tokenizer/价格变化和运行时是否属于 Claude Code。Sonnet 5 的价值不只是“更强模型”，而是让更大规模的长程 agent 工作可以落在成本可控的一层。
🔗 链接：https://www.anthropic.com/news/claude-sonnet-5 ｜ 代码：None

### SWE-INTERACT：把 SWE benchmark 改成多轮用户驱动开发会话
传统 SWE-bench 类评测通常把需求一次性说清楚，agent 只要在固定仓库里自主修补并通过测试；但真实开发里，用户经常一开始只给模糊需求，随后才补充约束、看中间结果、改变想法。SWE-INTERACT 把这个现实放进 benchmark：由用户模拟器从不完整请求开始，逐步查看 agent workspace，给反馈、修订和新约束，直到完整目标被交接。论文报告一个很关键的落差：最强模型在对应单轮任务上大约能解 50%，但到了 SWE-Interact 多轮形态只有约 25%。这说明 agent 的短板不只是写代码，而是发现用户真实意图、保留已出现的需求、在迭代中不重写坏已有工作。数据侧还提供 Hugging Face dataset，包含真实 GitHub issue/PR 衍生的 repo、base commit、patch、test patch、test commands 和 Docker image 等字段，方便复现实验。对后训练工程来说，这类数据非常适合训练“需求澄清轨迹”和“用户反馈整合轨迹”，而不是只训练静态 issue 到 patch 的映射。它也提醒 eval harness 要把用户模拟器本身版本化，否则不同 user policy 会显著改变 agent 表现。
🔗 链接：https://arxiv.org/abs/2606.30573v1 ｜ 代码：https://huggingface.co/datasets/sweinteract/sweinteract

### SWE-MeM：让 coding agent 学会主动决定何时、压缩什么、如何压缩记忆
长程 coding agent 的上下文里会很快堆满日志、文件片段、失败尝试和中间推理；简单等到快爆窗再整段总结，常常既丢关键信息又增加交互步数。SWE-MeM 把“记忆管理”从固定规则改成模型可学习的工具使用能力：agent 可以自己判断何时调用 memory tool、选择压缩哪段历史、写出保留任务连续性的摘要。训练上，它先合成带主动 memory-tool 调用的轨迹，再用 Memory-aware GRPO 做轨迹切分和步骤级信用分配，让模型同时优化任务完成和上下文治理。论文在 SWE-Bench Verified 上报告 4B 模型达到 43.4%、30B 模型达到 60.2% resolve rate，并在 32K 上下文预算下比现有 memory baseline 更高效。工程上最重要的不是某个 RL 细节，而是它把 memory decision 变成可观测、可训练、可打分的动作。未来采集 coding-agent 轨迹时，应保存压缩触发原因、被压缩区间、摘要内容、剩余工作描述和后续是否因此成功。对 trajectory selection 来说，好的记忆动作本身可能是高价值训练样本，坏的压缩则应像坏工具调用一样被标注和过滤。
🔗 链接：https://arxiv.org/abs/2606.28434 ｜ 代码：None

### AI-Infra-Guard：覆盖 AI infra、MCP、agent skills、jailbreak 的分层红队平台
AI agent 的攻击面已经不只是模型提示词：Ollama、vLLM、ComfyUI、Dify、LangFlow、MCP server、agent skill 包、浏览器工具和模型本身都可能成为入口。腾讯朱雀实验室的 AI-Infra-Guard 把这件事做成分层红队平台，而不是只发布一组 jailbreak prompt。它把攻击面分成 infrastructure、protocol/tool、agent behavior、model 四层，并为每一层选择不同检测范式：确定性规则、LLM-driven agentic audit、多轮黑盒红队或 jailbreak operator。报告里提到覆盖 75+ AI components、1,400+ vulnerability rules，能够扫描 MCP servers 和 agent-skill packages，也包含 26+ attack operators 与 16 个 jailbreak 数据集。对本日报关注的 Agent-Friendly Software 很重要的一点是，它把 skills 也当作供应链资产来审计，检查 skill poisoning、过度权限和嵌入式 prompt injection。工程启发是，agent 安全平台不应只看“模型是否会拒绝”，还要扫描工具包、技能包、基础设施、运行时权限和多轮行为。它的开源形态也让团队可以把 AI infra security 接入 DevSecOps，而不是把 agent connector 当作普通脚本上线。
🔗 链接：https://arxiv.org/abs/2606.31227 ｜ 代码：https://github.com/Tencent/AI-Infra-Guard

### ContextBench：用人工 gold context 打开 coding agent 的检索黑箱
很多 coding-agent 失败并不是补丁写错，而是从一开始就没找到正确文件、正确函数或正确调用链；最终 pass/fail 很难告诉我们上下文检索到底出了什么问题。ContextBench 给这个中间过程建立了可量化标准：它包含 1,136 个 issue-resolution 任务，覆盖 66 个仓库、8 种语言，并由人工标注 522,115 行 gold context、23,116 个类/函数和 4,548 个文件。评测时，框架会记录 agent 在轨迹中实际查看的代码区域，用 tree-sitter 映射到文件、AST block 和行级坐标，再计算 recall、precision、F1 和效率。论文的一个重要发现是，复杂 agent scaffold 不一定带来更好的检索，模型普遍偏向高 recall 但低 precision，且“看过相关上下文”和“最终补丁真正用上上下文”之间还有明显鸿沟。对后训练数据工程来说，这比单纯保存 `rg` 或读文件日志更有价值，因为它能告诉我们哪些检索步骤是必要的，哪些只是噪声。内部评测如果能加入类似 gold-context 指标，就能分清“模型写补丁能力差”和“上下文接口差”两种失败。需要注意的是该论文编号较早，本期按 v3 内容与仓库 07-02 活跃更新作为近月评测资产收录，而不是描述为今天全新发布。
🔗 链接：https://arxiv.org/abs/2602.05892v3 ｜ 代码：https://github.com/EuniAI/ContextBench

### Qwen Code v0.19.5：把技能、MCP 可靠性、channel loop 与 PR 安全预检继续工程化
Qwen Code 已经不是单纯“一个开源终端 coding agent”，而是在快速补齐长程运行、团队通道、技能、Web shell 和 CI 安全这些 runtime 细节。7 月 2 日的 v0.19.5 release 包含一长串工程更新：统一 reasoning effort 的 `/effort` 命令、skills ACP 输出展示、MCP capability discovery retry、channel lifecycle metadata、DingTalk proactive send、session timeline rail、credential redaction 和 fork PR safety precheck。很多改动看起来小，但都对应生产 agent 的真实边界：MCP server 可能初始化失败，WebUI 会话要避免阻塞，fork PR 自动化要先做安全预检，worker stderr 不能泄露凭据。它还继续打磨 web-shell 移动端体验、计划模式 E2E、YOLO 模式 MCP approval 等运行时行为。工程 insight 是，agent 产品成熟度越来越体现在“长时间运行不丢状态、多人通道可观察、技能能被发现、失败能重试、安全默认可控”。对后训练和评测来说，这类 release 也提醒我们，模型分数无法替代 harness 版本记录；同一模型在 v0.19.4 和 v0.19.5 下的轨迹可能因为 retry、skills 或 permission 行为不同而不可比。它进入 High，是因为它代表开源 coding agent runtime 正在从 demo 走向可治理系统。

### Chrome DevTools MCP v1.4.0：把浏览器调试能力与 skills folder 暴露给 coding agents
前端 coding agent 最大的盲区之一是浏览器真实运行状态：DOM、console、network、performance、redirect chain 和截图经常决定问题根因，但纯文件编辑 agent 不一定能看到这些证据。ChromeDevTools MCP 试图把 Chrome DevTools 变成 agent 可调用的标准工具层，v1.4.0 在 6 月 23 日发布，仓库已有约 45k stars。这个版本最值得注意的是发布 skills folder，说明浏览器自动化不再只是 MCP tool schema，还开始沉淀成可复用工作流知识。它同时修复 network redirect chain 在文本和 JSON 输出中的顺序一致性，并明确文档说明 CD4A 可以支撑 browser agent。对 Agent-Friendly Software 来说，这是把传统 GUI/DevTools 能力转换为 headless、可审计、可组合接口的典型案例。未来做前端 agent 评测时，不能只记录 Playwright 操作或截图，还应记录 DevTools MCP 给出的网络、console、performance 和安全事件证据。这个项目的热度也说明“浏览器即开发环境”的 agent 化会持续增强，特别适合与 UI QA harness、Canary 类证据包和 web-shell agent runtime 结合。

### SlopCodeBench / SCBench：用迭代规格变更衡量 agent 代码腐化与结构债
很多 benchmark 只看 agent 当前这一轮是否通过隐藏测试，但真实软件会不断增加需求，早期设计如果太随便，后面每次修改都会把复杂度继续堆到坏位置。SlopCodeBench 的核心设定是让 agent 反复扩展自己之前写的代码，每个 checkpoint 只给 CLI 或 API 层面的可观察行为，不规定内部结构。这样 benchmark 能看到“今天能过测试但明天难维护”的问题，并用 verbosity 与 structural erosion 两个轨迹级指标衡量冗余代码和复杂度集中。项目网站现在展示 v1.0、36 个问题、196 个 checkpoints、19 个模型的 leaderboard；GitHub repo 6 月底仍有更新。一个有冲击力的结论是，即使强 agent 也很难端到端完成全部迭代，agent 代码相比开源人类项目更容易越来越啰嗦、越来越集中到高复杂度函数里。对后训练软件工程来说，这提供了一种重要筛选信号：成功轨迹不一定是好轨迹，后续可扩展性差的“过拟合式修补”不应被高权重训练。它也适合作为 skill 或 harness 的回归测试，检验“先设计再实现”“最小改动但保持结构”这类工程纪律是否真的有效。
🔗 链接：https://www.scbench.ai/ ｜ 代码：https://github.com/SprocketLab/slop-code-bench

### Words Speak Louder Than Code：固定代码、改变上下文即可操纵 LLM 漏洞判断
LLM 已经被大量用于漏洞扫描和代码安全 review，但这篇论文提醒我们：模型不只看代码，也会被上下文叙事诱导。作者固定待审代码不变，只改变周围文字来触发 halo effect、framing effect 和 anchoring effect，例如作者归因、任务目标、后果描述或前置分析结论。结果显示 8 个模型在 3 种语言上都受影响，跨模型平均 susceptibility 中 framing 最高达 33.2%，anchoring 为 23.5%，halo 为 18.4%。更严重的是，作者展示了一个 black-box cognitive attack，可以让模型抑制最多 97% 先前检测到的漏洞报告。这个问题对 coding agent 安全很现实，因为 agent 常从 issue、日志、PR 评论、Sentry 事件和外部报告中读取“上下文”，攻击者可以不改代码而改叙事。工程上，安全 harness 应把代码证据和叙事证据分层，要求模型先独立审计代码，再读外部分析，最后比较差异。对评测防作弊来说，这类 benchmark 可以暴露 LLM judge 和安全 agent 的上下文污染风险，避免把带偏见的描述当成可靠标签。
🔗 链接：https://arxiv.org/abs/2606.30587v1 ｜ 代码：None

### Sento 2.0 Dream Engine：让 Claude Code fleet 每晚反思预测误差并更新私有记忆
许多“自我改进 agent”项目只是在日志后面追加总结，缺少能校准经验是否真的有用的信号。Sento 2.0 的 Dream Engine 设计了一个很具体的学习循环：agent 在不确定动作前记录预测，动作后记录结果，每晚 cron 触发反思，把预测误差转成可复用校准经验。它把记忆分成 private `SELF.md`、durable `MEMORY.md` 和 fleet candidates，试图区分个人自我模型、事实记忆和可共享经验。项目本身只有个位数 star，可信度和成熟度都很低，所以放 Medium 且可信度 Low；但 7 月 2 日 release 把“prediction-error ledger”作为 agent memory 的学习信号讲得比较清楚。这个方向值得关注，因为长期运行的 coding agent fleet 需要从真实结果中学习，而不是每天重复同样的错误和同样的自夸总结。工程风险也明显：夜间自我修改记忆必须有可审计 diff、回滚和误学过滤，否则错误经验会被固化。对后训练数据工程的启发是，agent 记忆不应只存事实，还应存“预期-结果-校正”的三元组。
🔗 链接：https://github.com/sentoagent/sento/releases/tag/v2.0.0 ｜ 代码：https://github.com/sentoagent/sento

### BloopAI vibe-kanban：把 Claude Code / Codex 多任务管理产品化成 kanban 控制面
当一个开发者同时跑多个 Claude Code、Codex 或 OpenCode 会话时，真正困难不只是让 agent 写代码，而是知道每个任务在哪、谁在做、是否卡住、哪些结果需要人工 review。vibe-kanban 把这个问题包装成任务管理控制面，定位是“让 coding agent 多做 10 倍工作”的 kanban 层。仓库目前约 27k stars，7 月 3 日仍活跃，说明社区对“多 agent 任务可视化和工作流管理”需求很强。它不一定带来新的模型能力，但把 agent 从个人终端会话推向团队级任务队列、状态追踪和交接界面。对后训练软件工程来说，这类控制面会改变轨迹形态：任务不再是一条孤立 transcript，而是 board item、agent assignment、status transition、review comment 和最终 merge 的组合。评测平台也应学习这种产品形态，把 long-running task 的状态、暂停、恢复、人工接管和多 agent 并发都记录下来。它按 Medium 收录，因为技术细节公开较少，但社区热度和痛点足够明确。

### Anthropic Fable 5 redeploy：用 cyber classifiers 与 jailbreak severity 框架治理高能力模型发布
Anthropic 6 月 30 日宣布 Fable 5 / Mythos 5 恢复访问，并在 7 月 1 日更新恢复状态；这不是 coding-agent benchmark，但它提供了高能力 agentic 模型如何被安全治理的官方样板。背景是美国政府曾因 Fable 5 / Mythos 5 的 cyber 能力和 safeguard bypass 报告要求暂停访问，Anthropic 随后与政府和 Amazon 等伙伴复核证据、训练新的 safety classifier。官方称新 classifier 对报告中的具体 technique 在超过 99% 情况下阻断，但代价是日常 coding/debugging 中误报会增加。更值得关注的是 Anthropic 提出 jailbreak severity 框架，按 capability gain、breadth、ease of weaponization、discoverability 四项给 jailbreak 评分，并计划 24/7 监控关键提交渠道。对我们关注的评测防作弊和 agent 安全来说，这相当于把“jailbreak 是否严重”从模糊争论变成类似 CVSS 的可沟通流程。工程启发是，frontier coding/cyber agent 发布不能只给模型卡，还需要 classifier、fallback model、误报治理、红队提交渠道、政府/伙伴复核和严重性分级。它放 Low，是因为主题偏官方模型安全治理而非软件工程后训练，但可信度和制度信号都很高。

### 🔥 大佬观点

**Hacker News 开发者工作流讨论：真正的生产力来自 skills、hooks、TDD、worktree 和可验证循环，而不是单次“vibe”。**  
近期 Ask HN 里大量开发者描述自己如何并行跑 Claude Code/Codex、用 custom skills 做 PR、code review、Jira plan，并用 hooks 防止 agent 幻觉或越权。这个讨论值得注意，因为它把社区共识从“哪个模型最好”推进到“怎样设计工作流、验证门、并行隔离和人工接管”。🔗 https://news.ycombinator.com/item?id=48413629

**Simon Willison / Karpathy 线索：给 agent 一个 benchmark script，`make it faster` 才会变成可执行目标。**  
Simon 转述 Karpathy/Tobi 的 autoresearch 模式时强调，974 个稳定单测和明确 benchmark 是 coding agent 自动实验的前提；没有验证脚本，agent 只能猜测优化是否有效。这个观点对后训练软件工程很重要：可验证环境和自动打分脚本不仅服务评测，也会成为 agent 自动生成改进轨迹的基础设施。🔗 https://simonwillison.net/tags/andrej-karpathy/

### ⭐ 超火仓库/项目

**QwenLM/qwen-code：25k+ stars，07-02 v0.19.5 继续加固开源 terminal coding agent。**

**addyosmani/agent-skills：68k+ stars，生产级工程 skills 成为 agent 行为标准化入口。**
