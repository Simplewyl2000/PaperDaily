## 📝 逐条讲解

### Harness Handbook：把 agent harness 代码按“行为”索引到实现位置
生产里的 agent harness 往往不是一个简单 loop，而是权限、工具调度、状态机、提示词模板、缓存、子代理、错误恢复和遥测散在很多文件里。开发者或 coding agent 想改一个行为，例如“删除文件前必须确认”或“子代理结果怎样合并”，首先要定位这个行为到底由哪些代码共同实现，这一步经常比真正写 patch 更难。Harness Handbook 的做法是先用静态程序分析和 LLM 辅助结构化，从 harness 代码库自动合成一份以行为为中心的“手册”，把高层行为单元链接到具体函数、触发条件、状态变化和源码位置。它还提出 Behavior-Guided Progressive Disclosure：先给 agent 看行为级地图，再逐步展开到实现细节，并要求候选位置能被当前源码证据验证。论文在开源 agent harness 的多类修改请求上评估，发现这种手册能提升行为定位和编辑计划质量，同时减少 planner token。它新在把“代码检索”从文件/符号维度推进到行为维度，特别适合那些实现点分散、很少执行、跨模块交互的修改。对后训练软件工程来说，harness 自身也会演化，训练数据里如果能记录“行为需求→实现位置→修改计划→验证证据”，会比只保存最终 diff 更有价值。
🔗 链接：https://arxiv.org/abs/2607.13285 ｜ 代码：https://ruhan-wang.github.io/Harness-Handbook/

### Anthropic：用 Claude Code 动态工作流做大规模代码迁移
大型代码迁移通常不是让一个 agent 逐文件翻译就能完成，因为规则会变化、依赖会交错、编译很贵，多个 agent 还容易互相踩工作区。Anthropic 这篇官方技术博客把 Claude Code 用于真实大规模迁移的流程拆开讲，核心是先写规则手册和依赖地图，再用小样本压力测试规则，最后把待迁移文件做成可恢复的机械队列。实现阶段不是单代理独跑，而是 implementer-reviewer loop：实现代理负责翻译或修补，审查代理必须引用源证据来反驳或确认结果。更关键的是 build daemon 设计，只有一个进程允许重建二进制、批量汇总错误并反馈给修复代理，避免几十个 agent 同时触发最贵的构建步骤。文章提到 Bun 的 Zig→Rust 迁移里，峰值约 64 个 Claude agents 在 4 个 worktrees 中并行，最终在合并前让既有 CI 测试全通过，合并后出现的 19 个回归也已修复。它值得关注，因为迁移成功的重点不是“模型会翻译语言”，而是规则、队列、工作区隔离、构建串行化、审查和测试门组成了完整 harness。对后训练数据工程来说，这类迁移轨迹会产生非常清晰的阶段信号：规则发现、依赖图、批次分配、构建错误聚类、review 反驳和回归修复都可以成为训练或评测单元。
🔗 链接：https://claude.com/blog/ai-code-migration ｜ 代码：None

### Claude Code Artifacts + MCP：发布后的 artifact 可按 viewer 权限拉 live data
过去很多 agent 生成的 artifact 只是静态快照：Claude 在构建时读到什么数据，HTML 或报告里就固定保存什么数据，过一小时就可能过期。Claude Code docs 现在描述了一个更 agent-friendly 的模式：artifact 发布后可以在 viewer 打开页面时调用远程 MCP connectors，按查看者自己的 OAuth 权限拉取最新数据。这样一个 PR dashboard、issue board 或部署指标页不再需要作者重新跑 Claude Code，也不会把作者凭证泄漏给别人。工程约束也写得很清楚：artifact 必须声明 connector allowlist，页面不能调用未声明 connector；本地 `.mcp.json` server 只在构建时可用，发布后的页面只能用 claude.ai 账户里的远程 connector；带 connector 的 artifact 不支持 public link。这个功能的意义不只是“网页能刷新数据”，而是把 agent output 从一次性 transcript 推向 durable application shell。对 Agent-Friendly Software 来说，它把工具调用、权限、UI 和分享边界统一在 artifact 这个载体里。对后训练软件工程的启发是，未来轨迹不应只保存 agent 生成了什么页面，还要保存 artifact 的 connector 声明、viewer 权限模型、缓存/刷新行为和哪些 action 允许产生副作用。
🔗 链接：https://code.claude.com/docs/en/artifacts ｜ 代码：None

### Steerability via constraints：用工程约束而非提示词监督 coding agent
很多团队监督 coding agent 时，第一反应是写更长的 AGENTS.md 或 system prompt，告诉模型不要做危险事、遵守风格、不要引入后门。Steerability via constraints 的观点更像传统软件工程：大型人类团队不是靠口头提醒保持可控，而是靠访问控制、网络策略、类型系统、lint、格式化、模块边界和文档 CLI 这类 substrate-level constraints。论文在一个包含 11 个后门的 Python codebase 上做 2×2 实验，让一个较小 reviewer 检查代码。无约束、无工具时，后门 recall 为 54.5%；加入结构化 substrate 和约 200 行 `docs` CLI 后，recall 提升到 90.9%，且 substrate 与工具各自都有独立贡献。它的工程含义很强：与其让 agent 在混乱代码库里靠自然语言自律，不如先把代码库改造成更容易审计、更少自由度、更容易投影成文档视图的工作面。它按 High 收录，因为这正是 agent oversight 和评测反作弊的落地路径：把约束放进运行时和代码 substrate，而不是只放进 prompt。对后训练数据来说，训练样本需要记录当时启用了哪些 lint、policy、CLI view 和访问限制，否则无法解释 reviewer 或 coding agent 为什么更可靠。
🔗 链接：https://arxiv.org/abs/2607.02389 ｜ 代码：None

### CC Safety Net：跨 Claude Code/Codex/OpenCode 的 destructive command PreToolUse hook
让 coding agent 拥有 shell 权限后，最可怕的失败常常不是补丁不对，而是它执行了不可逆命令：误删目录、重置分支、覆盖未提交工作或通过解释器一行脚本绕过简单 denylist。CC Safety Net 把这个问题做成一个跨 CLI 的硬约束层，支持 Claude Code、Codex、OpenCode、Gemini CLI、Copilot CLI、Kimi Code 和 Pi。它作为 PreToolUse hook 在权限系统之前检查每个 shell command，用语义命令分析而不是普通 wildcard 匹配来判断风险。项目说明它能递归解析 shell wrapper 到 10 层，识别解释器 one-liner，并区分安全的 `git checkout -b` 与危险的 `git checkout -- file`。这和普通 permission deny rule 的差别很关键：deny rule 配错或漏掉 wrapper 时，Safety Net 仍能先拦截。项目约 1.4k stars，6 月中旬发布 v1.0.6，7 月仍有活跃关注，说明“agent 本地安全保险丝”已经是现实需求。对后训练软件工程来说，destructive-command block 事件应进入轨迹，既可训练 agent 学会选择更安全命令，也可评估一个 harness 是否真的把安全边界落到了执行层。
🔗 链接：https://github.com/kenryu42/cc-safety-net ｜ 代码：https://github.com/kenryu42/cc-safety-net

### skillshare：把 skills / agents / rules 做成跨 CLI 的单一事实源
技能库正在变成 coding agent 的长期资产，但现实里同一团队可能同时用 Claude Code、Codex、Cursor、OpenCode、Gemini 或其它 CLI，每个工具都有自己的 skill/agent/rule 目录。手工复制会带来两个问题：一个是版本漂移，另一个是团队不知道到底哪个 skill 被哪个 agent 使用。skillshare 的核心模型很直接：把 skills、agents、rules、commands 等文件资源放在一个 source directory，再通过 `sync`、`collect`、`push`、`pull` 同步到 60+ 个目标工具。它支持 symlink、copy、merge 等模式，也支持用 git remote 做跨机器或团队共享。项目约 2.4k stars，v0.20.x 在 6 月底发布，7 月 16 仍有更新，说明技能管理已经从个人文件夹问题变成多工具治理问题。它的新意不在某个模型技巧，而在把 skill 当成可安装、可审计、可同步、可回收的工程 artifact。对后训练数据工程来说，轨迹必须引用 skill 版本和来源；否则同一个 agent 的成功可能其实来自某个本地 skill，而不是模型本身。对 skill evolving 来说，统一源目录还能让团队更容易统计哪些技能被频繁使用、哪些需要重构、哪些在不同 CLI 下行为不一致。
🔗 链接：https://github.com/runkids/skillshare ｜ 代码：https://github.com/runkids/skillshare

### Open Design 0.15：本地优先的 agentic design workspace 降低 prompt/token 成本
前端和产品设计是 coding agent 很容易失真的场景，因为需求往往来自视觉、品牌、组件系统、历史版本和交互细节，而不是一段文本 issue。Open Design 把自己定位成开源 Claude Design alternative：本地优先桌面 app，让 Claude Code、Codex、Cursor、Gemini、OpenCode、Qwen 等 20+ CLI/agent 参与原型、落地页、dashboard、slides、图片和视频生成。7 月 14 日发布的 0.15.0 重点优化 Design System Prompt，公开 release notes 称代表性评估中 time-to-first-token 缩短 49.5%，端到端时长缩短 21.2%，平均输入 token 降低 25.1%。这说明 agent-friendly design 工具的竞争点已经不是“能不能生成 UI”，而是能不能把设计系统、素材、版本历史和失败恢复组织成更省 token 的工作面。它还支持真实文件导出，如 HTML、PDF、PPTX、MP4，并让设计结果能交给编辑器或 code agent 继续生产化。项目约 79k stars，近期 release 密集，属于社区高热。对后训练软件工程来说，设计类 agent 轨迹需要保存的不只是最终代码，还包括 DESIGN.md、组件 manifest、视觉参考、artifact 历史、失败恢复点和模型/CLI 适配器配置。
🔗 链接：https://github.com/nexu-io/open-design ｜ 代码：https://github.com/nexu-io/open-design

### From Legacy Documentation to OSCAL：15 个 MCP server 支撑连续合规 agent pipeline
合规和安全评估里的一个老问题是，组织有大量 PDF、Word、旧文档和系统描述，但审计需要的是机器可读、结构化、可验证的 OSCAL 文档。纯 LLM 直接从自然语言生成合规 artifact 很危险，因为一个虚构 CVE、错配版本号或错误控制映射都可能污染后续审计。该论文提出一个八阶段多 agent pipeline：先从系统描述抽取实体，再通过 15 个 MCP servers 接入权威 Cyber Threat Intelligence 来源，把漏洞、D3FEND、攻击路径和 taxonomy 链接进知识图，最后生成 NIST OSCAL 的 System Security Plan 和 Security Assessment Report。评估场景是一个 evidence-based hybrid IT/OT water utility，五次运行里 CVE recall 稳定约 0.90，D3FEND recall 为 1.00，对确定性来源节点报告 0% factual hallucination。论文也没有回避风险：LLM 实体抽取阶段仍有 12.5% semantic hallucination，会向后传播成 contextual false positives。它值得关注，因为它展示了 MCP 不只是给 agent 接工具，也可以把“可验证权威来源”变成合规 pipeline 的 grounding layer。对 agent 工程来说，这类系统的关键不是 prompt，而是每个阶段的 provenance、schema validation、deterministic retrieval 和错误传播审计。
🔗 链接：https://arxiv.org/abs/2607.08288 ｜ 代码：https://github.com/awslabs/mcp-server-for-oscal

### DeepStress：用可控 synthetic retrieval 环境压力测试 deep search agents
搜索型 agent 在正常 benchmark 上表现好，不代表它们能处理真实世界里质量很差的证据。现实检索结果可能不可信、不相关、或事实错误；这些坏证据在常规数据集中出现频率不高，所以平均分会掩盖灾难性失败。DeepStress 的方法是把 search agent 的 retrieval module 替换成一个可控 synthetic environment，让研究者能精确调节证据的 trustworthiness、relevance 和 factuality。它在 HotpotQA 和 BrowseCompPlus 上测试多个 deep search agents，观察它们面对低质量证据时的鲁棒性差异，以及模型参数知识和检索知识冲突时会怎样决策。这个工作按 Medium 收录，因为它不是 coding-agent 专项，但它的评测思想对 agent eval 很重要：不要只测“能不能找到答案”，还要测“坏证据按可控比例出现时是否会被带偏”。对后训练软件工程来说，类似方法可以迁移到代码搜索和文档检索：构造过期 README、错误 issue 评论、相似但无关代码片段，观察 agent 是否能建立证据质量判断。它也提醒我们，trajectory 里需要记录检索结果的来源、可信度和冲突关系，否则失败只能被归为模型幻觉。
🔗 链接：https://arxiv.org/abs/2607.13920 ｜ 代码：None

### AgenticSTS：bounded-memory contract + typed retrieval 的长程 agent testbed
长程 agent 最常见的记忆方案是把过去观察、工具调用和反思不断追加到下一轮 prompt，但这会让上下文越来越长，也让每个记忆组件到底有没有用变得难以消融。AgenticSTS 反过来规定一个 bounded-memory contract：每一步都从 typed retrieval 重新组装 fresh user message，不把原始跨步 transcript 直接追加进去。它把信息分成固定协议、状态 schema、检索到的规则、历史运行总结和触发式战略技能等层，每层都可以单独 ablate。测试环境是 Slay the Spire 2，一个需要数百个战术和战略决策的封闭规则游戏；项目发布了 298 条完成轨迹、condition tags、冻结的 memory/skill snapshots、prompt records 和分析脚本。固定 ablation 中，无 store baseline 赢 3/10，加 strategic skills layer 后赢 6/10，作者也谨慎指出样本量下统计显著性有限。它对软件工程 agent 的价值在于，长程代码迁移、调试或运维也需要类似 bounded memory：不是无限转述历史，而是把可复用状态写入类型化层。对训练数据来说，这类 testbed 展示了应该保存 memory snapshot 和 retrieval layer，而不只是保存最终 transcript。
🔗 链接：https://arxiv.org/abs/2607.02255 ｜ 代码：https://github.com/AlayaLab/AgenticSTS

### Adoption and Ecosystem Health：用 contributor density 取代 stars 选择 multi-agent 框架
Agent 框架选择经常被 GitHub stars 牵着走，但 star 很容易反映 hype cycle、媒体传播或短期营销，而不一定代表真实采用。Adoption and Ecosystem Health 对 15 个主流开源 multi-agent 框架做纵向分析，覆盖 2022 年末到 2026 年初的 808,042 个 stars、73,997 个 PR、86,241 个 commits 和 987,330 个用户 profile。结论很实用：AutoGPT 一个月拿到 111,967 stars，但每千 star 转化出的 contributor 少于 9 个，而 LangChain 约为 41；一些低可见度框架反而 contributor density 更高。论文还发现 LangChain 吸引了 82.5% 的跨生态贡献者，像共享基础设施一样连接不同框架。第三个信号是贡献者留存：首次贡献后的前 30 天流失最剧烈，约 90 天后趋稳。它按 Medium 收录，因为它不是新的 agent 技术机制，但对工程团队选型很有帮助。对本日报关注的社区热点也有提醒：我们可以记录 stars，但不能把 stars 当成唯一“热度”，还要看 release cadence、贡献者、跨生态集成和真实使用。
🔗 链接：https://arxiv.org/abs/2607.02453 ｜ 代码：None

### AutoMem：把长程 agent 记忆管理当成可学习 skill 自动优化
很多 agent 系统把 memory 当成固定架构：选一种向量库、写几条检索规则，然后希望模型自然会用。AutoMem 的观点更接近技能学习：记忆管理本身就是 agent 的 cognitive skill，需要通过实践、反馈和轨迹审查来优化。它把优化拆成两个轴，一个是 memory structure，例如文件系统接口、prompt schema 和 memory-file schema；另一个是 memory proficiency，也就是模型如何决定写什么、取什么、什么时候使用。系统用 meta-LLM 读取长程轨迹，诊断失败并改写 scaffold，同时也训练专门的 memory specialist。论文称只针对 memory 这一能力，在三个长程游戏环境上取得约 2x 到 4x 的提升，接近 frontier proprietary systems。它按 Medium 收录，因为场景不是软件工程，但方法非常贴近 skill evolving 和 trajectory review。对 coding agent 来说，类似思路可用于自动改进项目记忆：哪些 bug 经验应进入 LEARNING.md，哪些环境约束应写入 skill，哪些旧经验会误导新任务，都可以由轨迹驱动优化。

### 🔥 大佬观点

**Thariq Shihipar（@trq212，Claude Code team）：thin prompts、thick artifacts + context、thin skills。**  
Thariq 的九行框架在 7 月 16 日被社区解读为约 82K views 的热点：prompt 只表达意图，真正的规格和上下文应沉淀到 HTML、JSON、图表、测试矩阵等厚 artifact 里，SKILL.md 入口则保持薄，把脚本和参考资料放到子目录。这个观点值得注意，因为同一天 Claude Code artifact MCP connector 让“厚 artifact”从静态文件升级成可用 viewer 权限刷新 live data 的工作面。🔗 https://explainx.ai/blog/thin-prompts-thick-artifacts-thin-skills-thariq-july-2026

**Anthropic / Bun 迁移讨论：64 个并发 Claude 不是重点，重点是 workflow、worktree、build daemon 和 reviewer gate。**  
围绕 Bun Zig→Rust 迁移的社区复盘指出，“64 agents”是传播点，但真正可复制的是 4 个 worktrees、每个 workflow 内 16 个 agents、规则先行、reviewer 反驳、build 串行和批量测试。这个 insight 很重要，因为它把多 agent 从“并发数量炫技”拉回到可恢复队列、冲突控制和验证瓶颈治理。🔗 https://www.developersdigest.tech/blog/bun-rust-rewrite-agent-fleet-case-study ｜ https://claude.com/blog/ai-code-migration

**OpenAI Developers / Codex Micro 讨论：开发者正在监督 agent，而不是只输入代码。**  
Codex Micro 的六个 Agent Keys、reasoning dial、approval/error 灯号和任务切换键，把 agent 状态、人类介入和推理预算做成了桌面控制面。它的社区意义不是键盘本身，而是说明多 agent 工作流需要低延迟的“等待输入/完成/错误/调高 effort”信号，否则人类会在多个窗口里错过关键节点。🔗 https://learn.chatgpt.com/docs/features/codex-micro ｜ https://techcrunch.com/2026/07/15/amid-hardware-legal-battle-openai-releases-a-230-keyboard-for-codex/
