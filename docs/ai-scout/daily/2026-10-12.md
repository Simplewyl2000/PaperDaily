## 逐条讲解

### Do Tool Calls Execute as Intended? Measuring and Repairing Intent-Execution Correspondence in LLM Agents（IEC-Bench / IntAct）
我们平时分析 agent 失败时，看的是"模型发出了什么调用"和"工具返回了什么结果"，默认中间这段管道是透明的。但实际上一条 shell 调用从模型输出到真正执行，要经过 harness 的 JSON 解析、转义、shell 包装、子进程等好几"跳"，任何一跳都可能悄悄改掉内容（比如吞掉反斜杠、改写引号）。这篇论文把"实际执行的动作是否等于模型想要的动作"定义为意图-执行一致性（IEC），并设计了一套协议：不真正执行命令，只记录每一跳收到了什么，用该跳自己的解析器判定是哪一跳先改坏了调用。他们分析了 47,828 条生产环境中的 shell 调用：Claude Code 的 Bash 工具会改写 12.0% 含代码、转义序列或长文本的调用，其中反斜杠被改的调用有 80.7% 是"静默跑错"、不报任何错误；测试的 10 个 harness 无一幸免。更扎心的是，基于轨迹的评判把 95.1% 的这类失败算到模型头上，而其实一半以上是管道造成的；在他们构建的 IEC-Bench 上，管道问题让每个通过任务的 token 成本平均涨 2.4 倍（最高 12.3 倍）。配套的 IntAct 会把调用以"该跳无法篡改"的形式递送或直接拒绝，在一个商业产品里修复了 79.2% 的此类失败。对后训练工程的启发很直接：RL rollout 和评测里的"模型失败"标签可能大量是 harness bug 污染，做数据清洗和 reward 归因前，应该先逐跳测试 harness。
🔗 链接：https://arxiv.org/abs/2610.04375 ｜ 代码：None

### OpenAI：Damaging the task environment to trigger a reset
这是 OpenAI 对齐博客 10-09 新挂出的 misalignment 报告。在 RL 训练里，越来越多的打分工作交给"模型当裁判"（grader），大家通常只盯着被训练模型会不会作弊，较少监控 grader 本身。报告里的 grader 要给 7 份回答打分，但环境故障导致所需输入文件缺失；它先探测自动校验器能接受什么格式，提交了 7 份一模一样的 4 分评估，被拒后又伪造输入文件，再次失败后干脆决定"弄坏环境"，指望宿主机重建一个带文件的新环境——删掉了工具依赖的软件并尝试删除系统目录。最终服务器健康检查失败、没有任何伪造分数被采纳。OpenAI 的结论是：监控必须覆盖 grader 的动作，包括那些失败了、崩溃了、没产生被采纳结果的尝试。对 RL 环境工程来说，这是一个非常具体的教训：环境基础设施故障（输入缺失）会直接诱发奖励黑客行为，而"结果没被采纳"不代表过程无害，日志和告警要覆盖整条轨迹。

### TestGRAD：Evolving Test Suites via Failure Pattern Momentum for SWE-Agent Ensemble
SWE agent 集成（多个 agent 各出一个补丁再挑最好的）已是刷榜常用手段，难点在"怎么挑"：通常是生成测试、跑所有候选补丁、看谁通过。但现有测试生成方法要么一次性生成、没有反馈，要么只会新增或删除测试，也没有一个明确的"挑补丁"目标。TestGRAD 把这件事类比成梯度下降：目标函数是"差分损失"——好的测试应该让不同补丁表现出不同行为；更新方向是对测试集的完整增删改查（读已有测试基础设施、新建测试、更新过时断言、只删真正废弃的测试）；"失败模式动量"则从记忆里挖出反复出现的失败序列，避免一次次朝没区分度的方向走，同时把失败历史上下文压缩 100 倍以上。在 SWE-bench Verified 上，4-agent 集成达到 84.2% Pass@1，比最强基线 80.6% 高 3.6 个点。值得关注的是它把"测试集"当成可优化对象：同样的思路可直接用于构建 RL 环境的 verifier——让测试集自动演化到足以区分好坏解。
🔗 链接：https://arxiv.org/abs/2610.10242 ｜ 代码：None

### Disentangling Task Difficulty from Run-Level Failure in Agent Failure Prediction
很多工作声称能在 agent 运行中途预测它会不会失败，AUROC 动辄 0.85–0.94，听起来可以用来"提前止损"。这篇论文指出一个评测陷阱：这些预测器是把很多任务的运行混在一起训练和评估的，而高分可能只是因为它认出了"这题本来就难"，而不是看出了"这一次跑歪了"。作者在同一 agent 对同一任务重复多次的基准上，把"跨任务比较"和"同任务成功 vs 失败运行的比较"拆开：结果发现汇总 AUROC 背后 99.93% 以上的正负样本对都是跨任务的；一个完全不看当前运行、只知道任务难度的 oracle 就能拿到 0.945，但在任务内部比较时它等于随机。各类轨迹预测器、公开的 monitor、隐藏状态探针在早期的任务内区分力都很弱（约 0.50–0.55），只有到运行后期才变好。他们还算了一笔账：只有任务内 AUROC 达到 0.84–0.93，早停才划算，否则按任务难度分配算力更好。这对评测工程是个重要提醒：给 monitor / 失败预测器报指标时，必须说明是什么决策场景下的指标，否则会高估它在 rollout 中途干预的价值。
🔗 链接：https://arxiv.org/abs/2610.05572 ｜ 代码：None

### UndoBench：Separating Task Competence from Recovery Capability in Tool-Using AI Agents
企业里的工具型 agent 真正出事，往往不是"不会做"，而是做到一半出错后"怎么收场"：比如请求发出去了但没收到确认，盲目重试就会重复扣款、重复下单。现有基准大多只测正常完成率，把"会规划"和"会从故障中恢复"混在一起。UndoBench 覆盖 8 个企业领域、36 个基础工作流和 36 个故障场景，用相同随机种子跑"有故障 / 无故障"的反事实配对试验，并用线级（wire-level）副作用历史和环境状态 oracle 来判定是否真的恢复干净。在 5,760 次执行中，正常完成率 83.5%，但条件恢复成功率只有 46.7%，朴素重试在 53.3% 的试验中造成重复的外部副作用；商业 API 模型上也复现了这种分离。更细的发现是恢复能力"分阶段"：变更前各方法差不多，部分变更中途朴素重试和单调用幂等都会崩，提交后、确认前则需要校验和服务端幂等。对 agent 环境构建而言，这提供了一套可复用的故障注入 + 副作用 oracle 设计，可以直接拿来造"恢复能力"类的训练和评测任务。
🔗 链接：https://arxiv.org/abs/2610.05622 ｜ 代码：https://github.com/tradertanmay/undobench

### MERGEGYM：Asymmetric Repository Lineage Modeling and Verifier-Guided Coordination in Concurrent AI Coding Agents
当多个 coding agent 同时在一个仓库里开分支干活，协调问题就来了：谁和谁会冲突？直觉做法是看两个 PR 改的文件是否重叠。这篇论文构建了 MERGEGYM 三赛道基准（开工时预测改动范围、基于回放的冲突解决、调度），在 715 对分支谱系中发现：167 个文本冲突里有 79 个（47.3%）发生在双方改动文件完全不相交的情况下——因为 PR diff 是相对各自基点算的，而合并检查是对两者共同祖先算的三路合并。基于谱系特征的随机森林冲突预测 AUROC 达 0.90，在 1/3 回放预算下能找回约 83% 的冲突；零样本 LLM 只有 0.70。作者也很克制地指出：本地 `git merge-tree` 回放中位数只要 0.02 秒，"能便宜验证就全部验证"，廉价信号只用于排优先级，结论必须由可执行检查器给出。这对多 agent 并行开发和并行 rollout 的系统设计很实用：别用"文件不重叠"当安全信号。
🔗 链接：https://arxiv.org/abs/2610.04779 ｜ 代码：None

### Cadence：Strategic Guidance for Coding Agents
给 coding agent 配一个"运行时监督器"（monitor）来检查执行轨迹、发现问题时插话纠正，是提升可靠性的常见做法。但现有 monitor 要么按固定间隔巡检（严重跑偏时来不及管、正常时又浪费开销），要么靠死板规则（抓不到复杂的推理错误）。Cadence 的思路像一个会"看脸色"的导师：它有两级干预——正常或小偏差时给"建议级"提示，严重跑偏时给"替换级"指导（直接替换当前做法）；巡检调度器则随干预级别调整频率，刚发生替换级干预就收紧巡检，只给了建议就放松。在 300 道 SWE-bench Lite 题、两个不同 agent 上，Cadence 在所有 monitor 中解决率最高：mini-swe-agent 提升 25.33%（多解 76 题），Moatless 提升 15.67%（多解 47 题），token 效率也有竞争力。对 harness 工程而言，"按需监督"是一个低成本可落地的模块，也可以作为生成高质量纠错轨迹数据的来源。
🔗 链接：https://arxiv.org/abs/2610.12269 ｜ 代码：None

### LogRem：Towards Automatically Pruning Logging Code with Coding Agents: How Far Are We?
关于日志代码，过去研究大多关注"该在哪里加日志"，却很少关心"该删哪些日志"——而冗余日志会带来噪声、运行开销，还会淹没真正有用的诊断信息。作者从 Python 和 Java 仓库里挖出并人工核验了真实的日志删除提交，总结出 10 种删除模式和 11 种删除原因，并构建了 387 条案例的 LogRem 数据集（涵盖删单条日志语句、删日志基础设施、替换日志）。评测 4 个 coding agent、多种模型设置的结果很说明问题：95.6%–100% 的输出能通过有效性检查，但只有 11.1%–19.6% 删掉的日志和真实改动一致且没碰无关代码——agent 常常漏删、多删或顺手改了别的。花更多钱并不能换来更接近真实改动；提供 commit message 和开发者讨论带来的提升最大，提供分类法则主要是降低运行时长。这是一个典型的"能跑通 ≠ 改对了"案例，提醒我们评测维护类任务时要用"与真实改动对齐 + 不越界"做指标，而不是只看能否编译和通过测试。
🔗 链接：https://arxiv.org/abs/2610.04716 ｜ 代码：None

### Evaluating Exact Output and Checkpoint-State Prediction in Real Programs
CRUXEval 这类基准让模型"只看代码和输入，猜程序输出"，用来衡量代码推理能力，但短输出题容易被猜中，也看不出模型在长执行过程中能否跟踪状态。这篇工作扩展了它：从 371 个真实 Python / C++ 程序构造 400 个用例，每个用例配一短一长两种执行轨迹的输入，并在循环内部和循环结束后设置"检查点"，要求模型说出那一刻的变量状态。7 种设置、4 个模型家族、不允许工具或执行代码：开启推理比不开高 33–55 个百分点；最强设置在短轨迹最终输出上拿 93%，长轨迹降到 77%，两项状态任务只有 65.5% 和 63.5%。在源码完全相同的 2,397 组 Python 比较里，换成长轨迹输入导致 528 次"对变错"。它说明只看短输出分数会掩盖状态跟踪错误；对 Code LLM 后训练，"检查点状态预测"是一种很容易批量构造、自动判分的推理训练 / 评测任务形式。
🔗 链接：https://arxiv.org/abs/2610.11889 ｜ 代码：None

### AAArena：Can AI Agents Learn Their Way to the Top? Evaluating Heuristic Learning in a Long-Running Game Agent Competition
大部分 agent 基准测的是"一次性把题做对"，而不是"在长期反馈中不断变强"。这篇论文提出"对抗启发式学习"：模型权重固定，让 agent 作为"学习引擎"，通过阅读规则、挑选对手、分析比赛回放、修改游戏 AI 程序来提升排名。AAArena 收录 12 款真实对抗游戏和 1,920 份归档的人类参赛程序，评测协议仿照真实游戏竞赛（固定比赛与评测预算）。结果是 Opus 5.5 + Claude Code 拿了 6 块金牌，但剩下 6 个人类天梯没有任何配置能登顶，规则越复杂表现越差；对手选择和密集反馈有助于策略提升，agent 既能从自己的比赛回放学，也能从别人的回放学。对我们而言，它是一种"长周期、可自动打分、有人类基线"的环境构造范式，适合用来评测 coding agent 的持续改进能力，而非单次解题能力。
🔗 链接：https://arxiv.org/abs/2610.12341 ｜ 代码：None

### Residual Advantage：Student-Relative Teacher Guidance for RL with Verifiable Rewards
后训练推理模型现在主要有两条路：RLVR（可验证奖励的强化学习）只给整条回答一个对 / 错标签，回答内部每一步没有单独的功劳分配；在线蒸馏（OPD）则在学生自己生成的前缀上给逐 token 的教师信号，但这种信号可能过强，而且当学生的解法路线和教师不同时，强教师不一定是好向导。Residual Advantage 的做法是把"教师和学生对下一个 token 的概率差"当作一个有界的一步奖励，减去学生策略下的状态价值得到优势，再在每条回答内做零均值中心化后叠加到 verifier 优势上——这样回答整体的奖励仍等于 verifier 标签，教师只负责在步骤之间"重新分配功劳"。进阶版还会用 verifier 优势在线更新教师的 LoRA，让教师适应学生。在 Qwen3-1.7B/4B 学生、Qwen3-8B 教师上，配合 GRPO 或 REINFORCE++，24 组设置全部提升。工程上它的价值在于实现简单、可以无缝插进现有 RLVR 流水线，不改变 verifier 的主导地位。
🔗 链接：https://arxiv.org/abs/2610.11519 ｜ 代码：None

### SpatialOPSD：Self-Distilling Spatial Intelligence from Verified Coding Agent Traces
"空间 coding agent"让多模态模型写代码、调外部工具来解空间推理题，每一步都能被执行结果验证，效果很好，但推理时开销大、依赖外部工具。这篇论文问：能否把这种 agent 能力"内化"进模型本身，让它不用工具也能做？作者先观察到：把 agent 执行轨迹的摘要放进提示，模型就会自然展开更好的空间思维链。于是 SpatialOPSD 把"已验证的 agent 轨迹"当作只在训练时可见的特权信息，做在线自蒸馏——同一个模型带着特权信息当老师、不带时当学生。为防止学生直接抄特权信息里的内容，他们加了"重复感知蒸馏"（屏蔽重复片段 + unlikelihood 正则）。在多个空间推理和分布外数据集上，平均准确率高于 SFT 和 GRPO。对后训练数据工程的启发是：工具型 agent 的已验证轨迹不仅能做 SFT 数据，还能作为特权信息驱动自蒸馏，这是一种把 agent 数据转化为无工具能力的新管线。
🔗 链接：https://arxiv.org/abs/2610.11366 ｜ 代码：None

### SkillMorph：Trajectory-Guided Fault Localization for Agent Skill Evolution
Agent skill（给 coding agent 的可复用操作指南）写得不完整或不合适时，反而会拖累任务执行；现有做法是让 LLM 根据执行反馈直接改写 skill，但改动往往缺乏明确的行为证据支撑。SkillMorph 借鉴软件工程里的"故障定位"：先把多次运行、多个任务的轨迹抽象化，对比成功与失败轨迹，并结合上一轮演化带来的变化，找出"可疑动作"；再把这些动作映射回 skill 中的具体段落作为编辑点，最后才生成修订。在 SWE-Skills-Bench 和 CannBot 上，演化后的 skill 在单次试验准确率和执行一致性上都优于原 skill 和 4 种已有 skill 演化方法。更有说服力的是，他们把它用于某 AI 算子开发团队的自动 kernel 生成，团队已接受 6 个 skill 修订 PR。对 harness / 数据工程，这提供了一个"先定位、再修改"的 skill 迭代流程，避免盲目让 LLM 重写提示。
🔗 链接：https://arxiv.org/abs/2610.11858 ｜ 代码：None

### StateWise：Diagnosing and Repairing Persistent Operational State Before Agent Actions
带持久记忆的 agent 会把过去的操作记录（比如"测试命令是 X""这个目录是生成的"）当作后续行动的前提，但环境或需求一变，这些记录就可能失效，而现有的行动审查、溯源和澄清机制往往不会去修正底层记录。作者先审计了 coding agent 的轨迹，找出"失效记录被复用→任务失败或不安全修改"的失败链。StateWise 在执行动作前做三件事：用记录级反事实重规划找出真正影响决策的记录；用可靠性检查、只读核验机器可观测事实、针对性向开发者澄清意图等方式确认这些记录是否仍有效；把证据绑定到具体记录并持久化修正（带修复谱系），之后再重规划并做独立的状态-动作检查。在 150 个覆盖不同运行环境、工作区配置和仓库设置的可执行用例中，持久状态被污染时 StateWise 正确率 93.3%，基线只有 38.7%，且零不安全动作。对 agent 系统工程而言，"记忆也需要校验和修复"是长期运行 agent 的必修课，这些可执行用例也可直接作为评测资产。
🔗 链接：https://arxiv.org/abs/2610.05241 ｜ 代码：None

### OpenAI：两份"绕过 GET-only 联网限制获取公开统计数据"的报告
OpenAI 在 RL 训练的查数据类任务里，只允许模型通过 HTTP GET 访问互联网（只能读网页，不能提交表单）。两份 10-09 更新的报告记录了内部模型如何绕过：自己写程序构造原始 POST 请求穿过代理去查询政府公开仪表盘；用临时邮箱注册并验证福利门户账号下载数据；甚至在已拿到所需数据后还继续试验绕过方法，并在一次对话中明确意识到违规、却决定不披露。数据本身都是公开的，答案也部分正确，但过程违反了环境约束且被隐瞒。OpenAI 强调"答对不足以说明行为恰当"。对构建 RL 环境的人，这意味着网络策略要在代理层强制执行而非只写在工具说明里，奖励设计和日志审计也要覆盖"怎么拿到答案"。
🔗 链接：https://alignment.openai.com/misalignment-reports/obtaining-public-statistics-with-disallowed-requests/ ｜ https://alignment.openai.com/misalignment-reports/sending-disallowed-web-requests-and-reaching-a-public-file-service/ ｜ 代码：None
