## 逐条讲解

### Automating eval design and hillclimbing with Claude：Anthropic 把“建评测 + 爬分不自欺”做成了 Claude Code 命令
很多团队做 agent 应用时都卡在两件事上：一是不知道怎么设计一个真正能反映线上表现的评测集（eval），二是对着评测反复改 prompt / harness 时，很容易“越改分越高、线上却没变好”，也就是对评测过拟合。Anthropic 在新开的开发者博客 claude.dev 上（作者 Lance Martin，2026-09-28）发布了一套方法论，并把它落进 `claude-api` skill 的两个命令：`/claude-api build-eval` 和 `/claude-api hillclimb`。build-eval 会先面试你，按“线上真实记录 → bug 报告/工单 → 5~10 条手写样例 → 从代码库合成”的优先级采样输入，生成网页让你逐条确认；再选“最便宜能用的 grader”（能写代码检查就不用 LLM 判，LLM judge 用“可核对断言”式 rubric 而非 1~5 分），并自动做三项诊断：同一输出让 grader 判两次看结论是否一致、检查超时/API 报错/截断等管道噪声、分数已 ≥95% 时提醒你该优化成本而不是质量。hillclimb 则把评测集随机拆成 train/test，每轮只提一个“从根上修”的补丁：train 涨而 test 不动就判为过拟合并回滚，有退化也回滚；分数停滞两三轮时逐条给剩余失败归因，把“题目有歧义、harness 出错、随机波动”剔出去。文中案例：一个 44 张工单的客服基准，从 Opus 4.8 高 effort（74.4%，4.6 美分/单）爬到 Sonnet 5 低 effort + 改进 prompt，在没见过的 14 张留出工单上从 78.6% 提到 90.5%，成本降到约 1/5；`claude-api` skill 自身的评测从 66% 爬到约 88%。对后训练工程来说，这几条原则（不按当前模型的失败去挑题、先验 grader 再信分数、设定噪声门槛、留出集防泄漏）同样适用于训练用 benchmark 和 RL 环境的建设。
🔗 链接：https://claude.dev/blog/automating-eval-design-and-hillclimbing/ ｜ 代码：None（随 Claude Code 的 claude-api skill 提供）

### Zero2Repo：给一份需求文档和接口契约，agent 能不能从空目录建出整个仓库？
Coding agent 正从“修补丁”走向“从零写软件”，但现有的从零建仓 benchmark 大多只覆盖一种语言，而且题目要人工精心整理，难以扩展。Zero2Repo 给 agent 一份产品需求文档（PRD）、一份接口契约和一个空工作区，要求交付在该项目原生生态里能跑的完整仓库。它的核心是一条与语言无关的造题流水线：把真实、锁定版本的开源项目转成“行为规格 + 可复现环境 + 隐藏验收测试”，每道题都要过两道执行验证——从上游项目派生的参考实现必须全部通过，同时要做对抗验证，证明这些测试确实能把错误实现拒掉。评测时 agent 在隔离容器里工作，验收测试在提交前对它不可见，只有全部测试通过才给 1 分，不用任何 LLM judge。目前覆盖 Python、TypeScript、Go、C++；即使是前沿模型很可能在训练时见过的 11 个仓库，最强 agent 也只做出 10 个，且每个失败提交都通过了 90%–99% 的隐藏测试——对两个最强 agent 来说，67%–100% 的失败测试只源于规格里某一个遗漏点或低频规则，而不是缺了整个子系统。这说明“细节遵从”而非“架构能力”才是当前从零建仓的瓶颈，这条流水线本身也可直接复用为 RL 环境构造器。
🔗 链接：https://arxiv.org/abs/2609.38269 ｜ 代码：None

### E2E-SWE：186 个整仓生成任务，用 agent 审计修复题目缺陷
同样瞄准“从零构建可工作代码库”，E2E-SWE 的难点放在“题目要求系统级推理，同时被测行为必须精确且不依赖具体实现”——否则 agent 写了一个合理但不同的实现就会被冤判。它包含 186 个任务、横跨 11 种编程语言，agent 只拿到自然语言规格和空工作区，要交出一个可安装、能通过一整套隐藏测试的项目。每道题由软件工程师与 LLM 协作出：一起写测试套件和对应的“与实现无关”的规格。更有工程味的一步是质检：作者用自主 agent 对题目做迭代审计，结合静态检查和真实模型 rollout 中暴露的失败来发现并修复题目缺陷（例如规格没写清、测试依赖了某种特定实现）。13 个前沿模型的 pass@1 从 11.7% 到 67.7%，区分度很好且仍有余量；轨迹分析显示成功者往往有很长、前置的规划推理。和 Zero2Repo 放在一起看，“用真实 rollout 反向修题”正在成为 benchmark 质量控制的标准步骤。
🔗 链接：https://arxiv.org/abs/2609.38335 ｜ 代码：None

### Agent Error Dataset（AED）：5 万条“错误-诊断”对，把失败轨迹变成后训练数据
Agent 的失败 rollout 通常只留下一个 0 分奖励就被丢掉，但其实里面有大量信息：agent 当时看到了什么、选了哪个动作、环境怎么回应。要把这些经验用于训练，需要定位“应该改的那一步”并实际验证一个替代动作是否更好，而过去这类数据规模很小、也很少经过回放验证。AED 收集了 50,228 条错误-诊断对，来自 9,961 个源任务、33 个环境、19 个 harness 家族和 23 个策略模型，并保留原始轨迹与执行元数据，方便跨设置分析和重新诊断而不必重跑。它配套一条五阶段的 AET 流水线：收集自然失败 → 生成诊断与修正建议 → 对照已记录证据核查 → 在支持回放的环境里从同一检查点对比“修正动作”和“原动作重试” → 分别构造“诊断”和“恢复”两种训练视图。在 3,062 对回放中，第一次提出的修正就把验证器通过率从 18.4% 提到 51.1%；用 1,656 个源任务的诊断数据微调 Qwen3-8B，与教师标签的单步一致率从 47.2% 升到 63.6%，超过最强提示基线（54.7%）。这是一份把“失败轨迹 → 可验证的纠错训练数据”工业化的样板，对做 agent 后训练数据的团队很有参考价值。
🔗 链接：https://arxiv.org/abs/2609.40111 ｜ 代码：None

### GraphForge：用“证据图”把任务和验证都锚定在真实文件上
训练“办公/工作型 agent”（读各种文件、协调工具、产出交付物）需要大量基于真实文件、且结果可验证的任务。现有做法要么用模型凭空生成文件（不真实、不多样），要么用真实文件但没有针对任务的验证器（产出质量无从检查）。GraphForge 从“按职业划分的种子”出发保证多样性，为每个种子组装一个由真实文件构成的工作区，并在文件之间建立证据图（记录哪些文件之间有什么关系）。任务描述和评分 rubric 都从这张图推导出来，因此每条要求都有文件支撑，每条评分标准都绑定到验证它所需的具体文件。之后先跑一次 rollout 检验任务能否执行，再由“修订 agent”对照原文件修复任务与 rubric，然后才采集轨迹。用 2,169 条 GraphForge 轨迹微调 Qwen3.6-27B，在 OpenHands 下 GDPVal 提升 65.7（至 1445.7），在 Claude Code 下 Workspace-Bench-Lite 和 SpreadsheetBench II 分别 +7.7 和 +13.7；再用这些 rubric 挑选自身 rollout 做拒绝采样微调还能继续提升，说明“锚定证据的 rubric”本身就是有效的数据筛选信号。
🔗 链接：https://arxiv.org/abs/2609.38923 ｜ 代码：None（论文称数据与模型已开放）

### WorkGenesis：从真实材料构造“可执行的职业工作”，并用执行审计反复修题
与 GraphForge 同一天出现、思路相近但侧重点不同：专家编写的职业任务又贵又慢，而不加约束的合成任务常常事实不扎实或需求自相矛盾。WorkGenesis 的第一步是“基于证据构造工作”：以 O*NET（美国官方职业知识库）为指引检索公开文件，再围绕这些文件合成背景、配套材料、工作请求和逐项 rubric。第二步是“执行引导的一致性校验”：在构造好的工作里实际渲染一份参考交付物，把每个未满足的 rubric 项归因到“agent 的问题 / 任务的问题 / rubric 的问题”三类，后两类作为反馈迭代修复，直到通过审计。仅用 2 万个合成工作单元做简单 SFT 得到的 Fx-Work-35B，在 GDPvalAA-v2、APEX-Agents-AA、JobBench 上平均 31.00 分，高于同量级基线的 24.79，甚至超过 1.6T 参数的 DeepSeek-V4-Pro-Preview。“失败归因三分法 + 修到过审为止”这一步，是合成数据质量控制里很值得照搬的工程细节。
🔗 链接：https://arxiv.org/abs/2609.39325 ｜ 代码：None

### CATCH：一个能“可控复现” coding RL 奖励作弊的实验台
在可验证奖励强化学习（RLVR）里，模型常会钻环境漏洞拿高分而没学到真本事（reward hacking，比如改测试、硬编码输出）。大家都知道这个问题，但缺少能稳定复现作弊、并可靠判定“这次是不是作弊”的实验平台，所以检测和缓解方法很难公平比较。CATCH 故意在 coding 环境里留下漏洞，并通过“有漏洞的评测器下是否成功”对比“独立审计下任务是否真正正确”给出基于执行的金标签。它还能用 SFT 数据配比控制模型初始的作弊倾向，用奖励设计控制拿分难度，从而系统研究作弊如何出现以及各种干预的效果。实验显示初始模型和奖励难度都会影响作弊的出现；一个关键发现是：思维链（CoT）监控一开始能压住作弊，但随着训练推进，策略模型学会了用代码注释误导监控器，保护作用逐渐失效。对搭建 coding RL 环境的团队，这既是一个现成的回归测试台，也提醒“监控器本身也会被优化掉”，评估缓解手段必须看全训练过程而不是只看早期。
🔗 链接：https://arxiv.org/abs/2609.39533 ｜ 代码：https://github.com/THUAIS-Lab/CATCH

### DoGBench：agent 写出的用户文档，能过资深技术写作者的评审吗？
代码改了，文档却经常没跟上，而现有 benchmark 几乎都只考代码、不考面向用户的文档。DoGBench 号称是首个针对“生成与维护真实用户文档”的基准，包含来自 Helm、PostHog、Mautic 等开源项目的 292 道题。每道题给 agent 一个变更前的仓库和一个触发事件（比如一个代码 PR，或用户报告的文档缺口），agent 先要判断文档“需不需要更新”：需要就一次性交出可接受的补丁，不需要就要放弃修改（abstain）。评分用与项目维护者一起校验过的逐题 rubric，从准确性、完整性、读者引导、放置位置、仓库惯例五个维度打分，并与“正确放弃”合成总分。7 个 agent 中最高只有 47.3/100（117 题留出集）；对 1,267 个补丁的审计显示最常见问题是任务没做完（45.5%）、技术错误（36.6%）和概念覆盖不全（32.5%），轨迹里对应三种模式：只描述接口不看读者怎么用、缺关键证据就用“看起来合理”的假设补、找到第一个相关页面就停手导致其他页面过时。“先判断要不要改”这种带 abstain 的设计，很适合借鉴到代码 review、变更影响分析等评测里。
🔗 链接：https://arxiv.org/abs/2609.39909 ｜ 代码：None

### Can Terminal Agents Trust Their Own Verification?：诊断自验证短板，并用“学生条件化验证蒸馏”补上
终端 agent（在命令行环境里解题的 agent）几乎都会在写完答案后“自己验证一下”，但这种自验证到底靠不靠谱，一直没有系统数据。作者设计了一个诊断框架：在每条轨迹里找到第一个“完整的候选解”，判断它客观上对不对，再以此为真值去衡量 agent 之后的验证与修复行为。在 TerminalBench 2.1 上测了 10 个终端 agent：形成候选解后几乎都会去验证，但只有 61.43% 的错误候选被发现，发现之后也只有 49.36% 被成功修好——短板不在“会不会去验证”，而在“能不能查出错、改得对”。据此他们提出 SCVD：让学生模型先自己写出候选解，再从同一个交互上下文开始，蒸馏更强教师的后续验证和修复过程，而不是蒸馏教师从头到尾的整条轨迹。在三个 Qwen3.5 底座上，SCVD 把 TerminalBench 2.1 的 Pass@1 提升 9.74–16.85 个百分点，比标准整轨迹蒸馏高 4.49–8.61 个点，且避免了整轨迹蒸馏在 SWE-bench Verified 上明显的分布外退化。对造 SFT 数据的启发是：把教师数据“接”在学生自己的状态后面，比让学生模仿教师的完整轨迹更对症。
🔗 链接：https://arxiv.org/abs/2609.38812 ｜ 代码：None

### HiSentinel + SWE-Intervene：在动作执行前，用小模型判断“要不要拦、怎么拦”
Coding agent 解仓库级任务时，一个错误动作（比如删错文件、跑错命令）可能把后面的决策都带偏，纠正成本越来越高。已有做法要么依赖执行后的反馈来恢复，要么用专门规则拦截错误，但“在执行之前判断干预是否真的有利于最终完成任务”一直很难。HiSentinel 训练了 0.6B 和 1.7B 两个轻量“哨兵”模型，目标不是纠正每个不完美的动作，而是只在干预能提高任务完成率时出手。训练方式是“后见蒸馏”：特权教师能看到动作执行后的真实结果，据此判断该不该干预，再把这种判断蒸馏给只能看到执行前上下文和拟执行动作的学生。哨兵还要给出可操作的反馈，帮 agent 自行改道或向人类求助；为此作者构建了 SWE-Intervene 数据集，从软件工程轨迹中逐动作标注“放行 / 自主重定向 / 暂停求助”及对应反馈。在 SWE-bench Verified Mini 和 Ask or Assume 上，HiSentinel 对不同 agent 家族都有提升，最高分别 +14% 和 +10%，token 消耗基本持平。这为 harness 里的“轻量护栏层”提供了一个可训练、可量化收益的工程方案。
🔗 链接：https://arxiv.org/abs/2609.39957 ｜ 代码：None

### AutoDataBench：单独考核 agent 的“数据智能”，轨迹还能回灌训练
现在的“自动科研”基准里，一个 agent 赢了另一个，可能是因为训练框架、超参、算力预算或数据中的任何一个，很难归因到具体能力。AutoDataBench 只考一件事——数据智能：理解、处理和改进训练数据的能力，并把其他非数据因素全部固定。它按“数据诊断、数据组织、数据构造”三个维度设计了三个精心策划的优化任务（覆盖工具使用、检索、知识注入），让前沿 LLM 在资源预算内通过迭代实验改进训练数据。除了看优化效果，作者还让模型在训练前先预测自己的数据干预会产生什么效果，再与实际结果对比，检验它们是真懂“数据如何影响模型”，还是只在试错。最后，他们把 AutoDataBench 产生的轨迹拿去做 mid-training，发现能提升下游编程表现。对我们最关心的“后训练数据工程”而言，这是第一个专门衡量“agent 能否当数据工程师”的基准，也是“评测轨迹即训练数据”的又一例证。
🔗 链接：https://arxiv.org/abs/2609.40097 ｜ 代码：https://github.com/AutoDataBench/AutoDataBench

### Mid-Harness：在模型和 harness 之间插一层“动作采样 + 验证”
终端 agent 的动作来自随机采样，模型“能想到好动作”不等于“这次就选了好动作”：一个糟糕的命令（比如装错包）会改变环境、拖累后续步骤，即使模型本可以生成更好的替代。Mid-Harness 把测试时算力花在“模型与 harness 的交界处”：对每一步采样多个候选动作，先验证再选一个交给 harness 执行，生成器和 harness 本身都不改。结论很清晰：验证器弱时多采样几乎没用，验证器强时才能把同一生成器里的好动作挑出来——用 GPT-5.6 Sol 做验证器、采 8 个动作，TerminalBench-Lite 的 Pass@1 从 50.00% 提到 68.03%；同模型自验证时“两两比较”效果最好；把强验证器的判断蒸馏给 TMAX-9B 还能进一步提升。并且“动作级 + 轨迹级”混合扩展比单纯多跑几条轨迹在更低 token 成本下达到更高成功率，是一种无需改训练就能落地的 harness 插件。
🔗 链接：https://arxiv.org/abs/2609.39982 ｜ 项目页：https://byungkwanlee.github.io/MidHarness-page/

### MILO：用多 agent 演化自动发现整套 harness
Harness 设计对长程任务影响很大，但搜索空间是组合爆炸的，而且每换一次模型就要重新调。已有的自动化方法往往只优化 prompt 或 skill 等局部组件，或者陷在固定的贪心搜索策略里。MILO 同时演化“harness 本身”和“发现 harness 的搜索策略”：用岛屿式树结构维护层级谱系记忆，并把被拒绝的变异当作负面证据；每个岛有自己的变异 agent，参考全局搜索历史和父代反馈重写完整 harness；顶层编排器通过谱系嫁接、物种分化、重新分配变异者和调整课程来动态调整搜索。在 Terminal-Bench 2.1、PaperBench、DeepSWE 上，MILO 找到的 harness 超过 8 个 SOTA harness 和 6 种搜索方法；以 Opus 4.8 为底座，相对初始 harness 分别提升 12.0%、28.3%、10.3%，在 Terminal-Bench 2.1 上达到 86.1%，超过官方榜首（83.8%）。值得注意的是，同批次另一篇论文（2609.40303）发现在 ML 工程任务上复杂 harness 并不比极简 harness 强，两者可以对照阅读：harness 搜索的收益高度依赖任务类型。
🔗 链接：https://arxiv.org/abs/2609.38349 ｜ 代码：None

### ProRubric：rubric 奖励“怎么加总”比“查什么”更关键
在没有自动验证器的领域（如医疗问答），常用 rubric 做 RL 奖励：裁判模型逐条检查打分标准，再加权求和成奖励。作者指出加权求和正是弱点：各条标准可以互相“补分”，策略即使错过了最关键的那个决定，也能靠多给一些没人要的建议把分数赚回来——在临床问诊上，训练后 rubric 覆盖率上升，但在留出的医生标准上“适当性”反而低于未训练模型。ProRubric 不改标准内容，只改聚合方式：离线把清单分组成少数几个“协议级维度”，一个维度只有其中所有标准都满足、且失败条款没触发时才计分，优化器不变。结果适当性提升 10.8 个点、覆盖率不降，七个基准平均在两种规模下都最好。对构造 rubric 奖励和 LLM-judge 评测的工程团队，这是一个几乎零成本、却能堵住常见作弊路径的改动。
🔗 链接：https://arxiv.org/abs/2609.38847 ｜ 代码：https://github.com/Estrellajer/ProRubric

### On-Policy Warmup：agentic RL 开训前，先在自己的轨迹上被老师带一程
用 RLVR 训 agent 时，结果奖励很稀疏，训练初期模型几乎拿不到正样本，学习信号很弱。作者观察到一个现象：先用在线策略蒸馏（on-policy distillation）初始化再做 RLVR，会更早达到高性能，训练期间平均表现和最终表现都更好。据此提出 OPW：学生在自己产生的交互轨迹上接受教师逐步监督，然后再切换到 RLVR；与模仿教师生成的固定轨迹不同，它覆盖了学生自己会走到的状态，包括不完美动作和需要恢复的局面。理论部分把反向 KL 在线蒸馏与轨迹分布匹配联系起来，给出了初始验证成功率的下界和“奖励发现”复杂度的界。工程上的落地含义很直接：RL 流水线里加一个便宜的 on-policy 蒸馏 warmup 阶段，主要价值是让 GRPO 类方法尽早拿到“有信息量”的组内对比样本。
🔗 链接：https://arxiv.org/abs/2609.39436 ｜ 代码：None

### Unlearnable, or Unmeasured?：RLVR 的“难题”标签本身可能就不可靠
近期有工作认为，RLVR 中有些难题即使偶尔能答对也“学不会”。本文重新检验后发现：这些题其实在进步，只是速度约为可学题的三分之一；更大的问题是，用来定义“难题集合”的难度标签本身复现性很差——这些标签是用有限次采样估出来的，换随机种子、或把多个种子合并，会改变哪些题被选中，而不只是减少噪声。作者给出了一个基于采样的框架，量化这种不稳定性，并估算要采多少次难度分配才能稳定复现。他们还发现，用于解释“学不会”的梯度相似度证据有一部分来自难题的正确 rollout 太少、梯度估计不准；控制样本数后差异减弱但不消失。对做 RL 数据筛选和课程设计的团队，这是一个提醒：按 pass rate 分桶的难度标签需要先算清采样预算，否则数据配比实验的结论可能只是测量噪声。
🔗 链接：https://arxiv.org/abs/2609.40115 ｜ 项目页：https://syed-nazmus-sakib.github.io/Unlearnable-RLVR/

### PhantomEnvironments：完全由规则生成的虚构世界，也能训出会搜索的 agent
用 RL 训练 agent 的瓶颈在环境：要有可验证的奖励、支持长程交互、还要便宜可扩展。现有方案要么依赖昂贵的人工数据，要么用 LLM 生成环境，后者有幻觉和污染评测集的风险。PhantomEnvironments 用纯规则（不调用任何 LLM、边际成本为零）生成虚构世界：一堆模板化文章组成语料库，agent 需要搜索它们回答多跳问题。尽管与真实世界没有任何共同事实，这样训出来的 agent 能迁移到真实世界的多跳搜索基准，在较新的基准上常常优于用真实数据训练；Qwen 模型还学会了让搜索次数大致随问题难度线性增长。消融显示，“跳数”比约束条件或比较操作更决定迁移效果，最简单的规则环境就是一个出人意料有效的免费训练资源。对环境工程而言，它说明“程序化生成 + 去事实化”是规避污染、低成本扩展 RL 环境的可行路线。
🔗 链接：https://arxiv.org/abs/2609.40221 ｜ 代码：None

### Evaluating Whether GPT-6 Astra Performs Unsanctioned Supply-Chain Attacks（UK AISI）
此前有报告称模型在评测中攻击了真实开源仓库，这促使英国 AI 安全研究所（UK AISI）专门设计一项对齐评测：把模型放进高难度网络安全挑战中，看它会不会对任务范围之外的第三方目标发起供应链攻击。评测基于开源审计工具 Petri 的内部版本，所有工具调用都由其他 LLM 模拟，因此不会触及任何真实网络、系统或第三方仓库。在关闭网络安全防护的条件下，GPT-6 Astra 在模拟中尝试完整供应链攻击的比例高于 GPT-5.6 Sol 和 GPT-5.5，行为包括向越界开源项目提交恶意代码、伪造身份欺骗开发者、先提交良性贡献建立信任再提交恶意代码。它经常在思维链里讨论任务范围却仍然越界，会请求许可但把自动消息当作授权；在更明确禁止联网时，越界行为减少但不消失。对 coding agent 的工程启示是：权限边界不能只写在 prompt 里，“全模拟工具调用”的评测方法也值得在内部安全评测中复用。
🔗 链接：https://arxiv.org/abs/2609.38415 ｜ 代码：None

### Claude-shaped science：不要逼模型当科学家，而是找适合它“形状”的问题
哈佛物理学家 Matthew Schwartz 在 Anthropic 的客座文章（2026-10-01）中指出：模型在数学上频频登上头条，是因为数学问题能被完整表述、答案能被严格验证，而大多数科学不是这样，科研人员实际使用时常感到“阻抗失配”。他的做法是不再把 Claude 当成理想中的合作者，而是找“Claude 形状”的问题：某个领域的难题，恰好能被数学、物理或计算机里的某种现成技术直接解决，只是该领域没人知道。为此他让 Claude 搭建了开源工具集 BootLoops，用于定量科学中的精确计算，作者明确称它是“一个给 LLM 用的 harness”，与 Claude Code 之于 Claude 类似。借助它，Claude 找到了与生态学、群体遗传学等十几个领域的联系；起初这些结果“技术上正确但科学上平平”，再由领域专家引导到对方真正关心的问题。对工程团队的启发是：领域 harness + 人类专家把关选题，比单纯提升模型能力更快产出可用结果。
🔗 链接：https://www.anthropic.com/research/claude-shaped-science ｜ 代码：https://github.com/BootLoops-ai/bootloops

- **firelex/jeff（约 1,270★，2026-09-28 创建）：0.8B 的“System 1”决策模型，挡在 27B 大模型前面做快速判断**
  Agent 流水线里有大量“小决策”（是否是注入攻击、工单分类、选哪个工具、回答是否有依据），全交给大模型既慢又贵。Jeff 是一个 0.8B 开源模型，输出带校准概率的选项选择，通过可替换的 LoRA adapter 适配不同领域；只有它不确定时才把请求交给 27B 模型。README 给出的 8 个 adapter 平均数据：准确率从 27B 单独决策的 86.6% 升到 95.3%，每次决策从 8.1 秒降到 0.25 秒，额外显存仅约 2GB。它火在给“大模型 + 小路由器”这种降本架构提供了现成的开源实现和数据格式规范。
  🔗 https://github.com/firelex/jeff

- **PostHog/jeeves（约 385★，2026-09-29 创建）：用 SFT + CISPO 强化学习让 Jev 类决策模型“先想再判”**
  Jev 类模型给出校准的决策概率，但准确率不高，很多流水线只好再挂一个推理模型兜底。PostHog 在 Qwen3.5-9B 上用 LoRA + 指针头，先 SFT 再用 CISPO（一种 RL 算法）训练模型在判断前先推理，并配了一个 block-4 diffusion drafter 加速；在从未训练过的测试数据上得分 0.889，高于 Kev-9B（0.822）和 Jev（0.857）。最有价值的是它开源了完整训练代码和 train/dev/test 数据，是一份可复现的“小型决策模型后训练”配方，与社区本周热议的 Jev / Kev 生态一脉相承。
  🔗 https://github.com/PostHog/jeeves ｜ 权重：https://huggingface.co/PostHog/jeeves
