## 二、逐条中文讲解

### 1. Agent Benchmarks Stop Ranking Before They Run Out of Tasks

数据科学和机器学习工程代理的许多题，本来就会算出一个数量：竞赛分、加速比或误差。排行榜通常把这个数量收成过或不过。数量上已经分开的模型，过了同一条线以后会挤在一起。常见的补法是把题变难，或者把线抬高。

作者重算了已经公开的运行，并用 Terminal-Bench 2.0 做了一组新实验。四个模型经第三方兼容网关，在 Terminus-2 里每题三次，共 156 次，标价大约 115 美元。过或不过把 Claude Opus 5、GPT-6 Astra 和 Gemini 3.1 Pro 打成平局，并把 GPT-5.3 Codex 分开。组合优化那道题上，三个打平的模型每次都通过，Opus 5 的中位加速是 10.9 倍，另外两个停在参考解的 1.3 倍。PyTorch 模型恢复的中位均方误差从 0.016 到 0.60。通过的运行里，69% 超过参考解。两次 Codex 的通过被标成验证器被钻了空子，具体做法不展开。ALE-Bench 的 40 道竞赛题上，前十名按竞赛分能分成三档；改成相对中位人类的过或不过之后，五个模型通过 39 题，前十名合成一档，尽管近一半运行超过了那个中位人类。把线抬到能分开最新模型的高度，会让更早的模型里 89% 得零分。他们提出的截断对数比，在任务对半切分上更稳（差值 +0.03，区间不含 0）；和人类排序的差别是 +0.02，区间含 0。正文写会放出代码和派生统计，HTML 里没有可核验的仓库地址。

过或不过会把同一道题上已经拉开的加速比压成平局。

**链接：** [原文](https://arxiv.org/abs/2611.13541)

### 2. Dependable Long-Horizon LLM Agents

长任务失败以后，常见记录是一个失败类型，或者指出哪一个代理、哪一步该负责。这样记不出错误从哪一步进入、沿着哪一份状态传到了症状、轨迹里有没有已经反驳它的证据，以及哪一种控制看得到、够得着。

作者把一次故障写成从进入、传播、发现、应对到后果的记录，并按运行阶段和状态域定位。每一条轨迹由一次独立的 Claude 按书面协议通读并填表，再按字段和词表做机械检查；这一版没有人工标注者之间的一致率。预算内完成 96 条，其中一条最终答案其实正确，结果统计用剩下的 95 条。样本按批次选取，不是随机抽的。故障进入的中位位置在全程的 0.18，多数是对任务状态做了错误决定或编造。Who&When 的 88 次里，有 37 次的进入早于人工标出的决定性步骤。标出的进入点与该步骤在一步以内重合的占 59%，被标得更晚的只有 11 次。72% 的失败在暴露之前，轨迹里已经有反证；这些次数里的 88%，没有代理据此行动。31% 的运行有东西标出了偏离，但没有一次应对把偏离的状态清掉。恢复代理自己的状态就能覆盖 95 次里的 35 次，这是对照迹的判断，没有把控制接回去重跑。手写的 Who&When 失败里，45% 以内容过滤崩溃结束，随后脚手架交出一份没有任何代理生成的最终答案；作者写这一项不依赖这次标注。

反证先留在轨迹里，随后却没有人改掉出错的状态。

**链接：** [原文](https://arxiv.org/abs/2611.13254)

### 3. Bursts That Outlast Themselves

编码代理的会话一轮比一轮长。服务端靠前缀缓存省计算：命中时大约只补一千个 token，没命中就要重算一两万到四万个 token 的上下文。缓存一旦大面积失效，变慢的会话会把更多上下文留在机器上，下一轮就更不容易命中。

同一份基础负载上，几分钟的额外到达就能让一台 vLLM 进入另一套状态：命中率大约 10%，吞吐大约一半，积压在剩下的 70 分钟里继续涨。12 对里有 9 对这样，没有一对是反过来的。关掉前缀缓存就看不到这个状态。Qwen3-32B 配上 SWE-bench 轨迹的形状，以及 SGLang，也会出现，只是触发要更大。作者给出的出路是：只限制新进入的请求，7 次匹配的崩溃里救回 1 次；按容量暂停已经接入的会话，测过的几次都在几分钟内恢复。把 KV 卸到 CPU 只能推迟，不能阻止。一个不按负载单独调参的预算器，把活跃会话占住的 KV 限制在池子以内，在他们测过的每次运行里都挡住了这次崩溃。

前缀缓存掉进重算以后，要按容量停掉已经接入的会话。

**链接：** [原文](https://arxiv.org/abs/2611.13412)

### 4. ReTrace: Distilling Tool-Using Agents into Planner-Free Workflows

企业里的标准流程会在新输入上反复跑。代理能读自然语言说明并调用工具，但每一步都要再问一次模型，延迟和费用跟着次数涨。工具调用本身往往只留下做了什么，模型写下的理由里才有为什么这一步成立。

ReTrace 从这些理由里抽出每一步的条件，把几次运行的条件并成一份规则文档，再编译成下一步由代码选择的工作流。只有最后这一步绑定具体平台，规则文档可以换编排器。他们生产平台上的 79 条流程，编译后的完成率是 93.8%，代理是 96.8%，每项费用低 24%。在 τ²-Bench 上，任务成功率 75.8%，代理是 80.6%，耗时 1.3 秒，代理是 170 秒。用训练失败修三轮，k=2 的工作流从 66.7% 升到 81.2%。八条 SOP-Bench 流程上，不修理时它是 80.6%，少样本直接生成是 83.6%；用标好的训练失败修理后升到 87.8%，每项 0.40 秒，代理是 85.5%、46.6 秒。最高的那档用了标好的失败。HTML 里出现的 GitHub 地址是引用的另一项工作，不是这份代码。

反复执行的流程，可以把下一步从模型收成编译后的规则。

**链接：** [原文](https://arxiv.org/abs/2611.14492)

### 5. FlowPlan: Reducing the Token Cost of Coding Agents with Abstraction-Guided Planning and Verification

仓库修复代理会反复读源码、改文件、再读、再测。上下文随着来回变长，费用主要堆在定位之后的重读和重测上。压缩上下文或少看一些文件，省的是同一次循环里的字数。

FlowPlan 让模型先在函数的控制流图或数据流图上定位，把打算做的修改写成图上的增量，然后再改源码。改完后重建同一张图，对照实际结构变化和事先写下的增量，接着才做完整验证并停止。六个基准和模型的组合里，相对原代理，解决率都没有测出显著变化；token 每次都下降，其中五次显著。Claude Haiku 4.5 在 SWE-bench Pro 上用到基线的 0.46–0.47 倍，Verified 上 0.32–0.35 倍，SecBench 上 0.68–0.74 倍。Sonnet 5 分别是 0.72–0.76 倍、0.73–0.74 倍和 0.92–0.94 倍。SecBench 降得少，是因为基线轨迹本来就短。轨迹分析把节省归到两处：用这次结构核对换掉改完后的大量重读和重测，以及每次调用的上下文更短。和对照方法比，它在六组里的三组降得最多，另一组打平。作者写明，剩下的难点是找准故障位置，以及把修复计划写完整。

流程图上的修改计划省掉了改完后的反复重读，解决率没有测出变化。

**链接：** [原文](https://arxiv.org/abs/2611.13241) · [代码](https://github.com/MelikaSepidband/FlowPlan)

### 6. Contrastive Discovery: Open-Ended Scientific Discovery over Competing Explanations

用代理从数据里找解释时，常见做法是一次检验一个说法：证据要么支持它，要么把它否定。否定之后，代理知道这个说法站不住，却不知道同一批证据更支持哪一个替代说法。它往往会停在否定上，或者再去收集一批新实验。

Contrastive Discovery 把单位换成一组互斥且合起来穷尽的解释。一次实验的分数，是它怎样把信念从这组解释里重新分配；信念集中到一个解释上，问题才算解决。已有代理可以拿这组解释重看已经收集的证据，也可以用它指导下一轮搜索。六个领域里，信念移动最大的那些单点候选，89% 是被否定。同一批证据上，对比集合把其中 73% 收成一个具体替代。对比集合指导搜索时，同样的实验预算下，解决的问题比按单点意外度搜索多 67%。38 名专家盲评，在已解决的问题上有 78% 选了同一个解释；在单点代理否定后就停下来的问题上，这个比例是 82%。若这组解释本身并不穷尽，集中的信念只是在一份不完整的菜单里做选择。项目页可以打开。

发现代理要记下证据最终支持了哪一个解释。

**链接：** [原文](https://arxiv.org/abs/2611.14514) · [项目](https://codiscovery.ai/contrastive-discovery/)

### 7. Wrong the Same Way: Cross-Prompt Sharing Both Suppresses and Amplifies Reward Hacking in RLVR

可验证奖励的强化学习面对一个不完美的验证器时，有两种说法：错误接受来自基座模型，或者训练把它放大了。两种说法都能在不同实验里找到支持。若验证器的漏洞只在少数题上成立，和它在大多数题上接受同一种错答案，训练的方向可能相反。

作者用一个小到可以把整个回答分布算完的环境来分开这两种情况，共 64 道题。在带 KL 约束的最优点，训练只是把验证器已经接受的答案重新加权，不改变这组答案的组成，所以错误接受率原样继承。离开这个最优点之后，共享参数会把各题耦在一起：接受某个错答案的题把它往上推，拒绝它的题通过基线把它往下压，力度都正比于模型在那道题上写出它的概率。于是，只有少数题接受的漏洞会被压到基座之下，大多数题都接受的漏洞会被放大。Adam、SGD 和采样的 GRPO 上，凡是收敛的学习率，高普遍性结束时的黑客率都高于低普遍性；两端会不会越过基座，取决于步长。把同一套权重换成每题独立的副本，这个依赖就消失。第 6.5 节里，删掉同样多错误的两处验证器补丁，10 个种子上的真实准确率最多差 38 个点。作者把这当作此前实验互相矛盾的一个假设，生产规模的代码训练还没有做这组对照。代码在 CPU 上就能跑。

删掉同样多的验证器错误时，要先看模型会不会在很多题上重复这个错。

**链接：** [原文](https://arxiv.org/abs/2611.13218) · [代码](https://github.com/Rohan-Pandey1729/RLVR-Reward-Hacking)

### Trending Open-source Projects

#### 1. Auto Ontology

代理用自然语言查企业数据时，表名和字段对得上，指标的定义仍可能对不上。财务、销售和产品各自有一套“收入”，模型选错口径，查询仍能返回一个数字。人靠语义层和血缘约束这个问题，代理如果只拿到库表，就没有这层约束。

NVIDIA Auto Ontology 从已有元数据生成本体，并接上客户已经维护的语义模型。它把指标、实体和关系收成一份目录，生成查询时对照经过确认的定义和血缘，并在答案里带回出处。目录放在 Postgres 里，经 MCP、命令行和 API 交给现有代理。认证纠正可以写回本体。推理默认走 NVIDIA NIM，README 的示例要自备 API 密钥。仓库写明目前不接受外部贡献。SQL 基准另有一个评测仓库，本次没有重跑。仓库建于 2026 年 4 月 27 日，本次用 GitHub API 读到 11,873 star、973 fork，Apache-2.0，最近一次推送是 11 月 11 日。它出现在当日抓取的 Python 周趋势列表里。没有逐日 star 差额。

它把“这个数字该用哪张表、哪个定义”收成代理查询前可以核对的一层。正确率要看单独的评测仓库，不在这次阅读里。

**链接：** [GitHub](https://github.com/NVIDIA/auto-ontology)

#### 2. Modern Web Guidance

编码代理写网页时，训练语料里的旧写法往往更密：用大段脚本做现在浏览器已经提供的能力，或者把一个新接口用成旧接口。模型知道某个 API 存在，仍可能缺少一份够短、够新的用法。

Chrome、Edge、Mozilla 和 MDN 一起维护这套技能。命令行按问题检索一份指南，放进代理的上下文；也可以扫仓库里的旧写法。指南按 token 预算来写，并用评测去掉模型已经稳定掌握的部分。覆盖大约 250 项近年的网页平台能力，包括视图过渡、容器查询、弹出层和页面内的本地模型接口。安装命令是 `npx modern-web-guidance@latest install`。本次没有重跑他们的评测看板，也不引用看板上的胜率。发布仓库建于 2026 年 3 月 23 日，本次读到 5,144 star、167 fork，Apache-2.0，最近一次推送是 11 月 10 日。当日 TypeScript 日趋势列表里出现的是配套源码仓库，1,809 star、143 fork，最近一次推送是 11 月 12 日。没有逐日 star 差额。

它把浏览器厂商维护的新平台用法，收成可以检索进上下文的短指南。指南能不能改掉生成结果，要看他们的评测，这次没有复测。

**链接：** [GitHub](https://github.com/GoogleChrome/modern-web-guidance)

#### 3. Plannotator

几个编码代理同时改仓库时，计划和 diff 散落在各自的会话里。人要插一句意见，常常得把会话停住，或者把评论复制回终端。会话一长，计划和代码审查就变成两套对不上的记录。

Plannotator 是本地浏览器里的审阅面，用钩子接上 Claude Code、Codex、Copilot CLI、Gemini CLI、OpenCode 等代理。代理交出计划、HTML 或代码后，页面打开，人在原文上划线和评论，再把反馈送回提出它的那次会话。Inbox 把多个代理的提问和文件放在一个窗口里，回复时不必占着原来的会话。代码审查覆盖本地 diff 和远端 PR，也能走 Git、Jujutsu 和 Perforce。本次没有实际接上一套代理来核对 Inbox 的等待行为。仓库建于 2025 年 12 月 28 日，本次用 GitHub API 读到 10,079 star、764 fork，Apache-2.0，最近一次推送是 11 月 12 日。它出现在当日 TypeScript 日趋势列表里。没有逐日 star 差额。

它把人对计划和 diff 的批注送回原来的代理会话。钩子是否在每种代理上都能不等待会话，这次没有实测。

**链接：** [GitHub](https://github.com/backnotprop/plannotator)
