## 逐条讲解

### AgentBug-Smith：自动复现真实 harness bug，建出“活的” Live-Harness-Bench
Agent 的 harness（模型外面那层负责调工具、管上下文、跑循环的框架代码）本身也会有 bug，而且这类 bug 很特别：常常跟模型输出的不确定性、工具调用时序、上下文截断纠缠在一起，传统软件的 bug 复现方法不太好使。此前针对 harness bug 的基准只有少量、固定的样本，而且每个都要人工花大量时间搭环境，构建成本动辄几百人时。AgentBug-Smith 的做法是持续去开源 agent 系统的 issue 里“捞” bug，自动生成能稳定触发它的复现脚本，相比通用 bug 复现方法成功率高 10.67%–27.56%。用它跑出来的 Live-Harness-Bench 目前有 200 个可执行 harness bug，并且可以随着社区新 issue 持续扩充，天然抗数据污染。作者还演示了两种用法：一是拿来评测现有 SWE agent（结果显示修 harness bug 的能力很弱），二是把已修复的 bug 当知识库蒸馏出“修复技能”，让 agent 的 harness bug 修复率提升 6.32%。对后训练工程来说，这是一条“把线上真实失败自动变成可执行评测样本 + 训练知识”的流水线范例，和我们做 SWE 数据时从 issue 挖样本的思路完全可复用。
🔗 链接：https://arxiv.org/abs/2609.37864 ｜ 代码：https://github.com/EaminC/AgentBug-Smith

### SkillGym：从网上 skill 自动造可验证环境，再用轨迹 SFT 教模型“会用 skill”
Skill（一份写给 agent 看的专业操作手册 + 脚本，比如 Claude Skills）已经是各家 harness 的标配，但“怎么造训练数据让模型学会读、会用 skill”几乎没人系统做过——很多模型拿到 skill 也不看。SkillGym 搭了一条全自动流水线：先从互联网爬大量 skill，只留下能离线可复现运行的；再用“builder 出题 + reviewer 审题”的双 agent 流程，按难度构造四类任务，每道题都配参考解和可执行 verifier（自动判对错的脚本）。最终产出 6.8k 个环境、19k 条验证通过的成功轨迹，直接用于 SFT。效果上，2B 到 122B 多个家族的模型在四个 skill-use 基准上都涨分，Qwen3.5-9B 微调后在其中两个上超过了未训练的 397B 模型。最有意思的分析是：训练后模型“读取相关 skill”的比例从 28% 飙到 96%，说明收益主要来自养成了查手册的行为习惯，而且对训练中少见的任务类型和没见过的 skill 也能泛化。这是一份非常完整的“环境合成 → 轨迹采集 → 过滤 → SFT”工程模板，对做 coding agent 工具/skill 使用数据很有借鉴价值。
🔗 链接：https://arxiv.org/abs/2609.37539 ｜ 代码：None

### Do Agent Benchmarks Do What They Say?：用“可执行契约”审计工具型 agent 基准
工具型 agent 基准（如 tau2-bench、AgentDojo）在打分时有一个隐含假设：模拟工具真的做了它接口文档里宣称的事，评分器依据工具“报告自己做了什么”来判对错。如果工具实现本身有 bug，这个缺陷会在每次重跑时都稳定存在，分数看起来很“稳定”但其实是错的，而现有基准审计的分类体系里甚至没有这一类。作者把每个工具的接口描述当成一份“可执行契约”，用静态检查 + 动态探测去比对实现是否符合契约，并顺着任务文件和评分代码追溯：哪些分数依赖了缺陷工具本该写入的状态。在 4 个基准的 34 个会改状态的工具里确认了 7 个工具缺陷和 1 个评分器问题；例如 tau2-bench 电信域的评分器会奖励“给停用号码充值”这种错误行为，而某临床基准的工具在“设计上不写入”的情况下仍告诉 agent 写入成功，导致评分只是在检查请求格式。对做评测工程的人来说，这提醒我们：基准的 verifier 和模拟环境也需要被测试，“环境正确性审计”应该成为 RL 环境上线前的标准步骤。
🔗 链接：https://arxiv.org/abs/2609.37315 ｜ 代码：https://github.com/rohithreddybc/tool-contract-conformance

### ReviveBench：让 coding agent 复活“跑不起来的老软件”，顺便审计出 28 个 verifier 缺陷
现实中大量科研/工业软件因为依赖版本不兼容、核心模块被删、构建系统过时而“死掉”，复活它们是非常真实的工程需求，但现有基准很少覆盖。ReviveBench 设计了两类任务：10 个“复活”任务（起始工作区全部无法通过验证，涉及依赖冲突、缺失模块、遗留构建甚至 GPU 基础模型），以及 13 个“按公开规格重建工业引擎”的任务（数值、几何、硬件、事务系统，如 CAD、CRM）。它用隐藏 verifier 打分，并且这些 verifier 是对照原生运行环境、成熟工程工具或专门写的参考实现校准过的；为防数据污染，还做了标识符混淆实验（相似度从 0.51–0.96 降到 0.03–0.44，通过率不变）和知识截止后新仓库实验。最强模型在每个复活任务上至少一次跑通。但最有价值的发现在“评测本身”：构建与审计过程中发现了 28 个 verifier 缺陷（24 个假阴性、2 个假阳性），作者据此给出三条实用自检：验证规定方法是否真能达到判分阈值、看多个独立候选之间是否一致、从提交产物重新计算诊断指标。这和上一条论文形成呼应——可执行 verifier 本身就是测量误差的重要来源。
🔗 链接：https://arxiv.org/abs/2609.36161 ｜ 代码：None

### LoLBench：从 5,000 字设计提案到 5,500 行 PR 的长程开发评测
现有长程 coding 基准大多给出详细规格，只考察 agent“照着写对代码”的实现能力；但真实的模块化开发中，开发者先拿到的是一份高层设计提案（类似 RFC / KEP），需要自己理解意图、定位到庞大代码库中的相关部分，再推导出具体规格。LoLBench 正是评测这条“提案 → 实现”的完整链路：100 个任务、29 个大型软件系统、5 个领域、多语言，平均提案约 5,000 字，系统规模约 240 万行代码，参考 PR 平均改约 5,500 行。在 28 个 agent 上，最好的只解决 14% 的任务，Fail-to-Pass 测试通过率 52.7%。失败分析指出“代码定位不完整”是主要瓶颈：如果额外提供从参考实现推出的文件树和 API 规格，解决率提升 16–22 个百分点，但最高也只有 34%。这说明“感知（理解意图、找对位置）”与“实现”都还是硬骨头，也为后训练数据提供了方向：需要更多“从设计文档到大规模改动”的长程轨迹，而不只是 issue 级小修补。
🔗 链接：https://arxiv.org/abs/2609.37143 ｜ 代码/数据：https://huggingface.co/datasets/lolbench26/LoLBench

### WitnessGym：自动构造“bug 见证”基准，考 agent 能否写出触发 bug 的可执行证据
审计报告说“这里有 bug”，开发者第一反应是“证明给我看”——bug witness（一个具体输入 + 测试 harness，执行时能暴露错误行为）就是这种可执行证据。但评测 agent 写 witness 很难：复用历史公开 bug 有污染风险，手工构造又贵。WitnessGym 用“注入 bug”的方式自动造题：只在真实项目中被测试覆盖到的路径上注入 bug，重新构建项目，并且只保留构造时就能被一个 witness 暴露的样本，保证每题可解；再通过“保持 bug 不变的代码变换”改变周围结构，以控制难度、抗记忆。基于真实 Java 项目自动生成 1,300 个用例，盲测中模型很难分辨注入补丁与历史真实 bug 补丁。在 6 组 agent 框架/模型组合上的评测显示，即使已知 bug 模式，构造 witness 依然困难。对于数据工程来说，它提供了一套“注入 + 可解性过滤 + 等价变换增广”的可扩展造题方法，也可直接迁移成 RL 训练环境。
🔗 链接：https://arxiv.org/abs/2609.36635 ｜ 代码：None（作者称框架、用例与评测脚本已公开）

### UserProxyBench：评测“扮演用户的那个模型”是否演对了
tau-bench 这类交互式基准和多轮 RL 训练里，都要用另一个 LLM 扮演用户；它决定 agent 什么时候拿到什么信息，但现有基准只给 agent 打分，从不检查“用户”有没有按剧本演。UserProxyBench 在 tau-bench 家族之上加了一层评测，提出用户保真度分数 UFS：用任务相关的 rubric 检查用户是否遵守了基准私有的用户指令，且独立于 agent 是否成功。实验中固定 agent 为 GPT-5.5，只换 user proxy，375 个企业任务的平均奖励就变动 15.2 分；24.4% 的成功回合里用户违反了设定。最常见的问题是“过早透露”：用户在被问之前就把信息给了，这对奖励影响不大，却让 agent 平均少调 1.06 次工具——也就是说你以为在评测“信息收集能力”，实际被模拟用户放水了。作者还在 7 个 proxy 上画出成本-保真度前沿，帮助选“够用且最便宜”的模拟器。做多轮 agent RL 的团队应该把 user simulator 的质量当成环境质量的一部分来监控。
🔗 链接：https://arxiv.org/abs/2609.38043 ｜ 代码：None

### CRJudgeBench + Sentinel：识别“看似合理但技术上错误”的 code review 评论
LLM 写 code review 评论已经很流畅，但流畅不等于正确：评论里的技术论断可能根本不适用于当前仓库上下文，反而误导开发者。现有 code review 基准主要评“生成评论”“发现问题”或整体质量，没有直接考“判断某条评论在技术上是否可信”。CRJudgeBench 从真实 PR 出发，加上专家验证过的扰动，构造了 1,199 个实例，覆盖可信评论和“看似合理实则不可信”的评论。作者还训练了 Sentinel：一个会主动去仓库里查代码证据再下判断的 agentic judge，从 Qwen3-Coder-30B-A3B 起步，用“特权教师”（看得到答案信息的老师模型）做逐动作的迭代学习。在 359 条测试集上 Sentinel 准确率 76.60%，比 GLM-5.3 高 6.13 分、比基座高 19.78 分。对后训练工程而言，“review 评论可信度判断”恰好是 AI code review / reward model 的关键能力，这套数据构造 + 特权教师蒸馏的配方可以直接参考。
🔗 链接：https://arxiv.org/abs/2609.37216 ｜ 数据：https://huggingface.co/datasets/dcloud347/CRJudgeBenchmark

### WEFT：不只扩环境，而是整体演化“环境 + 任务 + harness + 评估器”
过去一年扩展 tool-use 后训练的主流做法是大量合成可执行环境，但作者指出：环境只是 agent 交互系统的一部分，任务、harness、评估器之间如果不协调，单纯堆环境数量并不能换来对应的效果提升（比如评估器和环境状态对不上，学习信号就是噪声）。WEFT 把四者当成一个整体来构建：在环境广度、任务复杂度、交互多样性上同时扩展；再用“执行驱动的自我演化”——根据执行轨迹和状态证据定位失败是哪个组件造成的，针对性修改，再用新 rollout 验证修改是否有效，循环迭代。训练侧也做了工程保障：前缀保留采样保留已验证的进度、原子轮次级信用分配精确定位学习信号，MegaMCP 为并发 rollout 在共享工具服务上维持隔离、可恢复的状态。WEFT-14B 在 BFCL V4、τ²-Bench、Claw-Eval 上分别比 Agent-World-14B 高 6.41、2.23、12.27 分，35B-A3B 版本还延伸到 Toolathlon-Verified、AutomationBench 等长流程基准。对搭建 agentic RL 环境的团队，“用执行证据给组件归因并自动修复”这一闭环很值得照搬。
🔗 链接：https://arxiv.org/abs/2609.36887 ｜ 代码：None

### XRepoSkill：从成败轨迹的分叉点挖出可跨仓库迁移的 SWE 技能
给 SWE agent 加“从过往经验蒸馏出的技能”已经很常见，但这些技能换个仓库常常失效。根本原因是：成功轨迹中出现的行为不一定是成功的原因，它可能只是巧合，或者只是模型的习惯动作。XRepoSkill 把技能表示成一组“在什么时机做什么动作”的规则：先对比同一 agent 在同一 issue 上的成功和失败轨迹，从两条执行路径分叉的地方提取候选规则；每条规则配一个可执行谓词，能在其他轨迹上自动判断该行为是否发生；只有当规则与成功显著相关、且在多个仓库中反复出现时才保留，再把仓库特定的变体合并成通用规则。技能从 SWE-bench Verified 排行榜公开轨迹中学习，在 SWE-bench Pro 和 DeepSWE 上用三家厂商的模型评测（评测仓库均不在学习池中），六种组合全部最优；在 DeepSWE 上比无技能基线高 10.3 分、比最强技能学习基线高 5.0 分。它的“成败对比 + 可执行谓词 + 跨仓库复现”过滤思路，同样可以用于筛选后训练轨迹中真正有因果作用的行为。
🔗 链接：https://arxiv.org/abs/2609.36807 ｜ 代码：None

### LatentSift：用 policy 自己的隐状态给 SWE 候选轨迹做“零 token”预筛
测试时扩展（同一问题生成多条候选轨迹再挑最好的）能明显提升 SWE agent，但挑选本身很贵：常见混合流程先用一个 LLM 做免执行（execution-free）验证器过一遍所有候选，再跑测试，验证消耗的 token 几乎和生成一样多。LatentSift 把第一阶段换成“读 policy 生成时本来就有的隐状态”：把每个候选的推理、观察、函数调用三类隐状态，和训练时收集的成功/失败轨迹隐状态库比较距离，再与一个学习到的线性分数融合，只把有希望的候选送进后续执行验证。在 SWE-bench Verified 上，跨三种 agent、两种模型规模，免执行验证 token 减少 66.6%–81.0%，包含测试生成在内的总验证 token 减少 49.1%–62.1%（K=16），Best@16 不降反升（DeepSWE-Preview 从 59.26% 到 60.06%）。对 RL 训练里的 rollout 过滤和推理成本控制都有启发：训练时积累的成功/失败轨迹本身就是可复用的“验证资产”。
🔗 链接：https://arxiv.org/abs/2609.36371 ｜ 代码：None

### PACE：拆解异步 RL 的“陈旧度”从哪里累积
完全异步 RL 让 rollout 生成和策略更新并行，资源利用率高，但代价是 policy lag：轨迹生成出来时，训练器已经更新了好几个版本。常见做法是按版本差直接丢弃“太旧”的样本，但这会误伤长 rollout 或中途被打断的 rollout。作者把陈旧度拆成两段：生成阶段累积的 Generation Staleness，和生成完成后在样本池里排队等待累积的 Waiting Staleness。PACE 据此把样本池“超出部分的占用”转成自适应的拒绝预算，并用“等待陈旧度 + 前缀感知的生成陈旧度”组合打分排序，优先训练更新鲜的样本，同时不惩罚跨多个版本的长轨迹。这是典型的训练基础设施问题，对做长程 agentic RL（轨迹长度差异大、排队严重）的团队尤其实用。
🔗 链接：https://arxiv.org/abs/2609.36830 ｜ 代码：None

### VACE：模型权重和 harness 交替演化，但每次改 harness 都要过验证门
提升 agent 有两条路：更新模型权重（RL），或者改进 harness（提示、工具、流程）。两者相互耦合：权重变了，模型用 harness 的方式会变；harness 变了，用于训练的轨迹也会变。VACE 交替进行两件事：每个 RL 阶段结束后，复用收集到的轨迹提出一版 harness 修改，然后固定新模型，对比旧 harness 和候选 harness 的验证集表现，只有更好才采用并用于下一阶段训练。在 Qwen3.5-9B 上，OfficeQA 测试准确率 45.26%、AutomationBench 部分得分 75.19%，比只做 RL 分别高 6.43 和 9.09 分，比不加验证门的交替方案高 4.59 和 6.95 分。关键数据是：44 个 harness 提案中有 17 个会让验证表现变差，被门控拦下——说明“自动改 harness”如果没有回归检查，很容易把训练带偏。
🔗 链接：https://arxiv.org/abs/2609.37105 ｜ 代码：None

### PADMÉ：用小模型低成本合成“评估器元评测”数据
用 LLM 给 agent 轨迹打分（LLM-as-judge）已经很普遍，但怎么知道这个评估器和人类判断一致？这就是元评测问题：收人类标注很贵，绝对分数难对齐，再用 LLM 当元评估器又陷入“谁来评估评估者”的递归。PADMÉ 把问题改写成偏好判断：不比较人和 LLM 给同一轨迹打的绝对分，而是看两者对两条轨迹的偏好是否一致。在此基础上，它只用小模型、零人工参与、低算力合成按评估维度划分的元评测数据，原型在 4 个 agent 领域、3 个评估维度上合成了 1,000 条样本，并做了 150 条人工验证。对做 reward model / judge 的团队，这提供了一种便宜地持续校准评估器的数据来源。
🔗 链接：https://arxiv.org/abs/2609.36086 ｜ 代码：https://github.com/chc012/padme

### SYNTH（It's All Training）：完全合成、单阶段训练的开源配方
现在的预训练数据大多来自网页爬取，几乎不含显式推理过程，也不是为后续中训练、后训练设计的；前沿实验室用强模型生成的合成数据（如推理轨迹）来补，但这些数据都不公开。SYNTH 是首个开源的这类合成语料：以 58,698 篇维基百科条目为种子，通过结构化扩写，把预训练、中训练、后训练合并成一个训练阶段。作者训练了 56M、0.3B–0.6B 和 13B/1B 激活的 MoE 等模型，在同等算力下 SYNTH 优于过滤后的网页数据。它对“合成数据如何影响知识与技能获取”给出了可复现的开放实验平台，对我们思考“后训练数据能否前移”有参考意义。
🔗 链接：https://arxiv.org/abs/2609.37891 ｜ 代码：None

### Merged, Not Measured：agent 提的性能优化 PR，被合并不代表真的变快
很多 coding agent 会提交“提升性能”的 PR，但维护者如何对待这类 PR、它的性能宣称是否属实，几乎没人系统研究过。作者从 AIDev v4 的 71,677 个 agent PR 中筛出 6 个 agent 在 582 个仓库里修的 1,262 个性能问题，并实际重跑了 23 个被拒和 30 个被合并的修复。结论很扎心：57% 被合并，61% 的拒绝没有给理由；被拒的 23 个里只有 6 个宣称成立；被合并的 30 个中只有 18 个达到交付标准，9 个没有显著收益甚至变慢，14 个改变了未测试输入上的行为。是否被合并主要跟“这个 agent 在该仓库的历史合并率”相关，而不是修复内容本身；只有 11% 的修复带了性能测试。对于把“PR 被合并”当作训练奖励或评测信号的做法，这是一个重要警告：合并信号噪声很大，性能类任务必须配可复现的测量。
🔗 链接：https://arxiv.org/abs/2609.37985 ｜ 代码：None

### Formalizing Fermat's Last Theorem（Anthropic）
费马大定理的人类证明（Wiles 1995）长达上百页，社区从 2024 年起由 Kevin Buzzard 牵头用 Lean 证明助手做形式化，预期是多年工程。Anthropic 9 月 4 日公布：Claude 在约 11 天里基本自主地完成了首个端到端、计算机可检查的 FLT 证明，写了约 1,300 万行 Lean、证明了 29,500 个中间定理。Anthropic 强调这里的新意不在新数学，而在“验证”——像用计算器核对计算一样核对证明。对软件工程方向的启发是：这是一个超长程、强 verifier（Lean 编译器）约束下的 agent 工程案例，“可机器检查的奖励 + 长时间自主运行”的组合正在把规模推到百万行级别。
🔗 链接：https://www.anthropic.com/research/formalizing-fermats-last-theorem ｜ 代码：None
