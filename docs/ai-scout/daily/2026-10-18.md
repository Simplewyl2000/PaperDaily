## 逐条讲解

### GRADS：用"证据依赖图"控制合成数据的真实难度
做深度检索 / 长程 agent 的后训练，大家普遍靠合成数据：拿一个种子问题，不断"扩写"——加更多跳、更多证据——让它看起来更难。问题是"看起来难"不等于"真的难"：新加的证据和答案往往只是弱关联，模型可以绕过去，于是你以为造了一批 hard 样本，实际难度分布糊成一团。GRADS 的做法是在合成循环（选种子 → 扩展证据 → 构造问答 → 验证）里始终维护一张"推出答案必须经过哪些证据和推理步"的依赖图，每一步只基于相关子图生成，保证每条新增证据都是"不可或缺"的，同时不把无关上下文越堆越多。作者在安全、软件工程、科学文档三个领域验证：用独立求解器去测，GRADS 生成的任务难度分层是真正拉开的。在同等训练预算下，SFT 让任务"能收尾"的比例超过 95%、工具调用和轮数最多砍 75%，再做 RL 又省 19.5% 工具调用，最终 4B 模型在其软件工程留出集上追平 Sonnet 4。对我们最直接的启发是：**合成数据的难度标签应该由结构（依赖图）保证、并用独立求解器校验**，而不是靠"扩写次数"这种代理指标。
🔗 链接：https://arxiv.org/abs/2610.21167 ｜ 代码：None

### Interlock：把"每步都对、整体没做完"变成可合成、可验收的训练任务
长程 agent 有个常见失败模式：每个子要求单独看都满足了，但它们之间的关联没维护好——比如改了配置却没同步更新依赖它的脚本，结果"局部正确、整体未完成"。现有任务合成大多只描述"要做什么"，不描述"这些产物之间必须怎么咬合"。Interlock 把每个任务表示成一张类型化的"完成图"：grounding 边把公开证据连到决策，耦合超边表达跨组件的联合约束，realization 边把决策连到所有必须落地的下游效果；然后把这张图编译成一个可重置的工作区、一段给 agent 的公开需求和一份评测 rubric。为防止生成过程"丢需求"或"rubric 依赖了 agent 看不到的信息"，它加了两道审查（原始需求覆盖审查、公开输入可支撑性审查），最后由 agent-as-judge 检查执行产物、跑验证脚本，只保留满足全部必选要求的轨迹。用两款 Qwen3.6 在自己被接受的轨迹上微调后，AutomationBench 通过率 +4.0~4.5pt、JobBench +3.2~6.6、Harvey LAB +3.9~4.2。这套"图 → 工作区 + 需求 + rubric + 双审查"的流水线，基本就是一份可照抄的**长程任务数据工厂设计图**。
🔗 链接：https://arxiv.org/abs/2610.19686 ｜ 代码：None

### Explorer-Zero：不靠人工标注，让 agent 自己造任务和"分步奖励"
在有状态环境（比如 AppWorld 这种模拟手机 App 的世界）里训练 agent，最贵的是两样东西：人写的任务，以及可靠的验收器。自博弈（self-play）理论上能省掉人工，但难点在于自动生成的任务要"可完成、可组合"，而且只有 0/1 的成败奖励太稀疏，模型学不到东西。Explorer-Zero 训练一个"出题者"：它在环境里实际探索，一边构造任务，一边把中间状态和最终状态记录成验收检查点；"解题者"每完成一个子目标就能拿到部分奖励，两者交替训练，课程难度自动跟着解题者水平走。作者还从理论上说明了：子任务奖励能让"都失败了但失败程度不同"的 rollout 之间产生区分度，避免梯度坍缩。结果上，完全不用人工训练任务，在 ALFWorld、ScienceWorld、AppWorld 上都超过其他自博弈基线；AppWorld 上 30B agent 达到 59.67%，逼近用人工任务做 RL 的 62.65%，并且用它做初始化后再上人工数据 RL 还能进一步涨。对数据工程来说，**"探索时顺手录检查点 = 免费的稠密验收器"**这一招非常值得借鉴。
🔗 链接：https://arxiv.org/abs/2610.19868 ｜ 代码：None

### MLExpert：一套"造 Kaggle 任务 + 交互 harness + 窗口化 RL"的 MLE agent 训练配方
让模型自主做机器学习工程（读数据、做特征、调模型、看分数再迭代）被视为"AI 改进 AI"的入口，但训练很难：一次实验要跑很久，而每次实验的分数反映的是之前一串决策的综合结果，长轨迹里到底该奖励哪一段说不清。MLExpert 先搭了一个 Kaggle-MLE Factory，把竞赛批量转成可执行任务，并配一个"由模型自己组织实验"的交互 harness；训练分两步：分层 agentic SFT 用结果导向的监督把通用工具/编码能力迁到 MLE 场景，然后用 Windowed Interaction RL（WIRL）——把"两次实验结果之间的那段多轮决策"视为一个执行窗口，共享这次实验带来的结果奖励，相当于把一条超长轨迹切成很多段可归因的小段；再配合异步采集和策略校正，不必等整条轨迹跑完就能更新。35B MoE 模型在 MLE-Bench Lite 上的平均奖牌率从 37.9% 提到 72.7%，与 Kimi-K3、GLM-5.3 等更大模型相当，并能迁移到 agent 脚手架优化、算法优化等任务。对我们而言，**"按环境反馈事件切窗口分配奖励"**是长程 coding/实验类 RL 的实用工程解法，且代码已开源。
🔗 链接：https://arxiv.org/abs/2610.22344 ｜ 代码：https://github.com/InternScience/MLExpert

### Probe-and-Resume：critic 什么时候看、看什么，比搜索算法本身更重要
测试时搜索（比如 MCTS：每步多试几个动作，用一个 critic 打分挑分支）在数学推理里很有效，但作者在终端类 agent 任务上发现它几乎不涨分。原因有两个：agent 的观察只露出庞大系统状态的一小部分，critic 看不到评判所需的信息；而且中间状态本身就很难看出"这条路最后能不能成"——实测中间态 critic 排序只比随机好一点，给它环境访问权限也帮助有限。于是他们换了个思路：只在 agent 自认为"做完了"的节点才叫 critic，并且给 critic 一个当前状态和初始状态的**分叉副本**，允许读、写、执行，甚至做破坏性操作去把隐藏状态"捅出来"；critic 拒绝，agent 就从停下的地方继续干。在 Terminal-Bench 2.1 上，这比"MCTS + 常规 critic"高 8.4pt，接近同底模 Codex CLI 的成绩，但成本不到一半。对 harness 和 RL 验收器设计的启发很直接：**把验证放在"声明完成"的时刻、并给验证者沙箱级的主动探查能力**，远比在中途频繁打分有效。
🔗 链接：https://arxiv.org/abs/2610.21088 ｜ 代码：None

### EvalBuilder：能不能让 agent 自己把"贵的评测"压缩成"便宜的评测"
长程研究/工程类 agent 的评测非常贵：要跑很久、要人工专家判分。一个自然的想法是：给 agent 一个任务和一个昂贵的参考基准，让它造一个低成本的代理基准，只要能保住原基准的结论（模型排序、优劣判断）就行。EvalBuilder 把这件事正式定义成一个"元评测"问题，从三个维度打分：保真度（代理基准是否保住模型排名、能否泛化到没见过的模型和新采集的回答）、效率（成本降了多少）、鲁棒性（分数是否校准、是否有区分度）。它还提供一个迭代环境，让 agent 在固定时间预算内反复修改自己的基准。这项工作本身不是一个新榜单，而是**"评测构建能否自动化"的测试床**。对评测工程团队，它给出了一个清晰的验收标准：自动生成的评测集，必须在留出模型和新回答上保住原评测的排序，才算合格。
🔗 链接：https://arxiv.org/abs/2610.20099 ｜ 代码：None

### 基准饱和之后，还能从"解题过程"里读出能力差异吗？
基准一旦被刷到接近满分，就失去区分模型的能力，也就没法再支撑安全论证和前沿政策判断。但其实每道题除了"对/错"，还留下了一整份解题轨迹（推理过程、工具调用）。作者用历史基准和历史模型发布"倒推模拟"饱和场景：只拿已饱和基准上**做对了的**轨迹，看能否预测模型在未饱和留出题上的能力。比较了成对评判（让 judge 比较两份轨迹谁更强）、单轨迹绝对打分、基于确定性特征或 embedding 的预测几类方法，结果成对评判最好，预测误差比"只看饱和分数"的基线低 5.3 倍；能力信号主要集中在推理和工具调用这两段。但它也有短板：遇到分布突变（比如 2025 年初第一批推理模型出现）时会低估新模型。对评测工程的启示是：**评测平台应该完整保存轨迹**，它们是延长基准寿命的"二次矿藏"，但要配合分布漂移检测使用。
🔗 链接：https://arxiv.org/abs/2610.20667 ｜ 代码：None

### 3DCodeVerse：把 3D 内容生成变成"可执行、可验证的代码"问题
让 coding agent 生成 3D 内容（物体、场景）很有前景，因为代码形式的 3D 资产天然可编辑、可复现，但一直缺两样东西：大规模高质量的可执行 3D 代码数据，以及不靠人工就能自动验收的生成流程。3DCodeVerse 先构建了 3DCodeVerse-2M：从开源收集、把专用格式转换成代码、再用 coding agent 新生成，每个程序都打包好源文件、依赖资产、声明的运行环境和验证记录——这是典型的"可执行数据"工程。然后做了一个多 agent DAG harness，用执行检查、空间测量（尺寸、位置是否合理）和视觉反馈自动评估并修改程序，生成过程中无需人工反馈。在其数据上微调显著提升开源模型的 3D 编码能力；同样由 Claude Opus 5.5 驱动时，它的 harness 在人工成对评测中对 Claude Design（3D 物体）胜率 90%。对我们的价值在于：**"每条数据带运行环境 + 验证记录"**的打包规范和**"多模态信号做自动验收"**的 harness 设计，可迁移到其他代码领域的数据工厂。
🔗 链接：https://arxiv.org/abs/2610.22341 ｜ 代码：None

### JevAgentHarness：把 harness 里的"选择题"交给小模型，成本砍八成
agent harness 每一步都调用一次大模型，长任务又慢又贵；但作者观察到，大多数调用最终只是在做一道选择题——比如"下一步调哪个工具"。专门的决策模型可以直接回答这类问题，价格和延迟只是大模型调用的零头。问题是能否安全地委托：作者先建了 AgentDecisionBench，从孤立问题一直测到"接管一个正在运行的 agent"，发现孤立题上最准的决策模型也只能完成 69.5% 的 agent 任务，不加置信阈值直接委托工具选择会让成功率掉 19 个点。于是 JevAgentHarness 在 agent 自己的轨迹上为每类选择拟合一个置信阈值，低于阈值就交回大模型；又因为现有决策模型从没见过"agent 犯错之后"的状态，他们专门在这类状态上训练了开源 4B 模型 AgentDecision-4B。在与训练数据相似的任务上，agent 成本降 81–89%、速度最高 2.5 倍，成功率损失不超过 3 个点。这是一份很实用的**"harness 内模型路由"工程方案**，而且"在 agent 自己犯错后的状态上采数据"这一点对训练数据构造也有启发。
🔗 链接：https://arxiv.org/abs/2610.21412 ｜ 代码：https://github.com/JevAgentHarness/JevAgentHarness

### 代码越"健康"，agent 评审越省钱：一项预注册研究
越来越多团队把代码评审交给按 token 计费的多 agent 流水线，但"代码质量差会不会让 agent 评审更贵"一直没人量化过。这篇论文做了一个预注册（事先公开分析计划、避免事后挑结果）的观察研究：从 AIDev 数据集的 246 个仓库里，按 CodeHealth（一种对人类可维护性校准过的质量分）和 PR 改动规模分层抽了 465 个 agent 写的 PR，用一个固定的五 agent "评审 + 修复"流水线、三种不同 LLM 分别处理。结果三种模型下 CodeHealth 系数都显著为负：每高 1 分，token 成本低 3.5%–6.1%，且与 PR 大小无关；进一步分析发现多出来的成本主要在评审阶段——agent 在不健康代码上反复迭代，但并没多写评论；而控制被评分文件的大小后效应消失，说明背后是"大文件"在起作用。对我们的启示：**代码质量指标可以直接换算成 agent 推理成本**，在构造 code review 评测或做成本建模时，应把被评审代码本身的质量作为协变量。
🔗 链接：https://arxiv.org/abs/2610.21914 ｜ 代码：None（数据：https://doi.org/10.5281/zenodo.22127920）

### Terminal-RSI：已验证轨迹"自重写" + critic 继承的多轮迭代训练终端 agent
终端 agent 训练的两个难点是：如何把验证器的"成/败"结果变成有效的策略更新，以及如何把"修了一半"推进到"真正通过验收"。Terminal-RSI 交替两个阶段：一是对已验证成功的轨迹做自我重写（RSR），相当于把能过的解法提纯成更好的训练数据；二是带 critic 继承的策略精炼（RPR），每一轮的 critic 交给下一轮继续用，避免价值模型反复从零热身。工程上它设计了回合边界感知的 GAE（在多轮交互中按回合衰减但保留每个 token 的基线）、按任务族校准的稠密奖励，以及把"严格成功"和"部分得分"分开计算的成功优先奖励，防止部分分把模型带偏。从 Qwen3.8-27B 基座走五个阶段，得到的 27B 模型在 Terminal-Bench Hard 79%、TB 2.1 86.5%，LHTB 严格完成数从 0/46 到 5/46。偏算法较多，但"成功轨迹重写入库 + 严格成功与部分分分离"是可直接复用的数据/奖励工程技巧。
🔗 链接：https://arxiv.org/abs/2610.22192 ｜ 代码：None

### ReFlow：用经验回放摊薄 rollout 成本的 RL 后训练系统
LLM 的 RL 训练里，最贵的是生成 rollout；主流系统用异步执行让生成和训练重叠，但异步太轻提速有限，太重又会因策略"过时"损害模型质量。ReFlow 的关键观察是：现有框架每条轨迹只用一次，而对**最近**的轨迹做经验回放，可以在不引入太多过时问题的前提下重复利用样本，摊薄生成成本。系统上它有三件事：双回放数据循环（平衡吞吐与优化稳定性）、弹性资源池（根据 RL 负载随时间变化动态分配 GPU）、自适应调度器（协调生成策略和资源分配）。在单轮推理和多轮 agentic RL 上，训练吞吐最高比现有同步/异步系统快 2.06 倍，模型效果持平或更好。对搭建 agentic RL 基础设施的团队，"样本复用 + 动态资源"是比单纯加大异步度更稳的提速方向。
🔗 链接：https://arxiv.org/abs/2610.21640 ｜ 代码：None

### Mosaic：当一条轨迹跨越多个会话时，RL 该怎么分配功劳
现在的 coding/research agent 普遍会做上下文压缩（把旧历史总结掉）或派生子 agent，一条完整轨迹实际上由多个"会话"组成；但大多数 agentic RL 方法默认整条轨迹在一个连续上下文里，训练和推理形态不一致。常见做法是把整条轨迹的优势值原样广播给每个会话，但这分不清哪个会话真正有贡献，也无法引导模型合理分配会话数量。Mosaic 做了两层、无需 critic 的优化：轨迹层把"用了多少会话"纳入优势估计，会话层按估计的边际贡献重塑每个会话的优势。在 BrowseComp 上用 Qwen3.5-4B 测试，压缩和子 agent 分叉两种场景都优于广播法，且平均用的会话更少。对 harness 与训练对齐的问题，这是第一批正面处理"多会话轨迹"训练的工作，值得跟进。
🔗 链接：https://arxiv.org/abs/2610.22174 ｜ 代码：None

### MetaExp：通过"任务族"让模型学会积累和复用经验
agent 部署后会积累大量交互反馈，但把反馈变成可复用的"经验"一直很难：已有方法要么优化外部经验库，要么只在特定任务上训练相关行为，模型本身并没有学会"怎么从经验里学"。MetaExp 的关键是数据组织方式：构造可验证的任务族，族内保留一个可复用因素、其余部分变化——"共享工具族"固定一组黑盒工具，逼模型积累操作经验；"共享流程族"保留隐含的操作流程，逼模型积累流程经验——这样能迁移但无法直接抄答案。作者从 1000 个任务族收集并过滤 4956 条序列化交互轨迹，微调 Qwen3.5-122B-A10B，之后冻结参数、只靠非参数经验演化，SpreadsheetBench +8.5、AutomationBench +14.8，排除训练领域后收益仍在。对数据工程，"**按可复用因素设计任务族**"是训练元能力的一种新的数据构造范式。
🔗 链接：https://arxiv.org/abs/2610.21492 ｜ 代码：None

### EliteReplay：RL 后训练时保住"多种正确解法"
RL 后训练能提升可验证任务的准确率，但常把模型"磨窄"——只会一种稳定解法，pass@k 在大 k 时反而不如基座。已有补救方法优化的多样性指标，往往并不对应"正确解法的多样性"。EliteReplay 的做法偏数据工程：训练前先用冻结的基座模型做质量-多样性搜索，收集一个覆盖不同解题思路的"精英库"；训练时 GRPO 之外再加一项对这个库的回放损失。在多个 text-to-SQL 任务上，它的 pass@128 高于所有基线，不同的正确策略数比最强基线多最多 77%，并保留了基座大部分正确策略；在有歧义的问题（AmbiQT）上，覆盖两种解读的频率接近最强基线的两倍。对代码类 RL，"**训练前先建多样解法库再回放**"是一个低成本、易实现的防坍缩手段。
🔗 链接：https://arxiv.org/abs/2610.22290 ｜ 代码：None

### Multi-SFT：一份可商用的多语言 SFT 数据集及其构造流程
开源 SFT 数据集大多是英文，而且大量内容由闭源模型生成，这些模型的服务条款禁止用其输出训练竞品，导致数据"能用不能商用"。Multi-SFT 构建了 502,818 条覆盖五种欧洲语言的指令-回答对，全部可商用：常规任务走翻译管线，翻译不够用的任务（比如依赖语言本身特性的）走重新生成管线。人工评估的标注者一致性在所有数据集和语言上都 ≥0.87。用它微调三个家族（EuroLLM、OLMo 2、Qwen3，1B–32B）共九个模型、在 13 个基准上测试，单用 Multi-SFT 就能和更大的增强混合数据以及官方指令版持平，安全类任务上优势明显。对 SFT 数据工程，它提供了一个"**许可证合规优先**"的数据构造范例，在数据来源审计越来越严的今天很有参考价值。
🔗 链接：https://arxiv.org/abs/2610.22086 ｜ 代码：None

### NVIDIA Dory 1.0：推理时可调"思考圈数"的 4B 循环语言模型
NVIDIA 于 10 月 16 日在 Hugging Face 发布 Nemotron Labs Dory 1.0：一个 4B 的循环（latent-recurrent）语言模型，中间 20 层共享块在每个 token 上可重复执行 1、2 或 4 次，用更多计算在隐空间"多想几遍"，而不是输出更长的思维链。圈数在推理时设定，无需重训或换模型；它只缓存最后一圈的 KV，因此多跑几圈也不增加 KV 显存。按 NVIDIA 自测，4 圈时 SWE-bench Verified 从 50.3 升到 61.8、Terminal-Bench 2.1 从 12.5 升到 22.2。对本地/低成本 coding agent 来说，这提供了一个"同一份权重按预算调节能力"的新部署选项。
🔗 链接：https://huggingface.co/nvidia/NVIDIA-Nemotron-Labs-Dory1.0-4B-BF16 ｜ 代码：https://github.com/ggml-org/llama.cpp/pull/30306（llama.cpp 支持 PR）
