## 📝 逐条讲解

### Claude on call：Claude Tag 作为 Anthropic CI/CD 事故一线响应 agent
过去 CI/CD on-call 的痛点不是单个告警难看懂，而是告警、部署、PR、日志、Kubernetes 状态和历史事故散在不同系统里，人类需要在深夜把这些上下文临时拼起来。Anthropic 这篇官方案例把 Claude Tag 放进 CI on-call Slack channel，让它拥有频道级记忆、服务账号、Datadog/Grafana/PagerDuty/GitHub/Kubernetes 等连接器，并用 markdown skills 保存路由策略、排查步骤和 lessons.md。它的工作流不是简单聊天：Claude Tag 先按 deterministic alert rules 判断是否该升级，再由 orchestration agent 并行派 executor subagents 查不同依赖和信号源，最后合成 SITREP。文章给出的运营指标很具体：最近有 SITREP 的 CI incidents 都由 Claude 写第一份分析，通常 15 分钟内发布；最快案例 4 分钟给出 root-cause hypothesis。更值得关注的是自改进闭环：每次事故结束后把根因、修复和坑点写入 lessons.md，重复模式再提升成 investigation skill。对后训练软件工程来说，这是一条很完整的生产 agent 轨迹模板：触发条件、权限边界、连接器、调查子任务、证据、人工决策、修复验证、事后知识沉淀都应被结构化记录。它也说明 agent ops 的核心已经从“让 agent 写代码”扩展到“让 agent 成为可审计的工程流程参与者”。
🔗 链接：https://claude.com/blog/ai-ci-cd-on-call ｜ 代码：Setup kit（文章内链接）

### The Devil Is in the Interface：工具架构会改变 coding agent 行为
很多团队讨论 coding agent 时只问模型能力，默认工具只是在模型外面“提供功能”。这篇 Microsoft Research / Purdue / UChicago 等作者的论文把问题拆开：同样的信息和动作能力，如果以不同工具架构暴露给模型，会不会改变 agent 的轨迹质量。作者构造了 6 种工具接口，包括纯 bash、atomic 文件/搜索/编辑工具、自然语言搜索、Python CodeAct 风格执行块、HypoTrack 和 Scratchpad，并在 65 个 SWE-bench Live 任务上对 3 个 actor models 跑了 11,700 条轨迹。结果显示，架构本身会改变一致性、探索范围和成本：atomic 低层工具能让弱模型 pass^9 一致性最高提升 4.7 倍，自然语言搜索让相关文件访问率增加 11% 以上，而 Python CodeAct 风格在相近任务表现下减少 41.6% 步数和 56.3% token。相反，轻量 scratchpad / hypothesis 工具影响有限，因为它们只是让模型“写下想法”，没有真正改变信息获取和行动方式。工程启发很直接：MCP server、CLI wrapper、file operation API 和 search interface 不是中性包装，而是会塑造训练轨迹分布的 agent-computer interface。对后训练数据来说，不能只保存“模型调用了工具”，还要保存工具 surface 的粒度、抽象层、错误率和 token 成本，否则同一任务的轨迹不可比较。
🔗 链接：https://arxiv.org/abs/2608.11386 ｜ 代码：https://github.com/XZ-X/tool-arch-study.git

### Evo-Harness：把一次性执行上下文编译成可复用 skill harness
现在很多 self-improving agent 会把失败轨迹总结成 memory、reflection 或 rule，但真实任务常常只有一次执行机会，轨迹里同时混着可复用经验和本任务偶然细节。Evo-Harness 把这个问题定义为 online harness learning：冻结 agent 本体，让它在连续任务流中更新外部结构化 harness，而不是每次从零靠回忆。核心方法叫 context-to-harness skill compilation，也就是从单次嘈杂执行上下文中提炼可跨任务复用的 skill harness，影响后续 planning、acting、verification 和 recovery。和简单 case retrieval 不同，它不是“以后遇到相似任务再找回来”，而是把经验编译成更前置的操作规程和主题级策略。论文在 TerminalBench2、SWE-bench、CL-Bench、τ-bench、WebArena-Infinity 等五类真实 benchmark 上做评估，用来验证一次性经验是否能迁移。它值得关注，是因为后训练软件工程越来越关心“哪些轨迹片段值得变成技能”，而不是把整条历史塞进记忆库。对数据筛选来说，Evo-Harness 提醒我们要区分 task-specific artifact 和 transferable procedure，前者可能污染后续任务，后者才值得进入 skill 管线。
🔗 链接：https://arxiv.org/abs/2608.15071 ｜ 代码：None

### StagedWorkspace：为知识工作 agent 建立版本化 workspace-state contract
Coding agent 通常有一个相对明确的仓库状态：搜索、编辑、diff 和测试都围绕同一个 checkout；但 office、PDF、notebook、slides、spreadsheets 等混合格式工作区里，agent 搜到的 parsed view、实际编辑的 native file、审阅 diff 和最终提交物可能来自不同版本。StagedWorkspace 把这个问题命名为 workspace-state contract：每个视图都必须绑定到正在演化的 workspace 版本。它的做法是把 native workspace 作为权威状态，把 parsed records 和 review diffs 都绑定到源文件路径与 content hash；如果文件被修改，旧 parsed cache 会明确标成 stale，直到重新解析。这样 agent 可以先用 parsed search 定位证据，再打开 native 文件查看布局、公式或可执行内容，并在提交前检查 journaled diff。实验上，在 OfficeQA Pro 和 APEX-Agents 的 fixed-harness 消融中，parsed/native 双视图在所有测试模型上都有最高点估计，相比单视图提升 OfficeQA Pass@1 8.3-12.1 点、APEX 平均 rubric 4.7-9.2 点。这个工作对 Agent-Friendly Software 很重要，因为它把“文件系统是否对 agent 友好”从工具列表推进到状态一致性协议。对后训练和评测来说，未来混合文档 agent 的轨迹必须记录证据、编辑、审阅和提交分别对应哪个 artifact hash，否则评测会把状态漂移当成模型能力问题。
🔗 链接：https://arxiv.org/abs/2608.18050 ｜ 代码：None

### Kozuchi Agent：语言无关的开源权重软件修复 agent 与 CI 评测流水线
企业要跑软件修复 agent 时，难点不只是模型会不会写补丁，还包括长程执行、工具语法漂移、异构集群、评测复用和成本控制。Kozuchi Agent 是 Fujitsu Research 的 ASE 2026 experience report，目标是用本地托管 Qwen3.5-27B 这类 open-weight 模型，在可审计 harness 中完成真实 SWE 修复。它把 issue resolution 拆成显式阶段，使用 persistent state、确定性工具、模型无关 action interface，并通过 cross-agent test-time selection 在多个候选运行之间选补丁。最亮眼的数据是：不做 fine-tuning，TTS@8 下在官方 SWE-bench Verified 解出 374/500；同一 27B 配置不改核心 harness 迁移到 Multi-SWE-bench Java，解出 41/128，并在 strict open-weight submissions 中排名第一。论文还把剩余失败分解清楚：大多数补丁能干净 apply，问题主要是语义正确性和选择错误，而不是格式或 diff 生成失败。工程价值在于它把 benchmark-scale agent 运行变成 CI 管线，复用昂贵阶段，把 operator touch-points 从 5 个降到 1 个。对后训练软件工程来说，这类公开轨迹、selector regret、phase state 和 CI artifact 比单个 pass rate 更有价值，因为它们能告诉我们数据应该补哪里。
🔗 链接：https://arxiv.org/abs/2608.15579 ｜ 代码：None

### TDD-Agent：把测试驱动开发变成 repository-level code generation harness
很多 code generation 方法把测试当作事后验证器：先写实现，再用已有或生成测试检查；问题是自生成测试可能不完整、偏向模型自己的实现，甚至给出误导性反馈。TDD-Agent 反过来要求 agent 先生成可执行测试，把需求、输入输出和边界条件变成中间规格，再进入实现阶段。它不是生成一次测试就锁死，而是采用 dual-track refinement：执行失败时允许同时修改代码和测试，执行通过后还会鼓励 agent 考虑是否需要增强测试。作者先在 LiveCodeBench 用轻量 TDD-prompt 隔离 test-first reasoning 的作用，再在 RepoEval 这类 repository-level 场景里评估完整框架。结果显示，测试优先不仅提高代码正确率，也提高了生成测试自身的 pass rate、coverage 和 mutation score，说明测试可以作为演化中的 reasoning artifact，而不是固定 validator。工程上，这很贴近 coding agent 的真实需求：在复杂仓库里，先写测试往往是在澄清规格，而不只是做 QA。对后训练数据来说，应该把测试草稿、测试修正、执行反馈和最终实现一起记录，才能训练 agent 学会“如何通过测试理解任务”。
🔗 链接：https://arxiv.org/abs/2608.16742 ｜ 代码：https://anonymous.4open.science/r/TDD-Agent-Framework-6370/

### PMCoder：把层级规划和 episodic memory 双向耦合到 issue repair 轨迹
长程 issue repair 往往跨几十到几百步，agent 需要记住读过哪些文件、试过哪些假设、哪些编辑失败、当前处于定位还是验证阶段。许多系统单独加强 planning 或 memory，但 PMCoder 的观点是二者必须双向耦合：当前 plan phase 决定哪些记忆相关，记忆里的轨迹统计也应该反过来触发 stuck detection 和 replanning。它的 episodic memory 保存 observation、attempt、outcome 和 file metadata，并用 phase/subtask 约束检索；同时，它尽量用 issue-reproduction verdict 这类执行证据推进验证状态，而不是相信 agent 自称“已验证”。在 SWE-bench Verified 上，PMCoder 用 Qwen3-Coder-30B 平均解出 167.3/500，相比 harness-matched baseline 的 142.3/500 多 25 个实例，提升 5 个百分点；跨模型、OpenHands port 和 TerminalWorld sample 也有同向结果。消融显示 planning 与 memory 的交互本身贡献了额外收益，并减少 repeated failed actions、empty-patch exits 和 context-window exhaustion。这个工作对后训练很有启发：记忆不是静态 RAG，计划也不是一次性 checklist，它们共同构成轨迹状态机。筛选训练轨迹时，应优先保留那些带有明确 phase、证据、失败恢复和 replanning 信号的片段。
🔗 链接：https://arxiv.org/abs/2608.06811 ｜ 代码：https://doi.org/10.5281/zenodo.21035632

### An Instrument for MCP Agent Studies：用审计日志和配置消融做 MCP agent 实验
很多 MCP / agent 平台文章只给最后 benchmark 数字，但很少解释实验装置如何防止状态污染、客户端混淆和评测漂移。IMTI 这篇长文专门介绍 mcp-data-platform 背后的 36,000 行 Go benchmark harness，重点不是哪个模型第一，而是怎样让一个平台假设在一天内被验证或被否定。它的实验设计把 model、prompt scaffold、seeded data 和 task set 固定，只通过 YAML profile 变化平台配置，因此“新实验”通常只是一个新 arm config。更关键的是，它把平台 audit log 当成测量仪器，而不是只信 transcript；每次 attempt 后按 session id 回读审计行，若 tool call 计数落在理论边界外就让 run 失败。它还使用 320 个隔离 identities 避免 episode 之间通过账号状态污染，使用固定 seed 生成 ground truth，优先 deterministic graders，并把 LLM judge 限制在不影响 headline number 的 caveat 质量判断里。文章非常适合评测工程团队参考，因为它讲清楚了 fixture、driver、grader、archive、bootstrap interval 和成本控制这些“论文方法部分常被省略”的细节。对后训练软件工程来说，它提醒我们：如果轨迹的来源 harness 不可复现、审计日志不可信、客户端版本混在一起，那么这些轨迹即使很贵也不一定能训练出可靠 agent。

### MCP-Memory：OKF + SQLite FTS5 的项目隔离长程 agent memory server
长程 agent 需要记住项目事实、决策、约束和历史教训，但很多 memory server 要么是黑箱数据库，要么是纯 Markdown 文件，难以同时满足人类可读和快速检索。MCP-Memory 的设计是双层结构：每条记忆用 Google Open Knowledge Format v0.2 写成 Markdown，便于版本化和人类浏览；同时用 SQLite FTS5 建索引，提供关键字、frontmatter、tag 和 namespace 搜索。默认情况下，它在项目根目录下创建 `memory/` 与 `.mcp_memory/memories.db`，因此不同代码库的 agent memory 隔离，不会随意串场。它在 Hacker News Show HN 上获得约 70 points，GitHub 约 189 stars，热度不算顶级，但在 agent memory 工程里信号清晰。真实痛点是：agent 需要长期记忆，但团队又要能审计、迁移、清理和 diff 这些记忆，而不是把所有东西交给远程向量库。对后训练数据来说，这种 OKF+索引结构可以把“可训练的项目经验”变成文件化资产，同时保留检索日志和命中上下文。风险是 memory 写入策略和权限边界仍需额外设计，否则坏记忆、私密信息和过期事实会被快速检索放大。

### The Agent Harness Stack：把 loop、context、memory、tools、verification、permissions 拆成工程层
这篇文章不是论文，也没有实验数据，因此按 Medium / Low credibility 处理；但它用很直观的方式解释了 agent harness 的边界。作者把 agent 拆成 model、harness 和 environment：模型负责下一步预测和工具请求，harness 负责 loop、context assembly、memory、orchestration、tool dispatch、verification 和 permission gate。它的价值在于把“为什么同一个模型在不同产品里表现不同”讲成工程层差异，而不是神秘模型差异。文章还给出最小 agent loop 伪代码，强调工具调用后要经过 permission gate，最终答案要经过 verification gate，而不是模型说完成就停。对团队落地来说，这类框架有助于做 harness checklist：哪些规则在 prompt，哪些必须变成确定性 hook，哪些风险要在 sandbox 和 approval 层处理。它的不足是更偏概念综述，缺少受控实验；但与工具架构论文和 Claude Tag on-call 案例放在一起看，可以帮助工程团队把抽象组件映射到实际系统。对后训练软件工程来说，harness stack 也对应轨迹字段：每一轮 context 是怎么组的、权限怎么判的、验证怎么跑的，都应成为数据 schema 的一部分。

### MCP 2026-07-28 stateless migration：Codex CLI v0.147 的 gateway-friendly MCP 工程解读
MCP 2026-07-28 规范已经在前几期覆盖过，因此这条不作为 High；但这篇 8 月 15 日工程解读把迁移影响讲得非常具体，适合 MCP server 作者参考。核心变化是协议从带 session 的初始化握手转向 stateless request/response，请求通过 `_meta` 携带 protocolVersion 和 clientInfo，远程 server 不再必须依赖 sticky session。它还引入 `server/discover`、cacheable `tools/list` / `resources/list`、header-based routing、Multi Round-Trip Requests，以及把长任务移到正式 tasks extension。对 Codex CLI v0.147 来说，这意味着 MCP server 可以后台启动、工具列表分页发现、MRTR 接入 approval pipeline，远程或团队共享 server 更容易放在普通网关和负载均衡后面。这个方向与 Agent-Friendly Software 强相关，因为 agent 工具协议正在从“本地几个 stdio server”变成企业工具总线。工程团队如果维护 MCP server，应该开始清理 per-session state、实现 discover、给 list 结果加 TTL/cacheScope，并把 elicitation 迁到 input_required/inputResponses。对评测和训练轨迹来说，协议版本、工具发现缓存、MRTR 中断点和 approval 决策都会影响 agent 行为，不能忽略。

### Harness Evolver：用 LangSmith 做后端的 Claude Code harness 自动演化插件
自动 harness evolution 的论文很多，但工程团队常缺一个能接到现有观测平台和回归集里的工具。Harness Evolver 是一个 Claude Code 插件，目标是对任意 LLM agent codebase 自动优化 system prompts、routing、retrieval、tools 和 orchestration code。它用 LangSmith datasets / experiments / LLM-as-judge 作为评测后端，多个 proposer agents 在隔离 git worktrees 中提出修改，再用 regression guards、efficiency gates、rate-limit early abort 和 stagnation detection 控制合并风险。项目只有约 43 stars，最近活跃度也有限，所以不能当作热门成熟框架；但它把“harness 自演化”落到了大家熟悉的 git worktree + evaluation backend + trace hierarchy 上。真实痛点是，prompt/hook/tool 改动往往只靠人工直觉上线，缺少自动候选生成、并行试验和可回滚证据。对后训练软件工程来说，这类工具产生的 losing candidates、失败诊断、评测 traces 和 accepted harness diffs 可能比最终成功配置更有训练价值。需要注意的是，自动合并或自动修改 agent runtime 必须有严格 review gate，不能让优化器绕过权限和安全边界。
🔗 链接：https://github.com/raphaelchristi/harness-evolver ｜ 代码：https://github.com/raphaelchristi/harness-evolver

### Agent Workspace Fabric：多 coding agent 的隔离 workspace + PR 生命周期控制面
当一个团队同时跑 Codex、Claude Code、Gemini、OpenCode、Grok 或 Cursor agent 时，单个 CLI 的 session 管理很快不够用，真正的问题变成 workspace provisioning、服务依赖、验证策略和 PR 生命周期。Agent Workspace Fabric（AWF）把每个任务包装成隔离 git worktree + Docker Compose stack，再配上 profile-driven validation、PR 创建、CI/review/base-sync/comment-fix loop 和清理流程。它当前只有 11 stars，属于早期 alpha 项目，不应夸大成爆款；但它切中了“agent as disciplined contributor”这个生产需求。它的强项是把 coding agent 放进软件交付控制面，而不是让多个 agent 在同一个工作区里互相污染。工程上，这与 StagedWorkspace 的状态合同形成互补：一个关注混合 artifact 的版本一致性，一个关注代码任务的 workspace 与 PR 生命周期。对后训练数据来说，AWF 这类系统会产生非常清晰的 provenance：任务、worktree、服务栈、验证 profile、PR 事件、review 修复和最终合并状态都可以成为轨迹字段。风险在于仓库 README 提到可选 auto-merge，生产使用时必须默认关闭并保留人工审批。
🔗 链接：https://github.com/dimileeh/agent-workspace-fabric ｜ 代码：https://github.com/dimileeh/agent-workspace-fabric

他把 `The Devil Is in the Interface` 的 11,700 条轨迹实验映射到 Codex CLI 实践：raw shell、结构化 MCP tools、自然语言搜索、Python compound operations 和 memories 分别对应不同工具架构。值得注意的是，这个观点把“是否接一个 MCP server”从便利性问题提升为实验变量：它会影响一致性、搜索召回、token 成本和错误类型。🔗 https://codex.danielvaughan.com/2026/08/13/devil-in-the-interface-tool-architecture-shapes-coding-agent-behaviour-codex-cli-tool-surface-design/

**IMTI / txn2：评测 agent 平台时要从审计日志测量，而不是从 transcript 猜测。**
这篇 MCP studies harness 文章的关键 insight 是：transcript 会遗漏 transport failure、client-side tool search 和平台实际收到的调用，真正可靠的测量点应该是平台 audit log、fixture access log 和同步回读。它值得关注，因为许多 agent eval 仍把聊天记录当真相，而生产系统需要能证明工具调用、身份、状态和 grader 都可复现。🔗 https://imti.co/mcp-agent-benchmark-harness/
