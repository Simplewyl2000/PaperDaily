## 📝 逐条讲解

### LoopsBench：把 coding-agent 评测从单次 issue 推到依赖 DAG + regression obligation
很多 coding-agent benchmark 仍把任务看成一个孤立 issue：给 agent 一个目标，最后看隐藏测试是否通过。但真实软件开发更像一串互相依赖的开发单元，前面实现的接口、测试和行为会成为后面工作的约束，后续改动还可能把已经完成的部分弄坏。LoopsBench 把任务组织成 dependency DAG，每个节点是一个有来源证据、可单独测试的 development unit，边表示必须先完成的前置关系。它的 runtime 会沿着 ready frontier 释放测试，同时把已经完成的节点继续保留为 regression obligations，所以 agent 不能只冲终点，还要持续维护已经通过的中间结果。数据规模也比较贴近长程开发：112 个任务、8 种语言、9 个领域、超过 5,300 个开发单元，来源包括 PR sequence、课程项目和研究演化。结果显示最强配置也只解决 25.00% 任务，且计划经常漏掉真实依赖关系，回归事件在不同 loop profile 中都可见。对后训练软件工程来说，它把“长程循环是否可靠”拆成 planning、routing、state retention、testing 和 regression pressure 等可记录信号，适合用于筛选真正有训练价值的 agent 轨迹。  
🔗 链接：https://arxiv.org/abs/2608.00267 ｜ 代码：None

### SWE-Touch：用户中途改代码时，agent 是否能发现冲突并重新验证
现有仓库级评测通常默认 agent 独占工作区，代码在任务期间不会被用户或另一个开发者修改；但现实中，人类经常边看 agent 工作边直接改文件，或者另一个 agent 在同一个分支上推进。SWE-Touch 专门测试这个 shared workspace 场景：它先从多条 repair trajectories 中挖出任务关键区域，再生成看起来合理但会和任务目标冲突的 Counter-Edits，并在 agent 到达相关代码时注入这些改动和上下文消息。这样评测的不只是“会不会修 bug”，而是 agent 是否会重新检查工作区、理解用户改动和原始 issue 的关系、保留有用部分、撤销冲突部分，并用 targeted tests 重新验证。论文在 SWE-bench Verified、SWE-Bench Pro 和 DeepSWE 上测试九个 coding models，Counter-Edit 让平均 resolve rate 下降 7.7 个百分点。失败轨迹显示很多 agent 会直接保留冲突代码，或者粗暴覆盖用户改动但不重新检查相关行为。这个 benchmark 很适合生产 coding-agent 场景，因为它把人机协作中的状态漂移做成了可控压力测试。对训练数据来说，中途工作区变化、agent 是否检测到 diff、如何调和冲突、是否重新跑测试，都应该成为轨迹标签。  
🔗 链接：https://arxiv.org/abs/2608.02499 ｜ 代码：https://github.com/Trae1ounG/SWE-Touch ｜ https://trae1oung.github.io/SWE-Touch/

### HarnessCompass：限制自动 harness evolution 过拟合，把优化拆到组件级
自动 harness evolution 很诱人：让 agent 根据失败轨迹修改自己的 prompt、工具、上下文策略或控制流，然后继续跑评测，分数可能很快上涨。问题是这种流程很容易对 evolution tasks 过拟合，也容易把多个 harness 组件一起改，最后不知道到底是哪一层带来收益，甚至不同组件互相干扰。HarnessCompass 的核心做法是给自动演化加工程约束：只允许 task-agnostic 的 harness 修改，避免针对某个 benchmark case 写“暗门”。它还不只依赖执行轨迹，而是加入 agent 对 harness 使用体验的 proactive first-person feedback，用来发现工具面、上下文或控制流哪里阻碍了任务推进。最后，它把 prompt、tool、memory、control 等组件拆开分别优化，再合并成统一 harness，减少“所有旋钮一起拧”的干扰。论文报告在 SWE-bench Verified 上用 GPT-5.4，5 轮 evolution 把 Pass@1 从 54% 提到 66%，并且对 held-out tasks 和其它模型有更好迁移。对后训练软件工程来说，这篇提醒我们自动改 harness 本身也要有边界、分层和迁移验证，否则可能只是把评测集特征写进系统。  
🔗 链接：https://arxiv.org/abs/2608.01918 ｜ 代码：None

### Prompt-Induced Waste：同一任务里提示词和 harness 可让 coding-agent 成本放大 5–30x
很多团队在使用 reasoning models 做 coding agent 时，会习惯性加入“多想几种方案”“think deeply”“比较多个 approach”这类提示，以为更深思考一定更可靠。Prompt-Induced Waste 做了一个 preregistered two-harness benchmark，覆盖 6 个大 reasoning models、2 个真实 agent harness、24 个确定性 coding tasks 和 4,643 次有效运行，专门测提示词对成本和正确率的因果影响。结论很直接：要求模型生成并比较多个方案，是最稳定的浪费型指令，reasoning tokens 会增加 2.4–7.4 倍，但正确率没有同步提升。泛泛的 “think deeply” 也会增加 1.6–2.2 倍 deliberation，而限定 scope、acceptance criteria 和 stop condition 的 bounded-efficiency template 有时反而能把 reasoning 减半。更重要的是 harness choice 的影响甚至更大：相同 model-task-prompt triples 在 Claude Code 和 pi 之间，每个成功任务成本可差 5–30 倍，原因包括静态前缀、turn 数和工具循环差异。它还提醒 provider-side caching 只能改变账单，不改变行为，不能被当成 agent 本身更高效。对后训练数据工程来说，采集轨迹时必须保存 prompt template、harness、prefix、cache、turn budget 和 stop rule，否则我们无法解释“高成本成功轨迹”到底是能力、浪费还是 harness 偏差。  
🔗 链接：https://arxiv.org/abs/2608.01347 ｜ 代码：None

### Coding Agents as Test-Suite Auditors：让 agent 生成对抗测试，审计官方测试漏判
很多代码训练和评测都把 online judge 或 benchmark 官方测试当成 ground truth，但真实情况是测试套件可能漏掉 buggy submissions，也可能把错误解法标成通过。Coding Agents as Test-Suite Auditors 的思路不是再写一篇警告，而是把 coding agent 用作 test-suite auditor：让它生成对抗测试，找出官方测试没覆盖的行为。为了避免“agent 说有 bug 就算 bug”，论文设计了 certification chain：多个独立 accepted solutions 对同一测试输出达成一致，分歧时用 brute-force solution 解决，再用 per-problem validator 确认输入合法。单个 agent 在 AtCoder 的 20,375 个 accepted submissions 中找出 589 个 verified accepted-but-buggy submissions，五个 agents 的 union floor 达到 906 个。更有用的是，在没有官方测试的 post-cutoff Codeforces 问题上，同样的测试生成方法在不同 input budget 下都优于复现 baselines。它的工程价值在于把“测试套件可信度”也纳入了评测对象，而不是默认隐藏测试永远正确。对后训练软件工程来说，agent 生成的对抗测试、certification verdict 和被官方套件漏掉的失败用例，都是比单纯 pass/fail 更细的训练与评测信号。  
🔗 链接：https://arxiv.org/abs/2608.01715 ｜ 代码：None

### PATH-Bench：评测 lifelong agents 的经验路径依赖、迁移与遗忘
越来越多 agent 会把过去交互写成 memory、skills 或经验库，下一次任务再检索使用；但已有评测常只问“有记忆时做当前任务是否更好”，很少测经验路径本身会如何改变后续行为。PATH-Bench 把这个问题做成 path-dependent evaluation：先估计任务之间的 directed relationships，再构造以 probe task 为中心的序列，控制前面历史是 helpful 还是 interfering。它反复评估 probe task，测平均表现、forward transfer、backward transfer 和 forgetting，而不是只看一次最终成绩。论文覆盖 single-turn code generation 和 multi-turn tool-use tasks，发现经验是否有用取决于经验表示方式和任务交互结构，强迁移并不等于长期保持，后来的经验还会重塑早期收益。基于这些发现，作者提出 Selective Experience Use（SEU）harness，让系统按任务选择性接纳有帮助的经验，并过滤可能干扰的新旧经验。这个方向对 skill management 很重要，因为 skill/memory 如果不能区分“可复用经验”和“情境噪声”，长期运行的 agent 会越来越像背着一堆未审计补丁。对后训练数据工程来说，经验的来源路径、重复 probe 表现和遗忘曲线，应成为评估 skill 是否值得保留的标准。  
🔗 链接：https://arxiv.org/abs/2608.01149 ｜ 代码：None

### BoundaryBench：在加固 sandbox policy 下评测 coding-agent harness 行为
很多 coding-agent 安全评测关注 prompt injection 或越权工具调用，但真实部署中还有一个更底层的问题：同一个 agent 在不同 sandbox policy 下，会不会因为权限、网络、文件系统、进程和系统调用边界变化而表现不同。BoundaryBench 是 8 月 2 日创建的新仓库，定位为在 hardened NIST-derived sandbox policies 下评测 Claude Code、Codex、Terminus 2、Grok 等 coding-agent harness，任务来源对齐 Terminal-Bench 风格。它同时标注 Inspect AI 和 Harbor compatible，说明目标不是单个脚本，而是接入更标准的评测/执行生态。虽然当前只有 3 stars，可信度按 Low 处理，但选题很值得追踪：安全边界不该只是部署时配置，也应该成为评测变量。一个 agent 如果只在宽松 sandbox 下成功，到了真实企业隔离环境就不断失败或绕路，那么 pass rate 对生产价值的解释就很弱。工程落地上，这类 benchmark 应记录 policy profile、被拒绝的操作、替代路径、agent 是否请求权限、以及最终是否保留安全约束。对后训练轨迹来说，sandbox denial 和 agent 的恢复方式是非常高价值的安全/鲁棒性标签。  
🔗 链接：https://github.com/boundary-bench/boundary-bench ｜ 代码：https://github.com/boundary-bench/boundary-bench

### Practical Online KV Cache Compaction：面向 agent 长轨迹的在线 KV 压缩实证
长程 agent 的成本不仅来自输入 token，也来自推理时越来越大的 KV cache：每一轮 reasoning、tool call 和环境反馈都会增加后续计算负担。很多 KV 压缩方法假设未来 query 已知，适合静态文本；但 agent 场景是在线的，当前压缩时还不知道未来哪些信息会重要。Practical Online KV Cache Compaction 比较 token eviction 和 attention matching 两类方法，并研究 boundary、repeat-prefill、delayed future-generation 等 proxy query 来源。一个重要发现是，立即压缩往往会损伤表现，而等到 agent 产生一些未来 query 后再压缩，可以恢复相当多质量。另一个工程结论是，在 proxy 不完美时，token eviction 往往比 attention matching 更稳；在 BrowseComp-Plus 和 WideSearch 上，它能保留大部分准确率并把 KV cache 减少 80%。这篇按 Medium 收录，因为它偏推理基础设施，但它直接影响长程 agent 的成本和吞吐。对后训练软件工程来说，压缩事件也要进入轨迹：何时压缩、用什么 proxy、删了哪些 turn、是否改变后续 tool choice，都会影响可复现性和训练信号。  
🔗 链接：https://arxiv.org/abs/2608.00902 ｜ 代码：None

### MemSIF：把长交互拆成 topical segments + event trajectories，再写入双轨事实记忆
agent memory 的常见失败是把“时间上相近”误当成“语义上相关”，或者在写入时看起来不重要的信息，后来才变得关键。MemSIF 把这两个问题分别叫做 Temporal-Structural Misalignment 和 Delayed Utility Manifestation。它的做法是先把原始交互整理成两种结构：Topical Segments 保持局部主题连贯，Event Trajectories 维护跨时间的事件连续性。然后再把事实写入双轨记忆：CoreFact 在写入时巩固稳定、schema-guided 的信息，ActiveFact 则在查询时形成候选事实，并把多来源支持、反复被查询的内容提升为可复用记忆。这个设计比“每轮都做摘要”更像软件里的日志索引和事实缓存分层，既保留事件线索，也避免把所有细节一股脑塞进上下文。实验在 LoCoMo 和 LongMemEval-S 上报告相对强 baseline 有 2.29%–8.79% 和 2.87%–6.15% 的提升。对 coding agent 来说，类似结构可以用于项目记忆：哪些是长期稳定的接口事实，哪些只是某次 debug 中暂时有用的观察，应当分轨管理。对后训练数据工程来说，memory write、promotion、query-demand 和事实来源都应被记录，否则很难判断某条成功轨迹究竟依赖了什么历史。  
🔗 链接：https://arxiv.org/abs/2608.01742 ｜ 代码：None

### Cross-Benchmark Generalization：长程 agent 训练改动能否从 LHMTA 迁移到 SWE / terminal / tool benchmarks
很多 agent post-training 报告会在一个环境里做 SFT/RL、调 pipeline、选 checkpoint，再报告该环境分数；但我们真正关心的是这些改动是否能迁移到其它 long-horizon tasks。Cross-Benchmark Generalization 选择了 LHMTA 这类更宽的专业软件工作分布，覆盖 office suites、terminal、calendar、file systems 和 web，再测试训练改动能否迁移到 SWE-Bench Pro、Terminal-Bench 2、tau2-Bench、BFCL-V4 和 Toolathlon。论文特别强调外部 benchmark 的任务和 grader 没有进入 SFT/RL，也没有用于 reward、超参、checkpoint selection 或 early stopping，这是一条很重要的评测纪律。它把 in-distribution holdout 和 external benchmarks 分开：前者能证明 pipeline 没坏，后者才更能说明泛化。对工程团队来说，这种 protocol 可以避免把“调到某个榜单”误判成真正 agent 能力提升。它按 Medium 收录，因为主题跨多个 agent 域，不完全聚焦 coding，但它给后训练评估一个非常实用的模板。训练数据和 pipeline 的每次选择都应说明是否看过外部分数，否则 leaderboard 改善可能只是隐性调参。  
🔗 链接：https://arxiv.org/abs/2608.00181 ｜ 代码：None

### EvoBreak：良性经验组合也能攻击 self-evolving agents
self-evolving agents 会把过去任务提炼成经验、规则或技能，听起来能越用越强；但如果每条经验单独看都无害，组合起来却覆盖了危险目标的多个前置条件，就会变成新的安全风险。EvoBreak 提出 experience-conditioned sequential attack，不是一次性给恶意指令，而是让攻击者通过一串看似良性的任务，诱导 victim agent 逐步积累互补经验。攻击过程会观察 victim 生成了哪些 experience，再重新规划下一步，直到这些经验的联合覆盖足以在最终请求中被激活。论文还引入 BreakGym，用于合成 safety-sensitive target scenarios，并用 rejection-sampling SFT 与 Hint-guided GRPO 训练攻击策略。它最有价值的点在于把 persistent memory / experience 的风险从“单条记忆是否有害”推进到“多条良性记忆组合后是否危险”。这和 agent skill 管理很相关：技能库、项目记忆、失败复盘和自动规则生成都不能只做逐条审核，还要评估组合效果。对后训练软件工程来说，经验写入、合并、召回和最终任务触发之间的链路需要可审计，否则 self-evolving pipeline 可能把攻击面持久化。  
🔗 链接：https://arxiv.org/abs/2608.01759 ｜ 代码：None

### CoPES：资源受限下用协同子空间进化做 agentic LLM post-training
长程 tool-using agent 的 post-training 很吃显存和算力，因为每条轨迹多轮、长上下文、工具反馈多，传统 GRPO 这类梯度训练很快变得昂贵。CoPES 关注的是一个很现实的场景：只有少量 GPU 的团队，如何在不承担完整 GRPO 显存压力的情况下做 agentic post-training。它用 Cooperative Parameter-subspace Evolution Strategy，把全参数搜索拆成多个低维子空间，再让这些子空间协同演化。论文在 Qwen3.5-4B tool-using agent 上做数学任务训练，并在五个难度不同 benchmark 上评估；在与 full-parameter GRPO 最佳验证点相同 GPU-hour 预算下，CoPES 恢复了 92% 的 GRPO validation-accuracy gain，而标准 ES 只有 67%。它的理论 GPU 显存需求低于 full-parameter GRPO 的八分之一，并在 pass@k 上持续优于标准 ES 和 LoRA-based GRPO。按 Medium 收录，是因为它更偏训练优化算法，但工程动机清楚：降低资源门槛，让小团队也能探索多轮 agent post-training。对后训练软件工程的启发是，训练方法评估不能只报最终准确率，还要报告显存、GPU-hour、轨迹长度和可复现成本。  
🔗 链接：https://arxiv.org/abs/2608.02391 ｜ 代码：https://github.com/MetaronWang/CoPES

### Gemini Robotics 2：多步 embodied reasoning、multi-robot collaboration 与 ASIMOV-Agentic 安全评测
Gemini Robotics 2 不属于本日报主线的 coding-agent 或 code LLM 后训练，所以按 Low 处理；但它是 Google DeepMind 7 月 30 日的高可信官方发布，并且包含一些 agent runtime 和 safety evaluation 信号。Google 把系统拆成 Gemini Robotics 2（vision-language-action 控制）、Gemini Robotics ER 2（embodied reasoning agent）和 Gemini Robotics On-Device 2（本地运行与快速适配）三类模型。最贴近 agent 工程的是 ER 2：它负责观察环境、理解用户指令、规划多步任务、协调 VLA 执行动作，并在任务失败时做自我纠正。发布还强调 multi-robot collaboration，让不同机器人通过高层 agent 协作完成单体机器人做不了的流程。安全部分引入 ASIMOV-Agentic benchmark，用来测 embodied reasoning agent 是否会拒绝不安全 tool calls、是否能判断任务不可行并主动请求人类介入。虽然这是物理世界场景，但它反映了一个跨领域趋势：agent 评测正在从最终结果走向“是否能在不确定性下安全编排工具和请求人类帮助”。对软件工程 agent 来说，同样的思想适用于高风险代码变更、生产操作和权限边界。  
🔗 链接：https://deepmind.google/blog/gemini-robotics-2-brings-whole-body-intelligence-to-robots/ ｜ 代码：None

## 🔥 社区热点专栏

### 🔥 大佬观点

**OpenAI SWE-Bench Pro 审计引发的社区共识：coding-agent 榜单不能只看 pass rate，必须先审计评测本身。**  
围绕 OpenAI 7 月 8 日 `Separating signal from noise in coding evaluations` 的转述和讨论，社区重点不在“哪个模型掉分”，而在“一个被广泛引用的 benchmark 竟有约 30% broken tasks”。这条观点值得注意，因为它把 evaluation engineering 抬到了与模型能力同等重要的位置：prompt clarity、test coverage、implementation-agnostic validation、human review、agent-assisted audit pipeline 都是发布 agent 前的基础设施。🔗 https://openai.com/index/separating-signal-from-noise-coding-evaluations/

**Hugging Face / SWE-Touch 讨论：shared workspace 会重排模型名次，63.3% 失败运行保留了用户冲突代码。**  
SWE-Touch 的 Hugging Face paper page 把论文结论压缩成了很有冲击力的社区 takeaway：不是所有 autonomous benchmark 高分模型都能在用户中途改代码后保持稳定，很多失败来自没有重新检查工作区。这个 insight 对真实开发很关键，因为人类和 agent 共享分支、共享文件、共享 review comment 是常态；如果 agent 不具备状态感知和冲突调和，自动化越强越容易踩掉人类意图。🔗 https://huggingface.co/papers/2608.02499 ｜ https://trae1oung.github.io/SWE-Touch/

### ⭐ 超火仓库/项目

**Kiln-AI/Kiln：约 5,010 stars，8 月 4 日仍活跃，把 evals、synthetic data、dataset management、fine-tuning 和 MCP 放进同一 AI 系统工作台。**  
它火在解决“eval、数据集、微调、agent 实验散在多个工具里”的痛点，尤其适合想把失败样本、合成数据和评测闭环统一管理的团队。对后训练软件工程来说，Kiln 代表一种更平台化的趋势：数据构造、评测、优化和 agent tool surface 不再是孤立脚本，而是要有版本、审计和协作界面。🔗 https://github.com/Kiln-AI/Kiln

**Swival：约 311 stars，8 月 3 日仍活跃，小型开源 CLI coding agent，强调可用开放模型运行。**  
Swival 热在命中“不要所有 coding-agent workflow 都依赖闭源大模型客户端”的需求：团队希望用开源模型、本地模型或低成本 provider 也能跑完整 read-edit-test loop。它的信号不在 star 数爆炸，而在开源 coding-agent 宿主继续分化，给后训练和评测团队提供更可控的 harness 实验对象。🔗 https://github.com/Swival/swival

**remnic：约 154 stars，8 月 4 日活跃，把用户级 memory / provenance / retrieval quality / correction / boundaries 做成 MCP + HTTP。**  
它火在解决“agent 记忆不能只是向量库”的痛点：长期记忆需要 scope、来源、纠错、边界和 eval，否则会把旧错觉或不该迁移的信息带入新任务。对后训练轨迹来说，这类 provenance-aware memory 项目值得关注，因为它能记录 agent 到底引用了哪条记忆、为什么相信它、后来是否被修正。🔗 https://github.com/joshuaswarren/remnic

**BoundaryBench：8 月 2 日创建的新项目，虽然只有约 3 stars，但主题高信号：coding-agent harness 在加固 sandbox policy 下是否仍可靠。**  
它值得关注不是因为当前热度高，而是因为方向对：agent 安全评测不能只看文本安全，也要看在 NIST-derived sandbox 边界中遇到拒绝、权限限制和环境差异时能否完成任务。随着企业部署把网络、文件和进程权限收紧，这类 boundary-focused benchmark 会越来越重要。🔗 https://github.com/boundary-bench/boundary-bench
