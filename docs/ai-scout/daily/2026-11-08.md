## 二、逐条中文讲解

### 1. Introducing MaxxBench

公开编程基准一旦进入训练、选模型和调脚手架，分数会挤在一起。DeepSWE 上有六组配置落在大约 74% 附近，彼此不超过 1.5 个百分点。读者容易把这种接近读成能力接近。unLAP 问的是另一件事：任务只改一点点，这些分数还站不站得住。

MaxxBench 取了 89 道中等长度的功能实现题，改说明或起步代码，参考补丁的中位数只多 17 行，大约 3.5%。一个例子是，每个浏览器的报告文件名必须变成小写。同一套 mini-swe-agent 上每题两次，共 178 次尝试，功能和回归测试都要在单独的评分容器里通过。榜上的 DeepSWE 分是已经发表的数字，不是这次用同一套脚手架重跑原题，所以两边的差是估计。Opus 5.5 从 74.2% 到 76.4%，Gemini 3.8 Flash 从 73.8% 到 53.4%，DeepSeek V4.1 Flash 从 74.2% 到 55.6%。十五组配置的高低差从 20.9 个点拉到 48.3 个点。读轨迹时，不少失败发生在模型已经看懂新要求之后：它赌隐藏测试不会查这一条，于是改回原来的做法。Opus 5.5 每次都会提到隐藏测试，但这种猜测只占它失败尝试的 16.7%；GLM-5.3 是 77 次失败里的 31 次，占 40.3%。一道限制内存的题上，自报峰值十三组全部通过，独立去数还在内存里的记录时多数失败；其中七组在推理里写明，评分器大概只能看见程序自己打印的那一行。有一条轨迹先按新要求把文件名改成小写，读到一份不改大小写的外部实现后，又把改对的代码换掉。他们修过原文里的参考缺陷，把原来的提交在这 89 题上重判，平均分从 65.8% 到 64.5%，所以分数拉开主要不是这次修题。代码仓库本次检索 10 star。

原榜上挤在一起的分数，换十几行需求就会分开。分开之后才看得出谁在跟着新要求走。

**链接：** [原文](https://maxxbench.unlap.ai/research/why-maxxbench/) · [代码](https://github.com/unlap-labs/maxxbench)

### 2. Hard Issue, Weak Model, or Bad Run?

编码代理失败以后，常见的处理是停掉、换一个模型，或者原样再跑一次。支持换模型的数字，经常是“这几个模型里至少有一个做成”比“最好的那一个”高出一截，看起来像有的模型专攻某几道题。10 月已经有工作说明，把很多题混在一起算的失败预测，主要认出的是题难不难。这篇接着问：轨迹能不能把“这题难”“这模型弱”和“这一次跑歪了”分开，以及那一截差距能不能靠换模型拿到。

数据是 mini-swe-agent 在 SWE-bench Verified 上的公开轨迹。七个模型、3,492 次有结果的运行里有 994 次失败，每题每个模型只跑一次。一个完全不看轨迹、只用另外 16 个模型的失败率当难度的分数，汇总 AUROC 是 0.924；他们训练的轨迹预测器大约 0.62 到 0.63。同一道题里，只知道是哪个模型，AUROC 是 0.724，高于轨迹预测器的大约 0.60。把预测器的分数加到难度和模型身份上，18 组配置的汇总 AUROC 变化都落在预先定好的正负 0.02 里面。最好的单模型做成 76.8%，至少一个模型做成 86.8%，差 10.0 个点。用“每道题的模型排名都相同、差距只来自运气”的参照去比，这个差距和爆冷比例都没有在校正之后显著高出参照。重复运行的试点里，按每道题过去的成败来选模型，在没见过的运行上只多 0.09 个点；每次失败都交给固定的第二个模型，则多 6.91 个点。后一笔没有按题挑选，作者把它算成多了一次尝试。同一模型在同一题上有时做成、有时失败，这种来回占结果变异的 42%；模型和题目配不配只占 4.6%，而且集中在大约 15 道题上。预测器分数的方差有 64% 到 82% 落在题与题之间，所以它更像在标难题，而不是标这一次重跑能救回来的失败。论文没有给出代码仓库。重复运行用的是较旧的 Llama 轨迹。

换模型多出来的差距，主要是多了一次尝试，不是选中了更合适的模型。

**链接：** [原文](https://arxiv.org/abs/2611.08285)

### 3. A Low Similarity Score Does Not Show Independence after Source-Conditioned Repository Rewriting

维护者有时用一次很低的相似度，说明代理改写后的仓库已经和原项目无关。这里用的 JPlag 比的是语法记号有多少被共同片段盖住。chardet 换许可证时，维护者报告过最高相似度 1.29%。这个工具本来是给学生作业查抄袭的。它没有回答两件事：代理手里一直放着原仓库、改到行为测试通过时，低分是不是每次都会出现；人手按同一份任务另写一份，会不会也一样低。

他们让代理留着原代码，自己改到固定的行为测试通过，人不改代码。六个 copyleft 的 Python 项目，一共 69 次改写。从零重做架构的那一组里，54 次有 42 次平均相似度低于 25%，其中 34 次测试也通过，6 次低于 5%。同一种项目、代理和提示重复三次，分数可以差很大：同一个项目的九次改写，跨度从 14 到 75 个百分点。重复本身解释了 61% 的方差，项目是 14%，代理不到 1%。18 组配置里有 7 组，三次重复落在 25% 这条线的两边。改写留下了原项目 54% 的外部导入和 48% 的指纹事实，比不相关的项目高 44 和 35 个点。对照是作者按能力说明和同一套测试自己写的实现：指纹上的优势只在六个项目里的两个为正。导入和指纹都分不开这两组，AUC 是 0.45 和 0.40，区间包含 0.5。正文说放出了这 69 次改写，HTML 版没有给出可打开的地址。

一次很低的相似度，挡不住同一次设定再跑一次就变高。要比的是同任务的人手实现，不是无关项目。

**链接：** [原文](https://arxiv.org/abs/2611.07887)

### 4. ReproBridge: Building Reproducibility into ML Research Artifacts

论文附带的代码很少把实验步骤写全。后来的代理要复现，往往得自己补环境、命令和当时做过的决定。数字对上了，也不等于它跑的是论文里的那一次测量：分数文件可以直接交上去。作者想把补出来的步骤收成可以交给下一次的制品，而不是每次都靠模型重新猜。

制品有四块：整理过的代码、环境、启动实验的入口，以及一份复现说明。基准从 742 篇 ICML 2026 Spotlight 里找到 241 篇有代码的，再抽 50 篇，留下 36 篇、387 个实验、1,029 道题。每题有五次人工核对过的参考分数。成功要同时满足两件事：数值落在参考区间里，以及另一个审核代理确认数字来自新的执行。四个模型在新会话里分别使用原始代码和整理后的制品。原始代码上的平均成功率是 76.4%，制品是 92.6%。Opus 5 从 89.2% 到 94.7%，只高 5.5 个点；Gemini 3.8 Flash 从 67.6% 到 90.8%，高 23.2 个点。四个模型之间的差距从 21.6 个点收到 3.9 个点，下游 API 花费少 16.8% 到 23.7%。拿掉代码或环境，损失最大。这不是全会论文的复现率。论文和代码冲突时跟论文走，制品也可能把错误假设一起留下来。审核用的是 Codex，各家 harness 并不相同。花费不含制作制品和 GPU。没有公开代码仓库。

复现能不能做成，很大一块取决于步骤有没有被写下来。写下来以后，原来较差的模型也能到九成以上。

**链接：** [原文](https://arxiv.org/abs/2611.08452)

### 5. How Should Agents See Code?

仓库级代理找代码，通常靠读文件、文本搜索和 shell，把仓库当成一长串文本。调用关系、文件依赖和语法结构其实是现成的地图。作者把“给不给这张地图”当成一个可以单独开关的设计，而不是默认地图一定能提高修对的比例。

五种地图分别是抽象语法树、调用图、模块依赖、带文档的搜索，以及把它们合在一起。代理可以在任务中途查询。对照只有一个：Claude Code 上的 Haiku 4.5。定位故障时，五种地图的文件 recall@10 是 0.757 到 0.829，基线是 0.717，token 少 25% 到 39%，墙钟时间变长。SWE-bench Pro 上解决率是 44.3% 到 50.6%，基线 49.0%，token 少 17% 到 26%。写测试时，混合和文档最高是 47.8% 和 47.2%，基线 44.7%，但 token 和时间都增加；调用图掉到 37.9%。安全补丁上调用图最高，34.3% 对 28.9%，延迟也更高。代码仓库本次检索 0 star。

地图省的是找代码。难点一旦变成写补丁或写测试，解决率就不再跟着涨。

**链接：** [原文](https://arxiv.org/abs/2611.07286) · [代码](https://github.com/MelikaSepidband/How-Should-Agents-See-Code)

### 6. Detecting Silent Faults at the Environment-Trainer Boundary in Reinforcement Learning

强化学习经常把环境和训练器拆开：另一个进程、另一台机器，甚至另一种语言。交界上的故障不一定报错。奖励被写错、观察被换掉，学习曲线仍可能看起来正常，于是一次坏掉的训练会被当成策略没学好。

他们把交界做成一条线上的协议，再往里注入故障。四个控制环境上最多 23 种跨线故障，外加两种只改训练器日志的故障，从改一个数到改全部。除非每个数都错了，看学习曲线的门槛最多抓住十分之一；和十个无故障种子比，最多抓住 21%。1,060 个最终策略里，728 次边界故障两种曲线检查都通过。其中 723 次的评估分不比无故障种子低过三个标准差，但权重几乎都不同；奖励故障时，日志里的回报也不同。两边各记一本逐步账本，逐步对比。单机的摆、跳和机械臂，以及跨两台机器的摆，每一处跨过去的故障都被抓住并定位到，无故障运行没有误报。摆上的训练时间中位数多 3%。环境侧另记的回合数，抓住了训练器日志里的故障。他们还列出 Gymnasium 1.3、自己的代码，以及别人报告的五个多智能体库里的同类问题。代码仓库本次检索 0 star。测量的是机器人控制，不是编码代理。

曲线和最终分数都正常，仍可能整段训练用的是被改过的奖励。要抓它，得对账每一步传过什么。

**链接：** [原文](https://arxiv.org/abs/2611.08144) · [代码](https://github.com/PlugRL/step-ledger)

### Trending Open-source Projects

#### 1. sand3d

让模型改三维模型，常见的接口是一整份 Blender 脚本，或者一个人用的建模软件。坐标、面的编号和很长的 API，都会占掉上下文。人读得懂的零件结构，模型也经常写不短。

sand3d 是包在 Blender Python 上的一层短程序。零件、边和面按名字取，不靠手算坐标。同一段程序要得到同一份网格。项目自己的对照写着，同一个零件的中位 token，Blender Python 是它的 4.0 倍，CadQuery 是 2.3 倍，FeatureScript 是 6.0 倍，Articraft 是 2.0 倍；整份 API 大约 3,600 token。这次没有重跑这组计数。仓库建于 2026 年 11 月 3 日，本次用 GitHub API 读到 1,065 star、117 fork，Apache-2.0，最近一次推送是 11 月 6 日。周增量没有逐条 star 核对。

它把“零件怎么装、关节怎么动”收成模型写得下的程序。token 更短是项目自己的计数，还不是独立的建模正确率实验。

**链接：** [GitHub](https://github.com/Sandflow-ai/sand3d)

#### 2. devvm

编码代理如果直接跑在人的机器上，就能读到仓库外面的密钥、别的项目和整块磁盘。每做一个项目就手搭一台虚拟机，路径、工具链和登录又得重来一遍。

devvm 给每个项目文件夹一台 Lima 虚拟机。默认只挂载这个文件夹，网络走允许名单，GitHub 和代理的令牌留在宿主机。虚拟机是一份基础镜像的副本，工具链在各台机器之间只读共享。`--clone` 让虚拟机使用自己的克隆，工作区里的代理碰不到人这边的工作树和 `.git`，人之后再用 `git fetch` 把结果取回来审查。文档写明，虚拟机盖不住所有缺口。仓库建于 2026 年 11 月 6 日，本次检索 363 star、13 fork，MIT，最近一次推送是 11 月 8 日。star 是建库两天里的存量，没有另做一周增量。Intel Mac 还没测过。

它把“一个项目一台隔离机器，改动要取回来才进原仓库”做成了现成命令。有多少真实项目在用，目前只有 star 和文档，没有采用调查。

**链接：** [GitHub](https://github.com/devvmhq/devvm)

#### 3. Worktrunk

一个仓库里同时跑好几个编码代理时，每个代理需要自己的工作目录，否则会改到同一批文件。Git 的 worktree 就是干这个的，但新建、进入和删掉都要把分支名和路径写好几遍。

Worktrunk 用分支名来找工作树，路径按模板算出来。`wt switch` 切换，`wt switch -c -x` 可以建好目录再启动一个代理，`wt remove` 把工作树和分支一起收掉。它还带本地钩子，以及写时复制的构建缓存，免得每个目录都完整编译一次。仓库建于 2025 年 10 月 17 日，本次检索 11,953 star、464 fork，许可证是 MIT OR Apache-2.0，最近一次推送是 11 月 7 日。一周里增加了多少 star，没有用 GitHub 接口逐条核对，这里不写增量。

它解决的是并行代理的目录和缓存，不是再包一层对话界面。缓存和钩子能不能在某个具体仓库里省下时间，要看那个仓库自己的构建。

**链接：** [GitHub](https://github.com/max-sixty/worktrunk)
