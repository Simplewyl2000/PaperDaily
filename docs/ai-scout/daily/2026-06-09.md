## 📝 逐条讲解

### Socratic-SWE：用历史轨迹蒸馏技能，自演化生成 SWE 任务
软件工程 agent 后训练最缺的不是“更多随机 bug”，而是能持续击中当前 agent 弱点的可验证训练任务。Socratic-SWE 的思路是把 agent 过去解题时留下的轨迹当成矿，而不是只把它们当作奖励日志：它从成功和失败轨迹里蒸馏出结构化 Agent Skill Registry，记录常见失败、有效修复模式和仓库级操作经验。生成器再用这些技能去真实代码仓库里构造 targeted repair task，也就是专门针对 solver 当前短板的新修复任务。为了避免生成器胡编任务，它要求候选任务经过执行式验证，并用 solver-gradient alignment reward 判断这条任务是否真的有利于改进 solver，而不只是看起来像 SWE 任务。实验覆盖 SWE-bench Verified/Lite/Pro 和 Terminal-Bench 2.0，三轮迭代后 SWE-bench Verified 到 50.40%，说明“轨迹 → 技能 → 新任务 → 新轨迹”的闭环有训练价值。对后训练数据工程来说，这比固定 bug 注入更接近长期可扩展的数据飞轮：任务分布会跟着 agent 的失败模式一起演化。
🔗 链接：https://arxiv.org/abs/2606.07412 ｜ 代码：None

### Terminal-Lego：轨迹“会教”比老师“会做”更重要
很多团队默认用最强 agent 产轨迹做 SFT，因为强 agent 更会解题；Terminal-Lego 这篇直接挑战了这个默认假设。作者把 StackOverflow 真实问题转成 Docker 可验证终端任务，在同一 Terminus-2 harness 下比较不同 teacher 的轨迹教出来的学生。最反直觉的发现是：Claude Opus 4.6 单独做题最强，但它的短捷径轨迹反而教出的 Qwen 学生较弱；DeepSeek-V3.2 单独分数低，却因为更常“先观察、再行动、再验证”，教出的学生泛化更好。论文把这种可见的 inspect-act-verify 结构称为 Environment-Grounded Supervision，并提出 Targeted Observation Ratio 衡量动作是否被路径相关的 prior observation 支撑。15.3k Terminal-Lego 轨迹就让 Qwen3-32B 在 Terminal-Bench 2.0 达 24.3%，接近过去 30 倍数据量的效果。它给后训练团队的启发很直接：不要只筛“最终成功”的轨迹，还要筛“过程是否把环境状态讲清楚、做清楚、验清楚”。
🔗 链接：https://arxiv.org/html/2606.03461v1 ｜ 代码/项目：https://stephen0808.github.io/terminal-lego.github.io/

### Terminal-World：用 Agent Skills 合成终端训练环境
终端 agent 的训练样本很难造，因为一条样本同时需要任务说明、初始文件、依赖环境、验证脚本和多轮轨迹，任何一块对不上都会变成脏数据。Terminal-World 的关键抽象是把 Agent Skill 当作数据合成的中心原语：一个技能天然包含要做什么、什么时候适用、以及怎么执行。系统先从 ClawHub/SkillMP 等来源筛出高质量技能，再组合成 skill teams 和 skill graphs，用它们共同驱动 task instruction、environment blueprint、verifier 和 execution guideline 的生成。环境构建阶段用了 generate-verify-repair 循环，初始文件、setup script、pytest verifier 都要经过执行或一致性检查。最终得到 5,723 个高保真终端训练环境，平均每条轨迹成本约 $0.17；Terminal-World-32B 只用 Nemotron-Terminal 约 1.2% 的数据，就在 Terminal-Bench 2.0 上高出 +4.5 pass@1。它非常贴合本日报关注的“skill 管理 + 环境合成 + 可验证轨迹”：技能不只是推理时提示，也可以成为数据工厂的生产模具。
🔗 链接：https://arxiv.org/html/2605.20876 ｜ 代码：None

### TerminalWorld：从真实终端录像反推可验证评测任务
专家手写的终端 benchmark 往往很难、很干净，但不一定代表开发者每天真实敲的那些命令组合。TerminalWorld 反过来从 asciinema 上的真实终端录制出发，先收集 80,870 条公开录屏，再过滤掉隐私、安全、不可复现和无意义探索，最后由 LLM/agent 反推用户目标、参考脚本、Docker 环境和测试套件。最重要的工程环节是执行反馈：Claude Code 风格的 agent 会实际 build Docker、运行参考解、观察失败并修复环境；测试也要通过 all-passing、nop、partial 三类 trial，避免空状态也能过或正确解被误杀。最终产物是 1,530 个 validated tasks 和 200 个人工复核 Verified 子集，覆盖 18 类真实终端场景和 1,280 个独特命令，其中 91% 命令不在 Terminal-Bench。评测显示最强模型在 Verified 上也只有 62.5%，而且与 Terminal-Bench 的相关性只有 Pearson 0.20。对评测工程来说，它提醒我们：真实世界的 CLI 能力与专家构造难题不是一回事，自动从人类工作流反推 benchmark 是值得投入的新路线。
🔗 链接：https://arxiv.org/html/2605.22535v1 ｜ 代码：https://github.com/EuniAI/TerminalWorld

### Co-Coder：多 agent 编码何时值得并行？
多 agent 编码经常被包装成“像一个开发团队一样并行工作”，但一旦文件之间依赖很强，agent 之间反复传上下文的成本可能吃掉全部并行收益。Co-Coder 把这个问题说清楚：多 agent 编排本质上是分布式系统里的 communication-to-computation trade-off。它先用静态分析和 LLM 生成 Repository Interface Blueprint，得到文件级定义、引用和 import 依赖，再把仓库看成带权依赖图。接着它隔离结构 hub 文件，用 Infomap 做社区发现，把强耦合文件放在同一个 agent 内，同时用 dependency-aware scheduler 暴露真正可并行的部分。28 个真实任务上，Co-Coder 相比顺序和按文件粗暴并行的 baseline，pass rate 最多 +14.0%，wall-clock 最多 2.10x，API 成本最多降 35%。这对 agent 系统工程很有价值：并行不是“多开几个 agent”，而是要先理解代码依赖图，再决定哪里切分、哪里串行、哪里需要集成者。
🔗 链接：https://arxiv.org/html/2606.00953v1 ｜ 代码：https://github.com/Flitternie/CoCoder

### VirBench / gget virus：确定性检索层让科学 agent 可靠用数据库
这项工作虽然发生在生物数据场景，但核心问题与软件工程 agent 很像：agent 不是不聪明，而是它面对的工具/数据基础设施不适合机器稳定调用。作者让 Claude、GPT、Biomni、Edison Analysis 等 agent 去 NCBI Virus 检索病毒序列，构建了 120 条人工校验查询的 VirBench，覆盖 40 种病原体和复杂 metadata filter。没有专用检索层时，agent 准确率差异很大，Claude Sonnet 4 只有 16.9%，GPT-5.5 也仍有残余错误；这些错误会污染后续系统发育、疫苗设计或训练数据构建。gget virus 的做法是把网页里隐含的过滤逻辑重写成确定性 CLI/Python 层：先做 server-side filter，再做本地 metadata/GenBank 过滤，处理分页、重试、缓存数据包和大文件下载。给 agent 明确使用 gget virus 后，所有系统准确率提升到 90% 以上，GPT-5.5 到 99.7%，稳定性也接近 1.0。对 Agent-Friendly Software 的启发是普适的：把遗留 GUI/网页/半结构化数据库改造成可复现、可验证、机器可调用的窄接口，往往比继续换更贵的模型更有效。
🔗 链接：https://arxiv.org/html/2606.06749v1 ｜ 代码：https://github.com/pachterlab/gget ｜ VirBench：https://github.com/lauraluebbert/VirBench

### Terminal-Bench Science：把真实科研工作流变成终端 agent 评测
AI for Science 评测长期偏知识问答或小型推理题，但真正的科研工作流往往发生在终端里：准备数据、装依赖、跑脚本、检查中间产物、调参数、生成报告。Terminal-Bench Science 是 Terminal-Bench 团队把这一套评测方法扩展到自然科学工作流的项目，目标是让科学家把自己的真实计算流程贡献为 agent 任务。它沿用 Harbor/Terminal-Bench 的容器化执行和程序化验证，要求任务可解、可验证、说明清楚、科学上有意义，并且希望发布时 frontier agent 只有 10–20% solve rate，避免一上线就被刷穿。项目还公开了 task proposal rubric，评审会检查 verifiable、well-specified、solvable、difficult、scientifically grounded、outcome-verified 六类标准。相比纯论文 benchmark，这更像一套“科研 workflow → agent eval”的社区生产流程。对后训练软件工程来说，它提供了一个可借鉴模板：让领域专家贡献真实工作流，评测团队负责容器化、验证和 leaderboard 规范化。
🔗 链接：https://github.com/harbor-framework/terminal-bench-science ｜ 代码：https://github.com/harbor-framework/terminal-bench-science

### Statewright：用状态机硬约束 agent 工具空间
很多 agent 失败不是因为不会推理，而是因为在错误阶段拿到了错误工具：计划阶段就改文件、测试阶段乱删目录、修复时跳过验证。Statewright 的做法很直接，把 agent workflow 显式建成状态机，每个状态声明允许使用哪些工具和命令，越权调用会被 MCP gateway 或 hooks 在协议层拒绝，而不是靠 prompt 温柔提醒。比如 planning state 只有只读工具，implementation state 才能编辑，testing state 只能跑白名单测试命令；危险 shell 重定向、`rm`、`sed -i` 等也可以按状态封禁。项目作者报告在一个 5-task SWE-bench 子集上，13B–20B 本地模型从 2/10 提到 10/10，虽然这个结果还需要更大规模复现，但方向非常有工程意义。它解决的真实痛点是 tool explosion 与 workflow drift：agent 不是每轮都需要全量工具，工具空间越小、状态越明确，错误动作越难发生。对 harness engineering 来说，这是“把流程纪律做成机制”的典型案例。
🔗 链接：https://github.com/statewright/statewright ｜ 代码：https://github.com/statewright/statewright

### MRAgent：把 agent 记忆从“检索”改成“重构”
长期运行 agent 的记忆系统常用 RAG：把历史切块、向量检索 top-k、塞回上下文，但这种静态检索遇到多跳、时间线和隐含线索时很容易漏关键证据。MRAgent 的核心观点是“记忆是重构出来的，不是一次性取回来的”。它把记忆组织成 Cue-Tag-Content 图：cue 是实体、时间、属性等细粒度线索，tag 是 cue 到内容之间的关联类型，content 才是具体事件或语义记忆。回答问题时，LLM 不是被动拿 top-k，而是多步选择 cue/tag、读取内容、根据中间证据发现新线索，再剪掉无关路径继续探索。实验在 LoCoMo 和 LongMemEval 上相对 RAG、Mem0、LangMem 等 baseline 有明显提升，最高约 +23%，同时减少 token 和运行成本。它不专门针对 coding agent，但对 skill memory、项目决策记忆、长周期任务 handoff 都有启发：记忆工具应允许 agent 主动“追线索”，而不是只给它一次相似度查询。
🔗 链接：https://arxiv.org/html/2606.06036v1 ｜ 代码：https://github.com/Ji-shuo/MRAgent

### Codebase-Memory MCP：把代码库变成可查询知识图
coding agent 在大仓库里最常见的低效动作，是反复读文件、搜索字符串、再靠上下文窗口临时拼出结构理解。Codebase-Memory MCP 把这件事换成结构化索引：用 tree-sitter 解析多语言代码，把函数、类、调用链、HTTP route、跨服务关系等存进 SQLite 知识图，再通过 MCP 暴露给 Claude Code、Codex、Cursor 等 agent。论文版本报告 66 种语言、14 个结构查询工具，在 31 个真实仓库上达到接近文件探索 agent 的答案质量，但 token 和 tool call 明显更少；仓库近期也持续向更多语言和跨 repo 关系扩展。它的工程价值不在“又一个 memory server”，而在把代码结构变成 agent 原生可查询对象：查调用方、影响半径、入口点、模块 hub，不必每次都靠 `grep` 和全文上下文。对后训练数据与 harness 来说，这类结构化代码环境也能产出更干净的轨迹，因为 agent 的探索动作更可解释、更可审计。需要注意的是，图解析对动态语言和跨包语义仍有边界，但作为 codebase navigation primitive 很值得跟踪。
🔗 链接：https://arxiv.org/html/2603.27277v1 ｜ 代码：https://github.com/DeusData/codebase-memory-mcp

### DeepClaude：把 Claude Code agent loop 接到 Anthropic-compatible 后端
Claude Code 的价值不只在模型，也在它那套成熟的终端 agent loop、工具协议、上下文组织和用户体验。DeepClaude 抓住了这一点：用本地代理和环境变量，把 Claude Code 的 autonomous loop 接到 DeepSeek V4 Pro、OpenRouter、Fireworks 或其它 Anthropic-compatible 后端，同时保留类似 Claude Code 的使用方式。它还提供 backend 状态、成本比较、延迟测试和 session 中切换后端等功能，社区讨论也指出：真正有价值的不是简单改 `ANTHROPIC_BASE_URL`，而是把模型切换、成本跟踪和代理层做顺。这个项目的火点在“harness/model 解耦”：同一个 agent 壳可以跑不同模型，团队可以按任务难度、成本、延迟动态路由。它不等同于证明 DeepSeek 后端一定达到 Claude 质量，也不能绕过 Claude Code 自身兼容性与服务条款风险；但它说明开发者开始把 coding agent runtime 当成可替换、可路由的系统组件。对 Agent-Friendly runtime 工程，这是从“模型产品”走向“模型无关 harness”的信号。
🔗 链接：https://github.com/aattaran/deepclaude ｜ 代码：https://github.com/aattaran/deepclaude

### OpenAI Economic Research Exchange
OpenAI 6 月 8 日发布 Economic Research Exchange，目标是支持外部研究者用更严谨的实证方法研究 AI 对劳动者、企业、机构和宏观经济的影响。它不是模型或 agent 技术发布，因此按低优先级官方源收录，但它有一个与评测工程相关的点：研究将通过结构化项目协作、明确 milestones、数据治理和 review process 来使用 OpenAI 工具与数据集。过去 AI 经济影响讨论容易停留在个案和观点，这个计划试图把问题变成可申请、可审查、可复现的外部研究项目。对本日报的核心方向来说，它不直接提供后训练方法，但它体现了另一类“AI 影响评测基础设施”：用受治理的数据访问和外部研究协议来降低自说自话。后续如果公开 benchmark、匿名化使用数据或生产率测量方法，值得继续跟踪。

## 🔥 社区热点专栏

### 🔥 大佬观点

**OpenAI（Sam Altman / Jakub Pachocki）：自动化 AI researcher 成为三大当前目标之一。**  
6/8 官方计划文再次把“AI 做 AI 研究”放到战略中心，并明确说需要可控、可问责、与人类连接的 automated researcher。它值得注意，因为一旦前沿实验室把自动研究当主线，后训练软件工程里的可验证实验环境、实验审计、benchmark 防作弊和 research harness 都会成为基础设施瓶颈。🔗 https://openai.com/index/built-to-benefit-everyone-our-plan/

**Laura Luebbert / Anthropic Science：生物数据库像“汽车出现前的老城”，agent 需要确定性道路。**  
这条观点把 agent-friendly infrastructure 讲得很形象：软件工程有 git、API、包管理器和版本化文件，生物数据库却仍大量面向人类点击和非确定性脚本。真正的 insight 是，提升科学 agent 可靠性不只是换模型，而是把关键数据路径改造成可复现、可机器调用、可验证的工具层。🔗 https://www.anthropic.com/research/agents-in-biology

**HN / Statewright 社区：工作流纪律要靠协议硬约束，不靠 prompt 建议。**  
Statewright 的 Show HN 讨论集中在一个工程判断：planning、implementation、testing 等阶段应该拥有不同工具空间，越权调用应被 gateway 拒绝。这个观点重要，因为它把“agent 不听话”从提示词问题改造成 runtime/harness 问题，也解释了为什么小模型在受限工具空间里可能突然变可靠。🔗 https://news.ycombinator.com/item?id=48108778

### ⭐ 超火仓库/项目

**Statewright（statewright/statewright）：状态机式 tool gating，让 agent 不能在错误阶段调用错误工具。**  
它火的原因是痛点明确：agent 拥有 40+ 工具时会花大量上下文判断该做什么，还常常跳步骤；Statewright 把工具权限写进状态机，由 MCP/hooks 执行硬拒绝。虽然 SWE-bench 子集结果还需要独立复现，但“协议层约束 > prompt 层建议”的方向很值得 harness 团队跟踪。🔗 https://github.com/statewright/statewright

**Codebase-Memory MCP（DeusData/codebase-memory-mcp）：把代码结构变成 agent 可查的图数据库。**  
它近期在 awesome-harness-engineering 等列表里被反复引用，约 2k stars，主打 66+ 语言 tree-sitter、单静态二进制、SQLite 知识图和 14 个 MCP 查询工具。它解决的是 coding agent 高成本读仓库的问题：让 agent 问“谁调用了这个函数、这次修改影响哪些 route”，而不是每次从文件全文和 grep 重新推理。🔗 https://github.com/DeusData/codebase-memory-mcp

**DeepClaude（aattaran/deepclaude）：Claude Code UX + 可替换模型后端，约 2k stars。**  
社区关注点不是“换个 endpoint”本身，而是把 Claude Code 的成熟 agent loop、后端切换和成本追踪做成一个可操作层。它反映出一个趋势：coding agent 用户希望保留好用的 harness，同时按任务在 DeepSeek/OpenRouter/Fireworks/Anthropic 间路由模型，降低成本并避免单一厂商锁定。🔗 https://github.com/aattaran/deepclaude
