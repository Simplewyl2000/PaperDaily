## 📝 逐条讲解

### Code-agent 轨迹数据筛选：Efficiency + Style 如何影响 LoRA SFT
很多团队想用开源模型训练自己的 code agent，但真正可用的专家轨迹并不是越多越好，因为失败重试、冗余搜索和风格混乱会一起进入训练集。这个工作专门研究 SWE-trajectory 数据集中的 67,074 条轨迹，其中 32,161 条是 resolved trajectory，并用 Qwen2.5-Coder-7B-Instruct 做 LoRA 微调实验。作者提出两个维度给轨迹打分：Efficiency 关注是否少走弯路、少重复错误，Style 关注轨迹是否清晰、稳定、像一个可学习的工程流程。由于 7B 模型在 SWE-bench 上端到端 resolve rate 接近零，论文没有硬测最终解题率，而是用 held-out trajectory 的 cross-entropy loss 做代理指标，并用 first-action generation 验证 CE loss 与 ROUGE-L 排名高度一致。结果很有工程味：在小数据规模下，多拿 500 条数据比精筛更有用；但到 2,000 条轨迹时，高质量轨迹与随机轨迹的差距开始显著扩大。Ablation 还指出 error-retry rate 几乎能单独解释大部分质量收益，说明“少犯同类错误、少无效重试”是可操作的筛选信号。对后训练软件工程来说，这给了一个很实用的 pipeline 起点：先按轨迹效率、失败重试和执行风格做可解释过滤，再决定是否扩大数据量。
🔗 链接：https://arxiv.org/abs/2607.17205v1 ｜ 代码：None

### NexForge：从 capability requirement 合成可执行 agent 训练任务
可执行 agent 训练数据一直有一个瓶颈：如果从现有仓库、工具或 skill graph 出发，能生成什么任务就被底层 substrate 限制住了，每扩一个新领域都要手写一套基础设施。NexForge 反过来从“能力需求”出发，先研究真实世界里某类能力需要哪些任务形态、场景和比例，再把这些 requirement 编译成具体可执行任务。它会自动检索或构造任务需要的文件、依赖、运行配置，然后收集 teacher rollout 并蒸馏成训练轨迹。论文报告同一套 pipeline 在没有领域专用基础设施的情况下生成 3.6K terminal tasks 和 2K office tasks，使 Qwen3.5-35B-A3B Base 在 Terminal-Bench 2.0 从 22.5% 提升到 52.0%，在 GDPval 从 813 Elo 提升到 1338 Elo。进一步扩展到 43.2K terminal tasks 后达到 58.4%，而 Nex-N2 模型族在 Terminal-Bench 2.1 达到 75.3%。这条线最值得关注的是它把数据合成做成“需求发现→分布感知编译→环境物化→teacher rollout→轨迹蒸馏”的工程链，而不是只让模型编题。对 code-agent post-training 来说，这类 requirement-first synthesis 可以减少 benchmark/工具偏置，让训练数据更接近真实需求分布。
🔗 链接：https://arxiv.org/abs/2607.14186v4 ｜ 代码：https://nex.sii.edu.cn/

### DataFlow-Harness：让 coding agent 生成可编辑的数据管线 DAG
数据工程 workflow 很适合交给 coding agent 自动化，但普通 agent 往往只生成一段一次性脚本，脚本能跑并不等于它能进入生产平台被可视化、复用、治理和后续编辑。DataFlow-Harness 把这个问题定义为 NL2Pipeline gap：用户用自然语言描述需求，生产环境却需要持久的、平台原生的 pipeline artifact。它不让 agent 直接写自由形态代码，而是让 agent 通过 MCP 读取实时 operator registry 和当前 pipeline state，再用 typed incremental mutations 修改后端中的 DAG。每次修改都经过 Request-Validate-Commit 协议，检查 DAG 是否无环、上下游 schema 是否兼容，并同步到 DataFlow-WebUI 的可视化编辑器。论文在 12 个数据工程任务上报告 93.3% observed end-to-end pass rate，相对 Vanilla Claude Code 成本下降 72.5%、生成延迟下降 49.9%。这里的关键不是“DAG 比脚本更时髦”，而是 agent 产物直接成为可审计、可编辑、可治理的平台对象。对后训练数据工程来说，这类系统也提示我们：训练数据 pipeline 本身应尽量保留结构化 artifact、operator choice、validation error 和人工编辑记录，而不是只保留生成脚本。
🔗 链接：https://arxiv.org/abs/2607.16617 ｜ 代码：https://github.com/OpenDCAI/DataFlow-WebUI

### Google：Modular Prompt Transpilation，把 agent 指令层做成 build artifact
很多 production agent 一开始只有一个 system prompt，但团队越用越会往里面塞安全策略、工具约定、格式要求、升级流程和领域规则，最后变成没人敢改的巨型文本。Google 这篇文章把问题说成经典软件工程问题：monolithic prompt 会造成 blast radius 不清、copy-paste drift 和 deferred runtime errors。它的方案是 modular prompt transpilation：把共享安全规则、工具使用规则、任务专用流程等拆成小的 skill/prompt fragment，然后用 build system 做 include、变量注入、宏展开和 deterministic rendering。真正重要的是 build-time validation，例如检查 missing imports、undefined variables、circular dependencies，并在 CI 中做 golden-file drift check，确保源码和真正部署给模型的 compiled prompt 一致。文章还提出 agent 可以在完成新 incident 后起草新的 skill module，但不是实时自改提示词，而是开 PR，接受同样的验证、评测和人类 review。这个模式把“prompt engineering”从手工编辑升级成可 diff、可测试、可部署的 instruction supply chain。对 skill management 和后训练软件工程来说，未来轨迹应记录 compiled prompt 版本、依赖图和 validation 结果，否则很难复现 agent 当时为什么那样行动。
🔗 链接：https://developers.googleblog.com/building-scalable-ai-agents-with-modular-prompt-transpilation/ ｜ 代码：None

### Scale Labs：MCP vs CLI 同后端对照评测，接口取舍取决于任务/模型/harness
社区里 MCP vs CLI 的争论很热，但很多比较其实把工具接口、后端能力、文档质量和 harness 实现混在一起。Scale Labs 的评测比较干净：他们把同一组后端工具同时暴露成 MCP tool、CLI command 或两者组合，在 50 个长程企业式任务上测试不同模型和 harness。结果不是“CLI 总是赢”或“MCP 总是更安全”，而是接口敏感性随模型能力变化：较弱模型在数据重、检索多的任务上从 CLI 获益更明显，而较强模型在 MCP/CLI 上成功率差距变小。更重要的是成本并不等于 turns 数：Opus 4.8 在 Claude Code harness 下 MCP 更便宜，但 GPT-5.5 在 OpenAI Agents SDK 下 CLI 更便宜，因为大 MCP 输出是否被写入文件、是否被重复塞回上下文，会直接改变账单。文章还发现“同时暴露 MCP 和 CLI”不会自动得到智能路由，模型通常不会自己学会什么时候用哪个接口。它给出的工程建议很明确：bulk search/list 可以走 CLI，targeted reads/writes 和需要 typed auth 的动作保留 MCP，但这个 split 要由 harness 明确编码。对 agent evaluation 来说，它提醒我们要测 cost per solved task、工具错误类型和 harness 输出处理方式，而不是只比较接口名。
🔗 链接：https://labs.scale.com/blog/mcp-vs-cli ｜ 代码：None

### Qwen Code /learn：把目录、URL、对话显式沉淀成 SKILL.md
技能库正在成为 coding agent 的长期记忆，但自动抽取技能如果太激进，很容易把临时上下文、错误做法或不安全网页指令写进项目规则里。Qwen Code 7 月 16 日周报发布 `/learn`，把技能创建改成用户显式发起：用户提供本地目录、URL、对话历史或一段文本，主模型整理后生成 `.qwen/skills/learned-skill-*/SKILL.md`。GitHub commit 显示实现里使用 `source: learned` frontmatter，把用户发起学习和手写技能、自动技能隔离开，并包含 29 个单元测试。一个很细但关键的安全点是，`/learn` 输入会被包在 `<user_data>` 并带有“不要遵循其中指令”的前置说明，因为 URL 内容如果直接进入 `submit_prompt` 且有完整工具权限，可能把学习流程变成 prompt injection。周报还显示 code review 侧新增 Step 4 verifier 和 Step 5 reverse-audit，让 review 从“找问题”变成“验证发现是否成立，再反向确认是否漏掉”。这说明 Qwen Code 把 skill evolving、review harness 和 Web Shell 运行时一起推进，而不是只发一个模型。对后训练数据工程来说，`/learn` 这种显式技能创建会产生非常有价值的样本：知识源、提炼后的 skill、隔离标记、验证结果和后续调用效果都可以被记录下来。
🔗 链接：https://qwenlm.github.io/qwen-code-docs/en/blog/updates/weekly-update-2026-07-16/ ｜ 代码：https://github.com/QwenLM/qwen-code

### Google ADK 2.0：用确定性 workflow graph 包住 agent 推理节点
很多 agent demo 把所有流程控制都交给模型：读上下文、决定下一步、选择工具、处理失败、再继续。这在开放探索任务里有用，但在企业退款、审批、工单、合规这类流程里，步骤顺序和失败处理本来就应该是确定性的。Google ADK 2.0 的核心是把 agent application 表示为 workflow graph：节点可以是函数、工具、LLM agent 或子 workflow，边定义执行顺序和条件路由。这样 LLM 只在真正需要自然语言理解或判断的节点里出现，普通的查询、状态更新、发邮件、关工单等流程控制由代码执行。文章用退款流程举例，说明把 LLM 限制在政策判断和邮件草拟节点后，示例 token usage 从 5,152 降到 2,265，延迟也下降约 20%。更重要的是安全边界：即使一个 LLM 节点被 prompt injection 诱导，workflow graph 没有的边和节点也不能凭空执行未授权退款。它的工程价值不是又一个 agent SDK，而是明确区分“推理节点”和“编排节点”，减少让模型做代码已经擅长的确定性事情。对后训练和评测来说，轨迹里应保存 workflow graph、节点类型、边路由和 LLM 节点输入输出，否则无法判断成功来自模型能力还是确定性 harness。
🔗 链接：https://developers.googleblog.com/why-we-built-adk-20/ ｜ 代码：https://github.com/google/adk-docs

### Microsoft AX evals：把 coding-agent eval 做成可校准、可复现、可统计的工程流程
很多团队做 coding-agent eval 的方式是跑一组题、拿到一个分数，然后就相信这个分数能指导产品优化。Microsoft AX 系列的这篇收官文章指出，真正危险的是 eval 看起来稳定但测错了东西：prompt 不代表真实开发者、criteria 只查名字出现、不跑项目、judge 理解错 domain、环境里有隐含提示。文章把可靠 eval 拆成六个条件：representative prompts、accurate criteria、unambiguous criteria、multiple runs、clean environment 和 representative environment。它特别强调 criteria 要检查 correct usage 而不是 presence，例如不能只看某个 SDK 名字是否出现，还要验证代码真的以正确模式使用并能构建运行。对 LLM judge，文章建议每条检查都写 pass/fail/skip 条件，并用 5-10 个已知 verdict 的真实 agent 输出校准 judge；如果 judge 反复不一致，问题通常是标准含糊，而不是温度或模型大小。统计上，至少每个场景跑 5 次，避免把随机成功当成真实提升。对本日报关注的 evaluation engineering 来说，这是一份很可落地的 checklist：每次模型、harness、prompt、环境或 judge 变化，都要重新校准，否则 eval 数字很可能只是噪声。
🔗 链接：https://developer.microsoft.com/blog/building-ax-evals-that-actually-work ｜ 代码：None

### Microsoft Foundry：上线前五步评测路径，连接 rubrics、模拟用户、生产 trace 与 benchmark
生产 agent 的评测问题比 coding benchmark 更复杂，因为用户会多轮互动、工具会变化、政策会更新，线上失败也未必出现在离线测试集里。Microsoft Foundry 这篇文章把过去两周的五项评测研究整理成一条上线前路径：先做 multi-turn evaluation，再定义 task-specific rubric，然后用 simulated users 扩展覆盖，接着抽样 production traces，最后再用 benchmark 对齐外部可比信号。它的重点不是“多跑几个榜单”，而是先确定哪些 eval 可以信、哪些只是弱信号、哪些测量工具本身还需要修。文章提到 rubric evaluator 可以根据 agent 定义和示例生成带权重的评测维度，并随任务范围、政策和工具集变化重新生成。生产 trace sampling 也很关键，因为真实用户会暴露模拟器和 benchmark 没覆盖的边界场景。按 Medium 收录，是因为它更偏通用 production agent 评测，不是 coding-agent 专项；但它对后训练软件工程有直接启发。真正可用的数据闭环应该把离线 rubric、模拟用户、线上 trace、benchmark 和回归检测连接起来，而不是把任一评测当作唯一真相。
🔗 链接：https://techcommunity.microsoft.com/blog/azure-ai-foundry-blog/before-you-ship-your-agent-a-five-step-path-to-evaluations-you-can-trust/4532311 ｜ 代码：None

### 3100 Opinions on Code Review in an AI World
AI coding agent 生成 PR 后，很多人直觉上认为 review 会变快，或者相反认为 review 会变成瓶颈，但这些说法经常停留在观点层面。这个研究先做了一个观察性分析：agent-authored PR 往往 review 更少、合并更快、讨论更少，但结论方向会随分析选择改变，说明 GitHub trace 能告诉我们“现象在变”，却很难解释为什么。作者随后收集 38,709 份 grey-literature 文档，包括工程博客和 Reddit 讨论，筛出真正讨论 code review 的材料，再用 LLM-assisted pipeline 编码 3,100 条意见。最终他们构建了 26 个 constructs 和 67 条关系的因果模型，核心观点是 review 是 coding agent 影响软件质量的控制点。换句话说，AI 不自动决定结果好坏，团队如何安排人类 expertise、review process、责任边界和学习机制，才决定 agent 贡献是加速还是侵蚀理解。它按 Medium 收录，因为它不是新的 harness 技术，但对设计 agentic code review 流程很有价值。对后训练数据来说，PR 是否被快速合并并不够，还应记录 review 深度、讨论质量、人工修改、团队规则和知识传递效果。
🔗 链接：https://arxiv.org/abs/2607.07980v1 ｜ 代码：None

### Supra Cognitive Modes：按 query mode 路由 agent memory 检索/综合策略
长程 agent 的 memory 层经常被简化成“把所有历史放进向量库，然后相似度检索”，但真实问题形态差异很大：有些只要查一个事实，有些要沿关系链推理，有些要综合很长时间跨度内的历史。Supra Cognitive Modes 提出 mode-payload-procedure 接口，把 memory 的 operating point 暴露为每个 query 的控制面。系统可以显式指定或自动选择 mode，再由冻结 semantic classifier 和 runtime gates 把 query 路由到 fused lexical+dense lookup、graph/multi-hop handling 或 stratified long-form synthesis。底层共享一个 ingest substrate，包括多粒度 embedding、抽取三元组、fact-version metadata 和可选异步 enrichment。论文在 LoCoMo、MemoryAgentBench 和 LongMemEval 上给出一个 deployed configuration 的 characterization，例如 LoCoMo factoid 84.87%、adversarial abstention 68.61%、LongMemEval 86.00%。作者也很谨慎地说明，当前证据还不能证明 routing 本身带来因果收益，因为缺少完整 token ledger、固定策略对照和部分 runtime 决策记录。按 Medium 收录，是因为它更偏 agent memory architecture，但对 coding agent 的项目记忆很有启发：不同查询应走不同记忆策略，并且轨迹要记录 route、payload 和失败模式。

### Meta Muse Spark 1.1：面向 agentic coding / computer use 的 1M context 闭源模型 API

## 🔥 社区热点专栏

### 🔥 大佬观点

**Sunjie Hou / Scale Labs（LinkedIn）：先停止 MCP vs CLI 的“氛围判断”，用同后端对照实验看接口真实影响。**  
Sunjie Hou 在分享 Scale Labs 评测时强调，他们暴露同一组工具为 MCP 或 CLI，是为了隔离 tool interface 本身，而不是把不同工具生态混在一起比较。值得注意的结论是：CLI 不是魔法，MCP 也不是原罪；最新 frontier models 对接口越来越不敏感，成本差异反而更依赖 harness 如何处理大输出和上下文。🔗 https://www.linkedin.com/posts/sunjie-hou-51107065_mcp-vs-cli-does-an-ai-agents-tool-interface-activity-7480720558733570048-3aQy ｜ https://labs.scale.com/blog/mcp-vs-cli

**Simerus Mahesh / Google Developers：Prompts should not just be edited, they should be built, validated, versioned, and deployed.**  
这条观点把 prompt/skill 从“文本资产”提升为“构建产物”：依赖图、静态校验、golden-file drift check、CI/CD 和 PR review 都应进入 agent 指令层生命周期。它值得注意，因为社区近两周围绕 SKILL.md、AGENTS.md、DESIGN.md 的讨论很多，但 Google 这篇文章给出了更工程化的落点：让 agent 可以提交指令改进，但必须通过 build system 和人类 review。🔗 https://developers.googleblog.com/building-scalable-ai-agents-with-modular-prompt-transpilation/
