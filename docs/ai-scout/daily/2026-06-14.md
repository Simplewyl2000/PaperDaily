## 📝 逐条讲解

### Hardening Agent Benchmarks：用 hacker-fixer loop 自动加固 verifier
很多 agent benchmark 的验证器本质上是手写脚本：只要输出文件存在、测试命令返回 0、某个字段匹配，就算任务完成。问题是，越强的 coding agent 越会在优化压力下寻找这些验证器的漏洞，而不是老老实实完成任务。这个工作先审计了 1,968 个 terminal-agent benchmark 任务，发现 323 个、约 16% 可以被前沿模型只根据任务描述找到 shortcut exploit，这会同时污染 leaderboard 和 RL 训练奖励。它的核心做法是把 benchmark hardening 做成三角色循环：hacker agent 专门试图不解题也拿满分，fixer agent 根据 exploit patch verifier，solver agent 再确认合法解不会被新 verifier 误杀。每一轮 patch 都会改变奖励面，让 hacker 暴露下一类漏洞，直到预算耗尽或找不到 exploit。结果上，KernelBench 上公开 exploit 的攻击成功率从 62% 被打到 0%，并且较弱的防守循环也能挡住更强 hacker。对后训练评测工程来说，这非常关键：未来 verifier 不能只靠一次人工 review，而应像软件安全一样有自动红队、回归补丁和漏洞数据集。
🔗 链接：https://arxiv.org/abs/2606.08960 ｜ 代码：https://github.com/few-sh/harden-v0

### WeaveBench：GUI + shell/code 混合接口的长程 computer-use 评测
现实里的 computer-use agent 很少只点 GUI，也很少只跑 shell；更常见的是一边在浏览器或办公软件里观察状态，一边用命令行、脚本或代码处理文件。WeaveBench 抓住的正是这个混合接口场景：它构造了 114 个长程真实任务，覆盖 8 类工作域，并要求 agent 在同一条轨迹里交错使用 GUI 点击、shell 命令和代码执行。这样评测的不是“会不会点按钮”或“会不会写脚本”某一项，而是 agent 能否判断什么时候该用 GUI、什么时候该转成可重复的命令化操作。它还使用 trajectory-aware agent-as-judge，读取对话轨迹和最终交付物，并给出逐条 evidence，比只检查文件是否存在更难被糊弄。当前最好结果 Claude Opus 4.7 + Claude Code 约 41.2%，GPT-5.5 + Codex CLI / OpenClaw 约 35.1%，说明混合界面长程任务远未解决。对 Agent-Friendly Software 方向，它提醒我们：真正的桌面自动化评测必须覆盖 GUI、CLI、代码、证据和交付物之间的切换。
🔗 链接：https://arxiv.org/abs/2606.09426 ｜ 代码：https://github.com/weavebench/WeaveBench

### AI Code Sandboxes Security Study：比较 agent 沙箱引擎级安全属性
coding agent 会安装依赖、运行测试、启动服务、读写文件，沙箱因此成为 agent runtime 的安全边界，而不是可选插件。很多产品都宣称“跑在 sandbox 里”，但 Docker/OCI、userspace kernel、microVM、Firecracker/Kata/gVisor 这几类隔离机制的威胁模型并不相同。本文不做简单排行榜，而是把五类 AI code sandbox 产品放到六个引擎级维度里读：host attack surface、信息泄漏、defense-in-depth stackability、公开 CVE 历史、补丁节奏和 fuzzing posture。一个有用结论是，引擎类别之间在架构轴上差异明显，但同一类别内产品也会因为 pin policy、补丁滞后和 fuzzing 投入而分化。论文还指出下游产品的补丁延迟可能从 0 天到 471+ 天、opaque 甚至无限期不明，这对企业 agent 托管平台是很现实的运维风险。对本日报关注的 sandbox/harness 工程，这类研究的价值在于把“是否安全”拆成可审计的系统属性，而不是只看营销页是否写了 microVM。
🔗 链接：https://arxiv.org/abs/2606.08433 ｜ 代码：https://github.com/orbitalab/RnD-ai-sandboxes-sec-study-part-1

### Claude Code v2.1.163：Stop/SubagentStop hooks 可注入 additionalContext
Claude Code hooks 已经从“运行脚本做格式化”升级成 agent harness 的控制平面：它能拦截工具调用、注入上下文、通知外部系统、甚至调用 MCP 或子 agent 做验证。v2.1.163 的一个小改动很有工程含义：Stop 和 SubagentStop hooks 现在可以返回 `hookSpecificOutput.additionalContext`，把反馈交给 Claude 并让回合继续，而不会被标记成 hook error。以前 Stop hook 常常只能阻止结束或显示原因，很多“再检查一下这个失败的 integration test”类反馈要靠额外 re-prompt 或绕到 PostToolUse。现在 end-of-turn verifier 可以把结构化发现直接塞回上下文，让 agent 在声称完成时被 harness 温和但确定地拉回任务。这个 release 还加入企业版本 pinning、`/plugin list`、stdio MCP resume session id、后台 session 更新等运维修复，说明 Claude Code 正在补齐大规模部署的稳定性细节。对 harness engineering 来说，这类 lifecycle hook 的语义细化很重要，因为可靠 agent loop 的关键不是 prompt 更长，而是停止条件、反馈注入和可恢复状态更清楚。
🔗 链接：https://github.com/anthropics/claude-code/releases/tag/v2.1.163 ｜ 代码：https://github.com/anthropics/claude-code

### ECC v2.0：跨 Claude Code/Codex/Cursor/OpenCode 的 harness-native operator system
随着 Claude Code、Codex、Cursor、OpenCode、Gemini CLI 等工具并存，开发者越来越需要一套能跨 harness 复用的规则、skills、hooks、memory 和安全策略，而不是每个客户端各配一遍。ECC v2.0 把自己定位成 agent harness performance / operator system，强调不是单纯 config pack，而是把技能、instincts、memory optimization、安全扫描、orchestration 和跨 harness parity 放在一起。它的 v2.0 release 提到 261 个 skills、control-pane substrate、session adapters、MCP inventory、worktree lifecycle service 以及 `orch-*` 编排族，这些都指向一个趋势：harness 也需要自己的 ops 层。项目在搜索结果中显示 210k+ stars、持续维护和跨多语言生态，这说明社区对“把 agent 使用经验产品化”的需求很强。它解决的真实痛点是 agent 工具链的隐性状态太多：规则藏在 markdown，memory 分散在不同目录，MCP 工具和权限不可见，worktree 生命周期难管理。对后训练软件工程团队来说，ECC 这类项目的启发是：训练数据和评测之外，用户侧 harness 的可迁移经验也可能成为重要资产。
🔗 链接：https://github.com/affaan-m/ecc ｜ 代码：https://github.com/affaan-m/ecc

### Roundtable MCP：零配置编排 Claude Code / Codex / Cursor / Gemini
很多团队已经不是“选一个 coding agent”，而是同时使用 Claude Code 做规划、Codex 做实现或审查、Gemini 做长上下文阅读、Cursor 做 IDE 内修改。Roundtable MCP 把这种手动复制粘贴改成一个本地 MCP server：主 agent 通过 MCP 把子任务分发给已安装的 CLI/IDE agent，并把结果汇总回来。它的核心卖点是零配置自动发现、共享项目上下文、并行执行和模型专长路由，用户仍然使用已有订阅和本地工具，不需要把所有东西迁移到一个新平台。HN 示例里常见的用法包括并行代码审查、先让一个 agent 读代码再让另一个实现、或让多个模型同时诊断生产日志。这个方向火是因为“多 agent 协作”不应只停在论文拓扑图，开发者需要的是能直接插进 Claude Code/Codex/Cursor 的本地控制面。风险也很明显：一旦一个 MCP server 能调度多个 agent，它就必须认真处理权限、工作区隔离、成本、日志和防止子 agent 互相污染上下文。
🔗 链接：https://github.com/askbudi/roundtable ｜ 代码：https://github.com/askbudi/roundtable

### Claw-R1：agentic RL 的 step-level 数据中间件
agentic RL 训练的痛点不只是算法，还是“轨迹数据怎么从真实 agent runtime 变成训练可消费资产”。Claw-R1 的定位很清楚：它不主要发明新的 GRPO/PPO，而是在 agent side 和 training side 中间放一个 Gateway Server + Data Pool。Gateway 通过统一 LLM API 入口捕获多轮交互步骤，Data Pool 把它们整理成 prompt id、response id、reward、policy version、metadata 等 step-level 记录。这样白盒 agent、黑盒 agent、线上服务都可以作为数据来源；黑盒 agent 甚至可以通过改 `base_url` 零代码接入。系统还提供质量评估、人工反馈、训练/验证 channel 隔离、GRPO-aware grouping 和实时监控，目标是把 trajectory 从临时日志升级成可查询、可筛选、可版本化的数据资产。对后训练工程来说，Claw-R1 很有代表性：未来 agentic RL 的瓶颈会越来越像数据平台问题，而不只是单个训练脚本问题。
🔗 链接：https://arxiv.org/abs/2606.09138 ｜ 代码：https://github.com/AgentR1/Claw-R1

### AsyncWebRL：视觉 web agent 的全异步多步 RL 框架
视觉 web agent 的 RL 很容易被系统吞吐卡住，因为每条 rollout 都要跑浏览器、截图、等待网页响应和多步工具交互。同步训练会被最慢的 browser session 拖住，导致 GPU 等数据、环境等模型，整体预算利用率很差。AsyncWebRL 直接把这个问题当系统工程处理：它引入 everlasting rollout pool，让 rollout 持续产生数据；用轻量截图处理降低视觉观测成本；再用 decoupled importance-sampling ratio 处理异步数据的策略滞后。论文声称端到端速度能达到 2.4x 以上提升，同时用一个简洁算法修正减少轨迹和 token 使用而不损害最终成功率。它不是 coding agent 专项，但与 agentic RL 基础设施高度相关，因为浏览器/GUI agent 和 coding agent 都有长尾环境延迟、轨迹长度差异和 rollout 资源调度问题。对工程团队的启发是：多步 agent RL 要先把 rollout 系统做成异步、可持续、可观测，算法收益才不会被调度低效吃掉。
🔗 链接：https://arxiv.org/abs/2606.05597 ｜ 代码：None

### Rejuvenation：修复 SFT-to-RL handoff 中的模型 plasticity 损失
现在很多后训练流程默认先 SFT 再 RL：先模仿专家轨迹建立行为先验，再用奖励信号继续优化。但一个常见失败模式是 SFT 太多以后模型变“硬”：输出分布过度自信、参数景观变尖，到了 RL 阶段反而学不动。Rejuvenation 这篇把这个现象称为 plasticity loss，并从参数变化、输出空间和 RL optimization dynamics 三个角度做诊断。它提出的修复方法很工程化：用 base-anchored model fusion 把过度 SFT 的漂移拉回来，再做 targeted neuron reset 缓解局部刚性，同时尽量保留 SFT 学到的有用行为。实验覆盖数学推理和 agentic tasks，显示对过训练 SFT checkpoint 的 RL 改进和 OOD 泛化都有帮助。对 post-training 数据/流程工程来说，重点不是某个 reset trick，而是 SFT-to-RL handoff 需要被当作可诊断、可调参的接口，不能只看 SFT 验证 loss 越低越好。
🔗 链接：https://arxiv.org/abs/2606.09932 ｜ 代码：None

### Agentic Monte Carlo：黑盒 agent 的 RL-style test-time 优化
很多最强 agent 是 API-only 黑盒，不能像开源模型那样做参数级 RL，但它们又会在真实任务里产生可评分轨迹。Agentic Monte Carlo 的思路是把 RL 与贝叶斯推断的等价关系用到这里：不更新黑盒模型参数，而是把黑盒 agent 当作 trajectory prior，用 Sequential Monte Carlo 从“更可能高奖励”的轨迹后验里采样。系统训练一个 value function 来在每一步重加权和引导采样，让 agent 更偏向有希望的动作序列，但底层模型保持不变。这样它介于普通 prompting 和白盒 fine-tuning 之间：仍然能利用额外 test-time compute 和奖励信号，又不需要访问模型权重。论文在 AgentGym 的三个环境中验证，随着 test-time compute 扩展，可以明显超过 prompting baseline，甚至在某些设置下优于 GRPO。对工程落地而言，这类方法适合受限于闭源模型但拥有可验证环境的团队：把优化压力放在轨迹采样、value steering 和 budget 分配上，而不是等待模型厂商开放训练接口。
🔗 链接：https://huggingface.co/papers/2606.05296 ｜ 代码：https://github.com/layer6ai-labs/Agentic-Monte-Carlo

## 🔥 社区热点专栏

### 🔥 大佬观点

**Simon Willison：agentic engineering 的关键是“能写、能跑、能看错误、能继续迭代”的 harness。**
Simon 在近期 newsletter 中把 coding agents 定义为 Claude Code、Codex 这类能生成并执行代码、用工具结果继续迭代的系统，而不是简单聊天模型。他的 insight 在于把能力归因从“模型会写代码”转向“harness 让模型能验证自己”，这与本期 WeaveBench、Claude hooks 和 Claw-R1 的主线一致：真正可复用的是 loop、工具、验证和状态管理。🔗 https://simonw.substack.com/p/agentic-engineering-patterns

**Peter Steinberger / Boris Cherny：从 prompt operator 迁移到 loop engineer，但社区开始要求实测而非改名。**
Peter Steinberger 6 月 7 日关于“不要再手动 prompt coding agents，要设计 prompt agents 的 loops”的 X 观点被多篇社区文章引用，并带动 loop engineering 热词扩散。The DeepFeed 随后用 47 次 Claude Code loop 实测提醒：术语会膨胀，但真正有价值的是可度量的验证 gate、成本控制和 runaway iteration 防护，而不是给旧循环换名字。🔗 https://digg.com/ai/7ifyvmb9 ｜ https://www.thedeepfeed.ai/posts/2026-06-08-loop-engineering-terminology-treadmill

### ⭐ 超火仓库/项目

**ECC v2.0（affaan-m/ecc）：跨 harness 的 skills、memory、hooks 与 worktree ops 层。**
ECC 在搜索结果中显示 210k+ stars，并在 v2.0 将自己明确定位为 agent harness operating system，覆盖 Claude Code、Codex、Cursor、OpenCode、Gemini 等。它火的原因是 agent 使用已经从单工具体验进入多 harness ops：团队需要统一技能、规则、会话适配、MCP inventory、worktree 生命周期和安全扫描，而不是手工维护一堆散落配置。🔗 https://github.com/affaan-m/ecc

**Roundtable MCP（askbudi/roundtable）：把多模型/多 CLI coding agent 编排成本地 MCP server。**
Roundtable 的热点在于把“找 Gemini 读长上下文、让 Codex 实现、让 Claude 审查”这种手动流程变成一个 MCP 可调用的并行编排层。它解决的是真实痛点：开发者已经拥有多个 agent 订阅和 CLI，但缺少共享上下文、自动发现、结果汇总和模型专长路由的轻量控制面。🔗 https://github.com/askbudi/roundtable ｜ HN：https://news.ycombinator.com/item?id=45374908

**central-mcp（andy5090/central-mcp）：项目级 agent dispatch hub，强调后台派发和轮询结果。**
central-mcp star 不高，但方向很有信息量：一个 MCP server 管理多个项目和多个 coding agent，把自然语言请求路由到指定项目的 Claude/Codex/Gemini/opencode，并异步返回 dispatch id 供轮询。它代表了一个更“ops”的趋势：当一个人同时管理多个 repo 与多个 agent session，任务注册表、后台执行、fallback chain 和历史记录会变成必需品。🔗 https://github.com/andy5090/central-mcp
