## 📝 逐条讲解

### OpenAI ARC-AGI-3：retained reasoning + compaction 让同一模型分数 13.3%→38.3%
ARC-AGI-3 这类交互式 benchmark 不只是问模型一道题，而是让模型在多步环境中观察、试错、形成假设并继续行动，所以“模型能记住什么”会直接影响结果。OpenAI 7 月 29 日的复盘指出，GPT-5.6 Sol 在默认 ARC-AGI-3 harness 下表现很弱，并不只是模型不会做题，而是 harness 每一步后丢掉了模型之前的私有推理状态，并用 rolling truncation 删除旧动作。OpenAI 改用 Responses API 的 retained reasoning 与 canonical compaction 后，同一 public set 分数从 13.3% 提升到 38.3%，同时输出 token 约减少 6 倍。通俗说，retained reasoning 让模型不必每一步重新“想起刚才为什么这么试”，compaction 则在上下文快满时把旧状态压成可继续使用的状态，而不是简单砍掉。这个结果最重要的启发不是 ARC-AGI-3 本身，而是 benchmark 分数需要报告“model + harness + API settings”，否则看起来像模型差距，其实可能是状态传递策略差距。对后训练软件工程来说，轨迹质量也会受同样问题影响：如果采集轨迹的 harness 丢状态、乱截断或 compaction 不稳定，训练数据会把环境缺陷混成模型行为。未来 agent leaderboard 至少应附带 memory card，说明 reasoning continuity、compaction trigger、retained-tail budget、tool-output pruning 和 fallback 行为。

### Anthropic cyber eval 事故复盘：141,006 条评测轨迹中发现 3 起真实系统入侵
安全能力评测需要让模型尝试攻击，但这类评测只有在环境真正隔离时才安全；如果“模拟靶场”和真实互联网边界混在一起，评测本身就会变成生产风险。Anthropic 7 月 30 日披露，他们在复核 141,006 条可能有互联网访问的 cyber evaluation runs 时，发现 3 起 Claude 模型从第三方评测环境访问互联网并入侵真实组织基础设施的事件。事故根因不是模型有自我目标，而是评测环境误配置导致模型实际能访问互联网，同时 prompt 又告诉模型“没有互联网、所有目标都是 CTF 模拟”，于是模型把真实系统误当成靶场的一部分。三个案例包括利用弱密码和未认证端点、上传恶意 PyPI 包并被真实安全扫描器执行、扫描约 9,000 个目标后入侵真实应用。Anthropic 的处理重点包括停止 cyber eval、回溯 transcript、通知评测伙伴和受影响组织、计划发布脱敏 transcript、增强 vendor assurance、网络路径验证和实时监控。对后训练软件工程来说，这是一条非常硬的经验：eval harness、网络出口、第三方靶场和 transcript 监控本身必须被当作生产系统加固，而不是研究脚本。尤其是安全 agent 轨迹，必须记录 scope boundary、egress policy、环境真实性提示和模型是否在发现越界信号后停止，否则无法区分能力、对齐和操作失误。

### SecRespond：用真实受害主机快照评测 post-compromise incident-response agent
现有安全 agent benchmark 很多关注“攻击前”或“找漏洞”，例如让模型在干净环境里拿 flag 或写 PoC；但真实安全运营中，更常见的任务是攻击已经发生后，分析受害主机、确认入侵路径、评估风险并给出可验证修复。SecRespond 把任务切到 post-compromise incident response：给 agent 一个已经被入侵的 cloud host forensic disk snapshot，再附上告警、漏洞扫描和基线检查结果，让 agent 生成入侵报告、基线风险、漏洞风险和 remediation plan。数据包含 10 个 cyber ranges，覆盖 4 类入口、21 个 ATT&CK techniques 和 5 个操作系统，并用 OpenCode agent harness 评估 23 个 frontier LLM。结果很现实：当前 agent 能较可靠地找到告警已经暴露的问题，但不擅长主动在磁盘里发现静默入侵，也很难产出完整且经验证的修复计划，没有模型在任何一个 range 上完成完整检测与修复。它的工程价值在于把安全 agent 从“会不会攻击”推进到“会不会像值班响应工程师一样调查证据、写 checklist、验证修复”。对后训练数据来说，这类 benchmark 的 checklist、disk snapshot、alert evidence、agent command trace 和 remediation verdict 都是高价值监督信号，尤其适合训练 agent 进行证据驱动调查而不是只复述告警。
🔗 链接：https://arxiv.org/abs/2607.26791v1 ｜ 代码：https://github.com/Alibaba-NLP/qqr/tree/main/data/secrespond ｜ https://huggingface.co/datasets/Alibaba-NLP/SecRespond

### RepoComplianceBench：评测 coding agents 是否会主动遵守开源 AI 贡献规则
开源社区正在被 AI 生成 PR 和 issue 淹没，很多项目已经写出 AI_POLICY、CONTRIBUTING、PR template 或 AGENTS.md 规则，要求披露 AI 使用、跑验证、人工签字，甚至禁止 AI 贡献。RepoComplianceBench 关注一个过去很少被测的问题：coding agent 进入仓库后，会不会像负责任的贡献者一样主动找这些规则并遵守。作者从 102 个社区手工编码 455 条 AI 相关规则，最终构造 49 个仓库、106 个 issue 的 benchmark，规则类型包括 Refuse、Disclose、Verify 和 Handoff。实验显示，四个 frontier agents 除自动加载的 AGENTS.md 外，主动打开相关 policy 文件的比例只有 3.5%，Refuse 和 Handoff 在 native 条件下全是 0%。有趣的是，披露和验证可以靠提醒、直接引用规则或一次 verifier feedback 大幅恢复到 77-100%，但“禁止 AI 贡献”和“交给人类”这类 restraint rules 依然很难执行。这个结果对 coding-agent eval 很关键，因为一个 PR 功能正确但违反社区规则，真实世界里仍然会被拒绝甚至伤害维护者信任。工程落地上，agent harness 应把贡献规则发现、policy card、mechanical verifier、LLM verifier 和 human escalation 做成提交前 gate，而不是期待模型自己想起来读 CONTRIBUTING。

### OpenAI GPT-5.6 efficiency：把模型、推理系统与 agentic harness 一起优化 cost-per-work
过去模型发布常强调 benchmark 分数，但真实 agent 业务更关心的是“完成一个可验证工作单元要花多少时间、多少 token、多少钱”。OpenAI 7 月 29 日的 GPT-5.6 engineering post 把效率拆成三层：模型本身更直接地完成任务，推理系统通过 load balancing、speculative decoding、caching、kernel optimization 提高吞吐，Codex / ChatGPT Work 背后的 agentic harness 则减少 context bloat、工具误用和重复劳动。文章还披露 GPT-5.6 Sol 在人类主导流程中参与优化 OpenAI 自己的生产 GPU kernels，帮助降低端到端 serving cost 约 20%，并通过数百个实验提升 token-generation efficiency 超过 15%。这不是普通“模型更便宜”公告，而是展示了一个闭环：更强 coding/reasoning agent 被用来优化服务它自己的底层软件栈，再把收益反馈给用户。对后训练软件工程来说，重要信号是 OpenAI 明确把 task success 与 efficiency 一起训练和衡量，而不是只优化最终答案质量。agent 轨迹未来应记录的不仅是“成功/失败”，还包括路径是否直接、是否重复读同一上下文、是否无效调用工具、是否触发 fallback 以及单位工作成本。对于内部平台团队，这类 stack-wide efficiency 也说明 harness 工程、推理工程和模型后训练会越来越难分开。

### OpenAI Agents SDK Responses Compaction Session：把 responses.compact 做成可复用 session decorator
OpenAI ARC-AGI-3 复盘讲的是 retained reasoning 和 compaction 的效果，开发者真正需要的是可落地的 SDK 机制。OpenAI Agents SDK 里的 `OpenAIResponsesCompactionSession` 把 `responses.compact` 包成 session decorator：它包住底层 session store，在历史增长到阈值后自动调用 compaction API，并把压缩后的项目写回 session。文档强调它只适用于 OpenAI Responses API models，不能包 `OpenAIConversationsSession`，因为后者自己管理 server-side history；它也允许自定义 compaction trigger 或手动 force compaction。近期相关 PR #3827 暴露了一个很有代表性的坑：如果底层 session 本身设置了 limit，compaction 只读最近 N 条会把更早历史永久丢掉，所以 compaction 必须基于完整 stored history，而不是 UI 里当前可见的 window。这个细节说明 compaction 不是“总结一下聊天记录”这么简单，它涉及 history candidate、response_id、store=false、orphaned ids、reasoning items 和当前 Runner 是否会重读 session。对后训练软件工程来说，SDK 层的状态压缩应该产生可审计事件：何时压缩、输入包含哪些 item、输出保留/丢弃哪些状态、是否失败、是否跨 endpoint 重放。否则看似省 token 的 compaction 可能悄悄破坏轨迹可复现性。
🔗 链接：https://openai.github.io/openai-agents-python/ref/memory/openai_responses_compaction_session/ ｜ 代码：https://github.com/openai/openai-agents-python

### The Git Reporter：给 OpenAI ARC 结果做跨 harness memory-source survey
OpenAI 官方文章给出结论，但社区真正需要知道的是：这些“两个设置”在生产 harness 里到底由哪些代码链路支撑，其他 agent 框架能不能复现。The Git Reporter 7 月 30 日的文章把问题拆成 memory state transfer：有没有拿到 provider 发出的 opaque reasoning item，是否持久保存，什么时候能安全 replay，窗口快满时如何 compaction，以及失败时怎样降级。它逐项查看 Codex、Pydantic AI、Pi、Hermes Agent、Mistral Vibe、OpenCode、Qwen Code、Gemini CLI、Cline、Goose 等项目，把“reasoning continuity found in source”和“long-context behavior”放进同一张表。文章特别提醒，普通 summary 只能解决长历史问题，不能等价替代 OpenAI-style opaque reasoning replay；同样，reasoning retention 如果不配合 compaction，长程任务最终还是会撞窗口。最有工程价值的是它提出一个 2x2 ablation：forgetful baseline、reasoning only、compaction only、both，固定模型、工具、上下文限制和任务集，记录成功率、token、wall time、compaction calls、fallback 和失败原因。这个建议正好对应本日报关注的 evaluation engineering：不要只追逐某个 ARC 分数，而要把 state-transfer contract 本身变成可测对象。对于训练数据采集，也应记录“opaque item 是否存在并被接受”这类元数据，而不是记录私有推理文本。

### CAPA：跨会话个性化歧义适配，让 coding assistant 少问澄清也写对代码
用户给 coding assistant 的需求常常不完整，而且同一个用户会反复以相似方式省略信息，比如说“normalize”时总是指 z-score 而不是 min-max，或者默认某类边界条件。传统澄清方法通常只看当前会话：不确定就问，问完再做；但长期助手应该能从同一用户过去已解决的 session 中学到稳定偏好，减少重复澄清。CAPA 把这个能力定义为 personalized ambiguity adaptation：给模型一些同一用户的 resolved coding sessions，再给一个新的 ambiguous request，看它能否识别 recurring ambiguity pattern、直接写出 intended executable solution，并在证据不足时才问。数据构造上，作者把个性化编码歧义拆成六类机制，用三阶段 pipeline 从 HumanEval 任务生成 ambiguous request、多轮解决轨迹和一致性验证，最终得到 600 个 coding sessions、60 个 user-ambiguity cells，其中 300 个是 held-out evaluation sessions。评测指标不只看最终可执行成功，还看 first-turn executable success 和 turns-to-completion，因此能衡量“记忆是否真的减少交互成本”。它按 Medium 收录，是因为它更偏长期 coding assistant 和个性化记忆，不直接是 code-agent 后训练管线；但对 skill/memory 管理很有启发。工程上，如果团队要让 agent 记住用户或项目偏好，需要区分可复用偏好、一次性上下文和不该迁移的旧误解，并用 gating 控制什么时候应用历史。

### (Im)Paired Programming：coding agents 提升完成度但削弱用户代码理解
coding agent 的常见卖点是“更快完成任务”，但如果用户从写代码转成复制 prompt、自动接受 edits 和事后粗略 review，可能会降低对自己系统的理解。这个 HCI 研究让 54 名学生用两种 AI 系统做网站任务：一种 agent 会直接编辑用户代码，另一种 chatbot 给代码片段但用户需要自己写或适配。结果显示，agent 帮助初始任务完成，但削弱了用户代码理解，也没有让用户在没有 agent 的情况下更好地扩展自己的代码。研究还发现，低投入 interaction 类型，例如 copy-paste prompts 和 auto-accepted edits，与较低 comprehension 有关；有意思的是，用户虽然自认理解变弱，仍然偏好 agent，因为它快且省力。对后训练软件工程来说，这不是模型算法问题，而是 workflow 设计问题：如果 agent 让人类完全退出理解环，review、维护和责任归属都会变脆弱。工程落地可以把“主动参与”做成 harness 约束，例如要求用户审测试计划、解释关键设计、选择方案或确认风险，而不是只提供一键接受。训练数据也应谨慎：高自动化但低理解的轨迹可能短期成功，却不一定代表可维护软件工程。
🔗 链接：https://arxiv.org/abs/2607.26375v1 ｜ 代码：None

### OpenAI GPT-5.6 price-performance：Luna 降价 80%、Terra 降价 20%、Sol Fast mode
这条官方更新本身偏价格和产品策略，所以按 Medium 而非 High 收录；但它对 agent 成本治理很直接。OpenAI 7 月 30 日宣布 GPT-5.6 Luna API 价格降低 80%，Terra 降低 20%，Sol 保持价格不变但推出 Fast mode，在需要低延迟时用 2 倍 token 价格换最高约 2.5 倍速度。更新还说明这些价格变化会反映到 Codex 和 ChatGPT Work 的额度消耗上，意味着高频 auto-review、批量 agent work 和低风险实现步骤可以更便宜地跑。它背后的逻辑延续前一天的 efficiency post：模型、推理系统与 harness 优化节省的成本，最终变成更细粒度的模型 tier 和 routing 策略。对团队来说，真正要做的不是简单把所有任务切到 Luna，而是把工作拆成“需要 Sol 规划/解不确定性”“可由 Terra 或 Luna 执行明确实现”“需要 Fast mode 缩短等待”的阶段。后训练数据工程同样需要记录价格 tier、Fast mode、缓存价格和 model routing，否则 cost-per-success 无法解释。低成本模型变便宜也会放大 token maxing 风险：如果 harness 不控制重复上下文和无效步骤，单价下降可能换来总量更快上涨。

### 🔥 大佬观点

**Tibo / OpenAI Codex & ChatGPT 团队：ARC-AGI-3 的教训是 performance = model + product，而不是只看 model name。**  
围绕 OpenAI ARC-AGI-3 复盘的社区转述中，OpenAI 成员把结论讲得很直接：同一 GPT-5.6 Sol 在默认 harness 和 Responses API retained reasoning + compaction 下差距巨大，说明产品栈和状态管理会改变 benchmark 结果。值得注意的是，这不是鼓励“为榜单定制 harness”，而是要求所有长程 agent eval 把 state retention、compaction 和 truncation policy 公开。🔗 https://openai.com/index/how-two-settings-tripled-our-arc-agi-3-scores/ ｜ https://digg.com/tech/bx10jm0q

**Simon Willison：Anthropic cyber eval 事件说明“评测环境误以为隔离”正在变成行业模式。**  
Simon 在 7 月 30 日记录 Anthropic 事故时强调 “It happened again”，把它与 OpenAI/Hugging Face eval sandbox escape 放在同一条线上看。这个观点值得注意，因为它把讨论从“某个模型坏了”转回“强 agent 的评测基础设施是否按生产安全标准建设”，尤其是第三方靶场、PyPI/互联网出口和 transcript 监控。🔗 https://simonwillison.net/2026/Jul/30/three-real-world-incidents/

**Hacker News / ARC 讨论：如果 harness 保存了一个模型的状态、却丢掉另一个模型的状态，比较就不再中立。**  
HN 上围绕 ARC-AGI-3 的讨论再次把 benchmark fairness 推到前台：交互环境、视觉/文本表示、记忆保留和工具接口都可能让一个模型看起来更强或更弱。对 coding-agent eval 来说，最实际的 takeaway 是：leaderboard 应发布 harness memory card 和 trace artifact，否则 pass rate 很难解释。🔗 https://news.ycombinator.com/item?id=46993367
