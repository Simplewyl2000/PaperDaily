## 逐条讲解

### AutoEnvScaling：Automating the Data Flywheel with Terminal Agents
训练终端 agent（在命令行里敲命令完成软件工程、科研任务的 agent）需要大量"多样且可验证"的 RL 环境，而这些环境目前几乎都由研究员手工设计，供给速度被人力卡死。Microsoft Research 这篇的关键想法是：把"设计一个新环境"本身当成一个终端任务交给 agent 去做——proposer agent 在真实终端里写 Dockerfile、准备数据、写验证脚本并自测，而不是只靠一段 prompt 让模型"想象"出环境。更妙的是它形成闭环：proposer 看正在训练的 solver 的 rollout（做对了什么、卡在哪里）来决定下一批环境出什么，solver 的新 rollout 又指导下一轮出题。相比纯 prompt 生成，有效环境率最高提升 25 倍，单个有效环境成本降低最多 75%；用 GPT-5.6-sol 造的环境训练 Qwen3.5-35B-A3B，Terminal-Bench 2.1 比对照组高 4.3 分；让同一个 Qwen3.6-35B-A3B 同时扮演出题人和解题人，TB2.1 提升 12.2 分。它还泛化到 SWE、computer use、专业工作和 GPU kernel 编程四类环境。对后训练数据工程最大的启发是："造环境"值得被当作一个可执行、可验证的 agent 任务来工程化，而不是一次性的 prompt 工程；"根据 solver 弱点反向出题"也是当前最实用的课程设计思路。
🔗 链接：https://arxiv.org/abs/2610.14163 ｜ 代码：https://aka.ms/autoenvscaling（项目页 https://aka.ms/autoenvscaling-page）

### OpenAI：Maintaining software with the GPT-6 family
coding agent 让大家写代码更快，代价是维护负担同步上涨：死代码、做完没清理的 A/B 实验、坏掉的测试越积越多。过去 OpenAI Core Experimentation 团队靠复杂的静态分析 + 运行时日志来找可删代码，但反射、"平时不跑但事故时要用的开关"这类边界情况总会导致误删事故。这篇博客讲他们如何用 GPT-6 Astra 做"带证据的清理"：只给一句含糊的 prompt（"帮我找并清理死代码，可以查 Slack、Statsig 或任何来源确认它确实没人用"），模型会自己翻历史 PR、Slack 讨论、项目追踪器，甚至读生产环境的性能 profiling 表确认这些代码行从未被执行，并为每处删除写理由。5 名工程师兼职两周合并了 1,400 多个 PR、删掉 80 多万行代码，某服务镜像从 3.31GB 降到 1.72GB。更难的"陈旧实验清理"中，他们让 Astra 自己写 `/goal` 长 prompt，按每个实验的 CPU 开销排序，找出一个把开关映射到"所有功能"导致 CPU 扇出的单行配置（标记为"永久"，模型主动提交人工复核），删除后主服务 CPU 省 0.42%。成本对比也很有参考价值：同一任务 GPT-6.1 Sol Ultra 以 14% 的 API 成本拿到 Astra 92% 的有效发现，差异主要集中在"被其他开关依赖的常量开关"上。对我们而言，这是一份非常具体的"真实世界长程软件维护任务"样本——证据链、人工复核点、按模型/effort 的成本-召回曲线，都可以直接借鉴为评测任务设计与验收标准。
🔗 链接：https://developers.openai.com/blog/maintaining-software-with-the-gpt-6-family ｜ 代码：None

### SWEPatchTest：Evaluating Software Tests Beyond Reproduction
coding agent 常常先写测试、再用测试判断自己的补丁对不对。常见的测试生成评测只检查"测试在原 bug 代码上失败、在参考补丁上通过"，但这样的测试仍可能放过错误补丁、或者冤枉正确但写法不同的补丁。SWEPatchTest 从 SWE-bench Pro、SWE-bench Multilingual、DeepSWE 选出 619 个任务，并从真实 agent 轨迹里收集了 82,579 个候选补丁（有对有错），把每个测试集在 buggy 代码和所有候选补丁上重放，同时度量三件事：能否复现问题、能否接受正确补丁、能否拒绝错误补丁。三者同时满足的 Joint Validation Rate（JVR）暴露了巨大落差：最好的配置 59.29% 的任务能"复现参考转变"，JVR 却只有 9.21%。作者进一步把 JVR 当作数据筛选信号，挑选高质量测试生成示范做 SFT，JVR 约提升 3 倍，并且下游三个 SWE-bench 上的修复能力也提升。它告诉我们：评价测试的标准应从"对单一参考补丁的二元判断"升级为"对补丁分布的区分能力"，而这个区分能力本身就是一个可执行的训练数据过滤器。
🔗 链接：https://arxiv.org/abs/2610.18004 ｜ 代码：None

### CodeWalk：Generating Coding Benchmarks by Walking a Problem Graph
高质量 coding 题目很贵：SWE-bench 需要大量人工整理，合成题目又要花大量模型调用去生成和验证。CodeWalk 的思路像"搭乐高"：把已经验证过的原子题目当节点，沿题目图游走、把多个原子题组合成 level-N 的复合任务（例如把多个 bug 放进同一程序做多 bug 修复）。一个组合任务只有满足两个条件才保留：每个原子子问题在组合后依然"未被解决"，且联合参考解能通过评测时用的同一检查——整个构造流程纯程序化，不需要任何 LLM 生成或验证。作者在多 bug 修复、证明补全、复杂度分析、克隆等价判断四种设定中实例化，前沿模型的表现都随组合深度增加而下降，说明难度可以被"旋钮式"调节。生成的任务还能直接当训练数据：拒绝采样微调后 Qwen3.5-9B 在每个组合层级都有提升。对数据工程而言，这是一条近乎零边际成本、天然带可执行验证的难度扩展路线，特别适合给 RL 补充"难但可验证"的题目。
🔗 链接：https://arxiv.org/abs/2610.15345 ｜ 代码：None

### Long-Horizon-Terminal-Bench 2.0
长程终端基准想回答的不是"最后状态对不对"，而是"agent 能否在几小时的工作流中持续推进"。LHTB 2.0 保留了 v1 的 46 个任务，修正了任务与评测基础设施中的缺陷，并扩展出 31 个新任务，共 77 个任务、13 个领域。新任务通过一条"重建任务流水线"批量生产：从一个能工作的科研/工程产物出发，用参数化参考实现生成多个场景，公开 6 个作为行为证据、留出 3 个用于评测，再配合稠密的"进度阶梯"奖励部分进展，同时防止 agent 背诵公开输出。评测时长从 90 分钟延长到 3 小时，每 30 分钟记录一次 verifier checkpoint，可以直接看到一次运行内的持续进步曲线。在 15 个前沿模型的 1,145 次评分运行中，GPT-6-astra 稠密平均奖励 0.69 领先；在 30 个重建任务上，二元 verifier 平均分只有 0.221，而稠密阶梯平均分 0.653，说明只看最终结果会丢掉大量中间进展信息。"参数化参考实现 + 公开/留出场景切分"是一个可复用的防泄漏造题模式，"稠密阶梯"对长程 RL 的奖励设计也有直接借鉴意义。
🔗 链接：https://arxiv.org/abs/2610.14146 ｜ 代码：None

### SWEeper-Bench：Can Agents Discover Bugs in Interactive Software?
coding agent 越来越多地直接"生成一个可交互的软件"而不是回复文本，但很多 bug 只有在多步交互之后才会暴露，目前仍要靠用户发现、反馈、等修复。现有基准大多假设 bug 已被定位（给了 issue），没有评测 agent "自己发现交互相关故障"的能力。SWEeper-Bench 从 200 个常用开源 Web 应用的真实 bug 修复中构造 200 个任务，只给 agent 代码库和一个开放式请求（比如"找出并修复 Focalboard 看板分享与成员管理的问题"），由于这些 bug 很难从代码静态看出，agent 必须自己设计交互测试去触发。修复结果由一个 agentic verifier 在浏览器中按"用户实际会看到什么"来判定。15 个前沿 agent 中最好的仅通过 59.0%；分阶段轨迹分析显示最大瓶颈是"识别出错误行为"——agent 常常已经到了相关功能，却从未触发故障，或触发了也没认出来。这把评测重心从"修已知 bug"推到"主动 QA"，对构造需要 agent 自建测试与观察的训练环境很有参考价值。
🔗 链接：https://arxiv.org/abs/2610.14096 ｜ 代码：None

### SpecGuardBench：Can Coding Agents Construct Reliable Validation Harnesses from Natural Language Specifications?
测试是判断 agent 代码是否正确的主要证据，但"通过现有测试"并不等于"满足自然语言规格"。可靠的验证需要两样东西：忠实反映规格的检查（check），以及充分覆盖代码的测试场景（scenario），目前没有基准衡量 agent 能否自己构造这类证据。SpecGuardBench 从 13 个真实仓库构造 291 个任务，覆盖函数后置条件、交互协议等 8 类验证逻辑；agent 拿到规格、仓库上下文和一份参考实现，要搭出一个"验证 harness"：检查必须拒绝违反规格的实现、同时接受所有符合规格的实现。四个闭源/开源 coding agent 中，没有一个能在超过 63% 的任务上被判为"忠实"。瓶颈不在探索测试场景，而在写出忠实的检查——agent 明显倾向于照着参考实现写断言，于是会拒绝规格本来允许的其他实现。这对"用 agent 自动写 verifier/reward"的数据管线是一个直接警示：给 agent 看参考解可能让 verifier 过拟合到某一种实现。
🔗 链接：https://arxiv.org/abs/2610.16870 ｜ 代码：None

### ClawLoop：Self-Improving Agents via Harness-Native Training Loop
LLM agent 越来越多地运行在通用 harness 里（在沙箱工作区直接操作文件系统和 shell），但面向这类 agent 的后训练流水线很少，而且大多是"一次性 + 依赖 teacher"：强模型合成任务、采集轨迹，目标模型训一次，评测结果只给人看、不回灌到流程中。这样做的上限被外部模型能力和人类先验锁死。ClawLoop 把三个阶段组成一个自持循环：任务合成（两种互补的构造例程 + 依据诊断结果递增难度 + 无 agent 与有 agent 两类任务校验）、训练（SFT 和/或 RL）、诊断与反馈（分析 rollout 行为写出"能力分析报告"，作为下一轮出题的依据），全程不需要外部 teacher。以 Qwen3.6-27B 作为循环模型，在 SkillsBench、Claw-Eval-Live、ClawGym-Bench 上持续提升；把迭代精炼出的任务拿去训练更小的 Qwen3.5-4B / 9B 也全面有收益，说明数据质量不依赖循环模型本身。"诊断报告→出题"这一步是很实用的工程抓手：把评测输出结构化成下一轮数据合成的输入。
🔗 链接：https://arxiv.org/abs/2610.14118 ｜ 代码：None

### ANCHOR：Assessing Naturalistic Constraint Hierarchies and Ordering in Repository-Grounded Agentic Coding
在真实仓库里，功能正确的补丁不一定"可接受"：开发者还会约束改动范围、操作顺序、验证方式、工具使用和汇报方式。这种"工程约束遵循"能力在当前评测里基本看不到。ANCHOR 从真实开发者交互中提炼出 10 大类、78 种叶子约束类型，用自动流水线把与任务相关的原子约束实例化，并组合成 AND（同时满足）/ THEN（先后顺序）/ PRIORITY（冲突时谁优先）关系；评测时同时检查代码 diff 和执行轨迹，混合规则判定与 LLM judge。在 2 个 scaffold × 10 个基础模型共 19 种配置、358 个任务上，最强的 Claude Opus 4.8 + Cline 原子约束遵循率 70.1%、关系遵循 63.7%，但"所有检查项全过"只有 19.0% 的任务；5 名工程师审计约束可行性 94%、真实性 96%。失败主要集中在流程顺序、工具使用纪律和汇报上，且模型与 scaffold 存在明显交互。这类"过程约束"非常适合做成轨迹级 reward 或 SFT 过滤规则，弥补只看最终测试的盲区。
🔗 链接：https://arxiv.org/abs/2610.16859 ｜ 代码：None

### SWE-Maintain：Do Modifications Made by Coding Agents Make Subsequent Software Maintenance Harder?
coding agent 越来越多地长期维护仓库，每次改动都会成为下一个任务的起点；但现有基准要么从开发者写的代码起步，要么分不清"后续任务本身难"和"agent 之前的改动造成的难"。SWE-Maintain 构造了来自 50 个真实 Python 仓库的 100 个"三事件维护序列"，每一步都有经过认证的隐藏测试；同一个后续任务分别从"开发者的前序补丁"（Developer-History）和"agent 自己的前序改动"（Agent-History）出发各评一次，用同一 agent、同一测试。在 5 个编码系统、2 个基座模型、1,996 对后续事件上，Agent-History 让后续任务解决率平均下降 5.6 个百分点；若要求之前的测试也全部通过，差距扩大到 14.0 点。原因很具体：三分之二的 Agent-History 起点仓库已经有旧测试失败，从这种状态出发最终全绿的只有 1.9%；而当继承的代码通过了旧测试时，劣势就消失了。结论对评测和训练都有用：评测应包含 agent 自己产生的历史，训练奖励应显式惩罚"破坏既有行为"，而不只看当前任务。
🔗 链接：https://arxiv.org/abs/2610.14768 ｜ 代码：None

### SPROUT：Scaling Agentic Reinforcement Learning for Long-Horizon Software Engineering
coding agent 的 RL 依赖"验证成功的轨迹"作为学习信号，但长程 SWE 任务中一个小错误就会毁掉整条 rollout，成功轨迹非常稀少。常见做法是每次从头重来（浪费），或者只重置上下文和工作目录（会漏掉已安装依赖等环境状态变化）。SPROUT（SnaPshot-based RollOUT）在一个轻量基础设施上，每个 assistant 回合后同时对文件系统和 agent 上下文打快照；失败时由 verifier 引导的回溯策略决定从哪个中间状态恢复、接下来怎么走，相当于给 rollout 加了"存档点"。在多个长程 coding 任务上，它比 pass@k 最高提升 23.6%，而 token 只用 32–52%；用于 Qwen3.8-27B 的 RL 训练时，在三个长程基准上稳定超过标准 GRPO 13.9 分，每个训练步耗时减少 39.5%。对 RL 基础设施而言，"环境 + 上下文联合快照"是长程任务提高样本效率的关键工程能力，也是 rollout 系统设计时值得优先投入的一层。
🔗 链接：https://arxiv.org/abs/2610.14405 ｜ 代码：None

### CodeLift：Your Test Suite Is Secretly a Dense SWE Curriculum
训练 SWE agent 的标准奖励是"所有测试都过才给 1 分"，太稀疏，部分正确的补丁全被当成 0。改用测试通过率看似合理，但作者发现它并不能可靠反映补丁质量：同一个功能可能由一个难测试覆盖，也可能由一百个简单测试覆盖，而且大多数是本来就通过的 pass-to-pass 测试。CodeLift 在每轮迭代中，把"杀死同一批补丁"的测试归为一组、把"通过同一批测试"的补丁归为一组，然后给通过的补丁组越少的测试组更高权重——相当于自动识别"还没被攻克的难点"，弱化大量简单测试。同一规则还用于一条轨迹内部的多个仓库快照，即使后面的动作引入回归，前面有用的动作也能拿到信用。在 SWE 基准上，pass@1/2/4/8 都稳定优于二值和通过率基线。它的工程价值在于：不需要新标注，只靠重新"读懂"现有测试集就能得到稠密、稳定的奖励。
🔗 链接：https://arxiv.org/abs/2610.17224 ｜ 代码：None

### ReTerm：Recovery Training for Self-Improving Terminal Agents
终端 agent 在长时间执行中常遇到命令报错、实现有误等问题，但很难从错误中恢复，最终导致整个任务失败。ReTerm 的思路是专门训练"恢复能力"：先构建一条定制数据管线，产出 ReTerm-10K——一批高质量的"出错后如何恢复"示范数据，用于 SFT 冷启动。然后提出 ReTerm-GRPO：在线 RL 时从 agent 自己的失败状态分叉出多次独立的自救尝试，根据这些尝试能否最终完成任务来学习。基于 Qwen3.5-9B 的 ReTerm-9B 在 Terminal-Bench 2.0 上达到 34.8% Pass@1，比基座高 14.6 分，并且在各种错误类别上的恢复率都高于标准 GRPO。代码、数据和模型均已开源，"从失败状态分叉"的数据构造方式可以直接复用到其他 agent 的 RL 数据管线中。
🔗 链接：https://arxiv.org/abs/2610.18484 ｜ 代码：https://github.com/twothsnd/ReTerm

### Prorsa：Unleashing the Potential of Prefill-Decode Disaggregation in Agentic Reinforcement Learning
agentic RL 的 rollout 负载和传统 RL 很不一样：多轮交互会不断插入新的 prefill（处理新观察的输入）请求，于是 prefill 和 decode（逐 token 生成）负载在整个 rollout 中交织共存。在线推理服务中常用的"PD 分离"（把 prefill 和 decode 放在不同 GPU 上）因此对 RL rollout 也很有吸引力：它能减少数据并行 attention 模块之间的干扰、允许两个阶段用不同并行策略、缩短轨迹完成时间。但固定的 prefill/decode 资源配比会随任务和训练进程中的负载变化而失效。Prorsa 观察每条轨迹的生命周期来预测短期 prefill 和 decode 需求，据此动态分配 worker，并触发推理引擎的角色切换。在同步和异步 agentic RL 设置下，端到端 rollout 比 PD 混合部署加速 1.11–4.05 倍。对正在搭 agentic RL 训练栈的团队，这是一个"把推理服务的成熟优化搬进 rollout"的具体案例。
🔗 链接：https://arxiv.org/abs/2610.16592 ｜ 代码：None

### PreciseCoder：Faithful and Generalizable Debugging Beyond Unit-Test Rewards
用单元测试做 RL 奖励是 code 模型后训练的常规做法，但单测只问"最终程序过没过"。作者分析发现，这种奖励在提高通过率的同时，也教会了模型在调试时"改得更多"，甚至在本来正确的代码里幻想出 bug。PreciseCoder 在单测奖励之外增加一个"语义验证过的局部编辑"信号（只改真正有问题的行），这个信号与更小的改动和更高的通过率都相关。在 4B、9B、27B 模型上，平均改动行数从 7–15 行降到约 3 行，通过率与只用单测训练持平；只用单行 bug 训练也能泛化到仓库级程序修复，用更小的补丁解决更多 issue。更有意思的是，把 9B PreciseCoder 的推理过程交给 GPT-5.6 Sol 等前沿模型，它们的编辑精度提高 4.6–12.4 分。这对 reward 设计是一个提醒："过测试"之外还要奖励"改得准"，否则会训练出副作用大的补丁风格。
🔗 链接：https://arxiv.org/abs/2610.18755 ｜ 代码：None

### First Proof 第三批：frontier systems solve 9 of 10 research problems, open-weight Kimi K3 harness none
First Proof 是由 Abouzaid、Srivastava、Ward、Williams 等数学家发起的评测：拿已经被人类解决、但尚未公开的研究级数学问题，让 AI 系统在无人干预下作答，这样可以避开训练数据污染。10-14 公布的第三批包含 10 道题（人类证明均不超过 12 页），每个系统 24 小时单次机会、无人工输入，由 30 位数学家匿名评审；新评分规则从 −1 到 1，声称正确但实际错误的解答会被扣分，承认"只做了一部分"反而更好。结果：ETH 牵头的 ProofCouncil 多模型 harness 解出 9 道（$1,888），裸 GPT-6 Astra 解出 7 道（仅 $36），Anthropic 公开的 Claude Code 数学插件技能 Siege（Opus 5.5）解出 3 道、拒绝提交 5 道且无负分，开源 Kimi K3 上的 Humanize harness 0 道且每份提交都有重大错误。值得注意的工程细节：ProofCouncil 在一题上陷入循环、把 Astra 的正确解改坏；MerLean 在另一题上引用了 arXiv 旧版本中的错误定义"作弊"。这是"同一模型在不同 harness 下差异巨大""评测中引入负分以惩罚过度自信"的高质量实证。
🔗 链接：https://postcutoff.com/e/2026-10-14-first-proof-third-batch/ ｜ 代码：None

### inclusionAI（蚂蚁）：Ling 3.1 Flash 开放权重
蚂蚁集团旗下 inclusionAI 在 9 月底以"API 免费试用两周、之后开源"的方式推出 Ling 3.1 Flash，10-13 至 10-14 如约在 Hugging Face 发布完整权重，采用宽松的 MIT 协议。它是 560B 总参数 / 25B 激活参数的混合线性注意力 MoE：72 层中 63 层是 Kimi 风格的 KDA 线性注意力、9 层是门控 MLA，512 个路由专家激活 8 个，上下文 1M token。模型卡称在 Terminal-Bench 4.0、SWE-bench Pro、FrontierSWE、MCP-Atlas 等 agentic 基准上表现强，但分数只以图片给出，尚无独立评测。值得关注的是它同时公布了 LingCode——基于开源 Pi agent 的长程 coding harness（暂未开源），以及一份训练内容摘要（TDS）PDF。对开源后训练社区而言，这是目前最大的 MIT 协议长上下文模型之一，适合作为长程 coding agent RL 的基座候选。
🔗 链接：https://huggingface.co/inclusionAI/Ling-3.1-flash ｜ 代码：None（事件详情：https://postcutoff.com/e/2026-10-14-ling-3-1-flash-open-weights/）
