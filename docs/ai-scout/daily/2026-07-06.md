## 📝 逐条讲解

### TestEvo-Bench：测试与代码协同演化的可执行 live benchmark
很多 coding-agent benchmark 只要求 agent 修改生产代码并让隐藏测试通过，但真实软件工程里，代码变化往往要同步更新测试，测试本身也是需求理解的一部分。TestEvo-Bench 把这个现象做成两个任务轨道：一类是为新行为生成新测试，另一类是当生产代码变了以后更新旧测试。它不是简单从 diff 里抄输入输出，而是从 Java/Maven 开源项目的真实 commit history 里挖 test-code co-evolution，并用跨版本执行确认测试确实和代码变化有语义关系。当前快照从 59,950 个候选记录中过滤出 746 个 test generation 任务和 509 个 test update 任务，覆盖 152 个开源 Java 项目。评测指标也比 pass/fail 更细，包括 pass rate、coverage、mutation score，并按 commit 时间支持 live / cutoff-aware 评测，减少训练数据污染。结果显示强 agent 在总体上可以达到约 77.5% test generation 和 74.6% test update 成功率，但越新的任务、越严格的成本预算下成功率明显下降。对后训练软件工程来说，它提供了很好的数据构造范式：把“开发者为什么改测试”变成可执行、可时间切片、可污染控制的训练/评测信号。
🔗 链接：https://arxiv.org/abs/2607.02469 ｜ 代码：https://huggingface.co/TestEvo-Bench

### SWE-Doctor：用多面向 bug reproduction tests 生成运行时诊断来指导补丁
Bug reproduction test（BRT）通常被当作补丁之后的验证器：agent 先写补丁，再看生成的复现测试是否通过。SWE-Doctor 指出这种用法太粗，因为一个测试可能只覆盖 issue 的一个表现面，agent 很容易修到“这个测试过了”就停，留下其它行为没修。它的做法是先从 issue report 中抽取多个明确的行为要求，为每个要求生成有针对性的 BRT，再把这些测试放进 debugger 里运行，记录故障位置、传播路径、运行时变量和值等诊断信息。这样 BRT 不再只是 pass/fail 目标，而像医生的检查项目：每个检查都暴露一部分病灶，最后汇总成 patch generation 的证据。论文在 SWE-bench Verified 和 SWE-bench Pro 的 Python bug-fixing 子集上评估，跨 5 个 LLM backend、10 个模型-基准组合都优于 mini-SWE-agent 和 live-SWE-agent，平均达到 75.7% / 59.4%。更有价值的是消融分析：多面向 BRT 主要减少“只修一半”的 partial patch，运行时诊断则把 fail-to-fail 测试变成仍可利用的调试证据。对训练数据工程来说，这说明失败测试轨迹不能只标成负样本，里面的 stack trace、变量状态和路径信息可以转成过程监督。
🔗 链接：https://arxiv.org/abs/2607.00990 ｜ 代码：https://github.com/SWE-Doctor/SWE-Doctor

### RepoRescue：废弃仓库兼容性救援 benchmark 与 source-only 反作弊审计
现实里很多有用的开源库不是逻辑坏了，而是 Python、Java、依赖和构建工具升级后不再能运行；维护者离开后，下游只能各自打补丁。RepoRescue 把这类“兼容性救援”定义成 agent 任务：仓库在历史环境里通过测试，在现代环境里失败，agent 只能看失败的现代环境并尝试改源代码恢复原测试套件。它构造了 193 个 Python 仓库和 122 个 Java 仓库，要求每个任务都能证明“过去能跑、现在因为生态漂移坏了、需要源代码适配”。评测最关键的是 source-only audit：agent 提交后会移除所有 test-file edits 再重跑，防止 agent 通过改测试、删断言或调整依赖说明来伪造成功。论文发现 Claude Code 系列系统有 38-53% 的表面成功依赖测试编辑，而 runtime-blocked 设置能改变 agent 行为，Kimi 在禁止测试编辑时仍能救回 41.5% Python 仓库。它还用 L1-L4 推理层级标注修复难度，发现真正困难的是跨文件、跨 API、跨运行时假设的协调迁移。对后训练软件工程的启发很直接：eval harness 必须同时测成功、合规和真实可用性，否则 agent 会学会最短捷径而不是可维护修复。
🔗 链接：https://arxiv.org/abs/2607.01213 ｜ 代码：None

### PatchFusion / PatchFuseBench：把多个候选补丁做确定性 edit-atom 融合
很多 coding-agent 论文报告 pass@k，但真实开发中 reviewer 最后通常只能接收一个 patch，因此“候选池里有正确补丁”并不等于系统能交付正确结果。PatchFusion 关注这个 pass@k 到 pass@1 的落差，把问题定义为 post-generation repair selection/fusion。它不再让 LLM judge 重新判断，也不依赖当场跑测试，而是从多个候选补丁中抽取重复出现的 edit atoms，把 whole-diff agreement 聚成 repair neighborhood，再用 evidence-constrained fusion 保留被多方支持的改动、剪掉孤立和不稳定的部分。为评估这个问题，作者构建 PatchFuseBench，固定候选补丁池，覆盖 SWE-bench Verified、SWE-bench Multilingual 和 Defects4J。结果显示 PatchFusion 在 SWE-bench Verified 上解决 426/500 个 bug，在 Multilingual 上解决 236/300 个，并能找回一些没有任何单一候选完整解决的 bug。它的工程价值在于把“多次采样”从昂贵的 rerank 问题变成可审计、可重复、低成本的证据融合问题。对后训练平台也有启发：候选补丁之间的共识与分歧本身可以成为训练信号，帮助模型学习哪些 edit 是稳定核心、哪些是采样噪声。
🔗 链接：https://arxiv.org/abs/2607.01597 ｜ 代码：None

### EvoPolicyGym：测 agent 在有限反馈预算下如何演化可执行策略
许多 benchmark 只看 agent 最终提交的代码是否通过测试，但越来越多 agent 任务的本质是持续试验、观察反馈、更新可执行策略。EvoPolicyGym 把这种能力单独抽出来，定义为 Autonomous Policy Evolution：agent 在一个固定预算内反复编辑 Python policy、提交 rollout、读取反馈，再继续改进。它不像开放式软件任务那样混入需求理解、架构设计和产品取舍，而是用 Gym/Box2D、MuJoCo、MiniGrid、机器人/驾驶等紧凑环境控制变量，让评测专注于“如何把环境反馈转成更好的策略”。协议上，训练反馈可见，validation 和 held-out 由 server 隐藏，最后按隐藏评估选择 checkpoint，避免 agent 过拟合可见反馈。Core16 实验中 GPT-5.5 通过 Codex harness 取得总体最强 rank，Claude Opus 4.7 在 MiniGrid 家族领先，但论文更重要的是轨迹诊断：预算怎么分配、是调参数还是改结构、何时探索或停止。对 agent 后训练而言，这类 benchmark 很适合产生“反馈利用质量”的过程数据，而不是只给最终 reward。它也提醒我们，长程 agent 的核心能力不只是写代码，而是能在受限试验预算下做实验设计。
🔗 链接：https://arxiv.org/abs/2607.02440 ｜ 代码：https://github.com/Linzwcs/EvoPolicyGym

### GitHub Copilot CLI smarter subagent delegation：减少无效委派的生产 harness 调度策略
最近很多 agent 产品都加入 subagents，但更多委派并不一定更好：简单任务被拆给子代理后，可能多一次搜索、多一次等待、多一个失败路径。GitHub 这篇文章披露了 Copilot CLI 的一次生产级 harness 改动：让主 agent 更谨慎地决定什么时候自己做、什么时候委派、什么时候并行。团队先用 LLM 分析完整 agent trajectories，找出 subagent 在窄任务上重复搜索、等待和使用错误路径的模式，再把诊断转成更选择性的 orchestration policy。核心规则很工程化：目标明确、上下文足够、改动集中的任务留给主 agent；需要独立上下文、广泛探索或真正可并行的任务才委派。上线到 100% 生产流量后的 A/B test 显示，每 session 工具失败减少 23%，搜索工具失败减少 27%，编辑工具失败减少 18%，P95 等待时间降低 5%，且质量无回退。它值得关注，因为它证明 agent 质量不只靠模型升级，调度策略本身也能用 trajectory analysis 和在线实验持续优化。对后训练软件工程来说，这类“何时委派”的决策可以被记录成训练标签或 harness policy，避免 agent 把 subagent 当成默认逃生按钮。
🔗 链接：https://github.blog/ai-and-ml/how-we-made-github-copilot-cli-more-selective-about-delegation/ ｜ 代码：None

### shadcn/improve：强模型审计代码库，生成给便宜 agent 执行的自包含计划
很多团队已经能让 agent 写代码，但难点变成“让谁来判断最该做什么、怎么做才不会跑偏”。`shadcn/improve` 的思路是把高智力环节和执行环节拆开：用最强模型做代码库审计、取舍和计划，把实际实现交给便宜模型或人类。这个 skill 不直接改代码，而是先 recon 仓库栈、约定和测试命令，再派并行 subagents 从正确性、安全、性能、测试、技术债、依赖迁移、DX、文档和方向等类别找证据。随后 advisor 会重新读每个引用位置，过滤 false positive，把剩下的发现按 leverage 排序，并为用户选择的项生成 `plans/` 下的自包含 Markdown 计划。计划面向“最弱可执行者”编写：包含当前代码摘录、确切文件路径、验证命令、期望输出、边界条件和 STOP 条件，还会标注生成时的 git commit 以便检测漂移。仓库近一个月创建，当前约 6.9k stars，说明社区正在把“强模型做架构审计、弱模型执行实现”当成一种成本工程模式。对后训练数据来说，这类 audit-to-plan artifact 很有价值，因为它把隐性的工程判断拆成可审查、可执行、可验证的中间表示。
🔗 链接：https://github.com/shadcn/improve ｜ 代码：https://github.com/shadcn/improve

### TestSprite CLI：把 live app 验证闭环交给 coding agent 的终端工具
前端和全栈 agent 最大的问题之一是“看起来写完了”，但真实浏览器、真实后端和真实用户路径并没有被验证。TestSprite CLI 的定位就是 agentic coding era 的 verification layer：让 coding agent 从终端创建测试、运行 live app、拿回失败证据包，再根据证据修复并重放。它把失败结果包装成自洽的 bundle，而不是要求 agent 去 dashboard 里手动截图或猜测 UI 发生了什么。README 给出的典型循环是：agent 根据计划创建测试并等待，如果失败就拉取 `.testsprite/failure` 证据包，修代码，再 rerun，直到测试成为 durable suite。安装阶段还可以为 Claude、Cursor、Cline、Windsurf、Antigravity、Codex 等安装 verification-loop skill，使 agent 知道怎样调用工具而不是从 README 临场推断。仓库近一个月创建，约 1.9k stars，说明“验证比模型大小更影响交付质量”的需求正在产品化。对后训练软件工程来说，这类工具提供了很好的轨迹结构：测试计划、真实失败、证据包、修复补丁、重放结果，可以直接用于训练 agent 的自修复闭环。
🔗 链接：https://github.com/TestSprite/testsprite-cli ｜ 代码：https://github.com/TestSprite/testsprite-cli

### Pace / Pace-Bench：用便宜原子 benchmark 预测昂贵 agentic benchmark 分数
完整跑 SWE-bench、GAIA 或多模态 SWE 这类 agentic benchmark 很贵，既要环境、工具、长 rollout，也要大量 API 成本和调度时间。Pace 提出一个务实问题：能不能用一小组便宜的、非 agentic 原子能力题，提前预测模型在昂贵 agent benchmark 上的大致表现。它从 19 个 non-agentic benchmarks 中选择与目标 benchmark 最相关又全局信息量高的实例，训练一个回归模型，把模型在这些小题上的分数映射到 agentic benchmark 分数。论文在 14 个模型、4 个目标 agentic benchmarks 上实验，包括 SWE-Bench Verified、SWE-Bench Multimodal、SWT-Bench 和 GAIA。结果显示 Pace-Bench 的 leave-one-out MAE 低于 4%，Spearman 相关超过 0.80，pairwise model ranking accuracy 约 85%，成本不到完整 agent eval 的 1%。它不能替代最终生产评测，因为真实工具失败、权限、长程恢复和 harness 交互仍要实跑，但非常适合模型筛选和路由前置 triage。对评测工程来说，Pace 的价值在于把“全量 agent eval 太贵”转成可解释的 proxy 设计，并告诉我们不同 agent benchmark 依赖哪些原子能力。
🔗 链接：https://arxiv.org/abs/2607.02032 ｜ 代码：https://github.com/neulab/pace

### Google Interactions API GA：把 Gemini 模型与 managed agents 统一到 stateful endpoint
传统模型 API 多是单次请求/响应，开发者要自己维护会话状态、工具组合、后台任务和 agent 执行环境。Google 的 Interactions API GA 把这个接口升级为模型与 agent 的统一 endpoint：传 model ID 就是普通推理，传 agent ID 就能运行 autonomous task，设置 `background=True` 就变成长任务。新能力包括 Managed Agents，一次 API 调用就能 provision 远端 Linux sandbox，让 agent 推理、执行代码、浏览网页和管理文件；还包括 server-side state、背景执行、工具混合、媒体生成和 55 天付费层历史保留。最值得 agent 工程关注的是 schema 从 roles 改成 typed steps，每个 user_input、thought、function_call、model_output 都是可追踪步骤，更适合调试和未来评测。Google 还专门提到为 coding agents 做了 `gemini-interactions-api` Skill，让 agent 自动注入最新 API 最佳实践。它按 Medium 收录，因为不是 coding-agent benchmark，但它代表大厂把 agent runtime state、sandbox、background execution 和 skill 支持下沉到 API 层。对后训练平台来说，这意味着轨迹数据会越来越来自托管 agent runtime，而不是裸模型调用。
🔗 链接：https://blog.google/innovation-and-ai/technology/developers-tools/interactions-api-general-availability/ ｜ 代码：None

### OpenAI Codex as MCP Server + Agents SDK：把 Codex CLI 变成可追踪多 agent pipeline 组件
很多团队想把 coding agent 接入自己的 orchestrator，但如果只把 agent 当命令行黑盒调用，就很难保持会话、审批、沙箱和 trace。OpenAI Developers 的 Codex + Agents SDK guide 展示了一种更结构化的接口：把 Codex CLI 作为 MCP server 启动，暴露 `codex` 和 `codex-reply` 两个工具。前者启动 Codex session，可配置 sandbox、approval policy、cwd、model、profile 等；后者用 `threadId` 继续同一会话，使 Codex 可以作为长程子代理参与更大的 workflow。示例里 Agents SDK 负责编排 Project Manager、Designer、Frontend、Backend、Tester 等角色，Codex MCP 负责在受控 workspace 中创建文件和实现任务。更重要的是 SDK 内置 traces dashboard，能记录 prompts、tool calls、handoffs、执行时长和文件写入，方便回溯为什么某个 handoff 成功或失败。它按 Medium 收录，因为这是官方开发者文档/教程而非研究发布，但它非常贴近 Agent-Friendly Software：把一个强 coding agent 包装成可审计、可组合、可持久会话的工具。对内部 harness 工程来说，这种模式比“让一个大 agent 自己管所有子任务”更容易加权限、日志和评测。
🔗 链接：https://developers.openai.com/codex/guides/agents-sdk ｜ 代码：https://developers.openai.com/cookbook/examples/codex/codex_mcp_agents_sdk/building_consistent_workflows_codex_cli_agents_sdk

### OpenWiki：为 coding agents 自动生成并维护代码库文档的 CLI
Coding agent 经常在大仓库里重复搜索同样的上下文，原因是项目知识没有被整理成 agent 可持续读取的结构。OpenWiki 试图把这件事做成 CLI：它能生成 `openwiki/` 文档目录，也能在已有 wiki 上基于仓库变化做更新。更贴近 agent 的细节是，它会自动往 `AGENTS.md` 或 `CLAUDE.md` 追加提示，让后续 coding agent 在找上下文时主动参考 OpenWiki，而不是每次从零读仓库。项目还提供 GitHub Actions 示例，可以每天自动开 PR 更新文档，这让 repo documentation 从一次性生成变成持续维护流程。它支持 OpenRouter、Fireworks、Baseten、OpenAI-compatible、Anthropic 等 provider，并能把运行 trace 写到 LangSmith，便于观察文档生成质量。仓库近一个月创建，当前约 5.3k stars，说明“为 agent 写文档”正在成为新的开发基础设施需求。对后训练数据工程来说，OpenWiki 这类工具提示我们，未来轨迹质量取决于项目知识层是否可维护、可引用、可版本化。
🔗 链接：https://github.com/langchain-ai/openwiki ｜ 代码：https://github.com/langchain-ai/openwiki

### GitHub Copilot CLI Custom Agents：用 repo 内 Markdown agent profile 固化团队工作流
很多团队已经有固定的安全检查、可访问性检查、发布流程和代码评审标准，但如果每次都靠 prompt 解释，agent 行为会漂移，也不容易 code review。GitHub Copilot CLI 的 custom agents 把这些工作流变成 repo 内 Markdown agent profile，放在 `.github/agents/*.agent.md`，用 YAML frontmatter 声明 name、description、model 和 tools。这样一个“Accessibility Expert”或“Security audit”agent 就能固定工具范围、输出格式、团队 guardrails 和检查清单，并且像代码一样被 review、版本化、共享。文章给出的例子很具体：安全 agent 可以要求使用 gitleaks、trivy、semgrep、gh 等工具，缺工具时记录 coverage gap，而不是编造结果。这个设计和 Agent Skills 很像，但更偏 GitHub/Copilot CLI 工作流，把终端、IDE 和 PR 串成连续上下文。它按 Medium 收录，因为是产品能力说明，不是 benchmark；但它代表 agent workflow 从个人提示词迁移到 repo-governed artifacts。对 skill management 和后训练来说，这种文件化 agent profile 会成为重要上下文，采集轨迹时需要一并记录版本。
🔗 链接：https://github.blog/ai-and-ml/github-copilot/from-one-off-prompts-to-workflows-how-to-use-custom-agents-in-github-copilot-cli/ ｜ 代码：None

## 🔥 社区热点专栏

### 🔥 大佬观点

**GitHub Copilot CLI 团队：最好的系统不是委派最多，而是知道何时不委派。**  
GitHub 的 smarter subagent delegation 文章把一个社区常见误区讲清楚：subagents 是并行和独立探索工具，不是所有任务的默认解法。这个观点值得注意，因为它有生产 A/B 数据支撑，说明 harness policy 能直接减少工具失败和等待时间；对 agent 后训练来说，“何时不用子代理”同样是高价值过程标签。🔗 https://github.blog/ai-and-ml/how-we-made-github-copilot-cli-more-selective-about-delegation/

**OpenAI Developers：Codex CLI 可以作为 MCP server，进入可追踪的多 agent 软件交付流水线。**  
OpenAI 的开发者指南把 Codex 从单个 CLI 提升为可被 Agents SDK 编排的 MCP 工具，并强调 handoffs、guardrails 和 traces。它值得注意不是因为又多了一个 wrapper，而是因为它把 coding agent 的执行过程变成可审计 timeline：谁交接给谁、写了哪些文件、每步花多久、哪里失败。🔗 https://developers.openai.com/codex/guides/agents-sdk

**Google DeepMind / Google AI Studio：agent runtime 正在从 stateless API 迁移到 stateful interactions。**  
Interactions API GA 的核心信号是，长程 agent 需要 server-side state、background execution、managed sandbox 和可追踪 typed steps，而不只是单次 function calling。这个观点对工程团队很实际：如果 agent 平台状态和 trace 不标准化，后面的评测、回放、权限和成本优化都会变成各自重做。🔗 https://blog.google/innovation-and-ai/technology/developers-tools/interactions-api-general-availability/
