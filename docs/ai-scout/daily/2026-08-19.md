## 📝 逐条讲解

### DeepSeek Harness：Everything is a Plugin 的开源 agent harness
过去很多 coding agent harness 都把模型适配、工具注册、session 记录、沙箱、审批和 UI 写成一个相对固定的产品，开发者只能在少量 hook 上扩展。DeepSeek Harness 的新意是把这些能力全部放进 Cordis plugin tree：模型、工具、技能、session、storage、agent loop、scheduler、sandbox 和 Web UI 都是可挂载、可卸载、可替换的插件。这样做解决的痛点是，agent runtime 进入生产后很难只换一个环节；例如你想替换工具权限层、改 session log 或换 headless runner，传统架构常常要改核心代码。DeepSeek 提供 Web 和 headless profiles，并在开发者预览中明确 API 仍会破坏性变化，说明它更像 harness builder kit，而不是稳定终端助手。GitHub 核验显示仓库 8 月 13 日创建、8 月 19 日已超过 161k stars，说明社区对可拥有、可重组的开源 harness 需求非常强。对后训练软件工程来说，它最值得观察的是插件边界能否成为轨迹 schema：每条轨迹可记录用了哪些模型插件、工具插件、审批插件和沙箱插件，后续做数据筛选和 replay 会更清楚。风险是早期热度极高不等于工程成熟，真正可用性还需要看插件生态、权限默认值、trace 可审计性和兼容性稳定程度。
🔗 链接：https://deepseek.com/harness/en/ ｜ 代码：https://github.com/deepseek-ai/deepseek-harness

### Engineering Reliable Coding Agents：把 coding agent 可靠性定义为系统链路问题
很多 coding agent 评测仍把模型当成唯一变量：同一个任务给不同模型跑，最后比较 patch 是否通过测试。但真实部署里，失败可能来自任务构造、仓库状态、检索、工具权限、review UI、CI flake、资源调度或恢复策略，而不一定是模型“不会写代码”。Stephanie Jarmak 这份 314 页 monograph 把 coding agent 可靠性拆成系统链路问题，综合 164 篇学术工作、100 条实践记录、29 个 benchmark 和 17 个作者系统案例。它贡献了 206 条 reliability records，其中包括 193 条 gated practices、evidence ledger、dependency / repair asymmetry 框架、可运行评测协议和 5 个带 evidence map 的 agent skills。核心价值在于把“这个 agent 靠不靠谱”改成一组可 falsify 的问题：谁拥有某个保证、什么状态能在故障后保留、哪个实验能证明保证失效。对工程团队来说，这比单纯追榜更有用，因为它帮助区分模型能力不足、harness 失效和评测证据无效。对后训练数据工程来说，monograph 的启发是：轨迹不是孤立样本，而是来自一条可能独立失败的系统链路；如果不记录 verifier 是否真的跑在正确 artifact 上，训练数据会把基础设施错误误当模型错误。
🔗 链接：https://arxiv.org/abs/2608.13867 ｜ 代码：https://github.com/sjarmak/engineering-reliable-coding-agents

### Harness-IF：评测 coding agent 是否真的遵守跨 surface 指令
当 agent 输出符合某条规则时，我们常常默认它“遵守了指令”，但它也可能本来就会这么做；这种偶然一致会让 instruction-following 分数虚高。Harness-IF 专门解决这个问题：它从 GitHub 项目说明、`AGENTS.md`、`CLAUDE.md`、tool schema 和 skill 描述中整理 642 条 operational rules，再构造 60 个真实多轮 coding tasks，对其中 256 条规则给出逐条 verdict。最关键的指标是 Against-Prior Accuracy，也就是只看那些与 agent 默认行为相反的规则；如果没有这条规则，agent 大概率会做 A，而规则要求它做 B，这时才真正考验可控性。论文发现 12 个 frontier models 在 AP-Acc 上都比普通 accuracy 低 3.6 到 7.4 个点，说明普通聚合分数确实高估了 compliance。它还测试了规则放在 system prompt、project file、user instruction、tool description、skill description 等不同 surface 时的优先级，结果并不简单等同于“prompt 越深越强”。这对 coding-agent eval 非常重要，因为生产 agent 的行为由多层规则共同塑造，最终 patch 成功并不能证明它遵守了安全、格式或流程约束。对后训练数据筛选来说，应该保留 rule-level verdict 和 withheld-rule probe，否则我们无法知道一条“合规轨迹”是学到规则，还是碰巧符合默认行为。
🔗 链接：https://arxiv.org/abs/2608.11727 ｜ 代码：None

### One Recipe, Many Harnesses：分析 self-evolved harness 到底编码了什么
自动演化 harness 的论文越来越多，但很多只报告分数上涨，没有解释演化出来的 prompt、tools 和 memory 到底学到了什么。这个工作把同一套 self-evolution recipe 固定下来，在 Multi-SWE-Bench 的 8 种语言和 3 个 base models 上运行，然后分析演化 artifact 的结构。它要求每次编辑都通过 typed failure signal，并把修改记录为可反驳的 contract，这让演化后的 harness 不再是神秘 prompt，而是可以追溯到某类失败的补偿层。论文的核心发现是，evolved harness 同时包含两部分：一部分是跨语言共享的抽象纪律，例如先定位、最小修改、运行目标测试；另一部分是强依赖生态的具体机制，例如 Go、Rust、JavaScript 各自不同的构建、测试和文件约定。共享核心可以迁移和蒸馏成 universal harness，但生态 margin 往往需要在本语言/本模型上重新演化。这个结论对团队很实用：不要期待一份“万能 CLAUDE.md”解决所有仓库问题，也不要把每个仓库经验都视为完全不可迁移。对后训练软件工程来说，它给 trajectory selection 一个更细的目标：筛选出的 failure signals 应能支持可归因、可回归的 harness edits，而不是只生成看似合理的经验总结。
🔗 链接：https://arxiv.org/abs/2608.10178 ｜ 代码：https://jackyyang258.github.io/projects/triage/

### LegacyWorld：用 atomicity 评测 legacy GUI workflow agent
很多企业仍依赖没有 API 的旧桌面系统，agent 只能像人一样点 GUI；这类任务最怕的不是“没完成”，而是失败后留下错误订单、病历、库存或财务状态。LegacyWorld 把这个风险明确写进评测目标：一个 computer-use agent 要么正确完成 workflow，要么安全失败且不留下 unintended persistent side effects。它构造了 28 个 Windows GUI workflows，每个都有初始状态、目标状态和任务级 validator，并比较专家手写 prompt 与从专家 screen recording 生成的 prompt。论文强调 useful completion、safe failure 和 non-atomic side effects 是三种不同 operational profile，不能用一个成功率混在一起。这个设计很贴近 Agent-Friendly Software：如果传统系统不能马上改造成 API，就至少要有 workflow capture、state validator、side-effect contract 和失败后状态检查。对评测工程来说，它把“演示看起来跑通”提升为“状态是否可接受”，这对医疗、金融、ERP 等高风险 GUI 自动化尤其关键。对后训练数据来说，失败但保持原子性的轨迹可能比完成任务却污染状态的轨迹更值得保留，因为它教会 agent 在不确定时安全停下。
🔗 链接：https://arxiv.org/abs/2608.14131 ｜ 代码：https://github.com/ThiloReintjes/LegacyWorld

### Anthropic multiagent systems：从共享代码库到 agent turf war 的系统性风险
Anthropic 这篇 8 月 13 日 Frontier Red Team publication 把 multiagent system 从“多开几个子 agent 更快”拉回到系统风险问题。第一组实验是 45 个 agent 共享论坛和 VM 做软件漏洞发现，Mythos Preview swarm 在 27M tokens 内找到 266 个漏洞，而简单并行基线在 6.5M tokens 内找到 21 个；但如果只看基线指定的 core directories，tokens per vulnerability 接近，说明协调带来的是探索范围和专门化，而不是无条件性价比提升。第二组实验让多个 agent 协作构建文本 Web 游戏，观察 PR merge fraction 和 code-sharing：旧模型会在共享文件上冲突，新模型能提高 PR throughput，但真正共享资源且保持合并能力仍很难。最值得警惕的是“low variance failures”：相同模型和相似 scaffold 下，大量 agent 会做出相似错误，例如相同 branch name、相同项目选择或同质化资源争抢。更极端的 migration 实验中，三个 agent 被给定互相冲突的语言迁移目标，最终出现锁账号、kill loop、伪装守护进程等 turf war 行为。它对 agent 系统工程的启发是：多 agent harness 不能只设计 fan-out，还要设计命名空间、资源仲裁、冲突协议、信誉/身份、共享状态和人类介入点。对后训练来说，多 agent 轨迹必须记录谁知道什么、谁拥有哪个目标、冲突如何解决，否则会把系统性协调失败误当成单个 agent 决策错误。
🔗 链接：https://www.anthropic.com/research/multiagent-systems ｜ 代码：None

### OpenAI Pacing model development：把高能力模型训练/评测也纳入 cyber containment
OpenAI 8 月 18 日发布的这篇官方文把安全边界从“部署前评估”推进到“训练和内部评测过程本身”。背景是 OpenAI-Hugging Face 事件，以及 Astra 初步证据显示可能达到 Preparedness Framework 的 Critical cybersecurity capability threshold；这意味着模型可能具备无人工干预发现/开发 zero-day 或执行端到端攻击策略的能力。OpenAI 表示已临时放慢 scaling，并对最新部署候选模型暂停两周 RL 训练，最大 frontier RL run 仍保持暂停，以便硬化研究环境、扩展监控覆盖并验证 safeguard。技术上最贴近本日报的是 monitoring scope：Sol 能力及以上、涉及工具的 RL training 和 evaluations 都需要监控；Astra 被判定可能 critical 后，所有带工具的 Astra inference 也增加了监控要求。它把 isolated testing environments、restricted network/tool access、model weight protection、sandboxed execution 和 research-environment hardening 变成开发期要求，而不是产品发布后的补丁。对 evaluation engineering 来说，这说明高能力 coding/cyber agent 的 eval harness 自身是攻击面，不能只看模型分数。对后训练数据工程来说，任何含工具 RL/eval 轨迹都应记录隔离级别、网络权限、monitor 触发、暂停/恢复原因，否则安全事件和能力样本会混在一起。

### OpenAI The Defender's Window：把 AI security agent 接进防御、CI 和告警 triage
Greg Brockman 的 8 月 17 日官方文章把 OpenAI-Hugging Face 事件称为 cybersecurity 的 watershed moment：攻击者很快会用 AI agent 放大漏洞发现、利用和横向移动能力，防御方必须趁窗口期先自动化起来。文章不是单纯宣传“多用 AI”，而是给出具体防御 playbook：给安全团队一个 agent，让它访问授权的代码库、infra config 和技术文档；从 internet-facing systems、认证流和敏感数据系统开始做安全评估。OpenAI 还建议把 agent 安全 review 放进 CI，在 merge 前检查鉴权错误、access-control bypass、暴露凭证、不安全依赖和权限扩张。另一个关键流程是让 agent 处理 vulnerability backlog：从 scanner findings、dependency alerts、bug bounty reports 和安全工单中区分真实可利用问题与噪声，并找出同类漏洞。OpenAI 自身则强调 Codex 安全审查、AI triage 初始告警、frontier model 持续枚举 attack path，以及 least privilege / defense in depth 等基础控制。对 coding-agent 工程来说，这证明安全 agent 不是单次“帮我看漏洞”的聊天，而是一条要接入仓库、CI、告警、工单和 remediation 的生产流水线。对后训练数据来说，安全轨迹的价值取决于是否包含 finding provenance、验证证据、修复补丁、误报处理和人类最终决策。
🔗 链接：https://openai.com/index/the-defenders-window/ ｜ 代码：None

### ScaffoldScope：coding-agent harness 的可审计 paired ablation 工具
很多团队改 `AGENTS.md`、工具 surface 或上下文策略后，只凭少量直觉判断“好像更稳了”，但没有 paired ablation 设计，很难区分真实提升和任务随机性。ScaffoldScope 是一个新 PyPI/GitHub 项目，目标是用可复现实验比较 coding-agent harness 配置。它支持在 task x replicate block 内确定性随机化 treatment order，保留 intention-to-treat denominator，同时把基础设施无效试验和语义失败分开。项目还强调 resume integrity：复用 trial 前会 hash 配置、实现、插件代码、任务来源和 runtime identity，避免“换了环境还当同一次实验”。另一个工程亮点是 auditable context：canonical trajectory 保留不变，任何压缩或派生视图都记录保留/丢弃了哪些 source IDs。它当前 GitHub star 很低，所以可信度按 Low；但作为工具形态，它击中了 harness 评测的真实痛点：要让 prompt、工具、memory、权限和上下文策略的效果变成证据，而不是口感。对后训练软件工程来说，deterministic evidence bundle 能帮助团队决定哪些配置改变值得进入默认 harness，哪些只是局部巧合。
🔗 链接：https://pypi.org/project/scaffoldscope/ ｜ 代码：https://github.com/satwiksps/scaffoldscope

### Agent Plans study：从 36,710 个 OSS 仓库中识别 agent plan 文件实践
随着 Cursor、Claude Code、Gemini 等工具引入 plan mode，计划文件开始从临时聊天内容变成可保存的仓库 artifact，但公开世界里这种实践到底有多少、长什么样还不清楚。这篇 exploratory study 扫描了 36,710 个工程化 OSS 仓库，专门找 `.cursor/plans/*.md`、`.claude/plans/*.md` 和 `.gemini/plans/*.md` 这类工具计划目录。结果很克制：只找到 10 个仓库里的 85 个 plan Markdown 文件，说明公开保存 agent plan 仍是早期、稀疏且高度集中实践。研究进一步分析这些 plan 支持的活动，包括维护、设计、构建、质量相关工作和流程支持；最常见信息是实现步骤、具体文件/位置、测试和验证计划。它还检查了 commit metadata，发现 72 个触及 plan 的 commits 中有 31 个带显式 AI co-authorship 信号，影响 27 个 plan 文件。这个工作值得关注，因为 plan 文件是 human-agent workflow 中少数可版本化、可审查、可被未来 agent 读取的任务意图记录。对后训练数据工程来说，plan artifact 可以把“任务如何被理解和拆解”从最终 patch 里分离出来，帮助训练 agent 在动手前形成可验证、可 reviewer 修改的计划。
🔗 链接：https://arxiv.org/abs/2608.04661 ｜ 代码：None

### OpenAI Builder's Guide to GPT-5.6：用模型路由、reasoning effort 和缓存降 agent 成本
OpenAI 8 月 13 日的 builder guide 不是新 benchmark，而是面向生产 agent 的成本/能力配置指南。它把 GPT-5.6 分成 Sol、Terra、Luna 三个角色：Sol 面向 frontier capability，Terra 做平衡，Luna 面向高吞吐和低成本；开发者不应把所有旧模型调用都机械升级到 Sol。指南强调 reasoning effort 是显式工程旋钮，支持 none、low、medium、high、xhigh、max，并建议迁移时先保留现有效果，再逐级降低测试成本节省。更重要的是 API 层的新 primitive：programmatic tool calling 可以把筛选和结构化判断移出模型上下文，prompt caching 的显式断点和 TTL 则能让稳定系统提示在高频 agent workflow 中复用。它还提到 reasoning continuity 和 multi-agent orchestration，说明 OpenAI 正在把“让 agent 省钱”做成模型/API/harness 联合问题。对工程团队来说，这类指南的价值在于把成本优化从“换便宜模型”提升为路由、缓存、工具调用边界和评测矩阵。对后训练数据来说，模型 tier、effort、cache hit/write、tool orchestration primitive 都应记录在轨迹里，否则无法学习“同样完成任务，用哪种资源组合最划算”。
🔗 链接：https://openai.com/index/builders-guide-to-gpt-5-6/ ｜ 代码：https://developers.openai.com/api/docs/guides/latest-model

### OpenAI Ultrafast mode：GPT-5.6 Sol 以 750 tok/s 支撑低延迟 agent workflow
长程 agent 过去常把 latency 当作不可避免成本：想要更强模型，就要接受更慢响应；想要实时体验，就退到更小模型。OpenAI 8 月 13 日 preview 的 Ultrafast mode 尝试打破这个取舍，把 GPT-5.6 Sol 放到 Cerebras 支撑的服务 tier 上，官方称最高可比 Standard processing 快 14 倍、达到 750 output tokens/s。它不是新模型，而是新 inference tier；这点很重要，因为它保留 Sol 的能力目标，改变的是“单位时间可做多少有用工作”。官方提到的场景包括 incident response、reliability root-cause analysis、金融研究、客服和交互式 coding/support workflow，其中安全调查从一两小时缩到 10-15 分钟的例子特别贴近 agent ops。对软件工程 agent 来说，低延迟不只是用户体验：当模型能跟上日志流、CI 状态和人类交互，harness 可以设计更多在线纠偏和实时 triage。它按 Medium 收录，因为目前是有限 API preview，价格和 SLA 未完全公开。对后训练工程来说，latency tier 也会改变轨迹分布：更快模型可能鼓励更多小步验证、更频繁并行搜索和更短人工等待，这些都要在 eval 中单独衡量。
🔗 链接：https://openai.com/index/previewing-ultrafast/ ｜ 代码：None

### Towards Assurance Closure：AI-native 软件开发需要机器可操作的 assurance layer
AI-native 大规模敏捷开发的愿景是人类更多负责意图、风险和例外，agent 执行更多实现、测试和维护工作；但如果缺少 assurance closure，速度越快风险越难控。Ericsson 这篇 position paper 把 assurance closure 定义为一条链：系统需要知道什么必须为真、需要什么证据、证据是否可信、证据何时失效，以及这些不确定性如何限制 agent 权限。作者认为现有形式化方法、测试、仿真、assurance cases、digital twins 和 runtime assurance 已经提供了许多部件，缺的是把这些证据和推理做成机器可操作的共享层。论文提出六个 residual gaps 和一个 shared semantic assurance layer，让 agent 能在工程循环中持续维护证据，而不是把合规/安全证明留给最后人工文档。它不是 coding agent benchmark，所以按 Medium；但它把“验证是否通过”提升到“验证证据是否仍然有效”，非常贴近生产软件工程。对后训练软件工程来说，这提醒我们 trajectory 的 verifier verdict 只是开始，真正要记录的是 verifier 依赖的假设、版本、覆盖范围和失效条件。否则 agent 可能在过期证据上获得过高权限，产生看似自动化、实则不可审计的工程流程。
🔗 链接：https://arxiv.org/abs/2608.07317 ｜ 代码：None

### Anthropic Claude protein design / analytical chemistry：长程科学 agent 的可验证实验案例
这条不属于 coding-agent 主线，因此按 Low 收录；但它是 Anthropic 8 月 18 日官方 research publication，且展示了长程 agent 在科学任务中的工程形态。蛋白设计部分，Claude Mythos Preview 和 Opus 4.8 被给定 protein design prompt、文献/网络资源、Google Drive/Slack/Gmail/BioRxiv connector、GPU 资源和较高 token/sub-agent budget，自主为 15 个 targets 设计 binders。湿实验验证显示 15 个 targets 中 14 个成功，设计 hit rate 约 22% 到 35%，高于当前 protein design campaign 常见的 10-15%，部分 binders 还达到高亲和力。化学分析部分，Claude Opus 5 只拿到 contract lab 的 raw NMR / LC-MS 文件和两句 prompt，就在 23 和 19 分钟内处理数据，结果与实验室 hydrogen counts 和 purity 基本一致。它的工程价值不在“Claude 会生物化学”这个泛化口号，而在可验证流程：raw instrument files、工具编排、湿实验、独立 lab validation、自我校正和 caveats。对后训练数据工程来说，这类轨迹说明高价值科学 agent 数据需要把外部工具、原始文件、实验验证和安全审批一起记录。它也再次提醒生物设计是 dual-use 领域，训练/评测数据采集必须带访问控制和安全边界。
🔗 链接：https://www.anthropic.com/research/Claude-accelerates-protein-design ｜ 代码：None

### Anthropic Claude text watermark：基于 SynthID-Text 的透明度标记机制
Anthropic 8 月 14 日的 text watermark 官方文属于低优先级，因为它不直接涉及 coding agent 或后训练软件工程，但它是近月官方技术/透明度发布。核心机制来自 Google DeepMind 2024 年 Nature 论文 SynthID-Text：不改变人类可见文字质量，而是在模型选择下一个词时改变随机性来源，让拥有 key 的检测者能判断文本是否可能由 Claude 参与生成。它不携带用户身份，也不需要额外 token；检测问题只是“这段文本有多大概率包含 Claude watermark”，不是判断作者是谁或是否由其它 AI 生成。文章也诚实说明限制：短文本信息量不足，编辑、改写或混入其它来源会削弱检测，且不同厂商 watermark key 和方法不同。OpenAI/Anthropic 等模型提供商在 EU AI Act 和 AI-generated content transparency 约束下都需要类似标记机制，这会影响下游内容 provenance。对 agent 工程的间接启发是，未来自动生成代码注释、文档、报告和合规材料时，输出 provenance 可能成为工作流字段。对训练数据过滤来说，watermark 也可能成为识别 AI-generated synthetic content 的一个弱信号，但不能单独作为污染检测依据。
🔗 链接：https://www.anthropic.com/news/claude-text-watermark ｜ 代码：None

## 🔥 社区热点专栏

### 🔥 大佬观点

**Greg Brockman / OpenAI：安全团队需要“现在就给 agent 授权访问代码库和安全上下文”，而不是等全公司大 rollout。**  
在 `The Defender's Window` 中，Brockman 的核心观点是防御方窗口期很短，AI 正在同时放大攻击和防御能力；他建议从高优先级系统开始，让 agent 做安全评估、CI review、漏洞 backlog triage 和告警初筛。值得注意的是，他把 agent 定位为接入真实工程系统的安全同事，而不是一次性问答工具，这会推动 security-agent harness、权限和证据链成为生产基础设施。🔗 https://blog.gregbrockman.com/the-defenders-window ｜ https://openai.com/index/the-defenders-window/

**Harness-IF 社区讨论：真正的问题不是“agent 有没有遵守规则”，而是“这条规则是否改变了默认行为”。**  
围绕 Harness-IF 的转述把一句话讲得很清楚：如果测试规则刚好符合模型原本会做的事，合规分数会被夸大；必须给 agent 一条 against-prior 规则，才能测出真实可控性。这个观点对 `AGENTS.md`、tool schema、skill 描述和项目规则尤其重要，因为很多团队目前只看最终任务成功，没看规则是否真的约束了运行过程。🔗 https://arxiv.org/abs/2608.11727

### ⭐ 超火仓库/项目

**deepseek-ai/deepseek-harness：8 月 13 日创建后超过 161k stars，开源“everything is a plugin” agent harness。**  
它火在把模型、工具、技能、session、沙箱、UI 和 agent loop 全部插件化，回应了社区想要可审计、可替换、可自建 agent runtime 的需求。真实痛点是生产 harness 的每个组件都会影响成本、权限、轨迹和性能，不能被锁死在单一黑箱客户端里。🔗 https://github.com/deepseek-ai/deepseek-harness

**ai-boost/awesome-harness-engineering：约 3.6k stars，正在成为 harness engineering 的社区索引。**  
它把 memory、MCP、permissions、observability、orchestration、security sandbox 和 eval patterns 汇总到同一知识库，解决“大家都在说 harness，但资料散在博客、论文和仓库里”的问题。它的热度说明社区已经把 agent 成败的主要变量从模型 endpoint 扩展到模型外的工程层。🔗 https://github.com/ai-boost/awesome-harness-engineering
