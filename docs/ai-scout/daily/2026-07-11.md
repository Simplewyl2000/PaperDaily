## 📝 逐条讲解

### SWE-Router：用早期探索轨迹决定是否升级到强模型
很多团队为了保证 coding-agent 成功率，会把所有任务直接交给最贵的 frontier model，但真实工程任务里有不少只是局部 typo、简单依赖更新或小范围测试修复。传统模型路由器通常只看 issue 描述，这在软件工程里信息太少：同样一句“修复缓存 bug”可能是两行改动，也可能需要跨模块重构。SWE-Router 的做法是先让便宜模型跑几步探索，读仓库、尝试定位、收集早期证据，然后用 value head 判断继续用便宜模型是否划算，低于阈值再升级到强模型。这样路由决策不再依赖静态 prompt，而是依赖 partial trajectory，也就是 agent 已经实际观察到的代码和失败信号。论文还发布多模型轨迹数据，用于训练和复现实验中的 routing function。它值得关注，因为后训练和生产 harness 都越来越需要“成本-成功率”控制面，不能只靠模型名和固定预算。对 trajectory selection 来说，早期探索轨迹本身成为可学习信号：它既能判断任务难度，也能告诉系统何时该换模型、换策略或请求人工介入。
🔗 链接：https://arxiv.org/html/2607.00053 ｜ 代码：None

### TOFFEE：用执行反馈和 MCTS 合成企业数据 agent 轨迹
企业数据 agent 的训练难点在于，真实数据环境高度异构：表结构、业务字段、分析流程和工具约束都不一样，手工标注完整多轮轨迹既慢又贵。TOFFEE 把这个问题做成一个可执行轨迹合成系统，而不是简单让大模型凭空编几条 tool-call demo。它先从真实数据环境构造任务池，再用 Monte Carlo Tree Search 在分析状态上探索，每一步都实际执行工具并根据观察结果估计分支价值。系统还加入 Learned Cost Model，根据当前步骤复杂度自动选择模型 tier、reasoning effort、历史长度和工具配置，避免所有步骤都使用最贵模型。更工程化的是 cross-task prefix DAG：不同任务共享相同前缀时可以复用已有探索，减少重复执行成本。项目释放 TOFFEE-30K 轨迹语料，每条包含 reasoning turns、tool-call messages、tool outputs 和 tool metadata，可直接导出为 SFT 或 ICL 样本。虽然它面向数据分析 agent 而不是 coding agent，但“执行反馈 + 搜索 + 成本模型 + 可导出轨迹”的数据工程范式非常值得迁移到代码后训练。
🔗 链接：https://arxiv.org/html/2607.06233 ｜ 代码：https://github.com/wang0702/toffee

### Learning to Control LLM Agent Harnesses：把 harness 控制层做成离线 RL 问题
现在很多 agent 改进都集中在换模型、调提示词或手写 workflow，但真正影响可靠性的常常是 harness：什么时候检查、什么时候重试、什么时候压缩上下文、什么时候停止。本文把 harness 操作形式化为 Harness MDP，轻量控制器选择结构化执行动作，而底层 LLM executor 保持冻结。训练时只用离线 rollouts 和最终 task-rubric reward，通过 advantage-weighted regression 学习哪些 harness 行为更像高回报轨迹。作者还提出 Harness Maturity Score，把最终任务质量和“执行过程是否成熟”分开看，例如是否有证据检查、是否过早停止、是否在失败后修正。实验覆盖六个控制域和两个 public-benchmark adapters，显示控制器能稳定改善验证行为，并在 tau-bench retail、AgentBench DB-Bench 和带结构化 verifier 的 coding 任务上带来最终质量提升。它的新意不是又发明一个 agent 框架，而是把 harness 本身当成可学习、可评测、可离线优化的控制层。对后训练软件工程来说，这提示我们保存 rollouts 时要记录 harness action，不然以后无法训练“怎么跑 agent”而只能训练“模型说了什么”。
🔗 链接：https://arxiv.org/html/2607.05458 ｜ 代码：https://github.com/Hik289/Agentic-RL-harness

### SpellSmith：用安全感知 tool description 缓解 MCP taint-style 漏洞
MCP server 让 agent 能调用外部工具，但工具参数往往来自用户、网页、文件或其它不可信数据源；如果 server 把这些数据直接拼进敏感操作，就会形成类似传统软件的 taint-style 漏洞。SpellSmith 研究的问题是：能不能在不大改 server 代码的情况下，通过更安全的 tool description 让 agent 避免触发这些漏洞。作者基于 45 个 MCP servers 和 130 个 tools 构造了 792 个恶意 prompt，覆盖五类 taint-style 漏洞和多种 jailbreak 表面形式。实验结果显示，安全感知描述能显著降低 exploit-triggering behavior，报告 attack success rate 只有 0.13%，同时比代码级修复成本低、泛化性更好。这里的重点不是“工具描述万能”，而是 tool schema/description 已经成为 agent 安全边界的一部分，需要像 API 合约一样被测试。它对 MCP 工程很有启发：工具描述不应只是方便模型选择工具，还应明确不可信字段、敏感 sink、参数约束和禁止的数据流。对 eval anti-cheating 和安全后训练来说，这类 benchmark 能把“模型是否被诱导错误使用工具”测到 tool-level，而不是停留在泛化的拒答评测。
🔗 链接：https://arxiv.org/html/2607.07461v1 ｜ 代码：None

### Agent Data Injection：证明结构化工具响应也能被字段注入攻击污染
很多 agent 安全方案默认只要把工具响应结构化成 JSON/YAML，就能降低 prompt injection 风险，因为模型能区分字段和值。Agent Data Injection 这篇论文提醒我们，结构化格式本身也可能被攻击者利用：不可信字段中插入概率性 delimiter 或格式片段，诱导模型把内容解释成更高权限字段。作者在 AgentDojo 上把工具响应从 YAML 改成更常见的 JSON，并加入 108 个 ADI attacks，同时保留 935 个传统 instruction injection 攻击作对照。结果很有警示性：在多种已有防御下，传统指令注入几乎被压到接近 0% ASR，但 ADI 仍可达到 22.2% 到 50.0% 的成功率；只有 CaMeL Strict 完全阻断。它说明生产 agent 不能只靠“模型已经学会忽略恶意指令”，还要对工具响应的字段边界、可信来源和解析策略做工程防护。对 coding agent 来说，日志、测试输出、issue 评论、网页内容和依赖元数据都可能成为 ADI 载体。对后训练数据工程而言，工具响应格式、字段 provenance 和 parser 行为必须进入轨迹元数据，否则我们无法解释 agent 为什么被某个 observation 带偏。
🔗 链接：https://arxiv.org/html/2607.05120v1 ｜ 代码：https://github.com/compsec-snu/adi

### EvoAgentBench：把 agent 自我演化评测从记忆改为 procedural ability transfer
很多“agent 会学习”的项目其实只是在记忆里追加文本，总结上次发生了什么，但这不等于 agent 真能把经验迁移到新任务。EvoAgentBench 把自我演化定义得更工程化：有价值的经验不是事实记忆，而是可复用的 procedure，例如如何搜索、如何调试、如何验证、如何拆解任务。它从 agent 执行轨迹中抽取 trace-grounded Abilities，再把这些能力规范成 operational units，并构建 Ability Graph，连接训练任务和测试任务之间的程序性重叠。benchmark 覆盖 web research、algorithmic reasoning、software engineering、code implementation 和 knowledge work，软件工程部分基于 SWE-Bench，提供 train/test split 和标准化评测协议。论文报告 curated Ability content 能跨模型家族带来可靠迁移，但现有自动方法并不能在所有设置下持续正收益，说明“自动总结经验”很容易负迁移。它对 skill evolving 很重要，因为它要求技能或记忆必须通过 held-out transfer 验证，而不是模型自称学到了东西。对后训练软件工程来说，EvoAgentBench 提供了一个更细的诊断框架：我们要测 experience encoding、routing 和 uptake，而不是只看下一次是否碰巧分数高。
🔗 链接：https://arxiv.org/html/2607.05202v1 ｜ 代码：https://huggingface.co/datasets/EverMind-AI/EvoAgentBench

### Hindsight Supervised Learning：把失败轨迹里“意外完成的目标”重标成训练数据
长程 agent rollout 里经常出现一种浪费：任务本来失败了，但轨迹中某些片段其实完成了别的有价值目标，例如正确找到文件、成功配置环境、修复了次要问题或完成了子任务。Hindsight Supervised Learning 借鉴“事后重标”的思想，让辅助 LLM 审阅完整轨迹，找出 agent 实际达成的自然语言目标，然后把轨迹和这些重标目标配对成新的监督数据。为了减少脏数据，作者加入 irrelevant-action masking，避免训练模型模仿与新目标无关的动作；也加入 sample reweighting，降低低质量重标样本的影响。这个分支可以和已有 SFT 或 DPO pipeline 组合，不要求重做整个后训练系统。实验显示它在长程、目标空间多样的任务上尤其有效，在 ALFWorld 中只用四分之一 ground-truth demonstrations 就超过完整数据 baseline。它对 trajectory selection 的启发很直接：失败轨迹不应该整体丢弃或整体保留，而应拆出其中真正可训练的成功片段。对 coding agent 来说，未来可以把“定位成功但补丁失败”“测试构造成功但实现失败”“依赖修复成功但业务逻辑失败”等片段重标成细粒度训练样本。
🔗 链接：https://arxiv.org/html/2607.04235v1 ｜ 代码：None

### Anthropic + UST：Claude Code 进入硬件/硅验证闭环
这条 Anthropic 官方案例不是普通合作新闻，因为它描述了一个很具体的 agent 工程闭环：把 Claude Code 放进 UST 的硬件和硅验证平台。传统芯片或嵌入式验证里，工程师需要读 schematics、pinouts、设计文档和设备数据，手写 regression tests，并把真实设备信号和 digital twin 预期行为对比。UST 的做法是让 Claude Code 直接读取芯片 pinouts 和硬件 schematics，生成并运行回归测试脚本，检查设计变更是否造成下游影响。Claude 还会比较 live edge data 与 digital twin，标出 firmware regression 和 signal-integrity faults。UST 称其现有闭环 agentic validation pipeline 已能把验证周期缩短 50-70%，现在把 Claude 作为 reasoning layer 接入以进一步减少手工脚本和更早发现缺陷。它值得关注，因为 coding agent 的“代码仓库 + 测试”范式正在迁移到硬件/物理系统验证：输入不再只有源码，还有设计图、传感器数据和仿真模型。对后训练软件工程来说，这类轨迹会包含多模态工程文档、测试生成、真实设备反馈和长任务上下文，是比普通 bug fix 更接近工业自动化的 agent 数据。

### repository-harness：把 AGENTS.md、产品契约和验证矩阵做成 repo 级 agent harness
许多团队已经在仓库里放 AGENTS.md、CLAUDE.md 或各种 skill，但这些文件常常只是零散规则，缺少统一安装、产品契约、任务入口和验证要求。repository-harness 把“让一个仓库适合 agent 工作”做成一个可安装的 repo-level operating harness。它提供 AGENTS.md、product contracts、story packets、validation matrix 和 decision records，让 agent 在改代码前知道从哪里开始、工作风险是什么、需要什么 proof、哪些决策应被继承。对 Claude Code，它还会通过 `--claude` 安装或刷新 CLAUDE.md，使新的 Claude 会话能自动导入 AGENTS.md 和关键文档，避免规则对某些客户端不可见。项目 5 月创建、7 月 10 日仍活跃，GitHub 约 1.06k stars，说明“agent-ready repo”正在从个人习惯变成可复用工具。它的工程价值不是替模型写代码，而是把任务边界、上下文、验证和历史决策外化成可 review 的文件。对后训练轨迹来说，这类 repo harness 会成为重要条件变量：同一个 agent 在有产品契约和验证矩阵的仓库里，行为会和裸仓库完全不同。
🔗 链接：https://github.com/hoangnb24/repository-harness ｜ 代码：https://github.com/hoangnb24/repository-harness

### FableCut：用 JSON timeline + MCP/REST 把浏览器视频编辑器变成 agent 可控工具
Agent-Friendly Software 的一个关键方向，是把传统 GUI 工具变成 agent 能稳定调用、能检查结果、能重复执行的接口。FableCut 做的是浏览器视频编辑器，但它不是只给人一个 UI，而是把视频 timeline 暴露成 JSON，并提供 MCP 与 REST 接口，让 Claude Code、Codex 或其它 agent 可以直接创建和修改剪辑。它的 live-reloading UI 让人类能看到 agent 操作后的即时结果，而 JSON timeline 又让 agent 不必通过脆弱的屏幕坐标来操作复杂 GUI。项目 7 月 6 日创建，7 月 9 日仍活跃，约 307 stars，属于本周新建 agent-friendly 工具里的高热项目。它解决的真实痛点是：视频编辑、设计、文档排版这类任务本来高度 GUI 化，模型如果只能“看屏幕点击”，很难做可复现自动化。把 timeline 变成结构化、可 diff、可 API 调用的对象后，agent 才能做生成、修改、回放和验证闭环。对后训练软件工程来说，这类项目说明未来的 CLI Anything 不一定真是 CLI，也可以是“结构化状态 + 标准 API + 可视化确认”的 agent-native 软件层。
🔗 链接：https://github.com/ronak-create/FableCut ｜ 代码：https://github.com/ronak-create/FableCut

### CompactionRL：把长程 agent 的上下文压缩也纳入 RL 训练
长程 coding agent 经常在任务完成前耗尽上下文，因此很多产品会做自动 compaction 或摘要，但摘要质量通常只在推理时临时调，不一定经过训练。CompactionRL 的核心是把上下文压缩纳入 RL rollout：agent 不只学习怎么做任务，也学习在什么时候、用什么方式生成可继续执行的 compressed context。它联合优化 task execution 和 summary generation，并使用 token-level loss normalization 与 cross-trajectory generalized advantage estimation，让 compacted trajectories 也能提供训练信号。论文在 SWE-bench Verified 和 Terminal-Bench 2.0 上报告稳定提升，例如 GLM-4.5-Air 在 SWE-bench Verified 上达到 66.8%，相对 baseline 增加 7.0 分，在 Terminal-Bench 2.0 上增加 3.1 分。它被部署到 GLM-5.2 的 agentic RL pipeline 中，说明这不是单纯概念实验。它按 Medium 收录，因为更偏 LLM RL 方法和系统结合，而非专门 coding-agent benchmark。对后训练工程而言，compaction 不应只是产品层 hack，而应进入训练目标、轨迹 schema 和评测：摘要漏掉关键约束会直接改变后续行动。
🔗 链接：https://arxiv.org/html/2607.05378 ｜ 代码：None

### Single-Rollout Asynchronous Optimization：面向长程 agentic RL 的稳定异步训练
Agentic RL 的 rollout 很长、时延差异大，传统同步 GRPO 需要等一组样本都回来再更新，容易造成训练和生成资源互相等待。SAO 关注的是异步训练中的稳定性问题：如果 rollouts 到达就更新，吞吐可能变好，但 off-policy 与 group-wise sampling 会让训练不稳。它把采样改成 single-rollout sampling，也就是每个 prompt 只用一个 rollout，并配合实际 value-model training design 来降低 off-policy 影响。为了稳定 token-level 优化，作者还使用严格的 double-side token-level clipping。论文称 SAO 能稳定训练 1000 steps，并在 SWE-Bench Verified、BeyondAIME、IMOAnswerBench 等 agentic coding 和 reasoning benchmark 上优于 GRPO 及其变体，且用于训练 open GLM-5.2。它按 Medium 收录，因为重点更偏 RL 基础设施和优化稳定性，算法细节较多；但它触及长程 coding-agent 训练的真实瓶颈。对工程团队来说，agent RL 不是把 PPO/GRPO 套上去就行，还要处理 rollout 异步、长尾任务、数据新鲜度、价值模型和训练稳定性这些系统问题。
🔗 链接：https://arxiv.org/html/2607.07508 ｜ 代码：None

### AgentGym2：在非理想真实环境里评测动态工具获取与端到端执行
很多 agent benchmark 虽然比单轮问答复杂，但仍然给了干净 sandbox、固定工具和相对明确的 instruction，这和真实部署有差距。AgentGym2 的目标是构造 de-idealized real-world environments，重点看 agent 在工具不完美、任务开放、需要动态获取工具和端到端执行时的表现。它把 web navigation、shopping、science、text games、tool-use 和软件工程等环境放在统一 interaction interface 和 evaluation protocol 下，同时强调真实部署维度，例如 dynamic tool acquisition 与 robustness。论文指出即使强模型在这类设置中也明显吃力，说明当前 agent benchmark 仍可能高估生产表现。它按 Medium 收录，因为是广谱 agent benchmark，不专门服务 coding-agent 后训练；但它对评测工程很有价值。对软件工程 agent 来说，真实仓库也常常是非理想环境：缺文档、工具缺失、权限不完整、依赖会坏、需求不清。未来更好的 coding-agent eval 也应少给“完美工具箱”，多测 agent 如何发现、安装、验证和放弃工具。
🔗 链接：https://arxiv.org/html/2607.05174v1 ｜ 代码：None

### OpenAgent / PAFT：用轨迹扰动缓解 tool-use SFT 的静态过拟合
Tool-use agent 的 SFT 常常只训练成功轨迹，这会让模型习惯干净状态：工具名称稳定、反馈清楚、路径正确、环境不变。OpenAgent 这篇工作系统分析了 open-world setting 下的泛化问题，发现 SFT 和 RL 都会退化，但失败模式不同。SFT 更容易 trajectory overfitting 和 brittle symbolic anchoring，也就是学会某些固定路径或符号线索；RL 虽然语义 grounding 好一些，却可能因为 reward teleological bias 而出现 boundary blindness。作者提出 Perturbation-Augmented Fine-Tuning，把受控轨迹级扰动加入 SFT 数据，用来让模型见到错误状态、模糊反馈和符号变化。这个方向的工程价值在于，它把“泛化差”具体落到数据分布问题：训练集只包含成功执行历史，测试时 agent 却会进入错误、噪声和变动状态。它按 Medium 收录，因为主题偏通用 tool-use post-training，但对 coding-agent 数据构造非常相关。真实代码任务中，失败命令、过期文档、模糊测试输出和被改过的文件都是常态，训练数据如果只保存完美轨迹，模型就很难学会恢复。
🔗 链接：https://arxiv.org/html/2607.01084v1 ｜ 代码：None

### OpenAI Bio Bug Bounty：把 GPT-5.5 临时生物安全 bounty 升级为 GPT-5.6 持续项目
OpenAI 7 月 9 日把原本针对 GPT-5.5 的 Bio Bug Bounty 升级成持续性的 OpenAI Bio Bounty Program，主题不是 coding agent，因此按 Low 收录。它的技术重点是 universal jailbreak：参与者要找到能稳定绕过预定义 bio/chem safety challenge 的提示，而不是单个偶然越狱样例。新项目把 GPT-5.6 纳入范围，并在 GPT-5.5 原测试窗口结束前继续接受 GPT-5.5 提交；顶级奖励从 25,000 美元提高到 50,000 美元。项目仍是 private vetted platform，需要申请、ChatGPT 账号和 NDA，这说明高风险能力的 red-team 数据不会完全公开。它值得放进官方源和低优先主表，是因为它把安全评测从内部 benchmark 扩展成持续 bug bounty 机制，类似软件安全中的漏洞赏金。对本日报主题的间接启发是，高风险 agent 评测也需要可复用 challenge、明确成功标准、私密复现平台、奖励机制和 scope 更新，而不是一次性系统卡说明。对后训练工程而言，bug bounty 发现的 universal failure mode 可能成为未来 guardrail 与安全 SFT/RL 的重要数据来源。

### 🔥 大佬观点

**Karpathy / Lilian Weng / harness 社区：性能差距越来越像 harness 差距，而不只是模型差距。**  
近期围绕 harness engineering 的讨论把一个共识推到台前：同一模型在不同 agent loop、工具面、上下文压缩、验证策略和恢复机制下，表现可能差很多。这个观点值得注意，因为今天的 SWE-Router、offline harness RL 和 repository-harness 都在不同层面证明，生产能力来自模型与 harness 的组合，而不是单个 model score。🔗 https://lilianweng.github.io/posts/2026-07-04-harness/ ｜ https://dev.to/wdsega/karpathy-agent-performance-gap-is-in-the-harness-not-the-model-199j
