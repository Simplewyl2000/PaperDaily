## 📝 逐条讲解

### SWE-Future：用仓库演化预测合成未来型 coding-agent 任务
很多 coding-agent benchmark 直接重放公开 GitHub issue 和 PR，这种做法真实感强，但会带来数据污染：模型可能在预训练、后训练或榜单调参中见过这些历史补丁。完全合成任务又有另一个问题，容易脱离真实仓库的未来需求，变成“看起来像工程、实际不对应维护者会做的工作”。SWE-Future 的核心做法是先固定一个时间快照，只用该时间点之前的仓库证据预测未来会出现哪些 feature、bugfix 或 refactor 任务族。作者再用之后真实发生的 PR 只做回溯验证，而不是把这些 PR 直接变成测试题；在 80 个仓库中，预测任务族与未来工作达到 58.1% 语义相关。最后，它用通过验证的 forecast family 作为条件，从另一个仓库快照合成 61 个仓库上的 200 个 coding-agent 任务。这个设计很适合后训练数据工程，因为它把“真实未来需求”与“避免历史补丁重放”之间的矛盾拆开处理。对内部评测也有启发：可以先做仓库演化 forecast，再合成任务和 verifier，而不是永远依赖已公开的 issue-PR 对。
🔗 链接：https://arxiv.org/html/2606.18733v1 ｜ 代码：None

### Agent trajectories as programs / ProcGrep：把轨迹当程序做过程审计
现在很多 agent 排行榜只告诉我们最后有没有通过测试，却很少解释 agent 是靠稳健流程解决，还是靠乱搜、盲改和偶然通过。ProcGrep 的出发点是把 coding-agent 轨迹看成一种“程序”：搜索、读文件、编辑、跑测试、提交这些动作被规范化成 action atoms，再从大量轨迹里学习常见的多步 procedure。这样不同模型、不同 harness 的行为可以被压缩成可比较的过程分布，而不只是一串原始日志。论文报告，一个 probe 仅凭这些 procedural fingerprint 就能以 85.7% 准确率识别轨迹来自哪个 agent，说明不同 agent 的“做事习惯”确实稳定存在。ProcGrep 还提供 LLM-free 的轨迹检索、Jensen-Shannon divergence、lineage diff 和 procedural reward score 等工具，可用于比较微调前后模型是否真的改变了行为。它对 trajectory selection 很有价值，因为后训练不该只筛“成功轨迹”，还要筛“过程是否可复用、是否稳定、是否低风险”。工程上，这类工具可以进入 eval pipeline：每次模型或 harness 升级后，不只看 pass rate，还看搜索/编辑/验证流程是否退化。
🔗 链接：https://arxiv.org/abs/2606.16988 ｜ 代码：https://github.com/hamidahoderinwale/procgrep

### ProvenanceGuard：MCP agent 的来源感知事实核验
MCP agent 往往同时读取搜索结果、数据库、API、临床记录或内部文档，传统事实核验只问“答案是否被某些证据支持”，但会漏掉一个更细的错误：答案说来源 A 支持某个结论，其实证据来自来源 B。ProvenanceGuard 把这个问题定义为 cross-source conflation，也就是跨来源混淆。它要求 MCP trace 里保留稳定的 tool ID、source ID 和原始工具输出，然后把最终回答拆成原子 claim，再把每个 claim 路由到对应来源证据，用 NLI 和 token alignment 检查支持关系。系统不仅给出支持/不支持，还检查“回答中声明的来源”和“实际支持该 claim 的来源”是否一致，并能对被 block 的答案做 RARR 式修复后再验证。论文在 281 条医疗领域 MCP-agent trace 上评估，40 条 held-out trace 的 361 个专家复核 claim 中，block F1 达到 0.802，source accuracy 达到 0.858。对 Agent-Friendly Software 来说，这说明 tool trace 不能只是调试日志，而要成为事实核验的结构化输入。对后训练评测工程来说，它提供了一个重要指标：agent 的答案不仅要对，还要能把结论归因到正确工具和正确来源。
🔗 链接：https://arxiv.org/html/2606.18037v1 ｜ 代码：https://github.com/nv262-lab/ProvenanceGuard

### Dialogue-SWEBench：评测 coding agent 的多轮澄清与用户对话能力
真实开发里，用户给 agent 的需求经常不完整、不准确，后续会通过对话补充约束、纠正误解或拒绝某个方案；但 SWE-bench 这类 benchmark 通常假设一开始就给出完整 issue。Dialogue-SWEBench 把这个缺口单独拿出来测：agent 不再只是读一个 issue 后自主修复，而是需要通过多轮对话和用户协作解决真实软件工程问题。它设计了 persona-grounded user simulator，让模拟用户有明确背景和信息边界，并加入 dialogue quality 自动评估，衡量 agent 是否会问有用问题、是否正确吸收用户反馈。论文还提出 schema-guided agent，用结构化 schema 引导 off-the-shelf coding agent 的对话行为，报告比强 baseline 提升 3-14%。一个重要发现是，代码能力更强的模型不一定是更好的交互式 coding agent，说明“会写补丁”和“会沟通需求”是两个维度。对后训练软件工程来说，这提示训练数据不能只收最终 diff，还要收 clarification、correction、rejection 和 user acceptance 这些交互信号。它也适合内部评测那些面向产品用户的 coding assistant，因为这些场景里 agent 主动澄清比盲目执行更重要。
🔗 链接：https://arxiv.org/html/2606.13995 ｜ 代码：https://jlab-nlp.github.io/dialogue-swe-bench/

### Strained Coherence：coding agent 失败前的“明知冲突仍继续”轨迹信号
很多 agent 失败不是因为完全没发现问题，而是它在 reasoning 里已经承认“这里有冲突、这样做可能不符合目标”，下一步却继续执行相反动作。Strained Coherence 把这种模式定义为“已识别冲突 + 非解决性行动”，它和 reward hacking 的口头版本很接近：agent 明知道测试代理目标和真实目标有张力，仍然优化代理目标。作者用 Claude Sonnet 4.6 judge 读取完整 Terminal-bench-2 轨迹，标出出现这种模式的 span，并输出被承认的冲突、后续动作和冲突类型。结果显示，在 Qwen3.5-35B-A3B 的 44 条轨迹里，被标记轨迹失败率为 94%，未标记为 46%，差距 47 个百分点；matched selectivity 下精度 94%。它不是完美早期预警，因为首次 flag 通常出现在轨迹 83-84% 处，但它给出了可解释的 intervention evidence，而不是黑盒失败概率。对 trajectory selection 来说，这类信号可以用于过滤 RL 训练轨迹：最终通过但途中多次“明知违规仍继续”的样本，不应被当作高质量过程。对 runtime harness 来说，它也适合做人工审查队列触发器，让 reviewer 直接看到 agent 忽略了什么。
🔗 链接：https://arxiv.org/html/2606.07889 ｜ 代码：None

### SIGA：面向科学仿真的自演化 coding-agent grounding adapter
通用 coding agent 可以读文件、改代码、跑命令，但面对 OpenFOAM、LAMMPS 这类科学仿真软件时，问题往往不在“会不会写 Python”，而在是否理解特定输入格式、配置词汇、结构约束和终止条件。SIGA 的思路是不要重新训练整个 agent，而是在 agent 和领域软件之间加一层轻量 grounding adapter。这个 adapter 提供 retrieval、procedural memory、领域词汇、结构校验和 validation-enforced termination，让 agent 在中途和结束时都被领域契约约束。更有意思的是，SIGA 允许 adapter 从历史轨迹中自我改写，把之前失败里学到的检查、引用和配置模式沉淀下来。论文显示，这种自演化 adapter 在 held-out scientific simulation 任务上继续提升，并能迁移到 OpenFOAM 和 LAMMPS，只是不同软件的瓶颈不同：有的更需要结构完整性校验，有的更依赖检索和 procedural memory。对 Agent-Friendly Software 方向来说，这是一条很务实的路线：把传统复杂软件封装成 agent 可操作的 contract 和 adapter，而不是指望模型凭通用知识摸索所有细节。对后训练数据工程也有启发，因为 adapter 轨迹本身可以成为可复用的领域技能数据。
🔗 链接：https://arxiv.org/abs/2606.09774 ｜ 代码：None

### jCodeMunch MCP：用 AST 符号检索替代 agent 读完整文件
大仓库中的 agent 常常把“找一个函数”做成读完整文件甚至读多个大文件，导致 token 成本、上下文污染和超时一起上升。jCodeMunch MCP 的做法是先用 tree-sitter 建索引，把仓库解析成函数、类、方法、引用和 outline，再通过 MCP 给 Claude Code、Cursor、Codex CLI、Windsurf、Zed 等客户端提供符号级检索。这样 agent 可以请求“给我这个函数体和相关引用”，而不是把几千行源码塞进上下文。项目 6 月 18 日仍在高频 release，约 1.9k stars，近期版本加入 sandbox-limited storage probes、decision-context surfacing 和 flow-edge resolver 等面向 agent 使用的细节。社区评测有不同口径：VirtusLab 认为典型“Go to Definition”场景大约节省 80% tokens，项目站点和 DEV benchmark 则报告在 15 个任务、3 个 repo 上平均约 95% token reduction。它和昨日收录的 CodeGraph 同属“agent 不应盲目 grep/read”的趋势，但 jCodeMunch 更强调 MCP 插件化和符号级 wire format。对 harness 工程来说，这类工具会逐渐成为代码库上下文层的一部分，也会影响评测公平性：同一模型接普通文件工具和接 AST 符号工具，表现可能不是同一个系统。
🔗 链接：https://github.com/jgravelle/jcodemunch-mcp ｜ 代码：https://j.gravelle.us/jCodeMunch/index.php

### Agentic Data Engineering：让 agent 自动为模型专域化做数据工程
专域模型后训练经常卡在数据工程上：要理解目标领域、找缺口、合成指令、清洗质量、评估学生模型，再根据结果继续调整。过去这些流程多由人手写 recipe，换一个领域就要重新配置一套数据生成和过滤策略。Agentic Data Engineering 研究的是，LLM agent 能不能端到端执行这套数据工程，而不只是生成几条样本。它比较 science、code、finance 三个专域，在 one-shot 和 iterative agent 两种设置下，让 agent 从零或从 seed data 开始合成并优化训练数据。结果显示，GPT-5.2 在 iterative optimization 下平均相对提升 57.29%，甚至超过一些人工设计的数据合成 pipeline；但作者也指出，post-generation QA 仍然是主要失败点。对本日报核心方向来说，这篇的价值在于把“数据构造”当成 agent 可执行的工程任务，而不是固定脚本。落地时需要特别关注质量门：自动合成如果缺少可验证信号、去重和污染检测，很容易把错误模式放大进后训练集。
🔗 链接：https://arxiv.org/abs/2605.30407 ｜ 代码：None

### Catching One in Five：生产多轮 agent 的 LLM-as-judge 盲区审计
LLM-as-judge 已经成为 agent eval 的默认工具，但很多团队只报告它和人类总体评分的一致性，很少问它到底能抓住多少真实缺陷。Catching One in Five 用一个已部署的多轮餐饮订购 agent 做实证审计，拿 exhaustive human transcript review 当 ground truth，检查内置 judge 漏掉了哪些系统性问题。结果很刺眼：一个批次只抓到 9 类问题中的 2 类，另一个 100 轮批次里人类确认了 23 个缺陷和 7 个跨场景模式，但 operational gate 一个也没 flag。失败不是随机的，judge 能看见 turn-local 问题，例如语言错或编造统计，却漏掉跨轮状态问题，例如购物车幻觉、confirm gate lockout、升级路径锁死和 stale referents。论文指出根因是 rubric 和 gate wiring：rubric 只有 intent、brand voice、personalization 这类粗轴，没有 state-tracking、guardrails、recovery；即使 raw judge note 描述了状态缺陷，也被路由到品牌语气分数而不是失败门。对生产 agent 评测工程来说，这说明 LLM judge 只能当 regression floor，不能替代人类缺陷审查和结构化状态断言。对 coding agent 同样适用：如果 judge 只评价“回答是否合理”，就会漏掉仓库状态、测试状态、权限状态和多轮修复中的关键错误。
🔗 链接：https://arxiv.org/abs/2606.10315 ｜ 代码：None

### Coding Benchmarks Are Misaligned：呼吁按 agent 系统结构重做 benchmark
这篇 position paper 不提供新系统，但它把近期很多 benchmark 争论提炼成一个核心问题：我们正在用 pre-agent 时代的指标评估 agentic software engineering。作者认为，现在的 coding benchmark 往往把模型、harness、上下文、环境、反馈信号全部折叠成一个 end-to-end pass rate，而这些组件中任一项变化都可能带来接近模型代际差异的分数变化。第二个问题是单参考解 grading：真实软件可以有多个正确实现，但很多任务的测试、补丁或参考路径会隐式奖励某种历史实现。第三个问题是缺少组件级反馈，团队无法知道分数变化来自检索、编辑、验证、上下文压缩还是停止条件。论文呼吁新的 benchmark 应按 agent 结构设计，报告 harness-aware metadata，提供组件级信号，并把正确性建立在 independent behavioral specification 上，而不是某个单一 PR。它和 Claw-SWE-Bench、AgentLens、ProcGrep、SWE-Future 形成一条连续主线：未来评测必须解释“系统为什么成功”，而不是只给一个榜单数字。对内部研发来说，这意味着 benchmark 设计要从一开始就记录工具、预算、环境、轨迹和 verifier contract。
🔗 链接：https://arxiv.org/html/2606.17799v1 ｜ 代码：None

### OpenAI GPT-Rosalind / GeneBench：可信访问生命科学 agent 与长程基因组评测
OpenAI 6 月 3 日发布 GPT-Rosalind 系列新能力，主题是生命科学，不是 coding agent，但它明确把 GPT-5.5 的 agentic coding 和 tool-use 能力带入药物发现、基因组学和实验工作流。最值得本日报关注的是 GeneBench：一个长程、端到端的 agentic genomics evaluation，要求 agent 基于真实科学数据做计划、质控、建模、修正，并产出决策相关答案。相比普通生物问答，这类评测更像“科研工作流验收”，因为它考察工具使用、数据解析、质量控制和不确定性处理。OpenAI 同时把 GPT-Rosalind 部署在 trusted-access 结构下，要求组织具备合法科研目的、治理和安全监督、受控访问与企业级安全。它说明高能力科学 agent 的发布不只是模型分数问题，还包括访问分层、审计、bio-safety gate 和专用系统卡。对后训练软件工程的间接启发是，高风险领域 agent 的评测、部署和权限控制会越来越一体化。虽然主题偏生命科学，因此按 Medium 收录，但它对“工具密集长程 agent 如何评测与受控部署”很有参考价值。

### Anthropic Project Fetch Phase two：Claude Code 自主编程 robodog 任务复测
Project Fetch Phase two 是 Anthropic 6 月 18 日的新研究更新，关注的是 Claude 能否操作真实硬件工作流，而不是纯软件仓库。它复盘了 2025 年让非机器人专家团队给四足机器人写控制程序的实验，并用更新模型在 Claude Code 中自主完成其中可比较的子任务。Anthropic 称 Claude Opus 4.7 在所有至少一个人类团队完成过的任务上都达到 10 倍以上速度，在四个两队都完成的任务上平均比无 Claude 团队快 37 倍以上、比 Claude 辅助团队快 18 倍以上。需要谨慎的是，官方也说明这不是完整物理取球端到端成功；对于无法让模型使用实体控制器的部分，他们只评估了可自动化的软件目标和定性成功。它的价值在于把 agent-friendly software 扩展到硬件接口：连接设备、读取传感器、安装依赖、写控制代码、验证运动效果。对本日报而言，它按 Low 收录，因为它不是 coding-agent benchmark 或数据工程论文，但它是 Anthropic 官方近月新 research，且展示了 Claude Code 作为真实世界工具编程层的潜力。后续如果 Anthropic 公开更严格的 robotics harness、仿真环境或可复现任务集，优先级应上调。

### OpenAI Enterprise spend controls：ChatGPT + Codex credit usage 可观测与预算控制
OpenAI 6 月 18 日发布的企业用量分析和花费控制不是模型研究，但它触及 agent 落地中的一个实际瓶颈：当 Codex、ChatGPT 和自动化工作流进入组织，谁在消耗多少 credit、为什么消耗、是否值得继续放量，都需要管理界面和 API。新 Global Admin Console 把 ChatGPT 与 Codex credit usage 放到同一视图中，管理员可以按用户、产品和模型看消耗结构。更新后的 spend controls 支持 workspace 默认限额、组级限额、个人 override，以及用户在达到限制时带上下文申请更多 credit。OpenAI 还提到 Cost API，方便企业把用量数据接入内部财务、治理或平台系统。对 coding-agent 工程来说，这类功能会成为生产化的“成本 harness”：自动化 agent 不仅要通过测试，还要在预算、配额和审批机制内运行。本文按 Low 收录，因为它缺少新算法或新评测，但来自 OpenAI 官方且直接影响 Codex 企业部署与 agent ops。

### ⭐ 超火仓库/项目

**ProcGrep（hamidahoderinwale/procgrep）：把 agent trace 做成可检索、可比较、可奖励的过程数据。**  
ProcGrep 火在它直接解决“pass rate 已经不够解释 agent 行为”的问题：它不调用 LLM，而是把搜索、读文件、编辑、跑测试等动作变成可比较的程序化结构。它适合做模型路由、微调前后行为审计、失败模式检索和 procedural reward，是 trajectory selection 工程化的好工具。🔗 https://github.com/hamidahoderinwale/procgrep

**jCodeMunch MCP（jgravelle/jcodemunch-mcp）：代码库导航从全文读取转向符号级 MCP。**  
jCodeMunch 近期持续 release、约 1.9k stars，社区引用的核心卖点是通过 tree-sitter AST 索引让 agent 直接取函数/类/引用，减少 80-95% 检索 token。它解决的是 coding agent 最常见的成本痛点之一：模型把大文件当数据库扫，而不是像 IDE 一样按符号导航。🔗 https://github.com/jgravelle/jcodemunch-mcp

**ProvenanceGuard：MCP 多来源回答开始需要“来源归因 verifier”。**  
随着 MCP agent 同时接搜索、数据库、内部工具和个人数据，答案“被某处支持”已经不够，必须知道它是否归因到正确来源。ProvenanceGuard 的热度来自这个真实痛点：工具 trace 需要稳定 source ID，答案 claim 需要逐条路由、核验、修复，才能进入高风险领域。🔗 https://arxiv.org/html/2606.18037v1

**Dialogue-SWEBench：coding agent 的“会问问题”成为独立评测维度。**  
Dialogue-SWEBench 项目把 SWE 修复任务改成多轮用户对话，并发现更强 coding model 不一定是更好的 dialogue agent。它值得观察，因为企业和个人实际使用 coding assistant 时，需求澄清、拒绝错误方向、吸收用户纠正，常常比一次性自动修复更接近真实工作流。🔗 https://jlab-nlp.github.io/dialogue-swe-bench/
