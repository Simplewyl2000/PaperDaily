## 📝 逐条讲解

### Scrouting：先让 7B searcher 勘察仓库，再按成本路由给 fixer
很多 coding-agent 系统默认一上来就把完整任务交给最强、最贵的 frontier model，让它自己读仓库、定位代码、写补丁和验证。Scrouting 把这个流程拆开：先用一个 7B 级 SuperScout searcher 在仓库里做低成本勘察，产出结构化 handoff，再把真正的修复交给更贵或更便宜的 fixer。关键点是 handoff 不是普通摘要，而是会把发现的文件、证据和约束做 sandbox verification，剔除不可靠 claim 后再交给后续模型。论文还训练/发布了 searcher 权重、SFT search corpus 和 router feature 数据，使得路由不只是 prompt 工程，而是一条可复现的数据管线。在 SWE-bench Pro Python slice 的 266 个任务上，SuperScout 系统解出 159 个，和最佳单模型 158 个基本持平，但每个 solved task 成本约为后者五分之一。更有意思的是 ablation 显示，收益主要来自“先勘察再交接”的 handoff，而不是复杂路由器本身，因为 cheapest fixer + handoff 也能打平 routed system。对后训练软件工程来说，它把仓库探索轨迹变成可训练的前置技能：先定位、验证、压缩上下文，再把任务交给执行模型，这比把所有探索噪声都塞进同一条修复轨迹更容易筛选和复用。
🔗 链接：https://arxiv.org/abs/2608.04804 ｜ 代码：https://github.com/TransformerOptimus/superscout ｜ https://huggingface.co/SuperAGI/SuperScout-7B

### Trajectories That Segment Themselves：让 agent 在采集时声明语义边界
很多 agent 轨迹在训练时会被粗暴切成固定窗口，或者只用整条 episode 的成功/失败标签，这会把“错误假设、纠偏、验证、收敛”混在一起。这个工作提出 collection-time semantic self-segmentation：让执行中的 agent 在运行时声明自己当前采用的 causal hypothesis，也就是“我现在相信问题原因是 X，所以接下来要验证/修复 X”。这种声明不是简单打标签，而是一个可被 reviewer 反驳的接口；如果假设错了，数据采集协议可以构造“wrong cause -> correction”的过渡，这正是普通成功轨迹里很稀缺的训练信号。论文显示，给定切分点但不给 hypothesis，模型仍能把 action block 归因到对应假设，表现超过随机两倍以上，说明这些边界确实有语义结构。它还用 2,551 个 phase-boundary preference pairs 做 DPO，虽然规模小，但在匹配构造的 held-out items 上出现了从错到对的变化。工程价值在于，轨迹筛选不必总等事后 LLM 总结或人工标注；如果运行时就要求 agent 暴露阶段性假设，后续可以直接得到阶段级训练单元、审计标签和失败区域。对 code-agent post-training 来说，这能帮助区分“有用的错误探索”和“无意义的循环”，也让 reject sampling 从 episode 级变成 phase 级。
🔗 链接：https://arxiv.org/abs/2608.02302 ｜ 代码：None

### Exposed by Design：动态审计 414 个公网 MCP server，91.8% 无 OAuth
MCP 正在快速成为 agent 连接工具的默认协议，但很多团队部署 MCP server 时仍把它当成普通开发辅助，而不是一个会触发真实后端权限的攻击面。Exposed by Design 做了一个大规模动态安全评测：先用 Petrel 从证书透明日志、GitHub、npm、PyPI、Hugging Face、Smithery、Shodan、Censys 等 11 类来源发现候选 MCP server，再用 JSON-RPC initialize 主动确认协议实现。确认后，Corvus 框架用 34 个测试模块覆盖 10 类 MCP 专属漏洞，包括 tool poisoning、访问控制绕过、prompt template injection、SSRF、路径遍历和 shell execution 等。四轮 2026 年 7 月测量中，作者确认 640 个 production MCP servers，动态审计 414 个，发现 68 个 reportable vulnerabilities。最刺眼的数据是，91.8% 的动态审计 server 缺少 OAuth authentication，且 687 个 tool instances 暴露 shell execution 能力而没有访问控制。它对 agent 评测工程很重要，因为 MCP server 的安全性不能只看 README 或 schema，必须真实初始化、调用、 fuzz、生成 SARIF 并进入 disclosure pipeline。对后训练数据来说，如果轨迹里记录的是一个未认证公网 MCP 工具调用，训练系统也需要知道这是高风险环境，而不能只把它当作普通工具使用成功样本。
🔗 链接：https://arxiv.org/html/2608.00150v1 ｜ 代码：Corvus（paper release）

### SWE-NFI：用 92 条可执行规则评测 coding agent 的非功能改进能力
现在的 coding-agent 榜单大多关心“bug 修好了没有”或“功能测试过了没有”，但真实软件维护里有大量工作是非功能改进，例如重构、可读性、结构简化、性能和维护性提升。SWE-NFI 专门评测 agent 是否能做 behavior-preserving non-functional improvements，也就是不改变外部行为，却让代码质量更好。它从真实开源 Python 项目的已合并 PR 中构造 188 个任务，并把开发者关心的改进拆成 92 条可执行规则。评分不是只看测试绿不绿，而是先用功能测试确认没有破坏行为，再用规则评估是否真的完成了非功能改进。结果显示，最强 agent 能达到 70.0% functional correctness，但所有 agent 在整体 NFI 能力上都落后人类参考，结构性代码改进差距尤其明显。这个 benchmark 的新意是把“测试通过但工程质量没有变好”显式记为失败，而不是让 agent 靠保守或表面改动拿分。对后训练软件工程来说，它很适合构造代码质量类训练信号：一条轨迹不应只因为没有破坏测试就被保留，还要看它是否减少技术债、改善结构，并且改动是否可被规则验证。
🔗 链接：https://arxiv.org/abs/2607.27409 ｜ 代码：None

### ReviewBench：从真实 PR review 评论构造 Harbor code-review agent 评测
代码审查 agent 很难评测，因为“好 review”通常依赖团队内部规范、历史设计约定和 reviewer 对代码库的隐性知识。LangChain 的 ReviewBench 从 LangSmith monorepo 的真实 PR review 历史出发，先收集可信 reviewer 的评论，再过滤掉 nit、问题式提问和不可验证意见，只保留能代表真实缺陷的 substantive findings。随后这些 findings 被转成 59 个 Harbor 格式任务，覆盖 64 个 baseline issues；agent 会拿到 frozen PR context，通过本地 GitHub stub 读取 PR metadata 和 diff，再在完整 seeded repository 中查证。评分用 coverage 和 precision：coverage 看是否找到了基线问题，precision 看提交的 finding 是否确实被代码支持，最后用 F1 平衡“漏报”和“噪声”。实验结论很现实：在基本 Deep Agents harness 下，当前模型通常只能找回约 30% 的 curated reviewer findings。更值得关注的是 prompt/harness ablation：同一个 Luna 模型在结构化 review prompt 下明显提升，说明 code-review agent 的策略设计会强烈影响结果。对后训练工程来说，ReviewBench 展示了一条高价值数据路线：把真实 review 评论清洗成可验证 eval，而不是让模型对 PR 泛泛输出建议。
🔗 链接：https://www.langchain.com/blog/evaluating-code-review-agents-with-reviewbench ｜ 代码：None

### The most useful data arrives after training：失败运行应先修 context/skill pipeline
很多团队一看到 agent 失败，就会立刻想到“是不是要微调模型”，但 Kyle Jeong 这篇文章强调，agent 最有用的数据往往发生在训练之后。因为 agent 工作时面对的是私有代码、刚发布的 SDK、用户反馈、运行时错误和组织内部规范，这些内容本来就不可能存在于预训练或旧 post-training 数据里。文章把 skills 定位在一个很实用的中间层：它们是可编辑、可版本化、可检索的程序性知识，能在下一次运行中立刻生效。失败闭环被拆成四步：观察失败里的错误假设、缺失来源或跳过验证；修复对应 procedure；只在相关任务中精准检索；最后重新跑 workflow 衡量效果。它并不是否认 fine-tuning，而是提醒大量失败样本应先进入 context pipeline、skills、retrieval、verification 和 memory，而不是直接变成梯度数据。这个观点对后训练数据工程很关键，因为“失败运行”不是同质化负样本：有些失败应该变成 skill 更新，有些应该变成测试，有些才值得做 SFT/RL。工程上可借鉴的是把 compiler errors、repo conventions、human corrections 和 skipped checks 先沉淀为可回放流程，再决定是否进入模型训练。
🔗 链接：https://kylejeong.com/blog/the-most-useful-data-arrives-after-training ｜ 代码：None

### Evaluating Skills：LangChain 用 Docker + LangSmith trace 评测 coding-agent skills
Agent skills 已经成为 Claude Code、Codex、Deep Agents CLI 等 coding agents 的常用扩展方式，但“写了 skill”不等于“agent 会正确触发并受益”。LangChain 这篇文章把 skill evaluation 做成一个小型工程流程：先定义真实任务，再分别在无 skill、有 skill、合并 skill、拆分 skill等条件下运行 Claude Code。为了保证结果可比，他们在轻量 Docker scaffold 里运行 agent，避免工作目录和环境状态影响结论。指标也不只看任务完成率，还包括 skill 是否被调用、是否在不相关任务中误调用、完成了几个步骤、用了多少 turns 和真实耗时。内部 LangChain/LangSmith 任务上，带 skills 的 Claude Code 完成率约 82%，无 skills 时约 9%，说明结构化领域知识对 coding agent 影响巨大。文章还指出一个常被忽略的问题：Claude Code 有时不会可靠触发正确 skill，因此 AGENTS.md / CLAUDE.md 里的触发指导、skill 名称和描述质量都要进入评测。对后训练软件工程来说，它提供了非常直接的落地模板：skill 本身应有 A/B eval、trace observability 和回归任务，而不是作为静态 markdown 被信任。
🔗 链接：https://www.langchain.com/blog/evaluating-skills ｜ 代码：https://github.com/langchain-ai/langsmith-skills

### TrustHarness：用合成 MCP 环境做工具型 agent 的确定性安全测试
工具型 agent 的安全失败常常不是一句越狱文本，而是在多步工具调用里泄漏 canary、相信伪造审批、跨租户访问或把 fake secret 传到外部 sink。TrustHarness 是一个很早期的开源项目，星数几乎没有，所以可信度标 Low；但它的测试形态很贴近本日报关注的工程问题。它会启动合成 MCP 环境，里面包含 poisoned data、fake secrets、privileged actions 和伪造的 trusted approval authorities，然后让真实 agent 在这个环境中完成任务。评估不是 LLM judge，而是具体安全 invariant，例如 MustCall、ForbidCall、NoCanaryLeak、RequiresApproval 和 ArgumentsEqual。预设场景覆盖 coding、support、finance、personal-assistant 等，每条轨迹都会记录 attempted tool call、参数、返回值和 security role。它解决的痛点是：很多安全 eval 只看最终文本拒答，但真实 agent 风险发生在工具参数、审批来源和数据流上。对后训练数据工程来说，这类合成 adversarial MCP environment 可以生产结构化安全负样本，帮助筛掉“任务做成了但越权/泄漏”的轨迹。
🔗 链接：https://github.com/ofirtro/trustharness ｜ 代码：https://github.com/ofirtro/trustharness

### Hierarchical Server Architecture：MCP hub/worker/fleet 协调云、边缘和 HPC agent 资源
这篇论文的主场景是 agentic science，不是 coding agent，所以按 Medium 收录；但它对 Agent-Friendly Infrastructure 很有参考价值。科学计算任务经常需要跨云、边缘、HPC 集群和机构资源调度，单个 agent 如果直接面对所有资源，很容易卡在发现、选择、认证和调度上。作者用 MCP server 构建分层结构：父级 worker 或 hub 负责分发请求，多个 worker 组成 fleet，真正计算放在 leaf workers 或调用端。Resource Secretary 软件提供 51 个真实和模拟 resource providers，让 agent 可以询问某个任务适合哪些资源、如何选择、如何 dispatch。论文报告了 19,973 次 negotiation 和 6,952 次 selection simulations，negotiation accuracy 达到 87.71%，说明协议化资源协商至少在模拟中可行。它的工程启发是，MCP 不只是“把一个工具接给模型”，也可以组织成多层资源网络，处理 discovery、routing、auth、events 和并发请求。对软件工程 agent 来说，未来大规模 CI、GPU、browser farm、sandbox 和数据库副本也需要类似 hub/worker/fleet 的 resource negotiation，而不只是本地 shell。
🔗 链接：https://arxiv.org/abs/2608.05332 ｜ 代码：None

### Knowing When to Stop：agent loop 收敛要靠外部 stop rule 与成本门禁
很多 agent demo 喜欢说“让它一直迭代直到做好”，但真实系统里，能继续循环不等于会朝正确方向收敛。a16z 的 Yoko Li 把 loop convergence 拆成四个必要条件：明确 target state、可观察 current state、精确的局部修改机制、以及来自 generator 外部的 stopping rule。以 coding agent 为例，target state 可能是测试、规格或性能阈值；current state 需要文件、diff、trace 和错误，而不是只看最终渲染效果；修改动作也应尽量局部，避免每轮重生成导致进度丢失。最重要的是 stop condition 不能只让模型自称完成，而要由测试、约束、评分阈值或 reviewer 批准触发。文章还强调经济性：500 轮后终于成功的 loop 在技术上可能收敛，但在产品上不可接受。它按 Medium 收录，因为是方法论博客，但和最近 LoopsBench、Prompt-Induced Waste、FailFast-RestartSmart 等主题高度一致。对后训练软件工程来说，采集轨迹时必须记录停止条件、预算、进度曲线和 verifier feedback，否则我们无法区分“有效迭代”和“昂贵空转”。
🔗 链接：https://a16z.com/knowing-when-to-stop-the-art-of-making-a-loop-converge/ ｜ 代码：None

### Canopii MCP Security Index：按 star 分层观察 MCP server 安全分数与退化
MCP server 生态增长很快，但安全状态不是一次性扫描就能说明，因为 server 版本、依赖、认证配置和工具 schema 都在持续变化。Canopii 的 August 2026 MCP Security Index 试图把这个问题做成持续性观察：按 GitHub stars 分层统计 server 平均分和 D/F 等级比例，并跟踪单个 server 随 release 或 rescan 的分数变化。一个反直觉信号是，1,000+ stars 的 server cohort 平均分更低，D/F 比例更高，说明热门项目不一定更安全，甚至因为功能复杂和部署广泛更容易暴露问题。页面还展示了若干从 A 降到 F 或从高分大幅下滑的条目，强调安全姿态会随版本快速退化。它不像 arXiv 论文那样给出完整方法细节，所以按 Medium 处理；但作为 ecosystem monitoring，很适合补充论文型安全评测。对 agent 工程来说，这类 index 可以成为 MCP allowlist、企业 agent tool registry 和 CI gate 的输入。对后训练数据工程来说，工具源的安全等级也应进入 trajectory provenance：同样一次工具调用，来自不同风险等级的 server，训练价值和可部署性完全不同。
🔗 链接：https://index.canopii.dev/mcp-security-index ｜ 代码：None

### Pi：四工具极简 terminal coding harness，高热度但把 sandbox 责任留给用户
Pi 是 2026 年社区里非常热的 terminal coding harness，GitHub 核验约 86k stars，最近仍有推送。它的设计反过来挑战了功能堆叠路线：核心只提供 read、write、edit、bash 四类工具，系统提示很短，其他能力通过 TypeScript extensions、skills 和包生态按需加入。这样的好处是开发者能读懂、fork、改造整个 harness，不会被一个黑箱客户端的 prompt、权限和工具策略锁住。它也支持多 provider 和本地模型，适合团队做低成本或可控的 harness 实验。风险同样明显：它默认不提供商业 coding agent 那种完整 sandbox、审批、子 agent 和企业策略，用户需要自己补权限和安全边界。Pi 的热度说明社区正在寻找“可拥有、可审计、可改造”的 agent runtime，而不只是更强的闭源模型。对后训练软件工程来说，极简 harness 是很好的实验载体，因为工具面小、日志结构清楚，便于分析模型行为；但进入生产前必须补上隔离、成本和审计。

## 🔥 社区热点专栏

### 🔥 大佬观点

**Yoko Li / a16z：agent loop 的关键不是“继续跑”，而是预先定义 done means 和 done costs。**  
她在 8 月 6 日文章中把 loop convergence 拆成 target state、observable current state、precise change mechanism 和 external stopping rule，强调停止条件必须由测试、约束、阈值或 reviewer 这类外部机制判定。这个观点值得注意，因为社区正在从“让 agent 多试几轮”转向“每轮是否真的缩小差距、是否值得继续花钱”的工程问题。🔗 https://a16z.com/knowing-when-to-stop-the-art-of-making-a-loop-converge/

**Boris Cherny / Anthropic：harness 和 eval 都有半衰期，新模型发布后要重新做 ablation。**  
访谈转述中，Boris 强调 Claude Code 团队会在新模型代际到来时删除大量旧 prompt / harness 假设，再逐行验证哪些仍有价值；eval 也可能只跨 1-3 代模型有效。这个 insight 对 coding-agent 团队很重要：长期资产不是某份固定系统提示词，而是持续发现模型在哪些场景失败、把这些失败转成新 eval 的能力。🔗 https://officechai.com/miscellaneous/the-ai-model-is-almost-like-a-living-creature-each-generation-behaves-differently-anthropics-boris-cherny/

### ⭐ 超火仓库/项目

**earendil-works/pi：约 86k stars，四工具极简 coding-agent harness，近期仍活跃。**  
Pi 火在把 terminal agent 做到可读、可 fork、可扩展，而不是把所有能力预装进黑箱 runtime；它解决的是高级工程师想掌控 harness、模型 provider、提示词和扩展机制的痛点。需要注意的是，极简也意味着 sandbox、审批和企业策略要自己补，适合实验和可控团队，不是开箱即用的安全生产方案。🔗 https://github.com/earendil-works/pi

**IBM/mcp-context-forge：约 4.3k stars，把 MCP/A2A/REST/gRPC 统一成企业 agent gateway。**  
它火在解决 MCP 工具爆炸后的治理问题：企业不可能让每个 agent 直接连一堆 server，而需要统一 discovery、RBAC、rate limiting、observability、federation 和 API-to-MCP translation。ContextForge 的价值不在单个工具，而在把 agent tool surface 变成可运营的基础设施层。🔗 https://github.com/IBM/mcp-context-forge ｜ https://ibm.github.io/mcp-context-forge/

**anthropics/skills / Skills ecosystem：Anthropic skills repo 约 167k stars，skills 正在成为 agent workflow 的“新 dotfiles”。**  
社区报告显示 skills 生态继续高热，核心原因是 SKILL.md 让团队能把流程、规范、脚本和领域知识做成可版本化资产，并通过 progressive disclosure 控制上下文成本。它解决的真实痛点是组织经验无法随人和工具迁移；但数量爆炸也带来质量、触发、权限和供应链问题，因此 skill eval 和 provenance 会越来越重要。🔗 https://github.com/anthropics/skills ｜ https://skillselion.com/state-of-ai-agent-skills-2026
