## 📝 逐条讲解

### DeNovoSWE：从文档生成完整仓库的长程 SWE 数据集
过去的 SWE 数据和 benchmark 主要围绕“已有仓库里修一个 issue”，这对训练局部 bug fix 很有效，但离“根据高层文档从零搭出一个可运行仓库”还有很大距离。DeNovoSWE 正是补这个缺口：它把任务定义成给 agent 一份文档，让它生成完整 repository，并用真实单元测试和 Docker 环境验证结果。数据构造不是人工一条条写，而是用沙箱化 agentic workflow 自动完成，核心是 divide-and-conquer：先把仓库行为拆成文档、测试、组件，再用 critic-repair 循环不断修正文档与验证器的不一致。它还引入 difficulty-aware trajectory filtering，不是只留“完全成功”的简单样本，而是在质量和多样性之间筛出适合训练的轨迹。规模上，它包含 4,818 个高质量 whole-repo generation 实例，比过去几十到百级任务的 doc-to-repo 基准大很多。实验里，Qwen3-30B-A3B 经 DeNovoSWE 后训练后，在 BeyondSWE-Doc2Repo 上从 5.8% 提到 47.2%，说明仓库级数据真的能把能力从补丁扩展到架构生成。对后训练数据工程来说，它的价值在于把“整库生成”变成可执行、可验证、可规模化的训练资产，而不是停留在 prompt demo。
🔗 链接：https://arxiv.org/abs/2606.10728 ｜ 代码：https://github.com/AweAI-Team/AweAgent

### MalSkillBench：运行时验证的恶意 Agent Skills 基准
Agent Skills 正在变成 coding agent 的插件生态：一个 skill 目录里既有自然语言说明，又可能有脚本、资源、权限假设和工具调用习惯。这带来一种新的供应链风险，因为它既不是纯代码漏洞，也不是纯 prompt injection，传统扫描器常常只看其中一半。MalSkillBench 的核心贡献是把“恶意 skill”做成运行时可验证的 benchmark，而不是只收集看起来可疑的文本样本。它包含 3,944 个恶意 skills 和 4,000 个匹配 benign skills，并用 attack vector、behavior、insertion strategy 三个维度组成 108 个标签格。更关键的是，3,214 个生成样本必须在 Docker 沙箱里真实触发恶意行为，系统用 syscall monitoring、文件事件和 LLM judge 共同确认后才收录。论文还显示现有检测器在 code injection 上可能表现不错，但遇到 prompt-injection 和 agent-control-plane 攻击会明显崩塌，wild-only 评测甚至会让工具排名大幅摇摆。对 skills 生态和后训练安全评测来说，这提醒我们：skill 安全必须同时理解任务意图、自然语言指令、脚本行为和权限边界，不能只把 skill 当 markdown 或 npm 包来扫。
🔗 链接：https://arxiv.org/abs/2606.07131 ｜ 代码：https://github.com/lxyeternal/MalSkillBench

### SkillResolve-Bench：解决同能力技能检索的危险代表选择
当技能库只有几十条时，检索到“相关 skill”可能已经够用；但当技能库扩到几千上万条时，真正危险的是检索器找到的是正确能力族，却选中了错误代表。例如两个技能都叫“部署服务”，一个面向当前云环境，另一个依赖过期密钥、旧端口或错误前置条件，普通相似度检索很难区分。SkillResolve-Bench 把这种失败命名为 same-capability execution-risk retrieval，并构造了 661 对 helpful/risky sibling，每一对共享能力族但执行后果不同。它还提供 7,982 个候选 skill pool，并要求同时报告 helpful ranking 和 harmful sibling rate（HSR@K），让“找到了有用技能”和“暴露了危险相邻技能”可以同时被看见。参考方法 SkillResolve 先解析 active candidate families，再用 confusable library negatives 和 contract-profile cues 给查询条件效用打分，最后每个族只选一个代表。结果上，SkillResolve 在 Recall@3 0.766、NDCG@3 0.699 的同时把 HSR@3 压到 0，而普通 SkillRouter 的 HSR@3 高达 0.693。对 skill management 工程来说，这非常实用：技能检索不只是 RAG 排名问题，而是运行时暴露过程资产的问题，必须把“同能力但错误代表”当成安全风险来度量。
🔗 链接：https://arxiv.org/abs/2606.10388 ｜ 代码：None

### SeClaw：用规格驱动合成 agent 安全评测任务
自主 agent 的安全问题不是单轮回答能否拒绝，而是它在一组文件、权限、MCP server、skills、依赖和用户交互中会不会一步步走向危险状态。SeClaw 的切入点是 spec-driven security task synthesis：先用规格描述风险场景，再重建一个接近用户侧真实执行条件的任务环境。它把 ToolHub、Skills、MCP tools、文件系统、依赖和权限组合起来，让 agent 面对的不只是抽象 API，而是有资源、冲突目标和外部能力的多轮环境。评分也不是只看最终文本，而是结合 trajectory-based scoring criteria，检查 agent 在过程里是否越权、误用工具、触发资源风险或违反任务约束。论文还把资源风险扩展到系统指令、MCP server、skills、memory、外部能力等 agent 常用扩展面，覆盖面比传统“恶意 prompt”更接近生产。虽然作者标注仍是 preliminary work，但方向很重要：未来 agent 安全 benchmark 需要能自动合成、可审计、可复现的复杂执行场景。对 harness 工程来说，SeClaw 提醒我们安全评测要把“工具和资源怎么被配置给 agent”纳入任务本体，而不是只测试模型是否说了安全话。
🔗 链接：https://arxiv.org/abs/2606.02302 ｜ 代码：None

### Claude Agent SDK：把 Claude Code agent loop 变成 Python/TypeScript 库
过去团队想把 Claude Code 这类终端 agent 接进 CI、内部工具或生产自动化，常常只能脚本化 CLI，或者自己重写一套 tool loop、权限和上下文管理。Claude Agent SDK 的意义在于把 Claude Code 的 agent loop、工具执行、上下文管理和配置体系以 Python/TypeScript 库形式暴露出来，让“构建 agent”不再等于自己维护完整 harness。SDK 内置 Read、Write、Edit、Bash、Monitor、Glob、Grep、WebSearch、WebFetch 等工具，并支持 hooks、subagents、MCP、sessions 和 filesystem-based Claude Code 配置。它还明确区分 Client SDK、Agent SDK、Claude Code CLI 与 Managed Agents：Client SDK 是你自己写 loop，Agent SDK 是在你进程里跑带工具的 Claude，Managed Agents 则把 sandbox/session 托管给 Anthropic。6 月 15 日起，订阅计划中的 Agent SDK 和 `claude -p` 会使用单独 Agent SDK credit，也说明 Anthropic 开始把“可编程 headless agent”当成独立产品面来管理。工程上最值得关注的是 hooks 与 subagents 的组合：团队可以把审计、权限、二次 review、日志和 MCP 接入做成程序结构，而不是依赖交互式 CLI 人工盯着。对后训练软件工程方向，这类 SDK 会改变真实轨迹采集、CI agent、评测 runner 和企业 agent 产品的实现方式。
🔗 链接：https://docs.anthropic.com/en/docs/claude-code/sdk ｜ 代码：https://www.npmjs.com/package/@anthropic-ai/claude-agent-sdk

### What makes a harness a harness：给 agent harness 下必要充分条件
“harness”这个词在 2026 年被用得非常频繁，但大家常常把三件事混在一起：模型运行壳、评测执行器、以及外部 benchmark 的评分脚手架。本文的价值不在发明一个新系统，而在给 agent harness 这个概念划边界。它区分了执行型 harness 和评测型 harness：SWE-agent 是让模型感知并改变软件环境的 agent-computer interface，而 SWE-bench 是从外部执行任务并收集分数的 eval harness，两者不应该混为一谈。文章提出 harness 至少要包含 loop、agent-environment interface、context management 和 behavioral constraints/control 等条件，否则它更像普通工具包装或框架说明。这个定义对工程团队很有用，因为很多 leaderboard 争论其实来自“到底在测模型、测 agent runtime，还是测 evaluator”的边界不清。它还帮助解释为什么同一个模型在 Claude Code、Codex、OpenClaw、Terminus 等壳里会有不同表现：harness 是一个控制系统，不是透明容器。对后训练和评测工程来说，先把概念切清楚，才能设计 locked-harness、factorial evaluation、harness card 和可迁移轨迹数据。
🔗 链接：https://arxiv.org/abs/2606.10106 ｜ 代码：None

### codex-harness-mcp：跨客户端的 agent memory、policy、trace gate
随着 Claude Code、Codex、OpenCode、Gemini CLI、Cursor、VS Code/Copilot 等工具并存，很多团队的 agent 经验被切碎在不同客户端里：一个地方有 memory，一个地方有验证证据，一个地方有安全策略。codex-harness-mcp 的定位是给这些客户端加一层共享 MCP 控制面，把松散 agent work 变成可审计 loop。它提供 durable memory、research/implementation lessons、trace capture、verification evidence、governance policy、PASS/FLAG/BLOCK audit、observability report 和 eval run 记录。它还支持 harness profiles 与 Meta-Harness-lite promotion，让团队可以把 harness 变更当成候选方案记录、评估、晋升，而不是在 markdown 里手改后忘记原因。多客户端安装器覆盖 Codex CLI、Claude Code、OpenCode、Kilo、Gemini、Cursor、VS Code、Cline、Windsurf 等，说明它解决的是跨 harness 一致性的真实痛点。它不替代任何一个 coding agent，而是让它们共享更安全、更可回放的操作循环。对 harness ops 来说，这类项目代表一个趋势：可靠性和安全不是某个 CLI 的内置小功能，而会逐渐变成横跨 agent 客户端的本地治理层。
🔗 链接：https://github.com/chapzin/codex-harness-mcp ｜ 代码：https://github.com/chapzin/codex-harness-mcp

### UltraContext：给 Claude Code / Codex / Cursor 共享实时上下文层
开发者现在常常同时使用 Claude Code、Codex、Cursor、OpenCode 等多个 coding agent，但这些 agent 彼此并不知道对方做过什么，用户就成了上下文搬运工。UltraContext 的 HN 介绍抓住了这个痛点：它用一个 daemon 实时捕获各 agent session，并通过 Context API 和 MCP server 把上下文分发给其它 agent。这样你可以问“昨天 Codex 改了哪个 API”“把 Claude Code 的计划拿来继续实现”“这个项目今天各 agent 做了什么”，而不是靠复制粘贴 transcript。它还把上下文做成类似 Git 的版本化对象，支持 create、append、update、delete、time-travel 和 fork，这比普通向量记忆更接近工程资产管理。项目的 insight 在于，多 agent 协作未必先需要复杂调度器，首先需要共享事实层：谁读过什么、改过什么、计划是什么、验证结果在哪里。风险也很明确：实时捕获 agent session 会涉及敏感代码、日志、凭据和内部计划，因此权限、过滤、加密和 retention 策略必须跟上。对 agent 系统工程来说，UltraContext 是“跨 agent 共享上下文层”这个方向的代表性新项目，和本期 codex-harness-mcp 共同指向 harness ops 的中间层化。
🔗 链接：https://news.ycombinator.com/item?id=47300321 ｜ 代码：https://github.com/acontext/ultracontext

### SENTINEL：失败驱动的工具使用 agent 强化学习
工具使用 agent 的训练如果只看最终成功/失败，很容易浪费失败轨迹里的信息：同样是失败，可能是选错工具、参数构造错、忘了查状态、违反 domain policy，训练上应该对应不同修复方向。SENTINEL 的主题是 failure-driven reinforcement learning，把失败模式变成后续训练的引导信号，而不是把失败样本简单丢掉。它讨论的场景包括 APIBank、ToolBench、BFCL、tau-bench 以及 MCP-Atlas、MCP-Bench、MCPMark 等多轮工具和 MCP 评测，说明目标不是单轮 function calling，而是复杂真实工具环境。核心思路是从失败轨迹中挖出模式，再把这些模式反馈到训练任务选择、轨迹生成和策略更新中，让模型专门补历史短板。它和 Socratic-SWE、Role-Agent、CoEvolve 属于同一类方向：数据分布不应静态，而应跟着 agent 暴露出来的 failure modes 动态变化。对工程团队来说，重点不是某个 RL 算法细节，而是要把失败分类、任务检索、轨迹归档和训练采样接成闭环。这样的系统如果接入 Claw-R1 这类 step-level 数据中间件，会更容易变成可落地的数据飞轮。
🔗 链接：https://arxiv.org/abs/2606.12908 ｜ 代码：None

### Role-Agent：World-In-Agent / Agent-In-World 双角色演化
很多 agentic RL 环境是静态的：任务池固定，失败后只是在同一分布上多采样，导致训练越来越像刷一套题。Role-Agent 的思路是让同一个 LLM 同时扮演 agent 和 environment 的一部分，形成 dual-role evolution。World-In-Agent（WIA）让 agent 在行动前预测未来状态，增强规划和对环境反馈的预期；Agent-In-World（AIW）则反过来分析失败轨迹，抽取 failure modes 和 root causes，再检索相似任务来调整数据分布。这样环境不只是给 reward，而是主动把训练推向 agent 历史上容易忽略、容易失败的区域。它的价值在于把“失败反思”从自然语言总结变成 curriculum steering 信号，接近一个 agent-environment co-evolution 系统。和更工程化的 Socratic-SWE 相比，Role-Agent 的抽象更通用，不限于代码仓库，但也因此需要更强的任务检索和验证机制才能稳定落地。对后训练流程设计来说，它说明未来 agentic RL 的核心接口不只是 rollout API，还包括 failure taxonomy、task retrieval 和 distribution reshaping。
🔗 链接：https://arxiv.org/abs/2606.10917 ｜ 代码：None

### HomeFlow：可验证仿真里的智能家居 agent 数据飞轮
HomeFlow 的场景是智能家居，不是 coding agent，但它的工程模式很值得借鉴：用可验证仿真构建多轮 agent 训练数据飞轮。智能家居任务看似简单，其实包含状态、设备依赖、用户偏好、时序和安全约束，如果只靠对话 SFT，很难让 agent 学会什么时候该查状态、什么时候该执行动作。HomeFlow 用 blueprint-grounded synthesis 生成任务与环境，用 MCTS 扩展交互轨迹，再用 step-wise rewards 给每一步工具行为提供密集反馈。论文对比了只在最终动作给奖励的变体，发现最终奖励虽然能提升成功率，但容易让策略熵快速塌缩，而逐步奖励能保持探索并减少无谓工具调用。结果上，它把 Qwen 4B/8B 模型提升到约 84.2%/87.0% task success，说明小模型也能通过有验证器的环境训练获得稳定多轮控制能力。对后训练软件工程来说，HomeFlow 的启发是通用的：只要能把真实系统抽象成可执行模拟器和逐步 verifier，就能把用户工作流变成可训练、可诊断、可回归的数据飞轮。这个模式可迁移到 DevOps、桌面自动化、SaaS workflow 和 coding-agent 工具环境。
🔗 链接：https://arxiv.org/abs/2606.01230 ｜ 代码：None

### Vesta / Dawn：统计建模 agent 的动态工具生成与评测
科学和数据分析 agent 经常卡在一个地方：它会写解释，也会调包，但面对真实数据分布时，不知道该生成哪些诊断图、变换数据、检验假设。Vesta 把这个问题当作 tool-creation 与 exploration 问题，而不是只让模型反复 critique 自己的答案。系统允许 VLM 动态生成统计工具，用于数据变换、假设驱动可视化和 robust statistical tests；这些工具会积累在上下文里，供后续 refinement 复用。为了评测这类能力，作者提出 Dawn benchmark，覆盖分布拟合、时间序列建模和真实天文学任务，例如初始质量函数和引力波 chirp 信号。实验显示，动态模型生成工具在复杂、领域特定任务上比无工具或静态专家工具更强，而且生成的工具覆盖更多诊断类别。它不是 coding agent 专项，但与“agent 自动生成并管理工具/skills”高度相关。对后训练工程的启发是：开放式研究 agent 的能力提升，往往来自把探索工具显式化、可复用化，而不是只要求模型在文本里多想几轮。
🔗 链接：https://arxiv.org/abs/2606.00384 ｜ 代码：None

### From Prompt to Process：AI 软件开发 agent 框架的过程分类
很多 AI 软件开发框架并不直接跑 benchmark，它们更像过程支架：写规格、拆任务、生成工作包、安排 human review、把实现放进 worktree，再交给 agent 执行。From Prompt to Process 的价值在于提醒评测者：如果只看最终代码是否通过测试，会漏掉这些中间 artifact 对质量和可维护性的影响。论文提出一套 process taxonomy，用来比较 BMAD、Reversa、Spec Kit、Spec-Flow 等支持 AI software development agents 的框架，并观察它们如何处理 operational specification、execution、work contracts、persistent artifacts 和 review surfaces。它强调现代 agentic 工具的核心不再是“建议代码”，而是能真正触发工具、编辑代码、运行测试、接触接口，这让执行边界和过程文档都成为系统行为的一部分。对工程团队来说，这类分类可以帮助判断一个框架到底只是 prompt 模板，还是能为长期协作留下可审查、可恢复、可复用的过程资产。它也提示未来评测应覆盖 spec、plan、任务分解、review note、worktree isolation 等中间产物，而不是只给最终 diff 打分。本文按 Medium 收录，因为它偏方法论，但对“agent 工程流程如何标准化”有实际参考价值。
🔗 链接：https://arxiv.org/abs/2606.04967 ｜ 代码：None

## 🔥 社区热点专栏

### 🔥 大佬观点

**Addy Osmani：Loop Engineering 是 harness 之上的一层，目标是让系统定期驱动 agents。**  
Addy 在《Loop Engineering》中把近期社区讨论从“怎么 prompt agent”推进到“怎么设计会 prompt agent 的系统”：loop 会发现工作、分派给子 agent、检查结果、记录状态并决定下一步。值得注意的是，他把 Claude Code 和 Codex 的 subagents、skills、worktrees、MCP、automations 看成同一类 building blocks，说明工具差异正在收敛，真正要设计的是可验证、可复用的控制循环。🔗 https://addyo.substack.com/p/loop-engineering

**Cobus Greyling：终端 harness loop 与生产 runtime loop 是两级不同系统。**  
Cobus 的 playbook 把 solo/small-team 的 Claude Code/Grok/Codex 本地 loop 与生产级平台 runtime 区分开：后者需要 durable execution、checkpoint、cron、human interrupt、审计和隔离机器。这个区分很实用，因为很多团队把 `/loop` 跑在 TUI 里就以为是生产 agent；真正服务产品或团队时，崩溃恢复、权限和追踪才是边界。🔗 https://cobusgreyling.substack.com/p/loop-engineering-playbook

**HN harness engineering 讨论：把 issue、观测、skills 和 observability 都放进 repo，agent 才能闭环。**  
Hacker News 上围绕“Leveraging Codex in an agent-first world”的讨论强调，给 Claude/Codex 可运行的验证、Grafana/Prometheus/PagerDuty 观测入口、repo 内 worklog/plan/spec，以及完整 code lifecycle skill，比继续手动提示更重要。它值得注意，因为社区经验正在从“选哪个 agent”转向“如何把环境做成 agent 能自我验证和自我改进的系统”。🔗 https://news.ycombinator.com/item?id=48416264

### ⭐ 超火仓库/项目

**UltraContext（acontext/ultracontext）：多 coding agent 的共享上下文层。**  
UltraContext 在 HN 上的火点是“每个 coding agent 都是孤岛”这个真实痛点：它实时捕获 Claude Code、Codex、Cursor 等 session，再通过 MCP 分发给其它 agent。它解决的是跨 agent 协作中最基础的上下文同步问题，尤其适合多工具并行开发和长周期项目交接。🔗 https://news.ycombinator.com/item?id=47300321 ｜ https://github.com/acontext/ultracontext

**codex-harness-mcp（chapzin/codex-harness-mcp）：把 memory、governance、trace 和 eval 做成 MCP 控制层。**  
这个项目热度不靠 star 数，而靠方向准确：它把不同 coding agent 客户端接到同一个可审计本地 loop，记录验证证据、治理结果、observability report 和 harness promotion 决策。它解决的痛点是团队已经有很多 agent，但缺少跨工具一致的记忆、策略和“完成前 gate”。🔗 https://github.com/chapzin/codex-harness-mcp

**agent-harness-generator / create-agent-harness：把 agent harness 项目模板化。**  
社区 gist 展示的 generator 把一个 harness 直接打包成 CLI、MCP server、memory subsystem、learning loop、SBOM、default-deny MCP policy 和 release manifests。它之所以值得关注，是因为 agent harness 正从“每个团队手写 bash + markdown”走向可生成、可发布、可审计的软件包；默认拒绝网络/文件写入等设计也说明安全边界正在前移到模板层。🔗 https://gist.github.com/ruvnet/1b46293206a9dd9a729b18c48c305222
