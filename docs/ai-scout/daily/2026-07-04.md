## 📝 逐条讲解

### Dockerless：不用 per-repo Docker 也能做 coding-agent patch verifier
在 coding agent 后训练里，验证器通常是最贵、最脆弱的一环：你要给每个仓库构建 Docker 镜像、装依赖、定位测试命令，再把结果解析成可训练的 reward 或过滤信号。Dockerless 的切入点是把“运行测试”换成“带证据的仓库探索判断”：它不执行候选补丁，而是根据 issue、参考 patch 和候选 patch 生成若干验证问题，再派出并行 sub-agents 只读探索仓库，收集证据后给出 patch 是否正确的分数。这样做不是简单让 LLM 看 diff 打分，因为关键证据来自仓库调用链、被修改函数用途、可能破坏的周边代码和参考修复的意图。论文报告 Dockerless 在 verifier benchmark 上比最强开源 verifier 高 14.3 AUC points，并可同时作为 SFT 轨迹筛选器和 RL reward。端到端上，用它构建的完全 environment-free post-training pipeline 在 SWE-bench Verified、Multilingual、Pro 上达到 62.0%、50.0%、35.2%，接近或匹配依赖执行环境的训练路线。对后训练软件工程来说，这很重要，因为真实企业/遗留仓库常常没有可复现测试环境，或者构建成本高到无法大规模 rollout。它给出的启发是：验证信号可以从“测试是否跑通”扩展为“围绕补丁正确性的问题生成、证据探索、最终判定”的可训练 pipeline，但落地时仍要谨慎处理 reference patch 泄漏和 LLM judge 偏差。
🔗 链接：https://arxiv.org/html/2606.28436 ｜ 代码：None

### SWE-Together：从真实多轮用户会话重建 coding-agent interactive benchmark
传统 SWE-bench 风格任务通常把完整需求一次性给 agent，最后只看补丁是否通过测试；但真实使用 coding agent 时，用户经常先说一个含糊目标，再不断补充约束、指出方向错了、要求改交互或复查结果。SWE-Together 试图把这种真实协作形态做成 benchmark，而不是继续假设用户从第一轮就写好完整 spec。它从 11,260 条真实 coding-agent 会话中严格筛选出 109 个可复现 repository-level 任务，要求有可恢复仓库状态、清晰用户意图和可观察最终结果。评测时不是把原始聊天逐字重放，而是用 anchored、state-conditional 的 LLM user simulator：只有当被测 agent 走到特定状态或暴露特定问题时，模拟用户才按原始意图给出澄清或纠偏。除了最终 repository correctness，它还记录 User Correction 和 Intent Coverage，用来衡量 agent 需要用户推多少次、用户意图是否被稳定传达。这个设计对 eval 工程很有价值，因为它把“最终做对”和“少让用户操心”分开了。对后训练数据工程来说，这类数据特别适合训练需求澄清、反馈吸收和多轮任务状态管理，而不是只训练静态 issue 到 patch。
🔗 链接：https://arxiv.org/html/2606.29957 ｜ 代码：https://github.com/Togetherbench/SWE-Together

### Steer, Don't Solve：训练小 critic 在运行中纠偏大 code agent
很多 code agent 的失败不是因为不会写某一行代码，而是早早押错假设、重复无效搜索、快到步数上限还不提交，或者把调试目标带偏。Steer, Don't Solve 的核心思路是不要把所有能力都塞回主 agent 里训练，而是冻结主 agent，另训练一个较小 critic 在运行过程中每隔若干步查看部分轨迹并给出高层反馈。这个 critic 不直接下具体命令，也不替 agent 写代码，而是指出“你现在可能在循环”“证据不支持这个假设”“如果已经验证过修复，应考虑提交”等策略层信号。训练上，作者用 frontier teacher 生成 trajectory-prefix -> feedback 数据，再用 SFT 训练小 critic，并强调只学习 concise、高层的反馈，避免 critic 变成不可靠的 backseat driver。实验显示，在 SWE-bench Verified 上，一个训练在 CWM-32B 轨迹上的 critic 能迁移到两个未见 agent，带来 +3.0 到 +3.8 个百分点；加入目标 agent 轨迹后，对 Qwen agent 的提升达到 +4.4 到 +5.2 个百分点。更有意思的是 Qwen3-Next-80B-A3B 场景下，critic-guided 版本从 20.8% 提到 25.2%，同时单题成本从 0.11 美元降到 0.04 美元，因为轨迹变短抵消了 critic 调用成本。工程启发是，trajectory feedback 可以被拆成独立、便宜、可替换的监督组件，适合接入生产 harness 或后训练数据筛选。
🔗 链接：https://arxiv.org/html/2606.21811v1 ｜ 代码：https://github.com/shubhamrgandhi/critic-training

### MCP Server Architecture Patterns：给 MCP server 设计提炼 5 类模式与 4 类反模式
MCP 生态快速增长后，很多团队的问题已经不是“怎么把 API 接给模型”，而是 server 到底该怎么拆工具、怎么管理状态、怎么聚合多个上游、怎么避免工具太多让模型选错。MCP Server Architecture Patterns 把这个经验问题系统化：作者从 5 个生产 MCP server 和 10 个官方 registry 公开 server 出发，总结出 Resource Gateway、Tool Orchestrator、Stateful Session Server、Proxy Aggregator、Domain-Specific Adapter 五类模式。每个模式都按软件工程设计模式的形式描述 context、problem、solution 和 consequences，并额外总结认证、版本、可观测性等横切问题。论文还给出一些量化信号：分类 taxonomy 的 Cohen's kappa 为 0.76，stdio 本地传输 p50 约 0.01ms，streamable-http 本地 p50 约 0.39ms。最贴近 agent 工程的是 tool-count study：Claude Haiku 4.5 在每个 context 10-15 个工具后准确率跌破 90%，Sonnet 4 大约在 20-30 个工具后出现类似边界。这个结果说明 MCP server 设计不是普通 API 设计，LLM 通过自然语言描述选工具，过宽、过碎、命名含糊都会变成模型错误。对 Agent-Friendly Software 来说，这篇像是 MCP server 的早期“架构模式语言”，有助于把 server 审查从主观 prompt 调优推进到可复用设计准则。
🔗 链接：https://arxiv.org/html/2606.30317v1 ｜ 代码：https://github.com/rodriguescarson/mcp-patterns-icsme2026

### HCP：把 MCP-style 工具连接推进到可测试的 execution-control runtime
MCP 标准化了 agent 如何连接工具，但连接之后的执行控制仍常常散落在 client、server、prompt、OAuth、弹窗审批和日志里。HCP 这篇工作明确把问题从“工具能不能连上”推进到“工具调用的权限、数据流和审计是否由 runtime 统一检查”。它定义了 8 个安全 invariant，包括 metadata non-authority、grant-backed approval、canonical resources、principal binding、scoped capability invocation、source-and-target data-flow authorization、deny-path audit 和 explicit protocol state。实现上，HCP 用 Principal、Resource、Grant、Capability、Handle、Policy Decision、DataPipe、Audit Entry 等对象把权限和数据流变成 runtime 里的显式实体，而不是让自然语言工具描述或一次性用户批准承担安全语义。论文用 10 个 benchmark cases 对比 naive MCP-like runtime、practice-informed mitigation baseline 和 HCP；结果 naive baseline 放过全部攻击，mitigation baseline 仍放过 6/10，HCP 阻断全部 10 个并保留审计证据。它不是在宣称替代 MCP 或 OAuth，而是给出了一个可测试的 execution-control layer 研究原型。对我们关注的 agent runtime 工程很有启发：未来工具安全不能只靠 tool schema lint、per-call prompt 或用户肉眼审批，而要把 principal、resource、grant、handle owner、data pipe 和 deny audit 都记录成结构化对象。它也适合作为内部安全评测模板，用来构造 confused deputy、tool poisoning、数据外发和协议状态错乱的回归用例。
🔗 链接：https://arxiv.org/html/2606.29073 ｜ 代码：https://github.com/SymbolicLight-AGI/handle-capability-protocol

### SWE-MiniSandbox：用 namespace/chroot 替代重容器扩展 SWE agent RL
大规模 SWE agent RL 需要成批运行仓库任务、隔离文件系统、安装依赖、执行测试和回收环境；Docker 镜像虽然通用，但在高 rollout 量下会带来巨大存储、构建、解压和调度成本。SWE-MiniSandbox 选择更轻量的路径：用 Linux mount namespace、chroot、bind mount 和 venv/Conda 环境来隔离每个任务，而不是给每个实例维护完整容器镜像。它还设计了 environment pre-caching pipeline，把任务依赖和仓库打成可复用压缩缓存，并用 Ray 资源控制与信号量缓解并发解压的 I/O 瓶颈。论文称该方式只需要约 5% 的 Docker-based 存储，并把环境准备时间降到容器 baseline 的约 25%，同时保持和传统容器流程相当的训练/eval 效果。更重要的是，它不是孤立工具，而是直接对接 SWE-Rex、SWE-agent 和 SkyRL，试图成为 SWE agent RL 后端的 drop-in 替代方案。工程上要注意它并不否认容器价值：需要复杂系统依赖或强隔离的任务仍可用容器，而大量 Python/常规项目可以落到轻量 namespace sandbox。对后训练平台而言，这类 infra 会显著改变“能采多少轨迹、能跑多少 verifier、能不能让小团队复现”的成本结构。
🔗 链接：https://arxiv.org/html/2602.11210v5 ｜ 代码：https://github.com/lblankl/SWE-MiniSandbox

### Aharness：把 Codex 工作流变成 TypeScript FSM，而不是提示词约定
许多 coding-agent 工作流依赖一段提示词或 skill 说“先计划、再实现、再测试、再总结”，但模型一旦跑久了就可能跳步骤、忘检查、提前收尾或把证据写得不完整。Aharness 的观点是：流程不应只被描述，应该被执行。它让开发者用 TypeScript 写 finite state machine，每个 state 定义 Codex 当前能做什么、允许哪些 typed submissions、哪些 owner choice 或 approval gate 能触发转移，以及最终要产出什么 artifact。运行时 Aharness 只暴露当前 state 的合法出口，模型不能凭自然语言跳到没有声明的下一步；提交 payload 会按 sidecar schema 验证，转移和事件写入 JSONL evidence log。它还把 Codex app-server、skills/list preflight、hook dispatch、browser UI、recorded-run viewer 和 run artifact 组合成一个可检查 runtime。虽然仓库 star 很低，成熟度还早，所以可信度不能夸大；但 HN Show HN 讨论里的核心痛点很真实：长程 agent 的失败正在从“不会写代码”转向“流程漂移和上下文管理”。对 harness engineering 来说，FSM 化工作流提供了介于 prompt/skill 和完整自研 agent 平台之间的中间层，适合把 review gate、测试证据、人工选择和修复路径做成可版本化软件。
🔗 链接：https://github.com/Alfredvc/aharness ｜ 代码：https://github.com/Alfredvc/aharness

### self-learning-skills：让 agent 把 hard-won golden path 自动收割成可复用技能
团队使用 coding agent 的一个常见浪费是：某次会话终于摸清了一个项目的正确流程、命令或坑点，但下一次 agent 又从零开始试错。self-learning-skills 的目标是把这种“辛苦学到的 golden path”在会话结束前收割成可复用资产。它提供一个 meta-skill，教 agent 识别自己刚刚发现了可复用路线，然后把它保存成不同 agent 能自动加载的形式：Claude Code/Codex/Agent Skills 客户端用 `skills/*/SKILL.md`，Cursor 用 `.cursor/rules/learned/*.mdc`，其它工具可落到 `AGENTS.md` 或项目 notes。仓库 6 月 28 日创建，当前约 801 stars，并在 Trendshift 上显示有近期社交讨论，说明“技能自动演化”已经从论文概念变成社区实用需求。这个项目解决的不是通用记忆，而是更窄、更工程化的问题：什么时候值得把一次成功轨迹固化为规则，固化到哪里，下次如何被自动检索。风险也明显，错误的 golden path 会变成持久误导，所以需要人工 review、适用条件、反例和过期机制。对后训练数据工程来说，这类 skill harvesting 可以看成轨迹蒸馏的轻量产品形态：成功经验不是只进模型权重，也可以先进入可审查、可版本化的技能库。
🔗 链接：https://github.com/Kulaxyz/self-learning-skills ｜ 代码：https://github.com/Kulaxyz/self-learning-skills

### RolloutPipe：在 disaggregated GRPO/RLVR 中重叠 rollout 与训练
LLM RLVR 后训练通常把 rollout 生成和梯度训练拆到不同 GPU 池，这样资源配置灵活，但同步 GRPO 流程常常要等整轮 rollout 完成后才能开始训练，训练池会长时间空转。RolloutPipe 的核心改动是把“整轮完成”这个边界改成“complete group 完成”这个边界：只要某个 prompt group 的所有 responses、reward 和 advantage 都 materialize，就可以先进入 trainer FIFO，而剩余 groups 继续生成。它用 complete-group pipelining 保证已经可训练的 group 立即流向训练端，同时用 frontier-group dispatch 在 rollout node 侧优先调度将形成下一批训练 batch 的 group，减少 trainer 等待。这个设计避免了异步 RL 常见的 stale data 问题，因为同一轮 rollout 权重保持固定，仍维护 on-policy correctness。实验在 Qwen3-1.7B、4 个 reasoning/science workload、12 种设置上显示，相比 Slime，rollout-to-train-end 时间缩短 30.7%-42.3%，trainer waiting ratio 降低 37%-76%。它与 coding agent 不是直接绑定，但对大规模 agentic RL 的基础设施很相关：长程 rollout、验证器和训练池之间的流水线效率会直接决定可承受的数据规模。工程启发是，后训练优化不只在算法目标函数，也在 group 边界、队列策略、资源池拆分和数据 freshness 这些系统细节。
🔗 链接：https://arxiv.org/html/2606.26997 ｜ 代码：None

### SENTINEL：用失败轨迹生成下一轮 tool-use RL 训练任务
很多 tool-use agent 的 RL 训练会提前生成一批固定任务，但模型能力变化后，这批任务可能变得太容易、太难或无法覆盖当前模型真正的弱点。SENTINEL 把失败轨迹当成下一轮训练任务的来源，而不是只把失败当评测结果。它的 Controller 会分析当前 Solver rollout 中的失败，归纳出反复出现的错误模式，比如工具顺序错、漏掉政策约束、选错记录或缺少某一步；Proposer 再根据这些失败模式生成新的可执行任务，Solver 在这些有针对性的任务上继续 RL。这样训练分布会随着 policy 的弱点动态移动，避免 rollout 被浪费在已经会做或完全学不到的任务上。论文在 Tau2-Bench Retail 上用 Qwen3-4B-Thinking-2507 实验，Pass@1 从 66.4 提到 74.9，并优于在通用合成任务上做 RL。它的价值在于把“失败诊断 -> 任务生成 -> RL 优化”连成闭环，而且强调生成任务必须可执行、可验证。对后训练软件工程来说，这与 coding-agent failure taxonomy、trajectory selection 和 benchmark task synthesis 可以直接相互借鉴：最好的新任务往往来自当前系统刚刚暴露的真实失败。
🔗 链接：https://arxiv.org/html/2606.12908v1 ｜ 代码：None

### Self-Evolution ToolGraph+DPO：从工具轨迹分歧点构造偏好数据
多轮工具调用 agent 面对的难点不是单次 API 调用，而是在大工具面里选择正确顺序、追踪对话状态、满足业务政策，并决定什么时候停止查询、开始执行。Self-Evolution via Divergence-Point Preference Learning 用 tau2-bench 做实验，把工具 schema 和成功轨迹变成 ToolGraph：节点是工具，边来自共享参数和成功轨迹中的转移概率，再加上写操作前置条件、重复搜索 loop check 和 Critical Rules。这个图先在推理时帮助 agent 做结构化工具选择，然后作者进一步用成功/失败轨迹的“分歧点”构造 DPO 偏好对。分歧点指同一任务里成功轨迹和失败轨迹第一次采取不同动作的位置，成功动作是 chosen，失败动作是 rejected，并通过 action-correctness annotation 过滤，减少把偶然差异当偏好的风险。实验在 375 个 tau2-bench 任务上，ToolGraph 先把 weighted average reward 从 0.304 提到 0.338，ToolGraph+DPO 进一步到 0.355。更有工程价值的是作者指出训练和部署 context 必须一致：早期 bare prompt 下训练、ToolGraph prompt 下部署会造成偏好错配。对 trajectory selection 来说，这提供了非常实用的范式：不要粗暴比较整条轨迹，而要定位状态一致但动作分叉的点，并确保偏好数据与实际 runtime 上下文一致。
🔗 链接：https://arxiv.org/html/2606.23112v1 ｜ 代码：None

### Agent Skill Evaluation and Evolution：梳理技能演化、评测与安全缺口
Agent skills 正在从“提示词片段”变成可安装、可检索、可组合的工程资产，但技能库扩大后，怎么评估技能是否有用、是否过期、是否安全，反而成了新瓶颈。Agent Skill Evaluation and Evolution 是一篇 survey，把重点放在技能创建之后的演化与评测，而不是只讨论怎么写一个 skill。它把 skill evolution 分成四类：execution feedback、trajectory distillation、compression & augmentation、reinforcement learning；对应的信号来源可以是运行错误、用户偏好、多条成功/失败轨迹、库级重复与冲突、或任务级 reward。文中还强调技能使用本身需要 retrieval、routing、management，因为不可能把所有技能一次性塞进上下文。比较有用的工程判断是：直接从 raw trace 改技能容易把噪声固化，效果更好的系统通常先做 failure diagnosis，再生成 rewrite 或合并方案。survey 还指出现有 skill benchmark 往往只给 pass/fail，缺少 token cost、latency、错误类型、长期演化、安全性和技能冲突指标。对我们关注的 skill evolving/management 来说，这篇适合作为路线图：技能系统必须像软件包一样有生命周期、scorecard、依赖、去重、回归测试和安全门。
🔗 链接：https://arxiv.org/html/2606.11435v1 ｜ 代码：https://github.com/Cassie07/AgentSkill_Survey
