## 📝 逐条讲解

### Anthropic Claude Fable 5 / Mythos 5：Mythos 级长程 coding agent 基座
Anthropic 6 月 9 日发布 Claude Fable 5 和受限访问的 Claude Mythos 5，这是本期最明确的官方高价值更新。Fable 5 是同一 Mythos 级底座的公众版本，带有 cyber、biology/chemistry、distillation 等安全分类器；触发分类器时会回退到 Opus 4.8，而 Mythos 5 则通过 Project Glasswing 等 trusted access 场景放开部分防护。它最值得关注的不是短问答，而是长程 agentic coding：Anthropic 称其在 Cognition FrontierCode、CursorBench 等生产代码质量评测中领先，早测客户还提到 50M 行 Ruby 代码库迁移这类长周期任务。对后训练软件工程来说，这类模型会把压力转移到 harness：如果模型能稳定跑更久、改更多文件，评测、防作弊、工具权限、审计、回滚和成本路由就会变成部署瓶颈。Fable/Mythos 的“双版本 + 安全回退 + trusted access”设计也给高能力 agent 发布提供了一个工程样板：能力不是简单开关，而是按风险域、用户资质和日志保留策略分层开放。

### Adaptive Auto-Harness：面向开放任务流的持续自演化 harness
过去几天已收录不少 auto-harness 工作，但大多在固定离线 benchmark 上优化一次，然后看分数是否提升；真实部署更麻烦，任务会连续到来，分布会漂移，历史会越积越长。Adaptive Auto-Harness 针对的正是这种“开放任务流”：如果把所有经验都不断塞进一个越来越胖的 harness，短期可能涨分，长期会过拟合早期任务，甚至把 sports 预测里有用的技能错误迁移到 politics 预测里。它把问题拆成 evolution loss 和 adaptation loss：前者是 evolver 本身造不出好 harness，后者是同一个 harness 不适合所有任务。系统层面用四阶段多 agent evolver（Analyze/Research/Build/Verify）持续构建 harness tree，再在解题时由 router 选择最匹配的 branch，并用 temporal-reveal feedback 避免未来信息泄漏。在 PolyBench、CTF-Dojo、FutureX 三个时间序列任务上，它相对 A-Evolve、GEPA、Meta-Harness 等基线取得更稳的持续收益。对本日报关注的 harness engineering，这是从“一次性调参”走向“长期可维护系统”的重要一步。
🔗 链接：https://arxiv.org/abs/2606.01770 ｜ 代码：None

### ADK Arena：用 LLM-as-a-Developer 评测 51 个 agent 框架
agent framework / ADK 生态已经很拥挤，但开发者很难知道哪个框架 API 好学、跑得稳、能在真实任务里产出好 agent。ADK Arena 的方法很巧：不让论文作者手写每个框架的 benchmark 代码，而是让同一个 LLM coding agent 像新开发者一样读文档、看源码、写 `agent.py`，再通过静态检查、真实 LLM smoke test、真实 benchmark early-exit 三层验证不断修复。这样“生成一个可跑 agent 花了多少 token、失败了多少次、最后跑得怎样”就成了框架可用性和执行能力的量化指标。它覆盖 51 个 Python ADK、204 个 framework-benchmark pairs，包含 SWE-bench、tau2-bench、MCP-Atlas、Terminal-Bench，发现只有 57% 生成运行通过，单 agent 生成成本相差 5.6 倍。更有意思的是，某些框架在单个 benchmark 上能以很低成本超过通用 frontier coding agent，但中位框架只有约 32% resolve。对 agent 系统工程团队来说，这提供了一种可复用评测模式：框架不是看 README 漂亮，而是看一个新 agent 能否在有限预算里学会并产出可运行系统。
🔗 链接：https://arxiv.org/abs/2606.05548 ｜ 代码：https://github.com/jintao-h/ADK-Arena

### MCP-Persona：真实个性化 MCP 工具评测
MCP 正在成为 agent 接工具的标准接口，但多数评测只考通用搜索或无状态 API，离个人账号、企业协作、社交媒体这些真实应用还有距离。MCP-Persona 把问题放到个性化工具环境里：Slack/Lark/Rednote/Instagram/Notion 等工具的状态、用户资料、历史上下文会影响正确调用，而这些内容又不能直接公开真实账号数据。它的工程方案是先部署真实 MCP server 并遍历有效/失败 function calls，再用 LLM 总结成可执行 Python simulator；用户上下文用 Context-Tree 组织成可变状态树，任务则通过 Persona-Gen 注入上下文并故意保留真实用户指令里的含糊性。最终 benchmark 有 173 条人工核验任务、12 个 personalized MCP servers 和跨 server 场景。结果显示 GPT-5、Claude Sonnet 等强模型整体准确率仍低于 50%，常见失败不是不会调用工具，而是没有主动探索环境里隐含的信息。对 Agent-Friendly Tooling 的启发很直接：MCP 评测不能只测 schema 调用，还要测“带个人状态的、可变的、权限敏感的真实应用”。
🔗 链接：https://arxiv.org/abs/2606.02470 ｜ 代码：https://github.com/wwh0411/MCP-Persona

### Agent libOS：把长程 agent 当可调度、可授权、可审计进程
现在很多 agent framework 仍是“聊天循环 + 工具注册表”：模型看见一个工具 schema，就通过 wrapper 触达文件系统、shell、网络或凭据。Agent libOS 认为这层抽象太薄，尤其当 agent 要长期运行、fork 子任务、等待人类批准、动态生成工具、恢复 checkpoint 时，工具可见性不应等同于资源权限。它借鉴 library OS 和 capability system，把 agent 建模成 AgentProcess：有身份、父子 lineage、生命周期、Object Memory、capabilities、human queue、checkpoint 和 audit records。核心规则是“tools are libc-like wrappers; runtime primitives are authority boundary”，也就是工具只是模型可见的调用面，真正能否读文件、写对象、跑 shell、注册新工具，要在 runtime primitive 层按 capability 检查。原型实现了 async scheduling、namespace-local Object Memory、Deno/TypeScript JIT 工具通过 syscall broker 调 runtime、human approval、per-process cwd 等，并用 123 个 regression tests 验证隔离、撤权、fork 衰减、exec 不提权等性质。它暂时不声称提升 SWE-bench 分数，但对长程 agent runtime 的安全边界非常关键：可靠性不只靠 prompt，权限、审计和恢复必须成为运行时机制。
🔗 链接：https://arxiv.org/abs/2606.03895 ｜ 代码：None

### SkillRevise：用执行轨迹修订冷启动 agent skill
Agent Skills 的问题不是“能不能写成 Markdown”，而是一个看起来合理的 skill 是否真的会让 agent 在环境里做对事。SkillRevise 关注冷启动场景：只有一个初始 LLM 生成或人工写的 skill，没有大量历史轨迹可做自演化，如果直接投入生产，很可能语法漂亮但行为很弱。它的循环是执行当前 skill、从 verifier 反馈里诊断失败、从 Principle Memory 检索通用修复原则、生成带执行锚点的 skill edit、重新执行候选版本，再按实际 utility 保留最佳 skill。这里的“执行锚点”很重要，它不是笼统说“更仔细检查 JSON”，而是要求 agent 在某个阶段实际 reload 文件、parse schema、检查 key、跑本地验证。实验中 GPT-5.5 在 SkillsBench 从无 skill 36.05% 提升到三轮 revision 后 61.63%，且对 Opus、Kimi、Qwen、DeepSeek 等 executor 也有不同程度收益。对技能自动生成/管理方向，这是一个很实用的信号：skill 应该像代码一样被测试、修补和回归选择，而不是一次生成后直接进入库。
🔗 链接：https://arxiv.org/abs/2606.01139 ｜ 代码：None

### R3-Skill：skill 不是 document，路由要学兼容性
随着技能库从几十条涨到上万条，把所有 `SKILL.md` 塞进上下文已经不可行；但把 skill 当普通文档做向量检索也不够，因为任务通常需要一组“彼此兼容”的技能。R3-Skill 的核心观点是：document retrieval 里两个相关文档一起出现通常没问题，skill routing 里两个单独相关的技能一起出现却可能冲突、重复或引导 agent 走错生态。作者把 LLM 合成数据时通常丢弃的 SKIP/reject 信号保留下来：当 LLM 判断某组技能“不应共同服务这个 query”时，这正是兼容性负样本。数据集包含 10,246 个去重技能、41,592 个 accepted queries、32,828 个 SKIP annotations，覆盖中英四种语言方向，并有 8 类拒绝原因 taxonomy。方法上用两阶段 R3-Embedding + R3-Reranker，把兼容性负信号放在 cross-encoder reranker 阶段，因为单个 skill embedding 会被不同 query 的正负梯度相互抵消。对 skill management 工程来说，这补上了一个前端关键环节：不是只问“哪个 skill 相关”，而是问“哪一组 skill 对这个任务最小且足够、不会互相打架”。
🔗 链接：https://arxiv.org/abs/2606.03565 ｜ 代码：None

### Mastra Code Harness：把 context rot、审批链和观察记忆做成 harness 架构
Mastra 这篇长文不是论文，但把 coding agent harness 的很多真实工程问题讲得非常具体。作者指出朴素 agent loop 会遇到三类静默失败：context rot（上下文越来越长但信号越来越稀）、lossy compaction（一次性摘要丢掉关键约束）、stateless sessions（重启后项目决策全丢）。Mastra Code 的做法是把 conversation 当成一个持续 channel，而不是一次 HTTP 调用；所有模型/工具事件被规整成 semantic events，再由 reducer 折叠成可渲染 display state，让终端/Web UI 不需要重放原始流。它还把人工问题、plan approval、任务列表、工具审批链做成 harness back-channel，工具可以暂停并等待用户，而不是在模型上下文里假装完成。最有价值的是 Observational Memory：提前由 observer 模型把长对话转成结构化观察，再由 reflector 压缩，主 agent 读取 recent raw messages + observation log + reflections，而不是等上下文满了再粗暴总结。对 harness engineering 来说，这是一份难得的生产架构拆解，说明“长期会话记忆、审批、显示、subagent 隔离/缓存复用”都应该是显式系统层，而不是混在 prompt 里。
🔗 链接：https://mastra.ai/blog/anatomy-of-a-coding-agent ｜ 代码：https://github.com/mastra-ai/mastra

### Microsoft Agent Governance Toolkit v4：跨框架 agent 治理与策略执行
当 agent 从 demo 走向企业工作流，问题会从“能不能完成任务”升级为“谁给了它权限、它能不能越权、失败后能否追责”。Microsoft Agent Governance Toolkit v4 是一个高热度工程项目，定位为 policy enforcement、zero-trust identity、execution sandboxing 和 reliability engineering，仓库约 4.1k stars，并明确覆盖 OWASP Agentic Top 10。它的价值在于不绑定单一 agent 框架，而是提供 policy engine、capability model、audit、MCP gateway、identity、trust scoring、runtime privilege rings、saga orchestration、termination control 等组件。最新 v4 release 还扩展了 Claude Code、Google ADK、LangGraph、CrewAI、OpenAI Agents SDK、LlamaIndex、Mastra 等适配器，说明治理层正在走向“跨 runtime middleware”。对本日报关注的 agent runtime / harness 工程，这类项目很重要：它把安全和合规从建议变成可安装、可回放、可 lint、可审计的执行层。需要注意它仍需真实场景压力测试，但方向非常符合企业 agent 落地需求。
🔗 链接：https://github.com/microsoft/agent-governance-toolkit ｜ 代码：https://github.com/microsoft/agent-governance-toolkit

### InKH：金融 agent 的交互原生知识 harness
金融 agent 的难点不只是懂不懂金融术语，而是用户偏好、历史判断、风险假设、市场状态会不断变化，用户不可能每轮都重新解释。InKH 提出 interaction-native knowledge harness，把过去交互持续编译成结构化知识，而不是让 agent 每次自己临时查 wiki 或向量库。在线路径用 passive knowledge injection：系统根据当前事件、实体、风险类别，从 temporal knowledge graph 里取一个受治理、受 token budget 限制的上下文块，直接注入 working context；离线路径把完成的 workflow 提取成知识对象，并在写入时做 contradiction detection 和 invalidation。它还把 wiki 作为 human-readable audit surface，而不是在线检索主路径，这样既能低延迟运行，又能让人审计知识从哪里来、何时失效。实验是受控金融 benchmark，InKH 相对 WikiWalk 降低 82.95% latency、82.29% token load、96.58% stale-memory usage，同时提升任务质量和 traceability。虽然场景是金融，但工程模式可迁移到 coding agent：长期项目记忆也应区分在线低延迟检索、写时失效、成熟度 gating 和可审计 wiki。
🔗 链接：https://arxiv.org/abs/2606.01886 ｜ 代码：None

### LLM Consortium：系统比较 12 种软件架构多 agent 拓扑
多 agent 协作常被默认认为“人多力量大”，但真正有效的是哪种协作拓扑并不清楚。LLM Consortium 用 2×2×2 factorial design 系统比较 Authority、Roles、Dynamics 三个维度，跑了 12 种软件架构设计 workflow、8 个任务、520 次实验，再用 GPT-OSS、Claude Opus、Claude Sonnet 三个评估器按 12 维 rubric 打分。最强结果不是简单并行，而是 structural adversarial：一个 principal architect reviewer 不接受局部补丁，而是要求被拒部分推倒重写、解释为什么不用旧方案。第二名是 cross-model review，也就是一个模型生成，另一个模型家族审查，说明不同训练分布带来的 blind spots 很有用。最失败的是 parallel merge：三个独立设计合并时会因为 token starvation 和 Frankenstein effect 丢掉结构一致性，甚至比单 agent 更差。对软件工程 agent 编排而言，这篇给出很务实的结论：不要迷信并行合并，优先做强约束审查、跨模型复核和结构化 rewrite gates。
🔗 链接：https://arxiv.org/abs/2606.01490 ｜ 代码：None

### SCORE：深度研究 agent 的生成器与评估器共同进化
深度研究报告不像代码测试那样有明确 ground truth，所以直接用 RL 训练容易卡在“奖励不可验证、judge 静态、优化压力饱和”。SCORE 的思路是让 evaluator 和 solver 在同一个共享 actor 上共同进化：solver 生成报告，evaluator 根据 query-specific rubric 和检索证据评分；反过来 evaluator 也用一致性等信号更新，让评估标准随 solver 变强而调整。为了避免 evaluator 任意漂移，它引入外部 meta-harness 来动态控制 evaluation environment，包括可选评价维度、证据验证要求、rubric 结构限制和训练统计反馈。实验把 SCORE 接入 open-deep-research 与 gpt-researcher 两种 agent 范式，在 DeepResearchBench 等指标上提高分析深度和 citation validity，同时避免普通 GRPO 在某些 plan-and-execute agent 上的训练崩塌。它不是 coding agent 专项，但与“自动化研究 / research harness”强相关：当任务没有程序化 verifier 时，评估器本身也需要工程约束、动态更新和反作弊边界。对后训练软件工程的启发是，open-ended agent 的 reward system 不能只靠一个静态 LLM-as-judge prompt。
🔗 链接：https://arxiv.org/abs/2606.04507 ｜ 代码：None

### Google ADK 2.x：高热度 code-first agent development kit
Google ADK 是近期社区高热度的 agent framework，仓库约 20k stars，定位为 code-first、model-agnostic、deployment-agnostic 的 Python toolkit。它本身不是一篇新论文，但在 ADK Arena 这种框架评测出现后，ADK 类工具的 API 设计、任务抽象和可测试性会越来越重要。近期 2.x release 强调 Task API、结构化 agent-to-agent delegation、事件/会话 schema 更新以及多语言文档生态，说明主流厂商正在把 agent 开发做得更像软件工程框架，而不是 demo 脚本集合。它解决的真实痛点是：团队需要可部署、可评估、可编排的 agent runtime，而不是每个项目从 ReAct loop 开始复制粘贴。对后训练/harness 团队来说，ADK 这种框架也会成为评测和训练数据的环境变量：同一模型在不同 ADK 上可能表现、成本和失败模式都不一样。建议与 ADK Arena 一起看，把“框架选择”当成 agent 系统能力的一部分来度量。
🔗 链接：https://github.com/google/adk-python/ ｜ 代码：https://github.com/google/adk-python/

## 🔥 社区热点专栏

### 🔥 大佬观点

**Peter Steinberger（@steipete）/ Addy Osmani：从 prompt engineering 转向 loop engineering。**  
6 月 7–8 日社区围绕“不要再只 prompt coding agent，要设计会 prompt agent 的 loop”快速发酵，Addy Osmani 等人把它总结成 loop engineering。值得注意的不是新名词，而是工程判断：真正可靠的 agent loop 至少需要任务输入、持久状态、确定性 gate（测试/lint/CI）、失败反馈和硬停止条件，否则只是把人工监督换成无限重试。🔗 https://www.thedeepfeed.ai/posts/2026-06-08-loop-engineering-terminology-treadmill ｜ https://addyo.substack.com/p/loop-engineering

**Anthropic Claude Code 团队：dynamic workflows 让 harness 成为“任务输出”，而不是预先写死的脚手架。**  
Claude Code dynamic workflows 的社区讨论继续升温：Claude 可以按任务写 JavaScript orchestration script，fan-out 子 agent、做 adversarial check、决定模型与 worktree 隔离方式。这个观点重要，因为它把 harness 从静态产品功能变成可生成、可复用、可审计的中间产物，也解释了为什么长程任务需要“自定义 loop”而不是一个通用 agent loop 打天下。🔗 https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code

### ⭐ 超火仓库/项目

**Google ADK（google/adk-python）：20k+ stars 的 code-first agent development kit。**  
Google ADK 近期 2.x release 继续高速迭代，强调 Task API、结构化 delegation、model/deployment agnostic 和样例生态。它火的原因是团队需要像开发普通软件一样开发、测试、部署 agent，而不是每个项目手写一套 loop；也与 ADK Arena 形成互补，一个是框架，一个是框架评测方法。🔗 https://github.com/google/adk-python/

**Microsoft Agent Governance Toolkit：4k+ stars，面向 agent 的策略、身份、沙箱与审计层。**  
这个项目把 OWASP Agentic Top 10、policy engine、capability model、MCP gateway、runtime privilege rings 和多框架 adapter 做成可安装工具链。它解决的是企业落地最实际的痛点：agent 不只要能做事，还要可授权、可撤权、可审计、可回放，尤其适合 Claude Code / Google ADK / LangGraph / OpenAI Agents SDK 等混合栈。🔗 https://github.com/microsoft/agent-governance-toolkit

**Uni-CLI（olo-dot-io/Uni-CLI）：一个 agent-to-computer control plane，连接 CLI/MCP/浏览器/桌面。**  
Uni-CLI star 数还不算现象级，但方向很贴合 Agent-Friendly Software：它把 300+ 网站/工具、浏览器 CDP、桌面 app、MCP、本地执行、证据回传和 self-repair 放进统一 operation substrate。它的 insight 是“真实软件边界很多，agent 需要一个可治理的最小操作面”，这比单纯把网页或 GUI 暴露给视觉模型更可控。🔗 https://github.com/olo-dot-io/Uni-CLI

**Command Center（Show HN）：把 agentic coding 的重点放在首版之后的质量管线。**  
HN 上的 Command Center 讨论抓住一个现实痛点：生成第一版代码已经越来越容易，难的是把 2,000 行 diff 变成可审查、可重构、可解释、可提交的高质量变更。它主打并行生成多个 diffs、自动重构、生成 walkthrough、逐行反馈再派 agent 修正，说明社区正在把关注点从“vibe 出代码”转向“review / refactor / walkthrough / PR quality harness”。🔗 https://news.ycombinator.com/item?id=48453002
