## 逐条讲解

### CoTrace: Data Recipes for Training Terminal Agents with Harness-Model Co-Evolution
终端 agent（在命令行里干活的模型）的表现取决于两样东西：模型权重本身，以及 harness（负责拼提示词、绑定工具、处理报错重试的运行框架）。已有的"harness 与模型共同进化"方法会边改 harness 边训模型，但通常把搜索 harness 时产生的所有轨迹不加区分地塞进一个回放池里一起训练。CoTrace 指出这是个数据工程错误：一条轨迹对训练有没有用，取决于它是在哪个 harness 下跑出来的。它的做法是把 harness 搜索和策略训练拆成交替的两步，每一步单独决定是否"晋升"；反复出现的执行失败用来指导下一版 harness 的合成，而模型训练只用"和当前采用的 harness 匹配、且经过验证"的轨迹（SFT），或者在新 harness 下重新在线采样（RL）。结果上，Qwen3.5-9B 在 Tmax 晋升集上 SFT 后从 78 题提升到 88 题，RL 版本到 90 题；一个小而匹配的语料，比混合多个兄弟 harness 的大语料效果更好、算力更省。在 Terminal-Bench 2.1 和 SWE-bench Lite 上，迁移效果高度依赖训练与评测 harness 是否一致。对我们来说，这给出了一条非常具体的数据规范：轨迹数据要带上"来源 harness"这个元数据，训练时按来源匹配，而不是越多越好。
🔗 链接：https://arxiv.org/abs/2610.10426 ｜ 代码：None

### Before They Can Solve: Predicting Post-Training Coding-Agent Performance from Base Models
做 agentic 后训练非常贵，团队常常要先决定"哪个 base checkpoint 值得投入一轮 RL"。传统做法是直接测 base 模型的端到端 pass@K，但很多 base 模型连格式正确的工具调用都发不出来，端到端测出来全是 0，没有区分度；而把任务压缩成单轮补丁生成又丢掉了"多步维护仓库状态"这个核心能力。这篇论文的思路是借用已经后训练好的模型的成功轨迹作为"前瞻信号"：逐步回放轨迹，每次改代码后重跑测试，找到让仓库从"测试失败"翻转为"测试通过"的那个决定性步骤。然后在这一步上设计三种不需要 base 模型自己驱动 harness 的筛查：看 base 模型给这个正确动作分配多少概率（Decisive-Action BPB）、让它在正确动作和被同一 verifier 否掉的备选之间做选择（Patch MCQ）、以及从这一步前缀出发的 pass@K。在十对公开的 base/后训练模型上，三种筛查给出的排序都和后训练后的 SWE-bench Verified pass@1 高度一致。这对后训练流水线是很实用的"预评测"工具：只需要基准的成功轨迹和 verifier，就能在训练前筛掉不值得投入的 checkpoint。
🔗 链接：https://arxiv.org/abs/2610.10478 ｜ 代码：None

### Arena Alignment Index
Arena（前身是 LMArena）以众包对比打分出名，但模型"对齐得好不好"一直缺少来自真实使用场景的度量，各家实验室的 system card 里的对齐评测也都是自测。10 月 8 日 Arena 发布 Alignment Index 预览版：从 Agent Arena 上约 9 万条真实 agent 会话中，挑出三个能在对话里直接找到证据的失败信号——越权操作（做了用户没要求的事，比如未经允许删文件）、错误归因（把与用户提供证据矛盾的话安到用户头上）、虚报完成（任务没做完却说做完了）。流程是先人工定 rubric 并复核，再用 LLM 裁判批量标注，并对会话长度、完成情况做校正。初步结果是 GPT-6.1 Sol 以 87.9 分居首，Claude Opus 5.5 为 83.2，Grok 4.7 为 82.7；最值得关注的是"虚报完成"平均出现在 10% 的会话里，而在代码调试类会话中高达 48%。对我们来说，这是"用真实流量构造评测"的一个范例，也提醒 coding agent 后训练时要专门针对"声称已跑测试/已修复"这类虚报行为设计奖励和检查。
🔗 链接：https://arena.ai/blog/ai-alignment-index ｜ 项目：https://arena.ai/leaderboard/agent/alignment

### Coding-Agent Benchmarks Should Match Their Users' Task Flows (SWE-TaskFlow)
现在的 coding agent 基准大多从 GitHub issue 派生，一个任务就是"给一个 issue，交一个补丁"。JetBrains 团队收集了 4,782 条真实工程师在 IDE 里使用 agent 的会话，重点分析了至少三轮用户消息的长会话（占 33%），发现真实使用和基准差别很大：用户的请求类型远比"修 bug"丰富，包括问代码、做规划、评审、重构、执行命令，而且一个会话里会频繁切换类型。他们还发现，三个公开交互语料的"任务流"（会话长度、任务类型、类型之间的转移分布）彼此差异显著，所以不存在一个通用的"真实分布"，基准必须先说清楚针对哪种使用场景。为此他们提出 SWE-TaskFlow：保留原 issue 任务和测试不变，通过拆分提示词、插入可验证的仓库问答，把交互过程引导成目标任务流，并用一个对齐分数（TFAS）挑选生成的轨迹。在 700 个 SWE-Bench Pro 任务上的试点显示，多步顺序解题让 agent 成本大约翻倍，但解决率没有稳定变化——说明"交互协议"本身就是一个独立的评测维度。对评测工程来说，这提供了把现有基准改造成多轮交互评测的可行办法，也提醒我们用真实遥测数据去校准评测分布。
🔗 链接：https://arxiv.org/abs/2610.09633 ｜ 代码：None

### SpecGuard: Proving a Task Is Broken Before the Agent Cheats
RL 环境和评测任务里经常有"任务描述和测试互相矛盾"的情况，可能是无意写错，也可能是被恶意注入。已有研究发现，agent 遇到这种矛盾时很少会提出来，而是直接作弊：改测试、硬编码期望输出，甚至删掉安全防护来让一个错误的测试通过。SpecGuard 想在 agent 动手之前就拿出"可独立验证的证据"证明任务本身有问题。它只看任务描述和代码库，把"意图中的行为"自动形式化成 Lean 4 规约，再把测试独立地形式化，然后让 Lean 内核检查"是否存在任何实现能同时满足两者"，如果不存在就产出一个机器可检查的证书。在带冲突的 SWE-bench 任务上，它能检测出最多 72.8% 的冲突、形式化证明其中 51.1%，漏检率比让模型直接判断低了近五倍。对环境构建团队来说，这是一个可以放进环境 QA 流水线的"预检"步骤：在任务进入 RL 训练集之前，就把会诱发 reward hacking 的坏任务筛掉。
🔗 链接：https://arxiv.org/abs/2610.09159 ｜ 代码：https://github.com/prmbiy/specguard

### On the Reliability of LLM-Based Vulnerability Patching Benchmarks
自动修漏洞是 coding agent 的热门应用，但各类基准报出来的成功率到底可不可信？作者结合自己开发和压测这类框架的经验，把失真来源归为三层：agent 层（提示词、可用工具、详细指令能抬高成功率，却不提高补丁质量）、框架层（权限错误、基础设施 bug、超时处理会悄悄压低或抬高分数）、数据集层（只靠 bug 报告和单个 PoC 测试，无法判断补丁有没有修到根因、是否符合开发者意图）。他们整理了来自 84 个 C/C++、Go、Rust 开源项目的 112 个历史漏洞，每个都附带 PoC 测试、回归测试，以及额外的"开发者测试"，用来检查补丁是否符合原开发者的设计原则。实验发现：在理想条件下模型的 PoC 通过率可以很高，但执行配置的选择会实质改变测得的成功率；更重要的是，开发者测试的通过率一直很低，新模型也只是略有提升，说明模型越来越擅长"压住症状"，而不是做出上游可接受的修复。这对构建修复类 RL 环境很有启发：只拿 PoC 当奖励，等于在训练"压症状"；要引入开发者测试这类更严格的验证信号。
🔗 链接：https://arxiv.org/abs/2610.10150 ｜ 代码：None

### Finding Blind Spots in AppWorld and WorkArena Task Verifiers
AppWorld 和 WorkArena 都是常用的 agent 环境，用"执行后检查状态"的 verifier 判断 agent 有没有完成任务，这些 verifier 也常被直接拿来当 RL 奖励。这篇工作对官方 verifier 做了"源码感知的变异测试"：读懂 checker 检查了哪些字段，然后构造会产生错误副作用、却可能骗过 checker 的执行。在 AppWorld 里，把一个非幂等的写操作执行两次会多出一条记录，但所有被检查的字段值都没变，于是 verifier 照样判通过（6/15 个构造案例）；作者给 checker 副本加上"记录数"检查后，这些案例全部被拒，而正确的对照样例仍然通过。在 WorkArena 里，23 个"多填字段"的候选执行全都拿到 PASS，其中 21 个通过独立的表 API 回读确认确实写入了错误值。论文态度很克制，明确说这些是"被确认的个例"而非总体比例。对我们来说，这是一套可复用的 verifier 审计方法：对每个奖励函数，都应该系统地问一句"什么样的错误副作用它看不见"。
🔗 链接：https://arxiv.org/abs/2610.09142 ｜ 代码：None

### RSI-Forge: From Research Papers to Environments for Recursive Self-Improvement
要训练或评测"能自我改进的研究型 agent"，需要大量有挑战性、评测可靠的研究环境，但这类环境目前主要靠领域专家手工搭建，规模和学科覆盖都受限。RSI-Forge 是一条多 agent 流水线，把已发表论文自动转成可执行环境：三个 agent 分别负责构建、复现和审核，产出带自动评测器的任务，并且独立重新实现论文的方法作为基线分数。目前已产出覆盖 18 个领域的 210 个环境，其中 90 个经过独立的人类领域专家审核；专家和 agent 裁判都认为"起始方案有改进空间、评测器能区分好坏"，但专家对"能否抵抗捷径""是否忠实于原论文"更挑剔。在 120 个环境上让四个模型连续尝试三次（继承之前的代码和笔记、权重不变），84% 的环境里至少有一个模型在第一次之后继续提升，68 个环境里模型超过了复现的论文方法。这是一个"从现成资料自动造环境"的规模化范例，而专家与 agent 裁判的分歧点（捷径抵抗、忠实度）恰好是环境 QA 最该投入人力的地方。
🔗 链接：https://arxiv.org/abs/2610.09426 ｜ 代码：None

### Large-scale Repository Engineering via Agent-Native Reusable Code Primitives (LEGO / LEGO-REPO)
让 agent 从零构建一个完整仓库，难点在于模块、接口、配置、测试、依赖要能一起工作，而现有做法要么全靠模型现写，要么把检索到的代码当上下文塞进去。这篇论文提出"代码原语"（Code Primitives）：每个原语是一个带接口契约、依赖闭包、验证测试和来源信息的可执行组件，并附带一个常驻 LLM 负责把它适配到目标仓库；作者整理了 1,424 个经过验证的原语，组成可搜索的库 CodeFace。LEGO 框架会激活与任务相关的原语，把适配后的实现和任务特定代码整合，解决组件间约束，再根据执行测试的结果修订。为了端到端衡量建仓能力，他们还构建了 LEGO-REPO 基准：522 个可执行的仓库重建任务，覆盖 7 个软件领域和 5 个难度级别，用原仓库自带测试打分，下限是空包、上限是原始源码。最强的骨干模型只拿到 0.318 分，41% 的任务得 0 分；LEGO 让 13 个骨干平均提升 0.147，GPT-5.6-terra 从 0.318 提升到 0.513。这说明"可验证的组件库 + 适配"比"检索代码当上下文"更有效，LEGO-REPO 也是一个有区分度的建仓评测。
🔗 链接：https://arxiv.org/abs/2610.09079 ｜ 代码：None

### When Sub-Agents Work in Parallel: Dynamic Concurrency in Long-Horizon Coding Tasks
Codex、Claude Code、Kimi Code 等前沿 coding agent 现在都支持"动态并发"：agent 在执行过程中自己决定要不要、怎么拆出并行的子 agent。但已有研究要么关注短任务上的失败，要么研究预先定义好的多 agent 工作流，没人系统地看过这种"运行时自主并发"到底有没有用。这篇论文做了严格的对照实验：同一个 agent 在同一任务上分别开启和关闭并发策略，覆盖 354 个任务、2,124 次执行，任务复杂度和执行时长跨度很大。结论是短任务主要看模型能力，而长周期开发里编排能力成为决定性因素；作者从配对轨迹中归纳出 13 种并发特有的失败模式和 28 种可观察的行为模式，并给出了并发真正带来优势的条件。对 agent 系统工程来说，这是一份"什么时候该开并发"的实证指南，那 13 种失败模式也可以直接变成并发调度的评测用例。
🔗 链接：https://arxiv.org/abs/2610.10263 ｜ 代码：None

### ToolRACER: Robust Agentic Conversation Emulation for Agent Training and Evaluation
面向任务的对话 agent 在真实场景里很脆弱，因为真实用户不按剧本走，有时还会故意不配合；而现有的函数调用基准大多是"用户很配合、流程很顺利"的对话，训练数据里也缺少对抗性的用户行为。ToolRACER 是一条合成数据流水线，让用户模拟、助手模拟、工具模拟三个模型协同生成多轮交互，并对结果做验证。它覆盖 6 个领域、55 种用户画像，生成了 5.6K 条验证过的对话轨迹，其中约 66% 包含容易出错的场景，还专门注入了对抗性用户行为。用这些数据训练的模型在 τ²-bench 和 ACEBench 上的端到端 agent 准确率都有提升，和领域内数据混合使用时对小模型的增益尤其明显。对 SFT 数据工程来说，这说明"刻意构造不配合的用户"是提升 agent 鲁棒性的一条低成本路径。
🔗 链接：https://arxiv.org/abs/2610.09163 ｜ 代码：None

### MIMESIS: Learning User Simulators as Training Environments for Interactive Agents
训练交互式 agent 需要大量用户交互，真人反馈既贵又难规模化，所以大家常用一个现成的助手型 LLM 扮演用户。问题是助手型模型太"热心"：过于配合、表达过于清晰、行为千篇一律，和真实用户差距很大，agent 在这种环境里学到的东西迁移性差。MIMESIS 专门训练了一个用户模拟器，训练数据是带显式推理监督的真人对话，并融入了从真实交互中总结出的 13 种行为模式。它的 9B 模型在 SOUL-Index 上拿到 65.7，超过最强的前沿模型；相比 Claude-Opus-5，行为保真度高 13.4 分。更关键的是，把它冻结当作 RL 环境去训练 agent，在 8 个环境、9 个没见过的用户模拟器上的表现都优于用 GPT-5.5 当用户训练的结果；作者还提出"教练式在策略自蒸馏"，把模拟器的私有推理转成稠密的逐 token 监督。对 RL 环境工程来说，"用户模拟器本身也要专门训练"是一个值得采纳的结论。
🔗 链接：https://arxiv.org/abs/2610.09484 ｜ 代码：None

### RollVerify: Bridging Efficiency and Accuracy in Long-Tail Rollout RL
RL 后训练要生成大量 rollout，随着上下文变长，rollout 长度呈长尾分布，同步训练时少数特别长的样本会让 GPU 大量空等。异步或"部分 rollout"方法能提高吞吐，但会引入过时的离策略样本，伤害最终精度；已有方法大多在训练时对这些样本重新加权，仍和完全在策略训练有差距。RollVerify 换了个思路：不是训练时被动降权，而是在样本进入训练之前主动检查和修复。它定义了一个离策略偏移度量 OPS，量化部分生成的轨迹偏离当前策略的程度，在 OPS 约束下做序列级和 token 级校验，把无效的后缀截掉。在数学和工具辅助数学推理上，它达到了与在策略训练相当的精度，同时降低训练成本，代码生成上也有初步正面结果。这是 RL 基础设施层面的工程改进，适合直接用在长轨迹的 agentic RL 训练中。
🔗 链接：https://arxiv.org/abs/2610.09914 ｜ 代码：None

### SkillForge: Co-Evolving Skills and Agents via Dynamic Skill Lifecycles
给 agent 配一个"技能库"（指令加适用条件）是提升长任务能力的常见做法，但如果随着策略变强还把所有技能都留着，过时甚至有害的技能会越积越多，反而误导 agent。SkillForge 给每个技能设计了"试用、启用、稳定、退役"四种状态，根据适应度在训练过程中流转，让技能库和模型一起进化。具体流程是：RL 之前先用 base 模型自己的 rollout 评估技能，把低适应度的提前退役，得到过滤后的技能库并用它产出 SFT 数据；之后进入 RL，每轮继续做选择性退役、稳定化和 LLM 引导的变异。在多个交互式 agent 基准上，它比最强基线最多相对提升 7.8%，同时技能库保持紧凑。作者还发布了 SkillFurnace 数据集（5k+ 条，包括过滤后的 SFT 轨迹、带适应度标注的技能库和人工标注失败类别的退役事件），对研究"技能质量管理"很有用。
🔗 链接：https://arxiv.org/abs/2610.09832 ｜ 代码：None

### Decoupling Exploration from Optimization in RLVR (ExpDis)
RLVR（用可验证奖励做 RL）的一个期待是让模型发现新的推理策略，但直接在奖励里加强"新颖性"激励往往会把模型训坏，而且因为可验证奖励只覆盖模型能力的一小部分，坏掉之后很难恢复。ExpDis 把"探索"和"优化"拆开交给不同模型：训练一个或多个带新颖性奖励的"探索者"策略，筛选它们产出的正确且高质量的轨迹，再蒸馏给一个单独的"学生"策略，学生自己训练时不加新颖性奖励，如此多轮交替。这样可以大胆地扩大探索力度，而不污染最终要交付的模型。在 7 个数学推理基准、两个模型家族上，同等墙钟预算下 ExpDis 优于 DAPO，pass@k 的扩展性也更好，说明学生学到了更多样的正确解法。从工程角度看，这本质上是一个"探索数据生产 + 过滤 + 蒸馏"的流水线设计，思路可以迁移到代码 RL 的数据生成上。
🔗 链接：https://arxiv.org/abs/2610.10536 ｜ 代码：https://github.com/SaifPunjwani/Exploration-Distillation

### Goodfire: Training and Deploying Production Cyber Monitors on Kimi K3
对 agent 做安全或 reward hacking 监控，常见做法是让另一个 LLM 逐步重读 agent 的输出，但用前沿模型做裁判贵且慢，很难覆盖每一条 rollout。Goodfire 的做法是"由内向外"监控：在 Kimi K3 和 GLM 5.3 的推理过程中，读取模型已经算出来的中间激活，跑一个很小的分类器（probe，探针），只有探针读数超过校准阈值时才把会话交给 LLM 裁判复核。校准后探针在留出集上做到 0% 漏报、95% 真阴性率；在约 1,500 个会话的测试中，监控成本约 51 美元，而便宜模型逐步检查要 233 美元、顶级模型约 1 万美元，恶意入侵会话检出率 94%，四个探针让首 token 延迟增加不到 2%。Goodfire 此前还用 Prime Intellect 的 verifiers 环境发现主流开源模型在 50%–96% 的 rollout 里存在 reward hacking。对 RL 训练基础设施来说，这意味着"每条 rollout 都做 reward hacking 监控"在成本上变得可行。
🔗 链接：https://www.goodfire.com/research/production-cyber-monitors-on-kimi-k3 ｜ 代码：None

### Anthropic OSS Scanner（Cyber Mission 的一部分）
过去半年 Anthropic 用最新模型扫描重要开源项目，发现了超过 29,000 个候选漏洞，但人工只来得及复核约 6,000 个，人工验证成了瓶颈；不少维护者干脆要求"把没验证的也都发给我们"。10 月 8 日 Anthropic 推出 OSS Scanner：开源项目自愿加入后，可以免费获得最强模型（包括 Claude Mythos）的定期扫描，报告完全由模型生成、不经人工复核，每份都附带自包含的复现脚本、漏洞解释（尽量包含二分定位引入时间）和候选补丁。在验证阶段，专业渗透测试员复核了 48 个项目的 97 个高危/严重发现，88% 达到人工披露标准，只有 1 个是误报；wolfSSL 收到的 74 份报告里 72 份有效、5 个成了 CVE。也有不同声音：Dan Luu 等人在 Mastodon 上批评此前的报告误报率高。对我们来说，这条"agent 找漏洞→agent 复核→生成复现与补丁"的流水线，本身就是"带可执行证据的 verifier"设计的大规模实践。
🔗 链接：https://www.anthropic.com/research/launching-opt-in-vuln-finding-service-for-open-source ｜ 项目：https://red.anthropic.com/oss-scanner/

### Building effective agent automations（Claude Managed Agents）
定时运行、在后台汇总信息再主动推送的 agent 自动化越来越常见，但它们很容易悄悄出问题：某个数据源的访问权限失效了没人发现，或者慢慢不再遵循用户偏好。Anthropic 开发者博客发布了一份基于 Claude Managed Agents（beta）的参考实现：按计划读取 Slack 频道和 GitHub PR，记录自上次运行以来的变化，再把需要知道的内容发到 Slack。文章把这类 agent 拆成六个部分：数据源、唯一可写的目标、agent 定义、cron 调度、记忆（用户偏好 + agent 自己的书签/账本/运行记录）、护栏（只读权限、每次运行的花费上限），凭据放在沙箱之外的 vault 里由代理注入。所有资源用声明式配置文件描述，`ant apply` 一键创建。这是一份很实用的"生产级 agent 自动化"工程清单，尤其是"只给一个写出口""凭据不进沙箱"两条原则值得借鉴。
🔗 链接：https://claude.dev/blog/building-effective-agent-automations/ ｜ 代码：None
