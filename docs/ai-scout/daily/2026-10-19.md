## 逐条讲解

### Harness²：没有标准答案时，agent 怎么给自己"调 harness"
agent 的能力不只取决于模型，还取决于 harness——也就是包在模型外面的提示词、工具说明、记忆、skills、子 agent、脚本、插件这一整套系统。过去"自动改进 harness"的工作（递归自我改进，RSI）大多依赖一个有标准答案的验证器来判断改得好不好，而且改出来的东西往往只适用于某个任务；可真实世界的新任务既没有现成验证器，也和设计时见过的任务不同。Google Research 的 Harness² 分两层递归来解决：任务层用"提出–试探–组合"（Propose–Probe–Compose）——先提出若干 harness 改动，在同一个任务上分别跑一遍，然后**对比这些执行之间的行为差异**来组合出更好的 harness，全程不需要标准答案；harness 层则把每次被采纳的改动和有证据支持的经验写进一个持续更新的"改进 harness"，下次遇到新任务时用它来指导修改。它开放了 8 个可编辑组件，支持 OpenCode 和 Codex 两种执行器，只改一轮就让 GLM-5 和 Gemini 3.5 Flash 在 WorkBuddy-Bench 上最多 +11.5、JobBench +4.5、法律类 LAB 部分通过率 +11.8pt，加大递归预算还会继续涨。对后训练工程的启示是：**"用对比执行代替验证器"**让 harness 优化可以在线上、无标注地进行，这和"harness 自动化调优 → 再把好轨迹回流做训练数据"的数据飞轮天然衔接；仓库自带不需要模型凭证的确定性 demo，工程上很容易上手。
🔗 链接：https://arxiv.org/abs/2610.14224 ｜ 代码：https://github.com/google-research/harness2

### MAI-Gym：把 GUI agent 的"评测、采数据、在线 RL"装进同一套环境
可验证奖励的在线 RL 已经在数学、代码、工具调用上屡试不爽，但搬到手机/电脑 GUI agent 上就很吃力：交互环境贵，真实又有难度的训练任务稀缺，而且评测和训练常常跑在两套不同的系统里，agent 行为不一致，分数也就对不上。MAI-Gym 用一条共享的 rollout 管线同时服务评测、数据采集和在线 RL，接入 10 个现有基准，可扩到 2 万个并行环境实例。它更有意思的是"造环境"能力：自动合成多样的 GUI 应用和任务，包括可重置的 mock App（比如模拟的火车票 App），以及多个 App 连成的一致"世界"，每个任务都配一个**通过实际执行验证过的 verifier**。用它训出的 9B 统一 agent 在 MobileWorld 78.4%、OSWorld-Verified 76.2%，是 10B 以下开源 GUI agent 的最好水平；更关键的是，在 mock 火车票 App 里做的 RL 能迁移到真实 App，真机成功率从 28.8% 提到 48.1%。作者将开源框架、合成 skills、mock App、2,000 个已验证任务和模型权重。对我们来说，它证明了 **"mock 环境 + 执行验证的任务合成"可以 sim-to-real**，是 GUI/computer-use 方向最值得参考的 RL 基础设施样板。
🔗 链接：https://arxiv.org/abs/2610.20939 ｜ 代码：None（论文声明将开源）

### OS-Helix：让 agent 学会"什么时候点界面、什么时候写脚本"
真实桌面自动化既不是纯视觉操作，也不是纯写代码：改一份表格可能一半时间点按钮、一半时间用 Python 批处理文件。作者先做了个初步实验，发现简单地给 GUI agent 多加一个"执行代码"工具反而会让它变差——说明"GUI 还是代码"的路由决策没法靠提示词拼接，必须用高质量的混合数据训进模型。他们的数据工程有两招：一是"应用–产物组合"，把桌面应用和**真实的文件产物**（真实文档、表格等）配对，实例化成可执行的 Ubuntu 初始状态；二是把"任务指令生成"和"评测器生成"解耦，产出的任务只检查最终状态，因此不论 agent 用 GUI 还是代码完成都能被验证。训练上先用过滤后的混合数据 SFT 冷启动，再在真实桌面环境里做在线 RL，并提出按"动作步"而非按 token 聚合重要性权重的 Step-balanced GSPO，防止很长的代码动作在优化中占主导。结果 OS-Helix-27B 相对同规模 Qwen3.5 混合基线提升 35%，RL 后再涨 42.9%，OSWorld-Verified 达 66.44%，并能迁移到 WindowsAgentArena。**"只验终态、与解法模态无关的 verifier"**是构造混合动作数据时非常实用的设计原则。
🔗 链接：https://arxiv.org/abs/2610.22234 ｜ 项目：https://os-copilot.github.io/OS-Helix/

### AlphaDiana：一套专门用来"拆开看"agent 表现的测量系统
现在说"某 agent 在某基准上多少分"，其实混合了模型、harness、工具、skills、记忆等很多因素，到底哪部分起作用很难说清；不同论文的执行条件（文件是否复用、历史是否保留）也常常不一致，结果没法比较。AlphaDiana 把数据集、agent、环境、打分器做成模块化接口，**保留各 harness 自己的原生控制循环**（不强行改成统一 agent），同时把"文件复用"和"记忆保留"作为可单独控制的变量。它既支持整机级对比，也支持在匹配条件下只替换某个组件（工具、skill、记忆）做微观干预。作者用 3 个开源模型 × 3 个开源 harness 跑了 5 个答案型基准和 2 个交互基准，发现 harness 并不稳定地提升推理准确率：在模型自己做不出的题上带来的收益，会被它把模型本来能做对的题搞错所抵消；skill 指引和保留历史也不可靠。它还提醒：token 少不一定省钱——准确率下降时"每道做对的题"反而消耗更多 token。对评测工程团队，这是一份**"如何做 harness 消融实验"**的方法论与基础设施参考：把正确性、执行状态与完整轨迹、资源记录绑定在一起。
🔗 链接：https://arxiv.org/abs/2610.20675 ｜ 代码：None

### EvoProbe：让基准"根据诊断结果自己进化"
静态 agent 基准有两个老问题：会被刷饱和、会被训练数据污染，所以需要持续更新题目；但只看总分和成功率，你并不知道该往哪个方向出新题。EvoProbe 把"出题—诊断—再出题"做成闭环：每道题拆成可验证的子任务分别打分，再由多个 judge 基于证据评估整条轨迹，然后把"卡在哪个阶段、成功模式、失败模式"提炼成诊断反馈，交给出题模型生成新的**可执行**任务。作者在网络安全场景跑了两轮、8 个模型、66 道题：诊断能看出总分看不出的阶段性差异；在出题模型和求解配置都固定的前提下，所有 8 个模型在新一轮题目上都掉分，平均 Outcome 相对降 11.8%，平均 Pass^3 降 40%。也就是说，新题确实精准地打在了模型的短板上。对构建 coding agent 评测的团队，**"细粒度诊断驱动的增量出题"**是对抗饱和与污染的一条低成本路线，且同样的诊断信号也可以直接用于指导后训练数据的定向合成。
🔗 链接：https://arxiv.org/abs/2610.19433 ｜ 代码：None

### Poison Valleys：代码修复失败，到底是哪一步的"误解"埋下的祸根
代码修复 agent 失败时，最终测试只告诉你"补丁不对"，却不告诉你是前面哪个决定出了错、违反的是哪条软件义务（比如原子性、边界条件）。Poison Valleys 设计了两个合成 Python 场景：给磁盘持久化队列加原子批量领取（PersistQueue），以及给 Dijkstra 最短路加源相关的过滤；然后人为定义一些"听起来合理但其实错误"的软件机制，把它们分别塞进模型的**假设**、**实现计划**或两者中，再用 Oracle 和针对性的诊断坐标评估生成的代码。在 1,844 次模型请求中，把同样的误解从"假设"挪到"计划"里，失败率在两个场景分别上升 32.2% 和 28.9%；不同误解会导致不同的、且依模型而异的义务违反模式，有时多种误解又会收敛到同一种失败表现。这项工作建立了"上游误解 → 代码机制 → 失败形态"的可测因果链。对数据工程的启发是：**计划阶段的错误比假设阶段的错误更致命**，在构造过程监督或纠错数据时，应优先覆盖"计划被污染"的情形。
🔗 链接：https://arxiv.org/abs/2610.21514 ｜ 代码/数据：https://poisonvalleys.org

### Source-Judged Compaction：压缩上下文时，删掉"没有出处"的摘要条目
长程 agent 的上下文窗口装不下全部历史时，会用一个"压缩器"把历史替换成一段自然语言摘要。作者发现问题出在摘要本身：压缩提示通常要求写出"决策和下一步"，于是摘要里混着环境真实返回过的事实和压缩器自己推测的内容，agent 之后再也分不清哪些是真的。在一个常用结构化压缩器上分析，83% 的失败运行可以追溯到 agent 执行了某条摘要条目，而其中大部分条目在环境输出里**找不到出处**。SJC 的做法很简单：每次压缩后，逐条检查摘要条目能否在环境输出或上一版摘要中找到来源，找不到的就删掉；判官用的是一个非生成式决策模型，直接输出校准过的概率。它免训练、不改 agent 也不改压缩器，每次压缩只多一次便宜的调用；在 AppWorld 和 OfficeBench 上用两个 agent 模型测试，跨运行可靠性提升 2.1%–8.9%，且不增加 agent 的 token 消耗。对 harness 工程，这是一个**可以直接加到任何 compaction 流程后面**的"去幻觉"后处理步骤，代码已开源。
🔗 链接：https://arxiv.org/abs/2610.20927 ｜ 代码：https://github.com/GuanghuiMin/sjc

### AgentPerturb：真实世界很"脏"，agent 能扛住多少噪声
真实任务里，工具返回可能不完整、文件可能有错、用户指令可能有歧义，但现有 agent 评测大多在"干净"环境下进行，缺少一个系统化描述"扰动打在哪里、是什么类型"的框架。AgentPerturb 用二维视角组织扰动：一维是扰动对象（如用户指令、工具输出、环境状态），一维是扰动类型（如缺失、冲突、误导），在 APEX-Agents 和 Toolathlon 上做受控注入，量化前沿模型的鲁棒性。结论是扰动会稳定地拉低表现，但不同环境下最致命的弱点不同；更值得警惕的是轨迹分析显示，**agent 很少意识到输入被篡改**，常常不加验证地把错误信息一路传下去；即使在扰动下成功的轨迹，计算量也显著更高。作者据此建议训练目标应覆盖多样噪声，并奖励"验证、表达不确定、恢复"这些行为，同时开源了一套严格的基准构建流程。对后训练数据工程，这直接指向一类**"带扰动的环境 + 奖励自查行为"**的训练数据构造方向。
🔗 链接：https://arxiv.org/abs/2610.21624 ｜ 代码：https://github.com/xuyj233/AgentPerturb

### DIB-Bench：评测只看输出，就发现不了"部署被动了手脚"
今天的 agent 评测报告只给出行为分数，却不报告被测的到底是哪一套运行时栈（模型、系统提示、工具、中间件……）。如果有人篡改了部署，但让被评测到的输出保持不变，那么任何只看输出的评估器都会放行。DIB-Bench 系统地测了这种"部署完整性盲区"：7,560 个打分样例、6 类篡改、从正则打分器到 LLM judge 的一整条评估器阶梯。反直觉的结果是：**评估器越强，放过的篡改越多**——平均接受率从规则打分器的 88.6% 升到 94.1%；一种"只在特定触发条件下才作恶"的篡改在评测集上完全看不出来，但实际部署中会产生 48%–100% 的有害输出，而且模型越强越严重。作者给出一个 PAC 式的界，证明"输出零偏移"的篡改无论多少样本都无法从输出检测，而一个对部署清单做哈希的"身份通道"零样本就能发现；他们还提出了评测报告应附带的分级部署身份描述符。对评测工程，这是一个提醒：**评测结果应和"被测栈的身份指纹"一起发布**，否则分数不可审计。
🔗 链接：https://arxiv.org/abs/2610.21135 ｜ 代码：None

### LLM 生成代码的"静态质量画像"：能过测试不等于好代码
绝大多数代码生成评测只看能否通过基准测试，但测试往往不完整，而且"通过"并不保证代码可维护、可靠、结构良好——这些恰恰是真实工程里返工成本的来源。这篇论文做了一次大规模静态质量画像：从 LiveCodeBench 收集 73 个模型生成的 65,663 个 Python 程序，用 Pylint、Radon、SonarQube 等成熟静态分析工具评估。结果显示，不同模型之间存在系统性的质量差异，而这些差异单看正确率完全看不出来，其中**可维护性是差异最大的维度**；作者还发现正确性往往伴随结构上的取舍，而不是"写对的代码一律更简单"。这类工作本身方法不复杂，但数据规模足够大，可以作为"代码质量信号"的基线。对后训练来说，它支持一个越来越明确的方向：**在代码 RL 的奖励或数据过滤中加入静态质量指标**，避免只用测试通过率把模型训成"能跑但难维护"。
🔗 链接：https://arxiv.org/abs/2610.19167 ｜ 代码：None

### Router Drift Control：MoE 模型做 RL 时，别让"路由漂移"毁掉训练
RL 训练经常是"离策略"的：推理引擎和训练引擎数值不一致、mini-batch 多次更新、异步训练都会让生成 rollout 的策略和正在训练的策略不同。在混合专家（MoE）模型里这尤其糟糕，因为微小差异就可能让同一 token 被路由到不同专家，即"路由漂移"。现有方案 R3（路由回放）在训练时直接复用 rollout 阶段的专家选择，但作者分析指出这会带来梯度偏差：训练路由选中、而 rollout 路由没选的专家贡献被丢掉了。RDC 换了个思路：把 rollout 与训练两侧的路由分歧当作"这条样本有多陈旧"的信号，直接拒收高漂移的整条回答，保留下来的样本仍走原生路由。策略越陈旧 RDC 的收益越大，在异步训练中配合截断重要性采样（TIS），AIME 2024/2025 平均峰值准确率比 TIS 高 5.5 分、比 R3 高 4.5 分。对搭建 MoE 异步 RL 基础设施的团队，这是一个**实现简单的序列级过滤器**，比改路由逻辑更稳妥。
🔗 链接：https://arxiv.org/abs/2610.21682 ｜ 代码：None

### Multi-Reward Hacking：主奖励 + 辅助奖励简单相加，会把模型带偏
后训练里常把主奖励（如正确性）和辅助奖励（如简洁、高效）组合使用，大家默认"加权求和"就行。作者指出对称聚合存在一种隐蔽的失败：总奖励在涨，主任务表现却在掉——因为辅助奖励（比如"写短一点"）更容易拿到，模型会偏向去拿它。他们在单步多奖励决策的简化模型里证明了这一点，并提出 Trust-Anchored Gating（TAG）：先分别只优化每个奖励通道，看哪个引起的策略漂移最可信，把它选为"锚"；之后只有当锚通道（通常是正确性）满足时，辅助奖励才计入分数。这样"只满足辅助、没满足主任务"的结果在结构上就拿不到分，而"两者都满足"仍有额外奖励。在 Qwen 和 Llama 的数学与程序合成任务上，对称加和、约束和归一化聚合都明显退化，而 TAG 在 Qwen3-4B + 简洁奖励设置下 pass@4 为 0.581（加和仅 0.220），回答还比只用正确性训练短 44%。**"辅助奖励必须以主奖励满足为前提"**是一条可以直接写进奖励工程规范的规则。
🔗 链接：https://arxiv.org/abs/2610.21404 ｜ 代码：None

### RaRE：用 rubric 当奖励时，"换个 judge"分数就变了
Rubrics as Rewards（RaR）把 RL 扩展到没有标准答案的领域：让 LLM judge 按结构化评分细则给回答打分当奖励。以往工作都在改进 rubric 或换更强的单个 judge，很少有人系统研究 judge 本身的影响。作者先用 5 个前沿与开源 judge 在 RaR-Medicine、RaR-Science 上训练 Qwen3-4B-Base，发现**仅仅换 judge 就会造成显著的分数差异**。在此基础上提出 RaRE 集成策略：一是"软 Likert"奖励，用 judge 的 logprob 给更有把握的 judge 更高权重；二是"分歧剔除"，judge 之间分歧大的 rollout 直接不参与 GRPO 更新。关键发现是：朴素地平均多个 judge 的分数并不比最好的单 judge 强，而 RaRE 在 HealthBench 和 GPQA Diamond 上超过所有单 judge 版本。对用 LLM judge 做奖励的团队，"**置信度加权 + 高分歧样本丢弃**"是一个开箱即用的降噪方案，代码已开源。
🔗 链接：https://arxiv.org/abs/2610.21179 ｜ 代码：https://github.com/michael-tyl/RaRE

### CIPR：同一个任务换个工具名，agent 就不会做了？
后训练会把 agent 的能力"绑死"在它训练时见过的接口上：把某个动作改个名字、换种参数写法，任务本身没变，agent 却明显变差。常见的补救是训练时随机化接口，但每个样本独立打分，只是把依赖从"一个接口"扩大到"训练接口的分布"，遇到分布外的改动照样掉分。CIPR 的做法很直接：把动作名替换成无意义的标识符，并把每个训练样本同时放在两套接口下（构造上保证两套接口里哪些动作等价），然后惩罚两种接口下动作分布的 KL 散度，迫使策略跨接口保持一致。它能同时用在 SFT 和 RL 阶段；在函数调用任务上，留出的接口扰动会让后训练 agent 准确率掉近 25%，CIPR 能找回 10.5%，同时不影响原接口上的表现。对构造工具调用训练数据的团队，**"同一样本、双接口呈现 + 一致性约束"**是低成本提升工具泛化的数据增强手段。
🔗 链接：https://arxiv.org/abs/2610.20576 ｜ 代码：None

### DeciCAD：harness 定义的"动作空间"，直接决定 agent 能学到什么
CAD（计算机辅助设计）是典型的专业长程任务：状态持续存在、有几何约束、流程很长。用通用 coding harness 让模型写 CAD 脚本当然能做，但模型的决策空间被"写代码"这个形式限定了。DeciCAD 做了一个领域原生的 harness，向模型暴露语义化的 CAD 动作、面向决策的观察、环境反馈和持久状态转移，然后从交互轨迹里抽取"因果决策监督"做 SFT，再做以几何结果为奖励的在线 RL。在 4 个 CAD 基准上它拿到最好的 F1 和 IoU，且模型输出 token 比通用 coding harness 少 45–88%；在监督数据相同的情况下，SFT 策略的 F1 从 0.6883 升到 0.7437 并超过 coding 策略，RL 又把几何可用率从 66.5% 提到 73.5%、F1 提到 0.7880。它的意义在于用对照实验说明：**harness 不只影响推理时表现，也决定了训练数据的形态和策略学习的效率**——设计 harness 和设计训练数据应该一起考虑。
🔗 链接：https://arxiv.org/abs/2610.21755 ｜ 代码：None

### Waypoint-OPD：蒸馏 RL 成果时，只搬"方向一致"的那部分
"策略偏移蒸馏"是把一个教师模型 RL 前后的 log 概率差当作监督信号，在学生自己生成的轨迹上训练学生，相当于把 RL 带来的"偏好变化"搬给学生。问题是只看 RL 终点的偏移，看不出这个变化在训练过程中是否一致——同样的终点偏移，可能是早期和后期的变化相互加强，也可能是相互抵消后的残余。Waypoint-OPD 拿同一次 RL 训练的一个中间 checkpoint 作为"路标"，在学生访问到的前缀上比较早期偏移和后期偏移的方向，方向一致就保留终点偏移，方向相反就抑制。和只用终点的方法相比，它只多一次冻结教师的打分。作者用 RL 训练过的 Qwen3-4B 教师，在 Qwen3-8B、14B 等学生上验证了效果。对工程实践而言，它提示**RL 的中间 checkpoint 本身就是有价值的数据资产**，保存下来可以用于后续蒸馏的去噪。
🔗 链接：https://arxiv.org/abs/2610.21601 ｜ 代码：None

### Reflection Beam 1.0：带"后训练配方"一起发布的 501B 开源 coding 模型
美国新实验室 Reflection 于 10 月 16 日发布首个开源权重模型 Beam 1.0：501B 总参数、23B 激活的 MoE，1M 上下文，Apache-2.0 协议，主打 coding 和 agent 任务，并提供 BF16 / FP8 / NVFP4 三种精度和一个 DFlash2 投机解码草稿模型。官方成绩显示 SWE-bench Verified 81.6%、SWE-Bench Pro v1 66.1%、Terminal-Bench 2.1 80.1%。对我们更有价值的是它的发布形态：自带一个开源的 Rust harness，并与 Hugging Face 一起给出可直接运行的后训练配方——用 TRL 做 LoRA SFT（单台 8×B300 约 1.9 万 token/s），用 Miles 做全参或 LoRA 的 GRPO（Megatron 训练、SGLang 生成 rollout，最低 32 张 H200）。这类"**模型 + harness + SFT/RL 配方**"一起开源的做法，降低了团队在大规模开源模型上自做领域后训练的门槛。
🔗 链接：https://huggingface.co/blog/reflection-beam ｜ 权重：https://huggingface.co/reflection/Beam-1.0-501B-A23B ｜ 官方：https://reflection.ai/blog/beam-is-available
