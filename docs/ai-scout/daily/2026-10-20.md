## 逐条讲解

### MetaCurate: Evolving Curation Filters for High-Quality Agentic Coding Data
用 agent 轨迹做 SFT 是提升 coding agent 最直接的办法，但"挑哪些轨迹来训"一直是个手工活：成功解决问题的轨迹可能绕了很多弯、调用了一堆没用的工具，失败的轨迹里反而可能有很有价值的中间步骤，于是各家都靠专家手写规则和打分表来过滤，而验证一套新规则好不好又要真的训一遍再评一遍，非常贵。MetaCurate 的思路是让"过滤器本身"自动进化：过滤器是一段可执行的程序（规则 + rubric + 聚合策略），它给轨迹打分；同时让 LLM judge 对轨迹做两两比较，凡是过滤器的排序和 judge 偏好不一致的地方，就作为有针对性的反馈去改写过滤器。关键工程点在于成对比较只在"搜索阶段"用，最终得到的过滤器可以独立给每条轨迹打分，所以上线成本很低。作者从一个空白过滤器起步，不写任何任务相关的手工标准，在自建的未筛轨迹池和 Nemotron v3 SWE 数据集上做受控 SFT 实验：MetaCurate 选出的数据训练后 SWE-Verified 均值最高，赢过手写规则过滤和随机选择，也赢过一个搜索成本是它 3.5 倍的"边训边评"基线。对我们来说，它把"数据清洗规则"从经验活变成了可搜索、可复现的工程产物，后训练数据团队完全可以把它当成过滤规则的自动调参器。
🔗 链接：https://arxiv.org/abs/2610.23134 ｜ 代码：None

### EnterpriseSynth: Zero-Execution SFT and Evaluation Data from OpenAPI Specs
训练会用工具的 agent 需要大量"调 API 的轨迹"，但企业内部 API 往往碰不得：有权限控制、合规约束、限流，还可能误改生产数据，所以真实执行采集几乎不可行。EnterpriseSynth 换了个角度——企业 API 几乎都有 OpenAPI 规范（一份描述每个接口、参数、类型的机器可读文档），那就**完全不调用 API**，只根据规范合成训练数据。它是一个四阶段管线：解析规范、生成用户意图、合成调用轨迹、静态校验；每条轨迹都要和原规范逐项核对端点、参数、类型和 schema，通过了才能入库，同时配套生成评测样本。作者还用"对抗精化"去锤炼校验器：故意往数据里埋 schema 错误，校验器检出率从 57–80% 提到 98%（44 个埋点抓到 43 个）。在 17 个真实/合成 API 上，用它的数据微调的小模型在未见过的 API 上稳定胜过未微调模型和 Self-Instruct 基线。最有价值的一个发现是：只看"选对端点"会严重高估能力（48.9%），把参数选择和取值也算进去后端到端正确率只有 21.3%——这提醒我们做工具调用评测时必须细到参数级。
🔗 链接：https://arxiv.org/abs/2610.22412 ｜ 代码：None

### OpenAI：Advancing Coding in Low-Resource Programming Languages（MultiLangBench）
COBOL、Fortran、Visual Basic 这类"低资源语言"在网上可学的代码和文档很少，模型普遍写不好，但它们恰恰撑着银行（COBOL 承担了大量 ATM 和刷卡交易）、气象和核安全分析等关键系统，企业客户反复反馈"模型在这些语言上不靠谱"。OpenAI 10-19 发文，配套做了两个评测：一个是开源的 MultiLangBench，要求模型用指定语言从零写一个兼容 SQLite 的数据库引擎；另一个是 COBOL 迁移评测，考察把老程序迁到别的语言时能否保持行为不变。MultiLangBench 的设计很巧：不同语言的实现没法用同一套单元测试，于是用"数据库文件"做统一接口——给程序一个初始库和一条 SQL，程序输出修改后的库，再用真 SQLite 3.40.1 跑校验查询比对结果；测试从 SQLite 官方 TCL 测试集转换而来（5.1 万条里转成了 2.4 万条），环境里必须清除所有 SQLite 痕迹、禁止联网，写错语言直接判 0 分，分数报告为（API 成本，通过率）二元组。结果上，GPT-6 Astra 在 20 种语言平均通过率 87.4%（GPT-5.6 Sol 仅 26.8%），COBOL 从 10.9% 涨到 72.1%；COBOL 迁移评测上 GPT-6.1 Sol 低推理档 86.6%、高推理档 97.9% 接近饱和。对评测工程最值得借鉴的是"用参考实现 + 共享产物格式做跨语言判分"和"成本与通过率同时报告"这两个设计。
🔗 链接：https://openai.com/index/low-resource-programming-languages ｜ 代码：https://github.com/openai/MultiLangBench

### Between Spoilers and Guesswork: Avoiding Over-Specification in Coding Benchmarks
仓库级 coding benchmark 有个老问题：很多 issue 描述太模糊（欠规格），模型只能瞎猜，甚至被逼去"背题"或钻评测空子。于是 SWE-bench Pro、FEA-bench、Doc2Feat-bench、Multi-SWE-bench 等都给题面补"提示"，但这些提示往往是从标准答案（ground truth patch）里推出来的。IBM 这篇论文指出，这样做会走向另一个极端——过规格，也就是"剧透"：提示里漏了答案信息，模型可以跳过 benchmark 本来想考的最难那一步，分数虚高，benchmark 也就更快饱和、"保质期"变短。作者在多个基准上系统地尝试了不同的规格化程度，试图在"剧透"和"瞎猜"之间找平衡点，并总结出构造"简约提示"（只给必要信息、不泄露实现）的技术建议，还会公开整理后的提示。对做评测集的人来说，这是一份很实用的检查清单：补题面时要先问"这句话是不是从答案里来的"，否则测到的就不是真实的问题定位和设计能力。
🔗 链接：https://arxiv.org/abs/2610.22760 ｜ 代码：https://github.com/IBM/swe-hints

### MLOps-Bench: Benchmarking AI Agents on Production ML Engineering in Real Repositories
现在大家越来越希望 agent 能维护线上的机器学习系统，但已有的 ML agent 基准大多是"打 Kaggle 比赛"式的建模实验，要么是通用的仓库 issue 修复，都没测到真实生产 ML 工程里的那些活：改数据管线、特征工程、训练、模型服务、监控、CI/CD 和治理。MLOps-Bench 从 31 个公开 ML 仓库里构造了 212 道经过验证的题，每道题都有自然语言需求、标准补丁、一个"看起来合理但有问题"的 buggy 基线、fail-to-pass 测试（修好才能过）和 pass-to-pass 测试（防止改坏原有功能），以及数据来源元信息，共 636 + 856 个测试。评测 6 个 agent 后，最强的也只解决 31.2% 的题，但能通过 68.7% 的测试——说明 agent 常常"做了一半"，却达不到生产要求的完整行为。它的价值在于把评测从"建模型 / 修 bug"推向"在已有系统里做全生命周期改动且不破坏原行为"，构造流程（buggy 基线 + 双向测试 + 溯源）也可以直接复用到其它垂直领域的 SWE 数据构造中。
🔗 链接：https://arxiv.org/abs/2610.23506 ｜ 代码：None

### Harness-Delta Attribution: Dissecting Gains From Harness Evolution
"harness 演化"——不改模型权重、只自动优化外围的 prompt、技能、工具和编排代码——是这几个月最热的方向之一，很多工作报告在搜索集上涨分明显。但涨的分里有多少是真本事？可能有相当一部分是对搜索集的过拟合，或者只是演化后的 harness 用了更多推理算力。这篇论文提出 HDA 评测协议，把一次演化带来的涨幅拆成三块：产物驱动的过拟合、能被测试时算力解释的部分、以及剩下的"可能可泛化的提升上限"。作者在数学、代码、创作和 agent 任务上对 11 个执行模型、3 个 harness 演化框架做了归因：在 21 个有显著涨分的设置里，平均 54% 的涨幅来自过拟合、14% 来自算力增加，有 14 个设置两者合计超过一半；而且搜索集上的提升经常迁移不到留出集，用验证集信号也挡不住过拟合。结合昨天收录的 Harness² 这类自优化框架看，这篇是一剂冷静剂：做 harness 优化时必须配留出集、控制算力预算，并按 HDA 的方式报告归因，否则很容易自我感动。
🔗 链接：https://arxiv.org/abs/2610.22466 ｜ 代码：None

### Self-HPO: Self-Evolving Coding Agents via Harness-Policy Optimization
coding agent 的表现由两部分共同决定：策略模型本身，以及它和环境交互的 harness。以往要么只调 harness（为某个模型版本调好的 harness 未必适合更新后的模型），要么只训模型（但模型能学到什么受限于固定 harness 能引出的轨迹）。Self-HPO 让两者交替进化：每一轮先让当前模型分析自己的失败案例、提出新的 harness 候选并选出最好的（H-step），再在选中的 harness 下用 RL 更新模型（P-step），训练中发现的难题又成为下一轮 harness 搜索的题集，保证 harness 优化始终瞄准模型最新的弱点。在三个 coding 基准上，它把 Qwen3.5-35B-A3B 的平均解决率从 57.8% 提到 64.8%，优于只调 harness 或只训模型的基线，且在分布外设置上也有效；有意思的是，两者联合的收益大于各自收益之和，换用 Opus 4.8 当 harness 提议者还能再涨。对后训练团队的启示是：RL 训练时的 harness 不该是固定"脚手架"，而应作为训练流程的一部分协同迭代。
🔗 链接：https://arxiv.org/abs/2610.22791 ｜ 代码：None

### WebCoder: Scaling General Frontend Development with Artifact-Grounded Agentic RL
真实的前端开发是"复现问题、生成、修改、修复"混在一起，在一个不断变化的项目状态上反复进行的，要用 RL 训出通用前端 agent，难点在于如何把五花八门的执行反馈变成和任务对齐的奖励，并在很长的动作序列里分配功劳。WebCoder 的核心想法是"以产物为锚"：不管 agent 在做哪类开发活动，都通过它对同一个可执行应用的影响、以及该应用满足需求的程度来评价。为此作者搭了 Webdev-World 环境，整合了代码编辑、应用运行、浏览器检查和按需技能，并在多轮交互间保留项目状态；独立的 verifier 检查最终应用给终局奖励，中间产物的进度变化则用来把优势值重新分配到各个开发片段上。工程上还用了上下文压缩和"消息树"样本构造，既能训超出单个上下文窗口的长轨迹，又避免对共享历史重复算损失。结果 WebCoder-27B 在自建的 Webdev-Bench 上把需求满足度从 64.8 提到 72.8，超过 Claude Opus 4.8（65.1）；在 Vision2Web 上从 41.1 提到 62.4。环境设计 + 产物级信用分配 + 长轨迹样本构造这一整套，是做长程 SWE RL 很好的参考实现。
🔗 链接：https://arxiv.org/abs/2610.23104 ｜ 代码：None

### TokenEconomizer: Experience-Driven Black-Box Cost Control for Coding Agents
前沿 coding agent 越来越贵，但现有的 token 效率评测都是"单个独立任务"，而真实开发者是在同一个大项目里连续做很多任务。作者把评测改成"在同一仓库上连续做一串真实任务"，发现 agent 会反复付出和环境相关的固定开销——比如每次都重新摸索构建命令、反复加载用不到的工具、在失败循环里打转。TokenEconomizer 是一个挂在 agent 外面的黑盒控制器，根据过往经验决定三件事：注入哪些操作层面的"微技能"（比如这个仓库该怎么跑测试）、裁掉哪些一直用不上的工具、何时打断无效的失败循环。在 Claude Code、Codex 和 GitHub Copilot CLI 搭配不同前沿模型的组合上，平均 token 成本降低 18.4–30.9%，任务成功率基本持平，而且每个仓库、每种组合都有节省；迁移到连续 Web 开发和安全审计场景也能降 6.4–21.2%。它不需要改 agent 内部，对已经大规模部署 coding agent 的团队是一个可以直接落地的降本思路，也提示成本评测应该改用"任务序列"而非孤立任务。
🔗 链接：https://arxiv.org/abs/2610.22732 ｜ 代码：None

### From Approval to Abuse: Privilege Escalation Attacks on Harness-Protected Coding Agents
coding agent 的 harness 通常靠"权限边界"来兜底提示注入：凡是越出沙箱的操作都要停下来问用户。为了减少反复确认带来的疲劳，用户可以批准 agent 提议的 allow-rule（允许规则），之后匹配规则的操作就不再询问。这篇论文发现这个机制本身成了新的攻击面：攻击者在仓库里埋入恶意上下文，就能诱导 agent 在执行日常任务时，提出一条"理由听起来很充分、但范围极宽"的允许规则；一旦用户点了同意，这条规则就会让 harness 实质"失明"，之后的恶意操作都不再触发人工审核。在 Claude Code 和 Codex CLI 等生产平台上，58% 的实验能成功诱导出目标规则，这些规则平均能覆盖 56.9% 的同类能力测试用例；在规则获批的前提下，81% 的案例实现了经验证的静默攻击。对做 harness 和 agent 平台的工程团队来说，这意味着"规则提议"也应视为不可信输出，需要做范围上限、来源标注和更细粒度的规则审查。
🔗 链接：https://arxiv.org/abs/2610.22987 ｜ 代码：None

### Lean4AgenticRL: Advancing Agentic RL with Verifiable Multi-level Process Rewards
大规模 agentic RL（用于 SWE 和终端任务）基本只看最终结果给奖励，很少对单次工具调用或工作流阶段给反馈，训练信号稀疏、效率低。Lean4AgenticRL 先为每类问题搭一个"问题特定的工作流"，在 agent 自主性和可控性之间取平衡；再把工作流用 Lean4（一种形式化证明语言）统一形式化，从而能在通用 harness 里自动验证 agent 的行为，产出工具调用级、阶段级、结果级三层奖励，并配合按阶段归一化的 GRPO 训练。训出的 LAR-27B 在 TerminalBench-2.1 上达到 77.3%，平均比基座高 9.89%。它的工程意义在于给"过程奖励怎么可验证地自动标注"提供了一条形式化路线，而不是依赖昂贵的人工步骤标注或不稳定的 LLM 打分。
🔗 链接：https://arxiv.org/abs/2610.22448 ｜ 代码：None

### Reward Engine: Reward-Centric Self-Evolution for Open-Ended Tool Agents
开放式工具任务（比如办公自动化）可以走很多不同的工具路径完成，质量又取决于交互过程、环境状态和最终产物，几乎没有现成的可执行标准答案来当奖励。Reward Engine 像一个先搞清"怎样才算做好"再动手的学生：从任务描述和初始几条轨迹出发，构造一个 RewardPack——其中测试用例检查必须正确的部分，rubric 给质量打分，每一项检查都会返回带证据的判断。RewardPack 构造完就冻结，保证优化过程中奖励不漂移，然后用它来引导 agent 修订和挑选输出，也可直接当 RL 奖励。在 WorkBuddy Bench Office 和 Claw-Eval 上，它与官方评分器在 82.3% / 80.5% 的候选对上排序一致；用于修订执行后，三次一致成功率（Pass^3）分别从 45.0% 提到 54.0%、78.4% 提到 83.7%。对"没有 verifier 的任务怎么造奖励"这个后训练老难题，它给了一个可复用的"测试 + rubric + 证据"打包方案。
🔗 链接：https://arxiv.org/abs/2610.22915 ｜ 代码：None

### Batched Contextual Reinforcement II: Does RLVR Need Long Rollout Windows?
RLVR（用可验证奖励做强化学习）通常要很长的 rollout 窗口，非常烧算力；可是简单缩短窗口又会出问题——如果每条回答都在给出答案前被截断，组内所有样本都是 0 分，相对优势就消失了。这篇工作提出 CCR：在一条限长的训练回答里同时放三道可独立验证的题，截断前做对的题照样拿分，而共享的长度预算会自然促使模型推理更简洁，不需要显式长度惩罚。在 4B/8B 数学推理模型上，用 8k 窗口的 CCR 对比 32k 窗口的单题 GRPO，每步训练 token 分别从约 97.5 万降到 17.5 万、79.4 万降到 16.6 万，节省 82.1% 和 79.1%，同时单题评测显示推理质量基本保持。这属于"训练流程结构设计"层面的降本技巧，改动小、易于在现有 RL 管线中试用。
🔗 链接：https://arxiv.org/abs/2610.22887 ｜ 代码：None

### TreeOPSD: Tree-Aware Posterior Distillation for Long-Horizon Agentic RL
长程 agent RL 有两个老问题：只有终局奖励时，每一轮决策的功劳很难分清、方差大；在同一批 rollout 上连续做多个 mini-batch 更新，策略会越跑越偏离采样时的策略。已有的解法要么需要价值网络、步骤标注，要么需要更强的外部 teacher，都增加了训练复杂度。TreeOPSD 把每一轮交互看成树节点，从共享前缀分叉出多条后续，把终局奖励递归回传得到隐式的轮次级信用；再把信用映射成一个有闭式解、有界的 teacher 分布，让学生策略去逼近它，这样既恢复了策略梯度方向，又给连续更新设了一个不会冲过头的有限目标。在 Deep Research 设置上，它让 Qwen3-30B-A3B-Thinking 比 GRPO 平均高 4.97 分，长程任务收益更明显。对 RL infra 来说，它的好处是不需要 critic 和外部 teacher，只要支持树状分支采样即可。
🔗 链接：https://arxiv.org/abs/2610.23181 ｜ 代码：None

### ReDiST: Student-Conditioned Trace Construction for Reasoning Distillation
做推理蒸馏时，一条"答案正确"的推理链不一定对某个具体的学生模型有教学价值——可能太跳跃、学生看不懂，或者中间内容不扎实。ReDiST 从学生模型自己的尝试出发：答案对的草稿，按给定证据修订得更扎实；答错的草稿，借助已验证答案的额外提示去修复。然后用一个"与学生能力匹配的阅读器"给原始和修改后的候选打分排序，标准是读完这条推理能否还原答案、对正确答案的概率有多高，选出最适合这个学生的版本来蒸馏，并加一个辅助答案损失平衡推理和答案监督。实验显示它在源任务和跨基准迁移上都优于只给答案、用原始推理链以及已有的筛选/改写基线。对 SFT 数据构造的启发是："数据好不好"要针对学生来判断，从学生自己的分布出发改写往往比直接用强模型的推理更有效。
🔗 链接：https://arxiv.org/abs/2610.23831 ｜ 代码：None

### SPLIT: Allocating Test-Time Compute under Imperfect Verifiers
"多采样 + 验证器挑最好"是提升模型和 agent 准确率的常用招数，但真实的验证器（单元测试、多数投票、LLM judge、奖励模型）会误收错答案、误拒对答案，而且错误还相互关联；在固定预算下采多少样、用哪几个模型、花多少钱在验证上，目前基本靠经验拍脑袋。SPLIT 推导出一个精确公式，给出在"接受/拒绝"和"取最高分"两种选择方式下提交正确答案的概率，同时考虑题目难度差异、多个模型共同的盲区和重复调用验证器的相关性；只需一个小的带标签 pilot 集，用经验贝叶斯拟合后就能为新任务规划预算。在数学、科学问答、代码和 SWE agent 等 7 个基准、26 个模型、175 个 agent 系统、6 类真实验证器上，它离事后最优配置只差 0.02–0.8 个百分点，而所有固定规则都在某些设置下至少亏 2.5 分。它还解释了"为什么加更多 LLM judge 反而会降低精度"，对设计评测和推理期验证管线都很有参考价值。
🔗 链接：https://arxiv.org/abs/2610.23255 ｜ 代码：None

9 月底到 10 月初，OpenRouter 上有个匿名模型 "Space Bunny" 连续 10 天使用量第一、处理了 56.7 万亿 token，开发者在不知道是谁家模型的情况下大量选用它。10-19 MiniMax 揭晓这正是 M3.1 Flash 的早期版本，并正式发布：定位为便宜、快速的 agent 与编程模型，价格为每百万输入/输出 token 0.15/0.60 美元，约为 M3 的 1/3，速度约 3 倍。官方自报 DeepSWE v1.1 73.7%、OSWorld V2 61.7、Agents' Last Exam 29.6，并表示 10-23 放出权重。结合上周 DeepSeek V4.1-Flash-1017，"低价开源 agent 模型"竞争加速，这对需要大量 rollout 的数据合成和 RL 训练来说意味着更低的教师/采样成本（以上分数均为厂商自报）。
