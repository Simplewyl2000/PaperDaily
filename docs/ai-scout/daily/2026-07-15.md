## 📝 逐条讲解

### AgentCheck：把 MCP 工具故障做成可复现、可干预、可验证的 agent workbench
现在很多 agent 评测默认工具都是可靠的：API 会返回最新数据，MCP server 不会超时，tool description 也不会被污染。真实部署里最麻烦的恰恰不是工具直接崩溃，而是工具返回了“看起来很正常但其实已经过期、错误或被污染”的结果，agent 还会很自信地继续执行。AgentCheck 把 MCP server 变成一个可控干预面：先让 agent 跑真实工具并记录每个 tool response，再用 12 类故障注入器重放同一轮任务，例如超时、stale value 或描述污染。系统会缓存匹配的工具调用，直到 agent 行为分叉后再回到真实工具，这样开发者能比较 clean run 和 faulted run 到底在哪一步偏离。它的验证不是只看 transcript，而是用 deterministic pass/fail 规则加上经人工标注校验过的 LLM judge。实验里 5 个 agent 的最好结果通过 105/120 个场景，最弱只有 77/120；最值得注意的是，失败往往是 silent confident misuse，而不是显式报错。对后训练软件工程来说，这类可复现故障注入能产出高质量负样本：同一个任务、同一个工具调用、同一个故障，只改变 mitigation，就能判断 agent 是否真的学会了恢复策略。
🔗 链接：https://arxiv.org/abs/2607.11098 ｜ 代码：https://github.com/aritra741/AgentCheck

### Rethinking MCP Security / MCPZoo：大规模运行时 MCP server 安全测量与 scanner 审计
MCP 生态增长太快以后，安全问题不再只是“某个 server 有漏洞”，而是我们连可运行的 server 全貌、真实工具面和 scanner 误报率都缺少系统测量。Rethinking MCP Security 构建了 MCPZoo，把静态仓库通过多 agent 框架转换、部署、诊断和修复成可交互 MCP services，用真实协议交互验证是否能动态分析。论文报告收集 113,927 个 MCP server，其中 64,611 个 unique，超过 37,288 个支持 dynamic analysis。这个规模重要，因为很多安全扫描器只在静态 README 或代码片段上判断风险，容易把“声明上危险”和“运行时真的可利用”混在一起。作者发现现有 scanner 报告 96.89% 的 server 有风险，但人工验证样本里真阳性不到一半，而且不同 scanner 输出明显不一致。它的工程价值是把 MCP security 从单点工具扫描推进到“可运行语料库 + 多 scanner 对比 + 人工校准 + 公开查询接口”。对 agent harness 团队来说，未来选择 MCP server 不能只看 star 和描述，还要看动态行为、工具 schema、运行依赖和扫描器可靠性。
🔗 链接：https://arxiv.org/abs/2607.11086 ｜ 代码：https://security.fudan.edu.cn/zoo

### SWE-Review：把 AI 生成 PR 变成 generate-review-revise 闭环
现在很多 coding agent 的交付方式仍然是“一次生成一个 PR”，然后把是否过测试当作主要验收结果。真实软件开发不会这样做：PR 需要 reviewer 读 issue、读 diff、跑上下文、指出风险，再让作者修改。SWE-Review 把这个环节做成 agentic code review：reviewer agent 会探索仓库和候选 PR，输出 approve/request-changes 决策，并给出结构化诊断，帮助后续 revision。它构造了 SWE-Review-Bench，包含来自 500 个 SWE-bench Verified issue 的 1,384 个候选 PR，覆盖高、中、低质量分布；还构造了 SWE-Review-Traj，包含 8,914 条 decision-correct review trajectories。论文用 Completion Rate、Decision Accuracy 和 Resolve Rate after Revision 三个指标衡量 reviewer 是否能写出可解析 review、是否能做正确合并决策、以及 review 是否真的提升最终修复。训练开放 reviewer 时，8B reviewer 的 completion rate 从约 4% 提到 71-84%，decision accuracy 到 67-72%，混合训练还能带来最高 10.6 个百分点的最终 resolve-rate gain。对后训练数据工程来说，这说明“审查轨迹”本身是一类高价值训练数据，它不仅能训练 reviewer，还能训练生成器如何响应结构化批评。
🔗 链接：https://arxiv.org/abs/2607.06065 ｜ 代码：https://github.com/SWE-Lego/SWE-Review

### ChainSWE：连续多 bug 维护 benchmark，测试 agent 累积状态管理
传统 SWE 类 benchmark 通常每次只给 agent 一个 issue，仓库重置到干净 base commit，任务结束后就丢弃这轮状态。真实维护工作却是连续的：今天修的补丁会成为明天修另一个 bug 的基底，前一个错误可能会污染后续修复。ChainSWE 专门把这个差距变成 benchmark：它从六个 SWE-bench-family 数据集中抽取同一仓库的时间顺序 bug，构成 100 条 chronological chains，总计 304 个任务、54 个 Python 项目。评测时，agent 在第 k 步只看到第 k 个 issue，但代码库状态已经包含前面步骤 agent 自己写下的补丁。这样它不只测“当前 bug 单独能不能修”，还测早期 patch 是否为后续 fix 留下了可用 substrate。论文报告随着 chain length 增加，性能可下降最高 70%，说明很多 agent 的失败来自累积状态和 chain errors，而不是单个 bug 本身太难。对后训练软件工程来说，这类数据比一次性 issue 更接近生产环境，尤其适合训练 agent 维护 long-lived branch、回滚错误补丁、做连续 regression 检查。
🔗 链接：https://arxiv.org/abs/2607.02606 ｜ 代码：https://huggingface.co/datasets/C-lister/ChainSWE

### What Makes a Good Bug Report for an AI Agent?：把 issue 模板变成 agent 任务规格工程
过去我们写 bug report 主要是给人类维护者读，所以强调复现步骤、栈追踪和自然语言解释。Coding agent 成为第一个读者后，问题变了：哪些信息真的能让 agent 更快定位、更少乱搜、更可能生成正确补丁？这篇研究在 433 个 SWE-bench Verified issue、87 个 repair agents、37,671 个 outcome 上建模 27 类 bug-report features，并在 SWE-bench Pro 上做 controlled ablation。结果显示，fix suggestions、reproduction scripts、source code pointers、localization info 都和更高修复概率相关，而更长、更散的报告反而可能降低成功率。更细的 ablation 说明，section headers、lists 这类结构变化本身也会影响 solve rate，即使文本内容没有被删掉。直观地说，agent 不只需要“更多信息”，还需要能机器解析、能缩小搜索空间、能直接转成验证动作的信息。对后训练软件工程来说，issue template 应该被当成 harness 的一部分：它定义任务规格、定位线索、expected behavior 和 verification target，而不是普通协作文档。未来用 GitHub issue 生成训练/评测任务时，report structure 也应进入元数据，否则很难解释成功率变化。
🔗 链接：https://arxiv.org/html/2607.07593v1 ｜ 代码：None

### Tool-Making and Self-Evolving LLM Agents：把重复 SOP 编译成版本化工具
生产 agent 的一个隐性成本是，它们会在每次请求里重新写同样的临时代码、重新查同样的 schema、重新实现同样的 SOP 步骤。Tool-Making and Self-Evolving LLM Agents 的做法是把这部分从推理时搬到部署前：tool-maker 收集执行轨迹，观察 live backend schema 和真实值，生成候选工具，再用 labeled cases 修复并验证。运行时，生产 agent 直接调用这些 validated、versioned tools，只有遇到工具覆盖不了的场景才 fallback 到 code generation。论文把系统部署到 fulfillment-center alarm-triage 场景，任务是按 44-node SOP 跨多个 metric backend 诊断告警。结果很工程化：工具调用让生产 p50 latency 降低 42%，在 1,500 个历史告警上把端到端错误率最高降低 53%，direct-call architecture 的 controlled ablation 又把 p50 latency 再降 62%。它真正值得关注的是“自演化”不是让 agent 任意改自己，而是把重复过程沉淀成可版本化、可审计、可回退的工具。对后训练方向来说，这类系统会产生很有价值的 tool-making 轨迹：哪些 SOP 节点值得编译、工具如何验证、fallback 何时触发、版本升级如何影响错误率。
🔗 链接：https://arxiv.org/abs/2607.08010 ｜ 代码：None

### How Do Practitioners Build SE Agents?：20 访谈 + 80 问卷揭示 eval-driven SE agent 开发
很多 SE agent 论文关注模型和 benchmark，但真正构建这类系统的团队每天面对的是需求、协调、评审、部署、权限和回归评测。How Do Practitioners Build SE Agents? 通过 20 个 practitioner 访谈和 80 个 practitioner 问卷，研究团队如何实际开发软件工程 agent。一个核心发现是，代码实现变便宜后，瓶颈没有消失，而是转移到了非编码工作：需求澄清、协调、review、deployment、output evaluation 和 provider-side model update 带来的行为漂移。论文总结出一个 seven-stage workflow，并指出团队正在转向 evaluation-driven development：评测不是上线前的最后一步，而是持续引导 agent、spec 和 workflow 迭代的控制面。它还强调 specifications 正在变成版本化 artifact，同时供人类和 agent 阅读，而不是一次性需求文档。对后训练软件工程来说，这说明高质量训练数据不能只来自“模型输出代码”，还要保存 spec 版本、eval case、review 反馈、部署约束和模型供应商更新前后的行为差异。它是经验研究，但对工程实践很有价值，因为它把 agent 系统开发从 prompt craft 拉回到了可测、可版本化的软件过程。
🔗 链接：https://arxiv.org/abs/2607.10856 ｜ 代码：None

### CuratorKIT：把 post-training 数据摄取、合成、过滤、恢复和导出串成可审计 pipeline
后训练数据工程经常被拆成许多脚本：一个脚本读原始文件，一个脚本去重，一个脚本合成样本，一个脚本打分过滤，最后再临时导出给 trainer。CuratorKIT 针对的就是这种碎片化：一旦样本被拒绝，很难知道是因为 PII、毒性、幻觉、格式不合格，还是 judge 误判；一旦 pipeline 改动，也很难复现过去训练集。论文把摄取、schema detection、pre-generation hygiene、LLM-powered generation、质量门、adaptive recovery 和训练格式导出放进同一个 configurable pipeline。它包含六类 source format readers、自动 schema 检测、credentials/PII/toxic 内容处理、八类生成任务、三类 quality gates，以及 provenance-exact hallucination verification。最关键的是每个样本都有 append-only provenance chain，被拒绝的样本也带 structured failure reasons，而不是静默消失。它支持 100+ LLM providers、Python API 和 YAML CLI，并导出 TRL、Unsloth、AlignTune 等训练格式。对本日报最核心的 Code LLM post-training 数据工程来说，这类工具的价值在于把“训练数据怎么来的、为什么留下、为什么删掉、能否恢复”变成可审计资产。
🔗 链接：https://arxiv.org/abs/2606.21631 ｜ 代码：None

### From Registry to Repository：29,450 个 SE skills 的复用、适配与维护实证研究
Agent skills 已经从少数 prompt 模板变成工程资产：它们包含 domain knowledge、工作流、脚本、恢复策略和工具调用约定。问题是，我们很少知道这些 skills 在公共 registry 和真实项目仓库里到底如何被写、复制、改造和维护。From Registry to Repository 挖掘了 skills.sh 中 18,463 个 registry skills，以及 5,876 个 GitHub 仓库里的 23,199 个 personal-use skills，并识别出 3,709 条 reuse linkages。作者用 SWEBOK 知识域对 29,450 个软件工程 skills 分类，并抽样分析 180 个 SKILL.md 的内容结构，再对 444 次更新做 qualitative coding。一个很重要的发现是，skill reuse 往往是一次性 copy：很多 local skills 近似原样保留，后续维护主要是 additive，把本地知识继续塞进去。更值得注意的是，skill 的 behavioral contract，也就是它如何监控状态、如何和用户交互、失败后如何恢复，通常很少被真正重构。对后训练和 skill management 来说，这提示我们 registry 工具不应只帮助下载 skills，还应帮助维护项目绑定、版本差异、行为契约和恢复逻辑，否则技能库会快速变成不可审计的文本堆。
🔗 链接：https://arxiv.org/abs/2607.00911 ｜ 代码：https://zenodo.org/records/21032973

### PatchFusion：用确定性 edit-atom evidence 融合多个 repair candidates
很多 coding-agent 评测用 pass@k 说明“生成 k 个候选里至少有一个能过”，但真实开发者最后只能合并一个 patch。PatchFusion 关注的就是 pass@k 到 pass@1 的落差：当候选池里有一些正确局部编辑，也有一些噪声和错误改动时，系统如何低成本地合成一个最终补丁。它不依赖测试结果或 LLM judge 来重新评判每个候选，而是把不同候选 diff 拆成 edit atoms，先根据 whole-diff agreement 找 repair neighborhood，再用 evidence-constrained fusion 保留重复出现且互相支持的编辑，剪掉孤立或缺少证据的部分。它构建 PatchFuseBench，覆盖 SWE-bench Verified、SWE-bench Multilingual 和 Defects4J 候选补丁。结果显示在 SWE-bench Verified 上解出 426/500，在 Multilingual 上 236/300，并在 Defects4J plausible patch 场景中达到 87/371，超过匹配的 selector。它的工程意义在于，多个 agent 或多次采样产生的 patch 不一定只能二选一，重复 edit evidence 可以成为一种可审计融合信号。对后训练数据工程来说，候选补丁池、共同 edit atoms 和被剪掉的噪声都值得保存，因为它们能训练模型理解哪些改动是稳定证据，哪些只是采样偶然性。
🔗 链接：https://arxiv.org/abs/2607.01597 ｜ 代码：None

### AReaL 2.0 / Agentic RL systems：把自演化 agent 落到在线 RL 数据协议与控制平面
很多 self-evolving agent 设想听起来像模型自动学习自己经验，但企业部署里的 agent 通常是静态的：模型权重、system prompt、工具列表和 harness 一旦上线，就只能靠人工收集数据、离线微调、改配置、再重新部署。Next-Generation Agentic RL Systems 认为瓶颈不在某个 RL 算法，而在缺少面向真实 agent 工作负载的在线 RL 系统。论文提出三根柱子：标准化 Agent Trajectory Data Protocol，用 step-level 事件承载学习信号；enterprise-grade agentic data proxy，把真实工作负载转成受治理的学习 substrate；以及 agent evolution control plane，根据轨迹统计决定是更新权重、改 memory、patch skill、改 harness、调整 tool schema、回滚还是不动。AReaL 2.0 是它的一个具体分支，把已有 RL 基础设施重组为 agent-service-oriented online loop。它按 Medium 收录，因为很多部分仍是系统愿景和原型，而不是完整生产验证。对本日报主题来说，它的价值在于把“轨迹数据怎么进入训练、谁决定何时演化、演化什么、怎么回滚”说成了工程接口，而不是泛泛谈持续学习。
🔗 链接：https://arxiv.org/abs/2607.01120 ｜ 代码：https://github.com/areal-project/AReaL

### Which Pairs to Compare for LLM Post-Training?：偏好数据标注预算的 pair selection 设计
偏好对齐常见流程是每个 prompt 生成少量 completions，然后让人标注其中的比较对。问题是，人类偏好标签很贵，而生成更多候选通常便宜得多，所以关键不一定是“标更多 prompt”，而是“从更大的候选池里挑哪些 pair 最值得标”。这篇论文把 comparison curation 建模为 sampling-design problem，并以 DPO 为例分析不同 pair selection 如何影响最终 policy performance。它给出的核心对象是 design-dependent information matrix，把标注分配、参数估计误差和 policy suboptimality 连起来。通俗地说，它试图让标注预算花在最能减少后训练不确定性的比较上，而不是随机挑两个回答。实验显示这种设计比常见启发式更 sample efficient。它按 Medium 收录，因为偏理论和偏通用 preference post-training，不是 coding-agent 专项；但它对轨迹筛选和 DPO 数据构造有间接价值。未来如果要对 agent 轨迹做偏好标注，也可以借鉴这种思路：先生成更丰富的成功/失败/近似成功轨迹池，再挑信息量最大的 pair 给人或 verifier 比较。
🔗 链接：https://arxiv.org/abs/2606.19607 ｜ 代码：None

### Forensic Trajectory Signatures：用轨迹签名检测 agent memory poisoning
Agent memory poisoning 的危险在于，恶意内容可能先进入记忆，再在很久之后通过看似正常的 recall 影响高权限动作。Forensic Trajectory Signatures 研究的不是单条 prompt injection 文本，而是攻击在整条轨迹中留下的行为签名。作者发现，在被评估架构里，成功 exfiltration 通常依赖 memory_recall_fact 到 email_send_email 这类转移，这不是偶然相关，而是攻击完成所需的信息检索依赖。一个简单规则就能捕捉很强信号，而使用 19 个 trajectory features 的 full-session forensic classifier AUC 达到 0.9904。更实用的是它还给出 prefix classifier，AUC 约 0.934，可以在线阻断明显攻击；full-session classifier 则用于事后审计和边界案例分析。它按 Medium 收录，因为不是 coding-specific，但它直接说明 agent 安全评测需要轨迹级特征，而不只是 prompt/response 分类。对后训练数据工程来说，memory recall、工具调用顺序、动作间依赖和 send 前后状态都应结构化保存，否则这类攻击只能事后靠人工猜测。
🔗 链接：https://arxiv.org/abs/2606.30566 ｜ 代码：None

## 🔥 社区热点专栏

### 🔥 大佬观点

**SWE-Review / SWE-Lego 社区：AI PR 不应停在“一次性生成”，reviewer agent 会成为训练与部署闭环的一部分。**  
SWE-Review 的核心信号是，agent 生成补丁之后还需要另一个 agent 像 reviewer 一样探索仓库、判断是否可合并、给出可执行诊断，再驱动 revision。这个观点值得注意，因为它把 code review 从人类 bottleneck 改造成可训练轨迹来源，同时也给生产系统一个可量化的 RRR 指标。🔗 https://arxiv.org/abs/2607.06065 ｜ https://github.com/SWE-Lego/SWE-Review

**MCP 安全社区：最危险的工具失败往往不是崩溃，而是 silent stale / poisoned output 被 agent 自信使用。**  
AgentCheck 和 MCPZoo 都把焦点放到运行时工具行为：前者做故障注入和 mitigation 复验，后者做大规模可运行 server 安全测量。这个趋势说明 MCP 评测不能只看 server 是否连得上、schema 是否写得漂亮，还要看真实 tool response 在错误、过期、污染和 scanner 误报场景下会怎样影响 agent。🔗 https://arxiv.org/abs/2607.11098 ｜ https://arxiv.org/abs/2607.11086

### ⭐ 超火仓库/项目

**modiqo/waggle：约 613 stars，07-08 创建，做 agent handoff 的 attributed artifact reference layer。**  
它火在解决多 agent 协作里“复制一大段上下文给下一个 agent”的老问题：用约 30-byte reference 指向可解析 artifact，而不是把证据粘进 transcript。真正的 insight 是，handoff 不应只靠总结，还要有可归因、可解析、可审计的引用对象。🔗 https://github.com/modiqo/waggle

**SmileLikeYe/agent-chief：约 619 stars，本地优先的 attention/interrupt layer。**  
它把每个 agent、alert 和 feed 都变成一个判断：现在是否值得打断人类。这个项目的痛点很真实，因为多 agent 工作台越来越吵，生产效率不只取决于 agent 能做什么，也取决于哪些事件能安全延后、哪些必须立刻升级给人。🔗 https://github.com/SmileLikeYe/agent-chief

**Archive228/loopkit：约 617 stars，33 个 battle-tested skills + minimal `.claude` harness。**  
它代表社区把 loop engineering 从文章变成可复制 skill bundle：把常见 coding-agent 循环、检查和项目约定打包给 Claude Code、Cursor、Codex、Gemini CLI 等使用。相比临时 prompt，它解决的是团队如何把可靠做法沉淀到可安装、可共享的 harness 配置中。🔗 https://github.com/Archive228/loopkit

**awdr74100/figwright：约 110 stars，双向 Figma MCP，把设计稿和代码生成/回写连成工具层。**  
它解决的不是单纯“从 Figma 生成代码”，而是让 agent 能读设计、生成框架感知代码，并把代码变化推回 canvas。这个方向对 Agent-Friendly Software 很关键：设计工具不再只是截图输入，而是可读、可写、可追踪的结构化协作面。🔗 https://github.com/awdr74100/figwright
