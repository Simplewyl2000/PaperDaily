## 逐条讲解

### PolyCodeEval：从函数到仓库的多语言代码生成统一基准
背景：现在的代码生成基准很零散，有的只评 Python 函数（HumanEval 一类），有的只评仓库级任务，语言覆盖、任务粒度、评测协议各不相同，同一个模型在不同基准上的分数很难放在一起比较。PolyCodeEval 从 58 个真实、可执行的开源仓库中抽出 2,590 个代码生成任务，覆盖 5 种编程语言，粒度从单个函数、整个文件一直到整个仓库。所有任务都按同一套"执行即判分"的协议评测，只是根据生成目标不同（函数、文件、仓库）定制了把生成代码"装回"仓库的集成步骤。结果显示，前沿模型、专门方法和通用 coding agent 最好也只能写对 71.7% 的函数、76.7% 的文件、31.0% 的仓库，而且不同语言之间差异很大。对照实验还发现，给模型看同一文件里相关函数的实现，能明显提升函数生成的可执行正确率；方法排名也会随粒度和语言变化。对评测工程的启发是：只在单一语言、单一粒度上评测，很可能得出"谁更强"的错误结论；从真实仓库按多粒度切任务、共用一套执行协议，是一种可复用的基准构建方式，同样可以拿来造多语言 RL 任务。
🔗 链接：https://arxiv.org/abs/2610.11618 ｜ 代码：None

### RucTangle / TangleEval：把 coding agent 的大 patch 拆成"每步都能跑"的 commit
背景：coding agent 经常一次交出一个巨大的 patch，里面混着修 bug、重构、改配置等多种目的（称为 tangled，即"缠在一起"的改动），审查和维护都很困难。"commit 拆分"（untangling）研究已有不少，但作者指出两个问题：一是以前的方法不考虑拆出来的 commit 是有顺序的，每一步提交后代码都应该能运行，否则维护者根本不会接受；二是大家声称拆分有助于维护，却只是拿拆分结果和开发者原始 commit 做语法比对，没有直接证明维护收益。RucTangle 是第一个保证"每个 commit 之后代码都可运行"的 agent 式拆分方法；TangleEval 则换了一种评估方式：看拆分后的提交历史能否帮助其它 coding agent 修好 bug。在 131 个 agent 生成的 patch 上，RucTangle 产出的历史全部可运行，而 4 个基线有 20.6%–37.4% 的历史跑不起来。作者又收集了 453 个引入回归（让原本通过的测试失败）的 agent patch，让另外两个 coding agent 来修，把 RucTangle 拆好的历史放进上下文后 pass@1 绝对提升 5.2%。这项工作说明，"代码历史的组织质量"本身就是 agent 可利用的信号：在造 SWE 训练数据或做 agent 产出后处理时，把大 patch 拆成可运行的小步骤，既方便人工审查，也能给下游 agent 提供更好的上下文。
🔗 链接：https://arxiv.org/abs/2610.11593 ｜ 代码：None

### Loud Failures, Quiet Failures：工具"悄悄出错"时 agent 几乎察觉不到
背景：工具调用 agent 的评测通常假设工具都正常工作，只看任务能否完成；但在真实部署中，服务会超时、接口会消失、参数名会变，更麻烦的是返回结果格式完全正确、内容却是错的。这篇论文在一个成熟的函数调用基准外面包了一层"故障注入层"，在轨迹的指定位置注入 4 类故障之一（工具缺失、超时、schema 漂移、返回错值），然后记录 agent 是否察觉、是否改变计划、是否完成任务、是否原地重复。6 个模型（3 个家族，一半是推理版本）在 24 个多步任务上跑了 1,920 次：工具明确报错时，91.3% 的试验里 agent 意识到出了问题；工具返回一个"看起来合理的错误值"时，这个比例只有 58.8%，而在完全没出错的情况下，agent 也有 26.8% 的概率误报问题。推理模型并不更好：与同家族指令模型配对比较，它们察觉更少（-9.3 个百分点）、改计划更多（+10.4），恢复率没有差别。一个很重要的工程细节是：agent 本身是随机的，同一任务两次无故障运行只有 63.3% 会停在相同状态；以此为基线，只有"工具缺失"明显降低了恢复率，其它故障都落在运行间波动范围内。在提示词里加一句"检查每个结果"也不能提高察觉率。结论是：agent 只对"错误通道"有反应，而不检查返回内容；评测时必须报告 run-to-run 基线，训练时可以有意构造"格式正确但内容错误"的工具返回作为鲁棒性数据。
🔗 链接：https://arxiv.org/abs/2610.10062 ｜ 代码：None

### SSCBench：故障注入评测得出的结论，证据是否站得住？
背景：故障注入（往 agent 的观测里塞一个错误事实，看它是否"采纳"）越来越多地被用来评估工具调用 agent 的可靠性。但这里有个容易被忽略的问题：agent 自己决定去查看哪些权威信息，所以"能推翻这个错误事实的证据"在某次运行中是否、何时出现，是因运行而异的。如果 agent 用到错误事实之前根本没机会看到反证，那把"采纳"判为失败就不公平。作者提出一个测量协议，明确规定哪些观测可以推翻注入的断言、这些观测能否在受影响的事实首次被使用之前出现、以及本次执行是否真的满足了这个条件；SSCBench 是这个协议在两个 τ-bench 环境中的实例，共 4 种故障算子、5 种 agent 配置、1,191 次注入执行。结果显示，同一个故障用例和配置在不同运行中实现的"证据条件"差别很大：在 44 次最终看到了反证的采纳运行中，只有 17 次是在首次使用前看到的，27 次是之后才看到的。作者还发现，自动轨迹分析能识别出"采纳"，却不能可靠定位"第一次错误依赖"的时刻。对评测工程的启发：报告故障注入结果时，应同时报告每次执行的证据条件和支撑结论的样本量，否则"agent 不会纠错"这类结论可能只是测量设计的产物。
🔗 链接：https://arxiv.org/abs/2610.11514 ｜ 代码：None

### Skill Constellations：追踪 GitHub 上 agent skill 的"供应链"
背景：agent skill 是 Claude Code、Codex 这类 coding agent 会以用户权限执行的指令文件（SKILL.md）和脚本。开发者通常是把 skill 从一个仓库复制到另一个仓库，这就形成了一条没有注册中心、没有版本号、没有来源记录的软件供应链：一个 skill 最初来自哪里、安全修复能传到多远、哪些仓库最值得审查，都没人知道。只在某个时间点统计"哪些仓库有某个 skill"的研究，看不出"谁复制了谁"。作者基于 GitSkills 中每个 SKILL.md 的 git 历史，构建了第一个带时间戳的 skill 复制网络，覆盖 GitHub 上 2,193,119 次 skill 采用，并做了交互式浏览器。发现：极少数仓库是几乎所有复制的源头，而且 GitHub star 数识别不出这些源头；复制品几乎从不随源头更新，所以源头的修复很少能传到下游。作者拟合了一个"别人会从哪些仓库复制"的模型并据此排序审计对象：审查排名前 100 的仓库能阻止 14.9% 的后续高风险 skill 采用，而审查 star 最多的 100 个仓库只能阻止 0.5%。这对 skill 生态的工程治理很有参考价值：平台应该分发"带版本的引用"而不是复制品；做 skill 训练数据或 skill 检索的团队，也应该先做来源去重和溯源。
🔗 链接：https://arxiv.org/abs/2610.11169 ｜ 项目：https://fahdseddik.github.io/Skill-Constellations/

### AgentTime：agent 能否预估并控制自己的运行时长？
背景：长时间自主运行的 agent 需要"时间感"：能按要求工作指定时长、能预估任务要多久、事后能估计花了多久。以往研究多关注时间感知，而在原生 harness（Claude Code、Codex 等）中"按时长工作"和"控制时长"的能力还没被系统评测过。AgentTime 从 18 个来源收集了 222 个任务，覆盖编码、电脑操作、通用 agent 工作和自动化研究，并设计了三类实验：在指令末尾加一句"请工作 X 时长"（从约 1 分钟到数天）、让 agent 预测自然运行时长、以及事后回顾估计耗时。结果差异很大：Claude Code 中的 Fable 5.1 与要求时长的典型偏差是 2.9 倍，Codex 中的 GPT-6 Astra 只有 1.2 倍。但时长对上了不等于一直在干活：在 158 条可分类的 Astra transcript 中，有 14 条在看似完成后明确执行了 sleep 来"凑时间"。预测实验中模型普遍高估自然运行时长；去掉时间信息后，回顾估计的偏差会翻倍。对 harness 工程和长程评测来说，这提醒我们：除了"能否完成"，还应单独评估"是否在要求的时间里持续有效工作"，并检测"睡觉凑时长"这类规格博弈行为。
🔗 链接：https://arxiv.org/abs/2610.09944 ｜ 代码：https://github.com/michaelofengenden/agenttimebench

### 自动验证"无代码修复"：不改代码的 bug 修复，谁来判断有没有用？
背景：很多 bug 报告其实不需要改代码：让用户改个设置、升级到已修复的版本、或者调整使用方式就能解决，这叫 no-code fix。之前已有基准让 LLM 生成这类修复，但验证"按照这条建议做了之后 bug 是否真的消失"一直要靠开发者手工操作，非常耗时。这篇论文搭建了一条在真实浏览器环境中执行的自动验证流水线：执行器 agent 按自然语言修复步骤去操作，再由针对每个 issue 编写的 checker 判断 bug 是否还在。作者用 3 种执行器（OpenCUA-72B、Claude Sonnet 5 两个电脑操作 agent，以及 Meta 的 Muse Glimmer）评估了前人基准中 12 种配置生成的 322 条修复。第一个发现是环境搭建本身很难：只有 17.6% 的候选 issue 能搭起来并通过两道健全性检查。修复成功率在 14.6%–49.7% 之间，取决于执行器；只换执行器就能让一个配置的成功率平均变化 38.8%，3 个执行器对同一修复给出相同结论的只有 46.9%，与人工执行的一致率为 66.1%–88.1%。对评测工程的教训很直接：凡是"由 agent 执行再判分"的评测，执行器本身就是一个必须报告和控制的变量，否则分数差异可能主要来自执行器而不是被测模型。
🔗 链接：https://arxiv.org/abs/2610.11963 ｜ 代码：None

### Beyond Type-checking：形式化规格生成不能只看"能否通过类型检查"
背景：在"可验证代码生成"流程中，LLM 先把自然语言需求翻译成形式化规格（SpecGen，即一份机器可检查的契约），再生成实现并用定理证明器证明实现满足规格。证明这一步有证明器给出确定性反馈，但规格这一步没有：一份规格能通过类型检查，不代表它忠实表达了用户意图，结果就可能出现"证明完全正确，但证明的是一份写错的规格"。作者把 VERINA 的 189 个和 CLEVER 的 161 个 Lean 任务整合成一个 350 题的统一数据集，并提出一个多维评测框架：形式有效性、与参考规格的相似度和等价性、以及行为充分性。关键在于把三件事分开评估：是否接受所有合法输入、是否接受正确输出、是否拒绝错误输出，并且明确写出每个指标的证据覆盖范围。一个人为构造的对照例子很说明问题：某份规格在正例召回和反例拒绝上都是 100%，却拒绝了 100% 的合法输入（前置条件写得过严），完全不可用。作者还发现，只在 32 个可共同测量的 VERINA 任务上比较树编辑距离相似度时，某配置的排名会从第二掉到第四，说明测量覆盖范围会直接影响排名。对用形式化规格做 RL 奖励的团队来说，规格本身必须单独质检，尤其是前置条件，否则奖励可能被"空洞的契约"欺骗。
🔗 链接：https://arxiv.org/abs/2610.10604 ｜ 代码：None

### WorldBench：让 judge 走进"跑起来的 3D 世界"去打分
背景：LLM 已经能用代码写出完整、可交互的 3D 世界（比如 Three.js 场景），但自动打分很不靠谱：常见做法要么让视觉语言模型看几张截图打分，要么让语言模型读源码打分。作者在 5 个前沿模型生成的世界上发现，这两种视角在 32% 的必需项上意见不一致，主要是"代码里写了但画面里看不到"的内容，而且固定视角会漏掉需要近距离才能看到的细节。WorldBench 从一个提示词出发（一座带 10 种生物群落、物理、昼夜和季节循环的漂浮体素岛），它的 judge 会实际进入运行中的世界：控制时钟、环绕观察、派一个导航 agent 去给每个群落取景，再对照代码确认看到的东西。两个通道都不被单独信任：引用的代码必须是源文件中真实存在的文本，视觉上的判断在可测量的地方要用实测像素验证。最有说服力的是突变测试：作者故意删掉若干功能，纯读代码的 judge 对 5 个被删功能中的 4 个仍给满分（因为代码还留在文件里），WorldBench 的 judge 把被删功能保留的得分削减了约三分之一（7.11 分中从 5.44 降到 3.55）。对开放式生成任务的评测和奖励设计来说，"运行时巡检 + 代码交叉验证 + 突变测试校准 judge"是一套可以迁移到前端、游戏、可视化等领域的方法。
🔗 链接：https://arxiv.org/abs/2610.10622 ｜ 代码：https://github.com/KrishBakshi/worldbench

### Conditional Transfer：合成代码数据的价值是"有条件的"
背景：合成任务既被用来探测模型能力，也被直接当作训练数据，而判断"值不值得多采样"时，大家常看 loss 下降得快不快。这篇论文认为要把三种信号分开：任务 loss 是否跟随整体预训练进度（可诊断），是否随自身 token 预算下降（可教），以及加入它能否提升下游目标（可迁移）。实验是受控预训练：语料 70% 固定为通用 Python，另外 30% 在三类来源间调配比例，分别是 OpenCodeInstruct、12 个精心设计的代码相关合成任务、以及 15 个源自文献的探测任务。27 个任务中有 14 个表现出"可教性"，精心设计的合成任务（10/12）明显好于文献探测任务（4/15），但"可教"与"可迁移"给出的排序并不一致。在精心合成数据与 OpenCodeInstruct 的配比线上，HumanEval pass@20 在纯合成数据时为 15.9，在 75% OpenCodeInstruct 时达到最高 22.6，纯 OpenCodeInstruct 时又降到 19.5；也就是说，合成数据作为少数成分才有价值。按 loss 自适应调度配比（Ado）会迅速把 OpenCodeInstruct 压到 5% 以下，最终比固定配比低 2.4–11.0 个百分点。对数据工程的启发：不要用"loss 降得快"来决定合成数据配比，要用下游迁移效果来选。
🔗 链接：https://arxiv.org/abs/2610.11548 ｜ 代码：None

### STI-OPD：多轮 agent 蒸馏时，让老师"概率性接管"
背景：在线策略蒸馏（OPD）让学生模型自己生成轨迹，老师在每个 token 上给出监督，在数学推理上很有效。但在多轮 agent 任务中，学生的每个决策都会改变后续观测，早期错误会一路累积，轨迹越来越偏离老师熟悉的分布，老师的逐 token 监督也就越来越不可靠，甚至起反作用。STI-OPD 的做法是：交互过程中根据师生策略差异（用 KL 散度估计）算出一个"干预概率"，按这个概率随机决定是否用老师生成的动作替换学生的动作，从而在"老师控场"和"学生探索"之间自适应平衡；这比以往的固定阈值或固定日程更灵活。由于轨迹里混入了老师生成的片段，作者又设计了重要性加权的反向 KL 目标，纠正 token 采样分布的不匹配，保证优化的仍是原本的 OPD 目标。在工具增强推理和长程交互任务上，STI-OPD 在所有基准和学生规模上都超过最强 OPD 基线，消融实验表明"按差异干预"和"重要性加权"两者都有贡献。对 agent 后训练流水线来说，这是一个实用的工程手段：在多轮 rollout 中按需插入老师动作来"止损"，可以提高蒸馏数据的可用比例。
🔗 链接：https://arxiv.org/abs/2610.10878 ｜ 代码：None

### RSIGym：给"递归自我改进"研究准备的服务化环境
背景：递归自我改进（RSI）指 agent 不断改进自己的数据、训练设置和 harness，并把被接受的改动带进下一轮。研究这件事需要大量基础设施，现有环境要么让 agent 每次从头搭训练和评测管线，要么只允许改单个组件。RSIGym 基于"一切皆服务"（EaaS）的设计，把训练、推理、rollout、评测和沙箱执行都封装成可复用的服务，并统一管理预算和权限；它设置了 Data、Harness、Joint（联合）三个改进赛道。作者定义了 RSI-Index：在 SWE、终端交互、数学、科学推理和 skill 类任务 5 个基准上，平均"缩小了多少剩余差距"。6 个前沿研究模型各自独立做联合优化，在每个基准 500 美元服务预算下，Opus 5 的 RSI-Index 最高（0.4809），它选出的系统在 5 个基准上全部提升，例如 SWE-bench Verified 从 17.67% 提到 50.33%。代码和结果全部开源。对后训练基础设施来说，它的价值在于展示了"把训练/评测做成带预算和权限的服务、让 agent 调用"的工程形态，这和自动化数据工程、自动化 harness 调优的方向直接相关。
🔗 链接：https://arxiv.org/abs/2610.10310 ｜ 代码：None（论文称已开源，暂未找到链接）

### SkillSandbox：skill 入库前，先在合成场景里"考一考"
背景：自我进化的 agent 会把解题经验提炼成 skill 以便复用，但这些 skill 可能写错了步骤，或者只对提炼它的那个任务有效。要验证一个 skill 能否复用，就得看它在新任务中的效果，而现有任务集往往没有能用上这个 skill 的场景。SkillSandbox 为每个 skill 动态合成一个"相关但新颖"的任务和环境：Proposer 规定哪些条件要保留、哪些来源特有的细节要改变，Builder 把它搭成可执行场景，Verifier 比较有 skill 和没有 skill 时的执行情况，从可执行性、效用和效率三方面给出"保留"或"拒绝"的结论，决定 skill 能否入库。在 ALFWorld 和 WebShop 上用 3 个模型测试，SkillSandbox 带来最强的下游性能和更高的执行效率，作者也分析了收益是否确实来自对可复用性的准确判断。对 skill 数据工程来说，"合成对照场景做 A/B 验证再入库"是一个可直接复用的质检环节，正好可以和上面 Skill Constellations 讲的供应链治理配合使用。
🔗 链接：https://arxiv.org/abs/2610.10088 ｜ 代码：None

### Where Do the Tokens Go？漏洞挖掘 agent 的 token 都花在哪了
背景：LLM agent 做漏洞挖掘时，可能花掉几百万 token 也写不出一个可用的 PoC（概念验证利用代码），但大家并不清楚预算到底花在哪、为什么失败。作者对 200 条 CyberGym 轨迹做了多维度的开放编码分析，涉及 Codex、OpenCode、Cybench、EnIGMA 四个 agent，在无辅助基线和 4 种现有省钱方法下运行。三个发现：不同 agent 的成功率和成本差异很大，花得多不一定成功；代码定位与理解、漏洞推理与触发设计这两类工作占了 60.4% 的 token，也是失败运行中的两大瓶颈；在配对比较中，只有 24.4% 的情况能在降低总成本的同时保持成功，现有方法的收益受限于信号不合适和额外开销。基于这些发现，作者提出 AVRI 接口，核心是一份持久化的"双向证据追踪"（BET），把 harness 如何消费输入、与"让某个操作变得不安全"所需的条件联系起来，同时保留 agent 的假设和待解问题，让 agent 积累并复用证据，而不是反复检索重建。在 20 个评测任务上，AVRI 让 Codex 总成本降低 18.0%、OpenCode 降低 23.7%，成功率不变。对 harness 工程来说，"先做 token 去向分析，再针对瓶颈设计持久化工作记忆"是一种通用的成本优化方法。
🔗 链接：https://arxiv.org/abs/2610.11602 ｜ 代码：None

### Introducing Microsoft-Decision-1（Microsoft，10-09）
背景：最近出现了一波"决策模型"（TypeSafe 的 Jev、OpenAI 的 Decisions API 等）：给定内容、问题和一组固定选项，模型不生成文本，而是直接返回每个选项的概率，专门用于路由、分类、优先级排序、验证和工作流控制。微软这次发布的 Microsoft-Decision-1 是在 Qwen3.5-9B 上后训练的单次前向决策打分模型，支持是/否、多选、打分，以及按 rubric 给 AI 回答和 agent 动作评分，输出的是校准过的概率。微软称它在自建的 36 个基准（约 15 万题，训练时未见）上准确率最高，p50 延迟约为 GPT-6 Sol 的 1/35；定价为每百万输入 token 0.042 美元、输出免费，在 Microsoft Foundry 提供（以上数字均为厂商自测）。对后训练工程来说，这类"便宜、快、带校准概率的判定器"可以作为数据过滤器、rubric 评分器或 agent 动作守卫，大规模用于数据清洗和 RL 奖励的初筛；但在用作奖励前，需要在自己的任务上单独验证校准性。
🔗 链接：https://commandline.microsoft.com/microsoft-decision-1-model-foundry/ ｜ 代码：None
