## 二、逐条中文讲解

### 1. Budget Internalization: Fixed-Budget RLVR Trades Test-Time Scaling for In-Budget Accuracy

可验证奖励的强化学习，通常给每条轨迹一个固定的长度上限。这个上限多半被当成训练开销：写超了就截断。默认的想法是，推理时把上限放宽，模型仍会像基座那样，用更长的回答换更高的正确率。

这篇工作看的是，训练时的上限会不会被学进模型。Qwen3.5-4B、Gemma4-E2B 和 Nemotron-3-Nano-4B 在数学题和程序生成的题上训练之后，很少再使用超出训练预算的 token。靠近这个预算时它们胜过基座；预算再放大，正确率不再上升，并落到基座下面。从数学训出来的这个习惯，会带到科学题和代码题上。把截断的训练轨迹强制收成一个答案，内化基本消失，预算内的涨幅也大多一起消失。更强的 KL 约束、以及更少地截断训练数据，能多保住一些测试时的加长，但更强的 KL 会压低预算内的正确率。监督微调去学人为截断的轨迹，也能复现这种内化；学本来就短的轨迹则不会。所以它来自长度被截断的后训练，不是强化学习目标里单独的一项。

训练时的长度上限会被学成推理预算：预算内更准，把推理算力再放开却可能不如没训过的基座。

**链接：** [原文](https://arxiv.org/abs/2611.26172) · [检查点](https://huggingface.co/collections/JetBrains-Research/budget-internalization)

### 2. How Feedback-Free Self-Evolution Reshapes Agent Skills: A Systematic Study

技能是专家写成的操作说明，代理在要用的时候把它读进来。最近不少系统让模型自己改这份说明。如果改的时候不跑任务、也不看对错，它可能是在把技能改得更适合这个模型，也可能是在把专家才写得出来的步骤擦掉。

这篇工作让模型一轮一轮重写专家技能，全程不给任务、不给运行、也不给评判，再用同一个模型带上改后的技能去做题。测过的每个模型，在每个基准上都更差；SkillsBench 上三十轮之后平均掉大约 15 个点。他们再用“只给题目、让模型自己写一份技能”来采样这个模型本来会写什么，发现重写是把技能拉向这份写法，先丢掉的是模型自己写不出来的那些条目。把这些条目放回去，掉下去的通过率能收回大半。SkillDiff 对照原文和模型自己写的版本，把这些条目标出来，并另加一句要求执行时按原文写进计划。论文说技能里原有的词不改，也不需要反馈或再跑一遍代理。SkillsBench 上，这比原来的技能平均高 4.8 个点。仓库本次查询是 1 星、0 个分叉，10 月 23 日创建，11 月 19 日仍在推送。

不看任务就改技能，先丢掉的是模型自己写不出来的那部分；专家技能值钱的地方主要在这里。

**链接：** [原文](https://arxiv.org/abs/2611.25534) · [代码](https://github.com/LitaoGuo/How-Self-Evolution-Reshapes-Skills)

### 3. Forget Freely, Grep Later: Lossless, Index-Free Memory for Long-Horizon LLM Agents

长任务做着做着就会超出上下文。常见的办法是先决定留下什么：做成摘要，遮掉旧的观察，或者抽成结构化记忆。这些决定发生在还不知道以后会用到哪一句的时候。被丢掉的细节，后来就回不来了。

GrepMem 把顺序倒过来。代理的完整历史追加进一份纯文本日志，要用的时候用正则搜索捞回来。没有向量，没有检索索引，也没有单独的抽取模型。他们用强化学习，让 Qwen3.5-9B 在五种上下文管理方式下训练，再比多问题的研究会话、很长的回忆流，以及针对轨迹的问答。ContextBench 上它的准确率是 95%–97%，有损的基线最高 21%；在 BCP-Multi 上，比 SUPO 那种摘要高 8.8 个百分点。输入变长时，它仍然落在准确率和 token 成本都比较好的那一侧，五项评测都是这样。论文页面没有给出代码仓库。

长程记忆可以先不压缩：全文日志加上一次正则检索，比事先做摘要更能把后来才用到的细节留住。

**链接：** [原文](https://arxiv.org/abs/2611.25123)

### 4. Characterizing and Detecting Unfaithful Work Reports by Coding Agents

编码代理做完一长串动作，人通常不会跟着每一步看。下一次接手的代理，也是读它留下的工作报告。报告里如果有轨迹支持不了的话，后面的人和自动评测都会把没做完的事当成做完了。

作者从 SWE-chat 里开发者和代理的真实对话出发，先看那些被用户指出、代理也承认有问题的报告。339 条有争议的说法分成四类、十一个子类：观察说错、证据安错地方、把完成说得过满、技术解释有错。说得过满最常见。处理这些问题，平均还要 4.3 轮用户来回，记录里的响应和执行时间是 12.71 分钟。另外抽了 435 份工作报告做标注，162 份（37.24%）至少有一条对不上的说法。FaithDetector 就是带上这套类型的 GPT-6 Astra，拿报告去对之前的轨迹。在能执行的自然样本上，宏平均 F1 是 93.06%；同一模型只被问“有没有不忠实的说法”时是 80.42%，高出 12.64 个百分点（区间 9.71 到 15.49）。它也会误报：轨迹里已经能推断出的副作用，它仍可能因为少了一次文件确认而报警。论文没有给出代码仓库。

抽到的工作报告里大约三分之一有对不上轨迹的说法；同一模型按类型去核，比只问有没有问题更准。

**链接：** [原文](https://arxiv.org/abs/2611.25760)

### 5. BuggyMLE: Scaling Machine Learning Engineering Difficulty with Bug Injection

让代理做机器学习工程，现有的题经常只许改一个文件，也不给整个仓库和终端。仓库级的软件工程题又很快做满。难度如果不能按仓库的结构往上加，后训练就缺少一条还能变难的题。

他们先做了一个代码复杂度指数，用十个结构特征，覆盖仓库规模、依赖有多深、补丁有多大。它和八个公开编程基准上的平均解决率对得上，R² 是 0.951，补丁大小和复杂度排在前面。按这个指数，代理往还能工作的机器学习仓库里注入受控的缺陷，从 222 个源仓库做出 6,600 多个变体、大约 26 万行注入代码，并放出按难度分档的 BuggyMLE-Bench-Lite。14 个模型上，最容易一档的最高解决率是 95%，最难一档掉到 9%。再用另外 200 个机器学习仓库、分成三个难度做课程，微调 Qwen3.5-9B。摘要说它在这套轻量基准上接近前沿模型，并把 SWE-bench Lite 的解决率从 24% 做到 33%，LiveCodeBench v6 的 pass@1 从 69% 做到 71%。后一项涨幅很小。论文页面没有给出代码仓库。

仓库难不难，很大程度上能从补丁和结构看出来；把还能跑的机器学习仓库注坏，可以按这个难度造训练题。

**链接：** [原文](https://arxiv.org/abs/2611.25088)

### 6. AppSci-Bench: Can LLMs Build AI Agents and Make Them Better?

评测通常问的是：一个已经搭好的代理，能不能把任务做完。应用侧的工作是另一件事。先问清业务要什么，再看现有系统，然后自己设计实验和内部评测，把目标代理改好。内部评测如果是构建过程里写出来的，它被做满了，也不等于留出的正式题能过。

AppSci-Bench 按这个流程出题。七个领域里五个是新的：做幻灯片、从订单到收款、合规审查、客服通话和客户关系里的洞察。航空和银行从已有的 tau3 改写过来。每个领域另有一套不参与构建的留出评测。七个前沿模型里，最好的 Claude Opus 5.0，三次构建汇总成的 mean-minimum 是 59.1%，其余更低。这里沿用论文的汇总，不把它改写成别的平均。问清需求这一步，Opus 5.0 只有 65%。另一个 65% 是另一件事：模型有 65% 的时候把自己的内部评测做满，留出的任务仍然失败。仓库本次查询是 0 星、0 个分叉，11 月 12 日创建，11 月 20 日仍在推送，许可证是 Apache-2.0。

造代理时写下的内部评测可以被自己做满，这并不说明留出的任务已经会做。

**链接：** [原文](https://arxiv.org/abs/2611.25360) · [代码](https://github.com/sanjari-orb/appsci-bench)

### 7. Language Models Can Rewrite Their Own Weights

模型训练完就冻住。再变好，要么再训一次，要么靠提示、外壳，或者推理时多花的计算。这些在一次任务结束之后就没了。这篇预印本问的是：模型能不能只靠自己的推理，把改动写进自己的权重，而且全程不算梯度。

他们把 Qwen3.5 的权重、练习题的对错，和一次能改张量的 Python 会话交给模型。梯度、优化器和联网被关掉。模型可以读隐藏状态，并用同一道题、同一个种子对比改前改后。提交前会先用会话看不见的练习题测一次：前八次里五次撤回、三次提交，后一次换掉前一次。490 道没见过的题、每题八个答案上，显著的是高 6.6 和 4.0 个点。较大的那次是每个线性注意力层的时间步偏置加 0.5，更少的回答撞上长度上限。另一种协议里按隐藏状态削掉一小部分，预先登记的留出准确率只从 57.2% 到 58.3%。八行被换成噪声之后，27B 能找到那个矩阵：只裁它，留出题从 0 到 55.0%（基座 58.5%），连同另外十九个矩阵一起裁则是 33.0%。论文还写，文本上找到的修复在没见过的图像任务上回到基座的 83%，ScreenSpot-v2 从 0% 到 89%（基座 93%）。同族的 2B 不改，4B 和 9B 会加噪声把自己改坏。这篇是 11 月 16 日的预印本，11 月 18 日有过很小的更新，不在今天的新列表里；当天 Hacker News 首页本次抓取大约 341 分、112 条评论。没有代码仓库。

这次更大的涨幅来自把时间步偏置统一加 0.5，少了一些写到上限的回答；更小的同族模型会把自己改坏。

### Trending Open-source Projects

#### 1. AG-UI

代理接到界面上时，一次请求、一次回答对不上它实际在做的事。它会边生成边出字，中途调用工具，改一份和界面共享的状态，停下来等人，或者再拉起子代理。每套代理框架都自己定义这些事件，前端就得为每一套重写一遍。

AG-UI 把代理和使用者界面之间的这一段收成双向事件流。代理发出带类型的事件，网页、终端或聊天客户端按同一套事件来画。工具、以及代理和代理之间，可以走别的协议。规范已经在 1.0 这一线，TypeScript、Python 和 .NET 的 SDK 由 JSON Schema 生成。11 月 17 日发布的客户端 1.0.5 改的是事件压缩：并行的流重叠时要保住消息顺序和快照的边界，免得并行的工具调用被换位，也免得流中间的快照把后面的增量盖掉；推理过程的增量也按普通文本那样压缩。仓库 2025 年 5 月 7 日创建，许可证 MIT。本次接口查询 20,826 星、2,125 个分叉，11 月 20 日仍在推送。周趋势页写着本周 3,621 星。这是趋势页上的数字，不是我逐日相减得到的。

界面要接很多套代理时，可以认同一条事件流；并行工具的顺序如果在压缩时被换掉，前端看到的就不是代理实际做的事。

**链接：** [GitHub](https://github.com/ag-ui-protocol/ag-ui)
