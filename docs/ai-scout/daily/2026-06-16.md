## 📝 逐条讲解

### HarnessX：可组合、可适配、可演化的 agent harness foundry
过去的 harness 多半是手工搭出来的：prompt、工具、memory、retry、权限和 evaluator 混在一起，改一个地方就可能影响另一块，而且跨任务复用往往变成复制粘贴。HarnessX 试图把 harness 变成一等工程对象，而不是某个 agent 项目里的隐藏脚手架。它把上下文、工具、技能、控制、记忆等能力拆成 typed processors，并用 substitution algebra 在明确的 lifecycle hook 上插入、替换或删除组件。更重要的是，它引入 AEGIS 这个 trace-driven multi-agent evolution engine：先读执行轨迹，压缩失败证据，再规划 harness 改动、生成候选、用 critic 和确定性 gate 接受或拒绝。实验覆盖 ALFWorld、GAIA、WebShop、tau^3-Bench 和 SWE-bench Verified，报告平均 +14.5% 提升，弱基线场景最高 +44.0%。它还把轨迹同时作为 harness 更新和模型训练信号，提出 harness-model co-evolution，比单纯调 prompt 或单纯训模型更接近真实后训练系统。对后训练软件工程的启发是：harness 也需要模块化、版本化、可演化和可回归，而不是每个团队用 markdown 和脚本手工积累经验。
🔗 链接：https://arxiv.org/abs/2606.14249 ｜ 代码：https://github.com/Darwin-Agent/HarnessX

### HarnessBridge：把 harness 控制器训练成双向投影策略
长程 agent 的一个核心痛点是，模型看到的上下文越来越脏，环境收到的动作也可能越来越偏：旧错误、无关日志、过时假设会挤占窗口，重复命令和无效操作会浪费环境步数。HarnessBridge 把 harness 看成 agent 和环境之间的可学习控制器，而不是人工写死的规则集合。它学习两类投影：observation projection 负责把原始轨迹压缩成对决策有用的状态，action projection 负责把模型提出的动作变成可执行转移，或者给出带证据的拒绝反馈。这个设计有点像在模型和 shell/仓库之间放了一个训练过的“交通警察”：它既帮模型看清当前真正重要的东西，也阻止它把已被证伪的动作继续提交给环境。论文称其通过 unified instruction tuning 训练，在 Terminal-Bench 2.0 和 SWE-bench Verified 上能匹配或超过强专用 harness，同时减少 token 和轨迹长度。它的工程价值不在某个 benchmark 分数，而在把“上下文压缩、动作校验、loop 防抖”从手写 middleware 推向可训练模块。对后训练团队来说，这提示 harness supervision dataset 可能成为新的数据资产类型：不是训练模型直接答题，而是训练运行时接口如何筛信息、拦动作、给反馈。
🔗 链接：https://arxiv.org/abs/2606.12882 ｜ 代码：https://github.com/mandyyyyii/HarnessBridge

### LangChain Deep Agents：同模型仅改 harness，Terminal-Bench 52.8→66.5
这篇 LangChain 工程博客很适合当作 harness engineering 的实战案例，因为它故意固定模型 `gpt-5.2-codex`，只改 agent 外围系统。团队先用 LangSmith traces 找失败模式，再把 trace analysis 做成一个 Agent Skill：拉取实验轨迹、并行派分析 agent 看错误、最后把建议汇总成人可审查的 harness 改动。真正带来提升的不是一个神奇 prompt，而是一组机制：PreCompletionChecklistMiddleware 在 agent 想结束时强制做验证，LocalContextMiddleware 在启动时注入目录和工具上下文，LoopDetectionMiddleware 发现同文件反复编辑时提醒重新审视方案。它还强调 time budget 和 reasoning budget 的工程权衡，单纯开最高 reasoning 反而会因为超时而降分，最终用 planning/verification 更高、implementation 适中的“reasoning sandwich”。结果上，deepagents-cli 在 Terminal-Bench 2.0 从 52.8 提到 66.5，进入 Top 5，且代码开源在 Deep Agents 项目中。对后训练软件工程来说，这类博客的价值是把“轨迹 → 失败分类 → harness 改动 → 回归评测”的闭环讲清楚，能直接迁移到内部 coding-agent 评测和训练数据飞轮。
🔗 链接：https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering ｜ 代码：https://github.com/langchain-ai/deepagents

### AgentLens：识别 SWE-agent 评测里的 Lucky Pass
现在很多 SWE-agent 评测只问最终 patch 是否通过测试，但一个 agent 可能靠混乱试错、盲目重试或偶然撞对接口通过，这种成功不应该和清晰、可维护、可复现的成功等价。AgentLens 把这个问题命名为 Lucky Pass，并把评测从 outcome-only 推到 process-aware。它分析了 2,614 条 OpenHands 轨迹，从 60 个 SWE-bench Verified 任务中筛出 47 个有足够 passing trajectories 的任务，构成 1,815 条带过程标注的评测子集。方法上，它用 Prefix Tree Acceptor 合并多个正确解路径，形成任务级“合理过程空间”，再用 context-sensitive intent labeler 把动作按历史语境分成探索、实现、验证和编排。结果显示，在成功轨迹里有 10.7% 属于 Lucky Pass，不同模型后端 Lucky rate 从 0.5% 到 23.2% 不等，按质量分排序时有些模型名次会移动多达 5 位。它对评测反作弊和后训练很关键：如果 RL 只奖励最终 pass，就会鼓励脆弱过程；如果 reward 也看轨迹质量，就能减少盲试、漏验证和时序错乱。对工程团队来说，AgentLens 提供了把“通过但过程很差”量化出来的模板。
🔗 链接：https://www.microsoft.com/en-us/research/publication/agentlens-revealing-the-lucky-pass-problem-in-swe-agent-evaluation/ ｜ 代码：https://github.com/microsoft/code-agent-state-trajectories/

### Curation-Bench：让 generalist coding agent 自动迭代数据筛选策略
训练数据整理是后训练里最耗人力、也最影响最终效果的环节：研究者要提出数据策略、写过滤/采样代码、跑训练和评测、根据 noisy feedback 再改策略。Curation-Bench 问的是，通用 coding agent 能不能把这个数据整理循环自动化。它固定模型、训练 recipe 和 eval suite，只给 agent 命令行入口，让它检查数据、实现 data policy、提交到训练/评测流水线，再按结果继续迭代。一个重要发现是 execution-research gap：现有 agent 能把一个局部策略越调越细，却不太会主动探索新的策略家族，即便给了论文和策略指南也容易只做小改。作者加入 scaffold，要求每轮引用、实例化并改造已有方法后，agent 才明显转向 method-guided exploration，最终用十分之一数据预算组合出超过强 published baseline 的数据选择策略。它正中本日报最核心的“后训练数据工程”方向，因为它把数据 policy search 变成可运行、可评测、可追踪的 agent 任务。对落地团队来说，真正要学的不是让 agent 自由发挥，而是给它固定训练管线、方法引用约束、评测反馈和策略版本管理。
🔗 链接：https://arxiv.org/abs/2606.04261 ｜ 代码：None

### Google Gemini Managed Agents / Antigravity API：托管 agent harness + 沙箱
很多团队想把 agent 放进产品，但一上来就要解决沙箱、文件系统、工具执行、长会话、context compaction 和版本化配置，基础设施成本很高。Google 的 Gemini Managed Agents 把这层托管起来：通过 Interactions API 调用 Antigravity agent，就能在 Google 托管的隔离 Linux sandbox 中执行代码、管理文件、搜索网页和持续多轮工作。它还把 agent 行为配置放进 AGENTS.md 和 SKILL.md，并支持保存为 versioned managed agent，这说明大厂正在把“agent harness”产品化为 API 原语。文档里一个很工程的细节是 context compaction：长会话在约 135k tokens 触发自动压缩，避免工具结果和文件内容持续膨胀导致上下文腐烂。Quickstart 还要求保存 `interaction.id` 和 `environment_id`，让后续请求延续同一 sandbox 状态，这比单次 chat completion 更像真实 runtime。它的风险也很明显：托管沙箱隐藏了很多执行细节，团队仍需要审计网络、持久性、文件下载、日志和权限边界。对 Agent-Friendly Software 来说，这是“把本地 CLI agent 能力变成可调用托管 runtime”的重要官方信号。
🔗 链接：https://blog.google/innovation-and-ai/technology/developers-tools/managed-agents-gemini-api/ ｜ 代码：https://ai.google.dev/gemini-api/docs/antigravity-agent

### Claude Code v2.1.172：Sub-agents 可递归 spawn 到 5 层
Claude Code 之前的 sub-agent 结构基本是扁平的：主 agent 可以派子 agent，但子 agent 再派子 agent 会被限制，这能防 runaway，也限制了复杂任务的层次化分解。v2.1.172 的 release 改成允许 sub-agents spawn 自己的 sub-agents，最多 5 层，并修复了 nested child 停止后 background sub-agent 仍显示 active 的问题。Boris Cherny 在社区说明里把动机说成“agents kicking off agents as a way to better manage context”，也就是把大任务拆成隔离上下文的小任务，再把摘要向上返回。这个能力对长程 coding、代码库迁移、并行排查和多层 review 很有吸引力，因为每个子层可以只保留自己需要的局部证据。它也带来新的安全和成本问题：如果 sub-agent YAML 没有限制 Agent 工具或可用子 agent，旧配置可能突然拥有更宽的递归能力；深度越高，token、权限和审计链越难追。工程上最好的用法不是追求 5 层深，而是浅层、显式、带 budget 和 allowlist 的结构化 delegation。对 harness engineering 来说，这标志着 subagent runtime 正从“平行助手”走向“有栈深限制的递归控制结构”。
🔗 链接：https://github.com/anthropics/claude-code/releases/tag/v2.1.172 ｜ 代码：https://github.com/anthropics/claude-code

### SPOQ：用 DAG wave dispatch + 双验证门控编排多 agent 软件工程
多 agent 软件工程常被说成“像一个虚拟团队”，但如果任务依赖关系没建清楚，就会变成串行等待、重复实现和后期返工。SPOQ 的核心是把项目拆成有依赖的 DAG，再用 topological dispatch 找出可以并行执行的 wave：同一 wave 中互不依赖的任务并发跑，wave 之间按依赖顺序推进。它还加入双验证门控：执行前用 10 个 planning metrics 检查计划质量，执行后用 10 个 code metrics 检查代码质量，并要求达到阈值才进入下一步。Human-as-Agent 是另一个务实设计，人类不是最后才 review，而是可以参与拆解、验证计划，并在执行中被 agent 咨询。论文报告在真实 2-slot LLM backend 上稳定 1.4x 加速，在结构化 planning 中覆盖率提升到 99.75，双验证把缺陷从 0.34 降到 0.20，人类参与后残余缺陷降到 0.03。它还给出 17 个仓库、8,589 commits、1,822 tasks 和 13,866 tests 的纵向部署研究，虽然仍需外部复现，但比纯 demo 更接近生产。对 agent 系统工程来说，SPOQ 的价值在于把多 agent 编排落到 DAG、wave、门控、角色层级和人类接口这些可实现的控制面上。
🔗 链接：https://arxiv.org/abs/2606.03115 ｜ 代码：https://gitlab.com/kenth56/spoq

### Ada / SWE Agent Mindset：用 408 条轨迹观察 agent 如何理解代码库
很多 coding-agent 论文只关心最终有没有修好 bug，但开发者真正想知道的是：agent 在动手前有没有理解仓库，它看了哪些证据，什么时候决定“够了”，以及这种停止判断是否可靠。Ada 这篇工作把代码理解阶段当成可观察对象，而不是把它淹没在最终 patch 分数里。作者构造了一个 bounded-yet-wild 的环境，让 SWE agent 在真实代码库中通过有限工具自由探索，同时把每一步导航、证据选择、整合和停止记录成轨迹。然后他们设计 observation lenses，把 408 条 think-action chains 投影成可比较的行为视图，避免只数 tool calls，也避免过度臆测模型内心。研究还用不同 prompt framing 和 coach-judge 条件看外部干预能在多大程度上改变 agent 的探索方式。它不是一个直接提升分数的系统，但它提供了评测工程需要的诊断语言：什么叫“有证据地理解代码库”，什么叫“过早停止”，什么叫“导航很忙但 grounding 不够”。对后训练软件工程来说，这种 trajectory reading 可以帮助筛选训练轨迹、设计过程 reward，也能解释为什么同样 pass 的 agent 过程质量差很多。
🔗 链接：https://arxiv.org/abs/2606.08500 ｜ 代码：None

### The End of Code Review：主张把人工 review gate 改成 agent-driven verification
这是一篇立场很强的 position paper，不提供新 benchmark，但抓住了 AI coding 进入团队流程后的一个真实矛盾：agent 写代码越快，人类 mandatory review 越可能变成交付瓶颈。作者回顾 code review 的传统目标，包括缺陷发现、风格一致、知识传递和团队 awareness，并认为这些目标都可以由 agent review、自动验证和可审计报告以更高吞吐完成。文章的关键主张不是“人类不再负责质量”，而是“人类逐行检查 routine diff”不应继续作为默认 gate；人类应该转向规范、风险边界、架构判断和抽样审计。这个观点有争议，因为现实中 agent 仍可能 reward hack、漏掉语义风险或生成看似合理的修复，所以它不能直接被当成实践结论。它值得收录，是因为它把 code review 从社会流程问题重新定义成 agent-driven verification pipeline 的设计问题：哪些检查确定性化，哪些交给 reviewer agent，哪些必须升级给人。对后训练和 eval 团队来说，它也提出一个新指标：自动 review 不能只会写评论，还要能闭环修复、运行证据、生成审计轨迹，并明确风险升级策略。
🔗 链接：https://arxiv.org/abs/2606.13175 ｜ 代码：None

### SWE-Compass：统一评测 agentic coding 能力的 ICML 2026 benchmark
现有 coding benchmark 很多，但常常偏 Python bug fix 或算法题，难以覆盖真实软件工程中的语言、任务类型和开发场景差异。SWE-Compass 的目标是把这些维度统一起来，构建一个更生产对齐的 agentic coding 评测框架。它覆盖 8 类任务、8 种编程场景和 10 种语言，包含 2,000 个从真实 GitHub pull requests 中整理和验证的高质量实例。评测上，它同时跑 SWE-Agent 和 Claude Code 两种 agentic framework，这很重要，因为同一模型在不同 harness 下的工具、上下文、patch 提取和验证流程会显著影响分数。ICML poster 摘要强调它能揭示任务类型、语言和场景的难度层级，而不是只给一个总分。对工程团队来说，这种 benchmark 可帮助回答“我们的 agent 到底适合修 bug、写测试、重构、迁移，还是跨语言理解”这类更细的问题。对后训练软件工程来说，统一 taxonomy 和真实 PR 来源有助于做分层训练数据、按能力切片回归，以及避免单一 SWE-bench 分数绑架研发方向。

### Microsoft ASSERT + Agent Control Specification：跨框架开放 eval 与控制标准
企业 agent 落地时，评测和控制常常是两套东西：eval 团队写场景，runtime 团队写 guardrail，最后很难保证某个风险在生产生命周期的正确位置被拦住。Microsoft Foundry 这篇 Build 2026 文章把两者放到一起：ASSERT 用组织 policy 和 requirements 自动生成针对性评测场景，ACS 则定义 agent 工作流中的确定性控制检查点。ACS 的五个 checkpoint 覆盖 input、LLM、state、tool execution 和 output，并用标准 policy YAML 表达，目标是让控制逻辑跨框架可移植、可版本化、可审计。它和 MCP/A2A 的类比很有意思：MCP 标准化 agent 接工具，A2A 标准化 agent 间通信，ACS 想标准化 agent 安全控制插在哪里、怎么执行。相比只说“加 guardrails”，这种标准把 runtime control 变成可以在 PR、CI、生产监控里复用的接口。它与 6/10 已收录的 Agent Governance Toolkit 同一条线，但这里更强调开放 eval 与控制规格的结合。对后训练评测来说，这意味着 future benchmark 可能不仅测最终答案，还测 agent 是否在正确生命周期 checkpoint 上触发了正确的 policy。
🔗 链接：https://devblogs.microsoft.com/foundry/build-2026-open-trust-stack-ai-agents/ ｜ 代码：https://github.com/microsoft/agent-governance-toolkit

### Qwen3.7-Max：面向 agent 时代的 Qwen 闭源旗舰模型
Qwen3.7-Max 是 Qwen 团队面向 agent 工作负载推出的闭源旗舰模型，按本日报规则属于低优先级的高可信官方模型发布。它的重点不是单轮问答，而是 agentic coding、办公自动化、MCP 集成和长程自主执行，官方特别强调跨 Claude Code、OpenClaw、Qwen Code 等 scaffold 的兼容性。文章给出的一个信号是 35 小时、1,000+ tool calls 的 kernel optimization run，用来说明模型能维持超长轨迹的一致性。它还支持 1M context，并通过 Alibaba Cloud Model Studio/API 分发，因此更像一个可插入多种 harness 的 agent foundation，而不是单独产品。本文不按 High 收录，是因为它主要是模型发布，缺少数据工程、评测流程或 harness 实现细节。它仍值得跟踪，因为模型供应商开始显式把“跨 scaffold 稳定执行、长程工具调用、agent 兼容协议”作为发布卖点。对工程团队来说，这会推动 model routing：同一个 harness 未来可能按成本、地域、长上下文和 coding 能力在 Claude/Codex/Qwen/Gemini 之间切换。

## 🔥 社区热点专栏

### 🔥 大佬观点

**Boris Cherny（Claude Code lead）：nested subagents 是为了更好管理上下文，而不是盲目堆并行。**  
Boris 在 6 月 9 日的社区讨论中说明，Claude Code 新增 sub-agent 递归 spawn 是在实验“agents kicking off agents”来管理复杂工作流上下文，先把深度上限定为 5。这个观点值得注意，因为它把 subagent 的价值从“更多并行 worker”拉回到“隔离局部上下文、向上返回摘要”的 harness 设计问题；同时也提醒团队要审计 allowlist、成本和递归边界。🔗 https://digg.com/ai/megudrsi ｜ Release：https://github.com/anthropics/claude-code/releases/tag/v2.1.172

**Vivek Trivedy / LangChain：模型没变，trace-driven harness 改动让 Deep Agents 上升 13.7 分。**  
LangChain 的结论非常工程化：真正可调的不是单个 prompt，而是 trace analyzer skill、pre-completion verification、local context injection、loop detection 和 reasoning budget。它值得关注，因为这给团队一个可复制的改进路线：先把失败轨迹变成可分析资产，再让 harness 以小步、可回归的方式吸收这些失败。🔗 https://www.vtrivedy.com/posts/improving-deep-agents-with-harness-engineering

**Jeff Clune / Jenny Zhang：HyperAgents 讨论继续强调“改进改进过程本身”。**  
Jeff Clune 近期在 LinkedIn 推动 DGM-Hyperagents 讨论，核心是 agent 不只修改 task-solving 代码，也修改产生下一轮改进的 meta procedure。虽然这项研究不是本期主表核心新条目，但它与 HarnessX 的 harness-model co-evolution 形成呼应：长期看，agent 工程会从“优化一个解法”走向“优化产生解法和评测解法的系统”。🔗 https://www.linkedin.com/posts/jeff-clune-56403a26_github-facebookresearchhyperagents-self-referential-activity-7441889470540570624-MOEY

### ⭐ 超火仓库/项目

**Deep Agents（langchain-ai/deepagents）：24.6k+ stars 的开源 batteries-included agent harness。**  
它火的原因是直接提供 Claude Code/Cursor 类 coding agent 所需的核心构件：planning、filesystem、shell execution、sub-agents、context management、memory，并建立在 LangGraph 的持久执行和 tracing 上。更重要的是，本期 LangChain 实验把它从“框架项目”变成可度量的 harness 研究载体，证明开源 harness 也能靠 trace ops 快速迭代分数。🔗 https://github.com/langchain-ai/deepagents

**HarnessX（Darwin-Agent/HarnessX）：把 harness 组件化、版本化、演化化的新项目。**  
虽然 star 还不高，但它解决的是社区正在集中讨论的痛点：harness 不能继续是不可拆的 prompt+tool 脚本，而要成为可组合、可比较、可训练的运行时对象。项目用 processor pipeline、9 维行为空间和 reward-annotated trajectories 把 harness evolution 做成工程框架，适合后续观察是否会成为新一代 auto-harness baseline。🔗 https://github.com/Darwin-Agent/HarnessX

**AgentLens / code-agent-state-trajectories：Microsoft 开源 SWE-agent 过程评测数据与 SDK。**  
这个项目热在“通过不等于好过程”这个痛点非常真实：团队需要知道 agent 是稳定解决问题，还是靠盲试和偶然测试通过。AgentLens-Bench 的 1,815 条过程标注轨迹、PTA reference 和 Lucky Pass 分层，能作为训练 reward、内部回归和 leaderboard 解释层的基础数据。🔗 https://github.com/microsoft/code-agent-state-trajectories/
