## 逐条讲解

### Training the Whole Agent, Not Just the Model（HarnessAdapt-RL）
今天训练 coding agent 的标准做法是：harness（包住模型的提示词、工具、钩子和控制流程）固定不动，只用 RL 更新模型权重。但训练过程中的轨迹其实一直在"告诉你" harness 哪里有问题——比如某类任务模型总用错误的修复思路，或者某个工具的交互方式让模型反复踩坑——而且这些问题会随着策略变强而变化。HarnessAdapt-RL 的思路是"边训模型边改 harness"：针对任务层面的错误修复策略，让一个冻结的老师模型为该任务生成"机制级 skill"（类似一张针对性的解题提示卡）；针对跨任务反复出现的交互问题，由另一个老师模型演化工具和 hooks，而且每次改动只有在"观测通过率"或"可训练率"（即该题还能产生学习信号的比例）至少一项提升、另一项不降时才保留。用 9B 基座，它在 SWE-bench Verified、Multilingual、Pro 上分别比纯 GRPO 高 9.8、12.6、6.4 个百分点，并且超过使用人工设计 OpenHands harness 的 GRPO。很有意思的两个消融：skill 在评测时去掉，收益仍然保留（说明已内化进权重）；但演化出的 tools/hooks 在部署时去掉会掉最多 7.7 个点，所以训练的产物其实是"模型 + harness"的配对。对后训练团队而言，这意味着 RL 流水线里的 harness 不应该是写死的常量，而应作为可版本化、可随训练演进的工件来管理，并且发布时要和权重一起发布。
🔗 链接：https://arxiv.org/abs/2610.28069 ｜ 代码：None

### CUA-Recovery: Benchmarking Error Recovery in Long-Horizon Computer-Use Agents
长程的电脑操作 agent（CUA，跨多个桌面应用干活）有个致命问题：中途某一步悄悄做错，持久化状态就被污染，后面每一步都在错误基础上继续。现有基准大多只看端到端成功率，少数考察"恢复能力"的基准又是人工往环境里注入错误，和真实 agent 犯的错并不一样。CUA-Recovery 的做法是用一个叫 ReRail 的框架，把 MyPCBench 的任务拼成带可执行标准答案的长程工作流，让多个真实策略去跑，收集"经 verifier 确认的真实失败"，再把这些失败状态转成"从这里接手并修好"的恢复任务和恢复轨迹。最终得到 100 个任务上 2,250 个人工核验的错误状态做测试集，以及 377 个任务上 8.6K 条轨迹做训练集。测下来 6 个 agent 在 6 种接手深度下，"错误察觉率"（EAR，是否意识到前面有错）最高只有 44%，Pass@3 最高 25.5%；用训练集微调 Qwen3.5-35B-A3B 后，EAR 从 19.9% 升到 35.2%，而且在干净起点的 MyPCBench 上也涨了 15.3 个点。它和昨天的 SWE-Residual 方向一致：评测和训练数据都需要"脏起点"，而"从真实失败轨迹中采样起点"是一条可以直接复制到 SWE 场景的数据构造路径。
🔗 链接：https://arxiv.org/abs/2610.27645 ｜ 代码：https://github.com/xu-hu-2002/CUA-Recovery

### MemDev-Bench: Does Memory Help Code Agents? Benchmarking Memory Systems over Real Repository Histories
越来越多 coding agent 带"记忆系统"——把之前在同一个仓库里做过的任务经验存下来以便复用，但"记忆到底有没有帮助、在什么时候反而有害"一直缺乏可靠测量：已有基准要么历史在时间上不合法（用到了未来信息），要么无法控制"历史任务和当前任务有多相关"。MemDev-Bench 给每个目标任务配上同一仓库中较早的、带相关性标注的历史任务，从而可以人为构造"高相关/低相关/无关"的历史；更关键的是它有一条自动管线，能把这些历史任务也做成可执行、可验证的环境，总共为 555 个基础任务生成了 4,869 个历史任务。系统评测得到三个结论：记忆主要帮助细粒度的定位和编辑，从而提高功能正确性；但记忆也会让 agent 在原本能做对的任务上失败，无关历史尤其如此，根因是 agent 不重新评估记忆是否适用就直接套用；而直接给 agent 原始历史轨迹，比给经过压缩的"记忆"能显著减少步数，因为压缩丢掉了过程信息。对工程实践的启发是：做 agent 记忆时，"保留过程"和"使用前重新校验适用性"比"检索更准"更重要；"把历史任务批量做成可执行环境"的管线本身也可复用于构造多任务连续训练数据。
🔗 链接：https://arxiv.org/abs/2610.27524 ｜ 代码：None

### RELAY: Scaling Historical Build Restoration through Rule Reuse and Agentic Repair
漏洞基准和大量 SWE 研究（包括 SWE 训练环境）都依赖"把历史版本的软件重新构建起来"，但构建依赖的基础镜像、软件包等外部资源会独立于源码变化——这就是"环境腐烂"。作者在 14,159 个 OSS-Fuzz 案例上实测，69.7% 已经无法完成重建和验证；好消息是，大多数失败只集中在少数几种反复出现的症状上，因此"诊断一次、修复多次复用"是可行的。RELAY 是一个混合框架：先用 LLM 从有代表性的失败中推导并验证确定性的修复规则（比如替换某个失效的镜像源），之后对新案例直接套规则，完全不调用模型；规则解决不了的再升级给逐案例的 agent 去修。实验发现规则推导可以完全自动化，可复用规则恢复的构建数与逐案例 agent 相当但构建执行次数更少，而 agent 又能修好规则覆盖不到的案例，两者组合比任一单独方案恢复得更多、成本又低于纯 agent。对做 SWE 环境的团队来说，这是一个很实用的工程范式：大规模环境修复不要每个都派 agent 硬修，先把高频失败模式沉淀成确定性规则，agent 只处理长尾。
🔗 链接：https://arxiv.org/abs/2610.27784 ｜ 代码：None

### InterWebCoder: Learning Interactive Webpage Generation from Executable Tests via RL
让多模态模型"照着网页截图写代码"已经不新鲜，难的是还原多步交互行为（点按钮弹窗、切换标签、表单状态变化）。训练这种能力缺两样东西：一是好数据——真实网页代码常常夹杂大量无关脚本和外部依赖，不能直接当训练样本；二是快而稳的奖励——用 GUI agent 去点网页来判对错，又慢又不稳定。InterWebCoder 的数据管线先录制真实网页上的交互轨迹，再合成"自包含的网页代码 + 对应可执行测试脚本"，并且有一个"失败归因修复"机制：测试不过时根据运行时证据判断错的是网页代码还是测试脚本，再针对性修改，2,058 个任务最终产出 1,736 个验证通过的样本（成功率 84.35%）。训练上用"按测试 ID 加权的 SFT"加 GRPO，奖励直接用测试通过率和状态级视觉相似度。9B 模型在 IWR-Bench 和 Vision2Web 上超过 30B 级模型和 Gemini-3.7-Flash；奖励计算延迟降低超过 97%，端到端训练加速最多 1.4 倍。值得借鉴的是"测试与代码同时合成、出错时先归因再修"的数据闭环，以及"用可执行测试替代 LLM/agent 当判官"的奖励工程取舍。
🔗 链接：https://arxiv.org/abs/2610.28610 ｜ 代码：None

### DataPraxis: Scaling Analytics Tasks via Verified Workspace Evolution
专业数据分析类任务（读数据、反复探查、给出有证据支撑的结论）需要大量多样且有挑战的训练任务，但直接从原始数据表让 LLM 出题，往往只能出浅层问题，而且答案缺少可验证的证据。DataPraxis 的核心比喻是"工作区演化"：先在一个数据工作区里做分析，把验证通过的发现和中间产物（图表、派生表等）不断沉淀进工作区；再让新的工作区继承、组合已有工作区，从而"长出"只有在前面分析基础上才会出现的深层问题。任务是从累积的发现及其依赖关系中组装出来的，分析结果在演化过程中和任务组装后各验证一次。基于此构建的 DataPraxis-5K 包含 5,000 条已验证轨迹，覆盖多领域和多种输出格式，训练出的 DataPraxis-27B 在 DABStep 上达到 55.11、JobBench 51.9，追平或超过 GLM-5.2 这类前沿模型，数据集已在 Hugging Face 开放。它对 SWE 数据合成的启发在于"难度来自依赖链"：先让 agent 把中间成果验证并固化，再在其上出题，比一次性让模型拍脑袋出难题可靠得多。
🔗 链接：https://arxiv.org/abs/2610.26924 ｜ 数据：https://huggingface.co/datasets/stargazerhust/DataPraxis-5k ｜ 代码：None

### TEX: Test-Time Scaling Testing Agents via Execution-based Cross-Validation
让模型写"能复现 bug 的测试"是 SWE 流程中的关键一环（SWT-Bench 专门测这个），但常见的测试时扩展方法要么让多个候选各自独立跑再挑一个，要么把所有轨迹拼在一起汇总，后者在长程任务里上下文会爆。TEX 来自 Salesforce，思路很工程化：并行跑 K 个 agent，每个都同时产出一个测试和一个补丁，然后把每个测试拿去跑每个补丁，得到一个 K×K 的"谁的测试能区分谁的补丁"执行矩阵；每个 agent 只拿到自己那一行/列的结果来改进自己的测试，不需要共享冗长的轨迹。在 SWT-Bench Verified 上它达到 86.4%，比单 agent 基线高 9.0 个点，刷新 SOTA；更说明问题的是，即便从 TEX 的输出里随机挑一个，也有 84.4%，超过此前 SOTA（84.0%），说明交叉执行反馈提升的是整体解质量，而不只是"挑得准"。对后训练来说，K×K 交叉执行矩阵本身就是一个现成的数据过滤器和奖励信号：能区分正确与错误补丁的测试才是好测试，可直接用来筛选测试生成的训练样本或构造 RL 奖励。
🔗 链接：https://arxiv.org/abs/2610.27290 ｜ 代码：None

### ReuF2F: Benchmarking Coding Agents on Formalized Undergraduate Research Problems
随着 AI 开始尝试解决开放研究问题，"怎么可靠地验证它真的解决了"变得重要，形式化数学（Lean 证明可被机器检查）是理想的验证载体。但现有形式化基准要么是已知结论，要么只收录少数著名开放问题——后者一旦被解决并广泛传播，就很难再当作干净的留出评测。CMU 团队的 ReuF2F 从"本科生研究体验项目（REU）"中收集了 244 个形式化的开放问题：这些问题难度入门、关注度低，更可能长期保持未解，适合当"留出集"。评测方式完全对齐现代 coding agent：每道题把命题和它的否定都放进 Docker 里的一个 Lean 项目，agent 证明其一即可；作者还基于 mini-SWE-agent 搭了统一 harness（Leanimum-agent）保证不同模型公平比较。最强模型也只解决约 40%。它的价值在于给出了一个"不易被污染、可机器验证、且采用标准 coding-agent 协议"的评测设计模板，也是 RL 可验证奖励的潜在数据源。
🔗 链接：https://arxiv.org/abs/2610.27046 ｜ 代码：https://github.com/cmu-l3/reuF2F

### ExeBench-FHD: Addressing Fidelity Issues in Decompiler Evaluation
ExeBench 是评测 LLM 反编译器（把汇编还原成 C 代码）最常用的基准之一，但作者仔细审计后发现了 9 类影响"测得准不准"的问题。其中 3 类会让模型根本不可能还原出正确代码：整型和浮点参数混用时参数顺序有歧义、优化后的汇编可能把未使用参数删掉、常量存放在函数汇编之外的数据段里；另外 6 类影响测试有效性，例如非 void 函数没有 return、占位类型、被优化器删掉的 static/inline 函数、名叫 main 的函数、函数体过于简单或定义被截断。ExeBench-FHD 是向后兼容的修订版，新增 16 个字段，包括调用点汇编、数据段、测试 wrapper、链接后二进制的反汇编以及 5 个警告标记；38.9% 的函数至少带一个警告，去掉有问题的记录后保留 63.9%。补上这些信息后，GPT 6 Sol 在相应类型函数上的重执行成功率最多提高 26.5%。这再次说明：很多"模型做不到"其实是"题目本身没给够信息"，任何代码基准在用于训练或评测前都值得做一遍类似的保真度审计。
🔗 链接：https://arxiv.org/abs/2610.28212 ｜ 代码：None

### Recoverability and Verifier Strength: Two Measured Preconditions for Unattended Agent Self-Improvement
越来越多 agent 平台开始"自己改自己"：读部署中 agent 的执行轨迹，推导出一个改动，让自动验证器（通常是 LLM judge）批准，然后无人参与直接上线。问题是这个闭环里哪些环节可以安全地无人值守？作者提出两个可测量的量：一是"验证器强度 σ"，即手头的验证器与可信参考验证器的一致程度，它决定了每一步最多能改进多少；二是"可回滚性"，即一个坏改动能多便宜地撤销，以及回滚能恢复多少旧行为。规则很简单：两者都达标才允许无人值守；在他们的平台上，这条规则允许 prompt、工具和 skill 的修改自动上线，而权重更新仍需人工签字。实测发现很扎心：平台的 LLM judge 在 37 个设置中有 9 个"无论看到什么都给同一个分"且不报错，看起来健康实则什么都批；回滚方面，恢复保存的副本能完全回到原行为，但"让模型重新生成一个撤销"做不到；而且改动在部署期间已经改变了 17% 任务的结果（超出正常波动），这是任何回滚都弥补不了的。对做自动化评测和 harness 自进化的团队，这是一份很实用的上线守则：先测验证器（作者给了两个简单检测法），再确保旧版本留档。
🔗 链接：https://arxiv.org/abs/2610.27465 ｜ 代码：None

### Ask to Distill: Learning to Synthesize Data for On-Policy Distillation
On-policy 蒸馏（OPD：学生自己生成回答，老师逐 token 打分来指导）有个反直觉现象：用很少的训练问题就能成功，说明"问题"本身更像是把老师的分布知识引出来的载体。那么能不能在不知道正确答案的情况下判断一个合成问题对蒸馏有没有价值，并学会出更好的题？Ask-to-Distill 用冻结的师生对计算一个"分布代理价值"：老师和学生在这道题上的分歧有多大、老师在学生候选答案上分配了多少概率，再加长度和多样性控制，以此作为奖励训练一个从学生初始化的出题器；生成的题目经过过滤去重后成为只有 prompt 的题库，供标准 OPD 使用。在数学、代码和 agent 任务上，它优于未优化的学生自出题和经 KL 过滤的真实题库，并在评测设置中追平或超过用真实题库做 OPD。对数据工程的意义是：OPD 的数据不必依赖带答案的真实题，"让题目最大化暴露师生差异"可以作为无标注的数据合成目标。
🔗 链接：https://arxiv.org/abs/2610.27450 ｜ 代码：https://github.com/GasolSun36/Ask_to_Distill

### Capable Teacher, Myopic Scorer: Reward-Free Teacher Repair for Agentic On-Policy Distillation（R2S）
Agentic OPD 出问题时，大家通常归因于"误差累积"——学生犯错后走进了老师不熟悉的区域，所以已有方法会用课程、老师接管、前缀回放等手段把训练限制在老师可靠的范围内。这篇论文发现这个解释不完整：从学生偏离老师最严重的状态出发，让老师自己接管依然能完成任务，可学生按老师的逐 token 打分训练后却总是耗尽回合。原因是逐 token 打分是"短视"的：老师给每个 token 打分时看不到这局最后怎样，于是那些"安全但拖延"的动作也能拿高分，而基于结果的 RL 会给这种行为零奖励。作者称之为"老师做的和老师打的分之间的差距"，提出 R2S：先从未训练学生的轨迹中挖出高分歧状态，让老师从那里多次接管，用共识或 LLM judge 这类无需任务奖励的检查筛出成功的状态，再微调老师，让它在不看接管内容的情况下给出"知道结局"的打分，修好后的老师冻结作为 OPD 唯一打分者。3 个环境 × 2 个老师 × 4 个学生共 12 组设置中全部胜过三种 SOTA 方法，平均高 12.8 个成功点。启示是：在做 agent 蒸馏前，值得先检查"老师的打分"本身是否和"老师的行为"一致。
🔗 链接：https://arxiv.org/abs/2610.28586 ｜ 项目页：https://tree-shu-zhao.github.io/r2s/ ｜ 代码：None

### From RL Papers to Framework Code: Inclusion and Review in Seven Open-Source Training Frameworks
大多数从业者使用 RL 后训练方法的方式，是通过 verl、OpenRLHF 这类开源训练框架——一个方法被框架收录，用户只需改一行配置就能用上。作者追踪了 7 个开源 RL 后训练框架的提交历史，并与 2025 年 1 月到 2026 年 6 月间筛选过的 6,939 篇 arXiv 论文做关联：1,598 篇提出通用 RL 训练方法的论文中，只有 37 篇进入了至少一个框架；每个季度 180 天内被收录的数量稳定在 5–7 篇，而同期论文数从 72 篇涨到 386 篇。被收录的论文更常在 30B 以上模型上做实验（41% vs 10%），也更常是"改现有 loss 的一个系数、clip、mask 或权重"这类小改动（29% vs 9%）；是否开源代码反而没有差别。九成以上未被收录的方法在框架的 issue/PR 里根本没人提过。这份实证对我们的启示是：RL 算法论文爆炸，但真正进入生产流水线的是"大规模验证过 + 改动小易集成"的方法；作者开放的 tracker 也可以直接用来查某个方法在哪些框架里有实现。
🔗 链接：https://arxiv.org/abs/2610.28027 ｜ 代码：https://github.com/pth2002/rl-method-tracker

### Rewards for Budget-Aware Multi-Turn Agents That Adapt to Arbitrary Test-Time Constraints
实际部署的 agent 常常有预算限制（token 数、API 调用次数、环境步数），外部 harness 可以硬性截断，但更好的情况是 agent 自己学会"该在哪里花、花多少"。这篇论文系统地问了两个问题：agent 能否学会在动态给定的预算下分配资源？哪种奖励最能教会这种行为？作者把已有的长度惩罚改造成多资源预算约束，再提出新的奖励形式，一共 11 种目标放在同一条训练管线里比较，用 Qwen3.5 4B/9B 在 AppWorld（token、API 调用、步数预算）和 BabyAI（回合预算）上训练。结果是：惩罚超支的奖励显著提升预算内成功率和"自然遵守率"，agent 学会根据给定预算和任务难度调整资源使用，并能泛化到没见过的预算值和新基准；其中 sigmoid 超支惩罚最常拿到最高预算内成功率，固定负奖励的遵守性最好，把超支频率和超支幅度一起惩罚则在各预算下最稳。对 RL 工程而言，这是一份可以直接拿来选奖励函数的对照表，尤其适合想让 coding agent 在成本约束下工作的场景。
🔗 链接：https://arxiv.org/abs/2610.28409 ｜ 代码：None

### Cache Engineering for Agents（AKV）
Agent 的轨迹越跑越长，KV cache 的读写和存储成为主要成本，而且轨迹可能超过模型最大上下文。现有的"上下文工程"做法是裁剪或总结历史，但一旦改动了轨迹前缀，后面所有已缓存的状态都失效，必须对保留下来的上下文重新 prefill，代价很高；为了少重算又不敢删太多，准确率也受影响。清华团队提出"缓存工程"：让 agent 直接操作自己的 KV cache——用 drop 把选中的缓存排除在后续注意力之外，用 repos 调整保留 key 的位置编码——既不改轨迹也不用重新 prefill。这带来一个服务端难题：同样的 token 序列在不同缓存操作序列下会得到不同的缓存状态，传统的前缀匹配复用就不对了，所以他们同时设计了 AKV 服务引擎，对外保持无状态 API 兼容，对内管理有状态的缓存复用、驱逐和恢复。实验中"滚动丢弃工具返回"的策略相比阈值触发式总结，平均分 +1.7、成本 -27.7%，吞吐最多 1.2 倍、P95 延迟 1.5 倍加速。对训练侧的意义在于：长程 agent RL 的 rollout 成本大头就是长上下文，这类"不改轨迹的压缩"可以保持训练与推理的上下文一致性。
🔗 链接：https://arxiv.org/abs/2610.28577 ｜ 代码：https://github.com/thu-nics/AKV

### Elicitation or Expansion? Demystifying Gains from Agent Harness Optimization
最近一大批工作展示了不改权重、只优化 harness 就能大幅提升 agent 成绩，但单看成功率分辨不出：优化后的 harness 是让 agent 在"本来就做得到"的题上更稳定成功（激发），还是让它能做出"原本做不到"的题（扩展）？这个区分对递归自改进很关键，因为只有"扩展"才能带来新的成功经验去推动能力边界。作者借用 RL 领域比较训练前后模型的 pass@k 分析方法，比较优化前后的 harness，考察可达任务覆盖率变化、与"换更大模型""加推理算力"的对比，以及收益随任务难度的变化。结论是：harness 在 pass@1 上相对更强干预的优势，到更大尝试预算下可能反转；总体收益还会掩盖在难题上的短板。对我们的启示是，评估 harness 优化（包括昨天的 HarnessPro、前几天的 Harness² 等）时，至少要报 pass@k 曲线和分难度结果，而不是只报一个 pass@1。
🔗 链接：https://arxiv.org/abs/2610.27889 ｜ 代码：None

  Richard Socher 创办的 Recursive 发布的首个模型，MoE 架构，总参数 39.8B、每 token 激活约 2.5B，Apache 2.0 开源，官方称 Terminal-Bench 2.1 54.9%、SWE-bench Verified 74.2%，在 M4 Pro MacBook 上约 131 tok/s（同类模型约 58–69）。它火的原因有两个：一是"笔记本上能跑、速度快、代码不出本机"的本地 coding agent 需求很真实；二是它被作为"AI 主导研发"的公开样本——Eureka Machine 参与了更稀疏的模型形状、把模型缩小 71% 的低比特训练以及定制 kernel。已支持 llama.cpp、Ollama、vLLM、SGLang 等。
  🔗 https://huggingface.co/RecursiveSI/flint ｜ 发布文：https://recursive.com/updates/introducing-recursive-flint

- **FireTrident：80 个 coding agent 共享一个仓库，62 秒清掉 Hono 的 958 个规则违例**
  Cloudflare "Build the next GitHub" 竞赛（让数十万 agent 并发改代码）的决赛项目之一，作者 Matt Solt。它的思路是"蚁群而非队列"：agent 不在合并队列里排队，而是从会随时间衰减的"场信号"中自选任务，每个改动都会对照它读过的文件做校验，然后作为 git commit 落地；生产演示中 80 个模型驱动 agent 在 62 秒内清掉 Hono 的 958 个规则违例，压测中 2,000 个合成 agent 在 145 秒内落地 6,606 个改动。它戳中的痛点是：当 agent 数量上来后，"每人一个分支 + PR + 合并队列"的人类协作模型成了瓶颈，这与 Anthropic 此前介绍的 Scion 源码控制重设计属于同一问题。
  🔗 https://agihunt.info/en/p/1a15c6367c96113a4a0a6aa0a1d ｜ 竞赛页：https://www.cloudflare.com/git-competition/
