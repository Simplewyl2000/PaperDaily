## 📝 逐条讲解

### Skill-Use：评测 agent 是否真的会触发、遵循并约束技能
很多团队已经开始把重复工作写成 `SKILL.md`、插件或项目技能库，但以前的评测经常只问“有这个 skill 后任务是否成功”，没有单独检查 agent 是否真的识别、加载并执行了这个 skill。Skill-Use 把问题拆成三段：Trigger 看 agent 是否在只看到名称和简短描述时主动检索相关 skill，Compliance 看它是否按完整流程执行，Boundary 看它是否避开 skill 明确禁止的捷径或危险操作。数据集包含 79 个真实 skill 和 177 个可执行任务，覆盖软件开发、基础设施、数据科学、数据库、文档处理、安全和业务操作等九类场景。每个任务在隔离 Docker sandbox 中运行，并用 trajectory-based rubric 对工具调用、文件产物和过程证据打分，而不是只看最终答案。实验显示最强模型-harness 配对的 SU 分也只有 0.613，并且模型排名会随着 Claude Code / Codex 这类 harness 变化而改变。它的新意在于把“会不会用技能”从泛泛的最终成功率中剥离出来，变成可观察的触发、流程和边界三种能力。对后训练软件工程来说，这类 benchmark 很适合筛选 skill 数据：一条轨迹如果没有正确触发 skill，或者触发后没有按步骤做，就不该被当成高质量正样本。
🔗 链接：https://arxiv.org/abs/2608.04828 ｜ 代码：https://github.com/JinyiHan99/Skill-Use-Bench

### Harness-R1：从失败轨迹训练专门的 harness engineer 修改运行时
许多 agent 部署后会不断积累失败轨迹，但这些轨迹通常只是被人工复盘，或者被拿去训练任务模型本身，很少系统地改进模型外面的运行时。Harness-R1 的思路是把 harness 编辑也变成一个可训练任务：目标 agent 冻结不动，另一个 9B “harness engineer” 读取一批失败轨迹压缩成的 failure packet，然后生成可执行的 runtime overlay。这个 overlay 可以在 episode 初始化、决策前上下文构造、动作发出前 guardrail、反馈返回后恢复等生命周期节点插入代码，但不能直接替任务 agent 作答。每个候选 patch 都会被安装到同一批任务上重跑，只有实际提升目标 agent 成绩且不破坏已成功任务的改动，才给 harness engineer 训练奖励。作者先用强 teacher 产生约 1,000 个可执行编辑样本做冷启动 SFT，再用在线 GRPO 训练编辑策略；在 WebShop、ALFWorld 和 DBBench 上，冻结 Qwen3.5-9B 的平均成功率从 44.3% 提到 53.6%。这对工程团队的启发是，失败轨迹不一定只能用于 SFT 或写经验总结，也可以训练一个专门维护上下文、工具、恢复和验证逻辑的“运行时修理工”。后训练数据 pipeline 可以借鉴它的 same-batch rerun reward：任何 harness 改动都要用真实重跑结果验证，而不是只凭 LLM 解释看起来合理。
🔗 链接：https://arxiv.org/abs/2608.02276 ｜ 代码：https://github.com/DeepExperience/Harness-R1

### Scaffold-Mediated Post-Training：让技能图与模型参数共同演化
当前 code LLM post-training 常把模型参数训练和推理时 scaffold 设计分开：训练只更新权重，部署再手写 skills、workflow、prompt 和验证步骤。Scaffold-Mediated Post-Training 试图把这两层打通，把 procedural scaffold 组织成可演化的技能图，每个 skill 都有元数据、触发条件、执行过程、验证检查点、输入输出接口和反模式。系统先自动发现技能，再按任务组装 scaffold 子图，生成通过 verifier 检查的训练数据；模型通过渐进蒸馏吸收这些技能行为后，已经内化的 skill 会从外部图里移除。随后依赖它的上层技能会被 dynamic recompilation 自动重写和重新验证，从而形成“发现技能 -> 生成数据 -> 内化到参数 -> 重编译 scaffold”的闭环。在 FeatureBench 上，自动发现的 skills 把 passed rate 从 24.4% 提到 32.5%，蒸馏后在仍有 scaffold 时达到 31.5%，去掉外部 scaffold 后也保留到 27.7%。它最有价值的地方不是某个算法细节，而是把技能从孤立 markdown 变成带依赖、接口和验证信号的工程对象。对后训练软件工程来说，这说明 skill management 可以和参数训练协同：哪些流程应该留在 harness，哪些已经能蒸馏进模型，可以通过保留率、验证通过率和图重编译来决定。
🔗 链接：https://arxiv.org/abs/2608.05156 ｜ 代码：None

### Active-SWE：没有 issue report 时，agent 能否主动发现并修 bug
SWE-bench 这类基准通常给 agent 一份 issue report，里面包含错误现象、期望行为、甚至隐含定位线索；但真实生产里，很多 bug 在用户报告前就已经存在，且报告质量往往不可靠。Active-SWE 把评测目标从“根据 issue 修一个指定 bug”推进到“没有实例级 issue 的情况下主动审查代码、发现 bug 并修复”。它从 87 个 1,000+ stars 的真实开源仓库中挖掘高质量 bug-fixing PR，按六类 bug taxonomy 做共识过滤，并用 setup agent 构建 Docker 环境和测试脚本。任务构造分 simple 和 hard：simple 来自单个 PR，hard 用时间窗口组合多个相邻 bug 修复，要求 agent 在限定 review scope 内处理多个潜在问题。评测也分双轨，一边看 recorded bug 是否被修复，一边要求 agent 为潜在 bug 生成测试和证据，再由 judge 验证 bug-test-patch 的链条。结果显示当前强 coding agents 在定位已知 bug、处理多 bug 和发现有效潜在 bug 上都很吃力。它对后训练数据工程很重要，因为未来高价值轨迹不应只来自“用户已经把 bug 描述清楚”的场景，也应来自主动扫描、证据构造、测试生成和多缺陷修复这类更接近生产质量工程的流程。
🔗 链接：https://arxiv.org/abs/2608.04682 ｜ 代码：https://github.com/XLearning-SCU/Active-SWE

### MT-Web2Code：多轮前端区域重建与局部修改 benchmark
前端 coding agent 的真实工作通常不是一次性从截图生成完整页面，而是在已有代码上多轮修局部区域，同时不能破坏之前已经正确的内容。MT-Web2Code 正是针对这个缺口：它构造 102 个网页、覆盖 16 个垂直领域，评测 agent 在多轮 macro-level regional reconstruction 和 micro-level localized modification 中的表现。为了避免昂贵的逐轮人工标注，作者设计 Reverse-Corruption Trajectory Engine，从 golden page 开始逐步注入结构和样式缺陷，再把这个过程反过来作为 deterministic repair trajectory。宏观区域重建用五维 VLM rubric 评估目标区域是否恢复，微观局部修改用像素级 alignment 检查具体位置是否对齐，同时还衡量 unaffected content 是否被误改。实验覆盖 13 个 frontier coding agents，发现它们常常恢复目标区域不准、视觉和代码对应不细、早期小错误会在后续轮次雪球式放大。这个 benchmark 的工程价值是把“迭代式 UI 修复”拆成每一步都有明确目标状态和保留约束的轨迹，而不是一次性看最终截图相似度。对后训练来说，reverse-corruption 也提供了一种数据合成模板：先有可渲染黄金状态，再可控地制造缺陷，最后得到可验证的多轮修复监督。
🔗 链接：https://arxiv.org/abs/2608.03474 ｜ 代码：None

### PAST-Bench：用持久化开关归因 personal agent 是否真的从经验变强
很多 personal agent 都宣称会保存用户偏好、历史任务、工具流程和自生成技能，但“下次做得更好”到底是不是这些经验造成的，常常没有被严格验证。PAST-Bench 把这个问题做成 performance-attribution benchmark：每个 agent 走过一组有顺序的 fresh-session episodes，前面的 learn/update episode 给它机会写入经验，后面的 evaluation episode 测它是否能在新会话中重用。关键设计是 matched persistence on/off，对同一个 evaluation prompt、同一个模型和同一个工具环境，只切换是否允许访问家庭任务中产生的持久状态。它覆盖 26 个场景和 204 个 episodes，分成 memory、procedural reuse、information gathering 和 update 四类能力，并用 control episodes 排除表面记忆、错误机制和陈旧信息复用。论文还报告 mechanism evidence，例如是否写了 memory、是否读了正确 skill、是否调用 session search、artifact diff 是否符合预期。作者基于诊断结果提出 Hermes+，在 Plan、Render、Route、Gate、Close 五个环节增加机制，提升了机制证据分数，尤其对旧状态替换任务帮助更大。对后训练软件工程来说，它提醒我们持久记忆和技能库不能只看最终分数，必须记录“写入了什么、何时检索、是否走了正确路径、旧信息是否泄漏”，否则自演化很容易变成不可解释的缓存命中。
🔗 链接：https://arxiv.org/abs/2608.04003 ｜ 代码：https://github.com/Gen-Verse/PAST-Bench

### Meta Muse Code + Muse Spark 1.2：模型与终端 coding harness 联训
Meta 这次不是只发布一个 coding model，而是同时推出 Muse Code beta 终端 agent 和 Muse Spark 1.2，并强调二者是为彼此配合训练的。Muse Code 的运行时包含一个主 agent loop 和持续存在的 async background agents，这些子 agent 不是每个任务临时创建，而是在 session 期间保持活跃，减少重复搜集信息和重复上下文装载。它还使用本地 append-only event log，把每次模型调用、工具运行、审批和编辑都记录成单一事实源，因此崩溃后可以 replay-exact 地恢复，而不是从头再来。默认 skills 包括 `/plan`、`/grill` 和 `/goal`，分别服务于审批计划、压力测试计划和追踪目标完成。模型侧，Muse Spark 1.2 用 rejection-sampled harness trajectories、goals、compaction、subagents recipe 和 Muse Code toolset 做了联训，以提高模型在该 harness 下的可用性。官方还给出 GPU kernel optimization case：agent 在 Muse Code 环境里跑 1,000+ tool calls、最长 24 小时，写、编译、profile 并迭代 Triton kernel。对我们关注的后训练软件工程来说，它最大的信号是“模型 + harness + event log + skills”被当成一个整体训练和发布，轨迹格式、压缩策略、子 agent 生命周期和恢复机制都会直接影响模型行为。
🔗 链接：https://research.meta.ai/blog/introducing-muse-code-and-muse-spark-1-2 ｜ 代码：https://developer.meta.com/ai/products/muse-code/

### Agent Plugins 1.0：把 Agent Skills 与 MCP server 打成跨客户端插件
Agent Skills 和 MCP server 各自已经相对可移植，但真实分发时常卡在“外面那个盒子”：不同客户端要求不同目录、manifest、MCP 配置形状和扩展字段，作者最后不得不为 Claude、Codex、Cursor 等维护多个变体。Agent Plugins 1.0.0 试图把这层包装标准化成一个很小的目录规范：根目录有 `plugin.json`，skills 固定在 `skills/`，MCP server 固定在 `mcp.json`，客户端私有能力放到 reverse-domain namespace 中。Google 8 月 6 日宣布加入 core maintainers，并把 Agents CLI 和 Data Agent Kit 的技能/MCP 能力开始按这个格式分发。这个规范特意不管安装、权限、分发协议、沙箱和信任模型，因为这些在 IDE、CLI 和企业平台里差异很大；它只解决“组件放在哪里、客户端怎样发现它们”的最低公约数。项目仓库约 689 stars，且核心维护者/协作者覆盖 Amazon、Cursor、Microsoft、OpenAI、Vercel 和 Google，说明社区正在把 agent 扩展打包当作基础设施问题。工程上，这能减少技能和工具包装漂移，让同一套评测、部署或数据工程 skill 在多个 agent 宿主间复用。对后训练数据工程来说，插件格式标准化也意味着轨迹更容易记录：某次 run 用了哪个 plugin、哪个 skill、哪个 MCP server，以及哪部分是客户端私有扩展，都可以被结构化追踪。

### RAIL：用 recoverability 学习哪些 rollout 值得继续干预
在 GRPO 这类 critic-free group RL 中，训练通常给每个任务分配固定数量 rollouts，但不同任务和不同轨迹状态的学习价值差异很大。有些状态多采样几条就能出现成功/失败对比，给 policy gradient 提供强信号；另一些状态已经饱和或不可恢复，继续采样只会浪费预算并稀释更新。RAIL 把 rollout generation 本身当成可学习的干预过程，而不是固定采样规则。它定义 recoverability，衡量在某个任务或中间状态上追加某种干预后，能否产生更有信息量的 reward distribution contrast。系统先用 shadow phase 收集干预轨迹，再把“上下文状态、干预动作、实际 recoverability gain”训练成 contextual bandit controller，之后在 live phase 中按 utility gate 选择在哪里、用什么方式分支。它的重点不是提出新 reward，而是让训练数据生成过程随 policy 演化持续适配，解决固定启发式在非平稳训练中的失效。对软件工程 agent 来说，这个思想可以迁移到失败轨迹采集：不要平均地重跑每个 issue，而应优先在还能被测试、补丁、工具选择或中间状态纠偏救回的节点上分配 rollout 预算。
🔗 链接：https://arxiv.org/abs/2608.05080 ｜ 代码：None

### SpecRoll：面向 GRPO rollout 的两速自适应 speculative decoding
LLM post-training 中最耗时的一环常常是 rollout 生成，尤其是 GRPO 每个 prompt 要采多条长响应，而 agentic 场景还会夹杂工具调用和长上下文。普通 speculative decoding 可以让小 drafter 先猜未来 token，再由目标模型验证，但 RL 训练里的 target policy 不断变化，固定 drafter 很快过时，频繁训练 drafter 又会引入额外同步和反向传播成本。SpecRoll 的做法是使用轻量 future-token heads 直接从目标模型 hidden state 预测多个未来位置，并通过 exact target verification 保证最终采样分布不变。它提出 Reflex fast path：利用延迟到达的 verifier feedback 做局部、有限、无反向传播的 hidden-state 修正；同时只有在持续退化时，slow path 才更新 head 参数。系统还按当前未完成 responses 数量动态调整 sparse verification tree 的预算，在高并发时避免浪费，在并发下降时吃满硬件。实验覆盖 1.5B 到 14B 的五个模型和三个数学 reasoning 数据集，相比 vanilla GRPO 有 1.21-2.04 倍端到端加速。虽然它不专门针对 coding agent，但对后训练工程很实用：当我们把 agent rollout 扩到多工具、多轮、多样本时，生成效率和采样分布保持同样重要，否则数据管线本身会成为瓶颈。
🔗 链接：https://arxiv.org/abs/2608.04962 ｜ 代码：https://anonymous.4open.science/r/SpecRoll-26062006

### Agent-Pex：从 agent prompt 与 trace 抽规格，自动评测与生成反例
Agent 的失败不总是体现在最终回答错了：它可能工具参数不合规、计划漏步骤、该请求人工审批时没有请求，或者违反了系统提示里的某条行为规则。Microsoft Research 的 Agent-Pex 把 agent prompt、system instructions 和执行 trace 看成可提取的 partial specification，然后自动检查轨迹是否违背这些规则。它可以从 prompt 中抽出显式或隐式行为约束，例如“只有任务需要时才调用某工具”“输出必须满足某 schema”“特定身份信息不能乱说”，再对多步 trace 做 compliance scoring。项目还继承 PromptPex 思路，把规则反转成 adversarial tests，用来主动生成容易触发不合规行为的测试用例。Microsoft 页面称它能在 VS Code、M365 Copilot 等商业 agent traces 和 Tau2 benchmark 上做大规模分析，并支持 5,000+ traces 的跨模型对比。它的价值在于把自然语言 prompt 里的规则变成可重复执行的 eval，而不是等 reviewer 手动发现一次违规。对后训练软件工程来说，Agent-Pex 这类工具可以把“为什么这条轨迹不合格”转成结构化标签，进入回归测试、数据过滤和安全训练。
🔗 链接：https://www.microsoft.com/en-us/research/project/agent-pex-automated-evaluation-and-testing-of-ai-agents/ ｜ 代码：None

### Chrome Future Mode：把浏览器隔离、DLP 和 human approval 扩到 agentic browsing
这条不属于 code LLM 后训练主线，所以按 Low 收录；但它是 Google Cloud 近月官方技术博客，讨论的是企业浏览器如何承载 agentic browsing。传统浏览器安全假设“人”在点网页，而 agentic browsing 里，AI 可能跨多个 SaaS、内部文档和公网页面自动采集、填写和提交信息，数据边界会变得更复杂。Chrome Enterprise 的方案把 DLP、context-aware access 和 extension controls 扩展到 agent 行为：如果员工没有权限访问或导出某些数据，代表他行动的 agent 也不应有。更具体的三层架构包括 User Alignment Critic，它只看拟执行动作的 metadata 并判断是否仍符合用户原始目标；origin scoping 限制 agent 只能在与当前任务相关的站点范围内行动；work log 和关键动作人工确认则让用户能看到、打断和批准高风险步骤。博客还提到 Chrome History 会标记 agent background navigation，并把 agentic capability 纳入 VRP，最高奖励 20,000 美元。对软件工程 agent 的间接启发是，浏览器/桌面这类 runtime 需要把身份、数据流、动作日志、人工确认和红队测试统一设计。未来 GUI-to-Agent 或 browser-agent 轨迹如果缺少这些安全元数据，很难安全地进入训练和评测。
🔗 链接：https://cloud.google.com/blog/products/chrome-enterprise/future-mode-part-2-the-foundation-for-securing-agentic-browsing ｜ 代码：None

**Amit Kothari：Claude Code dynamic workflows 的真正价值是并行验证，不只是并行执行。**
Amit 的动态 workflow 分析强调，subagents fan-out 本身不是核心，关键是多个 agent 能互相检查，在结果交给用户前形成验证压力。他也提醒 ultracode / dynamic workflows 会放松自动编辑审批并显著增加 token 成本，因此适合大规模迁移、审计和跨模块验证，不应默认用于所有任务。🔗 https://amitkoth.com/dynamic-workflows/

### ⭐ 超火仓库/项目

**agentplugins/agent-plugins-spec：约 689 stars，Agent Plugins 1.0.0 把 skills + MCP server 包装成跨客户端最小标准。**
它火在解决 agent 扩展生态里很实际的“manifest 漂移”问题：同一个 skill/MCP 组合不应为每个客户端复制一份包装。Google 加入 core maintainer 后，这个标准更像是技能和工具分发层的共同底座，后续会影响训练轨迹里的 plugin provenance。🔗 https://github.com/agentplugins/agent-plugins-spec

**ShawnPana/phone-harness：8 月 7 日创建后约 239 stars，用 macOS iPhone Mirroring 让 agent 控制真实 iPhone。**
它的设计很极简：用 `screencapture` + Apple Vision OCR 作为眼睛，用 HID-level CGEvents 作为手，不用 jailbreak、Xcode 或 WebDriverAgent。它解决的是 Agent-Friendly Software 的核心痛点之一：真实手机 app 没有标准 API，agent 需要一个可观察、可验证、可人工接管的薄 harness。🔗 https://github.com/ShawnPana/phone-harness

**viticci/shortcuts-playground-plugin：约 1,017 stars，把 Apple Shortcuts 变成 Claude Code / Codex 可生成、可验证、可签名的插件。**
Shortcuts Playground 火在把传统 GUI 里的自动化能力转成 agent-friendly surface：用户用自然语言描述 shortcut，agent 生成 XML、结构化验证，再用 macOS `shortcuts` CLI 签名成可导入文件。它的真实痛点是 Apple Shortcuts 动作空间复杂且格式封闭，插件用知识库 + validator loop 把“能写自动化”变成可回归的 agent workflow。🔗 https://github.com/viticci/shortcuts-playground-plugin ｜ https://www.macstories.net/shortcuts-playground/
