## 📝 逐条讲解

### OpenAI Presence：把企业 voice/chat agent 做成可评测、可升级的生产系统
很多企业现在已经能做 agent demo，但真正困难的是让 agent 在客户支持、保险理赔、IT 服务台这类高价值流程里稳定工作，而且业务规则和用户行为还会不断变化。OpenAI Presence 把这件事包装成生产 agent 平台：每个部署从一个具体 job 开始，只给 agent 必要知识和系统权限，并由企业定义政策、可批准动作、何时升级给人。它最值得关注的部分不是 voice/chat 本身，而是把 policies、standard operating procedures、guardrails、approved actions、simulations、graders 和 rollout 流程放在同一套系统里。上线前，团队可以用常见请求、边界情况和高风险场景跑 simulation，grader 会检查 agent 是否达成正确结果、遵守政策、正确使用工具、该升级时升级。上线后，production sessions、escalations 和 quality signals 会暴露 agent 的缺口，Codex 通过 Presence plugin 调查这些信号并提出更新，团队再把候选改动与生产版本对测后批准受控发布。对后训练软件工程来说，这是很清晰的 deployment-to-training feedback loop：真实交互、升级点、grader 结果和策略变更都可以变成后续改进数据。它说明企业 agent 的核心不只是模型调用，而是可评测、可批准、可回滚、可持续更新的运行时系统。
🔗 链接：https://openai.com/index/introducing-openai-presence/ ｜ 代码：None

### Open-Kritt：开源漏洞研究 agent 编排平台，把安全扫描拆成 workflow + scan + post-processing
让一个 coding agent “找漏洞”通常效果不稳定，因为整仓代码、依赖、生产配置、赏金规则和漏洞类型会把上下文塞爆，模型也容易产出夸大或重复的报告。Open-Kritt 的做法是把漏洞研究拆成可复用 workflow 和一次性 scan：workflow 定义怎样搜索，例如先枚举 entry points，再为每个入口和 bug pattern 启动独立 agent；scan 则定义目标仓库、相关依赖、生产配置、模型/harness、重复次数、ranker 和 post-script。这个分层很工程化，因为同一个 workflow 可以在不同目标上复用，而同一批 raw findings 可以按不同 bounty scope、生产特性和证据标准做后处理。项目博客披露团队用内部系统在 9 个月里找到 20+ High/Critical 漏洞，最大单笔 bounty 25 万美元，并在 Firedancer V1 audit competition 中用 100% AI-driven research 拿到第一。开源版支持 Codex 和 Claude Code 两种 harness，每个 agent 在自己的隔离容器里运行，可以安装工具、编译项目、跑测试、fuzz 输入或构造 PoC。真正值得借鉴的是 post-processing：validation、false-positive filtering、anchored deduplication 和 pairwise ranking 都被放在 scan 层，而不是让一个大模型一次读完所有报告。对后训练数据工程来说，这种安全 agent 轨迹天然包含任务拆解、攻击假设、动态验证、去重、排序和人工复查点，是比单条“发现漏洞”文本更有价值的训练素材。
🔗 链接：https://kritt.ai/open-kritt-launch ｜ 代码：https://github.com/Kritt-ai/open-kritt

### Agentic Routing：把模型路由做成 harness-native data flywheel
传统模型路由通常只看单次 prompt：输入长不长、难不难、要不要用便宜模型，目标主要是省钱。Agentic Routing 这份技术报告把路由放回 agent harness：每一步选择模型时，路由器不仅看 query，还看当前 harness state、历史失败、工具反馈、任务阶段、成本预算和需要的能力。它的核心 insight 是，每一次路由决策都会自然产生一条训练记录：query、harness state、选了哪个模型或模型组合、执行 trace、结果和成本，而这些 label 来自环境反馈，不需要单独人工标注。OpenSquilla 把这个思路落成一个 token-efficient microkernel agent，使用本地 LightGBM + ONNX classifier 根据长度、语言、代码、关键词和 embedding 做 tier routing，并支持多模型 ensemble routing。GitHub 核验显示 `opensquilla/opensquilla` 约 6.2k stars，7 月 23 日仍在活跃推送，技术报告在 7 月 14 日公开。它解决的痛点不是“哪个模型最好”，而是同一个长程 agent 任务里，不同步骤可能需要不同成本/能力组合。对后训练软件工程来说，这把 routing 从 serving 优化变成数据工程：如果 harness 持续记录路由点和 outcomes，就能训练更好的 router、筛出高性价比轨迹，也能解释失败来自模型选择、上下文状态还是工具链。
🔗 链接：https://arxiv.org/abs/2607.11399 ｜ 代码：https://github.com/opensquilla/opensquilla

### Self-Improving AI Coding Agents：把每条 review feedback 沉淀为持久行为规则
coding agent 在不同会话里重复犯同类错误，是很多团队的日常痛点：今天 review 里指出“不应绕过现有 service abstraction”，下周另一个任务又犯一次。这个工作提出一个很朴素但可落地的闭环：把每条被接受的 review comment codify 成持久行为规则，放进版本控制的 instruction file，再让 agent 在提交前执行 self-review checklist。系统不是改模型权重，而是让规则集、语言/框架标准和 checklist 随真实 human review 逐步扩展，并用自动验证保证规则文件不被破坏或互相冲突。论文报告在一个 35+ service 的 microservices 平台上部署，规则集从 5 条增长到 18 条行为规则、15+ language-specific standards 和 15 项 self-review checklist。11 个记录会话覆盖代码生成、PR review、incident investigation 和跨服务重构，作者观察到 ruled-against error classes 的 recurrence rate 为 0%，review effort 从低级正确性问题转向设计级判断。它的价值在于把“经验学习”从聊天记忆变成 repo artifact：可 diff、可审查、可回滚、可跨 Claude/Codex/Cursor/OpenCode 等不同接口复用。对 skill management 和后训练数据来说，这类规则沉淀可以同时作为生产 guardrail、轨迹标签和未来训练样本的来源。
🔗 链接：https://arxiv.org/abs/2607.13091 ｜ 代码：None

### STRACE：从 noisy traces 里抽取 root cause，用于 agent 优化
长程 agent 失败后，直接把整条 transcript 喂给优化器通常效果很差，因为里面有大量无关搜索、重复验证、偶然错误和最终才暴露的症状。STRACE 试图解决“哪些失败轨迹值得看、每条轨迹里哪几步真正导致失败”这两个问题。它在 batch level 先挖掘 failure patterns，过滤重复或低价值 trace，保留代表性失败；在单条 trace 内，再把执行过程构造成 textual dependency graph，并做 causal localization，找出真正的 root-cause module。通俗说，它不是压缩 transcript，而是先判断每一步和后续失败之间有没有因果依赖，再把无关噪声拿掉。论文在 VeruSAGE-Bench 形式化验证任务上优化人类专家设计的 agent，报告 success rate 从 42.5% 提升到 58.5%，约 1.4 倍提升。相比只按最终 reward 做筛选，STRACE 更像一个轨迹清洗和根因抽取 pipeline，适合给 reflection-based optimizer、prompt/harness 更新或后训练数据筛选供料。对本日报关注的 trajectory selection 来说，它提示我们要保存 dependency、失败模式和 root-cause verdict，而不是只保存原始 log 和 pass/fail。
🔗 链接：https://arxiv.org/abs/2607.07702 ｜ 代码：https://github.com/moomight/STRACE

### ToolFailBench：隔离诊断 LLM agent 是否忠实使用工具返回证据
很多 tool-use benchmark 最后只看任务是否成功，但失败可能来自规划错、工具选错、检索错、工具执行失败，也可能来自模型拿到了正确工具结果却没有忠实使用。ToolFailBench 的设计重点是把“是否正确利用 returned tool evidence”隔离出来，减少 end-to-end 成功率把多个因素混在一起的问题。它关注 agent 在看到工具返回后，能否把 evidence 正确整合进后续判断，而不是继续相信先验、忽略冲突证据或编造工具没有给出的结论。这个问题在 coding agent 里很常见：测试日志、编译错误、API response、browser console 和 static analyzer finding 都是工具证据，但模型可能只挑自己想看的部分。该 benchmark 的价值在于提供一类更细的评测信号，让工程团队知道 agent 是工具接口、工具选择、证据解释还是最终合成出了问题。对 evaluation engineering 来说，这种拆解比单一 pass/fail 更能指导 harness 修改，例如是否需要更结构化的 tool output、是否要强制引用证据、是否要在冲突时触发 verifier。对后训练数据工程来说，工具证据与模型结论之间的忠实性标签非常适合构造负样本和 anti-hallucination 训练集。
🔗 链接：https://arxiv.org/abs/2607.04686 ｜ 代码：None

### Gemini CLI v0.52：Google 官方终端 agent 持续强化 MCP / ReAct / Code Assist agent mode
Gemini CLI 不是今天才出现，但 7 月 22 日 v0.52.0 release 和持续活跃推送说明 Google 官方终端 agent 正在快速补齐 coding-agent runtime 能力。GitHub 核验显示 `google-gemini/gemini-cli` 约 106k stars、14k forks，7 月 23 日仍在推送，最新 release 是 v0.52.0。官方文档把它描述成一个 ReAct loop 终端 agent，可以使用内置 grep、terminal、file read/write、web search、web fetch，也能接本地或远程 MCP servers。更值得注意的是，Gemini Code Assist VS Code agent mode 由 Gemini CLI 驱动，并暴露 MCP servers、`/memory`、`/stats`、`/tools`、`/mcp` 等 CLI 能力子集。这说明 Google 正在把 CLI harness 作为 IDE agent mode 的底层运行时，而不是把 IDE 与 CLI 做成两套完全不同系统。对 Agent-Friendly Tooling 来说，MCP server 的 `gemini mcp add/list` 和项目级 `.gemini/settings.json` 让工具接入变成可配置 artifact。对后训练软件工程来说，Gemini CLI 轨迹需要记录 ReAct 工具面、MCP 配置、Code Assist surface 和配额/认证路径，因为这些会直接影响 agent 的能力边界和成本。

### Early Adoption of Agentic Coding Tools by GitHub Projects
随着 Copilot、Codex、Claude Code 这类 agent 直接开 PR，开源项目需要治理的不只是“谁写了代码”，还有 agent-generated contribution 怎样被 review、合并或拒绝。这个研究分析了 2,361 个热门 GitHub 仓库中的 25,264 个 agentic PR，关注 project-level adoption、agentic PR ratio 和 human-agent collaboration pattern。结果显示，大多数项目仍处在低频、早期采用阶段，但不同项目间差异很大，一些仓库的 agentic PR 比例明显高于行业估计。协作模式上，单人监督占主导：通常是一个人 review 或修改 agent 贡献，多人共同审查 agent PR 的情况相对少。这个结论对工程组织很重要，因为 agent 引入后 review bottleneck 并不会自动消失，反而可能集中到少数维护者身上。它按 Medium 收录，因为它更像 adoption/治理研究，不是新的 harness 技术；但它给评测和数据采集提供了真实世界背景。对后训练软件工程来说，未来数据集不应只抓 agent 的 final patch，还应记录 PR discussion、reviewer count、人工修改量、合并/关闭原因和项目是否已有 agent policy。
🔗 链接：https://arxiv.org/abs/2607.14037 ｜ 代码：None

### From Conversation to Contribution：把 vibe-coding 对话与 OSS 贡献历史关联起来
“vibe coding”常被当作社交媒体口号，但真正要理解它对开源的影响，需要把 AI 对话和后续代码贡献联系起来看。这篇论文从 1,356 个仓库收集 AI conversation sessions，并把它们与 repository development history 关联，同时补充开发者调查。研究发现，AI 使用更集中在规模较小、成熟度较低、协作度较低的项目；采用 AI 后，项目往往有更多 active contributors，contributor concentration 下降，但沟通和审查责任仍然高度集中。Code Writing 是主导用途，几乎所有 AI 会话后都会跟随某种开发活动，但开发者仍关心质量、review burden 和贡献治理。它的价值不在于证明 AI 一定提升生产率，而是提供了一个可操作的数据模型：把聊天 session、代码变更、贡献者结构和 survey perception 串起来。对 coding-agent 后训练来说，这提示我们不要只从 agent logs 里采样，还要看这些 logs 对真实协作流程有什么影响。工程上更有用的问题是：哪些 AI 会话最后产生可维护贡献，哪些只是制造 review 负担，哪些项目需要更强规则和验证门。这样的研究可以帮助团队设计 agent policy、PR template 和 review automation。
🔗 链接：https://arxiv.org/abs/2607.05677 ｜ 代码：None

### Microsoft CLI coding-agent rollout study：Claude Code / Copilot CLI 早期组织采用与产出影响
企业内部部署 CLI coding agent 时，管理者关心的不只是“模型能力”，还包括谁会采用、谁会持续使用、token spend 是否值得、以及组织政策变化会不会扭曲使用数据。这个研究利用 Microsoft 2026 年初对 Claude Code 和 GitHub Copilot CLI 的内部 rollout，构造 adoption 和 impact 分析。样本设计上，作者把 2026-01-05 作为使用起飞的边界，选择在 1 月第一周有工具活动的 adopter cohort，并用从未使用这两种工具但有足够 PR 活动的工程师作为 control。结果变量聚合为每位工程师每天 merged PR 数，并用较长 pre-period 与 post-period 做对比。论文还特别说明 Claude Code 后续许可证政策变化会影响自然采用，因此分析窗口在政策迁移前截止，这种边界处理对企业遥测研究很重要。它按 Medium 收录，因为更偏组织采用与 productivity measurement，但对 agent platform 决策很有参考价值。对后训练软件工程来说，它提醒我们，真实生产轨迹经常受 license、quota、默认工具、组织迁移和合规政策影响；如果数据不记录这些背景，就很容易把制度变化误判为模型或 harness 效果。
🔗 链接：https://arxiv.org/abs/2607.01418 ｜ 代码：None

### Anthropic Economic Index connector：把 AI 工作使用数据变成 Claude 可查询 connector
Anthropic Economic Index 原本是面向研究者、记者和政策制定者的数据发布，但普通用户要探索它仍需要理解数据集、图表和限制。7 月 22 日发布的 Economic Index connector 把这批数据接进 Claude，用户可以直接问“哪些职业使用 AI 最多”“教师常用 Claude 做什么”“AI 自动化任务过去一年如何变化”等问题。它的工程意义不是新模型，而是把官方经济数据变成 agent-friendly data source：自然语言提问、逐步 drilldown、要求 Claude 展示 underlying data 和限制说明。文章也明确提醒，Index 反映的是 Claude 使用模式，不等于整个劳动市场，这种 source limitation 对数据型 agent 很重要。它按 Low 收录，因为主题偏经济研究和产品数据探索，不是 coding-agent 主线；但作为官方 connector，它展示了 Anthropic 如何把公开数据集转成可交互工具。对 Agent-Friendly Software 来说，这类似把数据库、研究报告和可视化 dashboard 包装成可被 agent 查询的接口。对后训练数据工程的间接启发是，任何基于真实使用数据的 agent 都应在回答中携带来源、采样范围和局限，避免把平台局部数据讲成全局事实。

### 🔥 大佬观点

**OpenAI Presence 相关讨论：生产 agent 的竞争点从“能回答”转向“能被政策、评测和受控发布管理”。**  
围绕 Presence 的 VentureBeat、Help Net Security 等报道都抓住同一个重点：OpenAI 不是只卖 voice/chat bot，而是在包装一个包含 policies、guardrails、simulations、graders、human escalation 和 post-launch update 的 agent operations layer。值得注意的是 Codex 被放进 production feedback loop，用来调查会话和升级信号并提出可测试改动，这把 coding agent 的角色扩展为“改进其他 agent 的工程师”。🔗 https://openai.com/index/introducing-openai-presence/ ｜ https://venturebeat.com/orchestration/openai-unveils-presence-a-new-platform-that-lets-enterprises-launch-and-manage-realtime-voice-agents-and-chatbots

**Open-Kritt 团队：domain knowledge belongs in the workflow，安全 agent 不是一个大 prompt。**  
Open-Kritt 发布文反复强调，真正有效的漏洞研究来自把研究者的技巧、协议知识、生产配置和 bug pattern 写进 workflow，而不是让模型泛泛“找漏洞”。这个观点值得注意，因为它把安全 agent 的后训练/评测对象从最终报告转移到 workflow 图、scan 配置、验证脚本、dedup/ranking 和失败回放。🔗 https://kritt.ai/open-kritt-launch

### ⭐ 超火仓库/项目

**google-gemini/gemini-cli：约 106k stars，07-22 发布 v0.52.0，Google 官方终端 agent 继续高速迭代。**  
它火在 Google 把 CLI harness 同时作为独立开发者工具和 VS Code Code Assist agent mode 的底层运行时，MCP、web fetch/search、文件编辑、terminal 和 `/mcp` 等命令都在同一体系里。对团队来说，Gemini CLI 不是“又一个聊天入口”，而是 Google 阵营可脚本化、可接 MCP、可进入 IDE 的 agent runtime。🔗 https://github.com/google-gemini/gemini-cli

**Kritt-ai/open-kritt：07-20 创建，约 322 stars，开源 AI 漏洞研究 workflow 平台。**  
star 还不算巨型，但热度来自强结果叙事和明确痛点：用 parallel agents、isolated containers、post-scripts、anchored dedup 和 ranking 把漏洞研究做成可复用 scan pipeline。它解决的是安全研究中最难规模化的部分：不是生成报告，而是拆任务、验证、去重、排序并把领域经验写进 workflow。🔗 https://github.com/Kritt-ai/open-kritt

**opensquilla/opensquilla：约 6.2k stars，07-23 仍活跃推送，主打 harness-native routing。**
