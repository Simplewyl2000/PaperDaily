## 📝 逐条讲解

### Patch the Planet：AI 安全发现到开源补丁落地的人工复核闭环
AI 安全工具现在越来越会发现漏洞，但开源维护者真正缺的常常不是“更多报告”，而是能判断哪些报告是真的、严重度如何、补丁是否可接受、测试是否完整的人力。OpenAI 与 Trail of Bits 推出的 Patch the Planet 把这个问题做成完整闭环：Codex Security 和 GPT-5.5-Cyber 辅助发现、复现、写补丁和测试，Trail of Bits 安全工程师再负责去重、误报过滤、严重度校正、协调披露和与维护者一起落地。首周公开数据已经包括 19 个项目、64 个 PR、51 个 issue，覆盖 cURL、NATS、pyca、Sigstore、aiohttp、Go、Python、PyPI、RustCrypto 等基础设施项目。更重要的是，产物不只是 bug report，还包括 fuzzing harness、历史 CVE variant pipeline、differential testing、zizmor CI 扫描、SBOM sidecar 和 release pipeline 加固。这个项目值得高度关注，因为它把 coding agent 从“找问题的助手”推进到“有人工门控的修复流水线”。对后训练数据工程来说，这类轨迹非常宝贵：每个候选漏洞都有验证、误报过滤、补丁、测试、维护者反馈和披露状态，可以构成高质量安全 coding-agent 训练与评测样本。
🔗 链接：https://openai.com/index/patch-the-planet/ ｜ 代码：https://blog.trailofbits.com/2026/06/22/introducing-patch-the-planet/

### Codex-maxxing：把 Codex 长程工作做成 durable loop、memory 和 goals
很多人使用 coding agent 的方式仍是一次提示、一次回答、一次补丁，但复杂工作不会在一个 prompt 里结束：它会跨 Slack、PR、邮件、文档、浏览器和本地文件系统持续推进。Jason Liu 的 Codex-maxxing 把 Codex 当成“工作可以居住的地方”，核心是 durable thread、Heartbeats、Goals、disk-backed memory vault、remote steering 和可审阅 artifact。Heartbeats 让一个线程定期检查 Slack、Gmail、PR 或反馈线程；Goals 则要求用户给出可验证的完成标准，让 Codex 持续 plan-act-test-review，直到测试或验收条件通过。文章里最工程化的建议是把记忆写到文件系统，例如 Obsidian/GitHub vault，而不是只留在长聊天里；这样 agent 对人的偏好、项目状态、决策和开放循环的理解都可以被 diff、review 和回滚。它不是单纯的生产力技巧，而是把长程 agent loop 的状态、调度、验证和人工介入点讲清楚。对 harness 工程来说，这说明未来的 coding agent 竞争点会越来越多地落在 memory substrate、scheduler、artifact surface、approval gate 和 stop condition 上。
🔗 链接：https://openai.com/index/codex-maxxing-long-running-work/ ｜ 代码：https://jxnl.co/writing/2026/05/10/codex-maxxing/

### ClayBuddy：用可编辑上下文、命令分类器和确定性 guardrails 缓解 coding agent 高风险失败
真实 coding agent 事故往往不是经典 jailbreak，而是更日常的失配：用户没说清楚时 agent 默认做了危险动作，模型明知目标却没有坚持安全策略，或者 harness 把正确意图执行坏了。ClayBuddy 把这些失败拆成 underspecification、capability error 和 harness error 三个环节，并用 8 类场景、20 个代码环境和 59 个合成 transcript templates 来评估。它提出的缓解不是单一安全 prompt，而是一组 harness 机制：让 agent 能选择性缓存自己的历史上下文、把关键文件设成用户才能解除的 immutable 状态、在删除前强制 `ls -la`、在执行脚本前强制读取脚本，并用轻量命令风险分类器捕捉目标漂移。这个设计很务实，因为它承认模型有时需要“修改自己的工作环境”，但这种修改必须有可审计边界。论文报告这些机制在统计意义上提高安全性，虽然代码仓库还很早期，完整复现需要继续观察。对后训练软件工程的启发是，高风险轨迹不应只用自然语言拒绝来处理；很多安全行为应下沉到 deterministic guardrail、文件权限、命令前置条件和上下文编辑工具。
🔗 链接：https://arxiv.org/abs/2606.19380 ｜ 代码：https://github.com/kenneth-ge/opencode-context-engineering

### CoDA-Bench：在 980 文件级 Kaggle 沙箱中评测 code agent 的数据发现 + 编程能力
现有 coding-agent benchmark 多数假设目标数据已经给好，agent 主要负责读代码、改代码或跑测试；但真实数据工程任务里，最难的第一步常常是从一堆相似文件中找到真正相关的数据。CoDA-Bench 专门测这个缺口：它基于 Kaggle 生态构建 Linux 沙箱，每个任务环境平均约 980 个文件，agent 必须先探索目录和数据关系，再写代码完成可验证的分析问题。任务不是随便编出来的，而是从真实 Kaggle notebook 的结果反推问题，并通过静态数据流、动态执行和对抗式任务演化验证答案唯一性。数据规模为 1,009 个任务、31 个数据社区，另有 119 个 hard subset，代码仓库提供 Docker 评测环境。结果显示，当前强 agent 在全量任务上最高约 61.1%，在 CoDA-Hard 上约 49.6%，说明“会写代码”不等于“会在噪声数据湖里找到正确数据”。它对本日报核心方向很重要，因为 code LLM 后训练如果要服务数据工程，就需要记录 data discovery、文件筛选、脚本验证和错误数据源排除这些过程信号。
🔗 链接：https://arxiv.org/abs/2606.15300 ｜ 代码：https://github.com/ruc-datalab/CoDA-Bench

### DCIChecker：大规模检测 MCP tool 描述与真实代码不一致
MCP 工具体系默认把工具名称、schema 和自然语言描述暴露给模型，模型根据这些描述决定什么时候调用工具；但如果描述说“只读搜索”，实际代码还会写文件、上传日志或消耗大量资源，agent 就会在错误前提下行动。DCIChecker 研究的正是 Description-Code Inconsistency，也就是 tool 描述和实现代码之间的语义不一致。作者把问题分成两大类：功能不一致，例如夸大功能、遗漏功能、功能错配；以及未声明副作用，例如状态修改、资源过度消耗和数据外泄。方法上，它结合结构化静态分析和 Direct-Reverse-Arbitration prompting，用正向和反向问题交叉验证，再在冲突时仲裁，降低 LLM 判断的迎合和幻觉。大规模测量覆盖 2,214 个真实 MCP servers、19,200 对 description-code pairs，发现 9.93% 存在不一致。工程意义很直接：MCP registry、企业 connector 审批和本地 agent 配置不能只看 README 或 tool description，还应该在接入前做 description-code consistency check。
🔗 链接：https://arxiv.org/abs/2606.04769 ｜ 代码：None

### SafeMCP：在 MCP server 侧做前瞻性工具过滤和危险调用拦截
传统 agent guardrail 往往在模型已经提出动作之后才判断“这个动作危险吗”，这会漏掉一种更棘手的情况：当前动作看似无害，但它会让 agent 进入更高权限、更难控制的未来状态。SafeMCP 把防线放到 MCP server 侧，在工具返回给 agent 之前就根据环境状态预测哪些工具会扩大危险行动空间。它提出两层防御：第一层 proactive filtering 先过滤会导致未来危险状态的工具，第二层 immediate intervention 在实际危险调用出现时拦截。论文把这个问题形式化为 Stackelberg power game，用环境动态 grounding、safe policy initialization 和带可验证双奖励的 RL 训练防御策略。实验覆盖 PowerSeeking Bench、ToolEmu 和 AgentHarm，目标是在尽量保留任务 utility 的同时约束 agent 的 power boundary。它的工程价值是把 MCP server 从“工具列表提供者”升级成“权限和状态转移控制面”，这比在 prompt 里要求模型自觉小心更接近生产安全。对企业 agent 平台来说，SafeMCP 提醒我们 tool discovery、tool gating、权限升降级和环境状态应该合并设计。
🔗 链接：https://arxiv.org/abs/2606.01991 ｜ 代码：https://github.com/wlc2424762917/SafeMCP

### PrologMCP：把 Prolog 作为可复用 MCP 推理工具暴露给 LLM agent
LLM 在长链演绎推理上常常会“看起来在推理”，但每一步是否真是前一步的逻辑后果并没有保证；增加 thinking token 也只是更贵，不一定更可靠。PrologMCP 走另一条路线：让 LLM 把自然语言规则翻译成 Prolog 程序，由符号求解器负责确定性推理，再把错误和结果结构化返回给 agent 修正。它作为 MCP server 暴露 Prolog，支持有状态 session、每会话隔离解释器、typed JSON diagnostics、predicate inspection、hot clause replacement 和 translate-run-inspect-repair loop。论文在 PARARULE-Plus 的两个子集上测试，增强 PrologMCP 的 formalizer agent 在一般样本上达到或匹配 reasoning LLM，在挑战子集上仍接近满分，而自然语言 reasoning 模型会下降。它对 Agent-Friendly Software 很有价值，因为它展示了如何把一个老工具封装成现代 agent 可发现、可调用、可调试的标准接口。对后训练数据来说，这类轨迹还提供了明确的 verifier：逻辑程序能不能编译、查询是否成功、失败树指向哪里，都可以直接成为训练和筛选信号。
🔗 链接：https://arxiv.org/abs/2606.14935 ｜ 代码：https://github.com/dicelab-rhul/PrologMCP

### Sandboxed Coding Agents：用终端工具把视频/音频任务转成可验证信息处理流水线
很多多模态任务默认被理解为“必须用原生音视频模型直接看完整媒体”，但这篇工作指出，sandboxed coding agent 可以把视频、音频和文档先转成 transcript、抽帧、OCR、元数据和中间文件，再用代码和工具链做信息处理。它在 Codex 和 Claude Code harness 上测试，发现 GPT-5.4 xHigh 的 Codex 在 OmniGAIA 上达到 75.0%，超过研究中最强 native omni model Gemini 3.1 Pro 的 66.1%。作者进一步做 trajectory analysis，发现优势来自 staged tool use，而不是模型直接感知原始视频；agent 会选择性调用 ffmpeg、ASR、OCR、脚本和文件分析工具来压缩证据。更贴近后训练的是 Code-X：它构造 6,035 条 OmniCoding 轨迹，用 SFT warm-start 加 GSPO RL，并设计 process-aware verifiable reward，惩罚跳过模态、工具调用格式错误和最终答案错误。论文还提出 TerminalBench-O，评测 agent 在真实多模态处理任务中的中间 artifact 和最终输出合规性，最强 GPT-5.5 Codex 也只有 24%。这项按 Medium 收录，因为主题偏多模态，但它对 harness 工程很有启发：许多“感知问题”可以被转成可验证的工具流水线和过程监督问题。
🔗 链接：https://arxiv.org/abs/2606.00579 ｜ 代码：https://github.com/Dongping-Chen/OmniCoding

### ScholarQuest：面向学术论文搜索 agent 的分类法引导 benchmark
研究 agent 做文献检索时，普通检索指标很容易失真，因为用户真正的问题常常带方法、场景、对比或范围约束，而不是只输入几个关键词。ScholarQuest 把学术论文搜索做成多轮 agent benchmark，覆盖 1,000+ 个计算机科学 topic 和四类研究意图：method-oriented、setting-anchored、comparison-based、scope-controlled。它还提供 ScholarBase 作为统一检索后端，包括论文元数据、引用关系、搜索、inspection 和 citation expansion 接口，让不同 agent 在同一个环境里比较。答案构造不是纯人工标注，而是用初始检索、引用扩展、多阶段相关性过滤和质量验证形成可扩展 gold set。实验显示，agentic search 优于 single-shot retrieval，但最佳系统 Recall@100 只有 0.314，Recall@All 只有 0.355，说明复杂约束下仍有大量 off-target exploration。它对本日报的间接价值是评测设计：不仅看最终找到哪些论文，还记录 search calls、expansion calls、候选观察数、不同 intent 下的鲁棒性，这些都是 search-agent 后训练和失败分析需要的过程信号。
🔗 链接：https://arxiv.org/abs/2606.20235 ｜ 代码：https://github.com/pty12345/ScholarQuest

### Workflow-GYM：专业 GUI 软件里的长程 computer-use workflow 评测
GUI agent 的很多评测仍停留在浏览网页、点设置、填表单等通用软件任务，但真实工作里大量高价值流程发生在专业软件中，例如设计、分析、行业工具或复杂桌面应用。Workflow-GYM 把“workflow”定义成专家日常完成的长程、可产生经济价值的 GUI 操作序列，并要求任务有真实软件环境、自然语言目标、无中间提示、自动可验证的最终状态或 artifact。构造流程由领域专家提出真实工作任务，再经过多阶段筛选、环境实例化和验证，确保任务不能简单搜索到答案，也不是短操作。实验发现，即使最强模型也只有略高于 30% 的成功率，失败集中在漏掉 workflow stage、错误传播、目标漂移和专业软件知识不足。它按 Medium 收录，因为不是代码仓库修复，但与 Agent-Friendly Software / Computer Use 方向直接相关。对工程落地来说，这类 benchmark 提醒我们：如果传统软件无法 CLI 化或 API 化，至少要为 GUI agent 建立可复现环境、明确 final-state oracle 和可审计操作轨迹。
🔗 链接：https://arxiv.org/abs/2606.11042 ｜ 代码：None

### Codex-Workflows：给 Codex subagents / MCP / skills 加 workflow-as-code 控制面
随着 Codex 支持 subagents、skills、MCP 和 goals，复杂任务已经可以被拆成多个并行 worker，但原生能力之外还缺一个“工作流控制面”：谁在跑、跑到哪、失败能否重启、阶段结果如何传递。Codex-Workflows 试图补这层，它用 TypeScript 做 workflow-as-code runtime，提供 phase DAG、live terminal dashboard、restartable agents、saved workflow scripts 和 review templates。README 提到它能显式请求最高 64 个并发 workers 和 2,000 个总 agents，并通过 MCP server 让 Codex 启动和查询 workflow run。它还把前一阶段 findings 显式传给后续 verify、probe、synthesize agents，避免每个子 agent 都重新猜历史。虽然当前 star 只有数十个，仍处在早期社区项目状态，但它击中的痛点很真实：长程多 agent 不需要更多聊天窗口，而需要进度、心跳、暂停/恢复、token/tool/time 指标和最终报告路径。对内部平台来说，这类项目可作为轻量原型，观察 Codex 生态如何把 subagent 能力产品化成可审计 pipeline。

## 🔥 社区热点专栏

### 🔥 大佬观点

**Jason Liu（OpenAI / @jxnlco）：长程 agent 的关键是 operating loop，而不是更长聊天。**
Codex-maxxing 的核心观点是，工作要有 durable thread、Heartbeats、Goals、disk-backed memory 和可审阅 artifact，才能在用户离开后继续推进。它值得注意，因为这把“提示词技巧”推进到 agent runtime 设计：状态写到文件、验收标准可运行、反馈由 heartbeat 触发、人工通过 diff 和 side panel 复核。🔗 https://jxnl.co/writing/2026/05/10/codex-maxxing/

**Trail of Bits：AI 找 bug 已经不是瓶颈，确认、修复、测试和披露才是瓶颈。**
Trail of Bits 在 Patch the Planet 复盘中明确说，Codex/GPT-5.5-Cyber 能把 fuzzing lab、CVE variant pipeline 和 differential testing 从数周压缩到数小时，但真正昂贵的是去重、误报过滤、严重度校正、写可接受补丁和协调披露。这个观点对安全 coding agent 很关键：如果没有工程师复核和项目特定 threat model，AI 生成的安全报告只会扩大维护者 backlog。🔗 https://blog.trailofbits.com/2026/06/22/introducing-patch-the-planet/

### ⭐ 超火仓库/项目

**Patch the Planet：不是“爆火 repo”，而是本周最有信号的 AI-assisted OSS security 项目。**
它火的原因是给出了真实产出数字：首周 19 个项目、64 个 PR、51 个 issue，且包含测试、CI、安全扫描、供应链工具和 disclosure 流程。它解决的痛点是开源维护者被 AI 生成漏洞报告淹没后，真正需要的是高信号、可复现、带补丁的工作流。🔗 https://openai.com/index/patch-the-planet/

**AgentArmor（Agastya910/agentarmor）：HN 讨论中的 8-layer agent security / MCP scanner。**
社区关注点集中在它把 agent 安全拆成 ingestion、storage、context、planning、execution、output、inter-agent、identity 八层，并以 MCP server 形式给 Claude Code、OpenClaw、Cursor 等工具调用。最有价值的不是又一个 prompt scanner，而是 `armor_scan_mcp_server` 这类 MCP rug-pull / TLS / OAuth / tool contract 检查，正好对应本期 DCIChecker 论文暴露的描述-实现不一致风险。🔗 https://github.com/Agastya910/agentarmor ｜ HN：https://news.ycombinator.com/item?id=47374958

**CoDA-Bench：数据密集型 coding-agent benchmark 开始补 SWE-bench 盲区。**
项目虽然 star 仍不高，但 ICML 2026、1,009 任务、Kaggle 数据生态、Docker 评测和平均 980 文件环境让它很适合成为数据工程 agent 的新回归集。它火在解决一个真实痛点：agent 不只是写代码，还必须在噪声文件系统中找到正确数据并验证结果。🔗 https://github.com/ruc-datalab/CoDA-Bench

**Codex-Workflows：Codex subagents、MCP、skills 之后需要 workflow-as-code。**
这个早期项目把 Codex 多 agent 运行包装成 phase DAG、live TUI、heartbeats、restartable workers 和最终报告路径，当前约 58 stars。它值得观察，因为 Codex 生态正在从“让模型 spawn subagents”走向“给 subagents 一个可暂停、可恢复、可度量的控制面”。🔗 https://github.com/robzilla1738/Codex-Workflows
