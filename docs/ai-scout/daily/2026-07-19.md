## 📝 逐条讲解

### Senior SWE-Bench：用“高级工程师级”任务评估 coding agent
许多 coding-agent benchmark 给的是很详细的技术规格，agent 只要按步骤实现并通过预写测试即可，但真实高级工程师收到的任务往往更像 Slack 或产品经理消息：描述目标，不规定实现路径。Senior SWE-Bench 试图把这个差距做成评测集，它从 12 个生产仓库的真实 PR 中构造 100 个任务，其中 50 个公开、50 个私有，用来降低污染和 benchmark 记忆风险。它覆盖复杂 feature、迁移、bug、性能问题等场景，并且刻意保留设计空间，让 agent 自己决定接口、模块边界和实现方案。最关键的新机制是 validation agent：专家先写抽象测试 recipe，验证 agent 再根据提交 patch 生成具体可执行测试，最后程序化运行，而不是只靠 LLM judge 看代码像不像。它还加入 taste judge，检查方案是否符合现有代码库风格、是否足够简洁、是否具备高级工程师会认可的 hygiene。当前领先模型 Claude Fable 5 的 tasteful solve rate 只有 29.1%，说明即使强模型也远未达到稳定高级工程师水平。对后训练软件工程来说，这类 benchmark 的价值在于把“开放设计 + 行为验证 + 代码质量 + 反作弊”合成一套更接近生产的 eval pipeline。
🔗 链接：https://snorkel.ai/blog/senior-swe-bench-evaluating-coding-agents-like-senior-engineers/ ｜ 代码：https://senior-swe-bench.snorkel.ai

### Reward-Free Evolving Agents：用 pairwise validator 替代自演化 agent 的标量奖励
自演化 agent 的常见做法是不断改自己的 prompt、程序或工具策略，然后用一个质量信号决定新版本是否留下。难点在于，这个质量信号通常很贵：要么需要领域专家设计标量 reward，要么需要带标签验证集，而这些成本可能和原任务一样高。Reward-Free Evolving Agents 提出把绝对打分换成 pairwise validator，也就是让一个冻结 LLM 比较 parent 和 child 两个候选，直接判断哪个更好。这个思路像代码评审里的“这个 patch 比上一个更好吗”，比要求评审者给 0 到 100 的精确分数更稳定，也减少了尺度校准问题。论文把这个 gate 接进 GEPA、ADRS、ShinkaEvolve 三个已有自演化引擎，并测试 prompt 和 code 两种 artifact substrate，结果在多数设置中达到或超过完整 reward baseline。它还给出 Soft Elo 变体，让 pairwise verdict 同时影响 parent selection，进一步减少对验证集标量分数的依赖。对轨迹筛选和 skill evolving 来说，这很有启发：很多时候我们不需要先定义完美 reward，只要能稳定比较“哪条轨迹/哪版技能更值得保留”，就能启动可扩展的演化闭环。
🔗 链接：https://arxiv.org/abs/2607.14408 ｜ 代码：None

### CAGE-1：企业 agent 上线前的控制、审计与 Prebind Assurance 评估框架
企业部署 agent 时，问题不只是回答是否正确，而是 agent 是否被授权、调用的工具是否允许、检索证据是否过期、记忆是否被污染、动作在产生业务后果前能不能被拦住。CAGE-1 把这些问题组织成 Control、Assurance、Governance Evaluation，用来判断企业 agent 是否可以进入真实工作流。它覆盖 authority、policy enforcement、retrieval quality、memory integrity、tool safety、auditability、human oversight、safe failure 等维度，而不是只测一次任务成功率。论文提出的 Prebind Assurance 很重要：在动作真正绑定到业务系统前，系统要能证明这个动作已被 admission、hold、narrow、refuse、escalate、quarantine 或 make non-effective。通俗说，agent 不应该先改生产系统再让审计系统补救，而应在动作生效前就被控制层裁决。它按 High 收录，是因为它把 agent 安全从“有没有 guardrail”推进到可评估的上线门槛，特别贴近工具权限、MCP、记忆和审计工程。对后训练数据来说，这意味着轨迹里应保存授权链、policy 决策、证据新鲜度、工具许可和 human escalation，而不只是保存 tool call 本身。
🔗 链接：https://arxiv.org/abs/2607.03510 ｜ 代码：None

### OpenAI codex-plugin-cc：Claude Code 内调用 Codex review/rescue/transfer 的官方桥
很多开发者实际会同时使用 Claude Code 和 Codex：一个擅长规划或交互，另一个擅长 review、rescue 或特定模型家族能力，但手工在两个 CLI 之间复制上下文很脆弱。OpenAI 的 `codex-plugin-cc` 是官方 Claude Code marketplace plugin，提供 `/codex:review`、`/codex:adversarial-review`、`/codex:rescue`、`/codex:transfer`、`/codex:status` 等命令，把 Codex 变成 Claude Code 会话里的可委派协作者。它不是 7 月才发布的新项目，但 7 月 8 日 v1.0.6 之后被社区重新发现，相关讨论把“两个竞争产品变成同一终端里的队友”推到热点。工程上最有价值的是它区分 read-only review、可编辑 rescue、后台任务、session transfer 和 review gate，不只是简单执行一个 `codex` shell 命令。官方插件还继承本机 Codex 配置与认证，让双 agent 工作流从临时 bash wrapper 变成可安装的 harness 扩展。风险也很明确：review gate 可能形成 Claude/Codex 长循环并快速消耗额度，企业还要同时治理两个 agent 的权限和 destructive-command 边界。对后训练软件工程来说，这类桥接会产生新的轨迹结构：主 agent 的计划、被委派 agent 的审查/修复、跨会话 transfer、以及人类何时接受 second opinion，都应被结构化记录。
🔗 链接：https://github.com/openai/codex-plugin-cc ｜ 代码：https://github.com/openai/codex-plugin-cc

### freeCodeCamp：用四道验证门和用户权限 MCP 把公司流程做成 AI-native
这篇开发者案例从一个很具体的企业痛点出发：文档会随着代码变更逐渐过期，尤其在受监管的 lending 系统里，过期文档会变成业务风险。作者用 Claude Code 构建内部文档平台，但重点不是“模型写了多少代码”，而是用 harness 让 agent 的输出可被信任。四道门很朴素：全仓 `tsc --noEmit`、核心业务逻辑 100% 覆盖、Playwright E2E、以及每次改动后真实运行应用观察行为。文章里最有价值的反思是，最严重的权限泄露 bug 仍然通过了所有门，最后靠真实使用发现，这说明 harness 不是取代人类判断，而是把人类判断从逐行 review 转移到设计 gate 和发现未编码失败类型上。后半部分的 MCP 设计同样重要：MCP server 不持有共享数据库凭证，而是转发每个用户自己的 token，由后端按当前 RBAC 做权限检查并写审计日志。这样 agent 的能力等于运行它的人，而不是一条绕过公司权限模型的后门。对 Agent-Friendly Software 来说，这是一条很实用的落地路线：先把流程数据结构化，再通过 MCP 暴露给 agent，同时保持真实用户身份、可撤销 token 和 boring error paths。
🔗 链接：https://www.freecodecamp.org/news/harness-engineering-ai-native-company/ ｜ 代码：None

### Harnessing LLMs for Reliable Academic Supervision：小模型 + LangGraph harness 胜过裸 GPT-5
这篇论文的场景是 academic supervision，不是软件工程本身，但它用清晰的 ablation 展示了 harness engineering 为什么不能只被看作“提示词包装”。作者比较一个没有脚手架的 GPT-5 chatbot baseline 和一个用 GPT-4o-mini 驱动的 ASuS 系统，后者外面包了 LangGraph harness。这个 harness 包括 symbolic-semantic retrieval、schema-validated outputs、LLM-as-judge bounded retry、HITL gates、确定性 weighted risk scoring，以及 per-node SQLite audit trail。十名盲评者在 grounding、explainability、consistency、process integrity、cognitive load、constraint adherence 六个维度上打分，ASuS pooled mean 为 4.08，而裸 GPT-5 为 1.23。2x2 model-harness ablation 进一步说明，结构化 harness 的贡献在很大程度上跨模型成立。它按 Medium 收录，因为领域不是 coding agent，但工程结论很强：如果系统需要追责、长期一致性和可审计流程，较小模型加好 harness 可能胜过更大裸模型。对后训练软件工程来说，这提示我们在构造训练样本时要记录 scaffold 组件和审计节点，否则会误把 harness 带来的可靠性归功于模型。
🔗 链接：https://arxiv.org/abs/2607.14707 ｜ 代码：https://doi.org/10.5281/zenodo.21380237

### awesome-harness-engineering：3.1k★ 的 agent harness 工程索引与模式库
社区围绕 coding agent 的讨论正在从“哪个模型最好”转向“怎样组织工具、权限、memory、评测和可观测性”，但这些知识分散在论文、博客、插件和仓库里。`awesome-harness-engineering` 把 agent harness engineering 的工具、模式、eval、memory、MCP、permission、observability 和 orchestration 收到一个索引里，7 月 18 仍有更新，GitHub 约 3.1k stars。它本身不是新算法，也不是生产级 runtime，但作为知识库很有价值：它把日益碎片化的 Claude Code、Codex、OpenCode、MCP、skills、hooks 等实践放到同一张地图上。对于团队选型来说，这类 curated list 可以降低初次进入的搜索成本，帮助工程师知道哪些概念已经形成社区共识，哪些仍只是一次性 demo。它也反映了一个趋势：harness engineering 正在变成独立工程门类，开始需要 awesome list、compatibility matrix、best-of catalog 和可安装模板。风险是 awesome list 容易追热点而缺少验证，所以使用时仍要回到 star 质量、维护频率、真实案例和安全边界。对后训练数据工程来说，这类索引不是训练数据本身，但能帮助定义轨迹元数据 taxonomy，例如 tool governance、context source、verification gate 和 human handoff。
🔗 链接：https://github.com/ai-boost/awesome-harness-engineering ｜ 代码：https://github.com/ai-boost/awesome-harness-engineering

### best-of-Agent-Harnesses：把 100+ harness 排名和推荐做成可被 agent 调用的 MCP server
当 agent harness 数量越来越多时，开发者不只需要链接列表，还需要根据任务复杂度、自治程度、恢复能力、MCP 支持、安全边界和维护状态做选择。`best-of-Agent-Harnesses` 的特别之处在于，它不只是人工 curated README，还提供 MCP server，让 agent 自己调用 `recommend`、`pick_harness`、`search_harnesses`、`get_harness`、`list_categories` 等工具来辅助选型。项目约 342 stars，7 月 18 仍在更新，并声称对 100+ agent harness 做 weekly rescoring。这个设计有点 meta：用一个 agent-friendly 目录帮助 agent 或开发者选择运行 agent 的 harness。工程价值在于把选型标准结构化，而不是只凭 GitHub stars 或社交媒体热度；例如复杂度、autonomy、recovery filter 会比“最火”更适合企业实际约束。它按 Medium 收录，因为目录评分方法仍需审慎对待，但方向很贴近工具供应链治理。对后训练和评测来说，未来自动生成实验矩阵时，agent 也许可以基于这种目录选择 harness 组合，并把选择理由写入评测元数据。
🔗 链接：https://github.com/RyanAlberts/best-of-Agent-Harnesses ｜ 代码：https://github.com/RyanAlberts/best-of-Agent-Harnesses
