## 📝 逐条讲解

### Lego-RL：在原生 coding-agent harness 中做在线 RL
很多 coding-agent 后训练论文会把 agent loop 改造成训练框架容易消费的格式，但这样会制造一个问题：训练时看到的轨迹，和真实 Claude Code、OpenHands、OpenCode 运行时的轨迹不完全一样。Lego-RL 解决的是这个“训练-推理不一致”问题，它不重写原生 harness，而是在模型 API 旁边放一个 in-process LLM proxy，捕获真实生成 token、上下文重写、compaction 和 MoE routing 信息。这样 trainer 可以在自己侧重新计算 log probability，保证 policy-gradient 更新对应的就是 agent 当时真实采样出的行为。执行侧，它把每条仓库任务放进 Harbor sandbox，用镜像缓存、阶段式校验、termination-aware filtering 和 reward-hack defense 保护稀疏 verifier reward。它还提供 live dashboard 和 trajectory diagnostics，让训练团队能看到失败到底来自 agent、环境、verifier、sandbox 还是优化器。实验中，Qwen3.5-35B-A3B 在 OpenHands SDK、Claude Code、OpenCode 三个原生 harness 上的 SWE-bench Verified resolve rate 都有 5.8 到 9.4 个百分点提升，并保持 rollout-training probability correlation 高于 0.99。对后训练软件工程来说，这篇的价值不在某个 RL 算法细节，而在把“真实 harness 中采样的轨迹”安全、可观测、可复现地接进训练管线。
🔗 链接：https://arxiv.org/html/2608.17393 ｜ 代码：https://github.com/LegoX/Lego-RL

### HarnessRisk：按生命周期阶段评测 agent harness 安全
许多 agent 安全评测只看运行中是否执行了坏工具调用，但真实 harness 的安全边界从配置阶段就开始了：连接器、权限模板、扩展安装、持久状态、恢复流程都会影响最终风险。HarnessRisk 把 agent harness 安全拆成六个生命周期阶段：Harness Configuration、Capability Extension、Runtime Operation、State Persistence、Action Control 和 Incident Recovery。它构造了 128 个 sandboxed workflows，每个都把良性用户目标和藏在非可信 workflow artifact 里的攻击指令组合起来，避免只测裸 prompt injection。评测指标也不是单一成功率，而是同时看 Utility、Attack Success Rate、Persistence 和 Detection，区分“任务做完了”和“安全地做完了”。结果显示，高 Utility 可以和高 ASR 同时存在，攻击成功率在不同 model-harness 配置下从 12.6% 到 80.9% 波动，最脆弱阶段还是配置阶段。一个很重要的工程结论是，模型显式识别风险并不等于会安全行动，有些配置 Detection 超过 90% 仍保留明显攻击成功。对 agent eval 和后训练数据筛选来说，这说明安全标签必须绑定生命周期阶段和 harness 配置，不能只保存一条笼统的“安全/不安全”结论。
🔗 链接：https://arxiv.org/html/2608.17597 ｜ 代码：https://github.com/Baiyajing/HarnessRisk

### HarnessSafe：追踪 memory / skills / MCP 等持久载体的延迟风险
现代 coding agent 越来越依赖 memory、skills、MCP tools、session summaries 和 shared artifacts，这些东西让 agent 能跨任务积累经验，也让恶意内容有机会“存下来、过一会儿再触发”。HarnessSafe 研究的正是这种 delayed safety risk：攻击输入可能在当前任务看起来无害，却被写入某个持久载体，并在之后的良性请求中重新进入执行链。它提出 Persistent-Risk Lifecycle，把风险从最初进入、被保存、跨边界传播、被良性任务触发，到最终造成可观察 violation 的路径完整描述出来。基准包含 328 个可执行 case，覆盖 memory、skills、Tool/MCP、memory-to-skill transformation、subagent delegation、session summary 和 shared-artifact reuse 等七类载体。它不只报告 attack success rate，而是用七阶段 trace-based evaluation 和 Chain-Stage Score 记录攻击链在哪一步被拦住。论文发现，固定 GPT-5.6-Sol 时，不同 harness 的 CSS 可以从 39.4 变到 62.3；固定 Claude Code 时，换后端模型也会让 CSS 从 22.7 到 58.7 大幅变化。对工程团队的启发是，持久状态安全不能只靠“更安全的模型”，还要逐载体设计写入审查、读取隔离、来源追踪、失效和清理机制。
🔗 链接：https://arxiv.org/abs/2608.06984 ｜ 代码：None

### RETRACE：用反向问题重构做 coding-agent patch 独立验证
Coding agent 现在能很快产出 patch，但一个经常被低估的问题是：补丁看起来合理、甚至通过了部分自检，不代表它真的修了用户报告的问题。RETRACE 的核心思想很直观：不要只让模型继续解释自己为什么对，而是反过来只看补丁和轨迹，推断“这个补丁到底像是在修什么问题”。它先做 forward reconstruction，从原 issue 和 agent 轨迹里抽出显式修复理由、证据和预期修改；再做 backward reconstruction，在不看原 issue 的情况下，从 patch 和相关轨迹反推被解决的问题。随后 reconciliation 阶段比较这两个视角，判断补丁是否在修原问题、是否修了一个 phantom issue，以及偏差来自推理、实现还是二者都有。这个过程不需要训练新 verifier，也不依赖 ground-truth patch，因此适合接在现有 mini-SWE-agent、OpenHands 或 Codex/Claude Code 的 PostToolUse / pre-submit hook 后面。实验中，RETRACE 在 SWE-bench Verified 上让 GPT-5-mini + mini-SWE-agent Pass@1 从 56.2% 到 63.2%，MiniMax-2.5 从 75.8% 到 79.4%，在 OpenHands 上也有类似提升。对后训练数据工程来说，它提供了一种很好的“轨迹质量信号”：好轨迹不只是有最终 diff，还应该能从 diff 反推出和原问题一致的规格。
🔗 链接：https://arxiv.org/html/2608.08950 ｜ 代码：None

### Palmyra x6：626 条高质量合成 tool-use 轨迹 + ASFT 后训练
很多 agentic model 报告会强调巨大数据量，但 Palmyra x6 走的是相反路线：用很小但严控质量的 synthetic tool-use trajectory corpus 做后训练。Writer 的技术报告说明，它在 GLM-5.2 系列 744B MoE base 上训练，目标能力是企业场景里的 multi-step planning、tool/function calling、MCP suite、web search、code execution sandbox 和 RAG workflow。训练数据只有 626 条 curated synthetic trajectories，任务提示来自 Writer 内部 SME 和部分外部 benchmark/task suite，而 assistant 的 plan、tool call 和 final answer 都是机器生成。关键工程点是 ASFT（Anchored Supervised Fine-Tuning）：在 SFT 外加 KL anchor，尽量让模型学会 agentic tool-use，同时不破坏 base model 原有能力。报告还做了 12 组 recipe exploration，固定数据配方后比较 SFT/ASFT、anchor strength、learning rate、epoch 和 optimizer，减少把效果归因到混杂变量。它在 MCP-Atlas、FinanceBench、IFBench 等六个评测上相对 Writer Agent 前一默认模型都有显著提升，并发布 BF16 / FP4 变体（商业许可）。对本日报的重点来说，它的启发是：agent 后训练数据的价值来自任务来源、轨迹过滤、目标函数和 ablation 纪律，而不是单纯堆更多合成样本。
🔗 链接：https://arxiv.org/abs/2608.16620 ｜ 代码：None

### GitHub Copilot Harness + Microsoft Agent Framework 稳定版
很多企业已经在用 GitHub Copilot 写代码，但如果想把 Copilot 的 coding-agent 能力嵌进更大的 agent workflow，过去通常要自己封装 CLI、审批、会话、工具和日志。Microsoft Agent Framework 这篇官方博客把 GitHub Copilot Agent 标为 .NET 和 Python 的稳定集成：Copilot 继续拥有底层 agent loop，包括模型调用、工具执行、planning 和 session state；Agent Framework 则提供统一的 run interface、streaming、middleware、tools、observability 和 human-in-the-loop approval。工程上，它支持 shell、文件读写、URL fetching、MCP servers、自定义函数工具和 session resume，每一类敏感动作都通过 permission handler 或 approval-required function gate 处理。这样开发者不是重新造一个 coding agent，而是把 Copilot CLI/SDK 当作可治理的执行引擎嵌入系统。内置 OpenTelemetry 也很关键，因为 coding agent 真正进生产后，团队需要看 tool span、token、错误、审批和运行时间，而不是只看最终答案。它的价值在于把“使用 Copilot”升级成“把 Copilot harness 作为企业 agent runtime 的一个 provider”。对后训练软件工程来说，这种 provider abstraction 会产生更标准化的运行轨迹，也会让不同 harness 的权限、工具和观测字段更容易比较。
🔗 链接：https://devblogs.microsoft.com/agent-framework/build-production-ready-agents-with-the-github-copilot-harness-and-agent-framework/ ｜ 代码：https://github.com/microsoft/agent-framework

### HarnessRouter：面向 Codex / Claude Code / Hermes 的统一 Harness API
现在很多产品团队面临一个新问题：不是缺模型 API，而是不同 agent harness 的任务、会话、文件、事件流、取消、恢复和 artifact 交付格式都不一样。HarnessRouter 的定位类似“面向 harness 的 LiteLLM”：用 Unified Harness Protocol 把 Codex、Claude Code、Hermes 等 runtime 包成统一 API。它的 Community Edition 是自托管网关，支持 harness CRUD、sessions、streaming、files、cancellation、failure handling，并允许配置 instructions、skills 和 MCP tools。HN launch 中作者说得很直接：frontier labs 和开源社区已经投入大量工程做 harness，与其每个产品自己重造 agent loop，不如像调用 LLM endpoint 一样调用 harness。项目 8 月 9 日创建，核验时约 363 stars、26 forks，热度不算 DeepSeek Harness 那种爆发级，但问题定义很清晰。真实痛点是 agentic product 需要把“用户给任务、系统跑 agent、返回成品”的流程服务化，而不是要求终端用户自己会用 Claude Code 或 Codex。对 eval 和后训练来说，UHP 这类协议如果成熟，会让跨 harness 任务日志、失败模式和成本字段更可比。
🔗 链接：https://github.com/HarnessRouter/harnessrouter ｜ 代码：https://github.com/HarnessRouter/harnessrouter

### Nimbalyst Agent Harness：把项目层 harness 拆成八个可拥有的工程层
这篇 Nimbalyst 博客不是论文，也没有大规模实验，因此按 Medium 收录；但它很好地总结了团队在 vendor harness 之上还需要拥有什么。作者把 Claude Code 和 Codex 看作底层 harness，而团队还需要一个项目层 harness：把代码、规格、决策、规则、工具、验证、视觉界面和多 agent 协调放在可读、可编辑、可版本化的文件与工作区里。文章用八个 failure modes 推出八个 pillars：context、provenance、capability、workflow、restraint、verification、visual interface 和 coordination。它的具体做法包括 root instruction files、path-scoped rules、skills、bug history、Excalidraw diagrams、tracker-linked decisions、permission/allowlist 和 paired-run benchmark protocol。价值在于把“agent harness”从抽象术语变成仓库结构和团队资产：模型可以换，项目规则、验证方式和工作流证据应该留在团队控制下。它还给出 `docs/THE_HARNESS.md` 这类 living catalog，让后来 agent 能读到真实规则和经验，而不是每次从聊天上下文重新学习。对后训练数据来说，这类项目层 harness 文档是重要上下文源，因为它解释了轨迹中很多动作为什么被允许、被拒绝或被验证。
🔗 链接：https://nimbalyst.com/blog/agent-harness-above-claude-code-codex/ ｜ 代码：https://github.com/Nimbalyst/nimbalyst/blob/main/docs/THE_HARNESS.md

### Copilot / VS Code OpenTelemetry：把 agent 使用、工具调用和 token 成本导出到 OTLP
Agent observability 近期已经从研究项目进入主流开发工具，Copilot / VS Code 的 OpenTelemetry 文档就是一个很典型的工程化信号。它允许 Copilot Chat agent interactions 导出 traces、metrics 和 events，字段遵循 OTel GenAI Semantic Conventions，因此 Jaeger、Azure Monitor 或其它 OTLP backend 都能消费。文档里列出的设置包括 `github.copilot.chat.otel.enabled`、exporter type、OTLP endpoint，以及默认关闭的 content capture，这说明隐私和可观测性需要同时设计。更细的价值在 span hierarchy：用户请求、Copilot CLI wrapper、SDK native spans、subagents、permissions、hooks 和 tool calls 可以形成一棵可追踪执行树。配合企业 managed settings，管理员可以统一下发 endpoint、headers、resource attributes 和 capture 策略，减少每个开发者自己乱配造成的数据缺口。对 coding-agent eval 来说，这类 traces 能把“这个 patch 为什么贵、为什么慢、哪里卡住、哪个工具失败”变成可查询事实。对后训练数据工程来说，标准化 OTel trace 也可能成为未来 trajectory schema 的事实基础，比事后解析自由文本 transcript 更可靠。
🔗 链接：https://code.visualstudio.com/docs/agents/guides/monitoring-agents ｜ 代码：None

### OpenAI Zero Data Retention for frontier models：ZDR 下的跨交互安全处理
OpenAI 8 月 19 日的官方文不直接讨论 coding agent，但它触及长程 agent 生产部署的一个核心矛盾：企业希望 Zero Data Retention，不希望 prompts/responses 被保留或人工查看；安全团队又需要识别跨多次交互才会显现的滥用模式。OpenAI 提出 Private Safety Processing，目标是在不让 OpenAI personnel 访问底层内容的情况下，对相关交互做自动化模式识别并返回有限安全信号。文中提到两种部署形态：内容保留在客户控制的基础设施里，或存放在 OpenAI 基础设施但由客户控制密钥加密。这个方向对 agent workflow 很重要，因为长程 coding/cyber agent 的风险经常不在单次请求，而在多轮工具调用、任务拆解和上下文累积中才显现。它目前仍是 preview，白皮书计划 9 月发布，因此按 Low 可信官方项而不是工程可复现框架处理。对后训练和评测来说，ZDR 场景下的安全 telemetry 会影响我们能收集什么轨迹、能保存哪些字段、能否跨 session 判断风险。它也提醒团队：隐私边界、数据保留策略和安全监控不是法务附属项，而会直接决定 agent 数据管线的可用信号。
🔗 链接：https://openai.com/index/offering-zero-data-retention-for-frontier-models/ ｜ 代码：None

## 🔥 社区热点专栏

### 🔥 大佬观点

**HN / Codex 实战讨论：很多开发者开始按“任务形态”而不是品牌选择 Claude Code、Codex、OpenCode 或其它 harness。**  
`Quick impressions: A week of using Codex more than Claude` 这类讨论的价值不在排行榜，而在真实用户开始比较 quota、稳定性、并行后台任务、复杂重构和 over-engineering 风格。它提醒 eval 团队：同一个模型分数不足以解释用户迁移，harness 的交互模型、审批策略、价格形态和失败恢复会决定生产偏好。🔗 https://news.ycombinator.com/item?id=49393051

**HarnessRouter / HN：应用不一定要重造 agent loop，可以像调用模型 API 一样调用成熟 harness。**  
HarnessRouter 作者在 Show HN 中把 UHP 类比为 harness 领域的 LiteLLM：不同 runtime 继续各自演化，但应用侧只对接统一 task/session/event/artifact 协议。这个观点值得注意，因为它把 agent 产品工程从“选一个 SDK 重写 loop”转向“把 Claude Code、Codex、Hermes 当可替换执行后端”。🔗 https://news.ycombinator.com/item?id=49335595

**MicroCodex / HN 讨论：轻量 agent runtime 的争论焦点不是二进制大小，而是 feature parity、可维护性和可嵌入性。**  
MicroCodex 用 C++ 重实现 Codex 风格终端 agent，号称小于 1MB，引发了“harness 是否需要小”和“是否能跟上官方 Codex 更新”的讨论。真正的 insight 是：边缘设备、短生命周期 sandbox、eval worker 可能需要轻量 runtime，但如果缺少 MCP、skills、compaction、权限和维护策略，小体积本身并不能保证生产价值。🔗 https://news.ycombinator.com/item?id=49147842

### ⭐ 超火仓库/项目

**HarnessRouter/harnessrouter：约 363 stars，把 Codex、Claude Code、Hermes 接到同一个自托管 Harness API。**  
它火在提出了一个非常具体的新层：模型有 LiteLLM，agent harness 也需要统一协议、会话管理、事件流、取消/恢复和 artifact 交付。对产品团队来说，这解决的是“我想把成熟 coding agent 放进自己的应用，但不想每个 runtime 写一套集成”的痛点。🔗 https://github.com/HarnessRouter/harnessrouter

**LegoX/Lego-RL：约 46 stars，但论文与代码同步公开，切中 harness-native RL 训练基础设施。**  
它不是社区爆款，但对后训练工程人群很有信号：把 Claude Code / OpenHands / OpenCode 这类真实 harness 接进 verl、Harbor、sandbox reward 和 live dashboard，是当前 coding-agent RL 的关键基础设施问题。它解决的是“训练管线要忠实观察真实 agent loop，而不是在实验室重造一个假 loop”的痛点。🔗 https://github.com/LegoX/Lego-RL
