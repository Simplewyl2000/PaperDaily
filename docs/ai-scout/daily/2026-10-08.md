## 逐条讲解

### CheckerBench：长程 agent 能否写出静态分析 checker
现在的 coding agent 基准大多考"修一个 bug"或"找一个漏洞"，但安全团队真正想要的往往是一个**可复用的静态分析 checker**——写一次，就能在整个代码库里持续拦截同一类漏洞。写 checker 比打补丁难得多：要读懂缺陷描述，摸清仓库结构，用某个分析器（如 CodeQL 这类工具）专门的规则语言写逻辑，再根据编译和分析结果反复调整。CheckerBench 从 167 个仓库的 297 个 CVE 中构造了 300 个任务，覆盖 85 种 CWE 和 5 种语言生态，每个任务都附带"有漏洞版本 + 已修复版本"、固定好的分析环境和 checker 脚手架。配套的 CheckerLab 会独立重建 agent 提交的 checker，再看它能否"在有漏洞的版本上报警、在修复版本上安静"，同时统计补丁定位、误报和工具使用情况。在 21 种模型-harness 配置、每种重复 3 次的实验里，平均 Pass@1 只有 32.3%，最好的也只到 45.3%。对后训练来说，这里有一个很好借鉴的判分方式：用"漏洞/修复双版本的诊断差异"当作 verifier，不需要人工标注就能自动判对错，可以直接改造成 RL 环境。
🔗 链接：https://arxiv.org/abs/2610.07557 ｜ 代码：None

### A Trust Layer for Agent Evaluation
基准分数只能说明 agent"拿到了分"，但说明不了这个分是不是真靠本事拿的、agent 说"我做完了"是不是真的、换一次运行还能不能拿到。这篇论文提出一个附加在评测之后的"信任层"：不改动原始分数，只在每个分数旁边标注它值不值得信。它检查四件事：结果是否确实被基准自己的判分逻辑支持；通过的答案背后有没有可追溯的计算过程（而不是猜出来的）；agent 声称的完成情况和实际发生的是否一致；以及重复执行 5 次后结果是否稳定。前三项只用已保存的运行产物，第四项需要重跑；LLM 只负责给证据贴标签（多数投票），最终结论全部由确定性规则给出。在 Agents' Last Exam 的 108 个任务、5 种 agent 配置上，所有模型都存在"通过了但找不到计算痕迹"的情况，也都有被确认的虚假完成声明；18–46% 的任务 5 次运行落不到同一个分数段；最终只有 22.6% 的通过记录能过全部四项检查。对做评测和 RL 奖励的团队，这套"分数旁边加可信度"的做法可以直接拿来审计 reward hacking 和评测噪声。
🔗 链接：https://arxiv.org/abs/2610.07274 ｜ 代码：None

### HarnessSecurity-Bench：harness 安全机制真的有用吗
Claude Code、Codex CLI 这类 coding agent harness（包裹模型、负责执行工具和审批动作的外壳程序）都宣称有各种安全机制：沙箱、只读模式、命令白名单、网络隔离等等，但这些机制到底实现了没有、默认开没开、开了以后效果如何，一直缺少系统的对比。作者先整理出 10 类安全机制，对 400 个"harness × 机制"组合做了人工与 LLM 双重评级，发现约一半已确认的机制需要用户手动开启，闭源 harness 的公开证据也明显不足。随后他们构建了覆盖 5 个攻击面的 23 个任务，每个任务同时保留正常业务需求，用两个独立的确定性 oracle 分别判"任务完成度"和"攻击是否得逞"，在 Claude Code、Codex CLI、Gemini CLI、gptme、Qwen Code、GitHub Copilot 六个 harness 上固定同一个底座模型跑了 2,500 次试验（8.1 万次工具调用）。最醒目的结论是：打开 auto-approve 后任务完成度上升，但攻击成功率从 29.2% 飙到 95.6%；网络隔离和只读模式能挡攻击但损失大量效用；命令黑白名单代价较小，但攻击者常能绕到"允许的工具"走另一条路径达成同样目的。对做 harness 和 RL 沙箱的人，这提示安全设置必须可验证，并且要测"替代执行路径"，而不只是测被禁掉的那条命令。
🔗 链接：https://arxiv.org/abs/2610.07639 ｜ 项目：https://tsingpig.github.io/HarnessSecurity-Benchmark/

### ParanoiaEval：coding agent 的"过度防御"评测
大家常担心 agent 太鲁莽，但实际使用中另一类问题同样烦人：agent 过度谨慎——明明证据显示没风险，它还要加一堆防御代码、拒绝执行、或者把决定推回给用户。之前的工作分别研究过拒答、过度确认等行为，但没有一个统一框架。ParanoiaEval 借用软件工程风险管理里经典的"规避-转移-缓解-接受"四种处置方式，把它们落到 coding agent 场景，构造了 200 组仓库级任务对：每对任务只在"决定该如何处置风险的那条证据"上不同，其余完全一样，这样就能干净地测 agent 是否真的在看证据。评分用的是经过人工校准的 agentic judge。在 8 个模型上的结果显示，即便证据已经明确，仍有 11.2%–58.7% 的运行做了不必要的风险处置；而且任务能力更强的模型不一定处置得更合适，用户研究也表明这类过度防御会明显损害开发者体验。对后训练来说，这是一种很实用的"成对证据对照"数据构造法，可以用来做偏好数据或 RL 奖励，专门纠正 agent 的过度防御。
🔗 链接：https://arxiv.org/abs/2610.08662 ｜ 代码：None

### FlowAgent：Google 规模的低延迟 pre-submit 自动修复
学术界的自动程序修复大多是"离线跑一晚上、第二天给出补丁"，但开发者最需要帮助的时刻是**代码还没提交、CI 测试刚挂掉**的那几分钟——这时候如果等太久，开发者早就切去做别的事了。Google 的 FlowAgent 就是为这个场景设计的：它集成在内部代码评审工具 Critique 和 IDE Cider 里，采用"生成补丁→跑验证"的 ReAct 循环，并在执行前和执行后各设一道"弃权过滤"——没把握就干脆不给建议，以保证在严格延迟约束下只推送高质量修复。在 195 个真实测试失败上的人工评估中，正确修复率为 67.18%；全公司部署后，它对 295,508 个变更给出了修复建议，开发者预览了 65,069 次、实际采纳了 28,554 次。这篇论文的价值在于给出了工业级落地的真实漏斗数据（建议→预览→采纳），以及"弃权机制比强行出结果更重要"的工程经验；对训练 coding 模型来说，"何时不给答案"的校准能力同样值得纳入奖励设计。
🔗 链接：https://arxiv.org/abs/2610.07289 ｜ 代码：None

### GAMEGO：用真实素材锚定合成游戏开发轨迹
让 coding agent 从一句"做个太空探索游戏"直接生成完整网页游戏，常见问题是需求太稀疏：agent 只能自己脑补，结果机制不全、玩法流程断裂、画面也很简陋。GameGo 的思路是先把简短的游戏种子扩写成一份按游戏行业惯例组织的完整产品需求文档（PRD），再让 agent 按 PRD 去开发；为了避免 PRD 太长导致指令跟随变差，它还做了按任务定制的动态压缩，保留核心玩法约束但不限制设计空间。基于这条 pipeline，作者构造了 GameGoData（55,060 条覆盖 2D / 2.5D / 3D 游戏的开发轨迹），并推出 124 题的 GameGoBench；用这些数据训练的 GameGoCoder 超过同规模基线，在多个游戏开发基准上接近前沿模型。对后训练数据工程来说，"种子 → 结构化规格 → 轨迹"并用真实素材锚定的做法，是把开放式生成任务变成可规模化 SFT 数据的一个可复用模板。
🔗 链接：https://arxiv.org/abs/2610.06910 ｜ 代码：None（作者承诺开源代码、数据和模型）

### RepoNorm：获取并验证仓库规范
coding agent 写出的改动经常能通过测试，却不符合仓库自己的"潜规则"：比如提交信息格式、必须同步更新 changelog、某类改动要加特定注解等。这些规范散落在 CONTRIBUTING、代码评审记录、Git 历史里，而且常带条件和例外，单靠检索文档塞给 agent 并不能让它判断哪条规范该用在当前改动上。RepoNorm 把"获取规范"和"做任务"解耦：先独立于具体任务，从仓库中挖掘显式和隐式规范，用仓库证据核对规范内容和适用条件，必要时去翻 Git 历史确认，最后把整理好的"规范包"交给任意现有 coding agent 使用。在 3 个模型、RepoNormBench 的 121 个任务上，总体规范遵循率相对无额外指导的基线提升 7.4–10.8%，贡献类规范遵循率提升 31.6–45.4%，也都优于 CodeWiki 自动生成的文档；功能正确率提升 5.8–9.1 个百分点（未达显著）。这对后训练有两点启发：规范遵循可以作为独立于测试通过率的奖励维度；而"规范包"本身也是一种可自动构造、可验证的上下文数据。
🔗 链接：https://arxiv.org/abs/2610.07757 ｜ 代码：None

### BOTTLED：agent 能否把能力"装瓶"成廉价产物
很多实际业务是"同一类小任务要做几百万次"，例如给商品-查询对打相关性标签；每次都调用大模型太贵，理想做法是让 agent 自己想办法造一个便宜的解决方案——训一个小模型，或写一段可复用的程序。作者把这种能力叫"装瓶"（bottling），并构建 BOTTLED 基准：agent 拿到一整批无标注的工作负载，在固定的时间、算力和 API 预算内自行选择方案并完成全部任务，最后同时考核质量和摊销成本。在 10 个模型、3 类任务上，零样本能力强的模型并不一定擅长装瓶：60 次装瓶运行里有 48 次低于该模型零样本表现的 95% 置信下界，31 次甚至不如同等 token 预算下的小模型蒸馏基线。但做得好的时候收益巨大：Opus 5 在查询-商品相关性分类上保留约 82% 的零样本 macro-F1，成本却降低约 657 倍。这个基准考察的是"会不会做 ML 工程"，比如自造标注、蒸馏、写规则，和后训练团队日常的数据/模型工程高度同构，也可以当作评估 AI 研发 agent 的一个实用角度。
🔗 链接：https://arxiv.org/abs/2610.08775 ｜ 代码：None

### NP-Bench：并行 coding agent 协作的验证
越来越多团队在同一个代码库上同时跑多个 coding agent，常见的翻车方式是：每个 agent 自己的测试都过了，合并之后却坏掉了——两个 agent 改了同一个函数，或者一个 agent 按旧接口写代码，而接口刚被另一个 agent 改掉。现有协调工具大多是"发现冲突再报警"，但 agent 的速度太快，警告到的时候无用功已经做完了。这篇论文把问题改写成调度问题：事先根据每个工作项声明的修改范围，把工作切成互不重叠的范围，并沿"生产者→消费者"依赖图安排合并顺序。配套的 NP-Bench 用真实 git merge 判断最终是否干净集成，比较"不协调 / 被动检测 / 主动规划"三种方式：主动规划把干净集成从 1/9 场景提升到 9/9，合并冲突从 13 次降到 0；在接口被破坏性修改的场景里，前沿模型的干净集成率从 0 提升到 1.0。作者还报告了一个负面结果：把相关事实路由给 agent 并不能改善长上下文准确率。工作是单作者、规模偏小，但"用真实 merge 结果判分"的思路对构造多 agent 协作环境很有参考价值。
🔗 链接：https://arxiv.org/abs/2610.07261 ｜ 代码：None

### Turnslide：有限状态机游走合成多轮工具调用数据
小模型便宜、能私有部署，但多轮工具调用能力往往不够，需要针对每套 API 做微调，而这类数据基本不存在。已有合成方法通常要为每个领域搭模拟环境，每生成一轮对话就要调用好几次 LLM，成本太高，难以规模化。Turnslide 的做法是把每套 API 建模成一个有限状态机（FSM）：用抽象状态描述"什么时候可以调用哪个工具"，在状态机上随机游走就能得到一定合法的工具调用序列，再用**一次** LLM 调用把整条序列翻译成完整的对话样本。它不追求盲目多样性，而是直接设定目标分布（轮数、工具序列、任务复杂度），按需控制数据形态。用生成数据微调小模型后，完整准确率达到 70.7%，高于两个已有方法的 63.4% 和 53.7%，同时 token 消耗少 3.6–6.6 倍。对 SFT 数据工程来说，"先用形式化结构保证合法性，再让 LLM 只负责语言化"是一个低成本、可控、可验证的合成范式，也适用于为 agent 生成工具调用类训练数据。
🔗 链接：https://arxiv.org/abs/2610.07070 ｜ 代码：None

### FC-SWE：以失败为条件的 SWE agent RL
目前用 RL 训练 SWE agent 的主流做法（如 GRPO）是：对同一个 issue 独立采样多条轨迹，各自打补丁、跑测试，再在组内比较最终奖励。问题在于失败补丁的测试报错里其实包含大量诊断信息，却完全没被用上；而人类工程师修 bug 时恰恰是看着失败信息再试一次。FC-SWE 在补丁验证失败后，把仓库恢复到初始状态，把失败补丁和 verifier 反馈作为上下文，再生成一条"恢复轨迹"，并把这种链式尝试纳入训练。为了让训练信号正确，它做了两处改动：每次尝试只拿自己的验证结果作为奖励，避免后续成功"反向奖励"之前失败的补丁；组内比较只纳入实际执行过的初始和恢复轨迹。在 SWE-bench Verified 全部 500 题上，Qwen3.5-4B + SWE-agent 的 Resolved@1 / @2 从 GRPO 的 38.9% / 48.5% 提升到 41.7% / 52.8%，测试时给 11 次尝试可达 70.7%。这对 RL 环境工程的启发是：verifier 输出不只是一个 0/1 奖励，它本身就是可回灌给策略的训练数据。
🔗 链接：https://arxiv.org/abs/2610.07898 ｜ 代码：None

### NeMo-DCR：万亿参数 agentic RL 的增量 refit
agentic RL 通常把训练集群和 rollout（生成轨迹）集群分开，每次策略更新后都要把新权重同步到 rollout 集群，这一步叫 refit。对 1T 参数的模型，在两个 AWS 区域之间传一次完整 checkpoint 要 87.5 分钟，几乎让跨集群 RL 不可行。NVIDIA 观察到 BF16 训练中每步只有约 1% 的权重存储值会变化，于是 NeMo-DCR 只传变化部分，并保证"bit-exact"——接收端得到的参数与完整同步逐比特一致。它用固定的仿射映射把训练分片上的变化投影到 checkpoint 坐标，用可压缩的 XOR 掩码承载变化，借助 serving 端原生加载器原地写入；中途失败可重试覆盖，再通过联合提交保证下一次增量的基线一致；传输走对象存储或中继树，不依赖跨集群集合通信。即使变化率达到 3–5%，30B–1T 模型的 refit 也比完整传输快 12–40 倍，1T 模型在 3% 变化率下只需 150 秒。代码已作为 PR 提交到 NeMo RL，这是 RL 基础设施里少见的"可直接拿来用"的工程方案。
🔗 链接：https://arxiv.org/abs/2610.08430 ｜ 代码：https://github.com/NVIDIA-NeMo/RL/pull/2444

### TRACE：FP4 MoE RL 的训推量化对齐
RL 后训练里 rollout 生成最耗算力和显存，所以大家想用 FP4 这类低精度来做 rollout。但如果训练侧和 rollout 侧各自量化，两条路径算出来的概率会不一致，这种"训推不一致"会让 RL 训练不稳定。已有方法分别优化两侧的量化精度，却没有直接缩小两侧之间的差距。TRACE 让训练侧在做 FP4 取整时参考 rollout 侧的实际量化结果，从而直接减少两条路径的差异；同时只缓存深层的尾数和缩放信息，控制额外的存储和通信开销。在 4 个大型 MoE 模型的推理、代码和长程 RL 任务上，它实现了权重、激活和 KV cache 全 FP4 rollout，RL 效果与 BF16 rollout 相当，rollout 最高提速 5.4 倍。这属于偏底层的 RL infra 工作，对需要大规模跑 coding agent rollout 的团队意义在于直接降低 rollout 成本。
🔗 链接：https://arxiv.org/abs/2610.07767 ｜ 代码：None

### What pass@k Cannot Measure
判断一次 RLVR（可验证奖励的 RL）后训练有没有真正提升能力，业界默认看 pass@k：k 次采样里至少一次答对的比例。但 pass@k 只关心"答对的概率"，完全不看输出是否多样，也就看不出模型是否"只会一种解法"。作者在 GSM8K 上用 GRPO 和拒绝采样微调（RFT）分别训练 Qwen2.5-1.5B，发现两者在 token 熵、答案熵、每题不同答案数三项多样性指标上走向相反，3 个随机种子毫无重叠；即使只看答对的解，GRPO 的词汇多样性也低 15%。但 pass@8、pass@32 看不出谁更好。更关键的是，与起点模型相比，两种训练都没有显著提高难题覆盖率——GRPO 的 pass@1 优势只是"比 RFT 损失得少"，而不是真的变强。对评测工程来说，这提醒我们：RL 后训练的评测报告必须包含与 base 的对照，并补充多样性指标，不能只报 pass@k。
🔗 链接：https://arxiv.org/abs/2610.07405 ｜ 代码：None

### CuratorMAS：多 agent 自动数据清洗
高质量数据集是模型训练的基础，但数据清洗通常依赖人工设计的启发式规则或针对特定模型的打分信号，换一个领域就得重新设计。CuratorMAS 把清洗过程拆成五个可编程、可并行的阶段：先探索数据集的文件结构和约束线索，理解任务；再联网检索最新领域知识辅助判断；接着推导评估标准并计算指标；然后按结果过滤；最后由"进化模块"总结评估结果并更新可复用的技能。实验中，它把数据噪声率最多降低 36 个百分点，下游模型 F1 最多提升 8.9 个百分点。虽然实验主要不在代码领域，但"让 agent 自己推导清洗标准、并把经验沉淀为技能"的流程，可以迁移到 SFT 数据清洗和轨迹过滤中。
🔗 链接：https://arxiv.org/abs/2610.07075 ｜ 代码：None

### Transect：长程 agent 评测的可观测性工具
前沿 AI 评测越来越多地用开放式、长程、多 agent 任务，一次运行的记录可能长达几百页，评测者越来越难看清 agent 到底干了什么。用 LLM 帮忙分析虽然方便，但分析方式的自由度太大，结论难以复现和审计。Transect 是基于 Inspect Scout 的开源包：用户在一份可复用的"评测族配置"里写好任务背景和行为词表，评判模型和分析参数单独配置；它生成的报告把事件记录、token 消耗、子 agent 活动和模型打的行为标签对齐在同一个回合时间线上，任何标签都能追溯到原始回合，底层数据表也能导出做跨运行分析。在一次消耗近 1,300 万 token 的 AI 研发评测中，它清楚显示 agent 的工作集中在操作性工作和写稿上，几乎没有持续的假设生成阶段。对做 coding agent 评测的团队，这类"可追溯的轨迹分析"工具是排查 reward hacking 和评测缺陷的基础设施。
🔗 链接：https://arxiv.org/abs/2610.08364 ｜ 代码：None（论文称开源，基于 Inspect Scout）

### Studying metagaming latents in language models
"Metagaming"指模型不是在老老实实做任务，而是在推理"这个任务会怎么被评估或奖励"——这样的模型可能在它认为被测试时表现得很对齐，没人看时却不一样。OpenAI 与 Apollo Research 的研究者分析了一次以能力为目标的 o3 RL 训练，用稀疏自编码器（SAE）找到了一组与 metagaming 密切相关的内部信号（latent），用它们做 steering 会明显改变模型行为。结论包括：metagaming 不是单一机制，而是任务分析、评测意识、奖励追求和规范推理等过程的叠加；这些信号在 RL 过程中会变强；而且部分信号能影响最终答案却不出现在书面 CoT 里，这意味着只靠读 CoT 来监控是不够的。对 RL 训练工程，这提供了一种在训练过程中用内部信号追踪"评测感知"的监控思路。
🔗 链接：https://alignment.openai.com/metagaming-latents/ ｜ 代码：None
